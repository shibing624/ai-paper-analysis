# 别再给 Deep Research 报告打总分了：DRBench Pro 用一棵知识树，把「覆盖」拆成广度和深度

你有没有碰到过这种事：两份研究报告，一份把十个方向都点到了但每个都只写两句，另一份只啃三个方向却顺着线索一路追到第三层细节。你让评委打分，两份都给了「内容比较全面，8 分」。

然后你就卡住了——这两个 8 分，到底哪个更「会做研究」？

我前阵子在调一个检索报告生成链路时就被这个卡过。reward 曲线挺好看，人工抽查却发现模型越来越爱铺方向、越来越不愿往下追。想加个惩罚项，又发现根本说不清「铺得广」和「挖得深」该怎么分别计量。看到 DRBench Pro 的时候，我的第一反应是：哦，原来可以把评分标准本身挂到一棵树上。

---

## 核心摘要

评 Deep Research 报告，老办法是给「整体质量」打分，或者拿一串细则数覆盖率。毛病在于，事实性核查抓不住**漏掉**的知识，而扁平的细则计数会把「广而浅」和「窄而深」压成同一个数。这篇论文换了个思路：从 Wikipedia 长出本地知识树，采样子图，用同一份子图既生成研究问题、又给每条边生成一条有证据出处的评分细则；评测时把细则判定回填到树上，自底向上聚合出**广度**（覆盖了多少主要研究方向）和**深度**（沿相关知识链走了多远），两者取几何平均作为总体覆盖率。规模是 24 个领域、144 个案例、44,102 条细则，16 个 Agent 里最好的 Claude Opus 5 只拿到 57.04%。

我读下来的判断：这不是模型能力的突破，是评测基础设施的一次结构升维，值钱的地方在于把「覆盖」从一个形容词变成可分解、可追溯的量。但 57.04% 这个数别急着当成「前沿模型只懂一半知识」——后面会说到，它更像一把刻度由构建模型决定的尺子。

## 🎯 问题动机：为什么「整体打分」不够用

开放式研究问题没有标准答案。你可以写十份都成立、但侧重完全不同的报告，单一参考答案根本装不下。于是评测界分成了几条路子：

事实性核查那条路能揪出「哪句话没依据」，但对「该提的知识压根没提」无能为力——报告里没有的句子，你没法判它错。另一条路是请专家写参考报告、列关键事实、编任务细则，从覆盖度、事实性、引用质量、行文几个维度打分。听着靠谱，代价是每加一个领域都得重新请人，细则是手工摊平的清单，一条条查也贵。

更要命的是第三层问题，也是这篇论文真正咬住的点：**哪怕细则全是自动生成的，一做扁平聚合，细则之间的结构关系就丢了**。你数出「满足 152 条 / 共 306 条」，得到 0.497，然后呢？这 0.497 是均匀撒在十个方向上，还是死磕两条链？看不出来。作者在引言里把话说得更狠：一个知识条目的价值，取决于它有没有连到报告里已经覆盖的相邻知识；而固定权重的拓扑评分不会随报告实际覆盖的交互关系调整，完整路径检查也只能给「有/没有证据」的二值判断，给不出「链子走到一半断了、还剩多少深度」的渐变分数。

说到这个，得把同期的几个前置工作摆一摆，才能看清 DRBench Pro 卡在哪个位置：

| 基准 | 核心做法 | 覆盖怎么评 | 主要瓶颈 |
|---|---|---|---|
| DeepResearch Bench（RACE / FACT） | 100 个博士级任务、22 领域；参考报告 + 自适应标准 + 动态权重 | 覆盖度、深度、指令遵循、可读性 + 引用准确性 | 依赖专家写参考与标准，扩域成本高；维度里「深度」仍是整体印象分 |
| ResearchRubrics | 101 个 prompt、2593 条**全人工**细则，投入 2800+ 小时 | 必选/可选/负分细则，逐条判定 | 任务量小、只评三个商用系统；作者实测「二值判定比三值更可靠」 |
| 树 / DAG 类方法 | 用图组织多跳问题、追踪证据来源、传递细则权重 | 结构服务于监督、任务完成或证据溯源 | 结构没被保留到**覆盖聚合**阶段，广度与深度没被拆成独立量 |
| DRBench Pro | Wikipedia 知识树 + 子图采样，查询与细则同源生成 | 自底向上按树结构聚合出广度 / 深度 / 几何平均 | 单一英文知识源、构建模型敏感（后文细说） |

论文 Table 1 用五个维度把自家和九个代表性基准摆在一起对比，只有 Ours 一列全是 ✓：自动化构建、结构化参考空间、结构对齐的评测单元、拓扑导出的广度–深度、以及把覆盖当**首要**评测目标。这张表有点自评表的味道，但「Coverage as Primary Target」那一列确实只有它是实心勾——其余九家都是把覆盖塞进一个更大的评分篮子里的。这个区分我觉得是成立的。

## 🏗️ 方法核心：把评分标准种在一棵树上

![图 2：DRBench Pro 全流程——A 构建 Wikipedia 本地知识图，B1 由子图生成研究查询，B2 每条边生成一条细则，C 智能体产出报告后由 Judge 逐边判定并做拓扑聚合](https://arxiv.org/html/2611.34852v1/main_method_overview.png)

*图 2（论文 Figure 2）：这是全篇最该先看的一张图。A 段从 24 个领域图标出发，选一个 Wikipedia 根实体（图里示例是 Whale shark），沿链接做多跳扩展，长出「Filter-feeding carpet shark」「Table Bay」这类关联页面，得到本地知识图，再采出 S1/S2/S3 三个子图。B1 用子图合成一个自然语言的 Query。B2 给子图里每条边配 Source page + Target page 的证据，让 LLM 写出一条 Rubric，汇成隐藏的细则集 R。C 段把 Query 丢给被测的 Deep Research Agent 出报告，Judge LLM 做逐边覆盖判定，把绿点（Covered）红点（Uncovered）回填到树上，最后用 Bottom-up Recursive Aggregation 算出 Breadth B、Depth D，以及 $S=\sqrt{B\cdot D}$。整条流水线的关键在「同源」：查询和细则来自同一份子图。*

### 一句话讲清核心 idea

以前是先有任务、再请人（或让 LLM）补一份评分清单，两者容易错位。这里是**先有知识结构，再从同一块结构里同时长出题目和答案钥匙**。题目圈定的知识范围，就是细则要查的知识范围；每条细则在树上的位置（它是哪条边、离根几跳、父节点是谁）从生成那一刻起就被记录下来，评测时原样用上。

### 第一步：知识树怎么长出来

领域取自 WebOrganizer 的全部 24 个主题分类，每个分类挑 2 个根实体，共 48 个。挑根的条件挺实在：条目本身足够详细、能被稳定解析、外链够多能撑住扩展。比如 Games 域选了 Roguelike 和 Games Workshop，Health 域选了 Ignaz Semmelweis 和 John Snow，Politics 域是非对齐运动和《怀唐伊条约》。

从根开始按 Wikipedia 链接做广度优先扩展，节点是实体，边是由链接锚文本和上下文支撑的关系。为了让每条边有唯一位置，把扩展结果组织成**有根树**：非根节点只有一个父节点，从根到它只有一条路径。距离按跳数算，扩到 3 跳就停。规模控制上，根保留 50 个子节点、其余节点最多 5 个子节点，过滤掉无效和重复候选后，交给 Claude Opus 4.8 按「与当前实体的相关性 + 对研究任务是否有用」挑选邻居。最后 48 棵树平均每棵约 1.5K 节点、1,528.6 条边（区间 1,365–1,550）。

我想停一下说个细节：为什么要强行压成树而不是留着图？因为「唯一路径」这个性质是后面所有公式的地基。图里一个节点可能有多个父节点，那「这条知识属于哪个研究方向」「它离根几跳」就会有多解，广度深度没法定义。这个取舍挺干净，代价是把 Wikipedia 天然的交叉引用砍掉了一部分——后面聊局限时会回到这点。

### 第二步：采样子图，一个子图就是一个 case

一整棵树覆盖的材料远超单次研究请求能合理瞄准的范围。于是按「分支」采样：一个分支 = 根的某个子节点 + 它的全部后代，代表一个研究方向；分支内部的路径就是知识链。每个 case 保留根 + **10 条完整分支**，且不做截断，深层关系全留着，否则没法学「沿链走多远」。

为了让范围自洽，Claude Opus 4.8 一次联合挑出三组分支，依据候选实体的页面摘要、与根的关系、后代信息；组内分支要求对同一个研究任务形成互补视角，三组之间不共享根分支。结果是每根 3 个 case、48 根共 144 个 case。落到数据上，每个 case 子图平均 306.3 条边（也就是 306 条细则，区间 236–310），10 个研究方向固定，最大跳数固定为 3。

### 第三步：查询与细则同源生成

同样用 Claude Opus 4.8，喂进去根实体 + 采样出的知识范围，让它写一段自然的研究请求。提示词里明确压着两件事：别把隐藏实体列出来，别把子图改写成 checklist。目的是让智能体去「调查一个主题」，而不是照着一份答案提纲填空。

细则这边，**每条保留边配一条 rubric**，问的是「报告有没有覆盖源实体与目标实体之间的关系」。生成时只允许用给定的证据：两页的页面摘要、锚文本所在句、相关段落、可得的反向链接上下文。这条约束我很喜欢——它把评分要求钉在可查的文档内容上，而不是模型自己脑补出来的「应该有」。每条细则还偷偷记下自己在树上的位置和跳数，但这些标注放在细则文本之外，被测 Agent 只拿得到 Query，参考树和细则全程隐藏。

看下论文附录里 Roguelike 那棵树的真实细则长什么样：

| 编号 | 关系 | 细则要求（摘译） | 判定 |
|---|---|---|---|
| R1 | Roguelike → Rogue | 报告明确说明或清楚转述：1980 年的游戏 Rogue 是 roguelike 类型的前身与命名来源 | ✓ |
| R2 | Rogue → Permadeath | 报告说明 Rogue 实现了永久死亡，角色生命归零即死亡 | ✓ |
| R3 | Permadeath → Save scumming | 报告说明玩家可借备份/恢复存档绕过永久死亡，这种叫 save scumming 的做法被视为作弊 | ✓ |
| R6 | Hack → 跨平台移植 | 报告说明 Hack 的跨平台移植及其图形 tile 的使用 | ✗（报告只谈了 Beneath Apple Manor 的图形 tile） |

R6 那个 ✗ 挺说明问题：它爸（上层关系）覆盖了，报告也聊了「图形 tile」，但没聊到 Hack 这个具体对象，照样不给分。作者的意思是要靠这种细粒度把「看着像覆盖了」和「真的覆盖了」分开。

### 第四步：把判定回填到树上，自底向上算两个数

Judge 给每条隐藏细则三档判定：Satisfied / Partially Satisfied / Not Satisfied。算分时做二值化，只有 Satisfied 记 1，另外两档都记 0（记作 $x(v)\in\{0,1\}$，$v$ 是边指向的目标节点）。

三个量里最外层这个最直观：

$$S_c=\sqrt{B_c D_c}$$

几何平均而不是算术平均，意思是广度或深度任意一边塌了，总分跟着塌。项目页给的离线示例很适合校准直觉：Breadth 0.84、Depth 0.4375，算术平均是 0.639，几何平均只有 0.6062——浅那一半把分数拽下来了。你想想看，一份报告十个方向全点名、但每个方向都只写了标题，不该拿高分；几何平均就是干这个的。

往里一层是两条递归。叶子节点直接取 $B(v)=D(v)=x(v)$；非叶子节点：

$$B(v)=\beta x(v)+(1-\beta)m_B(v),\qquad D(v)=\alpha x(v)+(1-\alpha)d(v)\,[\eta+(1-\eta)x(v)]$$

$B$ 里的 $m_B(v)$ 是子节点广度均值。默认 $\beta=0.60$，意思是「当前这条关系覆盖了」只占六成，剩下四成看后代铺得怎么样——**浅层关系漏了，靠深层覆盖能补回来一部分**，这正好对应广度「方向是否被覆盖」的语义。作者管它叫 local-descendant coverage fusion。

$D$ 更要讲究。$d(v)$ 是子节点深度的聚合值，用的是排序衰减（RankAgg）：把子树的深度从高到低排好，按 $\rho^{i-1}$ 的权重加权平均，默认 $\rho=0.50$。这么做的理由是「一条链挖得深」本身就很有说服力，额外的链有贡献但边际递减。方括号里的 $[\eta+(1-\eta)x(v)]$ 是连续性因子，$\eta=0.75$：当前边覆盖了，后代深度全额计入；当前边断了，后代证据只按 0.75 折价保留，不直接清零。$\alpha=0.25$ 则给「当前这条关系自己被覆盖」留一份独立贡献。

四个超参放一起：

| 参数 | 默认 | 作用 |
|---|---|---|
| $\beta$ | 0.60 | 广度递归里当前关系覆盖的权重，$1-\beta$ 给子树广度均值 |
| $\alpha$ | 0.25 | 深度里当前边直接贡献的权重 |
| $\eta$ | 0.75 | 当前边未覆盖时，对后代深度的保留因子 |
| $\rho$ | 0.50 | 深度聚合中相邻排序权重的比值 |

case 级广度 $B_c$ 是 10 个分支分数的算术平均（方向等权，避免细则多的分支霸榜）；case 级深度 $D_c$ 对分支做 RankAgg（强调挖得深的方向）。三个指标各自在 144 个 case 上取均值。

坦率讲，这套公式不算漂亮，甚至有点「手调权重」的味道。但它每一项的动机都能对上一句人话：广度要允许后代补偿，深度要奖励连续、对断点折价、对多条链边际递减。比起直接拍一个「深度 = 三跳细则命中率」，确实更贴近「做研究」这件事的形状。

## 🧪 实验结果：16 个 Agent，最好 57.04%

看到 57.04 这个数我愣了一下。不是因为它高，是因为它低——一个被寄予厚望的前沿 Agent，在别人替它划好的知识范围里，只覆盖了刚过一半的关系。但先别急着下「模型不行」的结论，后面构建模型敏感性那节会把这个数重新解释一遍。

几个不那么显眼、但我觉得更值钱的读数：

**广度和深度的排名是错开的。** 作者说两份榜单「substantially interleaved」。最清楚的例子是同名模型换配置：Qwen3.8 Max 在原生搜索下总体 36.53，换到本地研究框架变成 47.94，其中广度涨了 15.54 个点、深度只涨 6.28 个点。同一家族、同一名字，只因为检索和编排方式不同，探索形态就变了——一个更爱铺方向，另一个差异集中在深度上。Perplexity 产品线里也有类似对照：Sonar Deep Research 深度更高、广度略低于 Sonar Reasoning Pro。

**同分不同策略有实证。** 项目页给的 Lew Grade 案例比示意图更有说服力：Perplexity Sonar Deep Research 和 Grok 4.5 总体覆盖 38.83 对 40.31，几乎一样；拆开看是广度 27.33 / 深度 55.19 对广度 54.48 / 深度 29.82，几乎完全镜像。一个一路往深里钻，一个铺满了方向。要是只报总分，这两份报告的差别就彻底消失了。

**领域之间差得离谱。** 按 agent–domain 六案平均，覆盖率最高的是 Software Development 53.69、Science & Technology 52.36、Health 50.10；最低是 Industrial 28.58、Food & Dining 35.45。Claude Opus 5 在 23 个领域领跑，Literature 那格被 o3 Deep Research 拿走。我怀疑这跟「Wikipedia 上哪些主题的实体链接更稠密、更容易长成三跳树」有关，而不只是模型偏科。论文没往这个方向拆，可能我的理解有偏差，但这个混杂因素挺值得追一下。

**数据本身质量过关。** 144 条查询人工审过三轮：研究价值、公开可答性全部 Good；查询–领域匹配 141 Good、3 Medium，那 3 个是子图采样自然带来的跨领域重叠，作者说依然连贯可答。防泄漏查得更细：每个领域抽 1 个 case，把查询和子图里每个非根实体标题比对，共 7,385 次比较，命中的 34 个是「table」「level」这类通用词重叠（不算泄漏），确认泄漏 8 处，占 0.108%，且第一跳一个都没有。这个自查做得挺扎实。

## 🔬 可信度验证：这篇论文最硬的部分

评测类论文最怕自说自话：你说这个指标好，凭什么？作者用了四组验证，我把关键数字摆出来。

**判官跟人对不对得上。** 10 位博士级标注员、12 份报告、3,695 条「报告–细则」对，每条两人独立初标、第三人仲裁，产出人工参考（论文 Table 6）：

| Judge | 二值 Macro-F1 | 三值 Macro-F1 |
|---|---|---|
| Gemini 2.5 Pro | **0.893** | 0.806 |
| DeepSeek V4 Pro | 0.865 | 0.630 |
| Qwen 3.8 Max | 0.840 | 0.718 |

三个判官都是二值优于三值，和 ResearchRubrics 报告的「二值比三值可靠、能涨约 20 个点」结论对上了。所以正式评测选 Gemini 2.5 Pro，把它的三档输出折成 0/1。这算是个挺聪明的取巧：与其纠结「部分满足」怎么给分，不如承认这一档本来就判不准，直接归到未覆盖。

![图 3：人工标注界面，标注员对每条报告–细则对给出 Satisfied / Partially Satisfied / Not Satisfied](https://arxiv.org/html/2611.34852v1/figures/human_annotation_interface.png)

*图 3（论文 Figure 12）：界面左侧是报告列表（R01 Black Mountain College、R03 Roguelike 等），中间是带高亮引用链接的报告正文，右侧是当前细则的原文与出处。示例那条是「报告应明确说明或清楚转述 Roguelike 类型受 D&D 等桌上角色扮演游戏影响」，下面三个单选：Not satisfied / Partially satisfied / Satisfied。右侧还显示 R03 的 308 条细则已判 308 条。看得出标注是逐条对着报告段落做的，不是凭印象给整份报告打分。*

**指标跟专家排序对不对得上。** 3 位专家对 6 个 Agent 在 12 个 case 上的 72 份报告按 1–10 打广度、深度、总体分，取均值做参考，再算各打分方案的 Kendall $\tau_b$ 与 Spearman $\rho_s$（论文 Table 5 / 附录 Table 15）：

| 维度 | 打分方案 | $\tau_b$ | $\rho_s$ | 并列率 |
|---|---|---|---|---|
| 总体 | 论文最终指标 | **0.751** | **0.833** | 0.56% |
| 总体 | 层级均衡覆盖 | 0.615 | 0.718 | 0.56% |
| 总体 | 扁平覆盖 | 0.508 | 0.597 | 4.44% |
| 广度 | 论文最终指标 | **0.696** | **0.777** | 0.56% |
| 广度 | 分支覆盖 | 0.533 | 0.592 | 26.11% |
| 广度 | 去掉后代融合（$\beta\to1$） | 0.643 | 0.714 | 16.11% |
| 深度 | 论文最终指标 | **0.727** | **0.813** | 0.56% |
| 深度 | 路径内成对覆盖 | 0.577 | 0.664 | 2.22% |
| 深度 | 去掉连续性折扣（$\eta\to1$） | 0.668 | 0.761 | 0.56% |
| 深度 | 断点后不给后代积分（$\eta\to0$） | 0.653 | 0.755 | 1.11% |
| 深度 | 去掉当前边贡献（$\alpha\to0$） | 0.583 | 0.678 | 3.33% |

这组数字是全篇最有说服力的地方。扁平覆盖 0.508 对最终指标 0.751，差了 0.243——「保留树结构」不是包装，是真的把专家眼里的差别捞回来了。还有一个容易漏掉的读数：分支覆盖的并列率 26.11%，最终指标只有 0.56%。粗颗粒方案会把四分之一以上的报告对判成同分，等于丧失区分能力；结构化递归把粒度做细了。四个消融各自掉分，说明 $\beta$ 的后代融合、$\eta$ 的连续性折扣、$\alpha$ 的直接贡献都不是凑数的装饰。

**调参会不会把榜单翻过来。** 四个超参各取高低两档，共 8 组扰动，重算 16 个 Agent 的均值再和默认排名比（论文 Table 7）：广度的 Spearman 至少 0.997，深度至少 0.976，120 个 agent 对里最多出现 2 次「实际反转」（要求两次配置下分差都超过 0.5 个点）。深度对 $\alpha$ 最敏感，从 0.25 抬到 0.40 出 1 次反转、压到 0.10 出 2 次——因为 $\alpha$ 就是「当前边自己算多少分」和「后代算多少分」的平衡旋钮，两个极端都不符合作者对深度的定义。这个解释我认。

**换个模型来造基准会怎样。** 这节是我最想让大家看的地方。作者拿 Kimi K2.6 重新构建参考图、查询和细则，在 10 个 case 上让 Claude Opus 5 和三个原本接近的对手重跑（论文 Table 8）：

| 模型 | 原版总体 | Kimi 构建版总体 | 原版平均名次 | Kimi 版平均名次 |
|---|---|---|---|---|
| Claude Opus 5 | 56.84 | **40.20** | 1.2 | 1.8 |
| Grok 4.5 | 51.25 | 37.63 | 2.5 | 1.9 |
| GPT-5.6 Sol | 46.65 | 34.21 | 3.0 | 2.7 |
| Sonar Reasoning Pro | 44.09 | 25.84 | 3.3 | 3.6 |

名次大体稳住，Claude 的标准化优势仍在（只是收窄了），作者的结论是「换构建模型家族，优势可以延续」。但等等——**绝对分数从 56.84 掉到 40.20，掉了 16.6 个点**。这说明「57.04% 覆盖率」并不是一个关于模型知道多少知识的客观刻度，它是相对于「Claude Opus 4.8 生成的那 44,102 条细则」的命中率。换一个构建模型，细则的难度、措辞、覆盖偏好全变了，尺子就换了。作者自己也在文末承认构建模型「may still play a role」。

我觉得这不构成致命伤——排名稳定、相对可比，作为榜单够用了。但它明确划出了这个指标的适用边界：**别把绝对分值跨基准、跨版本地横向解读**。看到「57.04%」就感慨「AI 只掌握一半人类知识」，那是把尺子当成了温度计。

## 📊 过程分析：知识是在哪一步丢的

附录里这块内容，工程价值比主榜高。作者搭了个可复现的本地研究框架：固定的英文 Wikipedia 快照 `enwiki-20260701-v1`，只暴露 Search 和 Open 两个操作，关掉厂商原生联网搜索，七个骨干 LLM 共用完全一样的工作流和交互预算。目的不是刷分，是把检索源、工具、流程全钉死，让剩下的差异只反映骨干模型自身的行为。

![图 4：本地研究框架工作流——Planner 把查询拆成三个 Research Unit 并行取证，做一次覆盖缺口检查，必要时补一个 Gap Unit，最后统一综合成报告](https://arxiv.org/html/2611.34852v1/local_research_framework_overview.png)

*图 4（论文 Figure 11）：A 段 Research Planning，Planner 把查询 $q$ 拆成三个互不重叠的目标 U1/U2/U3。B 段 Parallel Evidence Collection，三个 Research Unit 并行跑在共享的 Frozen Wikipedia snapshot 上，各自 Search → Open → 产出 evidence note。C 段 Coverage Completion，把所有笔记汇总做**一次** coverage gap 判断：没缺口就直接进综合，有实质缺口才启动至多一个 Gap Unit 补证据。D 段 Report Synthesis，把原始查询和全部笔记一起喂给 Final Synthesis 出报告。注意「一次检查、至多一个补漏单元」这个预算约束，是让不同骨干公平比较的前提。*

![图 5：七个骨干 LLM 在本地框架下的六项研究过程画像](https://arxiv.org/html/2611.34852v1/figures/research_trajectory_local_observables_en.png)

**更多研究动作 ≠ 更高覆盖。** Horn & Hardart 那个 case 被单拎出来讲（论文 Table 24）：同样的冻结语料、工具、预算下，GLM 5.2 发了 12 次 Search、34 次 Open、检索 112 个页面、烧了 302.9k tokens、写了 2,214 词，总体覆盖 29.19；DeepSeek V4 Flash 只发 9 次 Search、28 次 Open、43 个页面、150.4k tokens、1,372 词，总体覆盖 45.54。作者说 GLM 把一部分力气花在重访已有来源和铺陈背景上了。这个 case 我读得挺舒服——它把「堆算力」和「会选证据」分开了。

**知识在写作环节漏掉一大截。** 把检索阶段和最终报告分开评，发现 47.0% 在检索材料里已完全覆盖的细则，到了报告里就不再完全覆盖；而且跳得越深丢得越狠。按模型看 3 跳知识的保留率（论文 Table 21）：Qwen3.8 Max 65.6%、MiniMax M3 56.7%、DeepSeek V4 Flash 56.5%、GLM 5.2 52.0%、Gemma 4 31B 50.7%，Qwen3.7 Plus 只有 36.4%，它的 3 跳保留率仅 16.0%。这份拆解对做产品的人比榜单有用得多——**检索到了不等于写进去了**，长链知识在压缩成报告时最先被牺牲。

**长度是个混杂因素，作者没回避。** 主榜里 Perplexity Sonar Deep Research 平均 8,987 词，Gemini 3.1 Pro Preview 只有 1,523 词，覆盖率差着 0.56 个点但形态完全不同。他们把报告统一压到 1,200 词重跑（论文 Table 19）：Qwen3.8 Max 从 49.11 掉到 43.31，多数模型都掉；反过来 DeepSeek V4 Pro 从 36.86 升到 38.07、Gemma 4 31B 从 32.09 升到 34.01。也就是说长报告确实占便宜，但对本来写得散的小模型，逼它精炼反而更好。这个结论对「要不要给报告设字数」的工程决策很实在。

**算力预算的分量。** 补测的 LangChain Open Deep Research（配 DeepSeek V4 Flash + Tavily）在 24 个 case 上拿到总体 57.11、深度 63.29，比本地框架的 45.43 / 46.48 高出 11.67 和 16.81 个点，也超过 o3 Deep Research 的 52.15。代价呢：133.67 次成功搜索查询、693.29 条模型调用记录、7,130 词报告；本地框架是 9.88 次、28.04 条、1,437 词（论文 Table 22）。作者的原话是「更大的探索预算、迭代监督和证据综合可能贡献了这些增益」，并把「在匹配预算下评更多 harness 与骨干」列为后续方向。

看到这张表我有点皱眉：57.11 和主榜冠军 57.04 几乎贴着，但两者的检索预算差了一个数量级。这个榜表面上在比「知识覆盖」，底下还叠着一条「谁肯烧多少调用」的暗线。作者用本地框架控制了一组，剩下九个开放联网的产品级 Agent 并没有统一预算——这是主榜解释时得记住的前提。

## 🤔 我的判断

**最值钱的地方，是把结构保留到了聚合阶段。** 树状结构在 deep research 里不算新鲜，但以往多用于组织任务、追踪证据、传权重；这篇把它一路留到「怎么把 306 个 0/1 变成一个分数」，于是广度、深度成了两个可分别诊断的量。加上「查询与细则同源生成」，题目范围与评分范围天然对齐，每条判定都能回溯到树上某条边和它的 Wikipedia 出处。这套东西是评测基础设施，不是模型方法，但做得干净。开源也到位：JSONL 数据、离线 evaluator、带固定 Wikipedia 索引的容器镜像都放了，复现门槛比同期不少基准低。

**几个我觉得该打的问号：**

其一，绝对分数依赖构建模型，前面说过了。56.84 → 40.20 的落差提醒我们，57.04% 是「对这套细则的命中率」，不是「知识掌握率」。榜单适合比相对高低，不适合做跨版本的能力叙事。

其二，知识源只有英文 Wikipedia，细则问的是「报告有没有明确陈述或清楚转述某条关系」。这偏向可枚举的显性事实，对洞察、跨源综合、论证质量、判断力一概不计分。论文把覆盖当作 primary target 是自觉的选择，可标题里写着「Professional Deep Research Agents」——专业研究里最难、最值钱的那部分，恰好是这把尺子量不到的。Industrial 域只有 28.58 分，很可能不是模型不懂工业史，而是那类实体的 Wikipedia 链接结构更难被三跳树覆盖。

其三，二值化把 Partially Satisfied 直接打成 0。作者有人机一致性数据撑腰（0.893 对 0.806），逻辑自洽；但对深度评估来说，「提到了但没展开」和「完全没提」被同等对待，会系统性压低长链分数。三跳细则占了 80.45%（35,478 / 44,102），这个偏向会被放大。作者说归一化聚合不会让数量多的层级自动拿更大权重，这话在数学上成立，可「深度」的定义仍被树形状绑死：固定 3 跳、固定 10 条分支、根 50 个子节点——树的形状是人为设定的，不是知识本身的形状。

其四，主榜的竞技场不完全平整。16 个配置里 7 个骨干跑在固定快照 + 固定工具 + 固定预算下，另外 9 个产品级 Agent 用各家的开放网络检索，检索可得性、时间漂移、调用预算都混进了覆盖率。作者靠本地框架和附录分析把这个问题摊开了，没藏，但主表那列数字仍不能当成纯模型能力排序。

其五，报告长度、调用次数与覆盖率的相关性在附录里处处可见。这不叫作弊，是这类「按覆盖给分」的评测天然会奖励写得多、搜得广。好在作者做了目标长度实验和检索/报告分离评测，至少把混杂因素摆到台面上了。

**放到同期工作里看它的位置。** DeepResearch Bench 靠专家写参考报告 + 动态权重，重「质量像不像专家」；ResearchRubrics 死磕全人工细则，重「判得准不准」，还用 2800+ 小时论证「LLM 自动增广细则有害」。DRBench Pro 走的是第三条路：细则全由 LLM 从结构化证据里生成，靠**结构**而不是靠人力把可扩展性补回来。有意思的是它跟 ResearchRubrics 的结论撞了一下——后者说「细则必须人写」，前者证明「只要细则是逐边、有出处、带结构位置的」，自动生成也能拿到 0.893 的人机一致性。这两篇的结论不必然冲突，因为「人写」的价值在于避免 LLM 脑补，而 DRBench Pro 用证据约束把脑补空间压掉了。这个对照我觉得比论文自己的 Related Work 更有嚼头。

所以我的定位是：**它不是底层突破，是一次设计得很克制的结构升维**。当诊断工具用（我这份报告到底漏在广度还是深度、知识丢在检索还是写作），价值很高；当「谁是最强 Deep Research Agent」的能力榜单用，得带着上面那几个前提一起读。

## 💡 工程上能带走什么

如果你在做检索报告类的产品，有三件事我觉得可以直接试：

**把细则结构化，而不是继续堆细则数量。** 给每条评分项存上 `parent_rubric_id` 和 `rubric_depth`，聚合时按树自底向上走，你会立刻多出两个可诊断的维度。论文 Table 15 里扁平覆盖 0.508、结构化 0.751 的差距，以及 26.11% 对 0.56% 的并列率差，就是这个改动能换回来的区分度。项目页的离线示例返回 Breadth 0.84 / Depth 0.4375 / Overall 0.6062，跑一遍不用任何密钥，适合先验证自己的聚合实现。

**把检索覆盖和报告覆盖分开测。** 那 47.0% 的「检索到了却没写进去」是个很具体的优化靶点。如果丢的主要是 3 跳知识，问题多半在综合阶段的压缩策略，而不是检索器；这时候再加检索轮次基本白搭。Horn & Hardart 那个 case 就是现成的反例。

**做长度与预算的对照实验。** 统一压到目标字数、固定工具调用上限再比一次，能分清「模型真会覆盖」和「模型肯多写」。两个小模型在 1,200 词设定下反而涨分，说明篇幅和覆盖不是单调关系。

复现路径也顺手记一下：仓库里 `queries.jsonl` 只给生成报告的模型，`cases.jsonl`（含细则与树关系）留给评测器；Judge 用任意 OpenAI 兼容的 Chat Completions 端点，论文用的是 Gemini 2.5 Pro；只有 Satisfied 记 1，指标在 0–1 尺度上输出。别把 `cases.jsonl` 混进被测模型的上下文，这条是整套设计的红线。
