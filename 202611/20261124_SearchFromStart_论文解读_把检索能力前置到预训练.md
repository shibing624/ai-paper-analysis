## 一个我盯了很久的错位

你有没有注意到一个挺别扭的事实：我们现在用的模型，推理的时候能联网搜索、能调工具、能翻网页，可它整个"学习期"——那几十万亿 token 的预训练——看的却全是静态文本。模型从零长到大的全过程，压根没见过"遇到不知道的东西就去查一下"这个动作。

等它长成了，我们再在 SFT 或者 RL 阶段塞几百条工具调用示例，指望它突然学会搜索。这有点像让一个人闭门背了二十年百科全书，临考前一天告诉他：其实你可以翻书。

我在小模型上尤其能感受到这个错位。400M、1B 这种规模，参数里能塞进去的事实本来就有限，闭卷答 TriviaQA 答不上来太正常了。可你给它配个检索器，它往往还是答不好——不是检索不到，是它不知道该搜什么，也不知道把搜回来的东西怎么用进答案里。做 RAG 落地的人应该都碰过这种憋屈：检索模块明明召回了正确段落，模型视而不见，照着自己那点半吊子记忆胡编。

这篇论文干的事，一句话能讲完：**把"什么时候搜、搜什么、怎么用搜到的东西"做成预训练数据本身**。不改架构，不加外部记忆模块，就是往普通文本里插搜索词和检索结果，然后照常做 next-token prediction。

---

## 核心摘要

现在的语言模型都在推理阶段挂搜索工具，但搜索能力基本靠后训练临时补。这篇论文反过来，把检索轨迹直接织进预训练语料：用一个小标注模型在文档里找插入点、生成搜索词，用本地 BM25 索引召回网页片段，训练时只对原文和搜索词算 loss、把检索结果 mask 掉。在 Wikipedia 和 DCLM-Edu、360M 到 3.3B 的规模上，这样训出来的 QueryLM 在八个知识密集 QA 任务上稳定压过 FLOP 对齐的基线，而且过了 SFT 优势还在。最扎眼的一个数：400M 的 QueryLM 带搜索，QA 平均 24.8%，比不带搜索的 SmolLM3-3B 还高，而预训练算力少了大约 6700 倍。我的判断是，这不是架构层面的突破，是一次很干净的数据侧实证——它真正证明的是"能力前置能吃到后置吃不着的红利"，做小模型、端侧、私有知识库的人值得细读，但它对检索源的敏感度和闭卷能力的退化，也得一并看清楚。

## 一、为什么"事后教搜索"补不回来

先把问题摆清楚。参数化知识有三个绕不开的硬伤：容量有限，小模型尤其明显，那些无法从一般规律推出来的事实只能靠死记；会过时，现实世界一变，权重里的旧事实就成了包袱；难更新，想改就得重新训练或者做知识编辑，成本都不低。

让模型学会搜索，理论上是解药：事实留在外部，可检索、可更新，模型只负责"找"和"用"。这条路走过好几茬了。推理时挂搜索引擎或 API 的一大堆工作（Lazaridou 2022、Nakano 2022、Asai 2023、Yao 2023、Jin 2025 的 Search-R1 等等），Schick 的 Toolformer 把工具调用示例内联进文本再微调，跟这篇的思路最接近。预训练侧也有人试过，Guu 2020 联合训练检索器、Borgeaud 2022 加专门的注意力层去读检索内容。更近的 LMLM 和 Co-LMLM 走的是另一条路：从训练数据里建一个显式的实体键值库，训练模型去查这个库。

但主流工业做法还是**后置**：预训练先把 next-token prediction 训到头，工具能力等到 SFT / RL 再灌进去。这篇的切入点就在这里，它援引了一批"能力相关的数据早点喂进预训练有好处"的工作——指令跟随、降低毒性、可引导性、推理、知识合成，都是同一个脉络，只是把"能力"换成了搜索。

于是问题被收得很具体：能不能用**普通文档**大规模增强出搜索能力，同时还保住原本的 next-token 目标？这句里的"普通文档"和"保住目标"是关键约束。以前这类尝试常常卡在数据量上，只能靠有限种子集或者合成数据，规模一上去就不成立。

说实话，我第一反应是怀疑这个痛点有多少是真问题。毕竟现在带搜索的商用模型看着都挺利索。但转念一想，那些基本都是大模型、重后训练堆出来的；小模型上"给了检索也不会用"是真实存在的工程泥潭。论文没有把痛点包装成玄学，这一点我先给个好感分。至于"后置补不回来"这个立论够不够硬，得看实验怎么设计——后面会专门回来算这笔账。

## 二、方法：把搜索轨迹织进语料

### 三步流水线

![图2：Search-Native Pretraining 的三步流水线](https://arxiv.org/html/2611.26809v1/overview_fin.png)

*图2：整条流水线。左边是把搜索块插进原始文档，中间是训练时的 loss masking，右边是推理时模型自己发 query 去查外部知识库。图里的例子是"贝果进 450°F 烤炉之前要先在碱水浴里煮"，检索结果回来的是煮贝果的碱性液体配方；推理那侧举的是"毅力号火星车靠什么供电"，答案是 Multi-Mission RTG。*

这张图把整套方法压缩得很清楚，我拆开说说。

第一步，**增强文档**。给一段原文找到该查资料的位置，插入一个 `QUERY` 块和紧跟的 `SEARCH RESULT` 块。图中橙色虚线框标出的 "Inserted Search Block" 就是插进来的部分，原文一个字没动。

第二步，**算 loss 时做掩码**。绿色块（原文 token 和 QUERY）打勾参与 loss，灰色的 `SEARCH RESULT` 打叉被 mask。这个设计是全文我最喜欢的一处，等下细讲。

第三步，**推理**。模型自己生成 query，去外部知识库取回结果，再接着往下生成。训练时见过的交互格式，推理时原样复用。

### 一条标注数据长什么样

![图3：文档标注示例，插入点与检索块](https://www.mulanai.com/fs/files/1124_91d6bae6_annotate.png)

*图3：Racetrack Playa（赛马场盐湖）会移动的石头那段文本。左边的原文里标了 a₀、a₁、a₂ 三个插入点，中间生成了 q₀「Racetrack Playa」、q₁「Racetrack Playa stone trail」、q₂「Racetrack Playa stone propelled by」三条 query，紧跟着是 r₀/r₁/r₂ 三段检索知识块，最右才是拼好、带 Q 和 R 标记的增强文档。*

注意插入点的位置。以前 LMLM 那类做法把插入点放在"实体的值"前面，比如 "Dante Alighieri was born in" 和 "May 1265" 之间。这里放宽了：可以紧跟在某个专名之后（"Dante Alighieri" 后面），也可以放在依赖远距离上下文的位置（"Dante Alighieri, […], originally titled his masterwork" 和 "La Commedia" 之间）。这一步放宽挺要紧，真实文本里值得查的东西不总是"实体 + 属性值"那种整齐结构。

图里左上角的小图例还给了两个特殊标记：`Q` 对应 `<|WEB-QUERY|>`，`R` 对应 `<|WEB-RESPONSE|>`。整条增强序列就是靠这两个标记切出结构来的。

### 何时搜、搜什么：用一个小模型批量打分

给每篇文档找插入点，不可能靠人标，也不适合让大模型逐条跑。作者的做法是训一个专门的标注模型 $M_\phi$。

种子数据从 1 万篇 Wikipedia 文档起步，用 GLM-5.2 当教师，让它挑出"能从外部检索获益的具体事实"前面的位置——人名、日期、数量这类。有个细节我很欣赏：教师模型看整篇文档来挑候选位置，但**生成 query 时只给左侧上下文**，跟推理时能拿到的信息完全一致。这样不会产生"看了答案再出题"的泄漏。

然后用这批种子微调 Gemma 4 E4B，得到标注模型。到了真正标注大规模语料的时候，对长度为 $T$ 的序列 $x$ 做**一次因果前向**，就能并行算出每个位置后面该不该插搜索：

$$
\pi_i(x) = \Pr\left(\texttt{<|WEB-QUERY>} \mid x_{1:i}\right),\quad i=1,\ldots,T
$$

$\pi_i(x)$ 就是第 $i$ 个 token 之后插入 query 的概率。超过阈值 $\tau$ 的位置进插入集合：

$$
\mathcal{A}=\{i\in\{1,\ldots,T\}\mid \pi_i(x)\geq\tau\}=\{a_1,\ldots,a_k\}
$$

预训练语料上取 $\tau = 0.05$ 做初筛，控制每篇文档的 query 数量、丢掉低质 query；再用检索结果 $r_i$ 与原文续写 $s_i$ 之间的 ROUGE-1 F1 重合度做二次过滤，拿词汇重合当相关性的代理指标。

单次前向就把整篇文档所有候选位置打完分，这个工程选择很聪明。要是逐位置调模型生成，100B token 的语料根本标不动。

### 模拟网页响应：为什么不直接调搜索 API

训练时要给每条 query 配上"搜回来的东西"。作者用 BM25 索引 Sphere（一个含 1.34 亿网页的公开数据集）来模拟。每条 query 取 top-10 原始段落，再挑出与 query 词干重合度最高的句子，拼成训练用的 web response $r_i$，默认长度 600 字符。

不用真实搜索 API 的理由很实在：标注阶段要跑几百万篇文档，API 成本会炸，而且结果不可复现。所以训练用本地 BM25，评测阶段才换成 Tavily 这种真实网页搜索。这个训练和推理之间的检索源落差，后面我会专门吐槽。

### 训练目标：只对"该学的"算 loss

这是整套方法的技术内核。给增强后的序列 $\tilde{x}$，长度 $\widetilde{T}$，把 web response 的 token（包括 $r_i$ 和 `<|WEB-RESPONSE|>`）下标集合记为 $\mathcal{I_R}$，目标函数是：

$$
\mathcal{L}(\theta)=-\sum_{t=1}^{\widetilde{T}}\mathbf{1}[t\notin\mathcal{I_R}]\log p_\theta(\tilde{x}_t\mid\tilde{x}_{\lt t})
$$

翻成大白话：原文 token、query token、`<|WEB-QUERY|>` 标记都算 loss，检索回来的内容全部 mask 掉。模型被允许**读**检索结果来预测后面的原文，但**不被要求复述**检索结果。

等等，这个 loss 真的能把能力学出来吗？直觉上会担心：既然结果不算 loss，模型会不会直接忽略它？实验给出的答案是不会，反而学得更"会用"。我想了想，原因大概是这样——模型要降低原文续写的 loss，而续写里那些具体事实恰好只在检索结果里出现过，于是注意力被迫去读那段上下文。它学到的是一条稳定的因果链：「发 query → 拿到证据 → 用证据填后面的空」。而如果连检索结果一起算 loss，模型会分出一部分容量去学"怎么把网页句子抄得像"，那反而是噪声。

把这个设计放到同类工作里看，位置就更清楚了：

| 方法 | 搜索能力引入时机 | 改架构 | 外部存储 | 训练目标 |
|---|---|---|---|---|
| 推理时 RAG | 不训练 | 否 | 检索库 | 无 |
| Toolformer | 后训练（微调） | 否 | 工具 API | 预测内联工具调用 |
| REALM / RETRO 系 | 预训练 | 是（联合检索器 / 专用层） | 检索库 | 联合建模 |
| LMLM / Co-LMLM | 预训练 | 否，但需显式实体表 | 实体 KV store | 查询键值库 |
| **QueryLM** | **预训练** | **否** | **无，只生成 query** | **原文 + query 的 LM loss，结果掩码** |

QueryLM 这一行最轻：没有检索器要联合训练，没有实体表要构建维护，架构就是个普通 decoder-only Transformer，唯一变化在数据和 loss mask。这一点对工程落地很友好。

## 三、实验怎么搭的

语料用了两套。Wikipedia 是知识密度高、便于受控实验的小场子；DCLM-Edu 是更接近真实预训练的多样化网页文本。增强后的 DCLM-Edu 语料超过 100B token，包含原文、query 和检索响应。

模型从零训，规模 360M 到 3.3B：Wikipedia 上用 SmolLM2 配置的 360M（为了跟 LMLM 对齐），四个 epoch 共 33.4B token，其中每个 epoch 4.01B 原文 token + 4.33B 增强 token；DCLM-Edu 上用 nanochat 配置训 400M / 1.4B / 3.3B，分别吃 10.6B / 44.0B / 99.8B token，其中原文占 6.8B / 28.2B / 64.0B（大约每个参数 20 个 token）。另外特意多训了一个"过训练"的 400M（65.1B 原文 token、101.5B 总处理量），用来跟在 FineWeb 上训的 Co-LMLM 对齐。

基线设计我要单独夸一句。每个 QueryLM 都配一个**同架构、FLOP 对齐**的基线，只吃原始文档。关键在于：虽然检索结果的 loss 被 mask 了，但它照样占序列长度、照样吃前向算力，作者把这部分计算**也算进基线预算**里做了对齐。很多检索增强的工作在这儿会偷偷占便宜——把额外上下文的算力当免费午餐，然后宣布自己赢了这个基线。这里没有。

评测覆盖面挺全。八个知识密集 QA 分两组：事实类 TriviaQA、NQ-Open、PopQA、WebQuestions，多跳类 HotpotQA、2WikiMultiHopQA、MuSiQue、Bamboogle（用 Search-R1 的评测套件）；事实接地用 FreshQA，幻觉场景用 HaluEval 和 RAGTruth；另外还测了通用语言理解与常识推理。

协议也交代得很细：base 模型给 4-shot 搜索示例，SFT 后 zero-shot；事实类给 1 次 look-up，多跳给 2 次；base 模型按 24-token 生成预算算"答案是否包含"，SFT 模型按 64-token 算 LLM-judged 准确率；都报 95% bootstrap 置信区间。检索源方面，为了跟 LMLM 公平比，Wikipedia 训的 360M 用 BM25 over Wikipedia，DCLM-Edu 训的 400M 用 BM25 over FineWeb-Edu + Wikipedia；主结果则额外报 Tavily 真实网页搜索。

SFT 分两种，这一步是整篇立论的关键。标准 SFT 按 Olmo 3 的配方取 Dolci 子集（本身带一点搜索混合），再加等量的自建 SmolTalk 搜索轨迹，模拟"搜索只在后训练引入"的常规流水线。Search SFT 则把搜索数据比例大幅拉高，用 52,806 条 SmolTalk / SmolTalk2 对话（覆盖通用聊天和工具调用），再用标注模型给其中一部分补上搜索交互。后者专门用来逼问：如果后训练给足搜索数据，能不能把预训练的红利追回来？

## 四、实验结果：数字说话

### 最扎眼的一张图

![图1：QueryLM 的三组核心结论](https://www.mulanai.com/fs/files/1124_5925c8a7_teaser_s.png)

*图1：(a) base 模型 QA 准确率随规模变化，蓝圆是带搜索的 QueryLM，灰方是 FLOP 对齐基线，橙菱和紫三角分别是不带搜索的 SmolLM3-3B 和 Qwen2.5-3B，标注了约 6700 倍算力差；(b) 标准 SFT 之后的八个任务平均准确率；(c) 给出反事实证据时模型跟随证据的比例。*

三个子图的数值我都抄下来了。(a) 里 QueryLM 从 400M 的 24.8% 走到 1.4B 的 30.3%、3.3B 的 32.0%，基线是 9.7%、15.2%、16.7%；(b) 标准 SFT 后 QueryLM 22.2% / 27.8% / 33.7%，基线 16.5% / 20.3% / 27.5%；(c) 反事实证据下 QueryLM 跟随证据 57.9% / 62.0% / 64.3%，基线 51.7% / 55.4% / 55.1%。

那个 "约 6700 倍更少算力"确实唬人，但我得给这个数降降温。橙菱和紫三角是**不带搜索**的 3B 开源模型，蓝线是**带搜索**的 QueryLM，两边条件并不对等，本质是"带工具的小模型"对"裸跑的大模型"。论文自己的图注也写明了 "without search"，没有藏着掖着。真正干净的对照是灰方那条 FLOP 对齐基线——而那条线上，400M 是 24.8 对 9.7。

### 主实验：跨规模、跨 SFT 配方

![图5：base 与两种 SFT 后的八个任务平均准确率](https://www.mulanai.com/fs/files/1124_adf54975_qa_base_.png)

*图5：左为 base 模型（4-shot，answer-contained），中为 Search SFT 后（0-shot，LLM-judged），右为标准 SFT 后（0-shot，LLM-judged）。灰柱是 FLOP 对齐基线，蓝柱是 QueryLM。*

把柱子上的数字整理成表，看得更清楚：

| 设置 | 规模 / 语料 | FLOP 对齐基线 | QueryLM | 差值 |
|---|---|---|---|---|
| Base（4-shot） | Wikipedia 360M | 4.3 | 7.0 | +2.7 |
| Base（4-shot） | DCLM-Edu 400M | 7.5 | 24.8 | +17.3 |
| Base（4-shot） | DCLM-Edu 1.4B | 18.6 | 30.3 | +11.7 |
| Base（4-shot） | DCLM-Edu 3.3B | 23.9 | 32.0 | +8.1 |
| Search SFT | Wikipedia 360M | 7.3 | 19.4 | +12.1 |
| Search SFT | DCLM-Edu 400M | 22.4 | 26.2 | +3.8 |
| Search SFT | DCLM-Edu 1.4B | 33.1 | 36.0 | +2.9 |
| Search SFT | DCLM-Edu 3.3B | 36.9 | 39.4 | +2.5 |
| 标准 SFT | DCLM-Edu 400M | 16.5 | 22.2 | +5.7 |
| 标准 SFT | DCLM-Edu 1.4B | 20.4 | 27.8 | +7.4 |
| 标准 SFT | DCLM-Edu 3.3B | 27.5 | 33.7 | +6.2 |

看到 400M 那一格 7.5 → 24.8 的时候我愣了一下，涨 17.3 个点，这幅度在小模型上相当能打。摘要里那句"1.4B QueryLM 打平或超过 FLOP 对齐的 3.3B 基线"，对上的就是 30.3 对 23.9 这组——小一档的模型反而更高。

再看趋势：规模越大，差距越窄。base 阶段从 +17.3 收到 +8.1，Search SFT 后从 +12.1 收到 +2.5。这基本坐实了作者的猜测——搜索能力主要在**补偿小模型参数知识的不足**，模型一大，自己脑子里就有货了，外部检索的边际收益自然变小。

而标准 SFT 那三行才是论文真正想给你的答案：就算两边都走完常规后训练流水线，QueryLM 依然领先 5.7 到 7.4 个点。Search SFT 把差距压到 2.5 到 3.8 个点，但**没抹平**。这就是"后置补不回来"的实证来源。

### 跟 LMLM、Co-LMLM 正面比

![图4：base 模型与外置知识库方法的对比](https://www.mulanai.com/fs/files/1124_553fe468_base_ope.png)

*图4：左为 Wikipedia 360M 组，右为 DCLM-Edu 400M 组。柱子依次是 Standard (BM25)、LMLM 或 Co-LMLM、QueryLM (BM25)、QueryLM (Tavily)，右上角标了 95% 置信区间。*

| 分组 | Standard (BM25) | LMLM / Co-LMLM | QueryLM (BM25) | QueryLM (Tavily) |
|---|---|---|---|---|
| Wikipedia 360M | 4.3 | 6.9（LMLM） | 5.7 | 7.0 |
| DCLM-Edu 400M | 10.4 | 19.1（Co-LMLM） | 19.8 | 26.7 |

这一段我读得挺舒服，因为作者没挑好看的讲。Wikipedia 那组，QueryLM 用同样的 BM25 检索源只拿到 5.7，是**输给** LMLM 的 6.9 的。作者给的解释是：八个任务里赢了六个，输在 PopQA 和 WebQuestions；PopQA 由 Wikidata 三元组构造，跟 LMLM 那套 Wikipedia 衍生知识库在结构上高度重合，等于撞到人家主场了。这种自我剖析比硬吹一句"全面超越"可信得多。

但换个角度，右边那组更值得警惕：DCLM-Edu 400M 上，检索源从 BM25 换成 Tavily，19.8 直接跳到 26.7，涨 6.9 个点。这个增益比不少方法层面的改进还大。说明这套系统里，**检索质量仍是主要瓶颈**，模型侧的贡献得放在这个前提下去读。

### 它真的"听话"了吗：反事实实验

![图6：无证据、原始证据、反事实证据三种设置下的 LLM-judged 准确率](https://www.mulanai.com/fs/files/1124_5ecf95fc_sft_cont.png)

*图6：三组子图分别对应无证据、支持原始事实的证据、支持反事实的证据，横轴是 400M / 1.4B / 3.3B，灰柱为基线，蓝柱为 QueryLM。*

做法是：从 DCLM-Edu 训练文档里抽 1000 条陈述事实，用 GPT-oss-120B 把原本支持正确答案的证据改写成支持一个"看起来合理但错误"的值（比如把爱因斯坦出生年从 1879 改成 1889），再看模型跟不跟。为了把"会不会写 query"这个变量摘出去，这一组固定住搜索 query，两边用同一套。

| 证据设置 | 400M 基线 / QueryLM | 1.4B 基线 / QueryLM | 3.3B 基线 / QueryLM |
|---|---|---|---|
| 无证据（闭卷） | 10.0 / 7.9 | 15.1 / 6.9 | 13.8 / 5.1 |
| 原始证据 | 23.6 / 25.0 | 26.6 / 28.5 | 30.1 / 29.7 |
| 反事实证据 | 51.7 / 57.9 | 55.4 / 62.0 | 55.1 / 64.3 |

这张表把 QueryLM 的性格暴露得很彻底。闭卷它更差（3.3B 上 13.8 掉到 5.1），一给证据就追上来，给假证据时跟随比例最高冲到 64.3%。说到底，它把一部分本该用来"记住答案"的容量，换成了"读上下文填空"。论文结论里那句"把预训练中的相当一部分记忆重构进了搜索目标"，讲的就是这件事。

可这把刀是双刃的。做 RAG 的人最怕什么？检索器返回一段脏数据，模型照单全收，比谁都听话。QueryLM 恰恰把这个倾向放大了。FreshQA、HaluEval、RAGTruth 上的补充实验也是同样的走势——更接地，也更易被误导。这一点论文没回避，但我觉得值得任何人往生产环境搬之前先敲黑板。

### 它写的搜索词更好吗

![图7：自生成 query 与强模型 query 的下游 QA 表现](https://www.mulanai.com/fs/files/1124_196a6cd9_sft_open.png)

*图7：三个规模各自的折线，横轴是 query 来源（Self 为模型自生成，Qwen 为 Qwen3-30B-A3B-Instruct-2507 生成），纵轴是平均准确率，灰方为基线，蓝圆为 QueryLM。*

| 规模 | 基线 Self → Qwen | QueryLM Self → Qwen |
|---|---|---|
| 400M | 15.7 → 23.6 | 23.7 → 25.0 |
| 1.4B | 26.0 → 26.6 | 27.1 → 28.5 |
| 3.3B | 29.0 → 29.7 | 29.5 → 30.1 |

换成强模型写的 query，400M 基线一口气涨 7.9 个点，QueryLM 只涨 1.3 个点。这个不对称说明 QueryLM 自己生成的 query 已经不赖，没多少可被替代的空间。固定住 query 来源之后，400M 和 1.4B 上 QueryLM 依然领先，差距就来自"会不会用证据"而不是"会不会搜"。

有意思的是 3.3B 上趋势反转了，两条线几乎贴在一起。作者的解释是规模大了以后参数知识和上下文推理都变强，query 质量不再是瓶颈。我大致认同，但也存个疑：这个反转只在 3.3B 一个点出现，样本太少，未必能当成规律。

### 检索源的影响

![图8：不同检索源下各规模模型的八任务平均表现](https://www.mulanai.com/fs/files/1124_fd194b3e_base_ope.png)

*图8：四个分组（Wikipedia 360M、DCLM 400M / 1.4B / 3.3B），每组四种设置——无上下文、BM25 over Wikipedia、BM25 over Sphere、Tavily over Wikipedia，空心方为基线，实心蓝圆为 QueryLM，横轴是八任务平均表现。*

Tavily 在每组都最靠右，这也是主结果选它做评测的原因。但训练标注阶段还是回到本地 BM25 over Sphere，理由前面说了：几百万篇文档调 API 成本受不了。于是就留下一道训练与推理之间的检索分布落差。作者在 6.2 节专门讨论了这个选择，也承认换成更真实的检索源两边都涨——算是把问题摆到台面上了，只是没条件做端到端的一致训练。

### 消融一：训练时给什么样的证据

这是全文我觉得最值钱的一组消融，反直觉。作者在 Wikipedia 360M 上固定文档和 query，只换 response 文本：LM-summarized 是用 Gemma 4 E4B 把召回文档做摘要，Oracle 是直接拿含标准答案的训练文档摘要（等于喂"完美证据"）。

| 预训练上下文 | 相对算力 | PPL 无上下文 | PPL 原始标注 | PPL 实时查询 | QA 开放域 | QA 多跳 | 通用 |
|---|---|---|---|---|---|---|---|
| Standard（无） | 1.00 | 7.57 | 10.01 | 9.70 | 3.2（闭卷） | 0.2（闭卷） | 35.1 |
| QueryLM（默认） | 1.04 | 7.96 | 7.44 | 7.78 | 12.2 | 5.7 | 33.7 |
| LM-summarized | 0.79 | 7.60 | 7.09 | 7.47 | 8.3 | 0.5 | 34.9 |
| Oracle | 1.04 | 10.17 | 5.03 | 10.07 | 9.7 | 4.0 | 31.8 |

看 Oracle 这行：给原始标注时 PPL 压到 5.03，远低于 QueryLM 的 7.44，说明它**极其依赖**检索上下文。可一到下游 QA，12.2 对 9.7、5.7 对 4.0，反而输了。喂太干净的证据，模型学到的是"照抄眼前这段"，换到 BM25 over Sphere 那种不那么听话的检索环境就抓瞎。

说实话这个结果我盯了半天。它暗示一件事：训练时的证据**得带点噪声才有用**。检索增强类的工作常常默认"标注越准越好"，这张表给了个反例。当然这是在 360M、Wikipedia 上的单点结论，我没把握能直接外推到更大规模，但思路上确实给了个提醒。

### 消融二：能不能把这笔钱省下来

默认每篇文档插 8.2 个 query–response 块、response 600 字符，算力是基线的 1.04 倍。作者试了两种省钱办法：把 response 砍到 50 字符、每篇只留两条重合度最高的插入。

| 增强方式 | 块/文档 | 相对算力 | PPL 无上下文 | PPL Gold | PPL Live | QA 开放域 | QA 多跳 | 通用 |
|---|---|---|---|---|---|---|---|---|
| Standard（无） | – | 1.00 | 7.57 | 10.01 | 9.70 | 3.2（闭卷） | 0.2（闭卷） | 35.1 |
| QueryLM（默认） | 8.2 | 1.04 | 7.96 | 7.44 | 7.78 | 12.2 | 5.7 | 33.7 |
| 50 字符响应 | 3.8 | 0.55 | 7.90 | 7.85 | 7.95 | 8.2 | 0.9 | 33.8 |
| 每篇 Top-2 query | 2.0 | 0.57 | 7.94 | 7.73 | 7.90 | 5.6 | 1.2 | 33.5 |

算力是砍掉快一半，可多跳 QA 从 5.7 塌到 0.9 和 1.2——这个代价不小。开放域还能保住 8.2 / 5.6，说明"简单查一次就够"的任务对证据量不敏感，多跳推理是真吃上下文长度。作者把 Top-2 方案在 3.3B 上又跑了一遍，知识密集 QA 落在 QueryLM 和 Standard 之间，通用能力跟 Standard 在置信区间内持平，算是个务实的折中。

### 通用能力和成本

闭卷通用能力上，QueryLM base 略输基线；过了 SFT 两边基本持平，各任务互有胜负。也就是说搜索预训练**没伤到**通用能力，但也别指望它顺带把闭卷推理带上去。这点挺诚实，没有把增益无限外推。

成本这块，标注阶段扫描规模为 $D$ 的语料、加 $A$ 条长度 $\ell_q$ 的 query，训练语料多出 $A\ell$ 个 token（$\ell$ 是 query 加 response 的长度）；数据准备每个语料做一次，可以跨模型复用。推理时开销随搜索轮数 $k$ 线性增长，多出 $k\ell$。能调的旋钮就是 $A$、$\ell$、$k$ 三个，前面两组消融正好对应前两个。

## 五、我的判断

**这篇论文最值钱的地方，我认为是那个 SFT 对照实验。** 它没有停在"我们的方法在 base 模型上更强"，而是把两边都送进同样的后训练流水线，再问一遍差距还在不在。标准 SFT 后还领先 5.7 到 7.4 个点，Search SFT 给足搜索数据也还差 2.5 到 3.8 个点。整篇"从一开始就学搜索"的立论，全靠这组数据撑着。要是只做到 base 对比就收工，说服力会掉一大截。

几个我确实欣赏的设计。loss masking 那个思路真的挺精巧——让模型学会用证据、又不学会抄证据，一句话讲得清，实现上只改个掩码，收益却贯穿全部实验。插入点用单次因果前向并行打分，是让这套方案能扩到 100B token 的关键一步，不是锦上添花。FLOP 对齐基线把被 mask 的检索 token 算力也算进去，这种公平性上的自觉，在检索增强的文献里并不常见。数据和权重全放出来了，复现门槛也降了一截。

但让我皱眉的地方也不少。

"后置补不回来"这个结论是有边界的。论文测了两种 SFT 配方，措辞用的是 "the tested post-training procedures"，很克制，这点我认可。可换成更强的强化学习、更多搜索轨迹、更长训练，未必补不回来。传播的时候这句话极容易被读成"后置一定不行"，那就过了。

主结果对检索源的敏感度偏高。BM25 换 Tavily 涨 6.9 个点，比好几处方法增益都大；训练用 Sphere、评测用 Tavily，两边分布还不一致。说到底，这里报的是"模型侧 + 检索侧"的联合收益，拆不干净。想照着做的人，最好先掂量自己手里的检索器是什么水平。

QueryLM 闭卷能力掉得明显，No evidence 那组 3.3B 上从 13.8 掉到 5.1。这是能力预算的重新分配，不是免费午餐。生产环境里检索服务一旦超时或返回空，它掉得会比基线更难看。反事实实验里 64.3% 跟随假证据，也是同一枚硬币的背面——更接地，也更易被带跑。做高风险场景的，得自己补一层证据校验。

数据构造链路偏长：GLM-5.2 教师挑位置 → 1 万篇种子 → 微调 Gemma 4 E4B 标注模型 → ROUGE-1 初筛 → BM25/Sphere 召回 → 句子级清洗。每一环都带偏差，比如 ROUGE 词汇重合当相关性代理，语义相关但用词不同的证据会被误杀。$\tau=0.05$ 这个阈值怎么定的，正文只说是"初筛"，细节在附录，坦率讲这块我没完全吃透，不敢替作者下结论。

规模天花板也得看清。3.3B 上增益收窄，query 质量实验里趋势还反转了。这条路线主要利好小模型，别顺手外推到 70B。

放到同期工作里定位，它不是底层架构突破，剥离包装看，是一次很扎实的数据侧工程整合，加上一个干净的实证结论：能力前置能吃到后置吃不着的红利。跟 LMLM / Co-LMLM 比，那边要建显式实体键值库，这边只让模型生成柔性 query，不改架构、不维护实体表，落地更轻；跟 Toolformer 比，那边是后训练注入工具调用示例，这边把同一类信号铺到了 100B token 的预训练规模。跟"早期暴露能力数据"那批工作（指令跟随、可引导性、推理、知识合成）是同一条脉络，这篇的推进在于换成了搜索，并且把规模真的做上去了。

值不值得花时间细读？值得，尤其你在做小模型、端侧部署或者私有知识库。但它给的是方向和证据，不是可以直接抄进生产线的配方。

## 六、收尾：几个能直接拿走的东西

如果你正在折腾 RAG 或者端侧小模型，我觉得这几条比结论本身更有用：

别一上来就堆参数。先测一下你的模型"给对了检索结果会不会用"——很多所谓的检索失败，其实失败在模型这一侧。构造一组固定 query、只换证据质量的评测，就能把问题拆开。

loss masking 的思路可以迁移到任何工具返回内容上：只学"发起调用"和"消费结果"，不学"复述结果"。这个原则放到代码执行、数据库查询、计算器调用都成立，实现成本几乎为零。

触发时机可以用一个小的打分模型离线批量标，一次性成本摊到整个语料上。别让大模型逐条生成，规模一上去就跑不动。

检索源质量很可能比模型侧的优化更值得投入。图4 和图8 都在提醒这件事。

评测里还一定要留一组"无证据 / 检索失败"的设置，别只盯着带检索的榜单。这篇论文自己就报了闭卷退化，你要是不报，线上出问题时连基线都没有。

还有个更本质的问题没解决：如果检索能力可以从预训练就长出来，知识到底该放参数里还是放外部？这篇的答案是"把预算挪一部分给后者"，可挪多少、在小模型上怎么找最优分配点，没有答案。训练时的模拟检索和推理时的真实网页之间那道缝，可能比字面上呈现的更要命。我自己也还在摸索这块，可能理解有偏差，欢迎拍砖。
