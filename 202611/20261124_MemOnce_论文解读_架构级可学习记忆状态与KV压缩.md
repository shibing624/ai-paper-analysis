# 1313 倍压缩还反超全长上下文：MemOnce 的「只写一次」记忆架构

上周压一个长会话服务，又撞上那堵熟悉的墙。对话走到三十来轮，KV cache 已经吃掉大半个 80GB 的卡，prefill 从零点几秒爬到几十秒，decode 吞吐掉到个位数。想省显存换成线性模型吧，用户三天前随口提的那个人名、某份文档里一个不起眼的小数，模型就再也捞不回来了。

记性和显存，好像永远只能挑一个。

这篇 11 月 20 日挂出来的 MemOnce，让我盯着 Table 14 看了挺久。它把 1M 上下文下的活跃显存从 32.05 GB 压到 25.0 MB，prefill 从 286.86 秒压到 41.36 秒，decode 吞吐从 8.4 tokens/s 拉回 29.3 tokens/s——同时在五个记忆基准上的平均分比全长上下文基线还高了 5.77 个点。两个方向同时变好，这在长上下文的账本里是不太常见的。

---

## 🎯 核心摘要

长程交互要复用历史，可标准 Transformer 每层每 token 都存 KV，显存随长度线性涨、算力随长度平方涨；线性模型（Mamba、RWKV、GDN 那一挂）把历史压进固定大小的状态，省是省了，细粒度细节却留不住。MemOnce 的解法是把「缓存」这件事重新定义：只保留每层末端输出里每个片段尾部 $1/r$ 的隐藏状态，写进一个全局记忆库，用到时再用轻量、逐层独立的 MLP 把它们解码回各层的 KV cache；而检索索引对整个输入只算一次，跨所有层复用。缓存因此从 $\mathcal{O}(LND)$ 掉到 $\mathcal{O}(CD)$，跟层数和长度都脱钩。适配到 Qwen3.5-4B 后，1M 上下文下记忆缓存缩了 1313 倍、prefill 快了 6.9 倍、吞吐涨了 3.5 倍，记忆平均分反而涨了 5.77 个点。

我的判断：这不是一次底层注意力机制的替换，更像把跨层 KV 共享、query 条件的稀疏检索、混合线性骨干这几条已有线索，重新参数化成一个干净的闭环。想法挺漂亮，工程账算得也细，但「首个超过全长上下文的原生记忆模型」这个帽子得打个折看——后面会细说。

## 🧠 问题动机：三条路都走不通

先把痛点摊开。持续交互里的模型，每一步都要面对历史 $x_{1:t-1}$ 和当前输入 $x_t$。传统做法是把历史重新算一遍或者把 KV 全留着，前者是重复劳动，后者是显存黑洞。论文在 Preliminaries 里给了一个挺有用的统一视角，把所有方法都写成「先构造一个活跃记忆状态 $M_t$，再条件生成」：

$$\pi_\theta(y_t \mid x_t, x_{1:t-1}) = \pi_\theta(y_t \mid x_t, M_t),\quad M_t \doteq f_\theta(x_t, x_{1:t-1})$$

你想想看，标准 Transformer 就是把 $f_\theta$ 取成「把所有层的 KV 全激活」，$M_t^{\text{KV}}=\{(K^l,V^l)\}_{l=1}^{L}\in\mathbb{R}^{L\times N\times 2D}$，开销 $\mathcal{O}(LND)$；线性模型是把历史压成每层一个固定大小的状态 $S_N^l$。差别全在 $f_\theta$ 怎么选。

论文把已有尝试分成三类，逐条数了它们的毛病：

**架构与注意力优化**（混合模型、跨层共享 YOCO/LastKV、稀疏 attention）。省了算力，可持续推理时那个随长度线性增长的全局缓存还在，层数 $L$ 这个乘数也甩不掉。

**原生记忆模型**（Titans、M+、Metis 这类）。把历史压成紧凑表示，方向对，但要么性能掉、要么逐层检索开销大、要么灾难性遗忘。说到这个，M+ 是把 MemoryLLM 的每层记忆池扩成 GPU/CPU 两层，靠 co-trained retriever 逐层捞隐藏向量，把可保留的记忆从 20K 推到 160K tokens——逐层捞这件事本身就是负担，后面 Table 10 会被 MemOnce 拿来正面比。

**外部记忆系统**（Mem0、A-MEM 这类显式数据库）。可解释、可编辑，可建库和维护都贵，还没法端到端优化。

三类都卡在同一个三角里：记得准、线性时间、有界的 GPU 缓存，最多同时拿到两个。MemOnce 想三个都要。

坦率的讲，我第一反应是「这不又是一个重新包装的 retrieval + KV sharing」。往下读才发现，它动的不是检索这一层，是「到底什么才算缓存」这个定义本身。

## 🏗️ 方法核心：只写一次，按需解码

![图2：MemOnce 架构总览](https://arxiv.org/html/2611.27973v1/img2.png)

*图2：MemOnce 架构总览。左侧是混合骨干，堆叠 $L$ 个 stage，每个 stage 交错 3 个线性块（如 GDN）加 1 个 Memory Sparse Attention 块；右侧是记忆编码器-解码器，把长期记忆池 $m_1\dots m_s$ 与短期窗口 $m_{s+1}\dots m_k$ 分开，用 Top-K 相似度挑出相关状态后，经逐层的 $K^l_{\text{Proj}}$ / $V^l_{\text{Proj}}$ 解码成 $l=1,\dots,L$ 各层的 KV cache。图中 $k=\lfloor N/r \rfloor$ 是压缩后的记忆表示数量。*

整篇论文的方法可以压成一行三函数：

$$G_t=g_\theta(x_{1:t-1}),\quad M_t=i_\theta(x_t,G_t),\quad C_t=u_\theta(M_t)$$

$g_\theta$ 写记忆，$i_\theta$ 检索，$u_\theta$ 解码。前两个合起来是 memory encoder-decoder 加 memory sparse attention，第三个是按需把表示还原成 KV。

### 编码器：只留尾部 $1/r$，把层数乘数干掉

这一步是整篇文章我最喜欢的地方。历史被切成若干片段 $x_i$，每段长 $n_i$，跑完骨干得到末层的隐藏状态 $h_i^L\in\mathbb{R}^{n_i\times D}$。因为线性块和因果注意力一直在往后聚合信息，片段靠后的那些 token 状态其实已经把整段语义「压」进去了——于是编码器干脆只保留每段末尾 $1/r$ 的尾部状态：

$$G_t=\operatorname{Concat}\big(\{h^L_{i,\,-n_i/r:}\}_{i=1}^{t-1}\big)=[m_1,\dots,m_k]^\top\in\mathbb{R}^{k\times D},\quad k=\lfloor N/r \rfloor$$

默认 $r=8$。这一刀同时砍掉两个维度：**层**上不再有 $L$ 份拷贝（原来每层都存一份 KV，现在全网络只存一份末层状态），**时间**上按 $r$ 倍压缩。合起来就是论文反复说的 $L\times r$ 倍持久缓存压缩。原来 $\mathcal{O}(LND)$，现在 $\mathcal{O}(ND/r)$，而且这唯一一份还能整个挪到 CPU 内存或者 SSD 上。

片段是并行处理的，prefill 不会被拖成串行。预训练时 $n_i=128$，后训练适配时 $n_i=512$。

### 解码器：同一份表示，逐层还原成不同的 KV

问题来了。把同一份隐藏状态直接当成所有层的 KV 用，不同深度的注意力块表达力会被锁死——YOCO、LastKV 那类跨层共享就是栽在这儿，Table 15 里 LastKV 只有 0.5109 的平均分，比所有 MemOnce 变体都低。

MemOnce 的处理是给每层配一组轻量、独立的投影：

$$K^l=K^l_{\text{Proj}}(M_t),\quad V^l=V^l_{\text{Proj}}(M_t),\quad l\in\{1,\dots,L\}$$

$\text{Proj}$ 是从冻结骨干里初始化出来的、按层训练的 MLP。也就是说，记忆只存一份「通用语义」，用的时候按层「翻译」成该层能用的 KV。这个设计挺精巧：它既吃到了跨层共享的显存红利，又没丢掉逐层表达力。论文把它叫 looped memory generation，我更愿意理解成一个可学习的、按层解复用的解码器。

### 稀疏注意力：索引只算一次，跨层复用

光压缩持久库还不够，1M 上下文下把整个 $G_t$ 解码一遍照样是线性开销。所以有了第二个设计。

记忆库被切成两半：长期池 $G_t^{\text{long}}=\{m_1,\dots,m_s\}$ 存远处历史，短期窗口 $G_t^{\text{short}}=\{m_{s+1},\dots,m_k\}$ 保最近的局部连续性。当前输入 $x_t$ 的末层表示 $h_t^L$ 经过 $\phi(\cdot)$（取末 token、过一层 MLP、做 $\ell_2$ 归一化）之后，跟长期池里每个 $m_i$ 算余弦相似度，挑 Top-K：

$$M_t^{\text{long}}=\operatorname{Top\text{-}K}_{m_i\in G_t^{\text{long}}}\Big(\operatorname{Sim}\big(\phi(h_t^L),\phi(m_i)\big)\Big),\quad M_t=[M_t^{\text{long}}\,\|\,G_t^{\text{short}}]$$

关键在**只算一次**。M+ 是每层都在 forward 里重新算路由、重新捞一遍；token 级稀疏注意力也是每个 query 反复算。MemOnce 把这套索引算一次，然后把同一个 $M_t$ 复用到全部 $L$ 个注意力块和后续所有解码步。默认 $K=64$。

拿到 $M_t$ 解码出 $(K^l,V^l)$ 之后，直接拼到当前输入的局部 KV 前面做注意力：

$$O_t^l=\operatorname{Attn}\Big(Q_t^l,\,[K^l\|K_t^l],\,[V^l\|V_t^l]\Big)$$

因为活跃子集 $|M_t|=C \ll k$ 是个常数预算，GPU 上真正要留的活跃状态就是 $\mathcal{O}(CD)$，对长度 $N$ 和层数 $L$ 都是 $\mathcal{O}(1)$。持久库 $G_t$ 可以一直长大，但那是 CPU/SSD 的事，不占显存。

论文给了一个很实在的数字：一次检索加加载端到端 64.2 ms，比 M+ 的逐层检索快 12 倍以上，比 RAG 流水线快 17 倍。

### 复杂度账本

| 模型 | 状态缓存 | Prefill 时间 |
|---|---|---|
| Transformer | $\mathcal{O}(LND)$ | $\mathcal{O}(LN^2D)$ |
| YOCO | $\mathcal{O}(ND)$ | $\mathcal{O}(LN^2D)$ |
| GDN / SWA / M+ | $\mathcal{O}(CLD)$ | $\mathcal{O}(CLND)$ |
| **MemOnce** | $\mathcal{O}(CD)$ | $\mathcal{O}(CLND)$ |

*表1：状态缓存与 prefill 复杂度（$L$ 层数、$N$ 上下文长度、$D$ 隐藏维度、$C$ 与 $N$ 无关的常数）。*

这张表把定位讲得很清楚：prefill 这一列 MemOnce 跟线性模型、M+ 是同一档，都是线性；真正拉开的是状态缓存那一列——别人还带着 $L$ 或者 $N$，它只剩一个常数。

### 训练怎么落地

预训练时骨干和编码器-解码器一起优化，历史片段并行编码成 $G_t$，梯度穿过活跃状态 $M_t$ 和解码出的 KV 直接回传。后训练适配时把骨干冻住，只动三样轻东西：两层 SiLU 的索引投影 $\phi$（把 $D$ 维映射到 $d_e=1024$，温度 $\tau=0.1$）、只在全注意力层上的按需解码器（Qwen3.5-4B 的 32 层里只有 8 层需要）、以及仅在记忆编码阶段激活的 LoRA。

这个「冻结骨干 + 历史只以内化 KV 的形式存在」的选择，是后面不掉通用能力的关键。生成的时候模型权重一点没改，软提示、线性状态那些往激活里硬塞东西的做法，恰恰是灾难性遗忘的来源。

## 🧪 实验结果：数字得拆开看

### 先说基础能力：压缩 8 倍几乎不掉点

![图3左：不同压缩比下的验证困惑度](https://arxiv.org/html/2611.27973v1/img3_1.png)

*图3左：FineWeb-Edu 上的验证困惑度随训练 token（4B 到 11B）的变化。灰色虚线是 Transformer，绿/橙/灰实线是 GDN、YOCO、MLA，蓝色系是 MemOnce 在 $r=1,2,4,8$ 四种压缩比下的曲线。$r=1$ 的 MemOnce 收得最低，接近 10.5；即便 $r=8$，曲线也压在 Transformer 之下，MLA 明显最高。*

![图3右：随模型规模的 scaling](https://arxiv.org/html/2611.27973v1/img3_2.png)

*图3右：验证困惑度 vs 参数量（0.15B / 0.3B / 0.6B / 1.0B）。蓝色 MemOnce 在四个规模上都最低，1.0B 时约 9.5，Transformer 约 9.7，YOCO 约 9.85，GDN 约 10.0，而且下降斜率最陡。*

说实话看到左图我愣了一下：$r=8$ 等于把时间维度砍掉八分之七，困惑度曲线居然还能贴着甚至压过 Transformer。论文的解释是尾部 $1/r$ 的末层状态已经把整段语义封装住了，消融也印证了这点——$r$ 从 1 拉到 8，持久库缩了 8 倍，平均准确率只掉 0.0025（0.5280 → 0.5255）。

Table 15 里还有个更狠的对照：GDN 和 Kimi-Linear 在 WikiText / PTB 上出现长程困惑度尖峰（26.03 / 223.14 和 26.70 / 223.33），MemOnce 是 19.28–21.08 / 138.31–151.80。纯线性模型的固定状态瓶颈，在这儿暴露得很直白。

60.07 对 54.30，还顺手把 M+ 的 41.39 甩开 18.68 个点、Metis 的 27.80 甩开 32.27 个点。1M 那一列尤其显眼：全长基线 33.60，MemOnce 48.00。

但等等，这个反超得拆一拆。全长基线在超长序列里本来就在遭 attention dilution——几十万 token 里绝大多数是噪声，全注意力硬把它们都算进去，反而稀释了真正相关的证据。MemOnce 的 query 条件稀疏检索，其实是先把噪声过滤掉再回答。所以这 5.77 个点里，有多少来自「记忆架构更好」，有多少来自「检索帮全长基线做了它本该做的降噪」，论文没做拆分实验。换个角度说，如果给全长基线也配一个同样的 top-K 预筛选，差距还剩多少？这个对照缺席了，我觉得是主实验里最该补的一块。

*表4：32K 记忆负载下的通用推理表现。*

这张表我觉得比 Table 3 更有说服力。全量 SFT 掉 27.48 个点，软提示掉 18.22，线性状态掉 22.53——凡是往模型内部激活或权重里塞历史，通用能力就塌。δ-Mem 靠「基本不记」保住了 65.93，可它的记忆平均只有 29.28，等于用放弃任务换来了不遗忘。MemOnce 是唯一一个两头都站住的：65.98 的通用平均，同时 60.07 的记忆平均。

原因前面埋过伏笔：骨干冻结，历史只作为解码出来的 KV 挂在注意力前面。模型本体没被碰过，自然谈不上忘。这个取舍我觉得是全文最干净的一处设计。

*表14：1M 上下文、4B 规模的推理效率（原文数据）。*

三个头条数字到这儿就能自己验算了：32.05 GB ÷ 25.0 MB ≈ 1313，286.86 ÷ 41.36 ≈ 6.9，29.3 ÷ 8.4 ≈ 3.5。数字是自洽的，不是拼出来的。

不过得留个心眼。1313 倍的分母是**活跃**显存，持久记忆库还在 SSD/CPU 上占着 640 MB，只是不计进 GPU 缓存这笔账。而且把镜头拉回 32K：Qwen3.5 prefill 0.87 秒，MemOnce 1.38 秒，反而慢了；吞吐 26.5 对 29.4，领先也不大。也就是说，这套架构的红利集中在 128K 以上，短上下文里它多出来的编码、检索、解码开销是净负担。宣传里那个 1313 倍，取的是最极端的 1M 处。这个数漂亮，但落到自己的服务上，得先问一句你的上下文到底有多长。

### 检索开销：省在哪儿

| 系统 | 128K 下的耗时 | 关键动作 |
|---|---|---|
| RAG-Rewrite | 1094.30 ms | 先用 LLM 改写 query（1081.84 ms）再检索 |
| M+ | 772.50 ms | 32 层逐层检索，CPU→GPU 搬 1150 MB |
| **MemOnce** | **64.24 ms** | 单次 query forward 60.39 ms + SSD 读 20 MB 用 3.85 ms |

*表10：查询时检索延迟拆解。MemOnce 比 RAG-Rewrite 快 17.0 倍，比 M+ 快 12.0 倍；若长期池已驻留 GPU，则降到 60.7 ms。*

这里能看清「只算一次」到底省了什么：M+ 的 772.5 ms 主要花在 32 层各捞一遍、还要搬 1.15 GB 的多层状态过 PCIe；MemOnce 只挑 64 个紧凑表示，20 MB，一次搬完。RAG 那个 1081.84 ms 的 query 改写更是重量级。

顺带说一句，3.85 ms 读 20 MB 是理想值，真实生产里 SSD 冷读、page cache 命中率、并发争抢都会把这个数往上抬。论文自己也给了带 OS page cache 的 63.0 ms 版本，算是留了余地。

### 消融：K=64 是个挺脆的甜点

| Top-K | 0 | 16 | 32 | 64 | 128 |
|---|---|---|---|---|---|
| 记忆平均 | 36.83 | 59.72 | 59.69 | **60.07** | 58.86 |

*表9：检索预算消融（MemOnce-4B，五个基准平均）。*

$K=0$ 只靠短期窗口，36.83；$K=16$ 一下跳到 59.72，涨了 22.89 个点——说明那一个个紧凑状态里信息密度确实高。峰值在 $K=64$，再放大到 128 反而掉到 58.86，论文解释是低相关状态引入了上下文噪声。

看到这条我有点皱眉。$K$ 从 64 加到 128 就掉分，说明这个余弦检索器的排序质量没那么稳，多捞一点就把噪声带进来了。真实多轮对话里 query 跟历史会漂移，多跳问题可能需要「先找 A 再顺着 A 找 B」的迭代检索，一次定死的 Top-K 够不够用？论文没给多轮检索的对照。这块我自己也还在摸索，不好下定论，但直觉上这是往后走会碰到的坎。

另外两个消融也顺手记一下：$r\in\{1,2,4,8\}$ 从 1 到 8，准确率只掉 0.0025；跨段线性状态「保留」和「丢弃」几乎没差别（$r=8$ 时 0.5255 对 0.5235），所以默认直接丢掉线性状态，等于又省了一份多层循环状态的存储。这两个结果合起来，把「记忆主要靠可增长的持久库，而不是靠固定容量的线性状态」这句话坐实了。

### 零样本外溢：检索与重排

Table 5 里 MemOnce 的学出来的记忆表示，不做任务微调直接拿去跑检索（Recall@10 / NDCG@10）和重排，跟 BGE-M3、Qwen3-Embedding-4B、Qwen3-Reranker-4B 这些专用模型打得有来有回。Table 6 更具体：在 LoCoMo 上当即插即用的 reranker，从 All-MiniLM-L6-v2 召回的 256 个候选里挑 Top-20，把 A-MEM 抬了 17.2 分（到 60.78）、LightMem 抬了 13.3 分（到 53.90），还压过了专用的 Qwen3-Reranker-4B。

这部分挺有意思，但读的时候我总有点出戏：重排器是重排器，记忆架构是记忆架构，把两者装进同一篇里，容易让人以为「记忆表示天然就是好的检索表示」。它们共享的是那个 $\phi$ 投影出来的语义空间，可这到底是架构带来的，还是 post-training 数据里恰好有对话段带来的，论文没剥开。

## 💡 我的判断

**最值钱的地方，是重新定义了「缓存」的粒度**。 别人在「怎么把每层每 token 的 KV 存得更省」上卷，MemOnce 退一步问：为什么非要存 KV？末层尾部状态已经是整段语义的充分统计量，存它就够了，KV 到时候按层解码出来就行。这个重新参数化把层乘数 $L$ 整个消掉，比在 KV 上做量化、做低秩、做共享都更彻底。

**第二个漂亮的地方是「一次性」这个设计**。 检索索引只算一次、跨层复用，把 M+ 那类逐层检索的开销从架构层面拿掉了，而不是靠工程优化硬压。Table 10 那 12 倍差距就是这么来的。

**但「首个超过全长上下文基线」这句，我得打个折**。 三个理由：

其一，全长基线在 1M 处本身已经半瘫了——32.05 GB 显存、8.4 tok/s，attention 被几十万无关 token 稀释。MemOnce 的 query 条件稀疏检索先做了降噪，等于替基线补了它本该有的预处理。缺一个「全长 + 同样 top-K 预筛」的对照，这 5.77 个点就没法干净地归给架构。

其二，baseline 口径不齐。Titans 被明确排除，理由是官方实现未公开、复现有优化不稳定——可它恰恰是这条线上最被熟知的那个，少了它，对比表就少了根硬骨头。M+ 用的是 8B，其余多是 4B，虽然论文给了 † 重训版本做公平对照，但 Tables 里官方数字和重训数字混着摆，读的时候得自己分。所有方法的最终准确率都交给 DeepSeek-V4.1-Flash 当裁判，生成式评判对软提示、记忆注入这类方法可能天生不利，这个偏好论文也没讨论。

其三，Table 3 里 MemOnce 在 LoCoMo 上是 67.01，其实略低于全长 Qwen3.5-4B 的 69.55；它赢在 128K 和 1M 那两列（53.60 对 43.50、48.00 对 33.60）。所以更准确的说法是「在超长、多会话的场景里超过全长基线」，而不是笼统地超过。

**跟同期工作摆在一起看**，Titans 走 test-time 梯度写入神经记忆那条路，Metis 走冻结骨干 + 无梯度在线更新，M+ 走逐层检索的 GPU/CPU 双层池，YOCO/LastKV 走跨层共享。MemOnce 更像把这几条线索里好用的零件拆下来重装：借了跨层共享的「只存一份」，补上了 YOCO 缺的逐层解码器，把 M+ 的逐层检索换成一次性全局检索，再用混合线性骨干兜住 prefill 的线性复杂度。底层机制没有新东西，整合得干净、账算得细，这是一次很扎实的工程级架构工作，离「注意力范式的替换」还差得远。

**一个我没完全看懂的地方**：逐层解码器从冻结骨干初始化，训练信号只来自后训练阶段那点 LoRA 和投影，它凭什么能把同一份 $M_t$ 还原成各层「该有的」KV？论文用下游效果回答了，但没给解码 KV 与原始 KV 的重建误差、注意力图相似度这类直接证据（附录 Figure 7 画了读写时的注意力动态，正文没展开）。这块如果补上，说服力会扎实不少。可能我的理解有偏差，但我觉得这是判断这套方法能不能迁移到别的骨干时，绕不开的一个问题。

## 🔧 工程上值不值得试

如果你在做一个长会话 Agent，历史以多轮对话或文档段的形式堆积，显存被 KV cache 吃紧，那这套「只存末层尾部 $1/r$ 状态 + 用时按层解码」的思路值得抄。它跟 RAG 不冲突，Table 12 里 MemOnce 在五个记忆基准的四个上胜过 RAG、平均高 7.20 分（RAG 只在 LongMemEval 上靠原样塞文本赢），Table 6 又证明它能直接给现成的记忆系统当 reranker 用，接入成本比换骨干低。

但有三件事先想清楚：

- 收益在长上下文才成立。32K 时它比全长基线还慢一点，别拿短对话场景去评估。
- 新瓶颈会转移到 CPU/SSD。1M 时持久库 640 MB，检索延迟对冷读和 page cache 敏感，得上内存池和预热策略。
- Top-K 是硬预算。$K=64$ 是甜点，$K=128$ 就掉分，多跳、跨会话漂移这类需要迭代检索的任务，得自己补一层查询改写或多轮检索。

还有个更根本的追问留在这儿：MemOnce 把历史压成了不可读的稠密状态，省了显存，也丢了外部记忆系统那种可检查、可编辑、可回滚的能力。金融、医疗这类要审计「模型到底依据哪条记忆作答」的场景，这笔账未必划算。效率上赢回来的，可解释性上可能得还回去。

## 📝 收尾

长上下文这几年一直在做加法：窗口越开越大，KV 越存越多。MemOnce 反着来，问的是「哪些东西根本不必存」。把每层每 token 的 KV 换成一份末层的尾部状态，再按需解码回去——这一步退得挺聪明。

我不觉得它终结了什么，但它把性能-复杂度那条 Pareto 前沿往右上推了一截，而且给出的三个数字（1313 倍、6.9 倍、3.5 倍）是能自己拿 Table 14 验算出来的。就冲这份账算得明白，也值得花一晚上读一读。

至于那个「只写一次」能不能撑住真实世界里会漂移、会多跳、会被反复追问的记忆，我还在等下一批实验。
