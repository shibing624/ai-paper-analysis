# 换了模型就失忆？给递归自我改进的优化器装一份改进记忆

你有没有碰到过这种事：花十轮迭代，把一个智能体的 harness 磨到顺手，执行检查、工具调用、完成判定都调得服服帖帖，分数也确实涨了。然后模型升级了一版，或者换了一批任务，你把这份 harness 直接搬过去，发现它不但没帮忙，反而拖后腿。更气人的是，接下来重新优化的过程里，优化器把之前踩过的坑又原封不动踩了一遍——同一个 gate 改四次，两次是为了修自己改出来的死锁。

问题不在 harness 本身，在于**它只带代码，不带理由**。

这篇论文切的就是这个缝隙。作者给"改 harness 的优化器"配了一份按问题归档的改进档案，叫 Self-Improvement Memory（SIM），把每次编辑的动机、预测要修哪些任务、实测结果、以及当时用的是什么模型和评测环境都记下来，跨数据集、跨模型时跟着 harness 一起带过去。四个域、六组跨数据集加四组跨模型对比，Full SIM 全部拿下；最能说明问题的是编码任务上十次独立配对实验，带 SIM 的续训比不带 SIM 平均高 2.36 分，配对 t 检验 p = 0.003。

我的判断：这不是什么底层突破，想法甚至朴素得有点"早就该有人做"。但它把一个大家心照不宣却没人认真量化的东西做扎实了——优化过程的历史本身是有价值的资产，而且这个价值可以被严格控制地测出来。对真正在做 agent harness 自动演化的团队，这篇比很多花哨的"自我进化"框架值得读。

## 一、为什么优化过的 harness，换个环境就"讲不清自己为什么长这样"

先把背景交代清楚，但不按论文的顺序来。

一个 LLM 智能体的表现，取决于两样东西：policy 模型本身，还有外面那层 harness——管上下文怎么组织、工具怎么调、执行流怎么走、什么条件下算任务完成。改 harness 不改权重就能涨分，这条路线最近一年挺热闹，Meta-Harness、AHE 这类工作把"提出编辑 → 在 evolve 集上跑 → 看执行反馈 → 挑选保留"做成了自动循环，也就是 harness 上的递归自我改进（RSI）。

但这些工作基本都锁死在一个 setting 里：固定的 policy 模型、固定的 benchmark。论文里把这个设定写成 $\sigma = (M, \mathcal{X})$，其中 $\mathcal{X}$ 分成互不相交的 evolve 集和 held-out 集，只有 evolve 集的反馈能进优化循环。

现实里这个假设撑不住。模型会换代，多模型服务里一个 harness 要伺候好几个 policy，任务分布也会变。于是作者提出 Continual Recursive Self-Improvement（CRSI）：在 benchmark 或 policy 变了之后，接着原来的 harness 继续优化，前提是执行接口还兼容。分两种情形——跨数据集（$\mathcal{X}_S \neq \mathcal{X}_T$，$M_S = M_T$）和跨模型（$M_S \neq M_T$，$\mathcal{X}_S = \mathcal{X}_T$）。

真正扎心的是这两个数：

- 跨模型实验里，用 Claude Opus 5.5 演化出来的 harness，头一次拿给 Gemini 3.8 Flash 跑 workspace 任务，得 68.41 分，比 Gemini 自己的 seed harness 的 73.89 还低 5.48 分。
- 跨数据集实验里，源任务上演化过的 FewShotAll harness，在目标任务上起点 72.92，反而低于 seed 的 75.72。

在源任务上演化的那十轮是白干了吗？也不全是——源 RSI 在六个 setting 上把 held-out 源分数抬高了 2.75 到 6.41 分。但**源上变好，不等于目标上起点更好**，这个反直觉的现象论文专门拎出来讲了一节。

于是问题就落在一个很具体的地方：优化器拿到一份继承来的 harness，怎么判断哪些机制还能留、哪些要改、哪些得删？光看代码不够。当初为什么加这个检查？当时预测它能修哪几个任务？测完到底修没修好？是在哪个模型、哪个 benchmark、第几轮测的？这些信息源 RSI 过程中全都产生过，但默认不会跟着 harness 走。

没有这份历史，目标优化要么重复试错，要么把继承来的组件当自己的东西乱改。论文后面那个案例特别传神：不带记忆的那次运行，把同一个 completion gate 改了四次，其中两次是修自己改出来的完成死锁，而且第 3 轮的理由里，把这个明明继承自源 RSI 的 gate 归功于自己第 1 轮。看到这段我愣了一下——这不就是每次接手别人代码时最怕遇到的事吗。

## 二、方法：记忆给"改 harness 的人"，不是给"干活的人"

这里有个特别容易滑过去的区分，也是我觉得整篇论文最值钱的一个判断。

Agent 记忆这条线已经很拥挤了： ReasoningBank、playbook、技能修订记录、示例记忆……这些都是给**执行任务的 policy**用的，帮它做题。SIM 反其道而行，记忆挂在**优化器**（proposer 和 selector）这一侧，记录的是"怎么改 harness"这件事的经验。论文在附录 B.4 还特意区分了一下：文本分类里任务 agent 读的示例记忆（example memory）和 SIM 是两套东西，别混。

一句话讲清核心 idea：把每次被选中的编辑，按它想解决的**反复出现的 harness 问题**（root-cause hypothesis）归档，连动机、事前预测、事后实测、评测上下文一起存下来；新的尝试追加到同一条目后面，而不是覆盖。

### 从基础循环到带记忆的循环

基础 RSI 一轮是这样的：评测器在当前 harness $H_t$ 上跑 evolve 集，返回分数、轨迹和报错 $F_t$；proposer 结合历史 $\mathcal{D}_t$（早先的反馈和代码 diff）生成 $k$ 个候选；selector 先筛再选，权衡表现、复杂度、领域特异性和回归风险。

$$\mathcal{C}_t = P(H_t, F_t, \mathcal{D}_t),\qquad H_{t+1} = \mathcal{S}(H_t, F_t, \mathcal{C}_t, F_t^{\mathcal{C}})$$

一轮没候选被接受就原地不动。proposer 和 selector 都是 LLM 当的 harness 工程师，$M$ 只负责执行任务，权重全程冻结。

SIM 的条目长这样：

$$m_i = \big(c_i,\ [(a_{ij},\, o_{ij},\, p_{ij})]_j\big),\qquad \mathcal{M}_t = \{m_i\}$$

$c_i$ 是根因假设（比如"过早判定完成"），$j$ 是按时间排列的尝试序号。每次尝试存三样：$a_{ij}$ 是改动和它的理由，$o_{ij}$ 是预测与实测的任务结果，$p_{ij}$ 是来源信息（domain、benchmark、policy、round）。预测哪些任务会被修好这件事，**在评估之前就写下来**，事后核对。

加上记忆之后，循环只多了一个参数，但语义变了：

$$\mathcal{C}_t = P(H_t, F_t, \mathcal{D}_t;\ \mathcal{M}_t),\qquad H_{t+1} = \mathcal{S}(H_t, F_t, \mathcal{C}_t, F_t^{\mathcal{C}};\ \mathcal{M}_t)$$

每轮 proposer 在 system prompt 里拿到**完整的** SIM，selector 评估候选时读同一份记录，两边都不做检索、不截断。提案必须要么引用一个已有根因，要么新建一个。选中之后只把被选中的那个候选记进 $e_t$，连它退化了、或者没修好预测中的任务，也照记。更新 $\mathcal{M}_{t+1} = U(\mathcal{M}_t, e_t)$ 是追加，不是覆盖。根因文本完全相同的条目会合并，但历史尝试一条不丢。

![图1：SIM 在 agentic 外循环中的位置（对应论文 Figure 1）](https://www.mulanai.com/fs/files/1119_6a58f715_overview.png)

*图1：SIM 在 agentic 外循环中的位置。Evolve 集任务经 Evaluator 在冻结 policy 下跑出反馈 $F_t$，同时写入 History $\mathcal{D}_t$（代码、日志、diff）；Proposer 和 Selector 都通过虚线 read SIM；Selector 选中的编辑连同实测结果（青色箭头）写回 SIM，下一轮从 Retained harness $H_{t+1}$ 继续。held-out 评估始终在循环之外。*

这张图有个容易被忽略的细节：SIM 和 History 是两个独立的框。$\mathcal{D}_t$ 是这一轮优化的运行日志，SIM 是跨轮、跨 setting 沉淀的**按问题组织的经验**。论文把 held-out 评价明确画在循环外，只在附录里补了一句"evolve 集的反馈才进优化"，这个隔离做得挺干净，后面批判实验设置时这点会帮它加分。

### 四种对照条件

作者设计了一组我认为相当克制的对照，把"记忆到底哪部分有用"拆开了：

| 条件 | 起始 harness | 携带的记忆 | 想回答的问题 |
|---|---|---|---|
| Cold Start | seed $H_0$ | 无 | 从头优化能到哪 |
| Harness Transfer | 源演化后的 $H_S$ | 无 | 只继承代码够不够 |
| Problem-Only Memory | $H_S$ | 只有根因 $\mathcal{M}^c_S$ | 只留诊断够不够 |
| Full SIM | $H_S$ | 完整记录 $\mathcal{M}_S$ | 完整经验的价值 |

后三个条件**共享同一个 $H_S$**，四个条件用同样的目标任务、policy、轮数和候选预算。这个设计让 Harness Transfer 成了 Full SIM 的直接对照——差异只可能来自记忆过程本身。说实话，看到现在很多自我改进论文喜欢拿"从头训"当 baseline 然后宣布大涨，这种把起点对齐的做法反而少见。

### 记录里到底存了什么

Appendix D 给了存储结构，比正文的公式具体得多。每次运行一个 JSON 文件，顶层是 `next_id`、`carried_from`（标出源运行和目标运行）、`aliases`（合并过的 ID，比如 P6 并进 P5）、以及 `problems` 数组。每个 problem 条目是 `{id, name, opened_round, attempts[]}`，其中 `name` 是根因假设，`opened_round` 是第一次诊断出来的轮次。

每条 attempt 更细：

```
{round, sample, accepted, backfilled, what, files,
 predicted, fixed, missed, passed, total, domain}
```

`predicted` 是评估前预期会修好的任务列表，`fixed` 和 `missed` 是评估后的实际结果，`passed / total` 是这次尝试在 evolve 集上的成功与总试验数，`accepted` 表示 selector 选了它——哪怕预测里有些任务没修好也算。条目匹配不额外训相似度模型，由 proposer 自己判断该挂到哪个根因下，判断结果在评估前写进 change manifest；只有根因文本完全相同才确定性地合并。

给 proposer 和 selector 的 prompt 指引有 8 条，挑几条我觉得有工程价值的：把条目当"先验经验"而不是硬约束，允许选不同的编辑；用之前先核对每条记录背后的 domain、benchmark、model；现有诊断能解释当前失败就从它出发；benchmark 或模型变了要重新评估改动，该改就改、该换就换、该覆盖就覆盖；只有出现新证据才回头重试已测过的方向；相似 setting 下给任务级证据更高权重，benchmark 和模型都变了就降低权重。

"预测前置、事后核对"这个设计我挺喜欢。它把优化器的判断变成了可追溯的观测，而不是一句模糊的"我觉得这样会好"。论文里 P3 那个条目就是活例子：源阶段预测修 4 个任务只修好 1 个，目标阶段第 5 轮预测修 2 个一个没修好，第 6 轮又追加一次尝试——**没兑现的预测也留在记录里**，后面几轮仍能看见。这跟很多"只记成功经验"的记忆库完全不是一个思路。

## 三、实验：四个域，十组对比，加一次带统计检验的配对研究

### 设置

四个域，都是源演化出的 harness 在目标上还能直接跑的：

| 域 | 源 → 目标 | 指标 |
|---|---|---|
| Coding | Terminal-Bench 2.1 → Terminal-Bench 4 | pass@1 |
| 文本分类 | 3 个数据集的源套件 → 8 个数据集的目标套件 | 按样本池化的 accuracy |
| Agentic workspace | Harvey LAB → JobBench / GDPval / APEX-Agents 等权均值 | rubric、win rate、pass@1 |
| 工程设计 | EngDesign → Frontier-Eng | pass rate / medal score |

任务随机对半切成 evolve 和 held-out，不做分层；每个任务 5 次 rollout，全部计入分母，基础设施失败的 rollout 记 0 分不剔除。分数统一 0–100 保留两位。跨数据集两阶段都用 Gemini 3.8 Flash 做 policy；跨模型则是 Opus 5.5 做源 RSI，Gemini 3.8 Flash 在同一 benchmark 和 split 上续训；proposer 和 selector 主实验也都是 Gemini 3.8 Flash。每个源、目标运行都是 $N=10$ 轮、每轮 $k=5$ 个候选，seed harness 用 AHE、Terminus-2、NoMemory、FewShotAll 和 RRSI 的 ReAct 工具带。

成本这块论文在 Appendix C.1 提了一句：一个编码轮次约 4 小时，其中评估 1.7 小时、候选采样 34 分钟，各方法匹配轮数和候选数，但 token 用量和运行时间可以不同。这句我后面要回来吐槽。

但 Table 5 里有个数据让我停了一下：NoMemory 那行，Cold Start 从 68.60 涨到 72.00，涨了 3.40 分，比 Full SIM 从 71.40 到 73.60 的 2.20 分还多。按"增益"看 Cold Start 赢了，按"最终分"看 Full SIM 赢。作者的处理是**两个端点都报，并且明确用共享起点的 Harness Transfer 当记忆过程的直接对照**，不拿 Cold Start 的增益说事。这个态度我认可，比悄悄挑一个好看的指标诚实得多。

### 模型代际链与共享 harness

两段补充实验，我觉得属于"把故事讲圆"，不算核心证据。

Table 1 是 Gemini 世代链：每一代都继承上一代的 harness 和 SIM，与每代从 seed 重新做 Fresh RSI 对比。

| Gemini model | Seed | Fresh RSI | CRSI |
|---|---|---|---|
| 2.5 Flash | 17.8 | 21.4 | **22.4** |
| 3.5 Flash | 70.2 | 73.3 | **76.8** |
| 3.8 Flash | 87.2 | 88.9 | **90.5** |
| 4 Argon | 89.7 | **95.6** | 94.8 |

后续三代里两代续训更好（+3.5、+1.6），Gemini 4 Argon 上反而低 0.8。作者没藏这个反例，挺好。第一代两者同 seed，比的就是 SIM 在初始运行里的作用。

Table 2 问的是"一个 harness 能不能同时伺候 Grok、Opus、Gemini"，统一合成（Unified synthesis）在 held-out 上 75.24，与分别演化的 per-model harness 的 75.20 基本打平，都高于共享 seed 的 73.28；Sequential CRSI 是 74.20。作者自己标注这是描述性对比，真正检验完整 SIM 流程的还是前面那组对齐起点的实验。分寸拿捏得比较准。

### 十次配对：整篇论文最硬的一块

![图4：编码任务优化曲线与十次独立配对的优势分布（对应论文 Figure 4 / Table 3）](https://www.mulanai.com/fs/files/1119_26ad64f8_converge.png)

*图4：(a)(b) 是从 AHE 和 Terminus-2 两个 seed 出发，每轮保留 harness 的 held-out TB4 分数；(c) 是十次独立源运行下，每次配对里 SIM 减 No SIM 的最终分差，虚线标出均值。*

上面那些实验每个条件只跑一次，作者显然知道这是个软肋，所以补了一次像样的重复：从 Terminus-2 在 TB2.1 上**独立做十次源 RSI**，每一次演化出的 harness 都派生出两个十轮 TB4 运行，一个继承该次源运行的 SIM 并追加目标尝试，一个不带 SIM。配对内部起始 harness、policy、benchmark、轮数、候选预算全部一致，独立源运行是分析单元。

| Run | Start | No SIM | SIM | Δ |
|---|---|---|---|---|
| 1 | 18.18 | 20.61 | 22.42 | +1.81 |
| 2 | 16.97 | 17.58 | 19.39 | +1.81 |
| 3 | 17.58 | 20.00 | 20.61 | +0.61 |
| 4 | 18.18 | 18.18 | 23.64 | +5.46 |
| 5 | 17.58 | 18.79 | 20.61 | +1.82 |
| 6 | 19.39 | 20.00 | 23.64 | +3.64 |
| 7 | 18.79 | 20.00 | 21.82 | +1.82 |
| 8 | 18.18 | 20.00 | 19.39 | −0.61 |
| 9 | 19.39 | 18.18 | 23.03 | +4.85 |
| 10 | 19.39 | 20.00 | 22.42 | +2.42 |
| **Mean** | **18.36** | **19.33** | **21.70** | **涨 2.36 分** |

10 对里 SIM 赢 9 对，唯一输的那对差 0.61 分。共同起点均值 18.36，带 SIM 到 21.70，不带到 19.33，平均配对优势 2.36 分，95% 置信区间 [1.05, 3.68]，双侧配对 $t(9) = 4.06$，$p = 0.003$；符号秩检验 $p = 0.006$，配对标准化效应量 $d_z = 1.28$。

统计这块做得挺规矩：给了置信区间、给了非参数检验、给了效应量，不只甩一个 p 值。而且图 4(a)(b) 显示 Full SIM 在两个 seed 上从第 1 轮到第 10 轮全程最好或并列最好，从 AHE 出发第 5 轮、从 Terminus-2 出发第 2 轮就超过了最强对照的最终分 20.61。也就是说优势不是第 10 轮才碰巧跳上去的。

不过有个我得说清楚的量纲问题：编码域的分数在 16 到 25 之间，workspace 在 68 到 88 之间。2.36 分在低分区和大分区里的"含金量"不是一回事，论文报的是绝对分数点，没做归一化。这不影响配对结论（同一域内比较），但把"2.36 分"直接当成跨域统一的效果量去理解会有点飘。

### 记忆还有个副作用：不太"遗忘"

![图6：目标 RSI 期间的源任务分数保持（对应论文 Figure 7）](https://www.mulanai.com/fs/files/1119_5a16447a_forgetti.png)

*图6：从 AHE seed 出发，每轮保留 harness 在 held-out TB2.1 上的分数。三个迁移条件从共同的源演化 harness（90.22）起步，Cold Start 从 seed 起步。*

附录 E.3 的这条曲线挺有意思：优化目标 TB4 的过程中，回头看源任务 TB2.1 会不会掉。三条迁移线都从 90.22 出发，Full SIM 和 Problem-Only 最终落在 88.89 和 88.44，最低点 88.44（掉 1.78 分）；Harness Transfer 第 2 轮就跌到 86.67，收在 87.56。带记忆的两条掉得更少。论文接着补了一句更细的对比：Full SIM 在 225 次 rollout 里只丢了 3 次成功，Problem-Only 丢 4 次，Harness Transfer 丢 6 次；而 TB4 上 Full SIM 涨 6.67 分、Problem-Only 只涨 0.61 分。

**同样的"保住源任务"，只有带完整记录的那个同时在目标任务上大幅前进。** 这条把"记忆不只是防止重复犯错，还让优化器敢改"的意思讲透了——它知道旧改动当初为什么在，才敢在保留验证的同时加目标侧的新检查。

![图5：源 RSI 在六个 setting 上的效果（对应论文 Figure 6）](https://www.mulanai.com/fs/files/1119_06d7c745_source_r.png)

*图5：六个子图分别是 (a) Coding/AHE、(b) Coding/Terminus-2、(c) Text cls./NoMemory、(d) Text cls./FewShotAll、(e) Workspace/ReAct、(f) Engineering/ReAct，每组对比 seed harness（空心）与源演化 harness（实心）在 evolve 和 held-out 两个 split 上的分数。*

这张图是给前面的反直觉观察做铺垫的：源 RSI 在六个 setting 上都把 held-out 源分数抬高了 2.75 到 6.41 分，其中五个 setting 的 held-out 增益还超过 evolve 集增益。源上确实学到东西了，可一到目标场景，这些收益并不自动兑现。

### 一个能看清机制的案例

论文 Appendix F.3 追踪了从 Terminus-2 继承来的那个 completion gate，把带 SIM 和不带 SIM 的两条编辑史并排放，我觉得比任何一张柱状图都说明问题：

| 轮次 | 带 SIM：同一个 gate + 源记录 | 不带 SIM：同一个 gate，无记录 |
|---|---|---|
| R1 | Gate + 规格参数审计 | Gate：更强的错误模式 |
| R2 | Gate + "可行 ≠ 最优"检查 | Prompt：配置完整性 |
| R3 | tmux 传输修复 | Gate：修完成死锁 |
| R4 | Gate + 可行性分数拦截（P8） | — |
| R5 | Gate + 耦合字段与测试套件审计 | Gate：跨轮测试失败锁存 |
| R6 | Gate + 防御性函数契约 | — |
| R7 | Gate + 不可行标记 | Gate：修锁存错误死锁 |
| R8 | — | — |
| R9 | Gate + 生命周期状态检查 | — |

带 SIM 的那条，第 2 轮 proposer 读到源记录 P5（诊断是"未经执行验证就过早判定完成"），保留 gate，同时要求 agent 在宣布完成前把得分和理论上界比一比——满足约束只说明可行，可能存在更好的解；后面再逐步加规格参数、生命周期状态的检查。**需求继承下来了，实现按新场景改了。**

不带 SIM 的那条，同一个 gate 被改四次，两次是修完成死锁，而且第 3 轮的理由把 gate 和死锁都归到自己第 1 轮——可 gate 明明是源 RSI 继承来的。

还有 P3、P8 这类条目：P3 的诊断是"交付物内部正确但违反 verifier 的外部契约（schema、耦合属性、API 签名、split 卫生）"，源阶段预测修 4 个任务只修好 1 个，目标第 5 轮预测修 2 个一个没中，第 6 轮继续追加。P8 是目标第 2 轮开的条目，第 4 轮那次改动后来被换掉了，**记录仍然留在 SIM 里**。论文管这叫"经验在编辑被替换之后依然可用"，我觉得这是整套设计里最不像"缓存"而像"档案"的地方。

## 四、我的判断

先给定位：这不是底层突破，是一次相当扎实的工程方案验证。核心想法——把优化过程的历史记下来给优化器看——朴素到你会怀疑"这也要写篇论文"。但把朴素想法做扎实，恰恰比堆一个花哨框架难：对齐起点、拆开记忆的组分、隔离 held-out、补十次带统计检验的配对，这几步每一步都在堵"自我改进类论文"最容易漏水的口子。

**我觉得真正值得带走的三点：**

1. **记忆的对象选对了。** 给优化器记，不给执行任务的 policy 记。这个区分让 SIM 天然适配任何"外层循环改代码、内层模型干活"的系统，而不只是 agent harness。
2. **预测前置 + 失败也记。** 把优化器的判断变成可核对的观测，未兑现的预测和被替换的编辑都留着。这比"只存成功经验"的记忆库信息量大一个量级，也是后面能支撑"保留 vs 修订"决策的前提。
3. **源上变好不等于目标上起点更好，这一点被量化了。** 68.41 对 73.89、72.92 对 75.72 这两个数，比十页 related work 更能让做迁移的人警醒。

**几处我保留意见的地方，按重要性排：**

- **除编码外每个条件只跑一次。** 作者在 Limitations 里主动认了。workspace 那个 11.33 分的差距、以及跨模型四个域的一致性，都还缺重复运行的支撑。十配对实验只覆盖编码域，其余三域的结论强度要打折看。
- **SIM 被当作一个完整流程在评估。** 论文明确写"我们把 SIM 作为完整过程评估，把继承记忆和目标阶段更新合在一起"。也就是说，"继承源记忆"和"目标阶段继续写记忆"各自贡献了多少，没拆干净。想照搬的人得自己再切一刀。
- **全量记忆塞进 system prompt，不做检索、不截断。** 正文 3.2 节写得很直白："Both read all entries without retrieval or truncation." 十轮、每轮一个编辑，规模还撑得住；可一旦轮数上去、或者像模型代际链那样跨多代累积，token 成本和上下文噪声都会长。论文在 Appendix C.1 说各方法匹配轮数和候选数、但 token 用量和运行时间可以不同，**没有把 SIM 的额外开销单独拆出来对比**。一块编码轮次要约 4 小时，记忆再往上堆会不会变慢、变贵，这块我是真的想看数据。
- **对比对象偏自造。** Problem-Only Memory 是作者自己拆出来的消融档，挺合理；但相关工作里那一串记忆方案（HarnessBank 按问题分库、playbook、自由文本笔记加源回放、改进图、技能修订记录）没有放进同一套实验直接比。Related Work 里挨个点到了，实验里没对上，读的时候要自己补这个空缺。
- **前提挺硬：兼容的可执行 harness 接口。** 四个域都是"源演化出的 harness 在目标上不改就能跑"。接口一变，继承本身就失效，SIM 里那些记录的适用性也要重估。论文把 planning、search 流程和工具接口都固定住了，等于把最难的那部分圈在范围外。
- **分数尺度不统一。** coding 十几分、workspace 八十几分，报的都是绝对分点。配对研究在同一域内比较没问题，但"平均 2.36 分"别当成跨域可比的通用效果量。

还有个不算问题但得提醒的：论文里的模型名（Gemini 3.8 Flash、Claude Opus 5.5、Gemini 4 Argon、Grok 4.20 Reasoning）都是这套 2026 年设定内的型号，读的时候按论文给定配置理解就行，别往自己熟悉的现役型号上套。

**工程上怎么用？** 如果你在做 harness / prompt / 工具链的自动演化，最小可试的一步不是搭一套记忆系统，而是**让 proposer 每次提交编辑时，先写下"我预期这次能修好哪几个 case"，评估后自动核对并把结果存档**。光这一步就能把优化过程从黑箱变成可追溯的观测。等这个跑顺了，再考虑按根因归档、跨 setting 携带。另外别学它"全量不截断"——真上生产，检索和预算控制迟早要补。

往大一点想，这篇其实在碰一个老问题：一个系统改过自己之后，怎么记住自己为什么改。持续学习里讲 retention 和 interference，版本控制里讲 commit message，到 agent 自我改进这里，答案还是那份朴素的档案。区别只在于这次作者拿 ten-pair 配对把它量出来了。

还有个更根本的追问留着：如果记忆让优化器越来越"懂"这份 harness，它会不会也越来越依赖旧诊断，反而在真正需要推翻重来的场景里放不开手脚？附录 D.2 第 7 条写了"现有诊断解释不了失败时新建条目"，算是给了个出口，但论文没测长序列下的这种路径依赖。这块我自己也还在摸索，可能理解有偏差，欢迎评论区聊。
