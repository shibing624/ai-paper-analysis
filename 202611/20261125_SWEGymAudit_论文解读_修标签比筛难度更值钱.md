# 训练 Coding Agent 的数据，"做不出来"多半是标错了：74% 假阴性，修标签比筛难度更值钱

你有没有碰到过这种情况：跑 GRPO 训编程智能体，任务池里总有一批题，八次采样一次都过不了。看一眼 loss 曲线，reward 在慢慢涨，唯独这批题像钉死了一样全是零。第一反应基本都是"这题太难了"，顺手把它们过滤掉，或者按 pass rate 排个课程表，从简单的开始喂。

我以前也这么干，而且从没觉得哪里不对。

上周 arXiv 上一篇 2611.30207 把我这个惯性给掀了：那批"从没解出来"的题，多半不是难，是判错了。判卷的隐藏测试本身有毛病，正确的修复被它拒了。更扎心的是，把题按通过率筛一遍根本解决不了问题——真正把模型教坏的错标，恰好藏在筛选器会留下的那些题里。

---

## 🧠 核心摘要

作者拿两个 LLM 家族（Claude Opus 5.5 和 GPT-6.1 Sol）对 SWE-Gym 的隐藏测试逐条断言做审计，任何"疑似错标"都必须跑出一个能复现的补丁或反例才算数，光靠模型打分不算。结果挺刺眼：9B 基座模型八次采样一次都没解出来的任务里，74% 存在会拒绝正确修复的测试（假阴性），而"有时能解出"的任务只有 20%；通过测试的补丁里约四分之一其实是错的（假阳性）。把标签修好或删掉之后，同等规模、匹配难度训出来的策略，在 SWE-bench Verified 和 SWE-bench Pro 上分别高 2.4 和 2.7 个点；单纯丢掉"从没解出"的任务没有这个收益。

这不是新算法，是一次测量加一组对照实验。我觉得它比不少刷点的论文值钱：它把"数据质量"这个含糊词，拆成了可以逐条断言复核、还能追到梯度上的具体东西。

## 🎯 问题动机：判卷的标准答案，从来没人检查过

先聊聊 RL 训 coding agent 的基本盘。SWE-Gym、R2E-Gym、SWE-smith、SWE-rebench 这类训练集，任务都是从 GitHub 挖来的：一个仓库快照、一条 issue、再加当初那个 PR 里的测试。智能体只看得到 issue 和代码，看不到测试；它交一个补丁，只有所有隐藏测试都过了，才拿得到奖励。

所以隐藏测试就是奖励标签。这句话论文里说得平淡，但分量很重。

一个任务被收进数据集，准入检查只做两件事：原始代码跑测试得挂，参考修复（gold patch）跑测试得过。这只能证明奖励"拿得到"，证明不了两件更要命的事——每个正确修复都拿得到吗？只有正确修复才拿得到吗？

![图1：两类标签错误及其分布](https://www.mulanai.com/fs/files/1125_895a8d01_fig1_tea.jpg)

*图 1：(a) 迭代式假阴性案例，测试依赖 `dvc.repo.Repo._collect_graph` 这个私有方法和私有开关，issue 里压根没提，换内部命名的正确修复直接被判 0 分；(b) 假阳性案例，补丁忽略了 `into=` 参数，原测试全过，反例脚本一跑就露馅（gold fix 给 OrderedDict 行，patch 给普通 dict 行）；(c) 红线是各通过次数 k 下带假阴性缺陷的任务占比，k=0 时冲到 74%，紫线是通过补丁里假阳性的占比，全程在 19–36% 之间晃。*

错标分两类。假阴性（FN）：正确的修复被测试拒绝，比如测试调了一个 issue 从没提过的私有 helper，或者要求某个警告文案逐字跟上游一致。假阳性（FP）：错误的补丁被测试放过，比如只处理了上报的那个 case，顺手把旁边一条代码路径弄坏了，而那条路径没有测试覆盖。

这两类问题在评测集上早有警报。SWE-bench Verified 当年请 93 名工程师从 1,699 道题里人工筛出 500 道，算是很讲究了；可 OpenAI 在 2026 年挑出 o3 在 64 次独立运行里经常失败的 138 道题再审一遍，59.4% 存在实质性的测试设计或题面问题，其中 35.5% 测试过窄、18.8% 检查了题面没要求的额外行为，OpenAI 因此不再报 Verified 的分数。SWE-bench Pro 公开集的坏题比例，审计估计在 30% 上下。评测集尚且如此，训练集的检查只会更粗——毕竟那边是几千上万个任务，没人逐题人工看。

那社区现在怎么处理？RL 配方按 pass rate 丢掉模型从没解出的任务（Kimi-Dev 那一路），或者丢掉采样组里奖励没有方差的组（DAPO 那一路）；再不然用 LLM judge 给整条任务的 issue 和测试打个总分，觉得不对劲就整题丢掉。这些做法有个共同的盲点：它们看的是"任务有没有产出奖励"，不是"这个奖励对不对"。

一句话，通过率能告诉你题做没做出来，告诉不了你判卷的有没有判错。而判错了，模型学到的就是错的。

## 🏗️ 方法核心：一条"没有执行证据就不算数"的审计流水线

直觉其实很朴素：**别整题打分，逐条断言审；别信模型的结论，只信跑出来的证据。**

形式化一下。一个任务 $\tau$ 由仓库快照、题面 $s$（issue 加上后补的要求）、隐藏测试和参考修复组成。补丁 $p$ 的奖励是二值的：让所有 fail-to-pass 测试通过、又不破坏 pass-to-pass 测试，$R_\tau(p)=1$，否则 $0$。难度用基座模型八次采样的通过次数 $k$ 定义，$k=0$ 叫从没解出，$1\leq k\leq7$ 叫有时解出，$k=8$ 叫总能解出。补丁"正确"的意思是按题面解决了问题、且没破坏既有行为。

![图2：审计流水线与四组训练集](https://www.mulanai.com/fs/files/1125_81586a2a_fig2_aud.jpg)

*图 2：(a) 上面红线是 FN 审计——两个家族逐条给 F2P 断言打分 → 写 witness 补丁并在容器里跑测试 → 修题面或移除；下面紫线是 FP 审计——审每个通过补丁 → 写反例脚本对比 gold fix 与候选补丁 → 加固测试。(b) 2,265 个进入审计的任务里 1,176 个被移除（262 环境与预筛、471 断言无法修复、404 修复失败、39 个有缺陷但总能解出），1,087 个发布为 SWE-Gym-Verified（903 原样、184 修过题面）。(c) 每组 512 个任务、难度配额对齐的 Orig / Clean / Clean+FP，RQ3 和 RQ4 分别挂在哪两组之间。*

审计从 SWE-Gym 的 2,438 个任务里挑出 2,265 个可用且去重的，其中 2,001 个的断言拿到了判定。两个 LLM 家族各配一个 coding agent：Claude Opus 5.5 跑 Claude Code 2.1.295，GPT-6.1 Sol 跑 Codex CLI 0.156.1，另外还有个 GPT-5.6 Sol 专门当"泄漏裁判"。有个细节我挺欣赏：打分和写 witness 的模型**看不到任务的通过率、难度和训练轨迹**，只拿得到题面、issue 讨论、测试源码、gold patch，以及一份机械生成的代码证据包（被 gold patch 改动的代码及其调用关系、测试用到的仓库定义、题面没提到的标识符在仓库里是否存在）。看不到难度，后面"错标集中在 k=0"这个发现才不是自己证自己。

### 假阴性：判每条断言，再跑一个 witness

两族模型给每条 fail-to-pass 断言打分：0 分是不会拒绝正确修复，1 分拿不准，2 分及以上能明确说出一个会被这条断言拒掉的合理替代补丁。双 0 直接放行，不必执行；双 2+ 进 witness 模式，各自写一个替代补丁在容器里跑；其余情况进完整升级流程——互相评审对方**执行过的** witness，再辩论一轮。374 个任务进了辩论，清掉 171 个。

最终 1,091 个任务拿到 FN 判决，963 个两族都确认，128 个是争议判决（只有一家坚持）；在 810 个确认判决里，两族写的 witness 栽在同一条测试上。还有个数字能看出这些 witness 有多"干净"：98.3% 通过了全部 P2P 测试，92.1% 也通过了所有不含被标记断言的 F2P 测试。被拒的就是那一个细节，别的地方没毛病。这一条把"测试过窄"从主观抱怨变成了可复核的事实。

处理方式是**优先修，不轻易丢**。学 SWE-bench Pro 的做法，往题面追加一段 Requirements，把测试偷偷要求、issue 却没写的要求补上，测试一行不改；修完要过四道检查：不能出现文件路径或私有命名、每条要求得对得上被标记的断言、两个泄漏裁判都得认定没泄露答案、部分任务还要让模型在看不到测试的情况下盲做一遍再从头复审。588 次修复尝试只成了 184 次，471 个任务因为改题面也救不回来被移除，404 个倒在修复环节。

修得到底对不对，有一个特别直接的验证：154 个有前后两次难度测量的修复任务，基座模型通过次数平均涨了 2.1（满分 8），而 92 个没改题面重新测的任务是 0.0。举的那个例子更夸张，getmoto/moto-4846 加一句话，从 0/8 直接变成 7/8。看到这组数的时候我愣了一下——原来"难度"这么大一部分是题面漏写导致的，跟代码能力无关。

### 假阳性：用反例确认，再把反例变成新测试

FP 的判定更保守。两个家族都得把补丁判为不正确，而且得跑出一个**反例脚本**：这个脚本在原始代码和 gold patch 上输出相同，在候选补丁上输出不同，从而暴露一处回归。只有两件事都成立才算 FP。这么定会漏掉不完整修复和跑不出反例的错误补丁，作者明说了这是下界。

确认过的反例被转成新的 P2P 测试，保留条件很严：在原始代码、gold patch 以及该任务上所有没被判 FP 的通过补丁上都得过。筛完只剩 493 条新测试，覆盖 143 个任务，能抓住 484 个带执行反例的 FP 中的 264 个。

### 判决本身可信吗

论文的 Table 1 是纯文字表，我直接转成 Markdown，信息不丢：

| 校验项 | 样本量 | 结果 |
|---|---|---|
| 两族标记同一批任务的一致性 | 2,001 | Cohen's κ = 0.80 |
| 两位作者盲标：被标记断言"题面/仓库未定" | 45 | 33 条判为未定（从没解出 8/8 全中，有时解出 25/37） |
| 每位作者盲标：对照断言"未定" | 30 | 3 条、1 条（人类之间 κ=0.89） |
| 每位作者盲标：假阳性补丁确实错 | 15 | 10 条、12 条（κ=0.86） |
| FN 判决 vs PAIChecker 人工标记的任务 | 726 | 82% 命中 |
| FN 判决 vs 其他任务 | 1,149 | 37% |
| 随机抽放行任务升级复审 | 79 | 只有 2 个查出 FN |

*表 1（据论文 Table 1 改写）：判决质量的四类校验。人类盲标只有 105 项，规模不大，但方向一致；放行任务的漏检率很低。*

这里得说清一件事，免得名字误导：SWE-Gym-Verified 里的 "Verified"，跟 SWE-bench Verified 不是一回事。后者是人工逐题筛过的 500 道题；前者指"两个 LLM 家族给每条 F2P 断言打过分，被标记的断言都用执行验证过"，人类只抽查了样本。发布出来的 1,087 个任务里，184 个带修复题面，难度分布是 138 个从没解出、570 个有时解出、379 个总能解出。

顺带提一下账单：审计每个任务的 LLM 开销至少 1.3 美元（GPT 家族的 agent 运行还没算钱），一次 witness 最长跑 90 分钟，容器 2 CPU、8GB、900 秒、无网络。这不是随手能跑一遍的轻量检查。

## 🔧 四组训练集：把"修标签"和"筛难度"摆在同一条起跑线上

实验设计是这篇论文最见功力的地方。四组数据，每组 512 个任务：

| 训练集 | 构成 | 基座通过率 | 备注 |
|---|---|---|---|
| Orig | 77 从没解出 + 435 有时解出 | 48.3% | 原始题面与测试；采样池已排除不可用、重复、缺陷 PR、题面欠明确 |
| Clean | 同样 77 + 435 配额 | 49.8% | 从 SWE-Gym-Verified 抽，与 Orig 共享 314 个任务，仅 42 个带修复题面 |
| Clean+FP | Clean + 493 条新测试 | 49.8% | 覆盖 143 个任务 |
| Orig+Filter | 0 从没解出 + 512 有时解出 | 56.8% | 把 Orig 的 77 个难题换成更容易的，其中 97 个是 FN 缺陷任务 |

*表 2（据论文 §5.1、Appendix D 整理）：四组训练集的构成。Clean 和 Orig 规模相同、难度配额相同、重叠 314 个任务，所以两者比较主要在测"移除与替换缺陷任务"，不是测"补题面"。*

有个容易被忽略的照顾：Orig 不算弱 baseline。它的采样池已经排掉了坏环境、重复任务、被 PAIChecker 标成 defective 的 PR、以及 GPT-5.6 Sol 判定题面欠明确的任务；而且把"从没解出"的比例人为压到 15%，池子里其实是 54%。等于说作者专门把对照组装得强一点，没给自己留便宜占。

训练侧：Qwen3.5-9B 基座，SWE-agent 脚手架，GRPO（Dr. GRPO loss，KL 系数 1e-3），80 步 × 每步 16 任务 × 每任务 8 采样，学习率 2e-6，三组种子全部共用；checkpoint 按固定的 dev-100（100 道 SWE-bench Verified 题）最优 pass@1 选。评测是两个跟训练无共同仓库的 held-out：Verified-397（397 道计分题）和 SWE-bench Pro v2 公开集（638 道计分题）。单组 run 要 168–401 GPU 小时。

## 🧪 实验结果：数字，以及数字背后那点不对劲

### RQ1 错标在哪：74% 对 20%

2,001 个被审任务里 1,091 个（55%）拿到 FN 判决。约一半涉及 issue 根本没要求的行为；未指定的接口、精确字符串、任意设计选择各占约五分之一（一个判决可以有多个成因）。

真正抓人的是按难度拆开之后：Orig 里 74% 的"从没解出"任务是 FN 缺陷，有时解出的只有 19.5%。这个对比换个定义还站得住吗？作者把能换的都换了一遍：

| 定义 / 口径 | 从没解出 | 有时解出 |
|---|---|---|
| FN 缺陷，Orig 默认口径 | 74.0% | 19.5% |
| 只算两族都确认的判决 | 67.5% | 12.9% |
| 把后来被修复的任务也算缺陷 | 83.1% | 28.0% |
| 只有 1 条 F2P 测试的任务 | 61.5% | 12.3% |
| 2–3 条 F2P 测试 | 77.8% | 24.4% |
| 4 条及以上 F2P 测试 | 83.3% | 31.8% |
| PAIChecker 人工标记，Orig 池 1,252 题 | 61.0% | 20.6% |
| 更大采样预算下仍解不出的题 | 79.2% | 34.4% |

*表 3（据论文 Table 4 改写）：难度对比在八种口径下都成立。连 PAIChecker 那套独立的人类标注都给出 61% 对 21%，这就很难用"LLM 判决不准"来解释了。*

FP 那边：Clean 任务上 1,854 个不同的通过补丁里，26.1% 是假阳性，另有 37.3% 悬着没定论；每个难度档的 FP 都在 19–36% 之间，432 个有通过补丁的任务里 224 个至少躺着一个 FP。假阴性挑难题，假阳性雨露均沾。

Takeaway 挺锋利：一个任务"从没解出来"，更可能是被标错了，而不是太难。把零通过率当难度读，方向就反了。

### RQ2 哪些错标真的进了梯度——我觉得这是全文最值钱的一段

GRPO 的优势是相对同一任务下其他样本算的，一组八个样本奖励全一样，这组就不带梯度。三次 Orig 训练共 3,840 组，2,365 组带梯度。错标能不能伤到模型，取决于它落在哪种组里。

![图3：沉默的错误与带梯度的错误](https://www.mulanai.com/fs/files/1125_ad47aa2c_fig3_sig.jpg)

*图 3：(a) 审计判为有缺陷的 57 个从没解出任务，训练奖励只有 0.8%；被审计保留下来的从没解出任务在 Clean 里能拿到 7.6%。(b) 142 个 FN 缺陷任务里有 85 个被通过率过滤器留下、40% 被丢掉；但它们对应的 482 个带梯度组里，过滤器只动掉了 4%。(c) 一个 GRPO 组里，2 个逐字复刻上游警告文案的样本拿 reward 1，4 个换了措辞的样本只栽在这一条测试上，另 2 个其他测试也挂了。*

57 个从没解出的 FN 缺陷任务，占 11.1% 的采样组，却只占 0.9% 的带梯度组，训练奖励钉在 0.8%。它们消耗算力，几乎不教东西。有意思的是，FN 打分模型从没见过通过率，判出来的结果却能把"训练里拿不到奖励"和"拿得到奖励"的任务分开——这算一次漂亮的交叉验证。

85 个"有时解出"的 FN 缺陷任务就不一样了：占 16.6% 的任务，贡献 19.5% 的带梯度组（只算两族都确认的判决也有 12.2%）。把被标记的断言在测试里屏蔽掉重跑，20 个这类任务上有 30% 的零奖励样本当场变成通过，49 个带梯度组里 26 个含这种样本。你想想看，模型在这些组里学到的区分，是"有没有踩中题面没写的那个细节"。

按 pass rate 过滤会怎样？丢掉 40% 的 FN 缺陷任务，看着挺狠，可只动了 4% 的相关带梯度组；全零组从 20.7% 降到 8.3%，有时解出的 FN 缺陷任务仍然贡献 19.9% 的带梯度组。过滤器精准地删掉了那些沉默的错标，把会教坏模型的那批原封不动留下来了。

图 3c 那个例子我看了两遍。pandas-dev/pandas-53409 要求弃用字面 JSON 输入，题面没给任何警告文案，隐藏测试却要求上游那句话逐字一致。一个组里，两个样本复刻了原句，拿 reward 1；四个样本换了个措辞、其他测试全过，只死在这一条上；还有两个别的测试也挂。于是 GRPO 的优势在奖励"背出上游文案"，而不是"修好问题"。另一个例子更极端，getmoto/moto-5137 的 40 个训练样本里 30 个按题面做了却零奖励，唯一拿到奖励的那个反而越过了题面范围（测试还要第二个没提过的 API）。

### RQ3 修完标签，策略真的更好吗

![图4：两个 held-out 上的收益](https://www.mulanai.com/fs/files/1125_ca100898_fig4_res.jpg)

*图 4：(a) 相对基座模型的 pass@1 收益，左组 Verified-397（Orig +3.0、Orig+Filter +4.1、Clean +5.4），右组 SWE-bench Pro（Orig −0.2、Orig+Filter −2.4、Clean +2.5）；括号标出 Clean 减 Orig 为 +2.4 和 +2.7 个点。(b) dev-100 随训练步的变化，前 40 步几组几乎贴着，Orig 在 30 步见顶 52.5% 后掉到 48.0%，Clean 收在 53.0%，Orig+Filter 49.3%，基座 46.8%。*

| 训练集 | Verified-397 | SWE-bench Pro | 相对基座平均收益 |
|---|---|---|---|
| 基座模型 | 57.2 | 53.8 | — |
| Orig | 60.2 ± 2.1 | 53.5 ± 2.1 | +1.4 ± 0.9 |
| Orig+Filter | 61.3 ± 2.1 | 51.4 ± 3.0 | +0.9 ± 2.5 |
| **Clean** | **62.6 ± 1.1** | **56.2 ± 1.3** | **+3.9 ± 1.2** |
| Clean+FP | 62.6 ± 1.0 | 57.3 ± 3.7 | +4.5 ± 2.2 |

*表 4（论文 Table 2）：三个种子的均值 ± 标准差，单位 %，checkpoint 按 dev-100 最优选。Clean 比 Orig 高 2.4 与 2.7 个点；Orig 在 Pro 上甚至比基座低 0.2 个点。*

几个值得抠的细节。三个种子平均到两个 benchmark 上，每一个 Clean run 都赢过每一个 Orig run；单看某一个 benchmark 会有重叠，但去掉任意一个 run 之后，Clean − Orig 仍至少 1.4 个点。Orig+Filter 任务更容易、训练奖励最高（60.6%）、带梯度组最多（70.8%），平均收益却只有 +0.9，还要看一个种子脸色——它在 Pro 上有个 run 比基座低 5.7 个点，去掉之后平均收益变成 +2.3，就能反超 Orig 了。训练奖励和数据好坏，在这组实验里是脱钩的。

差距也不是一开始就有的。dev-100 上前 40 步几组缠在一起，Orig 在 30 步见顶 52.5% 之后一路掉到 48.0%，Clean 稳在 53.0%。checkpoint 选择规则于是把 Orig 挑在 20–30 步、把 Clean 挑在 60–70 步。到第 80 步，每个 Clean run 都高于每个 Orig run。这个"晚出现"很关键——要是训练预算再短一点，或者习惯性早停，这组收益可能根本观测不到。

收益从哪来？作者自己承认拆不开：五分之一的 Orig / Orig+Filter 带梯度组落在会拒绝正确修复的任务上；而 Clean 里那些从没解出的任务是"奖励可达"的，贡献了 6.9% 的带梯度组（Orig 只有 2.6%，Orig+Filter 是 0）。两个因素捆在一起，实验没法分离。这种坦率我挺买账的。

### RQ4 给假阳性加测试，有用吗——一段诚实的负结果

![图5：加固测试后的训练奖励](https://www.mulanai.com/fs/files/1125_85fee363_fig5_har.jpg)

*图 5：(a) 143 个加固任务上，Clean+FP 的训练奖励全程比 Clean 低约 13 个点，但把 Clean 从没见过新测试的补丁拿来重判（虚线），奖励也掉得差不多；(b) 其余 369 个任务两组几乎重合；(c) 新测试在整个训练过程中持续拒绝 Clean 约 19% 的通过补丁（虚线为合并值 18.9%），假阳性没有随时间消失。*

Clean+FP 沿用 Clean 的种子和任务顺序，493 条新测试覆盖 143 个任务，能抓住训练补丁样本里 25% 的 FP。按直觉，模型该学会绕开这些坑。

结果是：这些任务上训练奖励全程低约 13 个点，其他任务持平。可把 Clean 那些从没见过新测试的通过补丁拿新测试重判一遍，奖励掉得差不多——说明策略几乎没适应新测试，整个训练平均下来只比 Clean 多过 0.4 和 1.8 个点（两个种子）。新测试从头到尾拒绝着 Clean 约 19% 的通过补丁，FP 也没随训练淡下去。

held-out 上，Clean+FP 减 Clean 是 −0.1（Verified-397）和 +1.1（Pro），都在种子波动里；三个种子也证明不了两者等价。更麻烦的是评测口径：held-out 用的是 benchmark 原始测试，那些测试本身就接受 FP，所以它根本测不出"策略是不是少写了看起来对的错补丁"。想回答这个问题，得换判卷方式。

同期的 Arctic-SWE 报告过加强测试带来 held-out 收益，但那是 4,889 个任务、单次运行；这里新测试只覆盖约四分之一任务、三个种子。覆盖率差这么多，两个结论未必冲突。

## 🔬 我的判断：这篇论文值钱在哪，又有哪些地方别急着信

**最值钱的不是 +2.4，是把两件事分开了。** "任务难"和"标签错"在通过率这个观测上长得一模一样，以前的办法是换个更聪明的过滤器，这篇直接去查判卷的。而且它没停在相关性上——RQ2 追到"哪些错标携带梯度"，把"为什么过滤器没用"讲成了机制，不是又一条经验规律。我读到 Fig 3b 那个 40% 对 4% 的时候，是真的有点被打动。

**执行证据这条底线守得很好。** LLM 只负责"提出嫌疑"，定罪必须靠跑出来的 witness 和反例；判决可复核、可争议，逐任务记录和完整流水线全放了。对照实验也干净：等规模、匹配难度、共享 314 个任务、三个种子、baseline 特意做强。加上敢报负结果（加固 FP 没检测到收益，训练奖励高不代表数据好），整体气质是测量驱动，不是刷点驱动。

要说保留意见，也不少。

**结论绑死在单一配置上。** 一个 9B 基座、一个 SWE-agent 脚手架、一套 GRPO、一个任务源、80 步、三个种子。作者在 Limitations 里认了。Clean+FP 在 Pro 上的标准差是 3.7，其中一个种子飙到 61.6%（+7.8），另一个 54.9%——三个种子的波动摆在那儿，小数点后一位别当结论。规模放大、训练拉长之后 2.4 / 2.7 还在不在，没有证据。

**"正确"仍是模型说了算。** 执行只能证明"测试拒绝了某个补丁"，那个补丁算不算题面的合理读法，还是 LLM 判断；128 个争议判决只有一家坚持，照样被修复或移除。人类盲标 105 项，一致性 κ 0.89 / 0.86，样本不算大。所以 SWE-Gym-Verified 的 Verified，千万别按 SWE-bench Verified 那个规格去理解。

**FP 的"约四分之一"是下界，且 RQ4 的负结果受覆盖率限制。** 只算两族都判错、又跑得出反例的回归，漏掉不完整修复；37.3% 的补丁悬而未决。加固只覆盖 143 / 512 个任务、抓住 25% 的 FP，就说"没用"，条件其实挺弱。真把新测试铺满全部任务、抓住全部 FP，结论可能翻过来——作者自己拿 Arctic-SWE 做了对照，这点算清醒。

**held-out 自己也可能带病。** 作者假设两类错标对所有训练集一视同仁，这个假设没验证。OpenAI 那轮审计说明 Verified 里模型常失败的题问题率相当高；如果测试集也在奖励"复刻上游文案"，Clean 的优势可能被压低，也可能被抬高，说不准。想彻底闭环，恐怕得要一套人工判过的 held-out，或者一个独立于测试的 verifier。

**账单没结完。** 至少 1.3 美元一个任务的 LLM 开销、一次 witness 最长 90 分钟，跑完 2,001 个任务不便宜。迁到 R2E-Gym 的 8,135 个任务、SWE-smith 的 5 万多个任务上，成本是真问题。论文其实留了个很有价值的线索：不做执行、单用 Claude 打分与最终判决一致 91%，GPT 是 94.8%；但"一次评分够不够 RL 用"没验证。这块我挺想看后续。

**放在同期工作里看，位置也清楚。** Verification Horizon 用整题 agentic judge 判质量、报过滤收益；Arctic-SWE 用反事实补丁改写题面、单次运行报 curation 和加强测试的收益；PAIChecker 给 PR-issue 错配做人工标注；TinyV 在数学 RL 里补假阴性拿到收益；Spurious Rewards 更狠，随机奖励都能把某些基座的数学准确率推上去——所以"比基座涨了"根本证明不了标签对，这也是作者坚持训练集之间互比、而不是跟基座比的原因。这篇没宣称第一个发现错标，它的增量在逐断言、执行证据、按梯度拆解、等规模匹配难度多种子对照。定位是严谨的数据工程与测量，不是新算法。我觉得这个定位反而更可信。

## 💡 工程启发：要是你也在攒 RL 训练数据

别把 $k=0$ 直接当难度。训练池里那批八次全挂的题，先怀疑测试是不是在要题面没给的信息——私有命名、精确字符串、没提过的第二个 API，都是高发区。至少抽一批出来人工看一眼断言，比调课程表划算。

过滤之前先问一句"这个错误带不带梯度"。按通过率丢掉的往往是全零组里的沉默错误；真正在教模型的，是 $1\leq k\leq7$ 那些奖励按未指定细节分化的任务。想省事就按这个优先级排检查顺序。

逐断言审计比整题打分可操作得多。一条断言对应一个 witness，一个 witness 对应一次执行，出错能定位、能复核、能被别人推翻。把 LLM 放在"提嫌疑"的位置，别让它下结论——这条不只对 SWE 任务成立。

修题面通常比丢任务便宜，但得配泄漏裁判、盲测和从头复审，不然一不小心就把答案写进题面了。补一句 Requirements 让 0/8 变 7/8 的例子，值得贴在墙上。

训练奖励不能拿来挑数据集，也不能拿来 early-stop。Orig+Filter 训练奖励最高、带梯度组最多，held-out 却没赢；差距到 40 步之后才拉开。用固定 dev 集按同一规则选 checkpoint，在 held-out 上报多种子均值加标准差，是这组实验里最该抄走的实验习惯。

想减少"看起来对"的补丁，光加反例测试不够，评测口径也得换。用原始测试的 pass@1 打分，FP 减少这件事你在数字上看不见。

能直接拿来用的东西不少：1,087 个 SWE-Gym-Verified 任务、每个判决附执行证据、四套训练集、完整审计流水线（代码 Apache 2.0）。那 484 个带执行反例的假阳性，拿来当 verifier 的小 benchmark 挺合适。

说到底还有个根上的问题没解：奖励标签的正确性，最终由谁裁决？这篇给了一套两个 LLM 家族加执行、再配少量人类抽查的可复核程序，可"补丁是否符合题面"终究是个解释题。数据规模再往上走，审计成本和执行覆盖率会变成新的瓶颈。修标签比筛难度更值钱，这句我信；只是账单还没结完。
