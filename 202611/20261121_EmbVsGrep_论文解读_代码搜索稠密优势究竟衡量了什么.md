# 稠密检索赢的那 0.2 分，一大半是评测自己送的

## 🎯 一个拧巴了很久的现象

有没有碰到过这种拧巴：benchmark 上，代码专用的 embedding 模型把 BM25 甩开 0.1 到 0.2 的 nDCG@10，团队照着这个差距吭哧吭哧建了向量索引、买了 GPU、维护了一套增量更新的流水线。结果一线跑 coding agent 的人告诉你，用 `grep` 加 `find` 一样把活干完了，检索压根不是瓶颈。

这两拨人到底谁在说谎？

说实话我以前偏向"benchmark 更可信"那一派。评测数字摆在那，0.2 的 nDCG 不是噪声。但每次自己动手给仓库做检索，心里总有个声音：用户搜 "reset_index names 参数不支持 tuple"，代码里明晃晃写着 `names`、`reset_index`、`tuple`，一个字面匹配就能命中的东西，凭什么非要过一遍向量？

arXiv 上这篇 2611.20455 就是在追问这件事。标题起得很克制——*Embeddings vs. Grep: Rethinking the Dense Advantage in Code Search*，但读完你会发现它干的事一点都不克制：它把"稠密检索更牛"这个几乎成了共识的结论，拆成了"评测设置送的分"和"查询里少写了几个词"两笔账，然后一笔一笔算给你看。

我的第一反应是：这题目选得太狠了。

---

## 📝 核心摘要（先说结论）

作者搭了一个叫 RepoPremium 的仓库级代码检索基准，把代码快照、标注规则、评测协议全部钉死，只让查询来源和时间变化。结论分两层：榜单上那 0.1 到 0.2 的稠密优势，大头来自评测偏袒——把文件切块喂给 BM25、把被改的测试文件算作相关文档；把这些坑抹平后，剩下的优势几乎只落在"查询里没写出代码的稀有标识符"这类样本上。让一个 LLM 把缺的标识符补进查询再跑 BM25（作者叫 generate-then-grep），BM25 在每个 Python 池里都追平甚至反超了稠密检索，连 LLM 发布之后才开的 PR 也一样。还给出三条工程准则：拿公平的 lexical baseline 去量稠密增益、把稠密检索和 BM25 固定融合而不是逐条路由、查询缺词就先把词补上。

坦率的讲，这不是底层突破，是一篇把评测擦干净、把机制归因讲透的诚实工程研究。做检索的人值得花一晚上读，做 agent 的人至少该记住那条 agent 边界的结论。

## 🤔 为什么这个问题值得较真

先别急着看方法，把"为什么现有证据说不清"这件事捋一遍，比结论本身还有意思。

代码检索基准和 coding agent 用的是两套完全不同的原料。CoIR 这类基准，查询是 docstring 或者网页风格的干净描述，配的是老代码；SWE-bench 这类 agent 套件，查询是原汁原味的 issue 和 PR 文本，脏、长、还带模板套话。拿前者的结论去指导后者的工程，中间隔着一层没人量过的缝。

更要命的是 baseline。神经排序领域早就有人念叨过弱基线会造出假增益（Lin 2018、Yang 2019、Kamphuis 2020 那批工作），但落到仓库级代码检索，一直没人认真测过。很多实验直接把稠密检索的分块方式套给 BM25：稠密模型因为要截断长输入，习惯把文件切成 1000 字符左右的块；BM25 却恰恰喜欢大窗口。把 1000 字符的分块强加给 BM25，等于先绑住它一只手再比武。

标注规则也在打架。SWE-bench 的 gold patch 里不含测试文件，而一个 PR 的 changed files 列表里是含的，除非手动剔掉，这些测试文件会被算成相关文档。两类查询放一起比，等于用两把不同的尺子。作者还挺坦白地写了一句：我们第一版也把测试文件留着了。看到这我笑了一下，这种"自己先踩一遍坑"的交代，比装作一开始就设计完美可信多了。

还有污染嫌疑：基准里的代码普遍早于 embedding 模型的训练 cutoff，模型可能压根背过这些仓库。

所以作者的问题不是"稠密检索和 BM25 谁强"，而是更刁钻的一句：**稠密优势究竟衡量了什么**？ 它衡量的是语义理解能力，还是衡量了评测设置 plus 查询措辞？

## 🏗️ 把变量钉死：RepoPremium 怎么搭的

要回答上面那个问题，得先把其它东西全固定住。RepoPremium 的设计思路就一句话：在每个仓库里固定代码快照、固定标注规则、固定协议，只变"查询从哪来"和"改动发生在什么时候"。

![图1：RepoPremium-Core 的六步构建流水线](https://www.mulanai.com/fs/files/1121_d3e8710c_fig_cons.png)

*图1：论文 Figure 3，四个 Core 池的构建流程。左侧 Step 1 锁定 10 个 SWE-bench Verified 的 Python 仓库并固定快照；Step 2 分成两路挖查询——curated 用 497 条 SWE-bench Verified 的问题陈述，raw 用合并 PR 的标题加正文、按 3 个时间窗口切；Step 3 把"这次改动编辑过的源文件"作为二值 gold 标签；Step 4 质量过滤（1–3 个 gold 文件、必须有代码改动），从 2733 条筛到 1265 条；Step 5 对所有查询剥离 PR 模板套话；Step 6 构建语料库——每个 .py 文件一个文档，每个仓库一个快照。最右侧产出四个池：Cur-Pre 472、Raw-Post 288、Raw-Pre'23 138、Raw-Pre'22 367。*

这套设计里我觉得最精巧的是时间窗口。Cur-Pre 是裁切前的 curated 查询；Raw-Pre'22、Raw-Pre'23 是 2022、2023 年的 PR；Raw-Post 是 2026 年 1 月 1 日之后开的 PR。中间 2024–2025 直接跳过，好让每个窗口干净地落在模型训练 cutoff 之前或之后，污染这件事就有了可对照的把柄。

Core 一共 1265 条查询、10 个 Python 仓库、10200 个被索引文件（单仓库 35 到 2752 个）。Ext 扩展集再加 1560 条，覆盖 JavaScript、TypeScript、Go、Rust、Java 五种语言、9 个 held-out Python 仓库，以及一个 91 仓库、预注册的 lockbox 测试池（539 条查询）。预注册这个词后面还会出现，它是这篇论文最让我有好感的设计之一。

评测口径也定死了。作者把稠密检索相对 BM25 的领先量叫 **dense premium**：

$$
\Delta(q) = \mathrm{nDCG@10}_{\text{dense}}(q) - \mathrm{nDCG@10}_{\text{BM25}}(q)
$$

按文件打二值相关性，gold 是被改动的源文件集合。另外报 Recall@10 和 MRR@10，因为"把更多相关文件捞进前 10"和"把第一个相关文件排得更靠前"是两码事——这个区分到结果部分会变成关键。

还有个后面要唱主角的量，查询区分度 $\tau$：

$$
\tau(q) = \max_{t \in q \cap g} \mathrm{IDF}(t)
$$

$q$ 是剥离后查询的词集，$g$ 是第一个 gold 文件的词集，IDF 在该仓库的分块语料上算。人话版：查询和目标代码**共享的那些词里，最稀有的那个有多稀有**。$\tau$ 高，说明查询里已经带着代码里的罕见标识符；$\tau$ 低，说明两边共享的都是些满地都是的普通词。它借的是 Hauff 等人 2008 年的 MaxIDF 预测子，但要读 gold 文件，属于离线统计量；作者另给了个可部署的代理 $\widehat{\tau}$，只取查询里最稀有的 5 个词的平均 IDF。

比较了 13 个稠密 encoder（jina-code-embeddings、Qwen3-Embedding、C2LLM、F2LLM、E5、gte-Qwen2 六个家族，全部不加 instruction prefix），外加 SPLADE 和 ColBERTv2。默认拿 jina-code-embeddings-0.5b 当标准编码器。

## 📊 那 0.2 分，一层一层剥掉

![图2：三种 BM25 设置下的稠密优势](https://www.mulanai.com/fs/files/1121_25ddd1ef_fig_prem.png)

*图2：论文 Figure 1，四个 Python 池里稠密检索（jina-code-embeddings-0.5b）相对 BM25 的 nDCG@10 领先量，三种 BM25 版本并排。浅蓝是没调过的 BM25（沿用稠密检索的 1000 字符分块），中蓝是调优后的整文件 BM25，深蓝是整文件 BM25 再加 LLM 写的锚点词。柱子带按仓库聚类的 95% 置信区间。纵轴是 $\Delta$ nDCG@10。浅蓝普遍在 0.12 到 0.19；换成整文件后塌到 0.03 到 0.13；加上锚点词，四个池全部翻到零以下，大约 -0.05 到 -0.08。*

这张图基本就是整篇论文的缩略版。三根柱子，一条下行曲线。

### 第一刀：分块方式决定了正负号

django 仓库上的数字我盯了半天。稠密检索在**整文件**上输给 BM25，$\Delta = -0.153$；把文件切成 1000 字符的块，同样的模型翻成 $+0.119$。一个符号翻转，0.27 的跨度，什么都没变，只变了切块。

原因不神秘：encoder 会截断长输入，django 里那些大文件被砍得七零八落，切块反而救了它；BM25 反过来，窗口越大越能吃到词频和文档长度的信号，切碎了等于自废武功。把稠密模型的分块方案原样套给 BM25，等于拿对方的规则罚自己。

换成整文件 BM25 之后，Cur-Pre 的 premium 从 $+0.121$ 掉到 $+0.034$，raw 池普遍缩掉三分之一到一半。13 个 encoder 里，没有一个在 Cur-Pre 或 Raw-Post 上还守得住不跨零的领先，其中 7 个在 Cur-Pre 上干脆掉到零以下。

这里有个特别值得记一笔的诚实：作者明说 BM25 的分块尺寸是在评测查询上挑的，所以这些数字是**稠密检索的下界**。人家没有把稠密模型一棍子打死，反而主动给对手留了余地。这个姿态比结论漂亮。

### 第二刀：测试文件算不算相关

稠密模型把测试文件排在首位的频率远高于 BM25，curated 查询上 59% 对 34%。一旦把被编辑的测试文件算进 gold 集合，调优后的 premium 立刻回血：Cur-Pre 从 $+0.034$ 涨到 $+0.165$，Raw-Post 从 $+0.059$ 涨到 $+0.136$。

更麻烦的是两把尺子混用。SWE-bench 的 gold patch 没测试文件，PR 的 changed files 有，两套查询并排比时，Raw-Post 减 Cur-Pre 的差距会从 $+0.025$ 被撑到 $+0.102$。也就是说，看上去"原始查询上稠密优势更大"这个现象，相当一部分是标注规则不一致造出来的。把规则统一到每个池上之后，curated 池和 raw 池几乎分不出来。

| 池 | 查询 | 年份 | n | $\Delta$ 源文件标注 | $\Delta$ 保留测试文件 |
|---|---|---|---|---|---|
| Cur-Pre | curated | cutoff 前 | 472 | +0.121 | +0.121 |
| Raw-Pre'23 | raw | 2023 | 138 | +0.128 | +0.192 |
| Raw-Pre'22 | raw | 2022 | 367 | +0.191 | +0.245 |
| Raw-Post | raw | 2026 | 288 | +0.152 | +0.192 |

*表1：论文 Table 4，$c=1000$ 下各池的 premium。curated 的 gold patch 本身不含测试，所以右边那列对它没变化；每个 raw 池被"保留测试文件"抬高 0.04 到 0.06。*

### 剥完还剩什么

把分块、标注两个坑都填平，剩下的领先主要落在**覆盖率**上：稠密检索能把更多 gold 文件塞进前 10（Recall@10 高 0.10 到 0.19），但把第一个命中排得更靠前这件事，只在 Raw-Pre'22 一个池上站得住。跨语言看，TypeScript 和 Rust 还剩一点，Go 没有（不过每种语言就一个仓库，这个结论我持保留态度）。

说到底，榜单上那 0.2 分，拆开是：评测设置一大部分，覆盖率一小部分，排序质量几乎没份。

## 🧠 那个让我愣了三秒的例子

论文 Figure 2 不是张图，是一段并列文本，我反而觉得它比任何柱状图都说明问题。

pandas 的 PR 58032，gold 文件是 `pandas/core/frame.py`。同一个改动，两种写法：

**Curated**（LLM 把改动重写成规范描述）：
> `DataFrame.reset_index does not accept a tuple for the 'names' parameter, despite documentation stating it should.`

BM25 把 gold 排第 1，dense 排第 7。

**Raw**（PR 标题，正文是模板套话，已剥离）：
> `DOC: DataFrame.reset_index names param can't be a tuple as docs state`

BM25 把 gold 排第 8，首个命中是 `doc/source/conf.py`；dense 把 gold 排第 1。

看到这个我愣了一下。差别就藏在 `DOC` 和 `docs` 两个词上——它们把 BM25 一路拽向文档目录，而稠密检索没被带偏。curated 那句"用代码自己的词把行为讲清楚"，反而让字面检索赢麻了。

你想想看，这几乎把整篇论文的机制摊在桌上了：稠密优势不是"更懂语义"，很多时候是"查询里混进了会把字面匹配带沟里的词，或者干脆没写出代码里那个关键的罕见词"。

这也顺手解释了 5.5 节那个匹配复现：36 个仓库上，把每个 raw PR 和它的 LLM 改写版配成对，同一个 gold 集合、同一份语料，raw 措辞的 premium 高出 0.091（jina）和 0.111（Qwen3-0.6B），区间都不跨零。同一件事，换个说法，稠密优势就变了。而 DeepSWE 那种"描述要做什么"而非"描述改完了什么"的任务描述，premium 干脆和零分不出来。

年份倒是没戏：2022、2023、2026 三个 raw 池互相差不到 0.063，没有按日期排序的规律；另外 11 个 Python 仓库上 2022 与 2026 的 PR 只差 0.019，也不是污染假说预测的"cutoff 之后优势变小"。作者自己补了句，仓库数太少，措辞或日期的温和影响排除不掉。这份克制我喜欢。

## 🔬 机制归因：优势坐在"查询缺词"上

现在轮到 $\tau$ 登场。

![图3：稠密优势随查询区分度衰减](https://www.mulanai.com/fs/files/1121_f61a997b_fig_intr.png)

*图3：论文 Figure 4，604 条 Cur-Pre 加原始 Raw-Post 查询上，premium $\Delta$ 随 $\tau$（MaxIDF）的十分位均值，红色圆点是十分位均值、粉色带是 query-bootstrap 95% 置信区间、蓝色虚线是线性拟合。横轴 $\tau$ 从约 4 到 10，纵轴 $\Delta$ 从 0.4 到 -0.1。走势清楚：低 $\tau$ 一侧 premium 约 0.18 到 0.28，高 $\tau$ 一侧掉到 0.04 附近。三条绿色竖线标出附录里的三个示例查询 (C)(B)(A)。*

具体数字：604 条查询上，最低 $\tau$ 四分位的 premium 是 $+0.217$，最高四分位只有 $+0.050$；换成整文件 BM25，从 $+0.125$ 一路到 $-0.046$。翻译过来——**查询和目标代码共享的最稀有词越是普通词，稠密检索赢得越多**。反过来，查询里一旦带着代码里那个罕见的类名、函数名、错误码，BM25 自己就能找到，稠密模型的用武之地就没了。

不过作者马上给自己泼了冷水：逐查询的相关只有 $r = -0.124$，这是组均值的规律，不是"给一条查询算个 $\tau$ 就能预言胜负"。而且 $\tau$ 是在这批 slice 上挑出来的。

![图4：38 个评测切面上的衰减规律（探索性）](https://www.mulanai.com/fs/files/1121_f98fa40a_fig_law_.png)

*图4：论文 Figure 5，探索性分析。(a) 横轴是仓库内 $\tau$ 百分位，纵轴是按切面中心化后的 premium 五分位均值；38 条细线按家族着色——蓝 Cur-Pre(curated)、橙 Raw-Post、绿 Raw-Pre'22/'23、黄 Held-out、粉 Desc(LLM 描述)、紫其它语言，黑色粗线是合并均值及 95% 带，从约 +0.09 一路压到 -0.05 再到 -0.045。(b) 逐切面斜率及 95% 置信区间，黑色虚线标出公共斜率 -0.165；38 个切面里 37 个斜率为负，绝大多数区间贴着或跨过零线。*

这张图挺漂亮，38 个切面（不同挖掘方式、13 个 encoder、5 种语言）里 37 个负斜率，公共斜率 -0.165。但我得把作者的免责声明一起抄过来：这是探索性的，$\tau$ 在这些切面上选的，而预注册的 29 个 held-out 仓库检验虽然符号一致，区间却盖住了零——附录 N 的标题直接写着 "The preregistered held-out test was not met"。所以这条"规律"还没坐实，别拿来当定律用。这块我自己也还在消化，作者把探索性和预注册结果分开摆，比含糊带过要干净得多。

### 把缺的词补回去

如果优势真来自"查询里少了代码的词"，那就把词补上，看谁受益更大。

generate-then-grep 的做法：一个 qwen35-122B，temperature 0，一个冻死的 prompt，只读剥离后的查询，**看不到 gold 路径也看不到 patch**，让它写出标识符、文件/模块提示、API、错误词和一段代码骨架，然后整段 prepend 到查询前面给 BM25 用。

| 池 | dense | BM25 原查询 | BM25 + 锚点 | premium | 补词后 |
|---|---|---|---|---|---|
| Cur-Pre | 0.532 | 0.498 | 0.613 | +0.034 | -0.081 |
| Raw-Post | 0.597 | 0.539 | 0.651 | +0.059 | -0.054 |
| Raw-Pre'23 | 0.544 | 0.455 | 0.603 | +0.089 | -0.059 |
| Raw-Pre'22 | 0.572 | 0.447 | 0.635 | +0.125 | -0.062 |

*表2：论文 Table 2，整文件 BM25 两臂，dense 是 $c=1000$ 的标准编码器；n 依次 472、288、138、367。premium 列是补词前 dense 减 BM25，末列是补词后。"-0.081" 那格在原文里是加粗的，表示按仓库聚类的 95% 区间不跨零。*

BM25 一口气涨 0.11 到 0.19 nDCG@10，四个池点估计上再没落后过稠密检索，Cur-Pre 上还反超 0.081。同样的补词文本喂给 encoder，只涨 0.03 到 0.07，BM25 涨 0.12 到 0.21，差值在每个池都不跨零。再拆细：真正管用的是标识符、API、错误词，纯把查询改写成通顺的检索短语没用；RM3 伪相关反馈甚至把 BM25 拉低了。

防污染的对照也做了。在生成器发布之后才开的 held-out PR 上，generate-then-grep 仍领先 0.094，记忆具体改动解释不掉；换成 Qwen3-Embedding-8B，三个 raw 池里两个 premium 更大，补词后一样不再领先；SPLADE 和 ColBERTv2 全程低于标准 encoder；小一些、权重量级匹配的生成器能关掉三分之二到 80% 的优势——方向稳，幅度看生成器。

**这里藏着全篇最值钱的一句诚实**：作者明说，生成器可能"认识"这些仓库，所以这套操作是**替换掉了 premium，并没有解释它从哪来**（"this replaces the premium but does not explain it"）。补词能追平，不等于"稠密优势 = 词没写全"这个因果链被证明。很多论文到这一步就开始宣称机制被破解了，这篇没有。我是真的觉得这个分寸感比数据更难得。

另外 5.4 节还有个反直觉的消融：把查询和 gold 共享的 5 个最稀有 token 换成合成字符串，如果稠密模型不依赖这些词，premium 该上升才对。结果 Python 上没升，两个检索器一起塌，encoder 掉掉三分之一到近一半的 nDCG@10。作者猜是被换掉的多半是普通词，编辑顺手把任务语义也删了。结论很克制：$\tau$ 能指出优势**在哪**，但它不是可以拧的旋钮。

## 🔧 别逐条路由，固定融合就够了

BM25 在 24% 的 Cur-Pre 和 21% 的 Raw-Post 查询上严格赢过稠密检索，一个逐查询的 oracle 能再添约 0.09 nDCG@10。有 headroom，那能不能学着挑？

作者试了约 30 个 router，特征涵盖查询结构、两个列表的一致性、分数；还试了查询特征上的分类器、查询 embedding 上的逻辑回归、两个 zero-shot LLM 裁判（qwen35-122B、gemma-4-31B-it）。AUROC 全在 0.47 到 0.54，每个区间都盖住 0.5。调过之后，每个都退化成"几乎永远选 dense"；不调，裁判又给大多数查询选了关键词检索，直接亏掉 0.1 以上。

唯一一个在开发集上增益不跨零的 router 被冻结，拿去那个从没被任何分析碰过的 lockbox（539 条查询、91 个仓库）上只跑了一次：相对"永远用融合"只多 0.005，而 oracle 是 0.077，区间盖住零，没达到预注册的标准。这个"冻结 + 一次性打分"的流程，说实话比大多数论文的调参式对比可信得多。

| 流水线 | 每条查询额外成本 | Dev | Lockbox |
|---|---|---|---|
| BM25，整文件 | 无 | 0.507 | 0.432 |
| Dense | 一次查询 embedding | 0.550 | 0.533 |
| RRF(dense, BM25) | 一次 embedding | 0.609 | 0.551 |
| Reranker | 一次 jina-reranker-v3 | 0.574 | — |
| Router（冻结） | 一次 embedding | 0.557 | — |
| Generate-then-grep | 一次 LLM 生成 | 0.625 | 0.534 |
| RRF(dense, gen.) | 一次 LLM + 一次 embedding | 0.638 | 0.578 |

*表3：论文 Table 3，按每条查询成本排的固定流水线，nDCG@10。Dev 是 604 条开发查询/10 仓库，Lockbox 是 539 条/91 仓库，按预注册的 released labels 打一次分。RRF 是倒数排名融合。*

固定融合在开发集上比纯 dense 高 0.060，跟 generate-then-grep 融合高 0.089；listwise reranker 在同候选集上并不比融合好。到了 lockbox，两种固定融合仍领先 dense 0.019/0.045（released labels）和 0.027/0.062（源文件标注），按仓库等权也站得住。

看明白没：逐条挑检索器这事儿，理论上有一大块肉，实际上从查询里读不出来。与其养一个 router，不如把两路结果固定融合，省事、稳、还过了预注册检验。

## ⚠️ Agent 边界：端到端分数根本不归检索管

开头那拨"用 grep 也活得好好的"的工程师，论文给了个正面回答。

固定 LLM、96 个 held-out 任务，让 SWE-agent 分别拿 unrestricted shell + `grep`、词法索引、稠密索引、$\widehat{\tau}$-router 四种工具，exact-match（最终 diff 编辑的文件集合等于 gold）全挤在约 0.04 的范围内。换个 LLM 会怎样？三种 LLM 乘四种配置，30 任务子集上 exact-match 从 0.03 一路铺到 0.30。

对 agent 来说，**换模型比换搜索工具重要得多**。

批判性地补两句：这里不跑测试，量的是定位能力不是修复正确率；作者在附录 Q.2 还自查出任务环境有污染、修掉并重跑了，把"哪里出了错、改了什么、改变了什么"单列一节。这种自曝其短在 agent 论文里不多见。

回到开头那个问题——benchmark 的 0.2 和工程师的 grep 可以都对。前者量的是检索模块在某种设置下的排序分数，后者是整条 agent 链路里的一环。端到端分数不拆开，你根本不知道该优化搜索、推理还是编辑。

## 💡 我的判断

给这篇论文打个标签：不是底层突破，是一次**评测卫生 + 机制归因**的扎实工程研究，选题切的是真痛点，实验设计比结论更值钱。

值钱在哪？预注册 lockbox 只打分一次、匹配复现把同一改动的两种措辞配对、两套标注规则并列报、时间窗口专门绕开 cutoff、自己承认 BM25 在评测查询上调优因而结论是稠密的下界、明确区分"替换了 premium"和"解释了 premium"。在一堆 demo 炫但实验经不起推敲的工作里，这种扎实反而稀缺。

局限也实打实：Core 就 10 个 Python 仓库、跨语言每种只 1 个仓库，温和效应排除不掉；BM25 在评测查询上调过；gold 是"一次改动编辑的文件"，函数级、行级目标没测；生成结论绑生成器；$\tau$ 那条漂亮的衰减规律没过预注册检验。这块我不是特别确定的是，generate-then-grep 里"LLM 可能认识仓库"到底把结论侵蚀了多少——作者排除了记忆具体改动，但仓库级熟悉度和"真的从任务描述推理出标识符"之间，论文没有给出干净的切分办法。

### 可迁移的准则（重点给做低成本、可解释检索方案的人）

这篇跟"工程化优先、能审计、别乱堆算力"的检索路线特别对口，三条准则直接能搬：

**G1｜量稠密增益之前，先把 lexical baseline 做公平**。 给 BM25 喂整文件而不是沿用稠密的分块，剥掉 PR 模板套话，先声明哪些被编辑的文件算相关、并对每个查询来源用同一把尺子。稠密数字旁边同时摆 Recall@10 和一个补了锚点词的 BM25 臂。不然你优化的是评测漏洞，不是系统。

**G2｜保留稠密检索，但固定融合，别做逐查询路由**。 倒数排名融合在开发集和 539 条 lockbox 上都赢过单路，约 30 个 router 没一个达标。如果调用方是 agent，预算先花在模型上，别先花在搜索端点上——5.7 节那组数据摆得很清楚了。

**G3｜查询缺代码的词，就先把词补上再搜**。 一次 LLM 调用起草缺失的标识符，整文件 BM25 就能顶上一个 embedding 索引。成本账作者算得很实在：这次调用每条查询都要重来，所以**低频搜索的仓库**用 generate-then-grep 更划算，不用养索引；**高频搜索的仓库**反而是 embedding 索引便宜。顺着这条往下想，对 TreeSearch 这类强调结构、可解释、可控预算的检索方案，结论就更直接了——显式标识符 + 字面匹配是可审计的，检索结果为什么命中能逐条摆出来；而稠密检索的领先，很大一部分可以用"把词补全"这种廉价、可解释的操作复现。值得为它单独训 encoder、单独维护一套向量基础设施吗？至少得先按 G1 把 baseline 擦干净再回答。

还有一条方法论上的迁移：**先拆指标，再归因模块**。端到端分数高，不等于检索是瓶颈；benchmark 分数高，不等于方法本身强。中间那层因果，得靠固定变量、并列标注、预注册检验去挤，不能靠直觉。

## 🔚 收个尾

所以，稠密优势究竟衡量了什么？

说到底，它主要衡量了两件事：评测有没有给 BM25 公平条件，以及查询里有没有写出代码自己的稀有词。至于"语义理解能力更强"这层解释，论文没能证实，也没假装证实——它甚至把"补词能追平"和"解释优势来源"之间的距离明明白白留了出来。

留一个我自己还没想清楚的追问：如果一次 LLM 补词加 `grep` 就能复现大半优势，那我们是不是把检索问题偷偷换成了生成问题？补词依赖 LLM 对仓库的熟悉度，这条路在私有仓库、新仓库、冷启动场景还能走多远，论文没测。这个口子，可能才是下一个值得投入的方向。

如果你也在做代码检索或者给 agent 配搜索工具，我的建议是先按 G1 把 baseline 重做一遍，很可能你会发现那 0.2 分本来就没那么实。
