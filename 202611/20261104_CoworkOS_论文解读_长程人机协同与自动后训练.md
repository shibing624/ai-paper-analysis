# CoworkOS：AI 同事真正缺的，可能不是更聪明，而是记得把工作做完

你有没有遇到过这样的 AI 助手：代码写得挺快，网页也能做出来，可你让它盯一次耗时数小时的训练，事情就开始变味了。上下文一压缩，它忘了上一轮为什么改数据；会话一中断，它不知道后台任务跑到哪；你在 CAD 里手动挪了一个零件，它还拿着旧版本继续改。

单次回答漂亮，和长期对一件工作负责，是两回事。

CoworkOS 盯上的正是这条缝。它没有再训练一个“更聪明”的模型，而是把模型外面的运行时、工具、工作区和记忆重新组织了一遍，让智能体既能做复杂交付，也能在跨天、跨会话的任务里持续关注、等待和决策。

**核心摘要**：CoworkOS 是一个面向长程人机协作的通用 Agent Harness，把任务策略与执行管理拆开：Main Agent 负责规划、委派和验收，Coordinator Runtime 负责调度、状态与反馈，Subagents 在独立上下文中完成局部工作。共享应用、分层工作区和持久语义记忆，则让人和智能体围绕同一份产物持续修改。统一使用 GLM-5.3 时，它在 12 项基准上整体与 Codex、DeepSeek Harness 等系统接近，并在生产力与机器学习编程领域平均分领先。更吸引人的是五轮自动后训练案例：八项基准均分从 33.19 升到 42.95。不过，这更像一份扎实的系统工程报告，而不是已经证明通用自我进化的算法突破。

## 一、真正的难题：不是把任务拆开，而是一直对结果负责

Agent 系统早期更像工作流：模型推理一步，调用一次工具，再根据观察继续行动。ReAct、Reflexion、MetaGPT、AFlow 等工作，大多围绕轨迹组织、反馈或协作流程展开。今天的编程助手和办公智能体则进入另一种场景：产物会不断变化，用户会中途插手，训练、构建和搜索也不会因为模型停一轮就自动结束。

CoworkOS 把这些要求压成两个维度。

| 维度 | 它关心什么 | 典型任务 | 主要失败方式 |
|---|---|---|---|
| 任务复杂度 | 决策数量、分支依赖、工具与证据的组合 | 做网站、写演示文稿、构建 CAD、跑机器学习实验 | 局部做对了，最终产物不完整或无法验收 |
| 时间跨度 | 目标保持活跃多久，期间要等待多少外部变化 | 盯训练、跨会话推进项目、监控事件 | 忘记目标、丢失状态、重复执行、错过反馈 |

这个划分挺实用。一个监控任务可能每一步都很简单，却要连续负责几天；一个复杂设计可能不需要等很久，却要求大量推理和验证。自动后训练恰好把两者叠在一起：先分析弱点，再改数据、训练、等待、评测，然后拿新结果修改下一轮方案。

所以，问题不再是“模型下一步该调用哪个工具”，而是“谁保存目标、谁维护状态、谁决定验收、谁在中断后接着干”。这就是 Harness 的价值。

## 二、三层运行时：把决策权与执行管理拆开

CoworkOS 的核心分工可以压成一句话：**模型决定做什么，运行时确保事情真的持续推进。**

![CoworkOS 三层运行时架构与共享行动空间](https://arxiv.org/html/2611.03178v1/framework-body.png)

*图 3：Main Agent 位于顶层，执行 Plan、Act/Delegate、Review、Accept；Coordinator Runtime 负责调用注册、调度、Inbox 路由、Jobs 与监控；底层 Subagents 各自维护 Context → Action → Observation 循环。右侧是通用工具、原生应用服务与共享资源，底部工作区保存语义记忆、Run 记录、已验收产物和资源引用。同步委派留在调用链上，异步委派则让 Main 先处理其他工作。*

### Main Agent：唯一对全局目标负责的人

Main 面向用户，保留完整任务上下文，既能直接调用工具，也能把边界清楚的工作委派出去。委派不是随手扔一句“你帮我看看”，而是一份证据契约：目标是什么、约束是什么、允许使用哪些能力、回来时必须带什么结果和证据。

这个设计很克制。Subagent 不必把漫长的中间轨迹全部灌回 Main，只返回报告、产物引用、支持记录和执行状态。Main 再根据这些信息决定整合、返工还是验收，全局责任没有跟着任务一起被拆散。

### Coordinator Runtime：不是另一个会聊天的 Agent

Coordinator 是控制面，不负责另起一套任务策略。它给每次委派稳定身份，保存分配、执行状态和待投递反馈，通过队列、租约与确认机制维护归属和投递状态。

这件事听起来不炫，却是长程系统的命门。模型上下文可以消失，进程可以重启，但“哪个子任务归谁、结果有没有送达、回调是否处理过”不能靠模型回忆。运行时保存这些事实，Main 才能根据操作证据继续，而不是根据一段可能已经不完整的聊天历史猜测。

### Subagents：隔离上下文，而不是隔离责任

每个 Subagent 在独立上下文中处理局部任务，可以进行较长的搜索、工具交互和验证。系统支持三种通信路径：Main 向 Subagent 下发与纠偏，Subagent 之间传递简短消息或文件引用，Subagent 向 Main 返回结果或请求决策。

同级通信被刻意做得很轻。它只解决接口、假设和候选产物之间的局部依赖，不形成第二套控制层级。任务范围、继续委派和最终验收仍归 Main。

同步与异步也值得分开看：

| 执行方式 | 结果如何返回 | 适合场景 |
|---|---|---|
| 同步委派 | 结果留在 Main 当前调用路径 | 下一步强依赖该结果，需要立即等待 |
| 异步委派 | 先返回确认与标识，终态稍后进入 Main 的 Inbox | 可并行调查、长工具链、耗时执行 |
| 后台 Job | 持久保存进程身份、状态与日志，按结果或计划唤醒 Main | 训练、构建、持续监控 |

说实话，我更看重这里的“可恢复投递”，而不是“多智能体”标签。多开几个 Agent 很容易，难的是重启以后不重复干活、不漏结果。

## 三、共享应用：人不是只在聊天框里提意见

很多所谓 human-in-the-loop，其实只是让人再发一句提示词。CoworkOS 把另一条路也接进来了：人可以直接改文档、演示文稿、CAD 参数或 Blender 场景，智能体再读取这份已提交的产物继续工作。

关键不在接了多少软件，而在**人和 Agent 改的是不是同一个有身份、有版本的资源**。

平台用 $r=(\iota,\kappa,x,v)$ 表示资源，其中 $\iota$ 是身份，$\kappa$ 是类型，$x$ 是应用内容，$v$ 是已提交版本。新操作必须通过版本检查：

$$
\operatorname{Commit}(r,u,\hat v,\alpha)=
\begin{cases}
(\iota,\kappa,T_\kappa(x,u,\alpha),v+1), & \hat v=v,\\
\text{conflict}, & \hat v\ne v.
\end{cases}
$$

$\hat v$ 是操作基于的旧版本，$\alpha$ 记录人或 Agent 的操作者身份，$T_\kappa$ 则保留不同应用自己的编辑语义。版本一致才提交；不一致就返回冲突，不静默覆盖别人的修改。

这就是共享编辑最朴素的工程底线。你想想看，如果人刚把楼上退出一米，Agent 还拿旧模型覆盖回去，再漂亮的自然语言协作也没用。

Subagent 还可以先做私有候选，而不是直接在共享产物上边探索边改。Main 审核后才决定是否合入；若基线已经变化，候选会保留下来重新检查，而不是强行应用。

系统接入分两类：原生应用由平台管理资源、版本与历史；MCP 集成则保留外部软件的所有权和接口。论文也承认，外部软件若没有暴露资源操作，就不能凭空获得同样的版本保证。这个边界写得比较诚实。

## 四、持久工作区：把“我记得”改成“系统查得到”

长程任务不能把所有信息都塞进上下文。CoworkOS 将任务保留状态拆成工作对象与产物引用、进度与决策证据、运行与等待状态三部分，再用 Run 记录每一次具体执行。

![CoworkOS 的任务文件结构、人机协同 CAD 修改和独立应用资源存储](https://arxiv.org/html/2611.03178v1/method-workspace.png)

*图 4：左侧目录把 Main、Subagent 与 Runtime 的记录分区保存，同时分开 inputs、artifacts、agents、runs、sessions 和 applications。中间展示一栋房屋从 v1 到 v4 的修改：Agent 加楼层和阳台，人直接调整上层位置，Agent 再补遮阳、台阶和栏杆。下方说明 Task A、Task B 通过身份与绑定引用同一份独立存储的原生资源，内容、版本和编辑历史不依赖某个会话窗口。*

工作区里有几条很具体的规则：

- Agent 工作区跨 Run 保留，后续执行可以复用已有文件；每个 Run 又单独保存事件、检查点和结果。
- Agent 默认只写自己的工作区，读取他人发现则通过共享引用；Main 审核候选后再发布到 Task 产物区。
- 长计算作为后台 Job 保存身份、进程记录和日志。进程消失但没有退出记录时，结果被标为不确定，而不是假装成功或失败。
- 外部监控由确定性脚本采样并对比基线，没变化就不调用模型；候选事件再交给 Main 或语义分析，减少空转成本。
- 等待前必须记录进度、等待条件和下一步。持续目标若没有活跃观察源，也没有明确复查时间，运行时会拒绝这次等待。

上下文管理也不是简单截断。Main 先更新包含目标、已完成工作、下一步和约束的语义记忆，再在阶段边界重建上下文：

$$
c^{\mathrm M}_{t,\mathrm{task}}=\Phi_{\mathrm{ctx}}\bigl(m_T,\rho_T(t),d_T(t)\bigr)\oplus h^{\mathrm M}_{t,\mathrm{recent}}.
$$

$m_T$ 是语义记忆，$\rho_T(t)$ 是当前运行时与目标状态，$d_T(t)$ 是实验摘要，$h^{\mathrm M}_{t,\mathrm{recent}}$ 是保留的近期历史。显式重置可以清空近期历史，自动压缩则保留一段近期消息；摘要和消息游标一起落盘，避免“摘要是新的、游标还是旧的”这种恢复错位。

我觉得这块最值钱的不是某个记忆算法，而是它把记忆、运行时状态和实验证据分开。模型记住“上一轮准备改数据配比”，系统还要能回答“训练是否还在跑、结果文件在哪里、哪些反馈没消费”。两类问题不能混成一段摘要。

四个领域平均分里，CoworkOS 都进前二，生产力和 ML 编程排第一。工具使用只比 DSH 低 0.09，搜索只比 OpenHands 低 0.08。ML 编程两项虽都第一，领先 DSH 的幅度却只有 0.20 和 0.05，称不上拉开差距。

有个表格细节很容易被略过：GDPVal 行展示的是 Elo，但生产力领域平均并不把 Elo 直接和其他百分制分数混合，而是使用 220 个任务的平局调整胜率。没有这个换算，领域平均根本没意义。

评测配置也并非轻量。MLE-Bench-Lite 用 22 个 low-split 竞赛，每题五小时、4 CPU、32 GiB 内存和一张 H200；MLS-Bench 的 30 个 Lite 任务也有五小时预算和按任务分配的 H200。这里比较的是完整 Harness 的执行结果，不是廉价、统一 token 预算下的纯模型能力。论文没有给出多随机种子方差，因此那些零点几分的领先不宜读得太重。

### 24 个真实案例：看交付物，而不是只看分数

![Codex、DeepSeek Harness 与 CoworkOS 在六类真实任务上的定性产物对比](https://arxiv.org/html/2611.03178v1/qualitative-cases-comparison.png)

*图 6：24 个案例覆盖 4 个前端网站、4 个游戏、4 个 Office 演示、8 个交互可视化、2 个 CAD 装配体和 2 个 Blender 场景。每行从左到右为 Codex、DSH、CoworkOS。图里能看到布局、材质、组件细节和信息组织差异，但它是定性展示，不是成功率或用户偏好统计。*

几个观察挺具体。Ridge Pack 中，CoworkOS 不只说“放不下”，还解释剩余总体积不代表可用连续空间；Paper Glider 的场景包含书架、窗帘、座位、梁和阴影，结果弹窗也说明漏环容忍规则；Office 案例里，它把数值、标签和解释留在各自卡片内，并将入流减少与蒸发画成两条汇入湖泊萎缩的分支。

附录没有一味挑好看的例子。VESPER Speaker 中，CoworkOS 多次操作也没有清楚露出分离内部结构；Codex 的 Saturn Atlas 剖面反而更清楚。Blender 的 After the Fall 还保留了公交车轮或车身下部与路面之间的可见缝隙。作者也明确说，CAD 展示不能证明参数可编辑、无干涉、可制造，场景深度也不能证明碰撞正确。

这种自我限定让我对定性部分更信任一点。不过，72 个产物仍主要来自人工检查，没有统一用户评分和跨多次生成的稳定性统计，不能把“某些视图更清楚”扩大成全面交付优势。

## 六、五轮自动后训练：最有意思，也最容易被误读

这个案例里，GLM-5.3 是控制器和主要数据教师，Qwen3.6-35B-A3B 是被训练、被评测的模型。R0 先用来自五个来源的 1,345 条工具交互轨迹做种子 SFT，随后执行五轮反馈驱动的后训练：

```text
评测当前模型
  → 诊断能力缺口并修改数据管线
  → 生成、验证、过滤数据
  → SFT
  → 重新评测并进入下一轮
```

所有训练数据经过 BM25 任务相似度过滤，阈值为 0.8，用来控制训练与评测任务的近重复；训练历史还会单独去重。八个评测分数取算术平均，每项权重为 12.5。这里的 GDPVal 是累计 rubric 归一化得分，不是主实验里的 Elo。

| 基准 | R0 | R1 | R2 | R3 | R4 | R5 | R5−R0 |
|---|---:|---:|---:|---:|---:|---:|---:|
| Automation | 11.00 | 35.50 | 30.83 | 39.49 | 41.83 | **44.15** | +33.15 |
| BFCL v4 | **63.48** | 61.81 | 61.76 | 62.11 | 61.76 | 70.83 | +7.35 |
| OfficeQA | 55.64 | 53.38 | 52.63 | 56.14 | 59.40 | **62.11** | +6.47 |
| Tau-3 Banking | 14.43 | 19.59 | 16.49 | 18.57 | 22.68 | 22.68 | +8.25 |
| Harvey LAB | 3.33 | 2.50 | 6.78 | 7.53 | 8.42 | **11.08** | +7.75 |
| SkillsBench | 20.85 | 30.38 | 23.18 | 34.16 | 33.84 | **35.76** | +14.91 |
| GDPVal | 74.11 | 75.43 | **77.27** | 75.14 | 76.45 | 76.45 | +2.34 |
| JobBench | 22.66 | 16.93 | 18.27 | 20.58 | **21.32** | 20.53 | −2.13 |
| 八项均分 | 33.19 | 36.94 | 35.90 | 39.22 | 40.71 | **42.95** | +9.76 |

均分涨了 9.76，七项超过 R0，这些数字确实能打。Automation 增幅最大，达到 33.15；SkillsBench 涨 14.91。可别只看首尾：R2 均分下降 1.04，JobBench 最终还比 R0 低 2.13，GDPVal 的最好成绩停在 R2。曲线不是自动向上的，系统是在波动中修改方案。

### 每轮到底改了什么

| 轮次 | 训练起点 | 独立轨迹与组成 | Epochs | 优化步数 |
|---|---|---|---:|---:|
| R0 | base | 五个来源的 1,345 条种子轨迹 | 1 | 66 |
| R1 | base | 1,345 条种子 + 244 条新增 | 1 | 69 |
| R2 | R1 | 135 条首次使用：77 条此前保留 + 58 条新生成 | 1 | 10 |
| R3 | R2 | 558 条首次使用：Automation 437、OfficeQA 85、Tau-3 22、SkillsBench 14 | 4 | 24 |
| R4 | R3 | 453 条首次使用，覆盖 Automation、OfficeQA、Tau-3、SkillsBench | 4 | 22 |
| R5 | R4 | 332 条新增：BFCL 203、Automation 84、OfficeQA 26、Tau-3 17、JobBench 2 | 4 | 20 |

R2 到 R5 的新数据采样倍数为 24，旧数据为 1。R2 只用 135 条首次使用轨迹并高强度重复，均分随后回落；复盘发现 42 条轨迹占了 84.2% 的监督 token，少量长轨迹主导了训练。R3 把独立数据扩到 558 条、训练四轮，均分回升到 39.22。

R3 的 Automation 数据占 78.3%，该任务之后连续改善；R5 则把 61.1% 的新轨迹转向函数调用，BFCL 从 R4 的 61.76 升到 70.83。失败分析也落到了演示规则上：R4 要求逐项处理、多约束检查和执行后状态回读，R5 补充实体与参数绑定、参数类型、必填字段等函数调用示范。

看到这里，我觉得这套系统真正的能力是“把评测失败翻译成下一轮数据和验收规则”，而不是神奇地发明了新训练算法。

也要把 RSI 的边界说清：控制器 GLM-5.3 并没有通过这套流程改进自身，被改进的是另一个 Qwen 模型；各轮同时改变数据、起点和训练策略，不能把提升归因给某个单独特定机制；轮次也不代表实际经过时间。论文没有报告总训练成本、人工介入量或多轮重复实验。因此，它是自动后训练的长程协作案例，还不是模型完全自主自我进化的证明。

## 七、我的判断：强在系统闭环，弱在因果拆解

把 CoworkOS 和前置工作放在一起看，它更像一次围绕真实工作场景的系统整合。

| 方案形态 | 主要关注 | CoworkOS 向前补的一层 |
|---|---|---|
| ReAct、Reflexion 等 Agent Workflow | 推理、行动与反馈轨迹 | 把轨迹外的工作状态、等待条件和恢复机制持久化 |
| LangGraph、AutoGen、MetaGPT 等编排框架 | 流程或多 Agent 协作 | 明确全局验收责任、证据返回和可恢复投递 |
| Codex、OpenHands、DeepSeek Harness 等工作环境 | 工具执行与实际交付 | 把共享原生应用、持续监控和跨会话目标放进同一任务生命周期 |

它的亮点不是某条新公式，而是几个机制彼此对得上：异步委派需要 Inbox，Inbox 需要持久状态；人机共编需要版本检查，版本检查需要独立资源生命周期；自动后训练需要实验账本，实验账本又必须和上下文重建、后台 Job 连在一起。这个闭环是完整的。

但论文也有明显缺口。没有针对三层架构、共享应用、持久记忆和 Job 机制的逐项消融，我无法判断 12 项基准的提升分别来自哪里。主实验统一基础模型是公平比较的必要条件，却仍允许不同 Harness 使用不同上下文策略与工具链，分数反映整个系统，不应归因给某一模块。真实案例很丰富，定量用户研究却不足。长程能力主要通过自动后训练展示，跨周监控、异常恢复成功率、重复执行率这些更直接的指标还没有系统报告。

所以我的定位是：**这是一份值得工程团队细读的 Cowork Harness 设计报告，也是一条有说服力的自动后训练案例；它还没有证明哪个组件不可缺，更没有证明通用 RSI 已经到来。**

如果你在做类似系统，可以先借走三个不依赖大框架的做法：把委派写成带证据要求的契约；把等待条件、进程状态和反馈投递放到模型上下文之外；让每一次人工直接编辑都成为可追踪的资源版本。至于“多 Agent 越多越好”，这篇论文并没有这样证明，也不该往这个方向抄。

我更关心一个问题：当 Agent 不只给建议，还能连续几天操作系统、修改产物并启动训练时，验收与权限边界会变成真正的瓶颈。CoworkOS 把责任集中给 Main，方向是对的；下一步需要看到的，是在故障、误操作和权限变化下，这份责任能否被量化地审计与验证。
