# 造训练环境不用让模型做题：RepoFactory 用三个代理指标，把 1 万个真实仓库炼成长程编码训练场

你有没有碰到过这种尴尬——想训一个能从零把整个项目搭出来的 coding agent，手上却没有足够的题。

修 bug 的任务好造。给一个 issue，跑一遍测试，对就是对错就是错，反馈干净利落。可"照着一份需求说明，从空目录开始写出一个能跑通测试的完整仓库"这种长程任务，光是把环境搭出来就够呛：你得有依赖装好的镜像、有原仓库当标准答案、有一套能打分的测试，还得保证这份题不是随便糊两行就能过。更要命的是，等你终于搭出一个候选环境，怎么判断它"值不值得拿来训练"？

以前的做法基本两条路。一条是流水线走到验证就停，跑得通就留、跑不通就扔，至于留下的题能教会模型什么，没人管。另一条更贵：让模型真的去把这道题做一遍，甚至训完一轮再看下游分数，用结果反过来改题。长程任务一次 rollout 动辄几十轮交互，这个反馈回路又慢又烧钱。

所以读到 arXiv:2611.21152 这篇的时候，我的第一反应是：他们居然想把反馈回路里那个最贵的环节整个拆掉。

---

## 核心摘要

这篇论文提出 RepoFactory，一条把真实开源仓库批量转成可验证长程训练环境的流水线，任务设定是"给一份自然语言规格说明和 API 清单，从零重建整个仓库"。真正让我觉得有意思的不是流水线本身，而是它给每个环境打的一个乘性分数 $Q = A \cdot C \cdot S$——有效性、结构耦合度、实现规模，三项全靠验证器执行和静态代码分析就能算出来，完全不需要让解题模型跑一遍。Environment Evolution Loop 拿这个分数当指南，最多 12 轮地改写标准答案、需求说明和测试，把不合格的仓库修活、把太简单的题改难。最终产出 10,159 个环境覆盖 17 个软件领域；用它们微调 Qwen3.5-35B-A3B 得到 RepoHorizen-35B-A3B，NL2Repo-Bench 从 23.8% 涨到 46.4%，涨 22.6 个百分点，五项基准平均涨 8.5 分。坦率讲，这不是底层算法突破，是一次很扎实的工程整合加一个聪明的代理指标设计；但它验证的那条路——不用模型试错也能判断训练价值——比那个 35B 模型本身值钱得多。

## 🎯 问题动机：造环境这件事，卡在三处

作者把现有做法的毛病拆成三条，我觉得拆得挺准，不是硬凑的 related work。

**第一条，流水线太刚，把仓库池子做小了。** DeNovoSWE、MindForge 这类流程是线性的：润色文档、修好构建，标准实现从头到尾不动。一个仓库要是修完还是不能用，就直接丢掉。于是"能不能规模化"几乎等价于"能不能找到更多天然符合固定要求的仓库"。说实话，这在我之前做数据清洗的时候也踩过——过滤条件越写越严，到头来剩下的样本少得可怜，而那些被扔掉的里面明明有一大半只是差个依赖版本。

**第二条，反馈只盯可靠性，不盯训练价值。** RefactorForge、TrajLong 会针对特定能力设计数据，ProgramGym 用执行诊断和覆盖率去修构建、加强测试，都是围绕一份固定标准实现打转。这些信号能告诉你"环境能不能跑"，但告诉不了你"这道题要不要动脑"。一个只要写三个独立小函数就能过的任务，验证器再稳，训练价值也就那样。

**第三条，靠模型执行拿反馈，长程任务上贵得离谱。** BenchEvolver、SETA 用模型表现来指导改题，DataMaster 甚至把下游训练塞进反馈环。短任务还扛得住，长程编码一次 rollout 要写一堆文件、跑一堆测试，成本和时间都被放大，改一轮题的代价高到没法大规模迭代。

三个问题指向同一个缺口：有没有一种**及时、可靠、便宜**的反馈，既能判断环境能不能用，又能判断它值不值得练？

这就是 RepoFactory 想填的坑。

## 🏗️ 方法核心：一个不用解题模型就能算的分数

### 先给一句直觉

别问模型"这道题难不难"，直接问代码本身：标准实现跑不跑得通测试（有效性）、函数之间是不是互相调用纠缠（耦合）、要写多少代码和装多少依赖（规模）。三个数一乘，就是这个环境的"训练性价比"。全静态、全可复算，秒级出结果。

这个思路真的挺精巧。它把"训练价值"这个本来要等下游评测才能知道的滞后量，换成了一个当场能算的代理量。

### 任务怎么定义

一个环境被形式化成 $e = (I, W, V, O)$：

| 符号 | 含义 | 训练时对谁可见 |
|------|------|--------------|
| $I$ | 自然语言规格说明 + API 清单 | 可见 |
| $W$ | 隔离工作区与运行时（依赖已装、外网已断） | 可见 |
| $V$ | 验证器（继承自原仓库的测试套件） | 隐藏，仅验证时可用 |
| $O$ | 原仓库的标准实现（oracle） | 隐藏 |

智能体 $\pi$ 拿到 $(I, W)$，从零写出项目 $P = \pi(I, W)$，由 $V(P) \in [0,1]$ 打分。这个设定挺关键：智能体看不到原仓库，也看不到评测代码，只能靠规格说明和自己对 API 的理解把整个项目重建出来。测试全都来自原仓库，不是只查几个端到端结果，而是铺在公开接口上的密集验证。

### 三个因子，一个乘法

核心目标函数就一行：

$$Q = A \cdot C \cdot S$$

用乘法而不是加权和，是个有态度的设计——任何一项塌了，整个环境归零。你想想看，一个跑不通验证的环境，代码写得再多、耦合再漂亮也没有训练价值；反过来一个只有二十行独立函数的环境，有效性再高也教不会长程协调。

**有效性 $A$** 是个二值门：

$$A=\begin{cases}1,& V(O)=1\ \text{and}\ V(P_0)=0\\ 0,& \text{otherwise}\end{cases}$$

标准实现 $O$ 必须拿满分，未经改动的初始工作区 $P_0$ 必须拿零分。后者这条容易被忽略，但它挡的是"题太水"——如果空目录都能过测试，说明验证器根本没在检查实现。

**结构耦合度 $C$** 用归一化传播成本：

$$C = \frac{R}{N^{2}}$$

$N$ 是分析出的函数数量，$R$ 是静态内部调用图里可达的有序函数对数量（含自环）。说人话就是：函数之间互相调用得越盘根错节，$C$ 越大，重建时越要盯着跨文件的一致性。$N^2$ 是个归一化，让不同规模的仓库能放在同一把尺子上比。

**实现规模 $S$** 把代码量和依赖广度摞在一起：

$$S = \log_{10}(\mathrm{LOC}) + \log_{10}(1+D) - 2$$

$\mathrm{LOC}$ 是源码行数，$D$ 是直接运行时依赖数。取对数是为了压住长尾，减 2 相当于把"一千行代码、零依赖"这种基线归到 1 附近，方便设阈值。

有一处我得坦白：$S$ 这个式子里行数和对数依赖直接相加，量纲上其实挺随意的，减 2 更像经验标定而非推导出来的常数。论文也没给敏感性分析。这块我自己不是特别确定它在跨语言场景下还剩多少意义，后面聊局限再说。

三项都在当前候选上算，演化循环就是在固定预算里把 $Q$ 往上推。

### 流水线全景

*图1：RepoFactory 六阶段全景。左侧 (a)-(e) 是从仓库搜索到环境物化的构建链，右侧 (f) 是环境演化循环。图里把 Q = A·C·S、阈值 S ≥ 0.5 / C ≥ 0.01、以及"只保留分数严格上升的修改"这些关键规则都画了出来。*

图1 信息量很大，顺着箭头捋一遍：

**阶段 a，仓库搜索与过滤**。从代码托管平台捞候选，排除已进入既有评测集的项目（这点很重要，防数据泄漏）。硬门槛写得很实在：要有包元数据和非空本地测试集、至少 5 个实现文件、Python 代码少于 4 万行；不要外部服务、出站网络、图形界面、专用硬件；网络类项目只有在测试里 mock 了外部调用或只用本地连接时才留。过滤条件还包括 Recent、Non-Fork、Not Archived、≥10 Stars，以及 Testable ≥1 Test、Scale ≥5 Files / <40k LOC、Isolated Offline CPU only。

**阶段 b，运行时构建与仓库分析**。把仓库复制进隔离目录，按构建文件和依赖清单打 Docker 镜像，由 agent 装依赖、找测试命令、必要时改镜像或执行配置。只有在全新容器、资源受限、断网条件下全部测试通过，仓库才被留下。然后在一个只读容器里做 AST 扫描，抽出公开类、函数、方法及其签名、异常、返回信息，记录测试 import 了哪些仓库符号，并生成不含测试文件的实现树。图里 Extract Evidence 那四个出口——Public APIs、Test Imports、Impl. Tree、Read-only AST Scan——就是后面合成规格说明和计算 $C$、$S$ 的原料。

**阶段 c，规格说明合成**。由 synthesis agent 写自然语言规格说明和 API manifest。这里有个很实用的细节：功能写对了但接口名或 import 路径跟测试对不上，照样全挂。所以流水线会把规格说明和 API 清单拿去跟原测试 import 的符号做覆盖检查，把缺失符号和它的 import 记录打回重写。图里那个 `12 / 15 API coverage` 和 `Missing Symbols` 就是在演示这一步，还给了个具体例子：测试里的 `tests/test_parser.py` 从 `pkg.import.JsonParser` 取符号，规格说明里就得把它点名。

**阶段 d 与 e，环境物化**。规格说明 + 验证过的运行时镜像合成环境 $e=(I,W,V,O)$。$I$、$W$ 对智能体可见，$V$、$O$ 锁起来，只在验证时开。

**阶段 f，环境演化循环**。右上角那个绿色大框，maximize $Q = A \cdot C \cdot S$。下面单独讲。

### 演化循环：先救活，再提质

循环的规则写得相当具体，我按执行顺序复述一遍，因为这部分是全文最值钱的地方：

1. 先查有效性 $A$。$V(O)=1$ 且 $V(P_0)=0$ 两个条件任一不满足，构造 agent 就拿验证报告和执行轨迹定位原因，修完重新验。**只有两个检查都过了，才开始优化 $S$ 和 $C$。**
2. 对每个有效候选，把 $S$、$C$ 分别跟阈值 0.5 和 0.01 比，优先补低于阈值的那项。两项都达标了，再按 $Q$ 挑一项继续推。
3. agent 决定怎么改标准实现 $O$、规格说明 $I$、测试 $V$ 三者，并且必须让描述和评测跟改后的功能保持一致——这一条是防止"改了题但答案没跟上"。
4. 每次改完重新验 $A$，挂了就退回修复。针对 $S$ 或 $C$ 的修改，**只有被选中的分数严格上升才保留**，否则回滚到上一版。
5. 最多 12 轮。每一轮靠验证器执行 + 代码分析给反馈，没有解题 agent 的 rollout，也没有下游训练和评测。

所有构造 agent 用的是 Qwen3.8-Max。

回到开头那个问题，这个循环的巧妙之处在于它同时干了两件事：$A$ 把本来要丢弃的仓库**救回来**，提高产出率；$S$ 和 $C$ 把有效的题**改得更值得练**，提高训练价值，而且两件事共用同一套便宜反馈。

顺手放一张对比，能更清楚它站在什么位置：

| 方案 | 反馈来源 | 要不要解题 rollout | 要不要下游训练 | 改不改标准实现 |
|------|---------|------------------|--------------|--------------|
| DeNovoSWE / MindForge | 构建与文档检查 | 不需要 | 不需要 | 不改，固定 |
| ProgramGym | 执行诊断 + 覆盖率 | 不需要 | 不需要 | 不改，围绕固定实现加强测试 |
| RefactorForge / TrajLong | 针对能力设计数据 | 不需要 | 不需要 | 部分改，但不优化任务内容 |
| BenchEvolver / SETA | 模型表现 | **需要** | 视方案而定 | 改 |
| DataMaster | 下游评测分数 | 需要 | **需要** | 改 |
| RepoFactory | 验证器执行 + 静态代码指标 | 不需要 | 不需要 | 联合改 $O$、$I$、$V$ |

看这张表就能明白，RepoFactory 不是比别人多了某个模块，而是把反馈回路里最贵的那两环砍掉了，代价是接受一个"不完美但及时"的代理指标。这个取舍我觉得是这篇论文最该被记住的判断。

几个数字值得单独拎出来：

- **多样性**：17 个软件领域，最大的一类只占 12.5%，只有 6.9% 落在命名领域之外。词云里 CLI applications、Pandas、Markdown、NumPy、SciPy、PyTorch、FastAPI、SQLAlchemy、Flask、Django 这些栈都在，说明不是靠某类项目刷量。
- **规模**：中位 oracle 4.2k 行源码，尾部还有更大的系统；10,159 个成功解析测试的实例加起来，验证器里有 209 万个静态识别出的测试定义。这个验证密度跟"看几个端到端结果"完全不是一个量级。
- **交互长度**：中位 oracle 26 个源文件，中位 SFT 轨迹 64 轮助手交互。一条成功轨迹得在多文件项目里持续记状态、边改边测，这才是长程监督该有的样子。
- **规模确实是难度代理**：把有匹配轨迹的环境按 $S$ 排序五等分，平均成功率从最小组的 23.0% 掉到最大组的 13.4%。$S$ 不是随便设的，它跟"题有多难"确实相关。

## 🧪 实验结果：数字说话，也别照单全收

### 实验设置

评测用 Claude Code 2.1.140 作脚手架，最大上下文 262,144 tokens，最大输出 32,768 tokens，用量到 80% 自动压缩；解码 temperature 1.0、top-p 0.95、top-k 20。五个基准：NL2Repo（整仓重建）、SWE-bench Verified / Pro / Multilingual（修 issue）、Terminal-Bench 2.1（终端任务）。

SFT 配置放在附录：3 个 epoch，rollout 与全局 batch 都是 64，单卡 micro-batch 1，开启动态 token batching、每 GPU 上限 80,000 tokens；AdamW，weight decay 0.1，$\beta_1=0.9$、$\beta_2=0.98$；峰值学习率 $1.0\times10^{-6}$，10% warmup 后 cosine 衰减到 $1.0\times10^{-7}$；TP=2、CP=4、EP=8，开序列并行。loss 只算 assistant 片段（含 tool call），system / user / tool-result 只提供上下文不进 loss。轨迹过滤阈值是 reward > 0.5，另有确定性检查加一个 LM judge 复查疑似违规样本。

我的读法稍微不同：这也可能说明前 3,000 个环境里同质化偏高，后面才补上了长尾的库和结构。不管是哪种解释，"继续扩环境还能涨"这个结论对工程实践都很有用——至少在万级这个量级，天花板还没摸到。

### 消融：演化到底在帮什么

作者把演化的两个作用拆开验，这个设计我挺认可。

**作用一：把废仓库救回来。** 从过滤后的候选里均匀抽 500 个仓库，比较"最多 3 步修复"和"不修复"，并发、超时、基础设施重试预算都固定，只看满足 $A=1$ 的环境数。

![图6：累计验证环境数随挂钟时间的变化](https://www.mulanai.com/fs/files/1119_3ad1fcd8_fig_feed.jpg)

*图6：每 30 分钟采一次点，横轴挂钟时间（小时），纵轴累计验证通过的环境数。四条阶梯线：无演化 169，演化第 1 步 344、第 2 步 345、第 3 步 347，图上标注 Total Δ = +178 environments。绝大部分增益来自第一次修复。*

169 到 347，成品率从 33.8% 抬到 69.4%，同一个仓库池子里多捞出一倍的有效环境。而且图里看得很清楚，第 1 步修复几乎吃掉了全部收益，第 2、3 步只多出 1 到 2 个。这个结论对工程很实在：如果算力有限，修复循环做一轮就够，别堆轮数。

**作用二：把题改得更值得练。** 从同一批 1,000 个随机环境出发，跑两组独立演化，一组只优化 $S$、一组只优化 $C$，都保留有效性检查。第 3、6、9、12 轮产出的环境记作 Level 1 到 Level 4，每级各取 2,000 条轨迹，用相同初始化和超参微调。

![图5：四个难度等级的统计与对应 NL2Repo 结果](https://www.mulanai.com/fs/files/1119_c52904e9_level_ov.jpg)

*图5：上排 (a) 优化实现规模 $S$，下排 (b) 优化结构耦合度 $C$；每排四个面板依次是交互轮数、上下文长度、每条样本监督 token 数、下游 NL2Repo 准确率，都带 p25–p75 区间、p90 虚线和中位数实线。上排准确率 30.2 → 31.1 → 31.8 → 32.9，三项长度/token 指标同步上升；下排准确率 30.2 → 31.0 → 30.4 → 32.5，交互轮数反而下降，上下文与监督 token 只是略降。*

这张图的信息量比正文那两段话更足。

优化 $S$ 那组，交互轮数、上下文长度、监督 token 全线上扬，准确率从 30.2 稳到 32.9——题变大了，模型练得更多，成绩跟着涨，逻辑顺。

优化 $C$ 那组不太一样：中间 Level 2、3 有波动（31.0 又掉回 30.4），到 Level 4 跳到 32.5，而交互轮数是**下降**的，上下文和监督 token 也只是轻微下降。也就是说这一组的提升不靠"练得更久更多"，靠的是组件之间的关系变复杂了。作者拿它论证"训练价值不只看实现工作量，还看被实现组件之间的关系"，我觉得这个论证成立，而且比主表更能体现 $C$ 这个指标不是摆设。

但有个地方我想抬个杠：两组消融的 Level 4 都只有 32.5 到 32.9，而主实验完整版是 46.4。差距来自消融只用了 1,000 个环境、每级 2,000 条轨迹，规模小得多。这倒是反过来又给 Figure 3 的环境 scaling 曲线补了一刀证据。

## 💡 我的判断

**这篇论文最值钱的地方，是把"训练价值"从一个滞后指标改成了当场可算的代理指标。**

做 agent 训练数据的人都被这个循环折磨过：改一版数据 → 训一轮 → 跑评测 → 几天后才知道好坏。RepoFactory 说，别等了，验证器跑一下、AST 扫一下，就能判断这个环境能不能用、值不值得练。$A$ 管能不能用，$S$ 和 $C$ 管值不值得练，三者相乘，便宜到可以在一万量级上迭代 12 轮。这个思路的价值远超 RepoHorizen 那个 35B checkpoint。

**但也别把它当成底层突破。** 拆开看：整仓重建任务不是它先提的（NL2Repo-Bench、DeNovoSWE 在前），Docker + AST 扫描 + 测试继承都是成熟手艺，SFT 配置也是标准做法，构造 agent 直接用了 Qwen3.8-Max。真正的增量集中在那个乘性目标和围绕它的演化循环。一次很扎实的工程整合，加一个聪明的指标设计，我觉得这个定位比那些自夸式话术准确得多。

几个我觉得该打问号的地方：

- **代理指标偏粗。** $S$ 是行数加依赖数的对数，$C$ 是调用图可达对占比，都是结构层面的量。论文自己在 Limitations 里也承认，这些指标还区分不了"某个任务具体需要哪种能力"。一个算法密集的小项目和一个样板代码堆出来的大项目，$S$ 可能差不多，训练价值差很远。$C$ 的阈值设成 0.01、$S$ 设成 0.5，也没看到敏感性分析。
- **只覆盖 Python。** 4 万行 Python 以下、不要 GUI、不要外部服务、断网跑通，这些门槛把项目池子削得很干净，但也把结论锁死在 Python 生态里。SWE-bench Multilingual 只涨 1.3 分就是直接证据。
- **$A$ 这个门可能被投机。** 只要求 oracle 满分、空工作区零分，没要求测试对"部分正确实现"有区分度。一个测试写得极松的环境照样 $A=1$，只是靠 $S$、$C$ 在后面兜底。
- **训练方式是 SFT，不是 RL。** 轨迹来自 Qwen3.8-Max，只留 reward > 0.5 的，再按多轮目标算 assistant 片段的 loss。这么一来学生模型上限被教师轨迹框住了，环境提供的"可验证反馈"其实只在造数据阶段用上，训练阶段并没有让模型自己在环境里试错。想做真正在线的 long-horizon RL，这套流水线还得再接一层。
- **分数全是自报。** 五个基准都用同一个 Claude Code 2.1.140 脚手架，脚手架版本对 agent 分数影响有多大，做过评测的人都清楚。换一版 harness 还剩多少增益，得等复现。
- **基座单一。** 主实验只微调了 Qwen3.5-35B-A3B 一个基座，跨尺寸实验虽然加了 9B 和 27B，但都没给完整五项基准。泛化性证据不算充分。

### 工程上能带走什么

如果你也在做长程 agent 的训练数据，我觉得有三条可以直接试：

1. **给流水线留一个"修复"分支，而不是过滤完就丢。** Figure 6 那个 33.8% → 69.4% 太诱人了，而且几乎全靠第一轮修复。很多被丢弃的候选只是差个依赖版本或测试命令配置，值得救。
2. **把"训练价值"做成可计算的量，哪怕它不完美。** 与其等下游评测，不如先找几个当场能算的静态指标当代理，让数据构造能快速迭代。关键是代理指标要跟最终目标有实证相关——论文用 Figure 2(d) 那个 23.0% → 13.4% 的成功率梯度替 $S$ 做了背书，这一步别省。
3. **别在环境数量上过早收手。** Figure 3 到 5,577 还在涨，而且后半段更陡。万级规模在同质化过滤之后才补到长尾结构，这个信号值得拿去说服老板多给点算力。

还有个更根本的问题没解决：代理指标再准，也只是在猜"什么题值得练"。真正闭上的环，应该是模型在环境里练完之后的进步，能反过来修正这些指标的权重。论文把模型执行和下游训练从反馈环里砍掉换来了低成本，代价就是这个环始终是开着的。$A$、$C$、$S$ 的权重目前全靠人工设定和阈值，会不会有一天让它们自己学着调？那可能才是 RSI 和这条路线该汇合的地方。
