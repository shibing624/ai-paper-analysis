# 不碰权重，把 RL 专家塞进 256 个向量里：CSPD 把「合并模型」改成了「拼提示」

你有没有碰到过这种糟心事：手里攒了四个 RL 训出来的专家，数学、代码、科学问答、指令遵循各管一摊，每来一个新的，就得把整套模型重新整合一遍。重新跑多任务 RL 太贵，拿 TA 或 TIES 把权重揉一次又容易把别的能力揉坏，按 MOPD 把所有 teacher 再蒸馏一轮动静更大。整完还得做一轮回归，因为总有几个原本挺好的指标突然掉了一截。

你想想看，这哪叫「装个新模块」，这叫「重新装修」。每次装修都得把整栋房子掀一遍，而且没人保证墙不会被敲坏。

上周读到 arXiv:2611.27376 的时候，我的第一反应是：终于有人把这件事从权重空间里搬出来了。

---

## 🎯 核心摘要

这篇论文提了件挺反直觉的事——把 RL 专家的能力蒸馏进一小段软提示（soft prompt），而不是写进模型参数。骨干模型全程冻结，每个专家只用自己的 verifier 过滤过的回答，独立训出 256 个向量；要用哪几个专家，就在系统消息里把对应提示直接串起来，不做任何联合训练。效果呢？23 个数学、代码、智能体设置里，22 个恢复了 teacher 至少 90% 的增益；四专家组合的四域均分从 50.41 涨到 **67.83**，跟需要重训全模型的 MOPD（67.79）打平；六个域外基准均分 56.6，比 MOPD 的 53.5 高一截；服务侧吞吐只比裸骨干低 1.5%，是 rank-4 LoRA 的 2.40 倍。

我的判断：这不是底层算法突破，是一次很干净的问题重述——把「怎么把多个专家压进一套权重」换成「怎么把多个专家挂在输入上」。软提示、序列级蒸馏、prefix-robust 训练都是现成零件，作者真正值钱的地方在于把持续后训练的增量成本压到了只和新专家有关。值得细读，但别被 107.5% 的恢复率晃了眼。

## 🤔 问题动机：为什么「合并专家」这件事越做越贵

RL 后训练有个很现实的约束：一个领域配一套数据、一个 verifier、一套环境，所以大家习惯一个领域一个领域地训专家，训完再合。问题在于新专家会不断来，整合就从「一次性收尾」变成了「持续过程」。作者把理想中的整合拆成三条，我觉得这个拆法比很多 related work 的罗列清楚得多：

新专家带来的能力要拿到；模型原来会的事（别的专家领域、通用能力）不能丢；更新代价只跟新专家有关，不能跟已有专家数量挂钩。

拿这三条去卡现有方案，几乎全军覆没。Joint multi-task RL 每加一个领域就得把所有领域的 RL 重跑一遍；sequential RL 只训新领域，但后面阶段的更新会把前面的成果不可逆地冲掉；权重合并（Task Arithmetic、TIES）靠参数做算术，不同专家的更新方向会互相干扰；MOPD 得让 student 对着所有 teacher 重训一轮。这四类还有个共同的毛病：给每个请求都用同一套固定混合，并且直接改写骨干权重，域外能力容易被磨损。

另一条路是保留多个专家、按请求挑。expert routing 得训一个 router，每加一个专家就得更它，而且一个请求里没法同时用两个专家，还得给每个专家托管一整份模型。按请求合并 LoRA 适配器能绕开前两个问题，代价是每一层、每个解码步都要多算一次适配器。

两条路有个共同前提：**专家住在参数里**。这篇论文动的就是这个前提。

![图1：MOPD 与 CSPD 的路线对比](https://www.mulanai.com/fs/files/1125_0a139d01_cspd_mop.jpg)

*图1：左边 MOPD 把 M/C/S/I 四个专家压进一份 trained student 的权重；右边 CSPD 把每个专家做成独立软提示，挂在 frozen student 前面，ADD / REMOVE 就是插拔。最右侧的分数牌很直白：域内均分 CSPD 67.83 对 MOPD 67.79，域外均分 56.6 对 53.5，学生基线 50.3。*

我把几条路线按那三条标准摆成一张表，方便对照：

| 方案 | 新增专家的代价 | 是否改动骨干 | 能否按请求组合 | 域外能力 | 解码时额外开销 |
|---|---|---|---|---|---|
| Joint multi-task RL | 重跑所有领域 RL | 是 | 否，固定一套 | 可能下降 | 无 |
| Sequential RL | 只训新领域 | 是 | 否 | 旧能力易被冲掉 | 无 |
| 权重合并 TA / TIES | 重算合并系数 | 是 | 否 | 常被磨损 | 无 |
| MOPD | 对所有 teacher 重训 student | 是 | 否 | 中等（53.5） | 无 |
| Expert routing | 重训 router + 托管新模型 | 否（多份模型） | 否，一次只能一个 | 视 router 而定 | 整份模型 |
| 按请求合并 LoRA | 训新适配器 | 否 | 是 | 中等（53.8） | 每层每步都要算 |
| **CSPD** | 只训新提示 | 否 | 是，直接串 | 最好（56.6） | 只在 prefill 多 256 个位置 |

这张表最值得琢磨的不是某一行多厉害，而是末尾那一列。把适配放到输入侧之后，「每个请求用不同专家」这件事从系统难题变成了批量推理里的一行配置。

## 🏗️ 方法核心：冻结骨干，把专家做成一段可拼接的向量

一句话讲清核心 idea：RL 专家的能力，其实可以用**序列级蒸馏**压进一段插在系统消息里的可训练向量，模型一个参数都不用改。

![图2：CSPD 方法总览](https://www.mulanai.com/fs/files/1125_7439b725_cspd_ove.jpg)

*图2：(a) 用 post-RL teacher 的回答，在冻结的 pre-RL student 上只训 $P_j$ 这 256 个向量（橙色可训练、蓝色冻结）；(b) 各专家独立训完形成一个 prompt library；(c) 推理时把选中的提示 concatenate 起来，注意图上那行小字 no joint training；(d) 带不同提示的请求共享同一个 pre-RL student 的 batch。*

### 蒸馏：只训 $L\times d$ 个参数

设 $p_{\theta_0}$ 是 RL 前的模型，$p_{\theta_j}$ 是从它出发训出来的领域专家，配一套领域问题 $\mathcal{X}_j$ 和一个 verifier。目标是学一段软提示 $P_j\in\mathbb{R}^{L\times d}$，也就是 $L$ 个落在骨干 embedding 空间里的向量，论文取 $L=256$。模板 $\mathcal{I}(P_j,x)$ 把这段向量塞进系统消息、放在问题 $x$ 前面。

训练数据不用 RL 轨迹，也不用 on-policy 采样：拿 teacher 对 $\mathcal{X}_j$ 里的问题生成回答，verifier 判过的留下，组成 $\mathcal{D}_j$，然后在这上面做长度归一化的负对数似然：

$$P_j^{\star}=\underset{P_j}{\arg\min}\;\mathbb{E}_{(x,y)\sim\mathcal{D}_j}\Big[-\frac{1}{|y|}\sum_{t=1}^{|y|}\log p_{\theta_0}\big(y_t\mid\mathcal{I}(P_j,x),y_{\lt t}\big)\Big]$$

这个式子里 $\theta_0$ 是死的，梯度只往 $P_j$ 上走。工程上挺讨喜：teacher 出题、verifier 过滤、student 做 SFT，整条链路没有 RL 的采样-打分循环，也不需要 reward model。参数量小到有点夸张——256 个向量在论文里是 737,280 个参数，作者自己在讨论里说大约占骨干的 0.01%。

说到底，这里赌的是一件事：RL 带来的行为变化，在表示空间里是低维的、能被输入侧的少量自由度重新唤起。LoRA 能匹配全参微调、单层训练能 recovers 大部分 RL 增益，这些前置观察其实都在给这个赌注背书。

### 拼接：不做联合训练

要组合 $1,\ldots,k$ 个专家，直接把软 token 串起来：

$$P_{1:k}=[P_1^{\star};\ldots;P_k^{\star}]\in\mathbb{R}^{kL\times d},\qquad p(y\mid x)=p_{\theta_0}\big(y\mid\mathcal{I}(P_{1:k},x)\big)$$

没有 joint training，没有合并系数，没有 router。持续后训练场景下，新专家来了就单独蒸一段提示、往已有提示前面一插，旧提示和骨干都不动；要下线一个专家，把它的提示丢掉就行。作者把这点总结成「把能力的获取和能力的组合拆开」——我觉得这是全篇最有分量的一句话，比任何一个数字都重要。

### 一个小设计，但缺了它真不行

有个细节容易被略过：提示是单独训的，推理时却要跟在别的提示后面。训练分布和推理分布对不上怎么办？

作者加了 **prefix-robust training**：一半的训练样本里，在软提示前面垫一段 128 到 256 token 的前缀，前缀从同领域其他问题里采样，不计入 loss，推理时也不出现。目的不是教内容，是让提示学会「不管前面挂了什么都能干活」。

这个设计的必要性在消融里能看到硬数字：去掉它，四域均分从 66.60 掉到 64.50，恢复率从 99.9% 掉到 87.0%（Table 5，AdamW + ISCM 设置）。掉 2.1 个点，比很多方法论论文里整套模块的贡献都大。

### 顺便说说评测口径

论文主指标是 recovery，定义为：

$$R=\frac{A_{S+P}-A_S}{A_T-A_S}\times 100\%$$

$A_S$、$A_T$、$A_{S+P}$ 分别是学生、teacher、加了提示的学生。100% 表示追平 teacher 相对骨干的增益。作者特意强调会同时报绝对分，因为 teacher 增益小的时候这个比值会被放大——这句话我建议在读 Table 1 的时候一直记着，后面会用到。

给一段伪代码，把流程收一下（比论文正文更接近工程实现）：

```python
# 每个专家完全独立，可并行训练
def distill_expert(backbone_frozen, teacher_rl, questions, verifier, L=256):
    P = init_soft_prompt(L, backbone_frozen.d)          # 只有 P 可训练
    data = [(x, y) for x in questions
            for y in teacher_rl.sample(x) if verifier(x, y)]
    for (x, y) in batch(data):
        if coin_flip():                                 # prefix-robust，半数样本
            x = random_domain_prefix(questions) + x    # 前缀不进 loss
        loss = -mean(log p_backbone(y_t | [P; x], y_lt_t))
        P.step(loss)                                   # 骨干梯度全程关闭
    return P

# 推理时按需拼接，无联合训练
def compose(prompt_library, requested_experts, question):
    P = concat([prompt_library[e] for e in requested_experts])
    return backbone_frozen.generate(system_msg=P + question)
```

## 🧪 实验结果：数字得挨个看，别只看结论

### 单专家：23 个设置，22 个恢复 90% 以上

作者挑了公开的 pre-RL / post-RL 模型对，覆盖数学、LiveCodeBench 代码、SWE-bench Verified 与 Terminal-Bench 2.1 智能体任务，模型从 7B 到 35B，稠密和 MoE 都有，teacher 的 RL 配方各不相同。每个对都在冻结的 pre-RL checkpoint 上蒸一段 256 向量提示。

我摘几行代表性的（Table 1，数值均为百分数）：

| 领域 / 模型对 | Student | Teacher | Student+SP | Recovery |
|---|---|---|---|---|
| 数学 MiMo-7B-SFT → MiMo-7B-RL | 63.77 | 73.18 | 72.25 | 90.15% |
| 数学 GPT-OSS-Swallow-20B | 76.53 | 90.21 | 89.67 | 96.06% |
| 数学 Qwen3-Swallow-8B | 63.68 | 83.01 | 82.28 | 96.22% |
| 数学 Nemotron-Cascade-8B (MathRL) | 85.25 | 89.34 | 89.30 | 99.18% |
| 数学 Qwen3-Swallow-30B-A3B | 72.91 | 86.25 | 86.23 | 99.79% |
| 代码 MiMo-7B (LCB) | 50.17 | 52.87 | 52.55 | 88.08% |
| 代码 Nemotron-Cascade-8B (CodeRL) | 55.73 | 69.39 | 69.56 | 101.21% |
| Agent SWE-bench Verified Nemotron-8B | 23.60 | 34.60 | 33.75 | 92.27% |
| Agent SWE-bench Qwen3-32B → DeepSWE | 24.90 | 44.05 | 45.65 | 108.36% |
| Agent Terminal-Bench 2.1 Qwen3.5-9B | 20.22 | 28.09 | 29.96 | 123.81% |

22/23 恢复 ≥90%，其中 15 个达到或超过 teacher 本人。看到这个覆盖面我确实有点意外——连多步智能体任务都能靠输入侧 256 个向量捞回来，说明 RL 改掉的主要是「行为倾向」，不是往权重里塞了多少新知识。

但等等，表里也有 200.00%、157.14%、143.44% 这种数字。这不是模型开挂，是分母太小：TMax-27B 的 teacher 只从 43.45 涨到 46.07，增益 2.62 个点，提示稍微多拿一点，比值就飞了。作者自己承认这点，所以坚持同时报绝对分。这个口径我认可，只是读的时候得带着这根弦。

### 主实验：四专家组合，跟 MOPD 打平

多专家实验用四个领域：instruction following (I)、science (S)、code (C)、math (M)，评测 AIME24、LCB v5、GPQA-D、IFBench，拼接顺序 MCSI（最新模块放最左）。Table 2 全表：

| 方法 | AIME24 | LCB v5 | GPQA-D | IFBench | Avg. | Recovery |
|---|---|---|---|---|---|---|
| Student (no prompt) | 55.94 | 58.61 | 44.38 | 42.71 | 50.41 | 0.0% |
| 单域专家（oracle routing） | 81.77 | 66.92 | 50.44 | 67.33 | 66.61 | 100.0% |
| Full model + Expert merge (TA, λ=1.0) | 78.85 | 64.52 | 54.14 | 71.58 | 67.27 | 104.1% |
| Full model + Expert merge (TIES) | 81.25 | 65.42 | 57.07 | 66.12 | 67.47 | 105.2% |
| MOPD | 83.28 | 66.24 | 55.21 | 66.42 | 67.79 | 107.2% |
| LoRA distill + TA (λ=0.5) | 80.21 | 63.10 | 56.22 | 62.46 | 65.50 | 93.1% |
| LoRA distill + TIES | 81.41 | 64.00 | 56.66 | 62.67 | 66.19 | 97.3% |
| Single-domain SP（各自单独用） | 80.89 | 64.67 | 49.24 | 66.71 | 65.38 | 92.4% |
| CSPD 去掉 prefix-robust | 76.98 | 64.15 | 51.89 | 65.00 | 64.50 | 87.0% |
| CSPD (ISCM) | 79.90 | 65.72 | 57.92 | 67.33 | 67.72 | 106.8% |
| **CSPD（MCSI）** | 80.47 | 64.67 | 57.77 | 68.42 | **67.83** | 107.5% |

有几个点值得停一下。

组合后的均分 67.83，比「每个 benchmark 都送给对应领域专家」的 oracle routing（66.61）还高。这说明拼接不是简单取并集，专家之间产生了正向迁移：GPQA-D 从单提示的 49.24 抬到 57.77，IFBench 从 66.71 到 68.42。代价是 AIME24 从 80.89 微降到 80.47。说实话看到 Table 2 我才意识到，作者拿 oracle router 当 baseline 是挺巧的一步——它把「组合是否带来额外收益」这个问题直接摆到了台面上。

跟权重侧比：MOPD 67.79、TIES 67.47、TA 67.27，CSPD 67.83。分域看各有胜负，MOPD 在 AIME24 和 LCB 更强，CSPD 在 GPQA-D 和 IFBench 更强。所以准确说法是「打平」，不是「赢」。那些把标题写成「超越 MOPD」的转述，多少有点抢跑。

LoRA 那两行我格外关注，因为它们用的是和软提示**完全相同的蒸馏数据**，只是适配表示不同：65.50 / 66.19，比 67.83 低 1.6 到 2.3 个点。这个对照比跟 MOPD 比更有说服力，它把变量收窄到了「适配写在哪」。

### 持续加入与插拔

![图3：逐专家加入与留一消融](https://arxiv.org/html/2611.27376v2/composition_dynamics.png)

*图3：(a) 按 I → SI → CSI → MCSI 逐个把提示前置，四域均分从 50.4 走到 61.0、61.7、63.7、67.8，虚线是单域专家均值 66.6；(b) 从 MCSI 里逐个移除一个提示后的分数变化，负值代表这个模块本来在帮忙。*

均分每加一个专家都涨，且不用重训任何已有模块，这条正好对上动机里的第三条。但图 3(b) 也把「可组合」的边界画出来了：移除 math 让均分掉 4.16 个点，其中 GPQA-D 掉 6.54；移除 instruction following 让 IFBench 掉 12.88。反过来，移除 math 反而让 LCB 涨 1.87 个点——专家之间有负向干扰。加 code 的时候 IFBench 一度从 66.71 掉到 64.58，后面加 math 才又拉回 68.42。

所以「拼接就能组合」成立，但不是无条件的无损叠加。顺序也有影响：MCSI 67.83，反序 ISCM 67.72。作者在附录里试了追加和前置两种放法，轨迹接近；可拼的排列远不止两种，四专家全排列是 24 种，这里只覆盖了 2 种。这个方向我自己也还在琢磨，先不下结论。

还有个反直觉的对照：Progressive Prompts 那种「每训一个新提示都把旧提示冻在前面」的做法，直觉上应该更适配组合，结果在每一个阶段都输给独立训练。作者的解释是独立训练配合 prefix-robust 已经够用，而渐进训练会把新提示绑死在特定的前置上下文上。这个结果挺漂亮，可惜只在一个四专家设置上验证过。

### 域外泛化：全篇我最买账的一组数字

把权重改了，最难保住的就是训练域之外的能力。作者在六个 held-out 基准上评了 MCSI 组合：XSTest（拒答）、TruthfulQA（真实性）、BFCL（工具调用）、TriviaQA（闭卷知识）、BBEH（难推理）、FinQA（金融推理）。Table 3：

| 方法 | XSTest | TruthfulQA | BFCL | TriviaQA | BBEH | FinQA | Mean |
|---|---|---|---|---|---|---|---|
| Student (no prompt) | 80.4 | 64.6 | 47.6 | 31.5 | 11.1 | 66.3 | 50.3 |
| Expert merge (TIES) | 82.4 | 63.7 | 48.5 | 33.6 | 25.6 | 70.9 | 54.1 |
| MOPD | 84.2 | 61.0 | 49.4 | 31.9 | 23.9 | 70.8 | 53.5 |
| LoRA distill + TA | 85.1 | 63.8 | 47.5 | 32.7 | 23.0 | 70.9 | 53.8 |
| **CSPD（MCSI）** | 88.2 | 64.2 | 55.6 | 33.5 | 25.8 | 72.5 | **56.6** |

CSPD 均分 56.6，六个里领跑四个，BFCL 上 55.6 对 MOPD 的 49.4，拉开 6.2 个点。TruthfulQA 反而是裸学生最高（64.6 对 64.2），TriviaQA 上 TIES 以 0.1 分领先。

我觉得这组结果比 67.83 更值得记。因为它验证的是动机里的第二条：骨干没动，通用能力就还在。MOPD 和 TIES 在 BBEH 上也涨得不少，但 TruthfulQA 分别掉到 61.0 和 63.7，那种「按下葫芦浮起瓢」的痕迹很明显。

### 消融：几个容易忽略的变量

Table 5 把优化器和拼接顺序拆开了（四域均分 / 恢复率）：

| 配置 | AIME24 | LCB v5 | GPQA-D | IFBench | Avg. | Recovery |
|---|---|---|---|---|---|---|
| CSPD (AdamW, ISCM) 无 prefix-robust | 76.98 | 64.15 | 51.89 | 65.00 | 64.50 | 87.0% |
| CSPD (AdamW, ISCM) | 79.74 | 65.94 | 55.78 | 64.96 | 66.60 | 99.9% |
| CSPD (Muon, ISCM) | 79.90 | 65.72 | 57.92 | 67.33 | 67.72 | 106.8% |
| CSPD (Muon, MCSI) | 80.47 | 64.67 | 57.77 | 68.42 | 67.83 | 107.5% |

换 Muon 比 AdamW 再多拿 1.1 个点，prefix-robust 值 2.1 个点。Table 4 还有一组监督信号的消融，同样 28,946 条回答：只用 verifier 判对的（Correct-only）恢复 96.06%，掺进 31% 错误回答（Mixed，69% 正确率）掉到 90.54%；同数据下 LoRA（K/V, r=5）是 95.72%。也就是说，verifier 过滤不是走个流程，它直接决定上限。

这里插一句吐槽：Table 4 里 best update 是 140 或 100，论文附录也提到训练曲线在第 60 步后就平台，峰值 92.62% 出现在 update 180，末 checkpoint 反而只有 85.68%。软提示这种小参数量的训练对 checkpoint 选择相当敏感，工程上得把「按验证集挑 checkpoint」写进流水线，不能拿末位那个凑合。

### 服务效率：真正让我想试的部分

![图5：单张 B200 上的请求级适配器服务](https://www.mulanai.com/fs/files/1125_84b374f4_serving_.jpg)

*图5：横轴是并发请求数，左列输出吞吐（越高越好），右列 P95 首 token 延迟（越低越好），下方小图是 SP 相对裸骨干的百分比变化。三个配置是 Backbone、SP (256 vectors)、LoRA (rank 4)。32 并发处标着 2.40× 吞吐比和 2.27× 延迟比。*

实验配置：单张 NVIDIA B200，SGLang，GPT-OSS-20B BF16，每个请求 20,480 输入 token、生成 512 token，模拟 agent 场景；每个请求挂一个**不同的**适配器，属于最极端的个性化情形。

32 并发时：SP 715.4 output tokens/s，裸骨干 721.3，LoRA 298.5；P95 首 token 延迟 LoRA 39.21 秒、SP 17.26 秒、裸骨干 16.89 秒。七个并发档位下 SP 吞吐都在裸骨干的 1.5% 以内。

原因不复杂：软提示只在 prefill 阶段多算 256 个位置，之后每个解码步只是多 attend 一段缓存好的 KV；LoRA 则要在每一层、每一步都做一次请求专属的低秩矩阵乘。作者还给了内存公式，256 个向量让 20,480 的输入只变长 1.25%。顺带测了投机解码兼容性：EAGLE-3 平均接受长度 2.34 → 2.28，DFlash 2.96 → 2.82，掉得不多。

不过得把话说全：这里比的是 **unmerged multi-LoRA**（CSGMV 后端），也就是每个请求一份独立适配器的部署形态。单个合并好的 LoRA 是另一种 regime，论文没比，作者也在附录里明说了。要是你的服务里所有请求共用一套适配器，2.40 倍这个数就不能直接搬。

## 🔬 软提示到底学到了什么

这一节我觉得是全篇最有意思的分析，虽然它不涨点。

作者拿 GPT-OSS-Swallow-20B 的数学提示开刀，让 teacher、student、加了提示的 student 各答 100 道 held-out AIME / MATH-500，再在每个回答位置上比 next-token 分布。度量是 KL gap 闭合比例：

$$G(A)=100\Big(1-\frac{D_{\mathrm{KL}}(T\|A)}{D_{\mathrm{KL}}(T\|S)}\Big)$$

![图6：软提示的机制分析](https://www.mulanai.com/fs/files/1125_1df77227_sp_inter.jpg)

*图6：(a) 软提示闭合 86.8% 的 teacher–student KL gap，而 Verify instruction 2.1%、Check instruction 1.6%、Neutral instruction 1.1%、high reasoning effort 0；(b) 被抬高概率的 token 是 ? (203)、But (199)、Check (107)、Let's (72)，被压低的是换行 (95)、So (71)、Thus (24)、Given (21)；(c) 只让 response token 看到提示能保留 80% 改进，只让 input token 看到只保留 33%，全屏蔽剩 1%。*

结论挺锋利：软提示没学到一句能写成文字的话，它学到的是 teacher 的**推理行为**——不下结论，先质疑、先检查。学生原本爱写「Thus…」一路推下去，加了提示之后开始写「But…」「Check…」，跟 teacher 一个路数。你写一句「请检查每一步中间结果」的自然语言指令，最多只闭合 2.1% 的 gap；把 reasoning effort 拉高，0%。

另一个细节我读了两遍：把每个软提示向量映射到词表里最近的词，六个模型里有 84%–100% 的向量，最近邻仍然是初始化时那个词，可向量本身已经跑得很远（中位余弦相似度只有 0.25–0.34）。所以「软提示是啥意思」这种问题本身就问错了，它压根不在词嵌入的可解释邻域里。

还有个注意力路径的结论：作用主要来自**回答 token 直接读提示**，而不是提示改变了模型对问题的编码。只让 response 看，保住 80%；只让 input 看，保住 33%。第 5 层把每个 response token 读到的内容换成同一个平均值，保留比例从 80% 掉到 28%——不同生成位置从同一段提示里取的是不同信息。

这块我自己也不是特别确定该怎么迁移到工程上，但至少有条实用提醒：别指望用一句 system prompt 复刻 RL 的效果，也别指望把软提示向量「翻译」成人话来解释模型行为。

## ⚖️ 我的判断：漂亮，但别急着当银弹

**这篇论文最值钱的地方**，是把持续后训练的三个约束同时满足了：新专家的代价只跟自己有关、旧能力没被覆盖、按请求组合几乎零成本。软提示（Lester et al., 2021）、序列级蒸馏（Kim & Rush, 2016）、Task Arithmetic、TIES、Progressive Prompts、Punica 那套多适配器服务，全是现成零件。作者做的是换了个问题问法，然后用一套很扎实的实验把答案钉住。这是高质量的工程整合与实证，不是新的底层机制。说到底，贡献是「适配位置的选择」加「prefix-robust 这个让拼接成立的小设计」。

下面几处我得皱眉。

**恢复率这个指标自带放大器**。 分母是 teacher 增益，增益小的时候比值会失真，Table 1 里 200% 就是这么来的。作者主动报了绝对分、也在 limitations 里点了这件事，态度是诚实的，但传播时很容易只剩「107.5%」「超越 teacher」这类话术。

**checkpoint 和系数在评测集上挑过**。 limitations 里那句「Several reported numbers, including single-expert checkpoints and TA coefficients, are selected on the evaluation benchmarks」，坦率的讲，读到这里我停了一下。Table 1 的 Student+SP 取的是「best evaluated prompted-student score」，TA 的 λ 也扫了 0.25 / 0.5 / 1.0 再挑（Table 6 里 λ=1.0 的 full model 是 67.27，λ=0.5 只有 65.76）。这在领域内算常见做法，可它确实让「和 baseline 打平」这句话的含金量要打折——baseline 也被调过，但 CSPD 侧多了一个按 benchmark 挑 checkpoint 的自由度。要是有独立的 dev split，结论会硬很多。

**规模证据偏薄**。 组合实验只用一个骨干、四个领域、少量 seed。专家数从 4 涨到 20 会怎样？论文没答，作者也把它列为 open question。每个提示 256 个位置，四个就是 1,024，20 个就是 5,120——在 20,480 的输入上，一个提示是 1.25%，二十个就是 25%，注意力和 KV-cache 的成本是线性往上叠的。作者把这个也写进了 limitations，没藏着。

「**免联合训练**」不等于「**免协调**」。 拼接顺序影响结果（MCSI 67.83 / ISCM 67.72），专家之间有正负干扰，移除 math 会让 LCB 变好、让 GPQA-D 掉 6.54。真上线的时候，新专家插在哪、要不要重排、怎么回归，还是一套要维护的策略。论文给出的 prompt selection 方向（学一个选择器，别手工挑）恰恰说明这块没做完。

**数据门槛被低估了**。 蒸馏依赖 teacher 生成的、verifier 判过的回答。Table 4 显示掺了 31% 错误回答就从 96.06% 掉到 90.54%，讨论里也提到拿不到原始训练数据时（MiMo-7B code 那一档，88.08%，是全表唯一没到 90% 的）恢复会掉。你要是只有别人发布的 RL 权重、没有配套 verifier 和数据，这条路不一定走得通。

**baseline 的部署形态要对齐**。 serving 对比的是 unmerged multi-LoRA，属于「每请求一个适配器」的极端情形，正好是软提示最占便宜的场景。共用一套合并适配器的服务不在这个比较里。2.40 倍是真的，但适用边界得标清楚。

顺带说一句同期定位：MOPD 那条线（Wang et al., 2026b；Ma et al., 2026a）解决的是「把多个专家合成一个更强 student」，CSPD 解决的是「让专家根本不用合」。两者目标不完全重合，硬说谁取代谁不太准确。更贴近的对位其实是多适配器服务（Punica、S-LoRA）和 Progressive Prompts 这一类持续提示方法——CSPD 的新意在于把「独立训练 + 推理期拼接」这套组合拿到了 RL 后训练这个场景，并且把服务侧的账算清楚了。

## 💡 工程启发：什么情况下值得试

如果你在维护一个「能力会持续增加」的骨干模型，这套思路值得排进实验队列。我列几条能直接落地的：

**把专家库做成配置，不要做成权重分支**。 骨干一份、提示库一份，每个提示记元信息（领域、verifier、训练数据版本、拼接优先级、回归分数）。新专家上线 = 加一条配置 + 跑一轮回归；回滚 = 摘掉那条配置。这比维护 N 份模型权重的运维成本低太多，也天然支持灰度和 A/B。

**蒸馏流水线里三件事别省**。 verifier 过滤要严、checkpoint 要在独立 dev 上挑、prefix-robust 的前缀采样得开。前两项直接决定天花板，第三项值 2.1 个点。论文附录里 AdamW 常学习率 0.01 跑两轮的旧配置，末 checkpoint 比峰值低了近 7 个点，这个坑很实在。

**按请求拼提示，跟批量推理天然合拍**。 不同的提示组合只是不同的输入前缀，可以继续共享同一个骨干的 batch 和 KV cache。多租户、按用户付费开能力、按任务类型动态选技能，这类场景比「训一个全能模型」更适配。要是已经在用 SGLang / vLLM，改动主要在前缀构造和缓存复用上。

**先算上下文预算再扩专家**。 每个提示 256 个位置，串 k 个就是 $256k$。长上下文 agent 场景里，这部分会挤占可用窗口、抬高 prefill 和 KV 开销。真要上几十个专家，得考虑更短的提示（附录里测过五种长度）、按请求只挂必要提示、或者给提示做一层选择/压缩。

**回归测试要覆盖「域外」和「组合顺序」**。 论文自己就发现加 code 会短暂压低 IFBench、移除 math 反而抬高 LCB。只测新专家自己的 benchmark，很容易漏掉这种跨域交互。建议把六个 held-out 基准固定成一张看板，每次加专家都跑一遍。

**别拿它替代 RL 本身**。 CSPD 是把已有 RL 专家搬进输入侧，teacher 从哪来还是得靠 RL 训。它优化的是整合环节，不是训练环节。

还有个更根本的问题没解决：为什么几个独立训出来的提示，串起来能互相增益，甚至超过 oracle router？论文给了现象（GPQA-D 涨 8.5 个点）和注意力层面的线索（不同 response token 读不同信息），但没有一个能预测「哪两个专家组合会互相帮忙、哪两个会打架」的模型。可能我的理解有偏差，但我觉得这才是「可组合」从经验技巧变成工程学科要补的那一课。作者列的四个后续方向——规模、提示选择、机制、成本——正好对准这块。

回到开头那个「重新装修」的困境。CSPD 给出的答案朴素得有点可爱：别装修了，把每个专家做成一张贴在门口的便签，要用哪几张就按顺序贴哪几张，房子一动不动。

这个想法挺漂亮的。至于贴到二十张便签时门还关不关得上，得等下一篇论文了。
