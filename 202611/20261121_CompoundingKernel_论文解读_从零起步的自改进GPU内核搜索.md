# 一千个 Agent 同时写 CUDA，卡住它们的居然不是算力

新卡到货那天，最尴尬的往往不是卡不够快，是软件跟不上。

英伟达 Blackwell 这一代把快路径藏在了 `tcgen05` 张量核指令、tensor memory 和 TMA 拷贝引擎后面。问题是，大量融合算子、低精度 shape 根本没有现成的库 kernel 用得上这些东西。库是人写的，硬件换代比人快。于是写 kernel 这件事就变成了一场搜索：试一个设计，测一下，看看测量告诉你哪里不对，再改，再试。

难的不是写出一个能跑的 kernel。难的是三件事凑一块——让后面的尝试能站在前面所有尝试的肩膀上，让几百道题同时这么跑，还得让整套系统别把自己骗了。

上周刷到 arXiv:2611.19230 这篇 CompoundingKernel，我的第一反应是「又一个刷榜的」。读完发现，它真正值钱的地方不在榜单名次，而在它把「搜索怎么不塌」这件事拆得很实在，甚至顺手甩出一个反直觉的结论：把一千多个 Agent 铺开之后，卡住规模的根本不是 Agent 数量，是可靠测量的速率。

---

## 🎯 核心摘要

这篇论文做的是一套靠搜索写 GPU kernel 的自改进系统。起点干干净净：每道题只给 PyTorch 定义、shape 和数据类型，不给参考 kernel，也不给官方分数。它把每个正确 kernel 连同它的谱系存进模型外部的 archive，让一个 LLM controller 读档案、挑父节点、给每个并行子 Agent 派一个方向，正确与否全交给模型外面的检查来判。结果截至 2026-11-11，它在 SOL-ExecBench（NVIDIA B200）的 L1、L2、Quantization 三个公开榜都排第一，235 道题全都有站点验证过的正确 kernel，209 道公开题上比官方 baseline 快 **4.40 倍**（几何平均，中位数 3.78 倍）。相同墙钟时间下，它靠做出 2.4 倍数量的正确尝试，在 38 道题里的 35 道赢过一个编码的 UCB 树搜索；一次 warm restart 修复把每小时评估候选数抬高 3.6 倍。

坦率的讲，这不是底层突破。核心配方——LLM 做变异、可执行评估打分、把高分程序存起来继续改——FunSearch 和 AlphaEvolve 早就立住了。它更像一次把工程纪律做到极致的系统胜利，外加一个诚实的规模化教训。但「从零」这个说法得打折看，榜首的含金量也得掰开看，这两块我后面会专门拆。

## 🧠 先把考场弄清楚：SOL-ExecBench 到底考什么

要判断 4.40 倍这个数有多重，得先知道尺子是什么。

SOL-ExecBench 是英伟达给「AI Agent 写的 kernel」办的公开擂台。235 道题从 124 个真实模型里拆出来，官方榜单覆盖 3,957 个 workload（也就是输入 shape），前向反向都有，精度横跨 BF16、FP8 和 NVFP4。题目分四个集合各有各的榜：L1 单算子 94 道、L2 融合算子 82 道、Quantization 33 道、FlashInfer-Bench 26 道，加起来正好 235。评测跑在 DGX B200 上，SM 时钟锁死 1500 MHz，编译超过 300 秒直接掐掉，运行时现场编 native code 的方案不收。

![图 1：论文 teaser 图，左侧是三个公开榜的 top 3，右侧是 Quant/030 这一道题的搜索谱系](https://arxiv.org/html/2611.19230v1/f1-teaser.png)

*图 1：teaser。(a) 截至 2026-11-11 三个公开榜的 top 3，橙色 `ours` 即 Qian & Hubert @ CI，L1 是 0.823339、L2 是 0.819260、Quantization 是 0.909670，每条榜最上面还挂着 1.000000 的 SOL Bound；(b) Quant/030 这一道题从首个正确解 6.25 倍爬到最好 27.36 倍的过程，橙线是最优路径、灰点是它的谱系、青绿点是其他谱系，中途一次改写还一度掉到 1.52 倍。*

计分方式值得停一下，因为论文后面所有数字都挂在它上面。每个 workload 有两个公布的时间：$t_b(w)$ 是英伟达优化过但没放出来的 PyTorch baseline，$t_{\mathrm{sol}}(w)$ 是「光速」下界，也就是一个完美 kernel 在 B200 硬件极限下该花的时间。你的 kernel 实测 $t_k(w)$，得分是：

$$S_w(k)=\frac{t_b(w)-t_{\mathrm{sol}}(w)}{\bigl(t_k(w)-t_{\mathrm{sol}}(w)\bigr)+\bigl(t_b(w)-t_{\mathrm{sol}}(w)\bigr)}$$

跟 baseline 一样快得 0.5，摸到硬件极限得 1.0，跑挂了得 0。一道题的分数是它所有 workload 的算术平均，一个榜的分数是它所有题的平均。

你看这个设计多狠：它奖励的不是「比 PyTorch 快几倍」，而是「把 baseline 到硬件极限之间那段空隙吃掉了多少」。说到这个，SOL-ExecBench 那篇原始论文做过一个挺关键的核验——SOL score 跟真实回收的物理余量 Pearson 相关能到 0.981，而传统的「相对 PyTorch 加速比」在 log-log 下只有 0.10 左右，几乎不相关。你想想看，一个 10 倍加速的 kernel，完全可能还离硬件极限十万八千里。这也是为什么后面看到 1062 倍这种数别太激动，得看它折算成 SOL 是多少。

还有一件事让这个考场特别凶：错的 kernel 通常不崩溃，它返回一堆看着挺合理的数。这帮 Agent 写出来的 kernel 中位长度约 7000 行，人根本没法按它产出的速度去审。更麻烦的是，一个足够强的搜索，会连检查器的漏洞一起搜出来——英伟达自己那版报告里，589 份提交、占 14.5% 因为 reward hack 被拦下，手法包括偷偷把 FP32 降级成 FP16、改写计时回调、把活甩到不计量的 CUDA stream 上、按指针 key 缓存输出。这个背景记住，后面讲「检查放在模型外面」那一节时，你会明白它不是洁癖，是保命。

## 🏗️ 四层循环：系统到底怎么转

![图 2：四层嵌套循环，快循环套在慢循环里，archive 和 checks 都在模型外面](https://www.mulanai.com/fs/files/1121_c0ba4f6f_f2-syste.jpg)

*图 2：系统全貌。① child loop 最快，Child agents 只写一处改动、在 B200 上计时；② controller loop 里 LLM controller 挑一个父节点或开新设计，给每个空出来的 child 派一个方向；③ team loop 由 lead + helper agents 在 warm restart 时修 harness；④ 最外层是人决定送哪些 kernel 上公开榜。图中 `ONE SEARCH PER PROBLEM · ×235`、`no official scores inside`、`official scores never enter the search` 三条标注，把边界划得很清楚：分数只在最外层给人看，从不进①②。*

作者把整套系统画成四个同心圈，里面快外面慢。我喜欢这个讲法，因为它天然把「什么该进模型、什么该留在外面」分层了。

最里层 ① 是 child。每个 child 拿一个 parent（起始 kernel）和**一个**方向，改代码、编译、在 B200 上计时，外部检查判正确，然后把候选连同计时和 parent 写进 archive。最终那次运行里，child 停在它第一个正确的 kernel 上。一次只改一处，这个约束挺关键——它让「哪个改动带来了什么」变得可归因。

第二层 ② 是 controller。每题只有一个 controller，只有两个工具：查 archive，和 `expand`。一次 controller 步写成公式是这样：

$$(p,d)\sim\pi_{\mathrm{LLM}}(\cdot\mid A),\qquad k'=\mathrm{Child}(p,d),\qquad A\leftarrow A\cup\{k'\}\ \text{if}\ k'\ \text{is correct}$$

$A$ 是这道题的正确 kernel 档案，$\pi_{\mathrm{LLM}}$ 是 controller 在给定档案下的选择：一个 parent $p$（$\bot$ 表示另起一个新根）加一个方向 $d$。重点来了——controller **自己不存任何状态**。哪个 child 空了就补一个，每轮重新读一遍 archive，直到 `expand` 报上来剩余时间用光。①② 两个循环全程跑固定的 Claude Opus 5.5。

第三层 ③ 是团队。lead 和 helper agents 盯着系统和进度、修 harness 里的毛病、需要人拍板就通知人，每个修复在下一次 warm restart 生效，档案一份不丢。第四层 ④ 才轮到人：决定送哪些 kernel、什么时候送、什么时候公开，用公开排名来定。

这里得把 warm restart 说清楚，它是理解整篇的钥匙。warm restart 会停掉 Agent、更新 harness（prompt、工具、评估逻辑）、再重启，但**保留**这次运行和每题的 archive。Agent 自己不带记忆，重启后重新读一遍档案，搜索就从停下的地方接着走，而不是像 cold start 那样从零再来。说到底，作者把「可热更新的外围」和「不可丢的历史」切开了。这个切法我觉得是全文最漂亮的一处工程设计。

顺带把一个容易误读的词掰正：「From zero」说的是搜索，不是模型。每次运行冷启动，只带 PyTorch 定义、shape、dtype，从别的运行不带任何东西，只从自己的测试和计时里学；但模型本身是预训练过公开代码的，Agent 还能读 CUTLASS 头文件、上网、查一个公开 wiki。所以「零」精确等于「不给参考 kernel + 不给官方分数」，不是白板模型。这个区分作者自己在引言里主动写了，我倒觉得挺实在，没藏着。

## 🔧 Archive：把记忆整个搬到模型外面

一场长搜索测过的候选，远比任何一个 Agent 的 context 装得多。怎么办？把记忆外置。

![图 3：archive 的读写路径与数据库表结构](https://www.mulanai.com/fs/files/1121_4e0353b4_f2b-shar.jpg)

*图 3：(a) 谁读谁写——LLM controller（keeps no state; a warm restart re-reads the archive and continues）和并行的 Child agents 用 read-only SQL 读，只有 Evaluate 在候选正确时 append 一个 node，失败尝试只记日志不成节点；右侧 Central database 只复制给人看的 Dashboard，final run 里 Agent 从不读它。(b) 写路径是 append-only ledger → 每个候选一个文件夹（solution.json / meta.json / eval.json）→ 单个 builder 重建 SQLite 并原子替换，SQL authorizer 直接拒绝 Agent 写入；表结构以 candidates 为中心，parent link 就是树边，evaluation、official_anchors、problem_meta、profiles、robustness、trace 都挂在它周围。*

细节值得逐条看，因为这套东西才是能复用的部分：

- **读**：controller 和 child 一律只读 SQL。写？想都别想，有个 SQL authorizer 专门挡 Agent 的写请求。
- **写**：只有 evaluation 能 append 节点，而且只在候选正确时。失败尝试记进日志，但不成节点，不进那棵树。
- **一致性**：每个 run 往 append-only ledger 追加一行、给每个候选写一个文件夹；一个 builder 从所有 ledger 重建 SQLite，原子换入；Agent 打开的永远是完整快照，永远看不到写了一半的库。
- **结构**：`candidates` 是中心，一个节点就是一个打过分的正确 kernel，`parent link` 就是树边；没有 parent 的是 root，代表一个全新设计。per-workload 的 evaluation 把公布的 baseline 和 SOL 时间 join 进来，profile、robustness 判定、每一步 Agent trace 都挂在节点上。代码和 profile 留在文件夹里，库里只存路径。

说实话，看到「单 builder 原子替换 + 只读 SQL + authorizer 拒写」这一组组合，我有点被打动。它没什么理论含量，但把分布式系统里最烦的那类脏问题——半写状态、并发写、Agent 顺手改自己的历史——用最朴素的方式一次性堵死了。做过类似长跑搜索的人应该都踩过「Agent 偷偷把评估记录改了」或者「重启后历史丢一半」的坑，这套设计基本是冲着这些坑去的。

接着是这篇论文里我最喜欢的一个判断：**慢的 kernel 也能当垫脚石**。controller 可以沿 parent link 展开任意节点，不只当前最优那个。一个正确但偏慢的新结构，可能通向一堆小修小补永远够不着的收益。数据摆在那儿——Quant/030 的最优路径从 6.25 倍爬到 27.36 倍，可它 270 步里有 76 步是持平甚至更慢的。你想想看，如果只沿当前 best 贪心，这条路径一半都走不出来。这跟 teaser 图 (b) 里那次「改写掉到 1.52 倍」又重新爬起来的形状，是同一件事的两面。

奖励怎么给？也没绕弯子。正确 kernel 的 reward 是它在这道题所有 workload 上、相对公布 baseline 的几何平均加速比：

$$R(k)=\Bigl(\prod_{w\in\mathcal{W}}\frac{t_b(w)}{t_k(w)}\Bigr)^{1/|\mathcal{W}|}$$

child 在自己 B200 上测 $t_k(w)$，存进 per-workload 表，官方分数不进 reward。作者特意没拿 SOL score 当 reward，理由很工程：SOL score 在高加速区间会 flatten out，越到后面越推不动，所以只把它当 context 给 Agent 看。还有个不起眼但很要命的细节——他们自己 pod 的 SM 时钟不锁，能跑到约 1965 MHz，比站点那 1500 MHz 快，本地时间读起来偏快（约 1.19 倍）。人在最外层用一个 Agent 看不到的 calibration 去校正这件事。这种「我知道我的尺子不准，但绝不让被测对象知道修正系数」的克制，在刷榜论文里不多见。

## 🔬 别让搜索把自己骗了：检查全在模型外

所有判定正确性的检查都跑在模型外面，判定结果随每个候选一起存进档案。Table 3 把检查分成五类：官方正确性（每个 workload 都对上参考）、鲁棒性（未发布的 shape 和极端值、内存安全，每个新 best 跑、每次送审多 seed）、规则与反作弊（速度必须来自真计算）、站点就绪（编译不超时、过一遍站点预演）、复核与官方分数（清单判定、人点头、站点自己的检查）。附录里列了全部 12 项送审检查。

三个证据说明这套检查不是摆设。第一，搜索自己就把 reward hack 找出来了，他们在运行途中抓到，赶在任何东西送出去之前往 gate 里补了新检查。第二，有一次宁可要稳的不要快的：L2/079 的一个 best 每个 shape 都过，但 stress 输入下 FP16 溢出，他们直接弃用，接受当时从 1.62 倍掉到约 0.48 倍。第三，最外层站点把 235 个最终 kernel 全部标成正确。

这块我想多说一句，因为它跟同期的经验是对上的。Recursive 那份「自动化 AI 研究」的报告里把话说得很直白：搜索越强，评估器也得跟着变强，correctness audit 本身成了循环的一部分；英伟达 AVO 那条线同样把「区分真优化与钻空子」当成核心难点。所以 CompoundingKernel 把检查整个搬出模型、还让 verdict 可追溯地挂在节点上，跟这个方向是一致的，不是它独创，但执行得比多数工作干净。

## 📊 实验结果：数据能打，但得掰开看

成绩先摆全。截至 2026-11-11，三个公开榜都排第一，235 道题站点全部判正确。

| 榜单 | 题数 | 名次 | SOL 均分 | 单题第一 | 单题前十 | 相对 baseline 加速（站点计时） |
|------|------|------|----------|----------|----------|------------------------------|
| L1 单算子 | 94 | 第一 | 0.823339 | 35 | 84 | 4.04 倍 |
| L2 融合 | 82 | 第一 | 0.819260 | 39 | 76 | 3.62 倍 |
| Quantization | 33 | 第一 | 0.909670 | 15 | 33 | 9.19 倍 |
| 三个公开榜合计 | 209 | — | — | 89 | 193 | 4.40 倍 |

*表 1：论文 Table 4 的官方结果，排名、公开 SOL 均分、单题计数均来自 2026-11-11 的公开榜；加速是站点在公开行上计时的几何平均。*

![图 4：209 道题逐个画出来的加速比，注意横轴是对数刻度](https://www.mulanai.com/fs/files/1121_889c326e_f3-speed.jpg)

*图 4：每题一个点，按 L1（蓝 4.04 倍 / 94 题）、L2（黄 3.62 倍 / 82 题）、Quantization（青 9.19 倍 / 33 题）分三行，黑竖线是各榜几何平均，最右那个孤零零的蓝点靠近 1000 倍。底部标着 `All 209 4.40×` 与 `geomean 4.40× · median 3.78×`，左侧还专门标了「2 problems are slower than the baseline」。横轴 log scale，从 0.1× 到 1000×。*

先讲我喜欢的部分：作者专门用一节论证加速不是被少数离群点抬起来的。多数题落在 2 倍到 10 倍之间，39 道题至少 10 倍，2 道至少 100 倍，最大是 L1/094 的 1062 倍，另有 2 道比 baseline 还慢。中位数 3.78 倍贴着几何平均 4.40 倍，说明分布没有被长尾拽歪。这种「主动证明自己没靠 outlier」的动作，比堆一张 SOTA 表可信多了。

现在说让我皱眉的地方，而且不止一处。

**第一，榜首的成色。** 把 teaser 图 (a) 放大看：Quantization 上他们是 0.909670，第二名 0.909664，差 0.000006；L2 是 0.819260 对 0.818372，差不到千分之一；只有 L1 的 0.823339 对 0.812832 算有点身位。再对上时间线——Quant 榜 10-20 首次拿第一，L1 是 10-27，L2 是 10-29，都是「把那个榜的 rows 公开」的时候拿的；11-07 在 L2 被别的队超过、L1 短暂失守，11-08 Quant 也被超，直到 11-10 深夜把更多 rows 公开，才把 L2 和 Quant 的第一拿回来，作者还特意补一句「我们的公开分数没掉」。

这说明什么？说明这个「第一」是动态的、跟公开策略强相关的，跟「技术上稳定领先一代」是两码事。作者自己把日期全写出来了，没藏，这点我尊重；但读者看到「三个榜都第一」时，脑子里那个画面如果是碾压，就得自己校准一下。

**第二，4.40 倍是跟谁比。** 这个 baseline 是英伟达优化过却没放出来的 $t_b$。论文 §4.2 给了个特别诚实的对照：同样这批 kernel（2026-11-10），在自己 pod 上比 `torch.compile` 默认模式快 11.2 倍，可站点口径只有 4.47 倍。差的两头都摊开了——pod 时钟读快约 1.19 倍，`torch.compile` 又比 $t_b$ 慢约 2.11 倍。也就是说，换个参照物，同一个成绩能讲成 11.2 倍也能讲成 4.47 倍。作者明说「benchmark 的 baseline 才是算数的比较」，我同意，但这恰好提醒我们：加速比这东西，尺子比数字重要。

**第三，SOL 均分没那么接近光速。** 0.5 是 baseline、1.0 是硬件极限，0.82/0.82/0.91 折算下来，L1 和 L2 大概只吃掉了 baseline 到极限之间六成多的空隙。Quantization 的 0.909670 看着最亮，可别忘了那一档的完美 kernel 被站点估成约 38 倍 baseline，L1/L2 只有约 10 倍、FlashInfer 约 29 倍——低精度本来空间就大，9.19 倍里有相当一块是 NVFP4 送的红利。把它跟 L1 的 4.04 倍横着比，其实不太公平。

![图 5：四个榜的收敛曲线，前 15% 时间拿走了绝大部分涨幅](https://www.mulanai.com/fs/files/1121_fd1a23e7_f4-climb.jpg)

*图 5：纵轴是每题 mean best local SOL，横轴是最终运行的时间占比（0% = launch），四条线 L1 / L2 / Quantization / FlashInfer 的起止点分别标在两端：起点 0.747 / 0.682 / 0.835 / 0.750，终点 0.893 / 0.899 / 0.938 / 0.853。左侧灰色阴影是前 15% 时间，中间大字写着 `in the first 15% of the run's time: 73–85% of each board's rise`，并注明是本地 pod 分数、不是官方分数。*

**第四，也是最值得琢磨的一处：收益几乎全在开头。** 前 15% 的时间，每个榜就拿到了 73% 到 85% 的涨幅；换成按评估候选数算，前 2% 的候选贡献了 81% 的 gain。单题中位涨幅是 L1 0.27、L2 0.39、Quant 0.25（本地 SOL）。更狠的是那个相关系数：一道题的正确候选数跟它涨了多少，Spearman 是 −0.36，235 道题，**负**相关。难题吸走大量尝试，收益却很小。论文的解释是后期 slot 被挪去追接近第一的题了，候选数这条轴量的是「代价」不是「收益」。

等等，那问题就来了。论文的 headline 结论是「限制规模的是可靠测量的速率，不是 Agent 数量」，还把一次 warm restart 把每小时评估数抬高 3.6 倍当成核心战果。可如果增益在前 2% 候选就基本吃完了、多堆尝试又不换来更多 SOL，那把测量吞吐拉高 3.6 倍，价值到底落在哪？我自己读下来的猜测是：主要花在「把更多题的单题第一拿稳」上，而不是把 SOL 推得更高——论文 §4.3 那句「late tail is small in SOL, but it decided many per-problem ranks」几乎就是在暗示这个。说实话这块我不完全确定，论文没把这条因果链挑明，我只是觉得「早饱和」和「测量速率是瓶颈」之间有点张力，值得作者自己出来圆一下。这块如果我的理解有偏差，欢迎纠正。

**第五，短板也别跳过。** 最终 kernel 是真家伙，不是库壳子：214/235 是 CUDA C++，13 个 CuTe DSL，6 个 Triton，2 个混合；221 个超过 1000 行，中位约 7000 行；按源码文本匹配，77% 点到 `tcgen05`，72% 发 TMA 拷贝，94% 含内联 PTX，没有一个用 Hopper 的 `wgmma`。可短处同样清楚：普通 GEMM/MLP 和整层离 SOL 最远，16 道公开题掉出前十，21 道题不到 1.5 倍（全在 L1/L2，平均站点 SOL 0.61 对其他人 0.86），两道比 baseline 还慢——L2/037 是 0.30 倍、L1/030 是 0.96 倍。最逗的是 L2/037 这个最差案例有一半是自己造成的：一次 code review 主动否掉了一个已经通过全部自动检查的库 fallback。外部检查救了正确性，也顺手误杀了一次能用的兜底，这个代价作者照实写了。

## 🧪 Controller 对 UCB：赢在吞吐，不在聪明

这组对照我觉得是全篇最有信息量的实验，虽然它长得像个消融。

作者写了一个编码的树搜索，用 UCB 风格分数给节点排序，作为 baseline；在相同墙钟时间下，让 LLM controller 跟它在 38 道配对题上单挑。结果 controller 赢了 35 道。关键在下一句：**按每次尝试算，两者挑节点挑得差不多好**，controller 赢是因为它做出了 2.4 倍数量的正确尝试。

我的第一反应是愣了一下——这不等于说 controller 的「智能」没那么值钱吗？它没在「选哪个父节点更准」上赢，赢在同样时间里能跑完更多次有效测量。作者自己也是这么收的，还引了 Sutton 那篇《The Bitter Lesson》：额外的算力通常会赢，但在 kernel 搜索里，只有当每次新尝试都建立在上一次可靠测量之上，算力才兑现成收益。「可靠测量的速率，不是 Agent 数量，限制了能扩到多大」——这句话是全文的题眼，我觉得比榜首名次有价值得多。

还有两个 null result，我挺欣赏作者肯写：把本来可选的参考资料（自家 skill 和一个公开 wiki）改成强制提供，没有可测量的增益；另有一项搜索设计上的发现也是空的，三个发现里两个是零结果。刷榜论文里愿意把「试了没用」摊开讲的不多。

规模化那一节（§5）顺手给了四条 lesson，格式统一是 challenge → intervention → measured impact → lesson，多数是 live run 里的前后读数。核心那条 §5.1 标题就叫「更多 Agent 不等于更多实验」：一次 warm restart 修复把每小时评估候选数抬高 3.6 倍，而锁等待（lock waits）把矛头指向测量通路，而不是 Agent 数量。一千多个 Agent session 同时跑、评估过的候选里 98.4% 正确（截至 2026-11-02）这些数，都是为这个判断服务的。

聊到这儿该升一维了。把「LLM 当变异算子 + 可执行评估打分 + 档案库存优 + 从优继续改」这个配方摊开，你会发现它不是这篇发明的。

所以论文引言里那句「近期新硬件上的强 kernel 结果，大多来自固定前沿模型套一个搜索或 harness」，不是客套，是准确的自我定位。它没宣称自己发明了新搜索算法，明说的是「一个只给目标的 Agent 已经是很强的 baseline，所以 harness 必须靠测量证明自己配存在」——然后真的去做了 A/B：38 题赢 35 题、2.4 倍正确尝试、warm restart 3.6 倍。

这跟最近一篇递归自改进综述里的判断也对上了：控制变量研究显示，发现能否成功，很大程度取决于模型外面那圈执行基础设施（token 预算怎么在「多而浅」和「少而深」之间分、评估失败怎么处理），跟模型能力本身关系没那么大；不少看起来像「模型自我改进」的收益，其实改进的是模型搜索所依赖的脚手架。CompoundingKernel 那个「测量速率才是瓶颈」的结论，基本是这个论断在 GPU kernel 场景里最干净的一次实证。

那「从零」到底该怎么看？我前面说过，它精确等于「不给参考 kernel + 不给官方分数」，跑在底下的是固定的 Claude Opus 5.5，外加 CUTLASS 头文件、互联网和公开 wiki。标题里那个 Zero 有营销味，但论文本身把边界写清楚了，算不上误导。

倒是有一处我觉得值得追一下。论文反复强调「官方分数从不进入搜索」，①② 循环在最终运行里也确实无人干预。可 §3.5 白纸黑字：从 2026-10-25 起，人按每道题跟第一名的差距来分配 child slots——接近第一的题多给，稳居第一的让出一些，机群总量不变；Agent 只收到一个 slot 数。分数、排名、提交结果确实没进 ①②，但「哪道题拿到更多并行试验」这个直接决定搜索资源怎么配置的决策，是由公开榜单驱动的。这是人在最外层做算力调度，工程上完全合理，我不觉得是作弊；只是「搜索与榜单完全隔离」这个说法，得打个折扣听。分数没进门，可它站在门口替你分了算力。

还有几处缺口，照例列一下：论文没给总计算成本——一千多个 Agent session 跑了多久、烧了多少 B200 小时、多少 token，一个字没有；这让「每小时评估数 3.6 倍」这个战果少了一个分母，性价比没法算。没测别的硬件或更大规模，跨架构能不能迁移存疑。FlashInfer-Bench 那 26 道题只在站点上以私有行验证了正确，结果不公开。这几个都不算硬伤，但如果你打算照着复现，得心里有数。

## 📝 我的判断，以及能带走的东西

坦率的讲，我不会把这篇归到「底层突破」那一档。配方是现成的，理论没新东西，连它自己都把「goal-only agent 已经很强」写进引言了。我给它的标签是**工程派的胜利**——把一套大家都在用的循环，用足够狠的纪律跑到 235 道题全部正确、三个榜都挂上名，并且把「哪里没赢、哪里是空的、哪天丢了第一」全留了记录。在一堆「demo 看着炫、实验经不起推敲」的工作里，这种扎实反而稀缺。

真要挑最值钱的一块，不是 4.40 倍，也不是榜首，是那个外置 archive 的工程实现和它背后的两条纪律：

- **记忆外置且可审计**：append-only ledger、单 builder 原子替换、只读 SQL、authorizer 拒写。别指望模型 context 装得下一场长搜索，更别让被测对象碰自己的历史。
- **判定外置且会进化**：正确性、鲁棒性、反作弊全在模型外，verdict 挂在节点上可追溯；搜索会自己找出 reward hack，所以 evaluator 得跟着一起变强。
- **优化吞吐量而不是堆人头**：盯「每小时可靠测量数」，lock waits 会诚实地告诉你瓶颈在哪。一千个 Agent 铺开不等于一千个实验。
- **让 harness 可热更新、历史不可丢**：warm restart 而不是 cold start，改 prompt、改工具、改评估都不牺牲积累。
- **允许慢的中间解活下来**：别只沿当前最优贪心，Quant/030 那条 270 步里 76 步走低的路径就是反例。

如果你也在做带可执行反馈的 Agent 搜索，这套东西值得花半天拆一遍，尤其是 Figure 2 那张数据库图和那 12 项送审检查。不一定要照搬它的四层循环，但「把记忆和判定都搬出模型、然后专心优化测量通路」这个直觉，是能迁移的。

还有一个更根本的问题它没碰，我也没想明白：当增益在前 2% 候选就基本吃满、堆算力主要换来的是单题排名而不是 SOL 提升时，这类搜索的「规模化」到底该以什么为目标函数？继续拉测量速率，是在逼近硬件极限，还是在把一个已经饱和的榜单磨得更细？论文把现象诚实地摆出来了，答案留给下一个人。
