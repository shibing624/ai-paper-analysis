# 一个 4B 小模型，凭什么接管所有 Agent 工作流的"选择困难症"？

上周我在算一笔账：一个跑 WebShop 的 Agent 完成一单购物要走十几步，每一步都得把整段对话历史、商品列表、页面状态重新塞给大模型，让它吐出下一个动作。看着账单我有点懵——这十几步里，一大半根本不是在"创作"，只是在"从几个候选里挑一个"：这个结果要不要点进去、颜色选哪个、价格有没有超预算。让一个按秒计费、按 token 收费的大模型反复做这种是非题，说实话挺奢侈的。

更别提那些本来就该写成 `if` 的判断，也被塞进了提示词里让模型"想一遍"。

你可能觉得，那就加个小模型呗，便宜的活交给它。这个思路一点都不新，业界已经有了一批所谓的"决策模型"。但真到自己动手的时候，麻烦就来了：每接一个新工作流，都得有人去读代码、手工挑出"哪几步是选择题"，再给这几步单独训一个小模型。工作流一换，前面全白干。

这篇论文戳的就是这个痛点。而且它给的解法，我读完之后的第一反应是——这个切入点选得挺巧的。

## 🎯 核心摘要

Agent 每一步都调大模型太贵，可大量中间步骤只是在有限候选里做选择。以前的双系统方案能给这类步骤配个轻量 System-1，但决策点全靠工程师按工作流手写 hook，换个场景就失效。AnyS1 换了个思路：直接从公开的、人类写好的程序性技能文档（`SKILL.md`）里，把"哪里要做选择、有哪些选项"自动挖出来，在隔离容器里跑真实轨迹收集状态，用双教师一致性标注，训练**一个**经过置信度校准的 4B 决策模型。运行时常规判断一次前向就出结果，置信度不够才 defer 回大模型。在三个没见过的基准、两套不同的大模型上，端到端成本降了 75–91%，关键路径模型时间降了 63–92%，任务成功率基本不掉。

但这篇文章最值钱的地方，不是那个"省 91%"的数字，而是它把"决策点从哪来"这件事从手工活变成了可批量挖掘的数据工程。至于省下来的钱到底该记在谁头上，坦率讲，得拆开看——这正是后面我要较真的地方。

## 🤔 问题动机：卡住双系统 Agent 的从来不是模型，是 hook

先把背景聊清楚。Kahneman 那本《Thinking, Fast and Slow》把人的认知拆成快、慢两套系统：System 1 快、自动、不费劲，认个脸、读个路牌；System 2 慢、费劲、讲逻辑，算个账、做个规划。搬到 LLM Agent 上，对应关系其实很直白：大模型负责规划、开放式生成、拿不准时的兜底；而那些"从固定选项里挑一个"的琐碎判断，完全可以交给一个不生成文本、只输出选项概率的小模型。

说到这个，2026 年这批"决策模型"（Jev、Kev 之类）就是干这个的：给一段状态、一个问题、一组候选，一次前向返回每个选项的概率，几十毫秒出结果，还自带一个能当阈值用的置信度。顺手一提，这类模型按输入 token 计价、输出不收费，官方口径是每百万输入 token 约 0.042 美元，比让大模型把动作一个字一个字生成出来便宜太多。`confidence >= τ` 就自己拍板，`< τ` 就升级给大模型——这套 confidence gating 现在几乎是双系统架构的标配了。

问题出在哪？出在这些方案全都绑死在一个固定工作流上。你得先有人通读这个 Agent 的代码，手工圈出"第 3 步是选商品、第 7 步是选颜色"，把这些点硬编码成 hook，再只在这些 hook 上采数据、训一个专属 System-1。工作流 A 训一个 S1A，工作流 B 训一个 S1B，各管各的。

![图1：先前的双系统方案与 AnyS1 的对比（对应论文 Figure 1）](https://www.mulanai.com/fs/files/1120_5fcf2335_fig1_mot.jpg)

*图1：上半部分 (a) 是老做法——每个工作流由工程师手挑决策点，训一个专属 System-1；下半部分 (b) 是 AnyS1——离线从十万级公开技能里挖一次决策点、训一个通用 System-1，运行时任何 Agent 选中某个技能，就把它当双系统工作流来跑。*

你想想看，一个通用 Agent 面对的是不断变化的新任务、新工作流，压根没人提前给它声明 hook。于是每一个判断都只能退回大模型，双系统等于白搭。这个"per-workflow engineering"的死结，就是标题里那个 "Anywhere" 想解的东西。

作者的观察挺有意思：现在通用 Agent 越来越靠**技能**（agent skills）来拿工作流。一个技能就是个文件夹，核心是 `SKILL.md`，里面写着分步骤的操作规程、分支条件、检查项。Anthropic 把这套做成按需加载的渐进式披露——平时只在系统提示里放个名字和一句描述，真用上了才把正文读进上下文，还能顺带带脚本和参考文档。

关键就在这：一份写给人看的"操作规程"，天然就写清楚了**哪儿要做选择**、**可选的有哪几种**。比如"先判断这是新设计、改现有界面、还是修某个具体 bug"，这本身就是一道三选一的选择题，还自带选项。所以技能文档不只是提示词，它是一份现成的、跨领域的决策点清单。

这个洞察我觉得是全篇最漂亮的一跃：既然决策点本来就藏在人类写的规程里，那就别再让人手工圈了，直接从技能库里挖。

## 🏗️ 方法核心：从散文里挖出选择题，再教会一个小模型

![图2：AnyS1 在单个决策点上的完整流程（对应论文 Figure 2）](https://www.mulanai.com/fs/files/1120_435862a3_fig2_fra.jpg)

*图2：左边离线——从 `frontend-review/SKILL.md` 里挖出 "UI 工作类型？" 这个决策点（design / build / review / fix / none of the above），用 OpenHands 在隔离容器里跑合成任务拿到真实状态，两个选项顺序颠倒的教师投票一致才保留标签，训出一个通用 System-1。右边在线——D 步跑代码、G 步交给大模型、E 步由 System-1 一次前向判定，置信度高就采纳（如 accept review），低就 defer（如 contrast ok? → System-2）。图里的概率是示意值。*

### 先把工作流拆成三类节点

AnyS1 把技能里的每一步按"要不要动脑、动多少"分成三类。这个分类是整篇文章的地基，值得单独摆一张表：

| 节点类型 | 通俗解释 | 谁来执行 | 占比（Any-DP 里） |
| --- | --- | --- | --- |
| D（deterministic，确定性） | 结果由结构化状态完全定死，比如固定工具调用、计数器加一、价格比较 | 直接编译成代码，零 token | 21.3% |
| E（enumerable，可枚举） | 读一段非结构化内容，从有限候选里选一个，比如选商品、判类型 | **System-1 一次前向**，低置信度才 defer | 64.5% |
| G（generative，生成式） | 开放式输出，比如写查询词、写点评 | 留给大模型 | 14.2% |

一句话概括这个拆法：能写成 `if` 的别问模型，必须创作的才找大模型，夹在中间那大片"选择题"才是小模型的地盘。而数据告诉我们，选择题才是大头——64.5% 的节点是 E，100% 的技能至少含一个 E 节点。

等等，这里有个容易被忽略的细节。作者特意统计了 E 节点的"判断类型"：64.6% 需要结合上下文做语义推断，只有 17.8% 是字面查找。这个数字其实是在替自己辩护——如果大部分 E 节点只是查表，那写几条静态规则就够了，根本用不着训个模型。正因为大半要靠语义，才需要一个真正学过的 System-1。

### 离线三步：挖点、跑轨迹、投票标注

**第一步，从技能散文里挖决策点** 对每个技能，让一个 LLM 分析器独立把 `SKILL.md` 和附带文档读三遍，输出结构化候选：问题 $q$、选项集 $O=\{o_1,\dots,o_n\}$ 及每个选项的一句话定义 $d(o)$，还有一段逐字引用作为证据。这个引用要用精确字符串匹配去核，防止模型瞎编。三轮结果再让 LLM 合并，记录每个点的支持度 $\sigma(p)\in\{1,2,3\}$，只保留 $\sigma \ge 2$、能从状态单独判断、且至少带两个候选外加 "none of the above" 的 E 节点。

三遍独立读 + 逐字核证据 + 支持度投票，这套组合拳的目标很明确：挖出来的点必须是技能里真有的分支，不能是模型脑补的。说实话，这种"用模型生成、再用确定性手段验一遍"的套路，在数据合成里已经是标配了，但用到"挖决策点"这个粒度上，我是真的觉得挺干脆。

**第二步，合成任务并在真容器里跑出状态** 光有 $(q, O, d)$ 模板不够，训练还得有真实的状态 $s$。作者明确点出：直接让 LLM 编一段"干净的状态摘要"是行不通的，因为真实轨迹里的工具输出是碎片化、被截断、夹着报错的。于是对每个技能合成一个多阶段的 Linux 任务：带输入文件、参考解、隐藏验证器，还故意塞两个跨类别的干扰技能，逼 Agent 既选对技能又跨过依赖阶段。任务只有在隔离容器里"验证器拒绝初始文件、接受参考解"才算合格。然后让 OpenHands Agent 真去跑这个任务，一个轨迹定位器把决策发生那一刻之前的原始观测（用户消息、工具输出，不含 Agent 自己的推理）逐字抠出来，当作状态 $s$。

这一步是我认为整篇最扎实的地方。它把"状态"从模型想象出来的漂亮散文，换成了容器里真跑出来的、带噪声的现场。后面消融实验会证明这个坚持值多少钱。

**第三步，双教师一致性标注** 执行 Agent 自己的动作未必最优，单次 LLM 教师又有选项顺序偏置。于是对每个状态查询两遍教师，第二遍把候选顺序整个颠倒（"none of the above" 始终排在末尾），只保留两遍答案一致的样本。教师一致率 89.2%，等于约一成样本被丢掉。

跑完这一整套，得到数据集 Any-DP：

| Any-DP 统计 | 数值 |
| --- | --- |
| 公开技能数 | 1,072（来自 SkillMD-138K，16 个类别） |
| 决策点（D / E / G，%） | 17,865（21.3 / 64.5 / 14.2） |
| 含 ≥1 个 E 节点的技能 | 100% |
| 容器验证过的合成任务 | 2,846 |
| 一致性标注状态 $\lvert\mathcal{D}\rvert$ | 25,986 |

附录里还有几个耐心的细节：用 MinHash 去重、每个仓库最多取 3 个技能、按仓库级别先切训练/留出集，并且把所有跟评测基准沾边的技能（SOPBench、ALFWorld、WebShop、SkillRL、τ-bench）严格排除，做 benchmark 去污染。标注样本中位选项是 3 个（外加 none），6.7% 的标签是 "none of the above"。冷启动阈值用的 153 个校准状态、离线开发用的 185 个状态，来自另一批 Apache-2.0 的容器轨迹，跟训练数据不重叠。

### 训练：一个 4B 的"指针"，重点在别太自信

骨干模型是 Qwen3.5-4B-Base，挂一个 option-interaction pointer head。运行时实例 $x=(s,q,O,d)$ 被结构化分隔符序列化成一条序列：

$$\tilde{x}=\big[\langle\mathrm{s}\rangle, s;\ \langle\mathrm{q}\rangle, q;\ \big(\langle\mathrm{opt}\rangle, o_i{:}\,d(o_i), \langle/\mathrm{opt}\rangle\big)_{i=1}^{n};\ \langle\mathrm{dec}\rangle\big]$

一次前向之后，把 `<dec>` 的隐状态和各个 `</opt>` 的隐状态丢进一层无位置的双向自注意力，让候选之间互相"照个面"，再各自跟 `<dec>` 匹配，softmax 出 $p_f(o\mid x)$。这么设计是为了让选项顺序不敏感、选项之间能互相比较——选择题嘛，选项本来就该放一起看，而不是各判各的。

训练配置（附录给的）：rank-16 LoRA（$\alpha=32$），铺在 attention、MLP 和 Gated DeltaNet 投影上；指针投影维度 256；bf16，1 个 epoch，学习率 $10^{-4}$。

但真正关键的，是那个损失函数：

$$\mathcal{L}=\sum_{(x,y)\in\mathcal{D}}\mathrm{CE}\big(p_f(\cdot\mid x),\,(1-\epsilon)e_y+\epsilon u_O\big),\quad \epsilon=0.1$

这就是 label smoothing，把 one-hot 标签往均匀分布上抹一点。为什么非要它？因为运行时那道门是靠"最大概率"当置信度用的。硬标签交叉熵会把没见过的状态也推到接近 1.0 的过度自信，模型一脸笃定地答错，门控就形同虚设。抹一点均匀质量进去，概率才有分辨力，阈值才跨得过域。这块后面消融会给一个挺直观的反例。

### 运行时：一道置信度门，和两种阈值

门控本身简单到一行：

$$g(x)=\mathbb{I}\big[c(x)\ge\tau\big],\qquad c(x)=\max_{o\in O}p_f(o\mid x)$$

置信度够就采纳 System-1 的选择，不够就退回大模型。`All-S2`（全交大模型）和 `All-S1`（全交小模型）是这道门的两个极端。

阈值 $\tau$ 怎么定，作者给了两套：

- **冷启动**（cold / AnyS1-zero）：拿 153 个留出开发样本拟合**一个**全局阈值 $\tau=0.918$，零目标任务运行，三个基准原样套用。
- **无标注开发校准**（warm / AnyS1-main）：对一个已经在跑的工作流，用大模型跑 50 个不带标注的开发 episode，同时记下 System-1 的打分，对着大模型的决策拟合 $\tau$。不用人工标注，但要额外跑这 50 趟。

每个阈值都要求在"被采纳的判定"上至少达到 95% 与大模型一致，且在任何测试之前就预先注册好。评测时各配置共享一份完全相同的大模型请求缓存，只有 System-1 真正拍板的地方才分叉——这个控制变量做得挺干净，值得点个赞。

### 顺手把成本账算清楚

作者给了一个成本分解式，我认为比任何单个百分比都更能说明这套方法的天花板在哪：

$$\frac{C}{C^{\mathrm{S2}}}\;=\;\underbrace{\frac{C_G}{C^{\mathrm{S2}}}}_{\approx\,1-s_E}\;+\;\underbrace{\frac{C_E}{C^{\mathrm{S2}}}}_{\le\,s_E}\;+\;\underbrace{\frac{C_{\mathrm{S1}}}{C^{\mathrm{S2}}}}_{\kappa}$$

$s_E$ 是未编译 Agent 花在 E 节点上的成本份额，$\kappa$ 是小模型自身的开销。翻译过来：能省的钱，上限就是 E 节点原本占的那部分，再减去小模型自己的成本。G 节点（开放式生成）那部分你动不了，D 节点本来就该编译掉。

这个式子后来直接决定了实验里那个"省多少"的物理边界。记住它，等下看 RQ3 会很有用。

## 🧪 实验结果：数字很能打，但得拆开看

### 设置

三个都没见过、跟 Any-DP 零技能重叠的基准：SOPBench（268 个留出任务，策略约束的多轮客服对话，从机器可读 SOP 确定性编译）、ALFWorld（134 个任务，多房间物体搜索，从 SkillRL 技能库编译成 6 个任务族程序）、WebShop（500 条指令、118 万商品的目录，编译成 7 个品类程序，15 步上限）。

两套大模型主干：DeepSeek-V4.1-Flash（主）和 GPT-6 Sol（跨家族）。System-1 始终是**同一个** 4B 模型，只在 Any-DP 上训过。基线有三个：直接读原始技能文档的未编译大模型 Agent、把技能编译成 D/E/G 但每步仍调大模型的 `All-S2`、以及商业决策模型 Jev 当 System-1。

指标上，任务效果看 Pass（SOPBench）、SR（ALFWorld）、Score / 二值 SR（WebShop）；效率看相对未编译 Agent 的每 episode 成本节省（Sav.%）和每 episode 关键路径模型调用时间。定价口径：大模型和商业 Jev 按官方 API list rate，自托管的 4B System-1 按 L4 GPU 服务吞吐折算成每千次单次判定 0.0045 美元。

看到这张表，我的第一反应不是"哇省了 89%"，而是先去找那个 −17.8。未编译 Agent 直接读技能文档，比编译后的版本低了近 18 个点——编译这一步把散文化规程变成显式的 D/E/G 控制图，机械的工具编排不再占大模型轮次，对话历史不再越滚越长，跳步也少了。**光是编译，就把宏平均效果拉了近 18 个点，省下 76–86% 的成本**（平均 81%）。

这就把标题里那个 75–91% 拆成了两截：编译贡献了大头，System-1 只是把剩余那部分 E 节点成本再吃掉一截，把平均节省从 81% 推到 89%。8 个点，不是零，但跟 81% 完全不是一个量级。作者在正文里其实很诚实地写了 "two orthogonal levers"，把两个杠杆分开讲了；只是摘要里那个 headline 数字，太容易被读成全是大模型省下来的。

回到 System-1 本身，几个数字还是挺能打的：warm 在三个基准上把关键路径时间压到 15.6 / 12.9 / 17.1 秒，相对未编译 Agent 是 70–92% 的降幅（All-S2 只有 51–87%）；WebShop Score 甚至从 66.9 涨到 68.1。作者的解释我买账——大模型在这种二元相关性判断上会"过度 deliberation"，反而不如小模型一次打分干脆。这算是省成本之外一个意外的顺带收益。

跨家族那半张表也值得看：换成 GPT-6 Sol，System-1 权重一个字没改，编译单独就省了 71%，warm 推到 82%，冷启动也能有 81% 且成功率只差 0.8 个点。一个只在 Any-DP 上训过的小模型，能同时伺候两套价格、风格都不同的大模型，这个泛化性是实打实的。

### 消融：三个组件，各值多少钱

| (a) 运行时门控 | SOP | ALF | WS |
| --- | --- | --- | --- |
| AnyS1 warm | 84.3（0.09×） | 95.5（0.12×） | 68.1（0.14×） |
| AnyS1 cold | 83.2（0.13×） | 95.5（0.15×） | 67.9（0.11×） |
| All-S1（无门） | 84.3（0.09×） | **40.3**（0.04×） | 66.3（0.02×） |

*表2a：括号里是相对未编译 Agent 的成本倍数。SOP/WS 是分数或得分，ALF 是 SR。*

短程路由工作流没了门控也活得下去，但长程的 ALFWorld 直接从 96.3% 塌到 40.3%。一次选错房间，后面几十步全在错的地方打转——这类级联失败，正是置信度门存在的理由。这个对比看得我有点后背发凉：省成本的方案一旦在长任务上翻车，翻得会非常彻底。

| (b) 训练状态来源 | Dev | SOP E | ALF E |
| --- | --- | --- | --- |
| Any-DP（容器真实状态） | 83.8 | 93.5 | 68.9 |
| LLM 编造的摘要 | 65.0 | 91.7 | 63.6 |

*表2b：三随机种子决策准确率（%）。*

容器里跑出来的真实状态，在留出开发集上比 LLM 写的漂亮摘要高出 18.8 个点，ALFWorld E 高 5.3 个点。而且附录里说，那个合成基线用了 84,481 条摘要，是 Any-DP 的 3.3 倍——数据更多反而更差。原因不难想：干净的散文摘要，跟真实终端里被截断、夹着路径和报错的输出，压根不是一个分布。这一步几乎是在给"别偷懒用合成状态"下结论。

| (c) 校准目标 | 平均准确率 | 平均 ECE | 平均门控一致率 |
| --- | --- | --- | --- |
| Label smoothing | 82.4 | 0.094 | 97.7 |
| 硬标签 CE | 82.3 | 0.146 | 92.4 |
| CE + Brier | 81.9 | 0.148 | 93.7 |

*表2c：ECE 越低越好。*

三种损失下原始准确率几乎一样（81.9–82.4），但校准差了一大截。硬标签把 logits 推到接近 1.0，于是拟合出来的阈值一路膨胀到 $\tau=0.998$——门几乎永远关不上，跨域一致率从 97.7% 掉到 92.4%。这条消融我特别喜欢，它把一个"看起来只是训练技巧"的 label smoothing，跟线上门控能不能用直接挂上了钩。**准确率没变，可用性却没了**，这种反差比涨几个点有说服力多了。

在留出 Dev 上，这个训过的 4B（83.8%）超过了商业 Jev（78.4%）和零样本的 Qwen3.5-27B（85.9 差一点，但那是 27B）。option-interaction head 比标准 pointer head 高 1.1 个点——不大，但方向对。

### 置信度到底选对了吗

| 基准 | AURC（门控） | AURC（等率随机） | 委派率 | 门控一致/每百错 | 随机一致/每百错 |
| --- | --- | --- | --- | --- | --- |
| SOPBench | 0.014 | 0.086 | 98.0% | 92.7 / 7.1 | 91.4 / 8.4 |
| ALFWorld | 0.100 | 0.318 | 50.4% | 92.4 / 3.8 | 68.2 / 16.0 |
| WebShop | 0.156 | 0.302 | 41.4% | 84.3 / 6.5 | 69.8 / 12.5 |

*表4：置信度门控 vs 同等委派率的随机委派，AURC 越低越好。*

这组数据回答了一个挺关键的问题：门控让正确率保持住，到底是因为"委派得少"，还是因为"委派得准"？等率随机委派的控制组说明是后者——委派同样比例的决策，随机挑会把与大模型的分歧放大四倍多，ALFWorld 每百个决策的不一致从 3.8 涨到 16.0。AURC 降了 2–6 倍。所以是**置信度排序**在干活，不是保守。

### 省钱的物理边界在哪（RQ3）

把成本和时间归一到未编译 Agent 上，E 节点在 ALFWorld / WebShop 占 17–22% 的成本、11–18% 的时间，SOPBench 只占 4% 成本和 19% 时间（G 节点反倒占 10% 成本、30% 时间）。这跟前面那个成本分解式对上了：SOPBench 的 E 成本天花板本来就低，靠委派已经快顶到极限，剩下的节省来自 G 节点一点边角（9.9% → 8.8%）。

延迟侧的数字很直观：本地 System-1 单次打分中位 21.8–31.7 毫秒（H100，附录实测），大模型一次 E 调用是 1.51–1.78 秒，快 56–81 倍；商业 Jev 走远程 API 要 0.65–0.67 秒。自托管小模型只占未编译 episode 时间的 0.2–0.3%，还省掉了网络往返。这也是为什么自托管 4B 能比商业 Jev 省得更多（89% vs 84%）且延迟更低。

还有个细节挺有人味：各工作流的 operating curve 长得不一样，一个全局阈值伺候不了所有域。冷启动那个 $\tau=0.918$ 在 SOPBench 上偏保守（只委派 40%，但一致率 100%），在 WebShop 上又过度委派（55%，一致率掉到 80%）。而针对目标工作流校准，只要 20 个开发 episode 就能把委派率贴合到全量拟合的 1 个点以内；只用 5 个的话，WebShop 会在 19–75% 之间剧烈摇摆。这个"少量开发集就能定位工作点"的结论，对落地其实比那个 91% 更实用。

## 💡 我的判断：工程整合很扎实，但别把它当成底层突破

聊了这么多数字，该说点不那么顺耳的了。

**那个 75–91% 得拆开记账** 前面说过了，编译平均贡献 81 个点，System-1 再补 8 个。更微妙的是，编译这一步跟 AnyS1 的核心主张（一个通用 System-1）其实是两件事——你把技能编译成 D/E/G 程序，本身就是个独立的、别的方案也能做的工作。论文把两者打包进一个端到端数字里报，读快了容易把功劳记错账户。我不是说作者藏了什么，正文里写得很清楚；只是这个 headline 数字对营销太友好了。

**Anywhere 的边界** 三个基准全都被编译成了显式 D/E/G 程序才跑得起来：SOPBench 靠机器可读 SOP 的确定性编译器，ALFWorld / WebShop 靠 LLM 把 SkillRL 技能库翻成结构化程序。Limitations 里作者自己也认了——最大的成本节省依赖"把程序性技能编译成显式程序"，而"自动编译开放式的仓库级技能"是留给未来的活。其实吧，今天这套能接的是**规程清晰、能翻成控制图**的技能；碰上那种靠临场发挥、分支模糊的开放任务，E 节点挖不出来，通用 System-1 也就没用武之地。标题里的 "Any Agent Workflow"，目前更准确的说法是"任何已编译的工作流"。

**标签的天花板是教师本身** 25,986 条监督标签，来自 DeepSeek-V4.1-Flash 的两遍投票，不是真人标注。所以训练出来的 System-1，本质是蒸馏了大模型在这些 E 决策上的行为。论文用"换成 GPT-6 Sol 权重不变也管用"来论证 Any-DP 抓的是"工作流内在的决策语义，而非教师特定的先验"——这个论断我有点保留。标签由一个教师产出，却说学到的东西与教师无关，逻辑上不是完全站不住，但至少该给个更强的对照。可能我的理解有偏差，但这里我倾向于打个问号。顺带一提，一致率 89.2% 意味着约一成样本被丢掉，这部分恰恰是教师自己都拿不准的硬例子——丢掉它们换来的干净标签，会不会让模型在真正模糊的边界上更没底？门控的兜底大概就是补这个的，但论文没单独拆。

**成本口径值得多瞄一眼** 大模型和商业 Jev 按官方 API list rate，自托管 4B 按 L4 GPU 吞吐折算成每千次判定 0.0045 美元。一个是真实账单，一个是自估折算，还不含运维、显存占用和冷启动。"89% 胜过 84%" 这种细粒度比较，对定价假设是敏感的。这不是硬伤，但读到"比商业方案更省"时，心里得有这根弦。

**放在同期工作里，它是什么位置**？双系统这条线并不新：FrugalGPT、RouteLLM 那类 LLM cascade 早就讲"便宜模型先过一遍、难的再升级"；SwiftSage、LUMOS 那批快—慢 Agent 也在做小模型配大规划器；商业 Jev 把"非生成式、单次前向、带校准置信度"的决策模型做成了品类，Kev、SearchJev、AgentDecision、AnyJev 各自在通用选择、搜索、Agent 状态、抗顺序偏置上补过刀。AnyS1 真正新增的，不是新的模型结构、也不是新的门控理论，而是把决策点从**人工按工作流硬编码**换成**从技能语料里批量挖掘 + 容器执行取真实状态**，再用 label smoothing 把校准塞进训练、用一个模型跨工作流复用。

所以我的定位是：这是一次很扎实的**数据工程 + 系统整合**，方法层面挑不出大毛病，实验也做得干净（共享请求缓存、阈值预注册、仓库级去污染、三随机种子），但离"底层突破"还有距离。它最可能留下的遗产是 Any-DP 这个数据集和"技能即决策点来源"这个视角——以后谁再做通用 System-1，多半得从这条路上走。

**值不值得细读**？值。尤其如果你在搭 Agent 平台、被推理成本摁着脖子，这篇能给你一套能照抄的拆解范式：先把工作流拆成 D/E/G，再看 E 节点到底占多少成本（这决定了值不值得上小模型），然后才是挖点、取真实状态、校准门控。别一上来就冲着"省 90%"去，先算你自己的 $s_E$。

## 🔧 工程启发与一个没解的追问

如果你也在做类似的事，有几条我觉得可以直接搬：

- **先量 $s_E$ 再决定**。E 节点占成本不到 5% 的工作流（比如 SOPBench 那种），上 System-1 的收益天花板就在那，别硬套。编译往往才是第一桶金。
- **状态一定要真跑出来**。让 LLM 编的状态摘要，跟容器里截断的工具输出不是一个分布，18.8 个点的差距不是小数目。
- **门控别省**。长程任务上一次错判会级联崩盘，96.3% → 40.3% 那个对比够警醒。而且校准要进训练目标，光在推理时调阈值救不回过度自信的 logits。
- **少量开发集就能定位阈值**。20 个 episode 够把每个工作流放到自己的 operating point，比"一个全局 τ 通吃"靠谱得多。
- **选项顺序、选项交互**这些细节别嫌麻烦，抗顺序偏置的两遍教师投票和无位置注意力，都是便宜又管用的加固。

还有个更根本的追问留着：当技能库本身在持续更新、新技能每天冒出来，这套离线挖点 + 重新训一个 System-1 的流水线，要不要跟着重跑？论文里的 "one System-1" 是在固定 Any-DP 上训一次就冻结的，真实产品里技能是活的。作者把"从 defer 回去的大模型调用里在线自适应阈值"和"自动编译开放式技能"都列进了未来工作——这两件恰好是把它从"离线演示"推到"线上系统"的关键，也都还没做。这块我自己也还在摸索，可能理解有偏差，欢迎评论区聊。
