# 会接话、会插话，却不会办事：Duopra 把全双工语音模型从「能聊」推到「能干」

🎯 你有没有碰到过这种语音助手：聊起来特别像人，你话说一半它就能「嗯嗯」接上，你中途打断它也能立刻收声，反应快得不像机器。可一旦你让它干点实事——「帮我查一下明天 CA1701 延误多久，啊不对，是后天那班」——它就开始装傻，或者把你那句改了三遍的话原封不动丢给后面那个大模型，然后石沉大海。

我第一反应是，这大概是后端不够强，换个更大的模型不就行了？但读到一个数字的时候我愣了一下：在作者搭的那套流式管线里，基线系统只在 11.0% 的会话中把请求递给了后端，最终 Pass@1 只有 4.7%。也就是说，后端就算开挂，理论上也翻不过 11% 这道墙——因为接近九成的请求压根没被发出去。

问题不在执行，在发起。

---

## 核心摘要

全双工语音模型擅长「什么时候听、什么时候说、什么时候闭嘴」，可一到要调工具办事就掉链子。这篇论文把失败定位得很准：前后端分离架构里，后端执行可以外包，但「把一条完整、参数正确、跟得上用户改口的请求发起出去」这件事只能前端自己扛，于是 Pass@1 被前端的发起率死死卡住，作者管它叫 **hand-off ceiling**。Duopra 的解法挺巧——把后端当成一个叫 `query(task)` 的普通工具，注册进前端原有的动作空间，让「直接调 API」和「委托给后端」共用一套接口和一套评分标准；再用三阶段训练（协议 SFT → 全双工 RL → 只修投影层）教前端在边听边说的流里及时把活干完。同一个 Qwen3-8B 后端下，Pass@1 从 4.7% 抬到 44.7%；不带后端直接调工具是 47.7%，换 DeepSeek 后端到 49.3%。我的判断是：这不是底层架构突破，是一次很干净的失败归因加上扎实的工程整合，但那个天花板分析比涨了多少点值钱得多，做语音 Agent 的人值得花时间读一遍。

## 🤔 问题动机：能聊天，不等于能办事

先把「全双工」这件事说清楚。说到这个，Moshi 那套东西绕不开——Kyutai 在 2024 年把用户和模型两路音频流同时建模，配一个 Mimi 编解码器和一条 Inner Monologue 文本流，理论延迟压到 160ms 左右，实测 200ms。它不再等你闭嘴才开工，而是持续听、持续生成，于是「嗯嗯」这类附和、被人打断立刻停、重叠说话都成了可能。后来 MiniCPM-o 4.5、BayLing-Duplex、Fun-Audio-Chat 一堆工作都在这个方向往前拱。

这类模型擅长的是**对话主体性**：决定何时听、何时说、何时停、何时续。作者给了个挺贴切的词，conversational agency。

但办事是另一码事。用户让你订个东西、查个状态、改个数量，模型得决定何时动手、记住你改口之后说的是什么、把有依赖的几步按顺序做完。作者叫它 **task agency**，任务主体性。全双工场景下这两件事还搅在一起：你的纠正可能在你自己话音没落的时候就到了，工具的返回结果也会在某个时间点插进流里，模型得一边听着一边把动作发出去。

主流做法是前后端分离。前端负责陪聊，判断「这事要不要交给后端、交给它什么」，后端拿着工具 schema 决定怎么执行。Realtime-Venus 的 Harness、DuplexOmni、JoyAI-VL-Interaction、SALMONN-duo 都是这个路子。好处显而易见：执行可以异步外包，前端不用背一堆 API。

坏处藏在一个很朴素的道理里：**没发出去的请求，后端执行不了；发得不完整，还会把后端带沟里。**

### 一个改了两次口的电商请求

![图1：FDB v3 中一个演化请求里前端的责任（ecommerce_19）](https://arxiv.org/html/2611.25773v1/fig1_timeline.png)

*图 1：上半部分是传统前后端分离，下半部分是 Duopra。用户依次说「Search for a laptop… / Wait, a tablet. / Add 2 to the cart… / Actually, just 1.」，同时改了商品和数量，而且 `add_to_cart` 要用到 `search_products` 返回的商品 ID。*

这张图我看了两遍，因为它把问题摆得特别具体。用户先说找笔记本，马上改口要平板；接着说加两个到购物车，又改口说只要一个。加上「加购」依赖「搜索」返回的 `tablet_001`，这已经不是一次请求，是一条会中途变形、还带依赖的链。

上半部分那套分离架构，前端看不到工具 schema，只能一遍遍把「Find a laptop.」→「Make it a tablet.」→「Add 2 to the cart.」→「Make it 1.」递给后端，图右上角标了 **4 hand-offs**。每次改口后端都得先 undo 掉上一个请求再想一遍，纠正信息和工具依赖在来回传递里特别容易丢。图里那几个被划掉的值和弯回来的箭头就是在画这件事。

下半部分 Duopra 让前端直接看见 `search_products`、`add_to_cart`、`query(task)` 三个 schema，自己决定怎么调，右上角是 **0 hand-offs**。前端一边说「Sure, searching.」「OK, a tablet.」「Adding two.」「Done, it's $99.」，一边把修正过的调用直接发出去，用户改口时同样用 undo 撤掉旧请求，但不再需要任何人转述。

图注里那句话是整篇论文的题眼：**Execution can be offloaded, but initiating a faithful request remains a frontend responsibility**.（执行可以外包，发起一条忠实的请求仍是前端的责任。）

### 那道 11% 的墙

作者把这个直觉写成了一个乘法。在请求式委托下，领域工具只有在前端调用了 `query` 之后才会跑，于是：

$$\text{Pass@1} = \text{Call} \times \text{Pass}\|\text{call}$$

`Call` 是有已执行领域工具调用的会话占比，完全由前端决定；`Pass||call` 是这些会话里通过的比例，取决于前端写的任务描述和后端执行。后端再猛，也只能动后面那一项。

RV-Audio + Harness 在 FDB v3 上交出的数字是：hand-off 只发生在 11.0% 的会话，Pass@1 4.7%。就算后端执行满分，天花板也就是那 11.0%。作者顺手做了个配对分析，把有领域调用的那 31 个会话单独拎出来，基线通过 14 个、Duopra 通过 12 个——**一旦请求真的发出去了，Duopra 并没有比基线更聪明**。全部增益来自剩下 269 个会话，Duopra 把其中 122 个基线从未执行过的请求做成了。

看到这张表我才意识到，之前「换个更强后端」的思路完全走反了方向。

## 🏗️ 方法核心：一个动作空间，三阶段训练

![图2：Duopra 在 RV-Audio 上的三阶段训练](https://arxiv.org/html/2611.25773v1/fig2_method.png)

*图 2：Stage 1 在 1 秒 unit 级会话上微调 thinker，冻结语音相关模块；Stage 2 用 Dr. GRPO 训 thinker 的 LoRA，环境里有脚本化用户、模拟工具、后端智能体和打分器，每个任务采样 G=8 条 rollout；Stage 3 冻结 thinker，只重训 thinker→talker 的 projector。图例里火焰是训练、雪花是冻结，括号里的动作是「私有动作，永不发声」。*

### 先把后端降格成一个工具

Duopra 最漂亮的一步，是没另起炉灶做路由，而是把后端塞进前端已有的动作表里。

每个 1 秒的 unit，thinker（语言模型）生成三类东西：双工控制 token `<|listen|>` / `<|speak|>`、会被念出来的公开文本 $w_t$、以及永远不发声的私有动作 $a_t$。$a_t$ 是编码在 `<delegate>` span 里的 JSON，`select` 用来取工具 schema，`call` 用来调已暴露的工具。talker 把公开文本合成语音，条件来自 thinker 的隐藏状态；runtime 校验调用，把返回结果作为 `<backend>` observation 插到结果回来之后的第一个 unit 边界。

后端在这里就是一个工具：`query(task)`，参数是一段自包含的自然语言任务描述，里面得带上用户最新的取值、要求的步骤、以及步骤之间的依赖。于是「直接调 `search_products`」和「调 `query` 把整件事委托出去」走的是同一个 `call` 操作、同一套参数校验、同一套成功标准。

作者由此定义了三种**工具可见性（exposures）**：

| Exposure | 前端能看到什么 | 对应做法 |
|---|---|---|
| Backend | 只有 `query`，领域工具在后端手里 | 传统请求式委托 |
| Direct | 只有领域工具 $\mathcal{F}$ | 前端自己调 |
| Both | 领域工具 + `query` | 由同一个策略自己选路，没有独立 dispatcher |

这个设计我喜欢的地方在于，它把「路由」从一个需要额外训练的开关，变成了策略在同一个动作空间里的自然选择。后面实验里 Both 下几乎不委托，恰恰说明模型确实学会了：工具都在眼前时，自己干更划算。

形式化也干脆。整条流是一个因果策略：

$$\pi_\theta\left(y_t\mid x_{\le t},\,e_{\le t},\,y_{\lt t}\right),\qquad y_t=(m_t,w_t,a_t)$$

对话主体性管 $m_t$ 和 $w_t$，任务主体性管 $a_t$，全双工主体性就是让这两组决策在同一个因果策略里都做对。判定「能不能发调用」的规矩叫**信息充分性**：每个必需参数都得有出处——用户语音（**以末次纠正为准**）、前序调用的返回值、或会话上下文里的默认值；缺哪个就只问哪个，可选参数走默认。成功要同时满足调用匹配 gold（参数归一化正确、不多不少）、回答只基于返回的 observation、以及信息充分后 $k_{\mathrm{act}}$ 个 unit 内动手。

### Stage 1：协议 SFT，先教「格式」

第一阶段的活儿不性感，但必要。在一堆合成的 1 秒 unit 级会话上微调 thinker，内容覆盖倾听、追问缺失的必需值、取 schema、发结构化调用、回报工具结果，再掺一些保能力的普通对话。Figure 2 右边那个航班例子很直观：用户问「Is my flight CA1701 delayed tomorrow?」，流里依次是 schema → 两个 `<|listen|>` → `<|speak|>`「Let me check.」→ 私有 `"tool":"flight_status"` → `<|speak|>` 念出「It's twenty minutes…」，工具结果在答案之前到。

损失只盖住 thinker 的参考输出位置（公开文本、私有动作、双工控制 token）：

$$\mathcal{L}_{\mathrm{SFT}}=-\mathbb{E}_{d}\!\left[\frac{\sum_{j\in\mathcal{M}(d)}\log\pi_{\theta}(z_{j}^{*}\mid H_{j}^{*})}{|\mathcal{M}(d)|}\right]$$

embedding、输出头、音频编码器、语音生成模块全冻着。出来的 Duopra-SFT 拿到 Pass@1 26.0%，但 Figure 3 显示 **55.3% 的会话仍然一次调用都没发**。格式学会了，敢不敢动手、什么时候动手，SFT 教不了。

### Stage 2：全双工 RL，教「时机」和「做完」

第二阶段用 Dr. GRPO 训 thinker 的 LoRA。每个任务采样 G=8 条 rollout，共享同一段脚本化用户音频和同一套工具目录；沙箱里有模拟领域工具、冻结的后端智能体（temp 0）、规则 + LLM 裁判组成的打分器，observation 在 unit 边界注入流里。Figure 2 中间那一栏把这套环境画得很全。

课程分两小段。Stage 2a 覆盖直接调用、纠正、澄清、打断、附和，产出 Duopra-RL1；Stage 2b 再加五类任务——有依赖和条件的调用、不同工具可见性下的后端委托、失败恢复——同时回放 2a 的任务，产出 Duopra-RL。

奖励是 time-anchored 的，这点我觉得是全篇最该抄走的工程细节。$k_{\mathrm{act}}=3$、$k_{\mathrm{stop}}=2$ 个 unit：信息充分后 3 个 unit 内动手 +0.1；**用了被用户改口改掉的值，每个 −0.6**；Stage 2b 的结果级奖励里，3 unit 内完整执行且回答有据给 1.2，3~8 unit 给 1.1，更晚 0.9；老实承认只做了一部分给 $0.1+0.15c$（$c$ 是正确执行的步数比例）；编造结果 −0.95；重复执行另罚。不管前端调的还是后端委托的，领域调用都算进完成度。

策略目标就是 Dr. GRPO 那一套，优势用组内均值做基线：

$$A_i=r_i-\frac{1}{|I|}\sum_{k\in I}r_k,\qquad s_{ij}=\min(\rho_{ij}A_i,\bar{\rho}_{ij}A_i)-\beta K_{ij}$$

其中 $K_{ij}$ 是对 Duopra-SFT 的逐 token KL 估计，$L$ 是固定的 token 归一因子。

结果有个很值得玩味的现象：Duopra-RL1 的 Pass@1 是 26.7%，比 SFT 的 26.0% 几乎没动，但 no-call 会话从 55.3% 掉到 43.7%。**多调工具 ≠ 多完成任务。** 真正把分数拉起来的是 2b 那五类带依赖、带条件的任务，以及「做完」而不是「发起」的结果级奖励。到 Duopra，Direct 下 Pass@1 47.7%，no-call 只剩 18.7%。

### Stage 3：只修投影层，把语音救回来

这是个容易被人忽略、但工程上很实在的坑。thinker 一更新，它喂给 talker 的隐藏状态分布就漂了，合成出来的语音会糊。真要重训 talker 代价太大，作者的取巧办法是：**冻结已经训好的 Duopra-RL thinker，只重训 thinker→talker 之间那个 projector。**

做法是把原始 thinker 和 RL thinker 跑在同一段前缀上，各自缓存隐藏状态 $h_j^{\mathrm{orig}}$、$h_j^{\mathrm{RL}}$，让新 projector 的输出方向去对齐基座 projector 的输出方向：

$$u_j^{0}=\mathrm{L2norm}\!\left(P_{\phi_0}(h_j^{\mathrm{orig}})\right),\quad u_j^{\phi}=\mathrm{L2norm}\!\left(P_{\phi}(h_j^{\mathrm{RL}})\right)$$

$$\mathcal{L}_{\text{proj}}=\mathbb{E}_j\!\left[1-\cos(u_j^{\phi},u_j^{0})\right]+\lambda\lVert\phi-\phi_0\rVert_2^2$$

第二项是 L2-SP 正则（$\lambda=0.01$），把 projector 参数往基座权重 $\phi_0$ 上拽。Figure 2 最下面那栏把这个「两条 hidden state 各过一次 projector、再比余弦」的结构画得很清楚。

一句话概括这个设计：**能力改动集中在 thinker，语音退化用一层轻量投影补回来，互不干扰。** 说实话这块我自己做类似事情的时候踩过坑，当时的选择是把整个语音链路重训一遍，成本高还容易把新学的能力冲掉，看到这个 projector-only 的思路确实有点相见恨晚。

一个动作长啥样，大致是这样（示意）：

```json
{"action": "call", "name": "add_to_cart",
 "args": {"product_id": "tablet_001", "quantity": 1}}
```

注意 `quantity` 是 1 不是 2，`product_id` 来自上一步 `search_products` 的返回值——用户末了那句「Actually, just 1.」和步骤依赖，都得在这一条 JSON 里同时兑现。

## 🧪 实验结果：数字，以及数字没说的部分

评测用 FDB v3：100 条真实、带自然卡顿和犹豫的英语录音，12 个模拟 API，其中 66 / 18 / 16 条分别需要 1 / 2 / 3 次调用。每个配置跑 3 个 decoding seed，也就是 300 个 session；一个 27B 规模的裁判模型判参数和回答质量。会话通过的条件很硬：执行过的调用必须匹配 gold，工具名、参数全部正确，不多也不少。对话控制另用 FDB v1.0 的三个 takeover rate（TOR）衡量，并在 MiniCPM-o 4.5 上做过校准。

### 主表：同一个后端，40 个点的差距

| 系统 | Exposure / 后端 | Call ↑ | Pass\|\|call ↑ | Tool ↑ | Arg. ↑ | Resp. ↑ | Pass@1 ↑ |
|---|---|---|---|---|---|---|---|
| RV-Audio + Harness | 原请求接口 / Qwen3-8B | 10.3 | 45.2 | 9.5 | 5.9 | 22.9 | **4.7** |
| DuplexOmni | 前后端 / Qwen3-8B | – | – | 60.0 | 27.5 | 42.0 | 17.0 |
| Duopra-SFT | Direct / 无后端 | 44.7 | 58.2 | 39.2 | 30.1 | 56.8 | 26.0 |
| Duopra-RL1 | Direct / 无后端 | 56.3 | 47.3 | 44.7 | 32.2 | 59.1 | 26.7 |
| **Duopra** | **Direct / 无后端** | 81.3 | 58.6 | 76.7 | 56.2 | 66.3 | **47.7** |
| Duopra | Backend / Qwen3-8B | 86.7 | 51.5 | 81.8 | 57.0 | 70.6 | **44.7** |
| Duopra | Backend / DeepSeek | 77.0 | 64.1 | 71.8 | 55.0 | 69.0 | **49.3** |

*表 1：论文 Table 1 的核心行（%）。绿色下标是相对 RV-Audio + Harness 的 Pass@1 增益，Direct 是 +43.0、Qwen3-8B 后端 +40.0、DeepSeek 后端 +44.7。*

同一个 Qwen3-8B 后端，只把前端换掉，4.7 → 44.7，配对 95% 区间不含零。这个幅度确实能打。但我更想让你看 `Call` 那一列：基线 10.3，Duopra 81.3~86.7。`Pass||call` 其实从 45.2 只涨到 51.5~64.1。**涨点几乎全来自「请求终于发出去了」，不是「执行变得更聪明」。** 这跟前面那个配对分析完全对得上。

还有个反直觉的点：Duopra 在 Direct（完全没有推理时后端）下 47.7%，反而比挂 Qwen3-8B 后端的 44.7% 还高一点。训练出来的前端自己就能干活，`query` 只是备胎。

### Pass@1 是怎么被拆开的

![图4：FDB v3 上 Pass@1 = Call × Pass||call 的分解](https://www.mulanai.com/fs/files/1124_05af4bd2_figA_dec.png)

*图 4：紫色是 Call（有已执行领域工具调用的会话占比），绿色是 Pass||call（这些会话里的通过率），误差线是 95% 的录音级 bootstrap 区间，每个配置 300 个 session。横轴下方标的是各配置的 Pass@1。*

这张图我盯着看了一会儿。从左到右：

| 配置 | Call | Pass\|\|call | Pass@1 |
|---|---|---|---|
| RV-Audio + Harness（FE–BE） | 10.3 | 45.2 | 4.7 |
| Duopra-RL1 / Backend | 33.7 | 59.4 | 20.0 |
| Duopra-RL1 / Both | 50.0 | 48.7 | 24.3 |
| Duopra-SFT / Direct | 44.7 | 58.2 | 26.0 |
| Duopra-RL1 / Direct | 56.3 | 47.3 | 26.7 |
| Duopra / Both | 76.0 | 58.3 | 44.3 |
| Duopra / Backend | 86.7 | 51.5 | 44.7 |
| Duopra / Direct | 81.3 | 58.6 | 47.7 |
| Duopra / Backend, DeepSeek | 77.0 | 64.1 | 49.3 |

紫柱子一路从 10.3 爬到 80 上下，绿柱子基本在 45~64 之间晃。这就是「发起」和「执行」两条独立的线，作者用一张图把它们分开了。

换 DeepSeek 那一列也挺有意思：Call 从 86.7 掉到 77.0，Pass\|\|call 从 51.5 涨到 64.1，乘出来 49.3，跟 Qwen3-8B 的 44.7 相比差异并不显著。更强的后端把已发起的请求执行得更好，但它没法凭空变出请求来。论文原话是 **A stronger backend improves the execution of initiated requests but cannot supply the requests themselves**。

### 训练三阶段：先会发起，再会做完

![图3：训练先压掉 no-call，再把调用变成多步完成](https://www.mulanai.com/fs/files/1124_2e00f047_fig3_ana.png)

*图 3：(a) 各 checkpoint 的会话结局分布，绿=通过、黄=参数错、橙=调用缺失或多调、粉=没调用但有说话、深红=没调用且沉默；(b) 按所需调用次数（1 / 2 / 3 次，对应 66 / 18 / 16 条录音）拆开的 Pass@1。*

(a) 那张堆叠条把训练逻辑讲得很直白：

| Checkpoint | Pass ↑ | No call ↓ |
|---|---|---|
| RV-Audio + Harness | 4.7 | 89.7 |
| Duopra-SFT | 26.0 | 55.3 |
| Duopra-RL1 | 26.7 | 43.7 |
| Duopra | 47.7 | 18.7 |

SFT→RL1 这段，no-call 掉了 11.6 个点，Pass@1 只挪了 0.7 个点。RL1→Duopra 这段，no-call 再掉 25 个点，Pass@1 涨了 21 个点。差别就在 2b 那五类「有依赖、有条件、要恢复」的任务和结果级奖励上。

(b) 按调用次数拆开更说明问题：

| 所需调用次数 | Duopra-SFT | Duopra-RL1 | Duopra |
|---|---|---|---|
| 1 次（66 条） | 38.4 | 40.4 | 58.1 |
| 2 次（18 条） | 3.7 | 0.0 | 24.1 |
| 3 次（16 条） | 0.0 | 0.0 | 31.3 |

SFT 和 RL1 在需要两三次调用的任务上基本是躺平的，Duopra 才把它们拉到 24.1 和 31.3。附录里另一组数字也印证：2~3 次调用任务的通过率，SFT 是 2.0、RL1 是 0.0、Duopra 是 27.5。

剩下的错在哪？no-call 少了之后，**「工具选对了但参数错了」成了最大的失败类**。作者给的例子挺扎心：订单号里字母 O 被听成数字 0。选对工具、保住用户改口后的值，是两件独立的事，模型目前只把第一件做得不错。

### 三种可见性和路由

Both 暴露下，Duopra 几乎不选委托：Qwen3-8B 下 133 个成功里至少 132 个没走 `query`，DeepSeek 下 134 个成功全部没委托，至少 27/28 的多调用成功也是自己调的。工具都在眼前时，策略自己学会了别绕路——这比硬编码一个 dispatcher 舒服多了。

但 Backend 强制只准用 `query` 是要付代价的。事实性回答的延迟，Qwen3-8B 下 Backend 14.85±0.53s 对 Both 10.42±0.33s，DeepSeek 下 13.60±0.60s 对 9.95±0.93s；Qwen3-8B 下 Backend 的参数错误率也明显更高。把结构化 API 调用压成一段「自包含自然语言任务」，等于又引入了一次 NLU，慢一点、错一点都合理。

### 对话控制：三个涨了，一个丢了

| FDB v1.0 TOR | RV-Audio | Duopra-SFT | Duopra-RL1 | Duopra |
|---|---|---|---|---|
| 用户说完后接话 ↑ | 59.1 | 75.1 | 75.6 | **75.6** |
| 真实停顿里误抢话 ↓ | 18.1 | 9.3 | 5.6 | **5.4** |
| 被打断后响应 ↑ | 79.5 | 97.0 | 96.5 | **91.3** |

*表 2：三个 takeover rate（%），均值±标准差在附录里，Turn 59.1→75.6±3.0、Pause 18.1→5.4±0.3、Intr. 79.5→91.3±0.6。*

三个指标全变好，这也是摘要里「task agency can coexist with conversational agency」的由来。但坦率的讲，这个结论得打个折：**所有后训练 checkpoint 在测试项上一个自发附和（backchannel）都不产生了**，而且 Duopra 对打断的响应率 91.3% 还不如 RL1 的 96.5%。作者自己在结论里也承认，spontaneous backchanneling 的丢失说明「保住全部对话行为仍是个开放问题」。

指标涨了、某项行为没了，这是典型的「训练目标写进奖励的才留得住」。奖励里给了 $k_{\mathrm{stop}}$、给了抢话惩罚，却没给附和一个持续的信号，模型自然就把「嗯嗯」优化掉了。看到这里我有点怀疑，如果真上线做陪伴型语音产品，「不会附和」的体感损失可能比 TOR 上那十几个点更致命。

### 语音修复：数字很漂亮，但要看清测在哪

![图5：训练各阶段的 talker conditioning 与语音错误](https://www.mulanai.com/fs/files/1124_2fd981f7_figA_pro.png)

*图 5：(a) 88 条固定文本 pilot 样本上的 CER / WER，灰=基座 RV-Audio、红=Duopra-RL1 配基座 projector、绿=Duopra（Stage-3 projector）；(b) 与原始 conditioning 的余弦相似度，实心点是均值、空心点是 5 分位数，虚线是 1.0。*

(a) 里中文 CER 是 2.05 → 5.17 → 1.78，英文 WER 是 8.97 → 10.33 → 8.70。RL 一训，错误率翻倍还多；换上 Stage-3 projector，不光救回来，还比基座略好。(b) 里 conditioning 余弦均值从 Duopra-RL 的 0.929 拉回 0.974，5 分位数从 0.807 抬到 0.919，直观解释了「漂移—修复」这件事。

正式的 Table 15 在 221 条固定轨迹语句（122 条中文 6156 字 / 99 条英文 2833 词）上，同一个 Duopra-RL thinker、只换 projector：

| Projector | CER ↓ | WER ↓ | ECAPA zh ↑ | ECAPA en ↑ |
|---|---|---|---|---|
| 基座 projector | 6.01 | 9.74 | 0.778 | 0.636 |
| Stage-3 projector | **2.58** | **7.66** | 0.782 | 0.648 |

中文 CER 砍掉一半多，音色相似度几乎没动，改动只落在一层投影上——性价比很高。但作者自己加了一句很诚实的注脚：**这 221 条正是用来挑候选 projector 的选择集，所以这个下降应视作选择集证据，不是独立的泛化估计**。说实话，愿意在正文里写这句的作者不多，这点我给好评。

### 商业系统那一栏，别急着排名

Table 1 上半部分还列了一堆已发表结果：GPT-Realtime 60.0、Gemini Live 3.1 54.0、Gemini Live 2.5 49.0、Cascaded 45.0、Grok 43.0、Ultravox v0.7 41.0，开源侧还有 DuplexAgent-RSI 47.0、Gander 40.0 等。Duopra 的 49.3 看着像是「打平 Gemini Live 2.5、逼近 Gemini Live 3.1」。

但作者明确写了：这些是**参考点，不是同一协议下的排名**。各家评测设置、裁判、打分协议都不同，商业数字用的是厂商自己的 judge，表里有些柱子在原始项目页上是画了斜线的。论文 Limitations 里也把「published results 的可比性」放在第一条。

所以 49.3 和 60.0 之间那 10 个点，既不能读成「只差一点」，也不能读成「开源追上闭源」。真要比，得把 Duopra 放进别家的 harness 里重跑一遍，反过来也一样。这种「同框但不同尺子」的表格，读的时候得多留个心眼。

## 💡 我的判断

**这篇论文最值钱的地方，我觉得不是那 40 个点，是它把失败切在了正确的位置。** 前后端架构大家都在做，遇到任务失败，本能反应是换更强的后端、加更多工具、调 prompt。作者用 Pass@1 = Call × Pass\|\|call 这么一个乘法，加上配对会话分析，把锅稳稳扣在「请求根本没发出去」上，还给了个能直接算的上限（hand-off ceiling）。这种归因做出来之后，解法反而顺理成章：既然瓶颈在前端的发起，那就别再往后端堆资源了，让前端自己能调、并且把「忠实发起」写进奖励。

**三阶段训练的逻辑闭环也挺干净。** SFT 教格式、RL 教时机和做完、projector-only 修语音，每一阶段都对应一个前面暴露出来的具体问题，不是「三个模块拼起来刷分」。特别是时间锚定的奖励——$k_{\mathrm{act}}=3$ 个 unit 内动手 +0.1、用了被改口的值每个 −0.6、编造结果 −0.95——把「全双工里什么叫及时、什么叫跟得住纠正」翻译成了可优化的信号。这个思路我觉得是能直接迁移的。

**但问题也不少，得一条条说。**

绝对数值还是低。47.7% / 49.3% 的 Pass@1，而且判定极严：工具名、每个参数、调用次数全部对上才算通过。作者也提了，用户体感成功率可能更高，因为部分调用其实已经把事情往前推了。可反过来说，300 个 session、3 个 seed、LLM 当裁判，这个统计口径离「稳定可用」还有距离，硬要往产品指标上套会出问题。

实验覆盖偏窄。单一 base model（RV-Audio）、合成语音且音色有限、FDB v3 只有 100 条预录请求和 12 个模拟 API。更要命的是**没有多轮**：固定用户输入不会根据 agent 的回答或工具结果再追问，作者把这条明明白白写进了 Future work。真实办事场景里，「查完了，那帮我改签到下一班」这种 follow-up 才是常态，任务状态能不能跨轮保住，这篇论文没验证。

「共存」的结论要打折。三个 TOR 涨了，自发附和全丢了，打断响应还比中间 checkpoint 退了。用三个指标代表 conversational agency，本身就是把「对话主体性」窄化了。这个方向我自己也还在摸索，可能我的理解有偏差，但至少从体感上讲，一个不会「嗯嗯」的语音助手很难说「更像人」。

还有一处我没完全看懂：`query(task)` 把结构化 API 调用重新压成一段自然语言任务，好处是接口统一，代价是多一次 NLU。在论文里 12 个模拟 API 的规模下看不出问题，可真实业务里 schema 动辄几十个字段、还要带条件依赖，这段自包含描述会不会把参数细节磨平，Backened 那组更高的参数错误率和延迟似乎已经在提示风险了。作者没在更复杂的 schema 上验证，这里留了个口子。

再说全双工 RL 的成本。每个任务 G=8 条 rollout，还得在流式环境里跑脚本化用户、模拟工具、后端和打分器，三阶段叠下来不便宜。论文附录里给了算力配置，但没讨论「只在一小组工具上微调」这种更省的做法，工程上想复现得先掂量掂量。

**放到同期工作里看**，它不算底层突破。Moshi 把双流 + Inner Monologue 做成 foundation model，那是架构级；Realtime-Venus / DuplexOmni / SALMONN-duo 把前后端分离和委托做成了范式；Qwen-Audio-3.1-Realtime 已经在用 GRPO 对齐「说还是做」；SHANKS 甚至让工具调用在用户说话期间就发起。Duopra 站的位置更靠后一层：不换架构，不换范式，而是**把已有范式里那个被默认忽略的前端发起环节拆出来，重新定义接口、重新设计奖励、重新修一遍语音链路**。这种工作容易被低估，但对真正要落地语音 Agent 的团队，往往比又一个新架构更解渴。

### 如果你也在做语音 Agent，几条能直接用的

- **先量发起率，再换后端。** 上线前把 Call / hand-off 比例打出来，如果只有 10% 量级，换什么大模型都白搭，先修前端。
- **把后端注册成一个工具**，让直接调用和委托共用 `call` 接口、共用校验、共用成功标准，别单独训一个路由器。Both 下模型自己会学会少绕路。
- **奖励要挂时间戳**，全双工里「做对了但晚了」和「做错了」是两种病，$k_{\mathrm{act}}$ / $k_{\mathrm{stop}}$ 这类锚点比模糊的「及时性」有用得多。
- **用户改口要显式罚**。每个被纠正后还沿用的旧值 −0.6，这类细粒度惩罚比笼统的「参数正确率」更能教会模型追踪最新意图。
- **动 thinker 之后一定检查 talker**。先量 conditioning 余弦，漂了就只修 projector，别整条语音链路重训。
- **别只盯 TOR**。抢话、停顿、打断这些指标好修，附和、语气、接话的自然度最容易在 RL 里被悄悄优化没，评测集里得给它们留位置。

---

说到底，这篇论文戳破的是一个挺朴素的错觉：我们把「执行」外包给后端之后，就默认「发起」是件不费力的琐事。可在一个用户边说边改口、工具结果随时插进来的流里，把一条完整、正确、及时的请求发出去，恰恰是最难的那一步。Duopra 没把这事做绝——49.3% 的 Pass@1、丢掉的附和、没验证的多轮，都还摆在那儿——但它至少把门指对了。

如果你也在调一个「聊得挺好、办不成事」的语音助手，先别急着换模型，去数一数它到底把多少请求真正发了出去。这个数，可能比任何一张榜单都更能解释你看到的现象。
