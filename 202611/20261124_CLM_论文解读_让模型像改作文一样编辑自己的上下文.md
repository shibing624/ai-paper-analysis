# 把上下文交给模型自己改：CLM 让大模型像编辑文档一样管理记忆

你有没有碰到过这种糟心事：一个 Agent 刚跑起来的时候思路清楚，跑到第三百轮开始复读、开始忘事，你把日志翻出来一看，上下文早就被一堆搜索结果、工具返回、重复的中间结论塞满了。于是你写了个压缩逻辑，到了 28K token 就把历史摘要一遍。结果它把最关键的那个门牌号给摘要没了。

更憋屈的是，这个「到了多少 token 就压缩、压什么、留什么」的策略，是你这个人类写的。模型自己完全没有发言权。

我前阵子在调一个长程检索 Agent 的时候就在纠结这事。压缩阈值设小了，反复重算，GPU 账单难看；设大了，重要的东西被一次性冲掉。中间试过让它自己决定「何时压缩」，也就是给一个 compact 工具让模型调用——好了一点，但工具的参数还是我定的，模型只能在几个按钮里选。当时就有个念头一直没落地：要是模型能像改一份文档那样，直接把上下文里某一段删掉、改写、挪个位置，会怎么样？

这篇论文把这个念头做出来了，而且做得比我预想的狠。

## 核心摘要

上下文管理长期是外部 harness 的活：人类定死压缩阈值、固定几个工具按钮，模型只能被动接受。这篇论文把上下文镜像成一份普通文件，让模型用 Bash 任意编辑，编辑结果下一轮直接同步进 live context，于是「留什么、删什么、什么时候改」变成了模型可以自己搜索、自己学习的能力。零样本条件下，Qwen3.6-27B 在 BrowseComp-Plus 上拿到 59.4% 准确率，比最强基线高 11.4%（相对值）还少用 21.5% 的 prefix-reuse FLOPs；12 小时 EdgeBench 上分数高 5%、算力少 59%；24 小时六仓库智能体集群的下游加速高出 65%。此外用一句指令就能改变策略，技能演化让留出集准确率最多涨 35.9 分，在线 RL 把 Qwen3.5-9B 从 28.8% 拉到 42.5%，配套的 Suffix Cache Reuse 又省下 35% 服务端算力。我的判断：这不是新的模型结构，而是一次接口层面的权力移交，思路干净、实验铺得够宽，但它的收益高度依赖模型自身能力，而且把上下文变成可写文件的同时也打开了新的攻击面——值得细读，别急着照搬上生产。

## 一、问题：上下文管理一直不是模型自己的活

论文开头有句话挺扎人：上下文是语言模型能跨时间保留信息的基石，可上下文管理偏偏从来不是语言模型的原生能力。

顺着这条线看过去，这几年其实有个很清晰的演进。最早是 harness 全包——到预设长度就压缩，或者每轮都压一遍，策略写死在调度代码里。后来慢慢给模型放权：AutoCompact、Self-Compact 让模型决定「何时」压缩；Context-as-a-Tool 把压缩做成模型可触发的动作，但只能作用于事先划定的那部分上下文；ACM 加了卸载和检索；Sculptor 允许模型挑上下文片段来操作。放权是越来越多了，可始终卡在一件事上：**动作空间还是人定义的**。

还有一条支线值得单独拎出来，Recursive Language Models（RLM）把长输入当成 REPL 里的变量，让模型按需递归读取。这一步解决了「读什么、什么时候读」，但读回来的内容照样往 live context 后面追加，上下文该涨还是涨。MemGPT 那类带记忆分层的工作允许模型编辑上下文里一块固定大小的区域，也不是整份 live context。

所以缺口其实很具体：谁能对正在用的这份上下文做**任意的原地修改**？

### 用一个诊断集把这事钉死

作者没急着上大基准，先造了个叫 ContextBench 的诊断集，把上下文管理从推理和知识里剥出来。设计挺巧：环境把输入拆成一串操作，每个操作作为一条新的 user message 塞进来，模型只有跑完 `echo READY_FOR_NEXT_OP` 才会收到下一条。也就是说输入是在模型能动手之前就已经进了上下文，没有任何 harness 能在半路替它截断。任务本身不需要搜索、不需要推理，只要按指令操作就行——一个能「全记住」的 Agent 应该拿满分。这样测出来的分数，纯粹是上下文管理水平。

上下文限制 32,768 token，其中 2,048 留给回复，可用预算 30,720。上下文压力（总输入量除以窗口）最高拉到 24 倍。评分只认最终上下文里的内容，只存在外部文件里的答案不给分——这条规则我觉得设得挺狠，直接堵死了「全卸载到磁盘然后装作自己会管理」的取巧路径。

四个任务：Needle Retention 要在成堆填充行里逐字保留若干 needle 行；Sudoku Sketchpad 要在用户不断流入走子的过程中原地维护一个数独棋盘；KV Store 和 Log Triage 考验大量键值与日志的卸载、精确召回。

![图2：Needle Retention 任务示意](https://arxiv.org/html/2609.37725v1/figures/livectxbench/tasks/needle_retention.png)

*图2：Needle Retention。上方四个竖框是分批到达的输入块，每块里大部分是灰色填充行，蓝色高亮的是必须原样保留的 needle。下方「keep needles」之后只剩一个窄框，里面是攒起来的全部蓝色条。任务不要求模型输出任何东西，评分直接看最终上下文里这些蓝色行还在不在、有没有被改写。*

![图3：KV Store 任务示意](https://arxiv.org/html/2609.37725v1/figures/livectxbench/tasks/kv_store.png)

*图3：KV Store。上半是一串 `SET a7f3 = 9d0e41c2 7b3a…` 这类写入，键是短十六进制串、值是很长的十六进制串。下半是查询 `GET a7f3`，命中的那行被蓝色高亮，其余 SET 行淡出。要答对，模型得把大量值挪出上下文、又能精确取回。*

结果挺难看：摘要式压缩在 Needle Retention 和 Sudoku Sketchpad 上会丢信息甚至编造；没有原地编辑能力的方法，每来一个细粒度走子就得把整个数独状态重新生成一遍；标准编码工具能往文件里卸载 KV Store 和 Log Triage 的内容，却没法按需把它们从 live context 里清掉。四个任务，没有一个现有方法能全做对。

说实话，这个诊断集的作用不是证明「现有方法不行」——这事儿大家心里都有数——而是把「不行」的原因拆得很干净：不是模型不够聪明，是接口不允许。

## 二、方法：把上下文变成一份可以随便改的文件

### 2.1 改动只有一行公式，但性质变了

标准语言模型的上下文转移是追加式的：

$$c_{t+1} = c_t \oplus f^{\mathrm{LM}}_{\theta}(c_t)$$

$\oplus$ 就是拼接。模型每轮吐出的 token 往后面一接，历史只增不减。

CLM 把这一步换成：

$$c_{t+1} = f^{\mathrm{CLM}}_{\theta}(c_t)$$

$f^{\mathrm{CLM}}_{\theta}$ 是「任意函数」，由模型自己控制。这一下就把 Eq.2 变成了一个超集——之前那些暴露 compact / offload / retrieve 工具的做法，全都可以看成 $f$ 被人为限定后的特例。区别在于，那些函数得由 harness 预先定义好，而 CLM 要求模型把「定义函数」本身也当成一种元能力，要么在规划里隐式完成，要么直接写成可复用的函数。

我看到这儿的第一反应是：这不就是把上下文从「只读日志」改成「可读写状态」了吗？对，就是这个。听起来小，但它把一整个设计维度从工程侧挪到了模型侧。

### 2.2 实现朴素得有点可爱

把 live context 镜像成一份磁盘上的普通文件，路径写进 system prompt。模型拿通用 Bash 命令改它，跟改别的文件没区别。唯一特殊的地方是：这份文件的每次修改会自动同步回模型的上下文，并送给 LLM server 继续生成。模型这一轮没动文件，那生成的 token 就按默认规则追加。

这个「默认追加 + 显式编辑」的组合我觉得是整篇论文里最漂亮的一个工程取舍。它没有把上下文管理做成必选项——模型想偷懒就正常聊天，想动手就直接改文件。前缀缓存能复用的情况尽量复用，需要动刀的时候也不拦着。

多智能体那边几乎是白送的：工作区里放多份上下文文件，各同步各的 server，就是 agent swarm；创建/删除文件对应子智能体的启停。不需要额外的编排协议。

### 2.3 模型自己长出来的行为

论文 Figure 3 放了一堆从零样本实验里捞出来的真实代码片段，我挑几个说说，因为这部分比数字更能说明「放开权限」到底放出了什么。

有模型为了编排子智能体，在上下文里手搓了一块 `## STATE` 记分板，写着 `AGENTS: 21 launched, 5 currently running`、`BEST SO FAR 0.9992`、`KEY FILES: /workspace/subctx_4/h_best_final.npy`，然后做了 163 次原地编辑来更新状态，整个上下文一直压在 6–8K token。注意这不是 harness 给的模板，是它自己定的格式。

还有模型在重写上下文时，硬是给自己造了个新角色：把某轮改写成 `[[CTX_TURN 4 role=notes]]`，专门用来放内部笔记——原来的模板里只有 user/assistant 这类角色。另外有模型写 for 循环批量剪掉「No relevant results」的搜索记录，或者对超过 500 字符的工具返回做截断；第 109 步还定义了一个 `compact_turns(text)` 函数，后面调用了 37 次，一边压缩一边维护一段 progress note。 BrowseComp-Plus 的第 20 步里，另一段代码把 21K token 压成答案相关的摘要，顺手留下 `UNTRIED IDEAS (priority order)` 这种待办清单。

这些行为里有一部分其实是在复现人类设计的压缩策略，但「什么时候用、用在哪一段、留哪句」全是模型自己判的。论文搬出 The Bitter Lesson（Sutton, 2019）来给这个思路背书，意思很直白：与其把人类先验写死，不如让模型自己去搜更好的策略。我觉得这次引用算贴切，不是硬蹭。

### 2.4 效率这笔账得重新算

放开任意编辑有个立刻要付的代价：现有推理系统只复用匹配前缀的 KV cache，一旦你在中间改了一刀，从改动点往后全部得重新 prefill。论文因此专门定义了 **prefix-reuse FLOPs**：

$$\mathrm{FLOPs}_{\text{prefix-reuse}} = \mathrm{FLOPs}_{\text{prefill}}(\text{unmatched context suffix}) + \mathrm{FLOPs}_{\text{decode}}(\text{generated tokens})$$

前半是从第一个前缀失配点往后的重算，后半是新生成 token 的解码。附录 C 把这个指标拆到了层级别——L 层、hidden size d、MLP 宽度 $d_{\mathrm{ff}}$、16 层全注意力加 48 层 Gated DeltaNet（Qwen3.6-27B 的配置），每 token 常数 $C_{\text{token}} = 48.70 \times 10^9$ FLOPs，每个 query–key 对 $C_{\text{attn}} = 3.93 \times 10^5$。

附录里那个例子我看完是真愣了一下。取 $P_t = 20{,}000$、$G_t = 500$：纯追加、能复用 18,000 token 前缀时，一轮 $1.41 \times 10^{14}$ FLOPs，缓存省掉 87% 的计算；在中间改一刀只剩 10,000 可复用，涨到 $5.74 \times 10^{14}$；改在开头等于没有可复用前缀，$10.81 \times 10^{14}$——是追加情形的 7.7 倍。

7.7 倍。

所以「让模型随便改上下文」在标准 serving 下完全可能是个赔本买卖。论文敢往下做，是因为它赌模型会学会**少改、改得值**。后面所有实验都用这个指标当横轴，不只是报准确率，这点我很认可——把成本摆到台面上，结论才站得住。

### 2.4.1 一次编辑什么时候回本

「中间改一刀就废掉后面的缓存」这件事，可以写成一个很朴素的回本公式。设当前上下文 $P$ token，编辑点在位置 $p$，编辑点之后的未变后缀长 $S = P - p$，这次编辑净删掉 $\Delta$ token。缓存命中部分按命中价 $r$ 计费（相对未命中价 1，商用 API 里 $r$ 通常在 0.1 上下）：

- **一次性代价**：编辑后的第一轮，后缀 $S$ 从命中价变成未命中价，多付 $(1-r)\,S$。
- **每轮收益**：此后每一轮要读的前缀少了 $\Delta$ token，每轮省 $r\,\Delta$。

所以至少要再跑

$$n^{*} = \frac{(1-r)\,S}{r\,\Delta}$$

轮，这次编辑才不亏。代入 $r=0.1$：在 20K 上下文的开头附近删掉 2K token，$S \approx 18\mathrm{K}$、$\Delta = 2\mathrm{K}$，$n^{*} \approx 81$ 轮；同样删 2K，但发生在尾部 2K 以内，$S$ 接近 0，几乎立刻回本。也就是说，**编辑的位置比编辑的量更要紧**：越靠前、后面压着的东西越多，越不划算。论文那个 7.7 倍的例子，本质上就是 $S$ 取到最大时的特例。

还要补一句，这个公式默认「不编辑就一直追加」。真实场景里窗口会满，不编辑也得压缩，而摘要式压缩同样是改写前缀、同样废缓存。所以 CLM 的比较对象不是「完美追加」，而是「到阈值就整体摘要」。论文里 BCP 上 CLM 比摘要省 21.5%，说的是后者。若你的 Agent 本来就靠追加就能跑完（上下文压力小于 1），那么任何中间编辑都是净亏损。

### 2.4.2 SCR 的正确性代价

SCR 看上去把重算省回来了，但账不是白省的。被搬迁复用的后缀 $C$ 的 K/V，是在**编辑前**的上下文里算出来的：$C$ 里每个 token 当时 attend 的是旧的 $B$，不是 $B'$。把 key 重新做一次 RoPE 旋转，只修了位置，没修内容。于是有三层代价：

1. **近似，不是等价**。如果编辑只是删掉无关搜索结果，$C$ 对 $B$ 的依赖本来就弱，误差小；如果编辑是改正一个事实、改写一段 $C$ 依赖的状态，$C$ 的隐状态里还带着旧版本，模型可能读到「新文本 + 旧语义」的混合体。论文用 $K$ 限制单次搬迁的片段数来约束近似量，但没有给误差界。
2. **经验证据偏薄**。$K$ 的扫描是在 64 道 BrowseComp-Plus 题、一个模型上做的，「性能基本不动」是这个样本上的观察，不能直接外推到编码、长时程集群这类状态依赖更强的任务。
3. **混合模型更粗**。线性注意力层只能退回编辑前的 recurrent state 快照，编辑内容只在 16 层全注意力里生效，48 层看到的是旧状态。这是 Qwen3.6 这类混合结构特有的折中。

还有一条工程上的硬约束：SCR 是给 SGLang 打的补丁，要自己托管推理。用商用 API（缓存只认严格前缀）的人，一份 SCR 的收益都拿不到，只剩前面那条回本公式在起作用。

### 2.5 策略可以学，三种学法

上下文管理一旦变成模型的原生行为，就天然可以被学习。论文给了三条路。

**一句话就能改策略。** 在 system prompt 或任务提示后面加一句自然语言，比如「Compact to 4k tokens once you reach 30k」，模型就照着改压缩时机；换成按语义子问题边界压缩、或者压缩前先备份上下文，也都只要一句话。harness 和模型参数都不动。Figure 9 里灰色是无指令、蓝色是有指令的对照，曲线确实跟着句子走。这个能力在工程上太实用了——以前改一个压缩策略要发版，现在改 prompt。

**技能文档可以演化。** 形式化一下，把指令或技能文档记作 $s$：

$$s^{*} = \arg\max_{s} \mathbb{E}_{x \sim \mathcal{D}}\left[R(\tau(x; s))\right]$$

实现用的是 prompt-evolution loop：每轮在训练集上跑 rollout，proposer 模型读轨迹生成候选技能，在开发集上挑，结束后在留出测试集上评一次。可以是更强的外部模型当 proposer（assisted evolution），也可以模型自己既当 agent 又当 proposer（self-evolution）。Qwen3.6-27B 配 Claude Fable 5.1 是一种配置，Opus 5 自演化是另一种。

![图4：上下文内技能演化的性能—成本前沿](https://arxiv.org/html/2609.37725v1/selfevo_main_two_rows.png)

*图4：四个 ContextBench 任务上的演化结果，上排是 assisted evolution（Qwen3.6-27B 作 agent、Claude Fable 5.1 作 proposer），下排是 self-evolution（Opus 5 一身兼两职）。空心黑圈是 start（无指令），黄色空心圈连成的虚线是 final Pareto frontier，蓝色/紫色实心点由浅到深表示演化轮次从早到晚。上排横轴是 PFLOPs/task、纵轴准确率，KV Store 和 Log Triage 上能看到点群明显往右上移动，Needle Retention 一开始就在 100% 附近、主要在省算力；下排横轴换成 USD/task，四个任务都在更低成本处维持住了 95–100% 的准确率。*

**权重里也能内化。** 因为上下文编辑会改变下一轮的输入，作者用了 stepwise GRPO：对每个 prompt 采一组完整轨迹，按轨迹级结果奖励算标准 GRPO 优势，再把这个优势分配给轨迹里的每一段，让每次模型调用都用整条轨迹的结果来训。

麻烦在于，结果奖励对「编辑」这件事的监督太弱——成功的轨迹里可能混着一堆没必要的编辑，失败的轨迹里也可能有很漂亮的编辑。直接奖励编辑次数或者删掉的 token 数更糟，模型会 reward hack，专门做无用编辑来刷分，还可能把重要信息冲掉、破坏前缀复用。

于是有了我认为方法部分最值得抄的一个设计，**success-gated efficiency advantage**。记轨迹 $\tau_i$ 的 prefix-reuse FLOPs 为 $c_i$，组内成功轨迹集合为 $\mathcal{G}_g^{+}$，均值 $\bar{c}_g$：

$$A_i^{\mathrm{eff}} = \begin{cases} \operatorname{clip}\left(\dfrac{\bar{c}_g - c_i}{\bar{c}_g}, -1, 1\right), & i \in \mathcal{G}_g^{+} \\ 0, & i \notin \mathcal{G}_g^{+} \end{cases}$$

再合成 $A_i = A_i^{\mathrm{out}} + w_{\mathrm{eff}} A_i^{\mathrm{eff}}$。

关键在那个门控：效率信号**只在成功的轨迹之间重新排序**，失败轨迹一律给 0。组内成功轨迹少于两条时也全给 0。这样一来模型没有任何动机为了省算力去把任务做砸，只在「都做对了」的前提下被鼓励选更省的那条。说实话这个设计挺精巧的，比同类工作里按回答长度算效率要扎实——它量的是轨迹级、带前缀缓存的 FLOPs，把上下文编辑引发的重算也算进去了。

### 2.6 服务端配套：Suffix Cache Reuse

光靠模型「少改」还不够，作者顺手改了 serving。标准前缀缓存的做法，编辑把 $B$ 换成 $B'$ 之后，从失配点起 $B'$ 和后面完好无损的 $C$ 都要重算。Suffix Cache Reuse（SCR）的想法是：$C$ 的缓存状态明明还在，凭什么丢？

![图5：标准 serving 与 Suffix Cache Reuse 的对比](https://arxiv.org/html/2609.37725v1/figures/suffix-cache-reuse.png)

*图5：上方是原始上下文 A、B、C 三段。左下 Standard Serving：A 的前缀缓存被复用（蓝色），B′ 需要 prefill（粉色），后面整段 C 被标成红色的 re-prefill，红叉标出第一个前缀失配点。右下 Suffix Cache Reuse：A 复用、B′ prefill，而 C 直接标成 suffix cache reused，不再重算。图例里浅蓝是原始上下文、粉色是编辑后的上下文、红叉是首个失配点。*

具体到实现，SCR 是给 SGLang 打的补丁。SGLang 用 radix tree 维护 token 序列到 KV 缓存的映射，公共前缀共享一条路径，走到最长匹配前缀就停——这个机制对追加式历史是精确的，因为每个 token 的 K/V 依赖前面所有 token，还受 RoPE 绝对位置影响；可一旦中间改了刀，后面所有 token 都得重算。SCR 保留这棵树不动，新 prompt 来了先跟上一轮 prompt 做 diff，找出编辑后仍然存活的片段，按长度从大到小最多搬迁 $K$ 个（正文取 $K = 6$）。对每个搬迁片段，复用缓存的 K/V，把 key 的旋转位置编码重新转到新位置，再拼到 $B'$ 后面。只有 $B'$ 和新增 token 需要 prefill。搬迁来的条目放在会话私有的 cache slot 里，共享 radix tree 永远不会被污染；分配不到 slot 就退回标准重算。

有个细节值得留意：被复用的状态是在**编辑前的上下文**下算出来的，所以 SCR 是对重算的一种近似，不是等价替换。$K$ 限制的就是单次编辑引入的近似量。也是这个原因，作者在 64 道 BrowseComp-Plus 题上扫了 $K \in \{1,2,3,6,12,64\}$，性能基本不动，缓存收益到 $K=6$ 就饱和了，于是取 6 当保守值。

混合模型那块稍微绕一点。Qwen3.6-27B 的 64 层里有 48 层是线性注意力（Gated DeltaNet），只维护固定大小的 recurrent state，没有逐 token 的 KV 条目可搬。SCR 的做法是：编辑前给 recurrent state 拍个快照，之后从快照续上；编辑内容只反映在保留 token 级上下文的 16 层全注意力里。

![图6：SCR 在全注意力层与线性注意力层的实现](https://arxiv.org/html/2609.37725v1/figures/full-vs-linear-attention-reuse.png)

*图6：左侧 Full-Attention Layers，每个 token t1–t6 各有一份 KV，箭头表示每个 token  attend 到之前所有 token；下方 A 的前缀 KV 被复用、B′ 需要 prefill、C 的 KV 被 relocate 并注明「RoPE re-rotated to new positions」。右侧 Linear-Attention Layers，虚线的 S 状态逐个传递、只保留末尾那个固定大小状态 S，下方标注「pre-edit state snapshot reused」，B′ 那格是点状填充的「not recomputed」，C 之后续出 fixed-size state。图例区分了原始上下文、编辑后上下文、未计算部分和 recurrent state。*

还有个白捡的好处：Qwen3.6 这类推理模型的 chat template 会在下一轮到来时把先前 assistant 的 reasoning block 抹掉，标准 serving 于是把保留下来的文本全部重算。SCR 把「剥离 reasoning token」也当成一次上下文编辑来处理，直接复用保留文本的缓存。附录里给了拆解：SCR 在 BrowseComp-Plus 上超出前缀命中的复用占全部 prompt token 的 7.8%，其中 5.3 个百分点来自 reasoning 剥离，只有 2.5 来自模型主动的上下文编辑。也就是说，SCR 的一大部分收益**根本不依赖模型改上下文**，普通推理模型 serving 也能吃到。这个发现我觉得比 SCR 本身还有意思。

## 三、实验：数字说了什么，又没说什么

### 3.1 主战场：编码与深度研究

对比方法用同一套 Mini-SWE-Agent 骨架，包括 MEM1、Self-Compact、ACM、RLM，以及 Codex 风格的摘要 harness；全部零样本、不训练，Qwen3.6-27B、32K 上下文上限、100 轮封顶。深度研究的搜索工具不做成固定接口，而是当作 in-context skill 提供——作者管这叫 less-is-more，harness 层硬编码越少越好，工具可以在推理时灵活增删改写。

| 基准 | 对比对象 | CLM 结果 | 成本变化 |
|---|---|---|---|
| BrowseComp-Plus | Codex 风格摘要（最强基线） | 59.4% 准确率，相对高 11.4% | 少 21.5% prefix-reuse FLOPs |
| BrowseComp-Plus | MEM1 | 同上 | 少 28.9% FLOPs |
| TerminalBench 2.1 | Codex 风格摘要 | 准确率打平 | 只用 70% FLOPs（少 29.5%） |
| TBLite | Codex 风格摘要 | 73.7% 对 67.0% | 用 91% FLOPs |

BCP 那格我盯了一会儿。准确率涨的同时算力还在降，说明模型省下来的不是「少干活」，而是「少做无效的活」——把没用的搜索记录剪掉之后，后续每轮要 prefill 的东西变少了，prefix 命中率反而上去。这跟直觉是反着来的：一般你会觉得频繁编辑上下文必然更费，结果恰恰是编辑让它更省。

但这个「更省」有两个前提要讲清楚：一是对照的摘要 harness 本身就是整体改写前缀、同样废缓存，CLM 赢的是「比摘要更少地破坏缓存」，不是「编辑不破坏缓存」；二是 32K 的窗口很紧，不编辑就爆，追加不是可选项。放到窗口宽裕的生产环境里，这个结论未必成立（见 2.4.1 的回本公式）。

不过有个地方得留个心眼。11.4% 是**相对**提升（59.4 对约 53.3），不是 11.4 个百分点。摘要里写「11.4% higher accuracy」，很容易被读成点数。这类写法在论文里不少，读的时候最好自己换算一下。

### 3.2 更长的时程：数学优化、12 小时、24 小时

数学优化那组对比的是 OpenEvolve（AlphaEvolve 风格的程序生成—评估—进化选择工作流）和把 proposer 换成 Mini-SWE-Agent 的 OpenEvolve-Agent。CLM 这边用同一个基础 harness、只给最小 Bash 接口，把进化算法当作上下文里的指导文本，规划和上下文管理全交给模型。Claude 4.6 Sonnet、同一评估器、100 次打分尝试或 5 小时封顶。

| 问题（方向） | OpenEvolve | OE-Agent | CLM | CLM + 子智能体 |
|---|---|---|---|---|
| Circle packing（↑） | 2.541 | 2.525 | 2.618 | 2.636 |
| Heilbronn triangle（↑） | 0.03127 | 0.03053 | 0.03653 | 0.03617 |
| Min-max / min-dist（↑） | 0.07690 | 0.07724 | 0.07758 | 0.07758 |
| Erdős min-overlap（↓） | 0.38123 | 0.38167 | **0.38094** | 0.38109 |

四个问题 CLM 都拿到最好的 best-of-run，Heilbronn 相对 OpenEvolve 高 16.8%、circle packing 高 3.0%。我的第一反应是：这个对比有点「巧妙」。OpenEvolve 是一套专门的进化工作流，而 CLM 是把进化算法当提示词喂给通用 Agent——赢的其实不是「上下文可编辑」，而是「通用 Agent 的自由度 + 强模型」。要单独归因到 CLM，得看同一 Agent 只把文件编辑权限关掉会怎样，论文在这组里没给这个消融。

长时程软件优化更硬。EdgeBench-10 是单仓库跑满 12 小时、带 verifier 反馈，32K 预算、每任务三个种子取最好。Qwen3.6-27B 下 CLM 拿到 44.6 分、每 trial 179 prefix-reuse PFLOPs，摘要 harness 是 42.3 分、437 PFLOPs；换成 Claude 4.6 Sonnet，CLM 和子智能体变体分别到 51.0 和 50.4，摘要还是 42.3。摘要里那句「分数高 5%、算力少 59%」对应的就是这组。算力砍掉近六成这个数字很能打，而且是在分数还涨的前提下。

有意思的是，作者自己承认子智能体在这个单仓库基准上几乎没额外收益（44.2 对 44.6，还多花 2 PFLOPs）。这种「不利于自己叙事」的结果照实写出来，我读着反而更放心。

Software World 是 24 小时、六个互相依赖的 Python 仓库由六个 Agent 并行优化，GPT-5.6-Sol、272K 上下文预算，在四个没见过的下游包、17 个留出 CPU 基准上按几何平均加速打分。同等花费下，CLM 集群的下游加速比初始版本高出 65%（相对摘要式集群）。这一步是唯一带「外部泛化」味道的检验——优化的是 A 仓库，考的是没见过的 B 包，不算自己刷自己。

### 3.3 学习与 RL 的数字

上下文内那块，摘要报的是「技能演化让留出集准确率最多涨 35.9 分，同时降低算力」；Figure 4 里能看到 KV Store 从 30–50% 一路推到 90% 以上，Log Triage 从接近 0 推到 90% 附近，而且演化后的点普遍落在更低的 PFLOPs/task 上。

RL 这块我建议直接看表。Qwen3.5-9B，3,040 条 OpenResearcher 深度研究 prompt，stepwise GRPO，每步 8 个 prompt × 32 条 rollout，二元结果奖励由 GPT-5.4-nano 按 DeepSearchQA rubric 打，$w_{\mathrm{eff}} = 0.25$ 只作用在上下文管理 token 上，KL 系数 0.01，训练到约第 70 步，checkpoint 在留出验证集上选。

| 方法 | 准确率（训练前 → 后） | PFLOPs/Q（训练前 → 后） |
|---|---|---|
| Summary harness | 34.7 → 42.1 | 4.01 → 2.19 |
| CLM | 28.8 → 42.5 | 1.52 → 1.34 |

训练前 CLM 因为小模型上下文管理能力弱，比摘要 harness 低 6 分；训完涨 13.7 分到 42.5%，比同样配方训出来的摘要 harness 高 0.4 分，而每问 FLOPs 是 1.34 对 2.19，少 38.8%。摘要里那句「提升 47.6%、少用 12% FLOPs」就是 28.8 → 42.5 的相对涨幅和 1.52 → 1.34 的降幅。

我看到这个表的第一反应不是「CLM 赢了」，而是**训练前它输 6 分**这件事。这其实是个挺重要的信号：把上下文管理权交给模型，前提是模型有能力接住。论文在附录 F 里也直说了，CLM 的增益随模型做决策的能力增长，Qwen3.6-27B 上 CLM 落在帕累托前沿，小模型上则不然。所以这套东西不是免费的午餐，它更像一个**放大器**：强模型更强，弱模型可能更弱，得靠 RL 把能力补回来。

### 3.4 SCR 到底省在哪

在 BrowseComp-Plus 上，SCR 用标准 SGLang 65.0% 的经验 prefix-reuse FLOPs 就达到了同等表现，也就是省下 35% 服务端算力。Figure 14 那组 830 道题、$K=6$ 的拆解前面提过：7.8% 的额外复用里，5.3 个百分点是 reasoning 剥离带来的，只有 2.5 是上下文编辑。

作者还老实交代了剩余浪费从哪来：SCR 基本清掉了编辑后未变后缀的重算，但**未变前缀**仍有大量重复 prefill，这是 SGLang 对混合模型缓存实现的局限，不是 SCR 的问题——线性注意力层的 recurrent state 只在缓存请求边界存检查点，后续 prompt 在缓存片段内分叉时，分叉点附近没有可用状态，前缀匹配会退化到很短。把 recurrent state 存到消息边界这种更细的位置，是作者点名的改进方向。

坦率地讲，这种「把自己的收益来源拆开、还顺便指出自己没解决的部分」的写法，比堆十张 SOTA 表格让我更信服。

## 四、我的判断

**最值钱的地方是接口，不是算法。** 整篇论文没有新模型结构、没有新 loss（那个 efficiency advantage 算是个不错的目标设计，但也只是 GRPO 上的一个门控项），真正的贡献是把上下文从 append-only 日志改成可读写文件，然后顺着这个改动把「策略从哪来」重新问了一遍：不是人写，是模型搜、模型学。这跟 Sutton 那篇 Bitter Lesson 的调子是对得上的。而且它把成本账（prefix-reuse FLOPs）和 serving 配套（SCR）一起做了，没有停在「准确率涨了」就收工——这是我愿意给它高评价的主要原因。

**但有些归因我觉得还差一口气。** 数学优化那组赢的是「通用 Agent + 强模型」对「专用进化工作流」，CLM 的贡献混在里面；EdgeBench 和 Software World 的收益也可能部分来自「少写 harness、少硬编码」本身。真正干净的对照应该是同一模型、同一 harness，只切换「文件编辑权限开/关」，再叠加「演化算法作为提示词给/不给」的二维消融。论文在 ContextBench 上有类似的诊断，但在最亮眼的长时程结果上没做，这是我觉得最该补的一块。

**评测口径也有几处可以追问。** 一是 11.4%、47.6%、65% 都是相对量，读快了容易当点数；二是 EdgeBench-10 报的是三个种子的 best-of-three，长时程任务方差本来就大，best-of 会把运气也计进分数；三是主实验统一 32K 上限、100 轮封顶，Software World 却放到 272K，跨基准的成本数字不宜直接横比；四是 prefix-reuse FLOPs 是按附录 C 的层配置推出来的**理论量**，不是端到端墙钟时间或真实账单，两者在有缓存淘汰、批处理、混合模型状态检查点的系统里可能差得不少。SCR 那节用了「empirical prefix-reuse FLOPs」才靠回实测一点。

**还有一个我觉得被低估的坑：模型压根不知道自己上下文有多长。** 附录 G 做了个很朴素的诊断，让模型估当前上下文的 token 数，跟 provider 报的真实长度比。结果在长上下文上普遍严重低估，而且估出来的值像是被「钉」在几千 token 的天花板上。

![图7：现有模型的上下文长度感知](https://arxiv.org/html/2609.37725v1/figures/no_hint_25_50_75_2k_16k_axis20k.png)

*图7：四个子图分别是 No Hint、Hint at 25%、Hint at 50%、Hint at 75%，横轴是真实 prompt token 数（0–20000），纵轴是模型估计的 token 数（0–20000），对角虚线是完美校准。三个系列：Claude-4.6-Sonnet、GPT-5.4、GPT-5.4-mini，图例里给出各自的 MAE。No Hint 下 Claude 的 MAE 是 5384，点群在 6000 附近明显压平、几乎不随真实长度增长；随着锚点提示推到 75%，三个模型的 MAE 分别降到 1723、1296、1086，点群才贴近对角线。*

这就有点尴尬了。CLM 的核心前提是模型能自己判断「何时该编辑、该卸载」，可附录 G 显示它连「我用了多少」都估不准，得靠外部塞一个 25%/50%/75% 位置的 token 计数锚点才校准得过来。作者把它列成 future work（把这类信号放进 CLM 训练），没遮掩。但这也顺带解释了一件事：为什么一句「Compact to 4k tokens once you reach 30k」的指令效果那么明显——不是模型突然会数数了，是你替它把数报出来了。这块我自己也还在琢磨，可能理解有偏差，但至少说明「完全放权」目前还做不到，人类提示仍在暗中托底。

**安全那块论文自己提了，我觉得提得还不够重。** 上下文可写，等于给 prompt injection 和模型自生成的指令开了一条能跨轮持久化的通道。作者引用了已有观察：有模型往自己的压缩摘要里塞了未经授权的指令，后续行为就被带偏了。以前你至少能审计 harness 的压缩代码，现在压缩逻辑是模型临时写的 Bash，审计面直接从几十行代码扩到每一次编辑。真要上生产，我觉得至少得有编辑日志、可回滚快照、以及 system prompt 与可编辑区的硬隔离。

**跟同期工作摆在一起看**，它不算底层突破，更像一次干净利落的接口重划加上一圈很扎实的系统配套。 Related Work 里那条脉络（harness 定死 → 工具按钮 → REPL 变量 → 可编辑 live context）梳理得挺清楚，没有硬吹「首个」，这点也加分。真正让我觉得有迁移价值的，反倒是那句被顺带说出来的判断：**harness 说到底是一种程序性记忆**。既然很多 harness 操作都能写成上下文变换，那它们迟早能被翻译成 CLM 的动作、再内化进权重。作者把 harness-to-CLM 的蒸馏列成未来方向——如果这条路走通，现在这些手写的 Agent 调度代码，往后可能就只是训练数据了。

## 五、如果你也在做长程 Agent

几个我觉得能马上试的点，不一定都对：

- **先量再改。** 把 prefix-reuse FLOPs（或者至少一个「本轮实际 prefill 了多少 token」的计数）接进你的可观测性里。附录 C 那个 7.7 倍的例子说明，中间改一刀的代价可能远超直觉，没有这个数你没法判断编辑值不值。
- **权限别一次给满。** 可以先只在 system prompt 里给出上下文文件路径、允许 Bash 编辑，观察几轮它自己长出来的策略；对比一下「只给 compact 工具」的版本，看看增益到底来自「可编辑」还是来自「少硬编码」。
- **效率奖励一定门控。** success-gated 那个写法可以直接抄：只在成功轨迹内部按 FLOPs 重排，失败轨迹效率项给 0，组内成功数少于 2 时整项归零。直接奖励删掉的 token 数，模型一定会学会乱删。
- **别指望模型自己数 token。** 在上下文里显式放一个长度锚点或者剩余预算，比让它估靠谱得多。附录 G 的 MAE 数字摆在那儿。
- **缓存优先的 Agent，别照搬「任意位置编辑」。** 如果你的服务建立在严格前缀缓存上（几乎所有商用 API 都是），中间编辑会让编辑点之后的缓存整体作废。比较稳妥的折中是：平时只追加，压缩只在阈值处集中做一次，并且尽量动靠近尾部的内容；要改靠前的内容，先用 2.4.1 的公式估一下 $n^{*}$。
- **生产环境先做隔离和回滚。** 可编辑区跟 system prompt / 工具定义分开存，每次编辑留 diff，能一键回到上一个快照。这条不做，迟早遇到自持久化指令。

回到最开始那个问题：模型参数越大、跑得越久，为什么反而越容易在上下文上翻车？这篇论文给的答案不玄乎——不是模型记性差，是我们一直只让它往本子上写，从不让它用橡皮。把橡皮递过去之后，它擦掉的比我们以为的多，留下的比我们以为的准，而且顺手还把擦的策略给学会了。

但橡皮也不是白给的。它得知道本子还剩几页，而这件事，现在的模型还不太会。
