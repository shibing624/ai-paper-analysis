# 把定位器交给修复器打分：不跑测试、不做 RL，还能少读 27.5% 的代码

给 Coding Agent 派活的时候，我踩过一个挺隐蔽的坑。让它先去「找 bug 在哪」，再把找到的文件塞给另一个模型去改，找的那一步我一直拿参考补丁改了哪些文件当标准答案。文件级准确率看着挺漂亮，端到端的解决率就是不动。

盯了几天 trace 才反应过来：一个 bug 的修复，往往依赖那些根本不用改的代码——调用它的地方、父类、一条测试、一段配置文件。你把「改哪儿」教给定位器，它就不会把「该读哪儿」交出来。这两件事长得像，其实不是一回事。

上周翻到 arXiv 上 2611.12164 这篇，标题就叫 *Let the Fixer Decide*，我第一反应是：终于有人把这个别扭的标签定义摆到台面上了。更让我意外的是它的收尾——方法在离线指标上确实成立，端到端却没赢，作者把 13 次评测全摊开，认了。这种写法现在不多见。

---

## 🎯 核心摘要

**痛点**：代码定位器一直用「参考补丁改了哪些文件」当监督信号，可修复器真正需要读的代码 ≠ 需要改的代码；想用结果来学，通常就得上测试执行 + 强化学习，沙箱成本压死人。

**方案**：把定位结果当成隐变量。定位器提多个候选，一个**冻结的修复器**用「已验证补丁的 token 似然」给每个候选打分，归一化成权重，再做一次普通的加权 SFT。一次前向传播就是全部「环境」，不跑测试、不做 RL，本质是 EM 的一轮。

**效果**：在 1,016 个任务上，FGL 选出的定位让修复器第一次编辑落在补丁位置的比例与教师定位持平（43.1% 对 42.4%，p = 0.74），但定位代码量从 2,731 token 降到 1,980，**少读 27.5% 的代码**，上下文溢出少 44%。端到端 78 个开发任务上，一轮 EM 让更多任务走到补丁（53 对 46）、更少任务卡在不存在的文件上（43 对 54），但解出任务数的差异没过显著性检验。

**评价**：底层突破谈不上，思路是 RAG 里「用 reader 监督 retriever」的老套路迁移到代码智能体，新颖度中等；真正值钱的是把整条数据链路打通、把负结果诚实摊开。想看「不靠 RL 也能拿到结果信号」怎么做的人值得细读，想找「解决率暴涨」的可以省时间了。

## 🧠 问题动机：改哪儿，不等于该读哪儿

先说清楚主流做法哪儿别扭。

SWE-bench 这类任务里，流水线派（相对自由探索的 Agent 派）一般拆成两步：先定位相关代码，再写补丁。开源模型做第二步时，定位器的训练标签几乎都取自「参考补丁编辑过的位置」——Agentless 用多级检索层层收窄到文件、类、函数、行，SWE-Fixer 用 BM25 粗召回加一个 7B retriever 精排，训练时喂的就是 gold defective files。做法干净，数据好造，可标签本身是个偷懒的替身。

论文里给了一组挺扎心的对照：一个文件级准确率约 80% 的定位器，端到端只解出 38% 的 issue（引自 BLAgent 那篇）。80 到 38，中间那截去哪了？我的理解是，定位器把「补丁动了哪些文件」背得挺熟，但修复器写补丁时要看的调用链、基类、测试样例，它一份都没给。补丁不碰这些代码，标签里自然也没有。

其实吧，RAG 圈早就把这事想明白了：检索器该学的是「什么对 reader 有用」，不是「标准答案在哪一页」。Lewis 那篇 RAG、Sachan 的端到端 reader-retriever、Atlas、REPLUG，一路下来都是让下游模型的反馈去 shaping 上游检索。顺手掏个旧知识：REPLUG 就是把黑盒 LM 对文档的似然当权重来训检索器，连梯度都不用透传。

麻烦在于，搬到修 bug 这件上，「有用」的判据通常得跑测试。SWE-RL、SoRFT 走的就是这条路：采补丁、丢进沙箱、拿测试结果做 RL。成本一下就上去了——沙箱调度、超时、环境不一致，哪一样都够喝一壶。

于是问题被收得很漂亮：**能不能只用监督微调，让定位器从修复器那儿学到「什么有用」？**

等等，这个 loss 真的会有信息量吗？作者给的答案是把定位当隐变量，用修复器的似然把梯度「借」过来。

## 🏗️ 方法核心：把定位当成隐变量

### 两个 agent，一个冻结基座

结构不复杂，一个冻结的 Gemma 4 E4B 上挂两个 LoRA adapter（论文 Figure 1 是 TikZ 画的架构图，源码包里没有独立插图文件，这里用文字拆开）。

| 角色 | 干什么 | 约束 |
|---|---|---|
| Fixer（主 agent，adapter θ） | 调用定位器这个「工具」，读它给的位置，可以再要更多代码，然后 edit、test、submit | 工具包括 run_command、read_file、edit_file、write_file、get_status、submit_patch 和 localizer |
| Localizer（子 agent，adapter φ） | 在一个全新的容器、全新 session 里探索仓库，返回一份定位列表 | 最多 15 次工具调用，最多 8 个位置，约 6K token 代码；无网络 |

每个位置是四元组：路径、符号、行范围，以及这个位置是「要改」还是「只读」。末尾这一项我挺喜欢——它逼着定位器显式区分「改」和「读」，正好对着开头的那个痛点。

两个 agent 共享同一个 tool-call 预算，单 agent 36 次、双 agent 44 次（多出来的 8 次留给重读 z）。共享预算这点后面会变成一个很现实的瓶颈。

### 隐变量与 EM

任务里有 issue $x$、仓库 $R$、教师补丁 $y^\star$（已经跑过测试通过了）。定位器给 $p_\phi(z \mid x, R)$，修复器给 $p_\theta(y \mid x, \mathrm{ctx}(z))$。「正确的 z」谁也没见过，那就把已验证补丁的边际似然最大化：

$$\log p(y^\star \mid x, R) = \log \sum_z p_\phi(z \mid x, R)\, p_\theta\!\left(y^\star \mid x, \mathrm{ctx}(z)\right)$$

对 $p_\phi$ 求梯度，得到的是在后验下的平均：

$$q(z) \propto p_\phi(z \mid x, R)\, p_\theta\!\left(y^\star \mid x, \mathrm{ctx}(z)\right)$$

于是训练该抬高那些「让补丁变得可能」的定位，压低其余的。这就是 EM：E 步用冻结修复器算权重，M 步做一次加权微调。作者特意点明，整个「环境」只有修复器的一次前向传播。

一句话讲清核心 idea：**别去定义「好的定位」长什么样，让修复器用它写补丁的把握程度来投票**。

### 打分公式里的三个小心机

从定位器自己采 $K$ 个候选，用修复器的分数做 softmax，权重就出来了：

$$s_k = \frac{1}{|y^\star_+|}\sum_{t \in y^\star_+} \log p_\theta\!\left(y^\star_t \mid y^\star_{\lt t}, x, \mathrm{ctx}(z_k)\right) - \lambda_{\mathrm{ctx}}\,\mathrm{tok}(z_k) - \lambda_{\mathrm{req}} |a_k|$$

$$w_k = \mathrm{softmax}_k(s_k / \tau)$$

看着平平无奇，三个设计缺一个都会翻车：

**只算新增行**。$y^\star_+$ 是补丁新增行上的 token。删掉的行和上下文行能从 $\mathrm{ctx}(z)$ 里直接抄，把它们算进去，等于在奖励「把要改的文件亮出来了」这种投机行为。说实话这个坑不踩一次想不到。

**对规模和额外请求收钱**。$\mathrm{tok}(z_k)$ 是定位代码量，$|a_k|$ 是修复器还得再读几次。没有这两项，最优解永远是「把整个仓库给它看」。两项惩罚都取 $0.25\sigma$，$\sigma = 0.068$ nats/token 是任务内分数的中位散布，换算下来约每 1K token 扣 0.0097、每次额外请求扣 0.017。

**按目标 ESS 定温度**。原始分差很容易把权重压成 one-hot，作者改成按任务选 $\tau$，让 ESS（effective sample size）$n^\star$ 落在目标上：$n^\star = 2$ 是 soft EM（约留两个候选），$n^\star = 1$ 是 hard EM（只留最好的）。这个 trick 比拍一个全局温度稳得多。

![图1：一轮 FGL 的三步循环](https://www.mulanai.com/fs/files/1125_1cd2e4c6_fig1_her.png)

*图1（论文 Figure 2）：蓝色的「1 Propose」由 Localizer 给出一叠候选定位，橙色的「2 Judge」由 Fixer 打出高低不等的分数，绿色的「3 Learn」拿这些权重更新 Localizer，底部 repeat 箭头回到起点。整轮里没有测试执行，也没有策略梯度。*

### 加权 SFT 与「两折防记忆」

定位器的损失就是加权负对数似然，外加一个锚在教师定位上：

$$\mathcal{L}_{\mathrm{loc}}(\phi) = -\sum_i \sum_k w_{ik}\log p_\phi(z_{ik} \mid x_i, R_i) - \beta \sum_i \log p_\phi\!\left(z_i^{\mathrm{teacher}} \mid x_i, R_i\right)$$

$\beta = 0.5$，防止一轮下来飘得太远。每个任务留权重最高的 3 个候选（权重 ≥ 0.01）加教师锚，权重和为 1，半学习率热启动。

整轮流程可以压成几行伪代码：

```python
for task in tasks:
    cands = other_fold_localizer.sample(task, K=8, T=0.8)
    cands += [teacher_z, edited_only, viewed_only, teacher_z_minus_one]
    cands = dedup(cands)                       # 平均 7.1 个
    scores = [frozen_fixer.logprob(y_star_new_tokens | ctx(z)) 
              - lam_ctx * size(z) - lam_req * n_requests for z in cands]
    tau = solve_tau(scores, target_ess=n_star)  # soft=2, hard=1
    weights = softmax(scores / tau)
localizer.sft(top3_per_task, weights, anchor=teacher_z, beta=0.5, lr=lr/2)
```

这里藏着全文我觉得最精巧的一处工程判断：**两折**。

把训练任务劈成 A、B 两半，各训一套定位器和修复器，专门用来「提候选 + 打分」，从不部署。原因不是防过拟合那套套话，是防记忆——一个在该任务补丁上训过的修复器，几乎能从任何上下文里把补丁复述出来，于是每个候选都拿高分，权重里一丁点信息都没有；同理，见过该任务的定位器只会重复教师答案，根本没得选。用另一折的模型处理每个任务，「打分的人没见过答案」这件事才成立。

我是真的觉得这条比打分公式本身更可复用。凡是「让模型给自己/同伴的候选打分」的 pipeline（自我奖励、reward model 蒸馏、best-of-N 蒸馏），都得先问一句：评分器见过标准答案吗？

![图2：RL 与 FGL 的训练信号来源对比](https://www.mulanai.com/fs/files/1125_de5e10ef_fig2_rl_.png)

*图2（论文 Figure 3）：虚线上方是 RL 路线——Sample patch → Run tests（红色烧瓶）→ Reward → Policy gradient，右侧红字点出代价是 sandboxes at scale；下方是 FGL——Sample z → Fixer forward → Weights → Weighted SFT，右侧绿字写着 no tests in training。两条路都拿到「结果信号」，只有下面这条不用跑测试。*

顺带一提，完整方法本来还要交替重训修复器。这篇只跑了一轮 EM、只更新定位器，所有双 agent 系统共用同一个 S2b 修复器。这个取舍在后面看结果时会显得要紧。

### 一件让我愣了一下的事：recall cleaning

教师经常「记得」上游的真实修复。它会引用 PR 编号、commit hash（有些是编的），甚至没读代码就先把补丁写了出来。学生在测试时可没这个外挂，拿这种文本去训练，等于教它一本正经地陈述自己从没见过的「事实」。

作者先提示教师别这么干，再跑一遍清洗：在 1,116 条轨迹里找出 3,233 段 recall 文字，**只重写这些推理段落**，工具调用、工具输出、补丁一个字不动。

这个克制我很欣赏。蒸馏轨迹最容易 contaminate 的地方就是「教师脑子里的先验」，多数做法是整条重写或直接丢掉，这里选择做外科手术。

### 一条轨迹，两条记录

教师是单 agent，学生要拆成两个。切法是在**第一次 edit** 处下剪刀：

![图4：一条教师轨迹切成两条训练记录](https://www.mulanai.com/fs/files/1125_294b63e7_fig3_one.png)

*图4（论文 Figure 5）：顶部是 Teacher 的 explore（蓝）→ edit（橙）→ test & submit（绿），红色剪刀虚线切在 explore 与 edit 之间。下方左边的 Localizer 记录框里是 explore → 一份文档 z；右边 Fixer 记录框里是读 z → ask more → edit → test & submit。橙色竖箭头把教师的 edit 原样接到 Fixer 的 edit，蓝色曲线把 z 递过去。*

前面的探索变成定位器记录，以答案 z 结尾；修复器记录则调用定位器、读完 z、按需 ask more，然后**原封不动**接上教师自己的 edit 与 submit。有两条硬规矩：

- 每一次额外请求，都只能用教师**确实看到过**的输出来回答，逐字节校验过，绝不凭空造 tool output；
- 新增的那几句过渡（「我还需要 X，我读过的代码里提到了它，我去读一下」）用固定短句写死。特意不让模型来写，就是怕它顺手把 recall 知识带回来。

还有个容易忽略的细节：轨迹里并不包含模型真正收到的请求文本——工具 schema、system prompt 补充、消息结构都来自 agent 框架。所以他们把每条轨迹用脚本模型在竞赛自己的 agent stack 里重放一遍，保留框架真正发出的 request，最终 token id 在 141 个测试 prompt 上与 vLLM 的渲染完全一致。

看到这段我是有点感慨的。做过 agent 蒸馏的人都知道，token id 对不上能让你白跑一周。

## 🧪 实验结果：数据说话，也打脸

### 离线：省 27.5% 的代码，效果不掉

训练之前，先在 1,016 个训练任务上做了一次 signal test：用另一折的修复器，分别从教师定位（T）和最高权重候选（S）出发实跑，看它编辑的位置和已验证补丁对得上多少（Table 3）。

| 指标 | T | S | Only T | Only S | p |
|---|---:|---:|---:|---:|---:|
| 补丁每个 hunk 都被复现 | 1.0% | 1.3% | 3 | 6 | 0.51 |
| 至少一个 hunk 被复现 | 5.3% | 4.9% | 24 | 20 | 0.65 |
| 第一次编辑落在补丁位置 | 42.4% | 43.1% | 155 | 162 | 0.74 |
| 有任何编辑动作 | 55.3% | 57.0% | 168 | 185 | 0.39 |
| 定位规模（token） | 2,731 | 1,980 | −27.5% | — | — |
| 上下文溢出次数 | 146 | 82 | −44% | — | — |

核心那行是「第一次编辑落在补丁位置」：43.1% 对 42.4%，p = 0.74，两边一样有用。可 S 小了 27.5%，溢出少了 44%。**同样的定位质量，少读四分之一还多的代码**——这才是论文标题里 27.5% 的真正出处，别读成解决率涨了 27.5%。

更值得咂摸的是偏好分布：修复器在 83% 的任务上更愿意要教师之外的候选，把规模惩罚去掉后仍有 86%；最常选的是定位器自己提的方案（43%）和「只给被编辑的函数」（26%）。说到底，教师那份「标准答案」又长又不合口味。

一个诚实的注脚：写出与 $y^\star$ 完全一致的补丁在这个模型尺寸下只占 1%，太稀疏，根本没法拿来做对比指标。

### 端到端：13 次运行全摊开

这里得说一处我自己没完全看懂的地方：Table 4 里 0.7 / 6,656 / 44 那行的 S3r1-soft 写的是 6 个 solved，摘要和正文都按 8 对 6 来讲；而 8 出现在 0.2 / 8,192 那一行。两组采样设置不同，严格说不该混着比。我倾向当成表里一个笔误或者引用了没列进表的一次运行，写在这里供复核，别把 8 vs 6 当成可复现的硬结论。其实就算按 8 算，p = 0.69 也说明不了什么。

三个更该记住的结论：

**单 agent 反而最稳**。S1 三次跑出 8、10、11，在 Base 的设置下是 10 和 11 对 8（p = 0.69 / 0.45）；所有双 agent 系统只落在 4–8。拆成两个 agent 多了协调成本和共享预算的消耗，4B 模型扛不住。

**几个任务的差距就是噪声**。同一个 S1 在不同 run 里从 8 晃到 11；两次温度 0.2 的运行，彼此还各有 2–3 个独解任务。13 次运行加起来，总共只有 18 个不同的任务被解出过。Table 4 里没有任何一组比较达到 p &lt; 0.05。作者把这句直接写进正文，坦率得让人有点不好意思。

**offline 的赢面没变成 solve**。信号测试和 EM 分数测的都是「修复器有没有看对代码」，可 E4B 规模下多数任务死在更后面：超时、循环、写错 edit。更好的定位器修不了这些。

### 4B 到底卡在哪儿（13 次运行的 trace 复盘）

这一段我认为是全篇最有工程价值的部分，四条瓶颈挨个来：

**训练过的 agent 探索三倍，然后没时间了**。Base 中位数只用 11 次工具调用、约 2.5 分钟就交卷，代价是 78 个任务里 61 个交的是跑不过测试的补丁。所有训练过的系统调用中位数涨到 30–44（约三倍），低温下错补丁降到 9–14，可 54–60 个任务撞上预算墙。教师在快速 API 上中位 15 次调用能塞进 8 分钟；学生在 4×L4 上 4 任务并行，约 50 token/秒/任务——它模仿了一个自己跟不上的节奏。

**低温引发复读机**。温度 0.2–0.3 时，每个 run 有 13–35 个任务出现「把一行重复到输出上限」的输出，每次吃掉 130–150 秒，超过四分之一预算。双 agent 的循环次数约是 S1 的两倍（28–35 对 13–18）。升到 0.6–0.7 就掉到 10–16。222 个循环输出里只有 16 个含那几句固定短句，所以锅不在固定文本。

**温度是在拿超时换错补丁**。S1 从 0.2 提到 0.6，超预算从 54–56 降到 24，错补丁却从 9–14 涨到 40，解出数没动。双 agent 同理（超预算 54–60 → 32–38，错补丁 10–14 → 25–31）。一旦时间够了，下一堵墙就是 edit 质量。

**训出来的定位器自带一套假想目录结构**。所有双 agent 系统都在 24–43 个任务里用了不存在的 `/workspace/src/` 路径（fastapi、rich 这类仓库），27–54 个任务里出现 ≥5 次「No such file」；S1 只有 6 和 2–7。哪怕列过目录，定位器还是坚持那个假设。S3 系列比 S2 少（24–35 对 41–43 个任务），正好和离线结论对上——EM 目标确实更接近修复器要的东西。

## 🔬 我的判断

### 值钱的地方

最值钱的不是 27.5% 这个数，是**对标签定义的重新审视**。过去大家默认「补丁改了哪些文件」就是定位监督，作者把它换成「哪些代码让修复器更容易写出通过测试的补丁」，然后用冻结修复器的似然去近似这个「更容易」。相似的思路在 RAG 里躺了好几年（REPLUG 拿黑盒 LM 的文档似然当权重，几乎是同一个套路），搬到代码智能体上，难点不在公式，在于怎么不跑测试就把 outcome 信号弄到手。

第二个值钱点是**负结果的诚实度**。「在 78 个开发任务上，没有任何训练过的系统明显优于未训练模型」——这句话被放在 Introduction 里，不是藏在 Limitations。配上 13 次全表、精确 McNemar、解出集合的波动、「差异就是噪声」的直白结论，比一堆刷点论文可信得多。看到 Table 4 我才意识到，这篇真正想交付的可能是「一套小 agent 的失效诊断」，FGL 反倒成了诊断工具。

第三个是数据链路的洁癖：3,233 段 recall 只重写推理段落、额外请求逐字节校验不造 tool output、141 个 prompt 上对齐 vLLM 的 token id、两折防记忆、附录 E 一口气列了 15 个踩过的坑（prompt 写 12 次调用却留了 15 次记录、622 个任务缺 base-commit 代码、公开 vLLM 不支持 Gemma 4 模型类的 LoRA、DDP 按位置广播 buffer 让 rotary 顺序随 hash seed 漂移、输出上限 16,384 配 32K 窗口导致前 5 个开发任务挂了 4 个……）。这份清单我建议直接抄进自己项目的 checklist。

### 让我皱眉的地方

**似然不等于正确**。修复器给高分，只说明在 teacher forcing 下这段补丁更好预测，不说明补丁对。它会偏爱常见写法、偏爱把相关文件全摆出来（所以才要规模惩罚），对「读起来顺但逻辑错」的候选毫无纠错能力。再说打分器和被训练的定位器共享同一批教师轨迹、同一个基座，是个自举闭环，偏好容易自我强化。作者自己在 Limitations 里也写了：signal test 只测修复器在哪儿编辑，不测补丁过不过。

**实验没真正检验方法的上限**。模型被竞赛钉死在 E4B、8 分钟、int4、4 任务并行，结果瓶颈全落在时间、循环和 edit 质量上。你想想看，「更好的定位器能否提升解决率」这个命题在这套设置里根本没被证伪也没被证实，只验证了「FGL 能改变行为」。要服气，得换更大模型或松预算再跑一遍。作者也明说了后续工作留着。

**78 个任务太小**。13 次运行里总共只见过 18 个被解出的任务，8 vs 6、53 vs 46 全在噪声带里。用 process metric 撑起结论是合理的退路，但读的时候得清楚那是过程指标。

**表格里那个 8 与 6 的对不上**，前面提了，复核时留个心眼。

还有一处我持保留意见：候选是在教师探索**之后**采的，不是定位器自己探索之后（Limitations 里承认了）。这让「从定位器自身分布出候选」的 EM 味道淡了不少，实际更接近「对教师轨迹做一组带权重的改写」。

### 跟同期工作摆在一起

| 路线 | 定位监督从哪来 | 要不要跑测试 | 代表 |
|---|---|---|---|
| 流水线式定位 | 参考补丁编辑过的文件（静态标签） | 训练时不用 | Agentless、SWE-Fixer、Co-PatcheR |
| 结果驱动的 RL | 补丁在沙箱里的测试结果 | 每个样本都要 | SWE-RL、SoRFT |
| RAG 式 reader 监督 | 下游 reader 对答案/文档的似然 | 不用 | RAG、Atlas、REPLUG |
| FGL（2611.12164） | 冻结修复器对已验证补丁的似然 | 训练时不用（仅数据验证阶段用） | 这篇 |

（Agentless、SWE-Fixer 的做法依据各自论文与公开解读：Agentless 把定位拆成文件→类/函数→行的多级检索；SWE-Fixer 用 BM25 召回加 7B retriever 精排、训练喂 gold defective files。这些数字与结论不属于 2611.12164，别混。）

摆在这个坐标系里，FGL 的位置挺清楚：**卡在「静态标签」和「测试 RL」中间的一次迁移**。说底层突破谈不上——EM + reader 似然当权重都是现成的；说工程整合也不太公平，两折防记忆、只算新增行、ESS 定温度、整条轨迹重放链路，都是针对代码 agent 的具体麻烦长出来的解法。我给它的定位是「一次扎实的方法迁移 + 一份高质量的负结果报告」，比多数刷点论文更值得读，但别指望它改写路线图。

## 💡 工程启发

如果你也在做检索器、定位器、路由器这类**上游模块**的训练，有几条可以直接搬：

**别再用结果文件的静态标签**。上游模块的服务对象是下游模型，那就用下游模型的可用性当软标签。加权 SFT 就能拿到 EM 的一轮效果，成本比沙箱 + RL 低一个量级。这篇给的公式可以直接套：下游模型对目标序列的 token 平均 log-prob，减去输入规模与额外交互的成本项。

**打分前先隔离记忆**。评分器见过该样本的答案，权重就会塌成常数。两折（或留出集）不是可选优化，是这套方法成立的前提。

**给候选加成本项，用 ESS 定温度**。「全给看」永远是裸似然的最优解；固定 τ 又容易 one-hot，按任务把 ESS 解到目标值更稳。

**蒸馏 agent 轨迹时把节奏折算到学生硬件**。教师在快速 API 上 15 次调用、8 分钟搞定的事，学生在 4×L4 上要跑三倍时间。按学生预期时间过滤或截短轨迹，别照抄教师时钟。

**小评测务必多次 + 配对检验**。78 个任务上同一个模型能晃 3 个 solved，只报一个 rate 会骗到自己。报解出集合、报 McNemar，比报百分比诚实。

**给上下文窗口留余量**。32K 窗口配 16,384 输出上限，等于 prompt 超过 16K 直接被拒，作者第一批 5 个任务就这么挂了 4 个。输出上限压到 6–8K 是更稳的选择。

还有一条偏玄但我觉得最实用的：**把失效诊断当成交付物**。这篇里「时间、循环、edit 质量比定位更卡脖子」的结论，对任何做小尺寸 coding agent 的团队都比一个新 loss 有用。

## ⚠️ 局限与还没解决的问题

只训了一个尺寸（E4B），只跑了一轮 EM 且只更新定位器，修复器从头到尾没动；每个设置每个系统只跑一次，两组 run 采样参数不同只能组内比；4 任务并行比正式 scorer 慢，超时数偏悲观；signal test 测编辑位置而非补丁是否通过；候选采样发生在教师探索之后。

更大模型、多轮 EM、交替更新修复器，作者留给续作了。

有个更根上的问题我想追问一句：如果评分信号来自一个和定位器同源、同数据、还冻结着的修复器，那这轮 EM 到底是在逼近「真实的补丁似然」，还是只是在把两个模块往同一个偏好上拧？要回答这个，大概得换一个独立训练的、甚至不同家族的修复器来打分看看权重会不会变。这块我也还在摸索，可能理解有偏差，但值得试。

不过话说回来，一篇论文敢把自己的上限写进 Introduction，还把 15 个开发期的坑全列进附录——光这份坦率，就够我给它留个位置了。

如果你也在训小尺寸 coding agent，或者正被「上游模块该拿什么当标签」折磨，2611.12164 这套两折打分 + 加权 SFT 的链路，真值得照着跑一遍。别指望解决率，指望的是把「该读什么」这件事从静态标签里解放出来。
