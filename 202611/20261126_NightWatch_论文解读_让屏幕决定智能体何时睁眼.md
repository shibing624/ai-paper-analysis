# 大模型还在慢悠悠地想，屏幕早就变了：给电脑智能体配个 0.8B 守夜人

## 🎯 核心摘要

你让 AI 帮你装个浏览器扩展，它截了张图，开始"思考"下一步点哪。六七秒过去，页面早加载完了、终端命令都返回了，它却还在按那张旧截图推演。这就是 computer-use agent 最容易被忽略的坑——不是看不清，而是看得太旧。这篇论文的解法挺反直觉：不去动那个又大又慢的主模型，而是外挂一个 0.8B 的小模型当"守夜人"，盯着屏幕流，专门决定主模型**什么时候该睁眼**、刚才那步还算不算数。OSWorld 上非推理时间砍掉 33%、浪费时间砍掉 53%，成功率没掉；动态网页 DynaCU-Bench 从 39.5% 抬到 44.2%。说到底这不是更好的视觉算法，是把**感知时机**扶成了和**感知内容**平起平坐的设计维度。我觉得这才是它最值钱的地方：一个纯粹的架构与调度层贡献，工程回滚成本几乎为零。

## 从一个真会让人抓狂的瞬间讲起

不知道你有没有亲手调过"操作电脑的智能体"：给它一句人话，比如"把这个表格按销售额排个序再导出 PDF"，它就自己截图、看屏幕、吐出一个 `click(x, y)`，再截图、再吐一个动作，一路循环。

这类系统有个特别隐蔽的别扭劲儿：**它每一步之间都在睡觉**。

标准循环长这样——截图，交给视觉语言模型（VLM）推理几秒，执行动作，`sleep` 一段写死的固定时间，再截图。论文翻了 OSWorld 官方 agent 脚本，动作后的等待从 0 秒到 10 秒都有，同一个基准差了二十倍。等短了拍到半渲染的过渡态，等长了那些一闪而过的通知早消失了，白白干等。

更要命的是"看"和"做"之间那道缝。论文引了几组实测：OSWorld 上从观察到执行平均隔了 6.51 秒，Android 上是 4.18 到 15.43 秒。这几秒里屏幕可没闲着——弹窗会跳出来、按钮会挪位置、色块会旋转、 loading 会结束。有工作测过，一个弹窗恰好落在这道缝里，能让任务成功率掉 47%。而基于旧截图做出的动作落到新屏幕上，智能体基本不会自己爬回来。

我的第一反应是：这不就是"模型看错了"吗，换更强的 VLM 不就行了？

问题恰恰在这儿。换再大的模型，它仍然是"一轮一轮地看"，两张截图之间依然瞎。瓶颈不在**看得多准**，在**什么时候看**。说实话，这个区分以前在 CUA 圈子里被含糊过去了，效率账本只记两笔：调了几次模型、走了多少步。那些 `sleep` 掉、拍早了、动作过期了的时间，几乎没人单独记账。

这篇论文（arXiv:2611.28947，*Don't Sleep, Keep Watch: Proactive Perception for Computer-Use Agents*）干的第一件狠事，就是把这笔糊涂账摊开，给了一个几乎不侵入现有系统的解法。

## 🤔 问题动机：三种"看屏幕"的姿势，差的不是清晰度

![图1：三种观察与执行控制范式对比](https://arxiv.org/html/2611.28947v1/teaser.png)

*图 1：论文 Figure 1。(a) 固定调度——弹窗出现后推理照旧继续，页面就绪后固定等待也照旧继续；(b) 被动观察——缓存的帧只喂给"下一次"观察，动作分派前查一次；(c) 主动感知——0.8B 的 System-1 watcher 加阈值规则，主动打断推理、作废动作、提前结束等待。右侧 (d) 是 OSWorld-Verified 的结果速览：wasted time 16.3%→7.7%，非推理时间 197s→133s，成功率 66.3%→68.0%。*

它把现有做法归成三类，这个分类本身就是贡献的一半：

| 范式 | 谁决定"什么时候看" | 代表做法 | 能拦住过期的推理吗 |
|---|---|---|---|
| 固定调度（Time-triggered） | 智能体自己的时钟 | Vanilla，动作后 `sleep` 固定时长 | 不能，两次截图之间全盲 |
| 被动观察（Passive watching） | 还是时钟，只是多存了些帧 | AOI（3Hz 采帧附到下次观察）、PUSV（分派前查一次目标） | 只能事后补看或拒一次动作，不能打断进行中的推理 |
| 主动感知（Proactive） | 屏幕本身 | NightWatch | 能，随时打断、作废、唤醒 |

AOI 和 PUSV 是两个关键 baseline，得说清它们"被动"在哪。AOI 按 3Hz 在两步之间多采几帧，用像素差和 CLIP 挑出关键帧，配一段视觉叙述挂到**下一次预定观察**上——是下一次，不是现在。PUSV 在每次点击即将分派前对着目标区域核对一次，发现不对就让智能体重新决策。两个都在"看"，却仍被固定节拍牵着走：屏幕没资格喊停，也没资格插队。

论文一句话戳得很准：它们没有一个让屏幕决定**何时**被看见，也没有一个能停掉"屏幕已经让它作废"的那段推理。

顺着上面的再聊聊。"让事件而不是时钟来触发采样"这套思路，控制论里早有名字——event-triggered control（Åström & Bernhardsson 2002、Tabuada 2007），机器人里"快检查 + 慢规划"的双层结构、异步 LLM agent 里用事件打断生成，都是近亲。说到这个，流式视频模型决定"哪一帧该开口"也是同一个味道，只不过它把这道门学进了模型内部。NightWatch 的取舍很明确：**门放在 harness 层，不改模型**。这也是我读的时候最欣赏的一点。

那为什么非得"主动"？论文给了三个挺实在的理由，我按自己的话捋一遍：

判断必须赶得上。打断要在动作分派之前落地，晚一步就没意义，所以监控得足够便宜、足够快，贵模型根本跑不起这个频率。还得分清"跟我有关的变化"和"无关的动画"：时钟在走、光标在闪、轮播图在转，这些不该触发打断；一个正好盖住目标按钮的弹窗就该触发。误报的代价很实在，一次没必要的打断会把快想完的推理整个丢掉；反过来，唤醒早了又给智能体看一张还没就绪的屏。两头都不能犯。这条约束挺紧，后面训练那块会看到作者怎么绕过去。

## 🏗️ 方法核心：一个常驻的 System-1，一个按需的 System-2

![图2：NightWatch 方法总览](https://www.mulanai.com/fs/files/1126_9a06f62b_NightWat.jpg)

*图 2：论文 Figure 2，整篇的骨架。左：屏幕按 10Hz 帧流进来，经像素门筛出变化，NightWatch-0.8B 读一份由"上次观察帧 / 半秒前 / 当前帧 / 变化区域裁块 + 待执行动作"拼成的视觉上下文，对一整套固定问题一次性给出概率。中：固定阈值把概率转成三类干预——Interrupt（推理中出现新事件就取消生成）、Void（分派前目标没了就丢弃动作）、Wake（屏幕一稳定就唤醒，取代固定 sleep）。右：离线训练，决策点采样 + teacher/gold 标签 + hindsight settledness + 保校准的目标函数。底部一行小字很关键：训练离线、部署在线、agent 全程未改。*

一句话讲清核心 idea：**在智能体和环境之间塞一个便宜的常驻监控，它不决定做什么，只决定什么时候看，以及刚才那段还作不作数**。

用 Kahneman 那套 System-1 / System-2 的话说，原来的大 VLM 是慢吞吞但会推理的 System-2，NightWatch-0.8B 是快而直觉的 System-1。区别是这里的 System-1 完全不碰决策内容——它不挑工具、不选动作、不写提示词，**看门，不做主**。这个分工我觉得是整篇最干净的设计决定：小模型读状态是靠谱的，让它做决策就不靠谱了，所以干脆把决策逻辑写成确定性的代码规则，模型只负责把屏幕"读"成概率。

### 先把"浪费"写成公式

作者没停在口号上，先在 harness 层把问题形式化了。设 $s(t)$ 是 $t$ 时刻的屏幕，智能体在第 $k$ 步于 $t_k$ 观察到 $o_k = s(t_k)$，推理完在 $t_k^{\mathrm{act}}$ 分派动作 $a_k$。屏幕在推理区间 $[t_k, t_k^{\mathrm{act}})$ 和等待区间 $[t_k^{\mathrm{act}}, t_{k+1})$ 里都会自己变。

固定调度就是 $t_{k+1} = t_k^{\mathrm{act}} + t_{\mathrm{fix}}$，硬等。它会招来两类时间损失：动作基于 $o_k$ 却作用在 $s(t_k^{\mathrm{act}})$ 上，屏幕把它作废了（stale action）；观察时刻 $t_{k+1} \lt t_k^{\mathrm{rdy}}$ 拍到了过渡态（premature），或者 $t_{k+1} \gt t_k^{\mathrm{rdy}}$ 让智能体干等。于是每一步浪费的时间写成：

$$W_k = (t_{k+1} - t_k^{\mathrm{rdy}})^+ + c\Big(\mathbf{1}\big[t_{k+1}\lt t_k^{\mathrm{rdy}}\big] + \mathbf{1}\big[v(a_k,o_k)\gt v(a_k,s(t_k^{\mathrm{act}}))\big]\Big)$$

第一项是纯空闲等待，第二项给"拍早了"和"动作过期了"各记一笔固定代价 $c$，$v(a, s)$ 是动作在某张屏上是否还成立。整个优化目标也就顺理成章：在**成功率不低于固定调度**的前提下，最小化 $ \mathbb{E}[\sum_k W_k] $。

等等，这个约束别一带而过。它是 $\min_{\phi}\ \mathbb{E}[\sum_k W_k]\ \text{s.t.}\ \mathrm{Succ}(\pi,\phi)\geq \mathrm{Succ}(\pi,\phi_{\mathrm{fix}})$——**省时间不能拿成功率换**。这一句直接决定了后面所有实验该怎么读：OSWorld 上"成功率持平"不是没涨够，是任务书里就写明了不许掉。作者也坦白说这个式子只是把权衡摆出来，并没真的拿它去端到端优化，$\phi$ 是靠一个学出来的 watcher 加固定阈值实现的。

还有个细节挺见功力：$t_k^{\mathrm{rdy}}$（就绪时刻）和 $v$（有效性）在决策当下都读不到，只能从不断展开的帧流里估。而且**就绪是语义的**，不是像素静止——时钟一直在走、光标一直在闪，屏幕永远不会"完全不动"；反过来，页面可能加载中途卡一下，看着安静其实没好。这个"**静下来不等于就绪**"的判断，是后面训练部分的题眼。

### 流式监控：一次编码，回答一整摞问题

NightWatch-0.8B 是个 System-1 decision model，特点是不生成推理文本，而是对一堆**带类型的选择题**从同一份编码里一次性给答案分布。某个时刻 $t$ 的上下文是：

$$x_t = \big(\underbrace{o_k,\ s(t-0.5\,\mathrm{s}),\ s(t),\ s(t)|_{B_t}}_{\text{视觉上下文}},\ \underbrace{\bar{a}_t}_{\text{待执行动作}}\big)$$

也就是"智能体正在推理的那张旧截图 + 半秒前的帧 + 当前帧 + 变化区域的裁块"，外加待执行动作的文字（点击坐标、输入的文本之类）。关键是 $p_\theta(\cdot\mid x_t,q) = R_\theta(E_\theta(u_t), \bar{a}_t, q)$：**视觉编码只做一次**，之后对当前阶段的所有问题 $q \in \mathcal{Q}_t$ 复用同一份编码，只是换个 readout。这是它能 10Hz 常驻还不烧钱的根本原因——成本按"请求"付，不按"问题"付。

问题库 $\mathcal{Q}$ 是写死一次的，16 个问题分四组，全是跨应用通用的、不点名任何任务或软件：

| 组别 | 问的是什么 | 举例 |
|---|---|---|
| A 变化与稳定 | 屏幕还在不在变 | `still_changing`（还在动画/滚动/绘制吗）、`loading`（有 spinner / 进度条 / Loading 字样吗）、`settled` |
| B 让计划整体作废的事件 | 有没有新东西盖上来 | `dialog`（新弹窗/权限请求）、`error`（报错）、`page_changed`（换了页面/应用）、`toast`（短暂通知）、`focus_lost` |
| C 待执行动作还作数吗 | 目标还在不在原位 | `target_present`、`target_occluded`（红圈处被新浮层盖住了吗）、`target_changed`、`target_disabled` |
| D 动作效果 | 上一步有没有可见结果 | 有没有出现预期/意外的结果 |

其中 `target_present` 是唯一一个回答"no"才触发的问题，其他都是"yes"触发。这套问题在三个检查点分别问：推理中（R）、分派前（D）、执行后（E）。分派前会把"上次观察里目标区域的裁块"和"当前屏同一区域的裁块"并排送进去，让它判断元素是不是还在原位置——Figure 5 那个色块旋转的案例就是这么被抓住的。

流式这块还有个便宜的门：像素级 $\chi(t)=1$ 只在当前帧和上一帧有明显差异时才发起一次请求，静屏则用 1Hz 的周期探针盯着（防止"加载卡住"这种静止场景被漏掉）。等待阶段只问 `settled` 和 `loading` 两个问题，跟全套检查分开跑，目的就是别让等待本身变长。

### 主动触发：三类干预，只有窗口和阈值不同

概率出来之后，决策逻辑全是确定性规则，透明得有点朴素。设 $g(S,t) = \max_{q\in S} p_q(t)$ 是某组问题里最强的那个响应，每个干预 $d \in \{I, V, W\}$ 守着自己的时间窗 $\mathcal{W}_d$，在触发条件第一次成立的时刻 $t_d^\star$ 开火：

| 干预 | 时间窗 | 触发条件（阈值） | 效果 |
|---|---|---|---|
| **Interrupt** 打断 | 推理中 $[t_k, t_k^{\mathrm{act}})$ | $g(S_{\mathrm{evt}},t)\geq \tau_I = 0.5$（新弹窗/报错/换页） | 取消正在生成的 token，本步从当前屏 $s(t_I^\star)$ 重新推理 |
| **Void** 作废 | 分派前 $\{t_k^{\mathrm{act}}\}$ | $g(S_{\mathrm{val}},t)\geq \tau_V = 0.8$（目标没了/被遮挡/新弹窗） | 丢弃 $a_k$，不落到过期屏幕上，本步重来 |
| **Wake** 唤醒 | 执行后 $[t_k^{\mathrm{act}}, \infty)$ | $\eta(t)\geq t_{\min}$ 且 $p_{\mathrm{settled}}\geq \tau_W=0.99$ 且 $p_{\mathrm{loading}}\lt \tau_L=0.5$ | 用在线估的就绪时刻替代固定 sleep，立刻取下一张观察 |

$\eta(t)$ 是距离上次显著变化过去的安静时长（若动作压根没产生可见变化，就从分派时刻算起，这样"无可见效果"的动作不必傻等超时）。把 $T_I=T_V=0$、$t_W^\star = t_k^{\mathrm{act}} + t_{\mathrm{fix}}$，就退化回固定调度——这个"特例"写得挺漂亮，说明整套框架是对原循环的超集，不是另起炉灶。

其他超参也一次性固定、跨应用跨基准共用：$t_{\min}=0.3$ 秒，benign 变化判定 0.6，像素静止兜底 0.6 秒，无可见效果兜底 1.0 秒，单步最大等待 10 秒，每步最多 2 次打断 / 2 次作废，帧采样 10Hz。看到这些数我有点感慨——**没有一个阈值是按任务或按步生成的**，全靠调一次就锁死。这既是它"即插即用"的底气，也是我后面要吐槽的泛化隐忧。

按论文机制整理成一段示意伪代码，工程读者可能对得上号：

```python
# 示意伪代码，非原文代码；watch 与 agent 并行
while not done:
    obs = screen.now()                 # agent 观察到的那张
    gen = agent.start_reasoning(obs)   # 慢，几秒级
    while gen.running:                 # —— Interrupt 窗口 ——
        if watcher.ask("dialog/error/page_changed") >= 0.5:
            gen.cancel(); obs = screen.now(); restart_step()
    action = gen.result
    if watcher.ask("target_present/occluded/dialog") >= 0.8:   # Void 窗口
        discard(action); restart_step()
    dispatch(action)
    while not (quiet_for(0.3) and watcher.ask("settled") >= 0.99
               and watcher.ask("loading") < 0.5):               # Wake 窗口
        stream_watch(10Hz)            # 一稳定就取下一张观察
```

注意全程没有一行改 agent 的 prompt、权重或动作空间。打断时是"取消生成并从 agent 历史里抹掉，把当前截图当成一次普通观察喂回去"，所以智能体永远看不到半截的、被丢弃的回答；唤醒只改**下一次观察的时间**；在 DynaCU 上作废动作会借 AOI 自带的 `[ACTION ERROR]` 反馈通道告诉 agent 重来。这种"只动时间、不动内容"的克制，是它回滚成本低的直接原因。

### 训练 watcher：最漂亮的那一刀在 hindsight 上

说实话，读到 3.4 节我才真正被打动。

通用 decision model 读静态状态是靠谱的，读**时序判断**就弱了——尤其"屏幕刚停下来的这一下，是不是真的完了"。作者的解法不是堆数据，是换标签定义。

决策点从真实轨迹里采：跑未改动的 agent，录下帧流，在推理中、分派前、执行后的若干延迟处各取一批时刻，按推理时一模一样的方式拼上下文。标签揉三样东西：一个更大的 teacher decision model 在同一请求上的分布 $y_i^{\mathrm{T}}$；录制流能直接判定的 gold 标签 $y_i^{\mathrm{G}}$（比如推理期间啥都没变就是"无事件"、分派前目标区域没动就是"目标还在"）；两者一致时 $y_i = \alpha y_i^{\mathrm{G}} + (1-\alpha) y_i^{\mathrm{T}}$，冲突时"关于像素的事实"由 gold 覆盖 teacher。罕见事件（弹窗、toast、报错）再用程序化生成的合成界面补精确 ground truth。

而 `settled` 的 gold 标签，是**用未来定义的**：

$$y_i^{\mathrm{G}} = \mathbf{1}\big[\chi(t')=0,\ \forall t'\in(t_i,\, t_i+h]\big]$$

也就是"从当前这一刻往后的 $h$ 窗口里，帧流都没有再变过，才算真的就绪了"。你想想看，如果按"已经安静了多久"来打标签，那每一帧刚停下来的都会被标成"没就绪"，模型永远学不会比像素静止更早唤醒——天生成了一个天花板。用 hindsight（事后回看）当监督，推理时却只看当下，等于把"预测未来会不会再变"这个能力压进了 0.8B 里。这个设计真的挺精巧。

目标函数是交叉熵加一个 Brier 项 $\mathcal{L}(\theta) = \mathbb{E}_{i\sim\mathcal{D}}[\mathrm{CE}(y_i,p_{\theta,i}) + \lambda\|y_i-p_{\theta,i}\|_2^2]$。加 $\lambda\|y-p\|^2$ 不是为了涨点，是为了**保住概率校准**——因为前面那些阈值全靠概率的绝对值卡，$p_{\mathrm{settled}}\geq 0.99$ 这种严阈值要是模型过度自信或欠自信，规则立刻失灵。作者还在一个留出集上拟合了最终温度。

实现上：从 d3-lite（一个 0.8B 的 System-1 decision model）初始化，用 LoRA 在 360 个自动生成的 OSWorld 任务上微调，然后**冻结**、同一套阈值直接上两个基准。跑在单张 NVIDIA L40S 上，10Hz 帧流，一次 settledness 检查约 0.3 秒。训练任务刻意和评测隔离：每个任务从全新启动的应用开始，指令跟任何 OSWorld 指令字符串相似度 ≥0.6 就丢弃，不用任何基准任务、文件、配置或轨迹。这一点对"是不是刷榜"的质疑挺重要，我等下会回来验。

## 💡 我的判断：它值钱在哪，又在哪儿有点虚

先给结论：**这是一篇扎实的架构 / 调度层工作，不是视觉感知算法的进步**。从"更好的界面理解模型"角度读它会读偏。它真正挪动的坐标，是把"什么时候感知"从被 `sleep` 默认掉的工程细节，提升成可以建模、可以优化、可以单独评测的一等设计维度。原文收尾那句 *the timing of perception is as critical as its content*，就是这个意思——**感知时机和感知内容同等重要**。

我觉得最值钱的三处，按重要性排：

**第一，wall-clock 记账这套方法论**。把空闲等待、过早观察、陈旧动作分开量化，写成 $W_k$，再显式加一条"成功率不许掉"的约束。以前调 CUA 效率只盯模型调用次数和步数，一大块时间在 `sleep` 里被无视了。哪怕不采用它的 watcher，照着做一遍这个 ledger，就够把自家 agent 的耗时剖面看清楚。

**第二，"看门不做主"的权力划分**。小模型只读状态成概率，确定性代码做决策，阈值全固定。好处是透明、可调、可回滚，出问题时你能指着某条规则说"是 $\tau_V$ 太松了"，而不是去猜一个端到端黑箱。而且 agent 全程未改，插上去、拔下来都不动业务。对要落地的团队，这个属性比涨几个点重要得多。

**第三，hindsight settledness 这个标签技巧**。用"未来窗口里没再变"当就绪的监督，推理只看当下，把预测能力压进小模型。这思路能迁移到一大类"等待型判定"——等下载完、等编译结束、等渲染稳定、等机器人动作收敛，凡是"安静不等于完成"的地方都用得上。

聊完好的，说几个我皱眉的地方。

**D3-27B 那个对比，公平性我存疑**。表里让一个 27B 的官方决策模型用**同一套问题库、同一套阈值**去跑，可 NightWatch-0.8B 是拿 360 个任务 LoRA 微调过、还拟合了温度的。让一个没针对性训练的大模型裸奔，然后说"0.8B 比大 30 倍的还强"，这个 framing 有点取巧。论文自己在 Table 3 里也放了没微调的 d3-lite（35.0s vs 28.8s），说明微调确实有贡献——那更该把"微调 vs 不微调"和"0.8B vs 27B"两件事拆开讲。说实话这块我也不是特别确定作者的意图，可能我的理解有偏差，但"30× 更大却更差"这句话被摘要和不少二手解读反复引用，容易被读成"小模型天生碾压大模型"，而实际上赢的是**专用化 + 低延迟**，跟参数量没那么直接。

**统计口径得看清**。DynaCU-Bench 只有 49 个任务、每个跑三次，标准差普遍 ±4~5，那个 4.7 点的提升落在噪声边缘。OSWorld 100 任务上"成功率持平"读着稳，但它是个准静态基准，官方等待本来就宽裕，本来就没什么成功率可涨——检验动态价值全靠 DynaCU 那 49 个，覆盖面不算厚。

**能力上限没动，作者自己也认**。Limitations 里写得很诚实：OSWorld 上有 11 个任务 Vanilla 和 NightWatch 三次全挂，绝大多数是 agent 自己给了个错误结果就结束了——NightWatch 改的是"何时看"，不是"能做什么"。更关键的一条：**interrupt 和 void 只是让推理在当前屏上重来，并不让它变快**，所以遇到"界面变得比一次生成还快"的场景（DynaCU 里最快的 toast 和游戏），动作分派时没有任何观察还算数，这套机制就无解了。作者给的适用边界很明确——适合"界面变化慢于 agent 推理"的接口，更快的得换更快的 agent。这条自我设限反而让我更信这篇，没硬吹成万能药。

**成本账有口径没算全**。"API 成本在 Vanilla 3% 以内"只算了 agent 的调用费。可 watcher 是常驻的：单张 L40S、10Hz 截屏流、每次检查约 0.3 秒，这些 GPU 时延和截屏开销没进 Table 2 那张账单。对本地部署也许无所谓，对云端按卡计费就不是零成本了。这不是硬伤，但读"零额外成本"时要补上这一笔。

**泛化的隐忧**。16 个问题、四个阈值、跨应用跨基准全固定，作者把它当"通用"的证据；我倒觉得这更像"恰好把这两类 benchmark 的失效模式覆盖住了"。合成界面能补弹窗、toast、报错这些罕见事件，可真实长尾里的权限弹窗、多显示器、深色模式、动画密集的 Web 应用会不会让 $\tau_I=0.5$ 变成误报机器，论文没给跨环境验证。那个"benign 变化判定 0.6"的旋钮，换个 UI 风格大概率要重调——而"重调"恰恰会削弱"即插即用"的成色。

放到同期工作里看，它不算凭空冒出来的底层突破。event-triggered control、active perception、机器人快慢双层、流式视频响应门、异步 LLM 事件打断，都是成熟亲戚；直接对手 AOI / PUSV 也已经把"步间看屏幕"做了一半。NightWatch 的增量是**把这三件事拧成一个 harness 层闭环**：能打断进行中的推理（AOI 只能补看、PUSV 只能查一次）、用语义判据替代像素静止（Table 10 那 37%）、并且完全不碰 agent。别被"first framework to bring proactive perception to CUAs"这个"first"带跑——它first的是这个具体组合，不是这个思想。

给工程落地的几句实在话：agent 卡在"慢"，先做一遍耗时剖面，把 `sleep`、拍早了、动作过期分开记账，别急着换更大模型；感知调度放 harness 层，别写进 prompt；阈值当旋钮一次调好、别 per-step 生成，否则校准一乱规则全废；上线前务必量一下 watcher 误触发的代价——一次没必要的 interrupt 会丢掉整段快想完的推理，这个成本被 `c` 一笔带过，落到真实流量未必小。

还有个更根本的问题没解决（好吧，说到底还是这个）：只要推理还是一轮一轮的、只要生成一个动作还要几秒，"观察—执行缝隙"就只能被**监控和打断**缓解，不能消失。NightWatch 是给一个慢系统配了个机灵的哨兵，不是让系统变快。要真把缝隙抹平，得等推理本身流式化、或者动作在生成途中就能被环境反馈修正——那会是另一篇论文了。

---

坦率讲，这类"不碰模型、只动调度"的工作特别容易被低估：没有新 loss、没有新架构、没有刷榜大数字。可你要真维护过一条跑在真实桌面上的 agent 链路，就知道"少睡三成、成功率还不掉"有多实用。它把一个被所有人当作背景噪声的变量，抬到了台面上。

如果你也在做长时程智能体，或者正被"它怎么老是慢半拍"折磨，这个思路值得花一晚上试试。
