# G-CAST：Agent 持续进化，难的不是重训而是准入门

一个采购 Agent 上线时只会调用 4 个工具，几个月后，平台给它加上了外部趋势查询、多模态理解、技能流程、沙箱和文件导出，工具总数涨到 23 个。功能看起来越来越强，模型却可能连旧活都干不稳：它不知道该何时调用新技能，也可能编出一个检索结果里根本不存在的商品链接。

更麻烦的是，旧奖励函数还会给这种回答高分。

这时候再跑一轮训练并不够。训练数据可能根本没覆盖新能力，奖励可能已经在鼓励错误行为，而新 checkpoint 即便学会了新流程，也可能把老用户依赖的功能忘掉。G-CAST 切的就是这个真实又不那么“算法性感”的缝隙：**模型、数据和奖励会一起过期，持续训练必须带着治理机制一起做。**

> **核心摘要**：G-CAST 把每日生产查询转成 8 次 rollout，按奖励结果路由到 SFT、RL 或回归监控，再用 token 熵安排池内训练优先级；发现奖励失配时，先暂停训练并修复奖励，候选 checkpoint 必须通过新旧任务的累计评测才能上线。第四阶段它的累计奖励为 0.8078，高于 AutoTrainess 的 0.7911，旧任务奖励从 0.8712 升到 0.8833，而 baseline 从 0.8907 降到 0.8739。我的判断是，这不是一个新 RL 算法，而是一套颇有价值的生产治理方案；真实部署是亮点，单一业务与私有数据则限制了结论外推。

## 工具变多了，Agent 为什么反而更不会干活？

我读到这部分时挺有共鸣。很多 Agent 项目默认一件事：harness 加了工具、记忆和技能，模型自然会用起来。可真到线上，新增能力往往只是“可调用”，离“会正确调用”还差得很远。

G-CAST 把模型当前可见的信息、可执行的动作、必须遵守的交互协议统称为 **capability contract，能力契约**。契约一变，三处会同时错位：

| 错位 | 线上表现 | 单纯重训为什么不够 |
|---|---|---|
| 模型错位 | 不知道何时用新工具，调用格式错误，或不会把工具结果整合进答案 | 新能力已经暴露，但模型仍按旧策略行动 |
| 数据错位 | 旧轨迹能教老功能，却几乎没有新技能、新流程的执行证据 | 直接回放旧数据，学不到新契约 |
| 奖励错位 | 没调用必需工具仍得高分，遵守新流程反而被旧规则扣分 | 训练目标本身已经错了，越优化越偏 |

这个问题在元采里很具体。通用助手要调度 20 多个内置工具，快速搜索走更短的商品与供应商检索路径，知识辅助模式还要结合业务 playbook、上传文档和历史交互。每次功能扩张，都重新规定了模型“应该知道什么、可以做什么、必须怎样做”。

论文把四个时期的生产需求冻成了四份快照：

| 需求时期 | 工具数 | 新增能力要求 |
|---|---:|---|
| Period 1 | 4 | 基础检索与详情查询 |
| Period 2 | 7 | 外部证据与趋势查询 |
| Period 3 | 17 | 技能、多模态与询盘工作流 |
| Period 4 | 23 | 沙箱、文件、导出与完整工作流 |

注意，这些 Period 不是训练算法的四个阶段名称，而是四个不同时期的需求与契约快照。每个快照独立保留生产查询和评测切片，作者借此模拟 Agent 上线后不断面对的新环境。

### 不更新模型，会发生什么？

![固定 checkpoint 在能力契约扩张后的性能退化](https://arxiv.org/html/2611.17814v1/Figures/original_model_degradation_hybrid_base.png)

*图 2：固定 checkpoint 面对四个需求时期时的 base reward。黑色虚线是累计均值，彩色曲线分别对应 CX1 至 CX4。为保证跨期可比，这里去掉了后期才加入的技能奖励项。*

## G-CAST 的核心：两条循环，一道准入门

![G-CAST 治理式持续自训练架构](https://arxiv.org/html/2611.17814v1/overview_v1_powerpoint.png)

*图 1：上方主循环完成多 rollout 生成、奖励可靠性检查、数据编排、模型适配和 checkpoint 准入；下方奖励演化循环负责标注、奖励更新、离线检查、试验性训练和联合评估。右侧 Evaluation Ledger 记录被拒绝的候选与观察到的退化。*

这张图信息密度很高，但主线其实一句话就能讲清：**先判断奖励还可不可信，再决定数据该怎么学，由准入门决定新模型能不能被接受。**

每轮都从一个不可变的 accepted checkpoint 出发。生产查询在当前 harness 下重放并生成多条轨迹，可靠证据进入训练，疑似奖励错误进入下方支路。候选模型只能从同一个已接受父节点训练，不能因为某次训练跑完了就自动替换线上版本。

这就是论文把 **checkpoint transition** 而不是“一次训练任务”视作适应单元的原因。训练结束只是产生候选，能否上线由另一套标准决定。

### 1. 奖励负责分池，熵只负责排队

每个查询用当前 accepted checkpoint 生成 8 条 rollout。作者先剔除有效奖励最高和最低各 5% 的轨迹，再计算剩余奖励均值，作为本轮参考线。随后按结果分布路由：

| Rollout 结果 | 去向 | 为什么这样处理 |
|---|---|---|
| 全部低于参考线，且存在已验证目标 | SFT 池 | 当前策略没采样出好答案，直接用可靠目标教 |
| 同时有高于和低于参考线的结果 | RL 池 | 同一查询已有结果差异，适合做相对优化 |
| 全部高于参考线 | 回归监控 | 当前模型已经会做，不必硬塞进训练集 |

这个分工挺漂亮。全失败查询拿去 RL，组内没有正例，优势信号很难提供方向；全成功查询继续训练，收益小还可能挤掉旧能力。混合结果才是 RL 最自然的素材。

路由结束后再做样本优先级排序。对每条 rollout 计算 token-level entropy，取其中第 90 百分位数；一个查询有 8 条 rollout，则取 8 个分数的最大值。用简洁记号表示：

$$H(q)=\max_{r\in\mathcal{R}_q}\operatorname{Percentile}_{90}\left(\{h_{r,1},\ldots,h_{r,T_r}\}\right)$$

这里 $h_{r,t}$ 是第 $r$ 条轨迹在第 $t$ 个生成位置的 token 熵，$\mathcal{R}_q$ 是查询 $q$ 的 rollout 集合。

关键在于，**熵不参与判断样本对不对**。奖励已经决定了它该进 SFT 还是 RL，熵只在各自池子里把训练预算优先分给不确定度高的例子。把“学习角色”和“训练优先级”拆开，避免把高熵直接等同于错误，也避免把低熵直接等同于正确。

说实话，这个设计比“按熵挑一批难样本，再统一训练”更符合实际。高熵可能来自有价值的探索，也可能只是模型在乱猜；先有奖励路由兜底，熵排序才不容易喧宾夺主。

### 2. 奖励错了，先停训，而不是继续优化错误目标

主循环里有个很容易被人忽略、我却觉得最值钱的动作：**Training Paused**。

当审计发现高分轨迹其实违反当前契约，训练就暂停。下方奖励演化循环开始工作：收集审计批次并做契约对齐的轨迹标注，提出可执行规则更新，再经过目标用例验证、已知正确样本回归、离线重打分、轨迹 replay 或 dry-run。候选奖励还要控制一次试验性适配，最终与候选 checkpoint 一起接受联合评估；没有收益或出现退化，就回到旧奖励和旧 checkpoint。

奖励因此不再是一段隐含在训练脚本里的固定逻辑，而是带版本、适用条件、验证记录和回滚路径的 **可执行对象**。

奖励随契约逐步扩张。Period 1 只有格式与交互合规奖励 $R_{\mathrm{fmt}}$；Period 2 加入 grounding 惩罚 $P_{\mathrm{gd}}$ 和检索失败惩罚 $P_{\mathrm{retrieval}}$；Period 3 再加入技能选择与技能遵循奖励：

$$R_{\mathrm{train}}^{(3)}=R_{\mathrm{fmt}}+P_{\mathrm{gd}}+P_{\mathrm{retrieval}}+R_{\mathrm{skill\text{-}sel}}+R_{\mathrm{skill\text{-}adh}}=R_{\mathrm{full}}$$

$P_{\mathrm{gd}}\leq 0$ 用来压低答案中缺乏用户输入或工具证据支持的事实内容，$P_{\mathrm{retrieval}}\leq 0$ 处理“声称检索失败却又给不出有效商品或店铺结果”的情况。$R_{\mathrm{skill\text{-}sel}}$ 对照教师验证的参考判断该不该选某个技能，$R_{\mathrm{skill\text{-}adh}}$ 则按规则检查是否遵循所选 SKILL.md 中的流程和工具顺序。

Period 4 没有继续堆新的标量项，而是扩大现有组件的适用范围，让沙箱、文件处理、导出和长工作流也进入相同的可执行检查。每个组件只在自己的契约条件满足时生效，不是对所有查询无差别加分扣分。

这里还有个实验设计上的细节：训练奖励可以演化，**所有报告结果却统一使用最终、冻结的完整评测奖励**。适用性只由查询契约决定，与 checkpoint 或消融组别无关。否则每轮换一把尺子，前后的分数根本没法比较。

### 3. 上线标准不是新任务涨分，而是新旧任务一起过关

候选 checkpoint 的评估集从 100 条逐期扩到 400 条。作者分别跟踪旧时期奖励 $R_{\mathrm{ret}}$、新时期奖励 $R_{\mathrm{new}}$ 和全部活跃时期的累计奖励 $R_{\mathrm{cum}}$。

这道门控防的是很常见的假象：新技能分数涨了，总体也涨了，但老功能已经退化，只是被新增指标掩盖。G-CAST 要求候选同时证明新需求适应与旧行为保持，拒绝结果会进入 evaluation ledger，成为下一轮证据。

跟几类相近工作放在一起看，定位会更清楚：

| 路线 | 主要更新对象 | 固定不变的部分 | G-CAST 多走的一步 |
|---|---|---|---|
| ACE 等上下文演化 | playbook、上下文 | 模型权重 | 让模型内化新能力 |
| SIA 等联合演化 | harness 与模型权重 | 既定任务规范和 verifier | 让契约、证据和奖励一起演化 |
| AutoTrainess | 数据、训练、评估和实验日志 | 预定义训练目标 | 检查目标本身是否仍然可靠 |
| G-CAST | 模型、奖励、学习证据与评测账本 | 已接受的不可变父版本 | 用累计评测治理每次 checkpoint 转移 |

AutoTrainess 原始论文把人类训练经验外置成结构化 Agent-Computer Interface，覆盖数据处理、训练、评估和日志规划，已经是较强的自主后训练 baseline。G-CAST 的差异不在于“更会跑训练脚本”，而在于它会追问：**这次训练使用的奖励，还配得上当前产品契约吗？**

## 实验：真正的分水岭出现在技能契约扩张之后

实验基座是 Qwen3-4B-Thinking-2507。四个时期各有一个冻结的 2,000 查询 rollout pool，以及事先隔离的 100 查询评测切片。每个查询采样 8 条轨迹，因此每个上下文在路由前产生 16,000 条轨迹。

新上下文加入时，先测 accepted checkpoint 在该时期 100 条查询上的表现；之后每个候选都要跑所有活跃切片，累计评测规模从 100 增至 400。对比方法共享父模型、harness 版本、候选集合、教师目标与解码配置，评测查询也排除在训练、合成和奖励开发之外。

这些设置在工业论文里算做得细。但先别急着看末尾的总分，逐期结果其实更有故事。

### 主实验：G-CAST 并非每一轮都赢

| 轮次 | 方法 | SFT / RL 查询数 | Post-RL 累计奖励 | 旧时期：轮前 → 轮后 | 新时期：轮前 → 轮后 |
|---|---|---:|---:|---:|---:|
| 1 | AutoTrainess | – / 1200 | 0.9360 | – | 0.9065 → 0.9360，增 0.030 |
| 1 | G-CAST | 94 / 500 | 0.9240 | – | 0.9065 → 0.9240，增 0.018 |
| 2 | AutoTrainess | – / 1200 | 0.8935 | 0.9365 → 0.9325，降 0.004 | 0.7965 → 0.8545，增 0.058 |
| 2 | G-CAST | 54 / 984 | 0.8835 | 0.9240 → 0.9300，增 0.006 | 0.7265 → 0.8370，增 0.110 |
| 3 | AutoTrainess | – / 1200 | 0.9210 | 0.8700 → 0.9119，增 0.042 | 0.9227 → 0.9392，增 0.017 |
| 3 | G-CAST | 62 / 778 | 0.9288 | 0.8198 → 0.9163，增 0.097 | 0.8964 → 0.9538，增 0.057 |
| 4 | AutoTrainess | – / 247 | 0.7911 | 0.8907 → 0.8739，降 0.017 | 0.3433 → 0.5428，增 0.200 |
| 4 | G-CAST | 122 / 859 | 0.8078 | 0.8712 → 0.8833，增 0.012 | 0.3983 → 0.5813，增 0.183 |

*表 2 核心结果。所有分数均为统一冻结评测奖励；旧时期均值按查询数加权。*

前两轮 AutoTrainess 的 Post-RL 累计奖励更高，分别是 0.9360 对 0.9240、0.8935 对 0.8835。G-CAST 的亮点是用较少训练查询取得接近的结果，但不能把它写成全程领先。

分水岭在 Period 3。契约开始显式要求技能调用和流程遵循后，G-CAST 以 0.9288 超过 AutoTrainess 的 0.9210；Period 4 继续以 0.8078 对 0.7911 保持优势。技能选择准确率也在第三轮达到 0.8667 对 0.8433，第四轮扩大到 0.7625 对 0.6875；技能遵循分数分别为 0.5233 对 0.5153、0.4503 对 0.4219。

第四轮的适应与保持尤其值得拆开看。AutoTrainess 的新时期增量其实更大，增了 0.200，G-CAST 增 0.183；但 G-CAST 的新时期终值更高，0.5813 对 0.5428，同时旧时期还增了 0.012，baseline 则降了 0.017。**它赢的不是单项冲刺，而是新能力终值与旧能力保留的组合。**

也得给一个公平性边界：双方虽然共享 rollout pool 和评测协议，训练查询数却由各自策略决定。第四轮 AutoTrainess 只用了 247 条 RL 查询，G-CAST 用了 122 条 SFT 加 859 条 RL 查询。因此这张表能支持“整套策略效果更好”，不能单独证明“相同预算下样本效率更高”。

### 数据消融：路由有用，熵排序再往上推一截

这部分控制得比较干净。三个组共享候选集合、训练预算和配置，每组都选 150 条 SFT、500 条 RL 查询。Random 不做奖励路由；Reward + Random 先路由再池内随机；Reward + Entropy 是完整方法。

| 阶段 | 数据策略 | 累计奖励 | 格式奖励 | 技能选择准确率 | 技能遵循奖励 |
|---|---|---:|---:|---:|---:|
| Base | Qwen3-4B-Thinking-2507-FP8 | 0.7331 | 0.7368 | 71.50% | 0.3446 |
| Post-SFT | Random | 0.7200 | 0.7300 | 71.50% | 0.3567 |
| Post-SFT | Reward + Random | 0.7361 | 0.7466 | 72.25% | 0.3570 |
| Post-SFT | Reward + Entropy | 0.7800 | 0.7831 | 73.25% | 0.3534 |
| Post-RL | Random | 0.7334 | 0.7520 | 70.00% | 0.3504 |
| Post-RL | Reward + Random | 0.7721 | 0.7814 | 73.00% | 0.3541 |
| Post-RL | Reward + Entropy | 0.7930 | 0.8069 | 73.25% | 0.3637 |

Post-RL 阶段，加入奖励路由让累计奖励从 0.7334 提到 0.7721，增加 0.0387；再把池内随机换成熵排序，来到 0.7930，又增加 0.0209。路由贡献更大，熵排序则提供了独立增量。

还有个反直觉点：Post-SFT 的 Random 从基座 0.7331 掉到 0.7200。数据多一点并不天然更好，没分清楚该教什么，SFT 也可能把模型拉偏。

技能选择准确率在三组间差距不大，真正的差别落在技能遵循。模型大概知道“该选哪个技能”，却未必能按规定顺序把流程走完。对生产 Agent 来说，后者通常才是更容易出事故的地方。

### 奖励消融：多加几个奖励项，不等于奖励治理

作者还审计了高分轨迹，发现两类反复出现的高分错误：搜索结果误用的假阳性率为 84%，答案实体幻觉的假阳性率为 82%。Agent 确实调用了看似合理的检索工具，却会输出工具证据不支持的 offer ID、URL、价格或电话号码。

所以问题不是“失败样本得分太低”，而是**错误样本得分太高**。这正是奖励可靠性检查存在的理由。

三组 RL 诊断从同一个 SFT checkpoint 出发，训练数据和非奖励超参数一致：

| 指标 | Static 固定旧奖励 | Ungated 一次性更新 | Gated 持续门控演化 |
|---|---:|---:|---:|
| 累计奖励 | 0.8810 | 0.8926 | 0.9288 |
| Period 1 奖励 | 0.9248 | 0.9380 | 0.9336 |
| Period 2 奖励 | 0.8381 | 0.8486 | 0.8990 |
| Period 3 奖励 | 0.8801 | 0.8812 | 0.9538 |
| 格式奖励 | 0.9055 | 0.9025 | 0.9143 |
| 技能选择准确率 | 0.6867 | 0.6956 | 0.8667 |
| 技能遵循 | 0.4508 | 0.4865 | 0.5233 |

Static 到 Ungated，累计奖励只增加 0.0116，Period 3 更只增加 0.0011；Gated 则把累计奖励推到 0.9288，比 Static 高 0.0478，Period 3 高 0.0737。差距最集中的地方正是技能选择与流程遵循，和契约扩张的位置对得上。

不过我会保留一个疑问：Ungated 是“一次性契约更新”，Gated 是“持续演化且每次过门控”，两者同时差了更新频率和验证机制。实验证明了完整治理方案更好，却没法把这 0.0362 的 Ungated 到 Gated 增量全部归因于“门控”本身。若再补一个“持续更新但不设门控”的组，因果拆解会更漂亮。

另外，Gated 的 Period 1 奖励 0.9336 略低于 Ungated 的 0.9380。它不是每个指标都单调变好，优势主要出现在后期契约真正新增的行为上。

## 生产价值：省下的不是 GPU，而是奖励审计与返工

论文报告，G-CAST 在元采部署后，每轮人工奖励审计从约 2 个人日降到 30 分钟，需求到验收的周期从约一周缩到两天。门控还拒绝了 3 个候选 checkpoint 和 2 个未通过验证的奖励版本。

我喜欢这组数字，因为它衡量的是治理本身，而不是又把训练分数复述一遍。被拒绝的 5 个版本尤其重要：一套只允许成功、不允许拒绝的自进化系统，很难让人放心放进生产环境。

但这些仍属于工程运营指标。论文没有给出线上 A/B、采购转化、用户满意度或业务收入变化，也没有报告完整 GPU 开销、训练时延和单位提升成本。因此，“部署有效”有生产证据支撑，“带来多少业务收益”则还没有答案。

## 我的判断：工程整合很扎实，科学证据还没完全闭环

这篇论文最值钱的地方，是把持续学习里常被分开的三件事绑到了一个版本化过程里：能力契约定义要学什么，生产轨迹提供能学什么，可执行奖励决定什么算好。checkpoint 不再孤立演进，而是和契约、奖励、证据、评测账本一起转移。

它也有几个清楚的边界。

实验只覆盖一个纵向生产应用和一个主要模型家族，数据、工具链、奖励实现均未公开，外部团队很难完整复现。每期评测只有 100 条查询，论文没有报告置信区间或显著性检验；0.8078 对 0.7911 的差距值得重视，但还不能据此推断到其他业务必然成立。

对比面也偏窄。AutoTrainess 是合理且较强的自主后训练 baseline，但论文没有横向比较更多经典持续学习策略，例如旧数据 replay、正则化抗遗忘或更简单的“固定奖励加全量累计回归”。现有消融能解释 G-CAST 内部组件，却不能完全回答这些更便宜的替代方案是否足够。

复现信息也不算完整。正文给出了基座、rollout 数、数据池和选择预算，却没有集中列出学习率、RL 算法细节、GPU 配置与训练成本。坦率地讲，我能理解并评估这套系统为什么可能 work，却无法仅凭公开正文把训练过程一比一复现。

所以我会把它定位为 **生产系统与训练治理的工程整合**，而不是持续学习理论的底层突破。这个定位不是贬低。线上 Agent 真正缺的，往往不是一个更复杂的 loss，而是知道何时该停训、何时该修奖励、何时该拒绝新模型。

如果要把思路迁到自己的 Agent 项目，我会先落地四件事：给工具与流程建立显式契约版本；让奖励组件带适用条件和回归用例；把全失败、混合结果、全成功轨迹分开处理；所有候选都在累计新旧任务上验收。熵排序可以后加，准入门和奖励可靠性检查不该省。

G-CAST 留下的追问也挺现实：当奖励本身需要持续演化时，谁来验证“验证器”？这篇论文给出的答案是契约标注、离线检查、试验适配和人工审计共同把关。它能减少人工，却没有消灭人工。对真正上线的自进化 Agent，这种克制反而是优点。
