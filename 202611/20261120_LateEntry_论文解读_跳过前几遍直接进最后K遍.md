# 早退出只做对了一半：循环语言模型该把算力花在末尾几遍

调一个循环结构的小模型时，我碰到过一件挺别扭的事：参数量压得很漂亮，推理却慢得让人想砸键盘。原因不复杂——同一套层栈要对每个 token 反复跑 $T$ 遍，跑得越深，串行解码延迟就跟着 $T$ 线性往上涨。想提速最自然的念头是「少跑几遍」，于是 early exit 顺理成章：跑完前 $K$ 遍就收工，剩下的直接砍掉。

我第一反应也是这么干的。但 2026 年 11 月挂到 arXiv 的这篇论文（arXiv:2611.24576）问了一句特别朴素的话：**如果只能跑 $K$ 遍，凭什么一定是前 $K$ 遍**？

答案有点打脸。把这几遍挪到末尾、让新 token 跳过开头直接进末尾 $K$ 遍，效果反而更好。不是好一点，是在同权重、同微调、同速度下把早退出甩开一大截。

> **核心摘要**：循环语言模型用「同一层栈重复 $T$ 遍」换取紧凑参数下的推理深度，代价是解码延迟随 $T$ 线性增长。常规早退出砍掉后面的遍数，却把历史 token 的 KV 缓存也一起冻在浅层；这篇论文反过来做，让新 token 跳过前几遍、直接进末尾 $K$ 遍，去读一份已经跑满 $T$ 遍的深度上下文缓存。跨过「隐状态范数对不上」这道坎只需一次轻量两阶段微调，之后深上下文就能顶替 token 自己被跳过的计算。再配上跨步流水补缓存和 Wake verification，作者在单张 H100 上把 Ouro-2.6B 的贪心精确解码做到 5.2 倍、有损解码做到 6.8 倍，Huginn-3.5B 在 $T=64$ 时贪心精确冲到 8.4 倍。我的判断：这不是模型结构的突破，而是把一个被默认接受的假设翻过来、再用相当扎实的系统工程兑现掉的范例——观察本身很值钱，数字得挑工况看。

## 🎯 一、T 遍循环，T 倍延迟：一个被默认接受的成本

先把背景聊清楚，不然后面的巧劲看不出来。

循环语言模型（looped LM）这条线，从 Universal Transformer 那会儿就有个很诱人的承诺：**参数不用涨，计算深度可以涨**。同一套 Transformer 层权重 $\mathcal{F}$ 被复用 $T$ 次，每个 token 的隐状态一遍遍被精炼：

$$\tilde{h}_i^{(k)} = \mathcal{F}\big(\tilde{h}_i^{(k-1)},\, \mathcal{C}_{\lt i}^{(k)}\big), \qquad \tilde{h}_i^{(0)} = e(x_i)$$

这里 $\mathcal{C}_{\lt i}^{(k)}$ 是第 $k$ 遍专属的、按遍对齐的 KV 缓存。Ouro（Zhu 等，2025）跑 $T=4$，Huginn（Geiping 等，2025）是 2 层 Prelude + 4 层 Core 循环 $T=32$ 次 + 2 层 Coda，等效 132 层却只有 8 层独立参数。听着很美。

问题出在自回归解码。生成一个 token 得老老实实串行跑完 $T$ 遍，于是「深度」直接翻译成「延迟」。$T=32$ 时 Huginn 的串行吞吐只有约 21.9 tokens/s，$T=64$ 掉到 11.1 tokens/s——参数没多，墙钟时间翻倍地往上堆。

于是省遍数成了刚需。early exit（Schuster 等，2022 那一挂）的做法是让 token 跑前 $K$ 遍就停。听起来无懈可击：前面几遍最「基础」，先算总没错吧？但作者盯住了一个被忽略的副作用——**早退出不只砍了当前 token，它把过去所有 token 的 KV 缓存也一并冻在了浅层**。往后每个新 token 做 attention 时，读到的都是没长熟的浅层上下文。

说实话，我以前也没往这层想。省计算的时候，大家盯的都是「这次前向省了几层」，很少去问「我给后面留下的缓存残不残」。

![图1：早退出与晚进入的对比，以及精度-吞吐前沿](https://www.mulanai.com/fs/files/1120_815d417f_fig_hero.png)

*图 1（论文 Figure 1）：四个子图把整个故事摊开。(a) 全深度：上下文里的 "Sam has" 和新 token "clips" 都跑满 pass 1→4；(b) 早退出：橙色只跑 pass 1，P2–P4 标着 unused，留下一份 shallow K/V；(c) 晚进入：上下文保留 deep K/V，新 token 跳过 pass 1–3，箭头标着 "enter at P4"；(d) 前沿条形图：Ouro-2.6B 上全深度块基线 4.1×，Wake K=2（τ=0）到 5.2–5.5×（greedy-exact，比 K=4 高 26%），有损晚进入（τ=∞）6.8×；Huginn-3.5B 上全深度块 3.4×，Exact Wake 6.1–8.4×（+82%~153%），有损 9.9–10.6×。*

图 1 的 (b) 和 (c) 放一起看特别直观：同样只给新 token 算几遍，一个把上下文留在浅层，一个把上下文喂到满深度。差别就在这份缓存上。

## 🤔 二、反直觉的那一刀：晚进入，以及它一开始为什么不 work

作者把问题收得很干净，先在「理想上下文」下问一句：**预算只有 $K$ 遍时，花在开头还是花在结尾**？

为了不被轨迹漂移干扰，他们用 teacher-forced agreement 来量：先按全深度贪心生成参考答案，再拿同样的前缀在减遍配置下重放，统计下一个 token 与全深度一致的比例。数据集是 GSM8K 和 IFEval，模型是 Ouro-1.4B（24 层）和 Ouro-2.6B（48 层）。

直接把裸晚进入套到现成 checkpoint 上，翻车翻得很难看：

| 喂给 pass 4 的输入（K=1，四遍上下文） | Ouro-1.4B | Ouro-2.6B |
|---|---|---|
| 原始 token embedding（裸晚进入） | .552 | .751 |
| 闭式线性投影后的 embedding | .816 | .919 |
| 真 pass-3 隐状态（诊断上限） | .991 | .992 |
| 参考：1 遍早退出 | .938 | .949 |

*表 1（论文 Table 1 节选）：78,693 与 70,101 个 GSM8K token 位置上，与全深度 T=4 解码的下一 token 一致率。*

.552 和 .751，比干脆把整个模型截成 1 遍还差。为什么？作者去翻了激活值，诊断很利落：**范数失配**。pass 1 期望的是原始 embedding，$\ell_2$ 范数中位数 0.76；pass 4 期望的是 pass 3 吐出来的 layer-normalized 隐状态，范数 37 到 51。把一个 0.76 量级的向量硬塞进等 40 量级输入的层里，预测不崩才怪。

有意思的是，他们没急着上适配器，而是先拟合了一个**闭式线性投影**（模型权重全部冻住），一致率立刻回到 .816 / .919，找回了通往 oracle 上限（.991 / .992）之间 60% 到 70% 的差距。这个诊断挺漂亮：说明主要不是「缺了前几遍的计算」，而是「输入表征对不上」。顺带一提，附录里试过把 embedding 直接归一化再按范数缩放到 37~51，结果更糟，掉到 .218 / .245；也试过冻权重训两层 MLP 入口适配器，仍然比简单截断低 1.1 到 3.4 个点。粗暴地对齐幅度没用，得让模型自己学会接这个输入。

真正的解法是一次两阶段微调（都跑在 Dolci-Instruct-SFT 上，各一个 epoch）：

- **Stage 1**：标准全深度指令微调，序列长 1024。
- **Stage 2**：MARS 式 mask-placeholder 块微调，16 token 一个块；**一半块从 pass 1 跑满四遍，另一半直接把原始 embedding 喂进末尾的晚遍**（$K \sim \text{Uniform}\{1,2,3\}$），前缀缓存保持满深度。学习率 $10^{-5}$，全局 batch 256，7395 步，约 1.9B tokens，单台 8×H100。

推理时**零额外参数**。训练消融把因果钉死了：

| 训练配置 | 全深度 Acc.（GSM8K / IFEval） | 晚进入探针一致率 | 晚进入解码 K=2 |
|---|---|---|---|
| 不微调（原始 base） | .729 / .442 | .751 | 无 drafter，跑不了 |
| 只做 Stage 1 | .880 / .728 | .699 | 无 drafter，跑不了 |
| Stage 1 + Stage 2，关掉晚进入曝光 | .820 / .708 | .738 | .636 / .529 |
| 完整配方 | .873 / .732 | .962 | .839 / .699 |

*表 2（论文 Table 9 节选）：探针列是 K=1、D=4 的 teacher-forced 一致率，右列是 K=2、B=8 的端到端块解码准确率。*

.699 → .738 → .962 这条线说明，光做指令微调、光做块微调都不够，**必须让模型在训练里真的见过「从原始 embedding 直接进末尾一两遍」这种输入**。这块我读的时候愣了一下：一个看似纯解码期的小技巧，落地门槛其实是一次接近 2B tokens 的 SFT。后面聊局限时还会回到这点。

## 🧠 三、为什么一遍就够：深上下文比 token 自己的账更值钱

对齐做完，作者把两个变量拆开来量：上下文缓存深度 $D$（前面所有 token 跑满几遍），和当前 token 的遍数预算 $K$（从第 $D-K+1$ 遍进，跑到第 $D$ 遍）。于是 $(K=2, D=2)$ 就是标准两遍早退出，$(K=1, D=4)$ 是「只跑一遍、但读四遍深度的上下文」。

![图2：单个适配后的晚遍为何够用](https://www.mulanai.com/fs/files/1120_187ceef1_fig_ctxd.png)

*图 2（论文 Figure 2）：(a) 机制示意——上格 Shallow context（K=2, D=2）里 P1/P2 是未精炼的浅 KV，token $x_i$ 得自己跑两遍，一致率 .954；下格 Deep context（K=1, D=4）里四遍上下文 KV 已经存好了多遍推理，P1–P3 跳过，一个对齐后的 Q 从 $e(x_i)$ 直接查深度状态，一致率反而 .962。(b) teacher-forced 条形：K=1 浅 .945 / 深 .962，K=2 浅 .954 / 深 .984，K=3 深 .992，图上直接标了 "1 pass > 2 passes (.962 vs. .954)"。(c) 自由生成 K=2 的柱状对比：GSM8K 从 .749 提到 .853（+10.4 点），IFEval 从 .588 提到 .708（+12.0 点）。*

那个 cross-diagonal 反转值得停一秒：**一遍深上下文打赢两遍浅上下文**（.962 对 .954）。Ouro-1.4B 上同样成立（.948 对 .922，bootstrap 置信区间不重叠）。

你想想看，这其实在说一件事——多遍循环精炼出来的东西，大部分被写进了 KV 缓存里。新 token 只要能直接查这份「已经想明白」的深状态，就不必自己再把那几遍重算一遍。早退出逼着每个 attention head 去读没长熟的前缀状态，等于把别人存好的成果扔了，自己从头再想。

同权重下把「前 K 遍」和「后 K 遍」摆在一起，差距也很稳：

| K | First K（前 K 遍，GSM8K / IFEval） | Last K（后 K 遍，GSM8K / IFEval） |
|---|---|---|
| 1 | .898 / .757 | .962 / .887 |
| 2 | .954 / .866 | .984 / .943 |
| 3 | .982 / .949 | .992 / .969 |

*表 3（论文 Table 2 节选）：同一 Stage-2 checkpoint，Ouro-2.6B，70,101 个 GSM8K 与 61,723 个 IFEval 位置。12 个格子全是「放末尾」赢，K=1 时领先 6.4 到 14.1 个点。*

机制上还有两组 fp32 探针挺有说服力。一组是**按遍一致的 K、V 配对**：把 pass-1 的 K 配 pass-4 的 V，一致率直接塌到 .000（100% 位置上吐 endoftext）；反过来 pass-4 的 K 配 pass-1 的 V 掉到 .296。也就是说晚遍查询要的是**同一遍的 K 和 V 成套**，光给深 value 没用。适配后 K=1 的隐状态与真 pass-4 状态的 linear CKA 到 .961，未适配只有 .273 到 .365。

另一组更关键：按全深度 top-1 置信度分层，GSM8K 上 68% 的 token 是 $p_{\max} \ge .95$ 的高置信位置，晚进入在这些位置上 K=2 的一致率是 1.000；剩下的误差几乎全挤在 6% 的 $p_{\max} \lt .50$ 不确定尾部（一致率 .827）。看到这个数我有点兴奋——**误差高度集中，就可以用一个便宜的兜底机制专门盯住那 6% 的不确定尾部**，而不必为所有 token 付全深度的代价。这篇论文后半段的系统，几乎就是从这句话长出来的。

## 🏗️ 四、从观察变成能跑的系统：三步流水线

观察归观察，真要落地得解决一个硬骨头：**新 token 的深上下文缓存从哪来**？ 你要是停下来把它 1→T 遍补完再继续生成，等于每步多 $T$ 次串行调用，省下的延迟全吐回去了。

作者的解法是让生成带上一个短流水线滞后，每个解码步干三件事（以 $T=4, K=2$ 为例）：

| 步骤 | 做什么 | 关键性质 |
|---|---|---|
| ① 暂定晚遍验证 | 候选块跳过 pass 1、2，只跑 pass 3、4（$K$ 次串行调用），吐出暂定接受的前沿和临时 KV | 关键路径只有 $K$ 遍 |
| ② 临时 KV 曝光 | 新接受的 token 先用从 embedding 算出的临时键值占住 P3*、P4* 槽 | 下一步不 stall |
| ③ 流水补缓存 + Wake | 在后续 $L=\lceil T/K\rceil$ 步里，这些 token 搭顺风车在同一次前向调用中补完真 1→4 遍 | 零额外串行调用 |

*表 4：论文 Section 3 的三步分解，T=4、K=2 时 L=2，T=32、K=8 时 L=4。*

![图4：单个晚进入块步内部](https://arxiv.org/html/2611.24576v1/fig_sched_web.png)

*图 4（论文 Figure 4）：T=4、K=2、B=2 的单步。末尾那个已提交锚 token "3" 和 2 个候选 "red"、"apples" 各挂 2 个 mask placeholder，凑成 $(1+B)^2 = 9$ 行，一起直接进 pass 3。结构化因果掩码保证候选只看得到锚和它前面的候选，placeholder 分支向前看 j 位。前缀验证接受 "red"（✓），被拒的换成 bonus "balls"（×），并把 "red" 后面 placeholder 的预测 "and"、"2" 直接复用成下一步的 draft，零独立 drafting 调用。*

这里借的是一个现成的、无参数的 mask-placeholder 块解码器（Liu 等 2026a；Jin 等 2026），作者只改了「关键路径跑哪几遍」和「提交后的 KV 怎么补」。$B=8$ 时活跃块有 $(1+8)^2 = 81$ 行，最多再加两组各 9 个 token 的补缓存行，合起来 99 行。

![图5：多步流水线](https://arxiv.org/html/2611.24576v1/fig_step_web.png)

*图 5（论文 Figure 5）：T=4、K=2 的三步流水线。每一步都只做 K=2 次串行前向。Group A（1+c ≤ 1+B 个 token）在 Step 1 跑晚进入的 pass 3、4，写下临时状态 P3*、P4*；随后在 Step 2 的 pass 1、2 和 Step 3 的 pass 3、4 里，作为并行 batch 行重算真正的 1→4 遍——图上明确标了 "adding zero extra serial forward calls"。*

为什么搭顺风车几乎不花钱？作者把话说得很实在：**零额外串行调用不等于零额外 FLOPs**，一个暂定 token 照样要跑 $K$ 遍验证加 $T$ 遍补缓存。但单序列（batch-1）解码是显存带宽瓶颈，不是算力瓶颈——层权重 $\mathcal{F}$ 一旦从显存流出来，多塞几行 token 几乎是白搭。H100 上前向 32 个并行 token 只比前向 1 个慢 9%。这些补缓存行就藏在这块冗余里。

顺带说个我挺欣赏的诚实：作者强调所有报出来的速度**都把这部分额外算力算进去了**，没偷偷扣掉。附录还做了消融——读一两步临时 KV 相比「下一步之前同步修好」零可测精度损失（p=.28 到 .77），而完全不补缓存会让 K=2 的 GSM8K 掉 4.1 点（.839 → .798）。补缓存不是可选项。

## 🔧 五、Wake verification：一个 τ 旋钮把 exact 和 lossy 收进同一张图

到这步，系统里其实已经悄悄算出了一样很值钱的东西：流水补完缓存时，那些 wake 隐状态 $\tilde{h}_i^{(1\dots T)}$ 和串行跑满 $T$ 遍的状态在数学上是**一模一样**的。朴素的有损晚进入写完 KV 就把它们扔了。

作者的做法是：别扔，把它们塞进**同一个 output GEMM**（就是 lm_head）里投影出来，和活跃块的 81 行一起算（B=8 时 90 到 99 行）。零额外层调用、零额外 kernel launch、零额外 CUDA graph。于是就有了一根连续的旋钮 $\tau$（logit-margin 容忍度）：

$$z_{1:T}^{(i)}(\hat{y}_i) \lt \max_{y}\, z_{1:T}^{(i)}(y) - \tau$$

$\hat{y}_i$ 是 $K$ 遍路径上暂定接受的 token，$z_{1:T}^{(i)}$ 是 wake 位置上的精确 $T$ 遍 logits。在区间 $[u,v)$ 里找最早满足上式的位置 $i^*$，一旦触发就把暂定前沿从 $i^*$ 之后截断，提交精确 token $y^*_{i^*}$，重置 wake 队列续跑。Figure 6 那个例子很具体：前缀 "2 + 3" 之后，晚遍在 "=" 上猜了 "6"，两步后 wake 发现真值是 "5"，logit gap $\Delta z = 2.4$，于是回滚、把 "5" 提交上去。

一个 $\tau$ 串起三种状态，我是真的觉得这个设计挺精巧的：

| τ | 状态 | 行为 | 精度代价 |
|---|---|---|---|
| $\tau=0$ | Exact Wake | 任何不一致都回滚，贪心精确等价于 T 遍解码 | 提交 token 差异 0.007%~0.09%，低于 bf16 顺序 floor 0.25%~0.33% |
| $0 \lt \tau \lt \infty$ | Margin-Gated | 放过 benign 近平局翻转，只回滚 confident 偏差 | 换 2× 到 16× 更少的回滚，精度基本不掉 |
| $\tau=\infty$ | 有损晚进入 | 完全不回滚 | K=2 时 1.4 到 4.0 点 |

*表 5：Wake verification 的 τ 谱（论文 Section 3.4、Table 7）。三种模式共用一张静态 CUDA graph。*

>98% 的位置上晚遍猜测本来就对，Group A 直接并入永久验证前缀、零回滚；只有那 6% 不确定尾部会偶尔触发。前面第三节埋的伏笔，到这儿收了口。

作者还做了个 factorization 验证：把同一个 verifier 换配一个无参数的 4/3/2-gram 上下文后缀 drafter，虽然原始块接受率略低（Ouro GSM8K 上 3.93 对 5.02 tokens/step），但 $K \lt T$ 带来的**倍数收益照样成立甚至更强**（1.37× 对 1.26×）。这说明提速来自「验证只跑 K 遍」，跟 draft 从哪来是正交的两件事。

## 🧪 六、数字都摆出来

## ⚠️ 七、我的判断：哪里漂亮，哪里有水分

先说被打动的。

**问题提得干净**。 「省遍数该省哪几遍」是个几乎没人正经问过的问题，而且答案反直觉。从 Table 1 的范数失配诊断，到闭式线性投影的定位，到 Figure 2 的 cross-diagonal 反转，再到 6% 不确定尾部的误差定位，因果链条一环扣一环，不是先有系统再补故事。

**Wake verification 的工程审美在线**。 把流水补缓存时反正要算的精确 hidden state 塞进同一个 output GEMM，用一个 $\tau$ 把 greedy-exact、margin-gated、lossy 三种模式收进一张静态 CUDA graph，还和 drafter 选择正交。零额外 kernel、零额外图，这种「顺手把废热用掉」的设计我一看就喜欢。

**验证不偷懒**。 同权重对比、matched fine-tuning 对比、专门训 early-exit 对照组、跨引擎归一化、Appendix E 的 committed-token 审计（0.007%~0.09% 差异低于 0.25%~0.33% 的 bf16 顺序 floor）、只用 K=4 拟合去预测 K<4 的 Roofline——该堵的口子基本都堵了。T 缩放还特意用同一 checkpoint 隔离 $T$，避开了 Ouro 对 Huginn 的家族混淆（这点作者自己也在正文里点明了，没藏着）。

再说让我皱眉的地方。

**5.2× / 8.4× 是实验室最优工况的数字**。 全是 batch-1、单 H100、greedy、同一 job 内配对的串行基线。生产环境是 continuous batching，作者自己在局限里承认：C 从 1 涨到 32 时，B=8 的全深度块解码从 3.90× 掉到 0.77×，主要锅在 $(1+B)^2$ 块膨胀，不是晚进入本身；晚进入相对同 B 块的增量倒是稳（1.65×→1.45×）。得靠动态把 B 从 8 缩到 4 再到 2，C=32 时才留住 2.31× 的 decode（算上在线 prefill 是 1.67×）。把 5.2× 直接当线上收益，会踩坑。

**它不是即插即用**。 Stage-2 那 7395 步、约 1.9B tokens、8×H100 的 SFT 是硬门槛。对不方便重训的模型，这套东西用不上。有意思的是 Huginn 给了个反证：因为 Prelude 已经把原始 embedding 映射成归一化锚点、每个 Core 步还会重新注入，范数失配天然被缓解——**即便在从没见过晚进入的 early-exit 训练 checkpoint 上，K=8 晚进入也打赢了它自己训过的 K=8 早退出**（.327 对 .271，p=2.2×10⁻⁶）。这暗示架构上内建入口对齐，可能比事后微调更根本。作者把「预训练阶段就暴露晚进入」留给了 future work，我觉得这反倒是更值得追的方向。

**绝对精度偏低，评测面有裁剪**。 Huginn 上只报 GSM8K、IFEval、BBH、MBPP 四个基准（8,871 条），明确略过 MMLU-Pro 和 MATH500，理由是 8 层 base 模型在这俩上接近随机。诚实是诚实，但 $T=32$ 的结论在这两类任务上就没验过；GSM8K 全深度 .393 这个绝对水位，也谈不上「模型很强，只是被解码拖慢」。其实，论文证明的是「相对全深度不怎么掉」，不是「绝对效果好」。

**τ=0 的精确有边界**。 精确等价只在 exact arithmetic 下成立，bf16 下有 0.007%~0.09% 的 token 差异（所幸低于顺序 floor）；而且只保 greedy，温度采样要靠 speculative rejection sampling 扩展，留给后续。浅 $T=8, K=2$ 那个反例也提醒了：$\tau=0$ 依赖「乐观猜测大多对」，一旦回滚太密（12.5 次/百 token），速度会跌破 K=T 块。

**定位上，这是解码系统层面的扎实工作，不是模型底层突破**。 它没有改循环 LM 的结构，也没有提出新的推理能力；它改的是「推理时把计算放在哪」以及「怎么把省下的延迟兑现成墙钟时间」。同期 SkipDecode（非循环 Transformer 上跳底层）、Mixture-of-Recursions、Relaxed Recursive Transformers 都在做 token 级的深度路由，LoopSpec / LoopAhead / DAS 在做循环模型的投机草稿——作者把自己的位置划得很清楚：那些方法验证路径仍走满 $T$ 遍，晚进入砍的是验证路径本身。这个区分我认，但别把它读成「推翻了早退出」；准确说法是「在共享权重、按遍对齐 KV 的循环模型里，砍末尾比砍开头更划算」。

## 💡 八、工程启发，以及还没解决的那个问题

如果你在做推理引擎，有三条我觉得可以直接拿去试：

- **先查缓存深度，别只数前向层数**。 任何「提前退出 / 跳层 / 减遍」的优化，都要问一句「我给后面的 token 留下了什么质量的 KV」。早退出真正的代价不在当前 token，在被冻住的浅层上下文。
- **把反正要算的东西复用起来**。 流水补缓存算出的精确状态，本来写完 KV 就丢；塞进现有 output GEMM 就能变成一个免费的 verifier。这类「废热回收」在 decode 引擎里往往比新加一个模块划算得多。
- **误差集中度决定兜底成本**。 68% 高置信位置上晚遍一致率 1.000、误差挤在 6% 尾部——有这种分布，就值得设计一个便宜的精确路径专门盯尾部，而不是给所有 token 上重机制。

但有个更根本的问题没解决：**既然深上下文缓存这么值钱，为什么不在预训练阶段就让模型原生支持任意遍进入**？ 现在这套还得靠一次 1.9B tokens 的补丁式 SFT 把入口对齐，说到底是在给一个没为这件事设计过的模型打补丁。Huginn 的 Prelude 已经露了点苗头——架构层面自带入口归一化，连没训过的 checkpoint 都能吃到晚进入的红利。要是把 per-token 自适应遍数、入口对齐、Wake 式验证一起放进预训练目标，说不定连 Stage 2 都省了。

顺着这块再聊一句：论文报的加速比全都锚在「全深度串行解码」这个基线上，可 $T$ 越大，这个基线本身越慢（$T=64$ 时 11.1 tok/s）。8.42× 听起来吓人，折算成绝对吞吐也就是 90 多 tok/s。数字没错，但读的时候心里得有这根弦。

说实话，这类工作我最看重的从来不是那个倍数，而是它把一个「大家都这么干、没人问过为什么」的默认选项重新摆上台面。**省遍数不一定非得省开头**。 光这一句，就够我记一阵子了。
