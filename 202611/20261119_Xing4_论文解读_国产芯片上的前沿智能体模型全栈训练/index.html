把流水线并行删掉之后，285B 模型在 8192 张昇腾卡上反而更快了

TeleChat to Xing4: Advancing Frontier Agentic Models on Domestic Chips and Frameworks arXiv:2611.22115 · Xingchen AGI Lab, China Telecom · 2026-11-17 提交（v1）

你有没有碰到过这种局面：模型结构照着前沿论文抄了一遍，卡也堆到位了，可训练吞吐就是上不去，profiling 里一大段一大段的空隙全是通信和调度在浪费时间。更憋屈的是，这类坑几乎不会写进论文——大家只发模型能力、发 benchmark 分数，底层那套「怎么把几千张卡喂饱」的工程细节，通常烂在团队内部的 wiki 里。

上周翻到中国电信星辰 AGI 实验室（Xingchen AGI Lab）这份报告，我的第一反应是：哟，居然有人把这套东西整整齐齐写出来了。它不是提出某个新算法，而是把「在国产芯片和国产框架上，从架构选型、预训练基础设施到强化学习后训练，端到端跑通一个前沿智能体模型」这条链路拆到了算子、通信、甚至 CPU 亲和性这个粒度。整篇 140 位作者，附录里作者名单单独占一节，一看就是大集群工程战的产物。

最让我停下来的一个数是：他们把流水线并行（PP）整个拿掉了，285B 模型的一步训练时间反而从 36.4 秒降到 31.8 秒。这个反直觉的结果，值得好好聊聊。

核心摘要

绝大多数开源大模型都在 NVIDIA GPU 上训练，国产芯片 + 国产框架上做前沿 Agent 模型，架构、预训练、后训练整条链路都是没人系统写过的系统工程难题。这份报告把 Xing 4（星 4）系列在昇腾 910C 与 MindSpore 上整套打通：架构侧用 MLA + DSA + IndexShare 压长上下文、宽而浅的 MoE 拓扑、DSpark 推测解码；预训练侧基于 MindSpore HyperParallel 做拓扑感知的 HSDP、Owner-based Muon、细粒度选择性重计算；后训练侧抛出 TeleGym 统一执行平台。它开源了一个 29B MoE（激活 4B、原生 256K 上下文），工程研究的主力是 285B MoE（激活 17B、1M 上下文），在 8192 张 910C 上预训练。效果数字很硬：prefill 吞吐最高 4.68 倍、推测解码 2.67–3.77 倍、去掉 PP 端到端快 12.6%、CPU 绑核在 8192 卡规模带来 5–10% 吞吐提升。一针见血地说：底层算法创新有限，它更像一份把散落的工程细节系统沉淀下来的工程实录，对做训练基础设施的人信息密度极高；但相当一部分数字来自仿真，读的时候得打个折。

🎯 为什么这份报告值得聊：一个几乎没人正面回答的问题

先把问题摆清楚。

过去两年，前沿模型的架构收敛得很快：MoE 成了堆参数的默认选择，MLA 压缩 KV cache，DSA 做稀疏注意力，Muon 优化器，MTP 多 token 预测，推测解码提吞吐……这些词你在 DeepSeek、Kimi、Qwen3 的技术报告里都见过。论文自己在引言里给同期的定位也挺准：Qwen3 和 Hunyuan-A13B 盯推理成本与部署效率，Kimi K3 和 GLM-5 强调长程推理与 agent 执行，DeepSeek-V4 把百万 token 高效注意力当成核心架构目标。

但有个前提被所有人默认了——这些都是在 GPU 上跑的。换成昇腾 910C 这种「Cube 矩阵算力很强、Vector 算力和 HBM 带宽相对受限」的硬件，很多在 GPU 上最优的选择就不一定最优了。网络太深，归一化、路由、索引、调度这些非矩阵开销会把 Cube 利用率拖下来；长上下文下 decode 延迟随长度线性涨，HBM 又吃紧。再加上框架是 MindSpore，不是 PyTorch，分布式那套得自己重新搭。

说实话，这才是这篇报告真正的问题：当硬件特性变了，架构选型和系统设计得怎么跟着变，才能把前沿模型完整训出来。它不是「我们也在国产卡上训了个模型」的宣言，而是把「怎么训」这件事一条条摊开。作为一个做过分布式训练的人，我看到第 3 节那些通信时间线的时候，是真的有点被打动——这些坑我都踩过。

报告自己列了三条贡献，我用自己的话转述：面向昇腾的架构设计、协同的系统与集群优化、以及 TeleGym + 统一强化学习。下面按这条线一层层剥。

🏗️ 架构：先摸清硬件脾气，再谈选型

一句话设计原则

论文把昇腾 910C 的特性总结成一句很朴素的话：Cube 矩阵算力是强项，Vector 算力和 HBM 带宽是短板。于是架构围着三件事转——多用矩阵主导的计算、用结构优化绕开 Vector 瓶颈、用稀疏访存降低 HBM 压力。

两个具体瓶颈被点名：

  1. 长上下文推理：MLA 把 KV cache 压小了，但超长上下文里主注意力仍要访问大量历史 KV，decode 延迟随上下文长度往上涨。
  2. 硬件效率：网络过深会放大归一化、路由、索引、调度、数据搬运这些非矩阵开销，把 910C 的 Cube 有效利用率拉低。

你看，这两条都不是「模型能力不够」，而是「钱花了但没花在刀刃上」。架构章节全部围绕这两条组织。

图 1：Xing 4 系列里 285B 代表模型的架构总览。从下往上：Input Text → Tokenized Text → Token Embedding（词表 131,072、hidden 4,096）→ Dense Block ×3 → MoE Block ×42，合起来是 Transformer Layer ×45 → RMSNorm → LM Head → Logits。右侧每个 Block 是 RMSNorm → DSA → Residual → RMSNorm → FFN → Residual 的结构，前 3 层用 Dense FFN、其余 42 层用 MoE FFN。左侧单独画了 DSA + IndexShare 的跨层调度：L0–L2 是 Full Indexer，L2 算出 Top-k 索引后 L3/L4/L5 直接复用（Shared Index），每四层刷新一次索引。这张图把「前 3 层稠密、每 4 层共享索引」这两个关键设计画得很清楚。

长上下文注意力：MLA + DSA + IndexShare 三层压缩

说到这个，先补个背景，免得没跟过 DeepSeek 那一系列的朋友掉队。MLA 是 head 维度压缩——把多头 KV 投影到低维 latent，KV cache 省一大截，但每个 query 还是得看全部历史 token。DSA 是序列维度压缩——用一个轻量 lightning indexer 给每个 query 选 Top-K 个历史 KV，主注意力只在稀疏子集上算，把 \(O(L^2)\) 降到 \(O(L \cdot k)\)。IndexShare 再补一刀：稀疏索引跨层复用，别每层都重算一遍 indexer。三者作用维度不同，可以叠。

论文在 285B 模型上比了三种变体，用华为「展露」仿真框架做性能建模，P/D 分离部署、256K 上下文、32 张 910C。结果全部归一化到 MLA 基线：

MLA + DSA 0.85× 逐 DSA 层 0.37× 0.84× 2.67× 1.18×

但等等，这里得踩一脚刹车。论文自己写明：这些是基于仿真的性能建模，只刻画了主要计算、访存和通信特征，用来比相对趋势，「由于仿真没有完全覆盖生产 serving 的全部开销，报告结果可能比端到端实测更乐观」。所以 4.68 倍别当成线上部署能拿到的数，它更像一个架构方向的相对排序。我看到这种诚实标注反而有好感——比那些把仿真数当实测吹的报告强多了。

宽而浅，别深而窄

第二个选择是网络的深度和宽度。直觉上深层网络表达力强，但在 910C 上，层数越多，逐层的归一化、路由、索引、调度这些串行非矩阵开销就越多，跨层通信和调度也越重。反过来，宽而浅的拓扑把每层矩阵乘做大，Cube 喂得更饱，串行开销反而少。

论文固定住基础组件（MLA、DSA、IndexShare、混合 Dense/MoE、MTP），只改层数、专家中间维度、每 token 激活专家数，做了组对照：

推测解码 DSpark：把 drafting 做成矩阵并行

第三个选择是推理时的推测解码。DSpark 组合了三样东西：一个块级 draft 模型（5 层 DFlash backbone 并行算出 7 个投机位置的表示）、一个轻量 Markov head（通过 logit 修正抓相邻提议 token 的依赖）、一个 acceptance confidence head（估计每个位置的接受概率）。draft 模型吃 verifier 多层中间表示，把 drafting 尽量做成并行的块级矩阵计算——这又是冲着 910C 的 Cube 强项去的。主模型做 verifier，判断提议块的接受前缀。

🔧 预训练基础设施：把 PP 整个拿掉

第 3 节是这份报告最硬、也最对我胃口的部分。主角是 MindSpore HyperParallel，跑在昇腾 SuperPoD 集群上。集群是两级网络：SuperPoD 内部高带宽、低延迟，扛细粒度的权重聚合和分片梯度；跨 SuperPoD 的带宽相对有限，只走粗粒度梯度归约。这个带宽层级，是后面所有设计的物理前提。

先给一组后面反复出现的基线：性能研究用 1024 张 NPU 的 profiling 集群、285B MoE、序列长 262,144、global batch 16、TP=4 / EP=64 / CP=32。生产预训练才上 8192 张 910C。HSDP 基线一步 31.8 秒，后面三项优化都是独立地跟这个「HSDP + Muon」配置比。

HSDP：去流水线的底气，来自零拷贝 + 三方重叠

传统训几百 B 的 MoE，得把 DP/TP/EP/PP 叠起来。PP 按层切分能解显存，但躲不掉流水气泡（pipeline bubble）。论文算了个账：\(p=4\) 个 stage、\(m=8\) 个 micro-batch 时，1F1B 调度的理论气泡占比是

\[\frac{p-1}{m+p-1}=\frac{3}{11}\approx 27\%\]

也就是说，光调度空转就吃掉四分之一还多。interleaved / VPP 能缓解，但消不掉。

作者的思路很漂亮：PP 的核心价值是「按层切显存」，那如果数据并行维度就能提供同样的显存缓解——让没有哪张卡需要同时常驻所有层的完整参数——PP 就没必要存在，气泡自然归零。FSDP 就是这个哲学，参数分布式分片、每层执行前 AllGather 重建、算完 reshard 释放。

但 FSDP 直接搬到几千上万张 NPU 上有问题：sharding group 随集群变大，AllGather / ReduceScatter 频繁跨 SuperPoD，把有限的跨 SuperPoD 带宽打满、还没法跟计算完全重叠，而分片度过大带来的显存收益又边际递减。

于是他们做了 HyperParallel-FSDP（HSDP）：参数在每个 SuperPoD 内做 FSDP 分片、在 SuperPoD 间复制。频繁的权重聚合和分片梯度同步被关在高带宽的 SuperPoD 内，只有粗粒度梯度归约跨 SuperPoD。两个关键设计：

一、逐参数张量直接通信，零拷贝。 PyTorch FSDP 为了通信效率会把多个参数 flatten 到一块连续 buffer 做融合集合通信，代价是通信前 copy-in、AllGather 后 copy-out，而 copy-out 在关键路径上、没法跟后续计算重叠。SuperPoD 内带宽足够高，细粒度集合通信照样高效，所以 HSDP 干脆对每个参数张量直接做 AllGather / ReduceScatter，去掉扁平 buffer 和所有打包、copy-in、copy-out。

图 2：HyperParallel-FSDP 的反向传播工作流（Figure 2）。核心是让权重重建、反向计算、梯度同步在 SuperPoD 内的高带宽域里闭环，粗粒度梯度才跨 SuperPoD。

图 3：(1) PyTorch FSDP 把多个参数 flatten 进连续 buffer 做融合通信，引入 copy-in / copy-out；(2) HyperParallel-FSDP 直接对单个参数张量做 AllGather / ReduceScatter，实现零拷贝通信（Figure 3）。copy-out 落在关键路径上这一点，是两种设计效率差异的根子。

二、反向传播的三方通信重叠。 每层反向涉及四件事：SuperPoD 内 AllGather 重建参数、反向计算、SuperPoD 内 ReduceScatter 同步分片梯度、跨 SuperPoD AllReduce 归约梯度。朴素实现里细粒度 AllReduce 频繁且低效，ReduceScatter 和同步还部分暴露在关键路径上，层与层之间能看到明显的通信空档。

优化后的调度把三件事叠起来：算第 \(i\) 层反向时，同时重叠第 \(i+1\) 层的 ReduceScatter、第 \(i-1\) 层的 AllGather、以及跨 SuperPoD 的 AllReduce；通信同步推迟到整个反向结束。融合 AllReduce 靠预分配连续梯度 buffer、让每个 ReduceScatter 直接写进对应区间来保证连续性，不用额外打包。

图 4：HyperParallel-FSDP 的执行时间线（Figure 4）。(1) 前向：每层计算前靠 SuperPoD 内 AllGather 重建参数；(2) 朴素反向：Inter-SuperPoD 通信只部分重叠、层间有明显空隙；(3) 优化后反向：三方通信重叠，通信同步推迟到末尾，绿色计算块之间的空隙被压到最小。这张图是「zero-copy + 三方重叠」最直观的证据。

Owner-based Muon：别让每个 rank 都重算一遍完整矩阵

Muon 用 Newton–Schulz（NS）迭代对矩阵参数做正交化，这需要完整权重矩阵，天然跟分片训练打架。朴素分布式实现里，每个持有二维权重切片的 rank 都得重建完整 NS 输入、跑一遍同样的 NS 迭代、然后只留自己那片结果——完整矩阵的计算被重复做了 N 遍。冗余在「谁来做全矩阵这一步」，不在「状态怎么分」。

解法挺干脆：给每个矩阵在它的 shard group 里指定唯一一个 owner rank。非 owner 用 P2P 把 input shard 发过去，owner 拼出完整输入、跑 NS、缩放更新、留自己那片、再把其余片 scatter 回去。参数和动量始终留在原来的分片布局里，只有全矩阵计算搬到 owner。调度器还按形状、shard group、估计代价给矩阵分组，兼容形状的完整输入能沿 batch 维堆起来用 batched matmul 跑，摊薄 kernel launch 开销——但每个矩阵仍独立归一化、独立正交化，batching 绝不把不同权重拼成一个更大的 NS 问题。

原文 Figure 5 把这套机制画得更具体：四个 rank 各持一个矩阵的示意切片，选 r2 作 owner，基线里每个进程都重建并正交化完整输入，优化后只有 owner 跑一次 NS，其余靠 P2P 收发切片。参数与动量布局始终不动，只有全矩阵计算搬到了 owner 上。

细粒度选择性重计算：把它写成一个 0-1 背包

整层重算太粗：一个 layer 里所有算子一视同仁地「存或重放」，对长序列 DSA 特别亏——有些算子跑起来贵、输出却小，重放它花大算力只省一点激活显存。原生算子级 selective checkpointing 又有个毛病：每次算子 dispatch 都调一次 Python policy callback，前向一路全是 host 开销，kernel 一短就 host-bound。

他们的做法是 object-based exclusion：把算子在初始化时挂成命名模型对象的成员，用成员路径配置它是否重算。同一算子类型的不同实例用不同成员区分，贵算子放进 exclude（保存）区、周围计算仍可重放，不需要框架级 dispatch policy、也不用每次 dispatch 调 Python callback。

选择哪些算子保留，被形式化成一个 0-1 背包。对每个候选算子 \(i\) 记录前向耗时 \(t_i\) 和由输出形状/类型估出的输出显存 \(m_i\)，设 \(x_i=1\) 表示保留该输出、把它排除出重放，\(M\) 是其它训练分配之后剩下的激活显存预算：

\[\max_{x_i\in\{0,1\}}\;\sum_i x_i\,t_i \qquad \text{s.t.} \qquad \sum_i x_i\,m_i \le M\]

保留一个输出花 \(m_i\) 字节、省掉 \(t_i\) 的重放时间。目标就是在有限显存里，优先买下「重放最耗时」的那些算子，而不是给整层套一个统一策略。用伪代码表达这个选择逻辑大概是：

# 按每层 profiling 数据求解算子级重计算策略
def select_exclude_ops(profiles, budget_M):
    # profiles: [(op_id, t_i, m_i), ...]  耗时 / 输出显存
    candidates = sorted(profiles, key=lambda p: p.t_i / p.m_i, reverse=True)
    chosen, used = [], 0
    for op in candidates:                 # 贪心近似 0-1 背包
        if used + op.m_i <= budget_M:
            chosen.append(op.op_id)       # 放进 exclude 区，保留输出
            used += op.m_i
    return chosen                         # 其余算子仍可重放

（真实实现是按 profiling 数据解 Eq. 1，并配合 3.3.2 的边界处理，这里只是把「时间/显存比」的直觉写成可读形式。）

DSA 长序列训练：三招专治「等 token 不等于等计算」

第 3.4 节处理一个 TND（packed 多文档）长序列训练里很容易被忽略的事实：token 数一样，计算量未必一样。文档被 mask 掉的部分可能仍占着物理 KV 输入，辅助 indexer 图还可能长时间活着。他们沿三条边界优化。

逐层 indexer backward（收益最大）。 融合 KL 算子在前向就能返回对 indexer 投影输出的预计算梯度，显式反向把它传回 indexer 投影参数，辅助 loss 不沿 teacher 或主分支输入反传。于是辅助图能逐层消费、不用等主分支 LM backward 结束才退休；有 IndexShare 共享图时按组聚合、只反传一次。开了主分支重算时，框架自动把 Indexer 和 IndexerLoss 排除出重算、保留早反向需要的输入，用户不用手动设 exclude_op。

🤖 后训练 TeleGym：让轨迹跨过策略版本活下去

第 4 节把镜头从预训练挪到推理 / agentic 能力的强化学习后训练。这里要解决的麻烦，跟前面完全不是一类：agent rollout 的时长极度不齐——工具调用、工作区操作、奖励评估能把一个任务拖得比同批其它样本久得多；而策略模型还在不断发新版。一个长任务怎么跨过多次权重更新、还能保持轨迹连续，是真正棘手的地方。

三层架构：执行、转换、优化各管一段

图 16：统一强化学习框架（Figure 16）。左边青色是 TeleGym（轨迹执行）：各种 task harness（TeleAgent、OpenClaw、OpenCode、Claude Code、Pi、DeepSeek Harness 等）在 Sandbox 里跑，产出 Interaction 和 Outcome，底部标注 Execution & session identity。中间蓝色是 Server（interaction-to-training bridge）：Capture interactions（tokens、logprobs、versions）→ Align trajectories（context、masks、execution IDs）→ Assemble samples（rewards、complete groups），并通过 Model API 跟底部 SGLang（model generation）双向交互。右边紫色是 Slime（asynchronous RL）：Rollout manager 消费 training groups、旁边有 Surplus buffer，下接 Training actors 做 policy optimization。橙色虚线是 Policy sync：Interrupt → Update → Resume，从训练侧指回 SGLang。三层职责分得很干净。

三层各司其职：TeleGym 管异构 harness 的执行和 agent 会话；中间 server 把模型请求接到策略服务、把交互和结果转成训练就绪的轨迹；Slime 协调 rollout 调度和策略优化；SGLang 负责生成。数学任务走直接 rollout + 答案判分，代码任务走可执行测试，通用 agent 任务支持自动 / 模型 / 混合评估。

server 这层有个设计我觉得挺关键：它记录采样 token、behavior-policy 的 log 概率和策略版本，对齐 context 与 response token、生成 token mask、把打分后的执行组装成 training group。对多轮任务，一个 execution 可能产生多个训练片段，但仍算一次独立尝试，所以 group-relative reward 在「同一 prompt 的 execution」这一层处理，再传播到片段——防止调用模型次数多的任务被当成额外的 attempt 混进 group 统计。只有被确认的任务结果才进 group，缺分或评估失败跟「有效但失败」严格区分开。做过 RLHF 的都知道，这种「一个 episode 多段、按 episode 算 baseline」的细节，漏了就会悄悄把优势估计算歪。

图 17：TeleGym 平台架构（Figure 17）。任务引擎经编排层连到 batch / interaction 两类引擎，编排层容纳 black-box 与 white-box 两类 agent adapter，资源访问层下面挂 Sandbox 与会话管理。它把数据合成、评估和 RL 三条需求压到同一套执行机制上。

TeleGym 本身四个面向：任务侧执行（batch 编排 vs interactive 编排共用一套 episode 生命周期）、harness 无关编排（black-box 接外部 harness、white-box 接原生/自定义 agent，runtime adapter 翻译动作、归一化结果）、沙箱与会话管理（runtime 绑沙箱上下文、备好工作区与依赖，跨 action 保留 session，工件在清理前可供评估）、以及跟训练循环的集成（episode 级关联元数据把环境侧执行连到 server 的 token 级轨迹）。任务合成（4.3）也复用同一套执行接口：general agents 围绕信息检索 / 文档处理 / 工具使用，code agents 围绕软件项目的实现与改 bug，多个 harness 一起提案、独立验证、再去重。

异步训练与 partial rollout：三个边界解耦

4.4 是这节的硬核。作者把三件事明确拆开：任务完成、训练 batch 组装、新策略发布。一个长任务因此可以跨多次策略更新，不要求所有并发任务一起收尾。

  • Disaggregated execution：生成和策略优化跑在独立设备池，推理服务常驻，trainer 更新时 rollout 管线能继续备下一批数据，凑够「完整、已打分」的 group 就开训。策略发布是训练池和推理池之间一个显式的协调点。
  • Bounded oversampling：调度器授权比下一批所需更多的 rollout 工作，好让晚完成或被奖励过滤掉的 group 有替补；有限 lookahead 窗口 + pending/ready group 上界，防止快生产者或慢消费者堆出无限 backlog。超额的已完成 group 留到后续更新用。
  • 策略发布与轨迹续跑：发布时控制器暂停新请求准入、中断在途生成、等模型执行到安全同步边界，再换权重、推进 policy version、重开准入。未完成的轨迹保留 execution identity 和进度，同步后恢复——对多轮 agent，这保住了「早先的回复、工具交互」和「新策略下的后续调用」之间的关联。同步边界管的是模型执行，不是整个 agent 会话的结束；中断本身既不分配 terminal reward，也不让未完成前缀变成可训练样本。

图 18：partial rollout 与异步训练（Figure 18）。顶部时间轴分三段：Concurrent rollout & training → Policy sync → Resume & continue。一条 Long trajectory 在 policy k 下 Generate，到 sync 处 Retain progress 暂停，在 policy k+1 下 Resume & continue；Group A 完成进 ready buffer 支撑 Update k+1，Group B/C 作为 surplus 被保留，B 在 Update k+2 才被消费，右侧还有 New rollouts。紫色是 Policy trainer，橙色虚线是 Publish weights。这张图把「轨迹跨版本存活、surplus 缓冲」讲得很直观。

策略滞后单独处理：恢复的轨迹和缓冲 group 可能含旧策略生成的样本，每个生成段保留采样时的 log 概率，作为优化时重要性比率里的 behavior-policy 概率——用新权重重算概率不替换这份记录。可选的 stale-data filtering 按观测到的策略版本整组剔除旧轨迹（保住 group-relative reward 的成员关系），是 trajectory 级启发式，不是严格的 token 级年龄界。checkpoint 时还要把数据生产/消费状态、execution identity、版本元数据先落盘再存模型和优化器状态。这一整套，说到底是在「异步吞吐」和「on-policy 正确性」之间找平衡，而且把每个妥协点都标出来了。

📊 连主机 CPU 都没放过

第 5 节是我一开始没料到会写进论文的部分，但想想又很合理。主机 CPU 负责数据处理、任务提交、通信调度；一个关键 host 线程一旦等不到 CPU 时间，就可能晚提交算子、晚到达集合通信，延迟再扩散到别的训练进程。集群越大，这种抖动越致命。

他们用两招：CPU pinning（设线程亲和性）和 core isolation（把系统服务、日志监控、可移动 IRQ 处理挪到训练 CPU 池之外的独立池 H）。粗粒度 pinning 是一个 device 一个进程、线程共享该 device 池；细粒度按角色分区。论文给了 device 0 的具体划分：共 28 个逻辑 CPU \(\{8,10,12,14,16\text{–}39\}\)，细粒度下 PyNative 拿 \(\{8,10,12,14\}\)、MindData 拿 16–23、Main 与 runtime/支持线程拿 24–39。还反复提醒要核对 NUMA 拓扑、SMT 是否开启、cgroup v2 的 cpuset.cpus.effective，内存绑定要跟 CPU 亲和性分开配。

💡 我的判断：它到底是个什么定位

把整篇合上，说说我的看法。

先说它值钱的地方。 这份报告真正的贡献不是某个新算法，而是系统性地把「国产算力训前沿模型」这条链路拆到了别人不写的粒度：从架构怎么迁就 Cube/Vector 比例，到 HSDP 零拷贝 + 三方重叠怎么让 PP 彻底下岗，到选择性重计算的 0-1 背包建模、逐层 indexer backward 的 15.2%，再到 TeleGym 让轨迹跨策略版本续跑、以及 CPU 绑核那 5–10%。这些细节在别家报告里基本是黑盒。对做训练基础设施、做国产芯片适配的工程团队，它的信息密度比一堆刷榜论文高得多。而且作者几乎每报一个数都附带边界条件——「仿真可能偏乐观」「不是零显存代价」「不是 bitwise 等价」「三层收益别加两遍」——这种克制在工程报告里相当罕见。

再说让我皱眉的地方。

第一，数字口径得擦亮眼睛。最吸睛的 4.68× prefill、深度-宽度那组 1.20×，都来自「展露」仿真框架的性能建模，不是端到端 serving 实测；作者自己认了可能偏乐观。真正落在实测 step time 上的，是 Table 7–11 那一串 31.8s → 24.5s。两类数字别混着用。

第二，没有模型能力的主实验表。整篇看不到 MMLU、GPQA、SWE-bench 这类能力分数，也没有跟同级模型的横向对比。它是一份 design / systems report，不是「我们模型多强」的成绩单。想判断 Xing 4 到底处在什么能力档位，这篇给不了答案——开源了 29B 权重，得自己跑。

第三，三项系统优化是独立对比、不是叠加连乘。Table 8/10/11 每一项都单独跟同一个 HSDP + Muon 基线（28.9s）比，把 9.1% + 6.9% + 15.2% 直接相加会高估端到端收益。论文反复强调这点，读者别自己脑补。

第四，很多设计是对既有思路的迁移与工程整合，不是从零发明：MLA/DSA 来自 DeepSeek，IndexShare 是跨层索引复用，Muon、MTP、DSpark/DFlash 都是引用外部工作，HSDP 建在 FSDP 之上。论文的功劳是把它们按昇腾硬件特性重新选型、并把分布式执行自己实现了一遍。这没什么可指摘的，但别被「首个」之类的字眼带跑——它本来也没这么宣称。
