# 用户改了口、镜头转了个角度，Agent 却还在按旧脚本点鼠标：EgoUseBench 把"变化"本身做成了考题

你有没有碰到过这种事：让助手帮你把"这个"加进购物车，它照着第一眼看到的包装选好了，你随口补一句"再加点酱"，镜头一转，画面里露出的其实是另一款包装。这时候正确的做法不是再点一次"加入购物车"，而是回头把刚才那件撤掉，重新判断哪件才对。

人做这件事几乎不费劲。Agent 做起来会翻车，而且翻得很隐蔽——界面上每一次点击都成功了，购物车里也确实多了东西，只是最终状态和你的真实意图对不上。

EgoUseBench 就是冲着这个缝隙来的。

---

## 🎯 核心摘要

一篇把「执行过程中信息会变」当成一等公民的基准论文。作者从超过 74 小时真实第一人称录像里造出 693 个任务，把 Computer-Use、Offline Ego Use、Online Ego Use 三种设置放在同一批任务上对齐比较，还把变化拆成 Graft（用户改需求）、Refresh（新画面推翻旧判断）、Clarify（智能体主动问）三类，分别追踪第一人称观察、用户需求、网站状态这三条状态线。六个先进模型跑下来，Computer-Use 平均成功率 86.1%，Offline Ego Use 64.2%，Online Ego Use 63.4%，Online 相对 Computer-Use 低 26.3%。我的判断：这不是新模型、新算法，是一套做得很细的评测基础设施与诊断报告；最值钱的地方是把"新旧选择叠加"这个失败模式量化出来了，但那个 26.3% 该怎么读，得拆开看，别被标题带走。

## 🤔 一、为什么"先看一遍录像"根本不够

先说一个我自己的经验。之前调一个带视觉输入的浏览器智能体，任务是从截图里认出商品再下单。单轮跑得挺漂亮，一旦允许用户在中途追加一句话，成功率就往下掉，而且掉的不是"没听懂新要求"——它听懂了，新东西也加了，就是没删掉旧的。购物车里两件并存，评测器判失败，日志里每一步却都是合法操作。

这类错误的名字叫"状态没跟上意图"。传统基准测不出来，因为它们的世界是静止的。

Computer-Use 这一脉的评测做得很扎实：Mind2Web 铺了大规模网页任务数据集，WebArena 用四个自托管应用做执行式评估，VisualWebArena 把图像理解加进来，OSWorld 把桌面应用和跨应用流程拉进来。这些基准的共同前提是目标由用户一次性给全，反馈只来自数字环境（几家公开榜单汇总的数据里，WebArena 发布时最好的 GPT-4 Agent 是 14.41%，OSWorld 发布时最好模型 12.24%，人类分别约 78.24% 和 72.36%；数字来自公开基准榜单整理，不是这篇论文的实验）。前提一变，题目就不一样了。

第一人称这条线也在往前走。Ego4D、EgoLife 做长时程活动理解，Ego2Web 把预录好的第一人称视频和真实网页操作绑在一起，EgoBench 加了工具调用和多轮交互；流式这边，EgoSAT 测时序推理，Vinci2 与它的 EgoServe 基准测"该不该主动开口"，ProactEgoMem 盯状态跟踪，OmniAssistBench 看多轮多模态对话。这些工作要么把视觉证据一次性给全，要么只要求理解和提醒，不要求把网页状态一路改到正确。

EgoUseBench 卡在中间的空档：观察在流、意图在变、已经点过的按钮还留着痕迹。

作者在引言里给的场景特别具体：用户一边做零食一边说"把我用的这种玉米饼加进购物车"，镜头只拍到包装的一角，产品其实不确定；接着用户说"再加个抹酱"；再往后，新画面显示先前选的玉米饼跟手里拿的并不是一回事。三件事分别对应三层能力——从不完整画面里定位目标（Context Grounding）、把追加的话接到同一个任务上（Intent Continuity）、发现旧选择作废并回头改（Execution Adaptation）。

第三层才是真麻烦。新信息会改变"什么样的终局算对"，却不改变网站当前的状态。写成式子就是：

$$\mathcal{G}^{-}\to\mathcal{G}^{+},\qquad x\ \text{不变}$$

$\mathcal{G}^{-}$、$\mathcal{G}^{+}$ 是更新前后可接受的目标状态集合，$x$ 是网站状态。目标集合换了，购物车里那件东西还在。基准的全部设计，差不多都是围绕这个不对称展开的。

| 基准脉络 | 视觉证据何时给 | 用户需求会变吗 | 主要考什么 |
| --- | --- | --- | --- |
| Mind2Web / WebArena / OSWorld | 不给物理场景 | 一次给全 | GUI 定位、规划、数字执行 |
| Ego2Web / EgoBench | 执行前整段预录 | 基本固定 | 第一人称视觉落地到网页动作 |
| Vinci2 / EgoServe、EgoSAT 等 | 持续流 | 以理解与提醒为主 | 时序推理、主动介入、记忆 |
| EgoUseBench | 执行中按步投递 | 按时间表改，且可主动提问 | 新旧信息下网页状态的持续对齐 |

*表 1：几条评测脉络的差别。前两行依据公开基准资料整理，后两行依据原文第 2 节与附录。*

## 🏗️ 二、把"演化"做成可测的东西

### 三级设置，一张图讲清

![图 1：三种交互设置的对比](https://arxiv.org/html/2611.34466v1/strategy.png)

*图 1：论文 Figure 1。左侧 (a) Computer-Use 只有显式指令，Agent 与 GUI Env 之间来回传动作和截图；(b) Offline Ego Use 多了一叠"Pre-recorded video"，录像在执行前一次给全；右侧 (c) Online Ego Use 按 $t_0$、$t_1$、$t_2$ 连续投递第一人称画面，用户话语从 $u_0$ 走到 $u_0$ 再到被改写的 $u_1$（revised），三行橙色标签正好对应 Context Grounding、Intent Continuity、Execution Adaptation。图里那个红色的 revised 框，是整篇论文的题眼。*

三种设置的差别只在"第一人称上下文什么时候可用、会不会变"。Computer-Use 拿显式指令；Offline 在执行前拿完整录像；Online 边执行边收画面，用户意图还会中途改写。网站、起始状态、可用动作、步数上限、最终判分标准全都不动——这个"其他一概不变"的配对设计，是后文所有结论能站住的前提。

### 三条状态线，三类变化

数据规模：693 个任务，来自超过 74 小时真实第一人称录像。拆开是 293 个 Online Ego Use 任务（200 个主集 + 93 个组合任务）、200 个 Offline、200 个 Computer-Use。后两组是同一批任务、同一批网站、同一批终局的匹配版本，不是另外采集的新题。

主集 200 个 Online 任务按变化方式分：142 个 Graft、30 个 Refresh、28 个 Clarify；另有 93 个把三类混合起来的组合任务。任务形态覆盖商品挑选、教程检索、地点收藏，主集里分别是 82 个购物、117 个教程检索、1 个地点收藏——这个分布后面我还要吐槽。

素材来自 Ego2Web、CaptainCook4D、HD-EPIC、EgoOops、EgoLife、HoloAssist、EgoSchema 七个公开数据集，附录 Table S1 给了明细：Ego2Web 贡献 132 个，CaptainCook4D 和 HD-EPIC 各 28 个，其余零星。三类变化的定义值得逐字看：

- **Graft** 改的是用户要求，细分 Refine（调属性或数量，73 个）、Augment（加条件但保留旧的，47 个）、Replace（换掉某个选择，14 个）、Drop（撤回要求，8 个）。
- **Refresh** 不改措辞，只给新画面。Replace 子类的新证据会推翻先前选择（15 个），Retain 子类的新证据不改变答案（15 个）——这一对设置得很巧，能区分"真的用了后面帧"和"碰巧一直对"。
- **Clarify** 是智能体主动问。开场画面里存在多个说得通的指代对象，固定回复用空间位置（Position，12 个）、时间顺序（Sequence，11 个）、可见属性（Variant，5 个）来消歧，且不直接点名网站上的商品。

说实话，Refresh 里那个 Retain 子类是我觉得最见功力的地方。它专门用来抓"模型看到新画面就手痒改答案"这种过度反应，后面消融里 DeepSeek 在这上面吃了亏，正好印证。

网站是本地仿真的 Amazon、YouTube、Google Maps，用公开的条目信息重建界面，检索用 BM25 排公开字段，目录规模是 11,660 个商品、16,389 个视频、289 个地点。每个 episode 从隔离的初始状态开始，动作效果一直留着。评分只认终止时的网站状态：

$$N(x_T)\in\mathcal{G}$$

$N(\cdot)$ 把购物车、收藏列表这类状态归一化成"选了哪些实体、各多少、必填字段是什么"，忽略展示顺序，把登记的等价包装换算成要求的单位。中间点错没关系，终止前改回来照样算成功；中间点对了但没删掉过期的，照样算失败。这个判分规则看着简单，恰恰是把"新旧选择叠加"钉死的关键。

### 一步里到底喂了什么

![图 3：单步输入与三种视觉历史策略](https://arxiv.org/html/2611.34466v1/figures/input_design.png)

*图 3：论文 Figure 3。(a) 每个决策步 Agent 同时拿到三样东西：第一人称画面（8 秒源视频、1 fps、四帧拼一张 JPEG）、当前网页截图（含无障碍树）和按投递步标注的用户原话；(b) 三种历史策略对比——Opening 批次与 Latest two 批次三种条件都完整保留，变的是 Older batches：Full 保留每帧，Compressed 抽到 0.5 fps（默认），Summarized 换成智能体自己写的短文本。横轴是投递顺序。*

节奏是固定的：每个有效动作步推进 8 秒源录像，与模型延迟无关；录像不循环；主评测最多 20 步，组合任务 30 步。Graft 的追加请求按审阅过的 onset 跟着批次到，Refresh 的变化跟着后面的场景到。还有个容易被忽略的细节：如果 Agent 在追加请求到达前就宣告完成，episode 进入 standby，请求到达时带着同一份网站状态把执行唤醒，standby 不耗步数——这就是后面 Arrival 消融里 Wake-up 条件的由来。

![图 2：EgoUseBench 全流程概览](https://arxiv.org/html/2611.34466v1/method_overview.png)

*图 2：论文 Figure 2。左栏是任务构造与校验（Ground a request → Graft/Refresh/Clarify 标注 → 构造目标集合与冻结网站 → 程序检查、回放窗口复核、保存反例、人工复核）；中间是 One Ego Use Episode 的 step 1 到 step 7，每步 8 秒画面，初始请求是"加一包我抹在玉米饼上的酱，要不同牌子"，step 4 追加"再加一罐 2kg 装的顺滑酱"，购物车从空 $x_0$ 走到 $x_1$ 再到 $x_2$；下方 Three Sources of Task Change 把 Graft（keep A, drop B, add C）、Refresh（后帧把炒卷心菜换成鸡蛋面食谱）、Clarify（"蓝包装旁边那颗糖，左边还是右边？"）各举一例；右栏是 Final-state Check，用归一化的 $N(x_T)$ 匹配 12 个可接受购物车之一，并列出 update ignored、item dropped、wrong item 等失败样例。*

防捷径这块做得比一般基准认真。校验分三层：可接受结果集合人工核对（等价包装、最小容量、数量换算都编进可执行目标）；信息捷径检查——把录像或某次更新拿掉，看剩余输入是否还能唯一指向某个答案，能就直接判为有捷径，改请求或换素材；再让一个独立的 Coding Agent 在看不到拟定答案的前提下先写一遍解法，然后查覆盖与捷径，语义上拿不准的交人工。两名独立评审在 40 个分层抽样任务上各自接受 95%，双方都接受 90%。开发期用 Qwen3.5-Flash 做纯文本捷径测试，与正式评测的模型分开。

我的第一反应是：这套流程比不少"造题 + 跑分"的基准多走了一步，至少承认了"题目可能不用看视频也能做对"这件事。

## 🧪 三、实验：数字摆出来，再说说哪些数字别急着信

模型是六个：GPT-6.1 Terra、Gemini 3.8 Flash、Doubao Seed 2.1 Pro、DeepSeek-V4.1-Flash、Kimi K2.6、qwen3.5-27b，共用 BrowserGym 的 JSON 动作接口；另外补了一个 UI-TARS-1.5-7B。主评测每个模型 200 个 Online 任务、每任务每条件跑一次、最多 20 步，Overall 对任务等权，配对比较用 2,000 次按录像分层的 bootstrap 给 95% 区间。

范围从 39.0% 到 87.0%，跨度快 50 个点。多数模型 Graft 比 Refresh 高，也就是"用户明说改了什么"比"自己从新画面里悟出旧选择作废"容易。Kimi 在 Refresh Replace 上只有 6.7%（15 个里成 1 个），这个数我看到时愣了一下。另一个反常识的小点：qwen3.5-27b 总体 41.0% 跟 Kimi 的 39.0% 贴得很近，Clarify 上还反超 DeepSeek，参数量却小得多——能力跟规模在这张表上没有单调关系。

UI-TARS-1.5-7B 三个设置全 0/200，轨迹里全是不支持的动作名、非法元素 ID 和格式错误的回复。作者自己在附录里说清楚这是共享 JSON 接口不兼容，不是原生适配器下的能力结论。这点我给好评，没拿它凑"小模型不行"的叙事。

*表 3：前四列来自原文 Table 2（同一 200 任务的三种设置）；后两列来自附录 Table S9 的配对 SR 差值与 95% 区间。附录 C.2 明确写了：从未四舍五入的均值算，Online 相对 Computer-Use 的相对降幅是 26.3%，相对 Offline 是 1.2%。*

先把算术摊开：86.1 减 63.4 是 22.7 个百分点，22.7 除以 86.1 约等于 26.3%。所以 26.3% 是相对降幅，不是"低了 26.3 个点"。更重要的是，Offline 到 Online 只掉 0.8 个点，六个模型的配对区间全都跨 0，Terra 甚至反向涨了 3.0 个点。

这就是我要挑的第一处：**在线演化本身带来的额外难度，在这套实验里几乎没被测出统计上的差异**。26.3% 的大头来自"要不要读第一人称录像"这道跨模态落地关，而不是"边执行边变"这道关。论文自己的消融也佐证：Online 里最难的是 Refresh Replace（新画面推翻旧选择），可这类任务在 Offline 设置里同样难，因为完整录像一次性给全反而更难定位哪一帧有效。标题党一点的说法是"Online 比 Computer-Use 差 26.3%"，准确的说法是"把物理场景接进网页任务，成功率从 86.1% 掉到 64% 上下；再让信息边执行边到，几乎没有额外损失"。这两种表述给人的产品判断完全不同。

还有一处公平性问题：Computer-Use 拿到的请求是"已解析的最终需求"文本，且禁用提问——作者明说了，这个设置直接把最终要求写清楚，不含网站答案标识也不含动作序列。它不是同等信息量的对照组，而是一个信息上界。拿它当分母算降幅，量到的是" oracle 指令 vs 含糊的第一人称线索"的落差，不完全是"演化上下文"的代价。这个 baseline 选得有点巧妙，读的时候得心里有数。

话说回来，配对设计里有一段我挺喜欢的：相近的总分可以藏住完全不同的题。qwen3.5-27b 在 Offline 成 83 个、Online 成 82 个，看起来几乎持平，但 200 个任务里有 53 个结果翻了向（27 个从成变败、26 个反过来）；Kimi 是 23 输 20 赢。只看均值会以为模型稳定，看配对才知道它在乱换答案。这种"均值掩盖换分"的分析比多刷几个点有价值。

| DeepSeek | 178.2 | 347.3 | 290.2 | −16.4% |
| Kimi | 84.2 | 328.3 | 226.8 | −30.9% |
| qwen3.5-27b | 132.6 | 425.5 | 288.6 | −32.2% |

*表 4：原文 Figure 4(b) 的每任务平均总 token（千），成功与失败的运行都算在内。*

Online 比 Offline 少用 16.4% 到 38.0% 的 token。别急着当成"在线更省"，附录 D.2 讲得很直白：省下来的主要是输入侧——Offline 每个决策步反复塞整段录像，Online 分批投递且把老批次压到 0.5 fps；输出 token 各模型有涨有跌。浏览器操作次数也没少，Kimi 还更多。所以这是上下文管理的账，不是推理效率的账。

### 消融一：追加请求什么时候到（Arrival）

| 模型 | Concurrent（执行中到达） | Wake-up（先完成再唤醒） |
| --- | --- | --- |
| Terra | 89.8 | 81.6 |
| DeepSeek | 73.5 | 53.1 |
| Kimi | 44.9 | 29.6 |

*表 5：原文 Table 3(a)，同一 98 个 Graft 任务，20 步预算相同、网站状态都保留。*

三个模型 Concurrent 全赢，DeepSeek 差 20.4 个点。附录 Table S10 把原因挖出来了：Concurrent 成功而 Wake-up 失败的配对里，DeepSeek 有 26 组，其中 20 组是"找到了正确的新答案，但留着旧选择没删"；Terra 是 10 组里 5 组，Kimi 是 24 组里 11 组。有个具体例子：Wake-up 下 DeepSeek 先存了"熨 T 恤"教程，用户改口要"熨斗怎么用"，它在第 9 步存对了新教程，第 10 步就收工，第一个教程还挂在收藏里；Concurrent 下只存对的那一个。

看到这段我有点兴奋，也有点皱眉。兴奋的是它把"没有撤销动作"这个工程 bug 变成了可复现的量化结论；皱眉的是 Wake-up 的平均送达步数是 8.50 / 8.09 / 7.18，Concurrent 才 2.49，唤醒后剩下的步数天然更少，虽然作者举了"步数还有富余"的例子，两个变量还是缠在一起。说实话这块我也不是特别确定该扣多少，单独控制"送达后剩余步数"会更干净。

### 消融二：老画面怎么留（Retention）

| 模型 | Full（全帧） | Compressed（0.5 fps，默认） | Summarized（智能体写摘要） |
| --- | --- | --- | --- |
| Terra | 85.1 | 89.4 | 85.1 |
| DeepSeek | 57.4 | 63.8 | 48.9 |
| Kimi | 42.6 | 36.2 | 48.9 |

*表 6：原文 Table 3(b)，同一 47 个任务（34 Graft、9 Refresh Replace、4 Retain），只改历史表示，帧采样与投递节奏不变。*

"更多视觉历史不一定更好"这句话有了数据，但得加个限定：Summarized 条件要求模型在批次还可见时自己写描述，等老批次移出窗口后拿描述顶上。附录 Table S11 后面的统计挺扎心——最终请求里至少缺一条老批次描述的情况，Terra 是 0/47，DeepSeek 36/47，Kimi 41/47。也就是说 Summarized 的成绩里混进了"模型会不会按要求写记忆"这项能力，不只是"摘要好不好用"。有个例子：DeepSeek 把倒进壶里的豌豆写成深绿色叶子，丢帧后一直找菠菜食谱，两份都没存；用 Full 历史时第 9 步就切回豌豆，两份都存对。

摘要把早期误读固化下来，原始帧被删掉后就没法翻案。这条对做长程视觉智能体的人是个很实在的提醒。

### 消融三：给不给场景变化提示（Cue）

| 模型 | Silent | Cued（加变化提醒） | Cued + facts（再加核实过的场景描述） |
| --- | --- | --- | --- |
| Terra | 83.3 | 86.7 | 86.7 |
| DeepSeek | 43.3 | 50.0 | 56.7 |
| Kimi | 26.7 | 26.7 | 30.0 |

*表 7：原文 Table 3(c)，同一 30 个 Refresh 任务（15 Replace、15 Retain），图像与投递时间固定。*

提醒本身涨得有限，补了文字描述整体再涨一点，但结构上有反噬。附录 Table S13 里，DeepSeek 从 Cued 到 Cued + facts 在 Replace 上 +33.3 个点，在 Retain 上 −20.0 个点：描述说"用户把蓝白衬衫放到一边、拿起红黑那件"，它就跟着换目标，可用户问的衬衫压根没变。视觉变化不等于意图变化，模型把两件事粘一块了。还有个更细的干扰：Cued + facts 下 Terra 有个金枪鱼食谱任务在第 5 步就终止，第 12 步的更新根本没送到，配对差值里混进了"跑得够不够久"。

### 消融四：多类变化叠在一起（Composite）

| 组合 | 任务数 | Gemini | DeepSeek |
| --- | --- | --- | --- |
| Refresh + Graft | 25 | 76.0 | 56.0 |
| Clarify + Graft | 25 | 92.0 | 44.0 |
| Clarify + Refresh | 21 | 61.9 | 23.8 |
| Clarify + Refresh + Graft | 22 | 77.3 | 36.4 |
| Overall | 93 | 77.4 | 40.9 |

*表 8：原文 Table 4，30 步预算，两模型共用任务、网站、观察窗口、更新时刻。*

Gemini 77.4% 对 DeepSeek 40.9%，差 36.5 个点，比主集里 76.0% 对 62.5% 的差距大得多。附录里那句诊断挺关键：智能体会对新信息作出反应，却把早先的指代悬着不管——可能选中新露出的东西却没解决最初指的是什么，也可能去找改后的目标却留着过期的选择。"响应了更新"和"完成对齐"是两件事。

### 消融五：请求改得越多越难吗（原文 Figure 5）

这个问题问得挺反直觉，答案也反直觉：不一定。作者用 46 对任务、每版跑三次，25 对把两个请求合并成一个（原本请求更多），21 对插入一个中间请求（变体请求更多），录像、网站、澄清规则、最终目标、末次更新的时刻、步数预算全部固定。插入组在所有比较里均值持平或更高，拆开两次请求则有涨有跌，有些差异在重复运行里直接翻符号。

原文 Figure 5 画的是 46 对任务的组内 SR 差（填充点是三次运行均值、误差棒是按录像分层的 95% bootstrap 区间、空心点是单轮差值，C/R/G 分别指 Clarify/Refresh/Graft）。附录 Table S17、S18 给了底数：三源插入组 Gemini 的三轮 more − fewer 是 −14.3%、+28.6%、−14.3%，Clarify + Graft 插入组 DeepSeek 是 +28.6%、+14.3%、−28.6%；92 个任务版本里 Gemini 有 17 个、DeepSeek 有 24 个在三次运行里既成过也败过。

方差大到这个程度，单次跑分的结论就得打折。额外一次请求有时逼着模型回头修正（Gemini 第 9 步收到"五分钟以内"的限制，把 6:48 的规则视频删掉换成 1:41 的讲解），有时被套到错误对象上（DeepSeek 收到"玻璃材质"就去找玻璃水壶，却没问用户说的是哪个物件）。同一机制，两种结果。

### 失败都败在哪（原文 Figure 6）

作者拿 604 条已标注失败轨迹（Terra、DeepSeek、Kimi、qwen3.5-27b 在三种设置下）做归因，用 gpt-6-luna 判、人工兜底，五类底层错误归到三大挑战下。Computer-Use 的失败里 Linking（选中的网页条目跟要求冲突，或明确拒掉了兼容候选）占 90.2%；Kimi 和 qwen 在两种 Ego Use 设置里都以 Linking 为主，占它们 Online 失败的 50.0%。Terra 和 DeepSeek 反过来，Intent（锁定一个没解决的指代，或明确照着过期要求做）是主因，占两者 Online 失败的 45.7%。State Control 与 Verification 合起来只占 Online 失败的 9.2%。

这个 9.2% 别误读成"执行适配没问题"。作者另外统计：六个主模型里，14.6% 的 Graft / Refresh 更新送达时，网站恰好满足初始请求、却需要改动才能满足新请求；1,019 条收到更新的 Online 运行里有 149 条处在这个状态，其中 107 条最终改对、42 条失败。也就是说机会是有的，失败集中在"找到新答案但没删旧答案"。

还有一组让我停下来的数字：附录 Table S14 复核了 78 个最终判成功的 Online Clarify 运行，其中 69 个在做出最终选择时，仍有两个以上说得通的指代需要不同的网站条目——引用根本没消歧，只是选对了。Table S15 里各模型在 28 个 Clarify 任务上主动提问的次数少得可怜（Terra Offline 2 次、Online 1 次，多数模型是 0）。评分器奖励结果，不奖励过程，于是"蒙对"和"对齐"长得一模一样。论文自己在附录里点破了这一点，没藏着，这点我认可。

## 💡 四、我的判断：值不值得花时间读

**先把定位摆正**。这不是底层能力突破，也没有新训练方法，是一份基准设计 + 诊断报告。放到同期工作里看，Ego2Web 已经把第一人称视频接到网页任务，Vinci2 / EgoServe 已经在做流式主动服务，所以看到"first to introduce Ego Use"这类表述我会本能地警觉。真正的新增在两处：把执行中的信息变化做成受控变量（三条状态线分离、三类变化、配对任务版本），以及把"新旧选择叠加"这个失败模式从轨迹里挖出来。属于评测基础设施层面的扎实推进，不是能力层面的跃迁。

**最值钱的三点**。一是终局判分配合轨迹复核，中间错误允许自我纠正，逼着模型对"状态"负责而不是对"动作序列"负责；二是 Refresh 里 Replace / Retain 这一对镜像条件，能抓过度反应，也能抓迟钝；三是防捷径流程，独立 Coding Agent 先做题、纯文本捷径测试、双人复核 90% 一致，比常见的"造完题就跑分"扎实。

**我保留意见的地方，攒一攒说**。Computer-Use 是解析后最终需求构成的信息上界，拿它做分母会把"跨模态落地"的落差算到"演化上下文"头上；Offline 与 Online 配对区间全跨 0，"在线"的独立代价没被分离出来；网站是冻结的本地仿真加 BM25，跟真实电商、视频平台的动态与噪声差得远；主集 200 个任务里 117 个教程检索、82 个购物、只有 1 个地点收藏，任务形态偏得厉害；693 这个数里有 400 个是匹配对照版本，Online 两侧的独立录像其实只有 214 段；Clarify 的固定回复只测"问不问"，不测"会不会问"和"听不听得懂答"；多数结果单次运行，Figure 5 那三轮一反转就说明方差不小；失败归因依赖一个 LLM Judge 加人工兜底，标签分布难免受 Judge 口径影响。还有个可复现性的小坑：模型走服务接口，附录里 DeepSeek 的具体版本写成 DeepSeek-V4.1-Flash-1017，UI-TARS 的 0 分也源于接口不适配，跨模型横比时要记住它们不在同一条起跑线上。

说实话，这些毛病大多数是"基准类论文的固有代价"，不是这篇做砸了。受控实验要固定网站、固定录像、固定投递时刻，就得牺牲一点真实感；要配对比较，就得造变体，任务计数看着会比独立场景多。真要挑一个我最想让后续工作补上的，是把"Online 相对于 Offline 的独立效应"真正做出来——现在这套设计里，它几乎是 0，可产品直觉明明告诉我们流式上下文会持续制造麻烦。可能的解释是 Offline 一次性给完整录像反而更难（信息过载抵消了在线的劣势），也可能是 20 步预算和 standby 机制太宽容。这个方向我自己也还在摸索，可能理解有偏差，但觉得值得追。

**放到产品里怎么用**。如果你在做带视觉输入的浏览器智能体，有几条能直接搬：把"新信息到达"实现成一个显式事件，触发对既有状态的重评估，而不是往动作队列里追加一条；给每个选择绑上它是被哪一帧、哪句话支持的，证据过期就撤销，撤销比追加难得多，得专门设计；视觉历史别轻易丢原始帧，Summarized 那种"记忆缺失锁死早期误读"的坑很实在；歧义检测要跟具体指代绑定，别让提问退化成一个固定回复的装饰；评测同时看最终状态和轨迹归因，只记一个成功率会漏掉"分数没变、答案全换"的假稳定。

一小段伪代码，把重评估这件事写成工程约束：

```python
def on_new_information(event, state, decision_log):
    # event: Graft / Refresh / Clarify reply
    affected = [d for d in decision_log if d.supports(event.referent)]
    for d in affected:
        if not still_valid(d, event):
            state.revoke(d.entity)       # 先撤销，别叠加
    goal = resolve_goal(event)           # 重算可接受终局集合
    return plan_toward(goal, state)      # 再规划，而不是重跑整条轨迹
```

这段不是论文给的，是顺着它的失败分析写的。四行里最难的是 `still_valid`：要判断新画面是否推翻旧证据，恰恰是 Refresh Replace 上 Kimi 6.7%、DeepSeek 53.3% 这些数字指向的缺口。

回到开头那个厨房场景。这篇论文给出的答案有点让人不舒服：最先进的模型不是不会点鼠标，也不是看不懂截图，它们是在"世界变了但界面没变"这件事上缺少一次回头。购物车里多出来的那件旧商品，就是全部问题的缩影。

想把它修好，光堆模型规模大概不够，得让智能体学会对自己的历史动作负责。EgoUseBench 没给出解法，但它把这道考题摆到了桌面上，还把评分标准写得挺细。冲这一点，值得读一遍原文，尤其附录 C 和 E——比主文好看。
