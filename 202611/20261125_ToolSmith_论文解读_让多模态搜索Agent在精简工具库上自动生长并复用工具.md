# 工具库冻住了，Agent 就该认命吗？聊聊让搜索智能体自己造工具、自己验收、自己复用的 ToolSmith

你有没有碰到过这种憋屈：线上跑着一个多模态搜索 Agent，工具箱是当初几个工程师拍脑袋攒的——网页搜索、OCR、图像框选、代码执行，齐活。刚上线那阵挺灵，可用户丢过来的问题越来越刁：一张大巴照片问"这辆车跟哪个历史事件有关"，一张选美冠军的照片问"她关联的是什么赛事"，一张标了红块的美国地图问"这个州的州长是谁"。Agent 拿着老三样硬上，先 OCR 没读出字，再瞎搜一通，把人认错、把州认错、把年份认错，然后一本正经地给出一个错误答案。

我之前调这类系统的时候，解法特别朴素：把失败 case 攒一攒，喊人补一个工具，发版，重启。慢，而且永远追不上新题型。

上周刷到一篇新 paper（arXiv:2611.31198），给的解法让我停了一下——它不让人类去补工具，而是让 Agent 从自己失败的轨迹里挖出"我缺什么能力"，然后自己写一段 Python 把这个能力造出来，自己跑两道验收门，通过就放进工具目录，下次遇到类似问题直接检索来用。出发点朴素得有点可爱：人不也是这么干的吗，手头的家伙不够使，就用熟零件拼一个新的，用完还留着下次接着使。

---

## 🎯 核心摘要

一句话：这篇论文把多模态搜索 Agent 那套"冻结的手工工具库"改成了一个会长大的工具库——**八个精简基础原语打底**，从失败轨迹里聚类出能力缺口，判定该复用还是该新造，让一个强生成模型把新工具写成 Python，过沙箱冒烟测试 + LLM 静态代码审查两道门，再按 query 检索 top-K 挂回推理。效果不夸张但很扎实：Qwen3-VL-8B 上域内涨 **2.20 个点**、域外涨 **1.33 个点**，换到 32B 域外涨到 **2.98 个点**，且骨架越大收益越大。我的判断是，这不是底层突破，是把 Voyager、CRAFT 那条"Agent 自己造工具"的线，第一次认认真真搬到多模态搜索这个长轨迹、图文混杂的场景里，工程闭环做得相当完整；但也正因为是搬运 + 整合，那几个点的增量到底值不值这一整套流水线，得掰开看。想做自进化 Agent 的，值得花半小时细读方法部分。

## 🤔 问题动机：工具库"冻住"到底是不是真痛点

先把论文对"工具"的定义摆清楚，不然后面容易鸡同鸭讲。这里说的 tool，是一个带类型 schema 的可调用 Python 函数，吃结构化输入（一句话、一张图、一个 URL），吐出证据给 Agent 下一轮推理接着用。造一个新工具，就是造出这么一份 schema + 执行逻辑 + 描述，然后登记进推理时能翻的目录。

当下的多模态搜索 Agent，套路基本是"推理 + 感知 + 实时联网检索"多轮编排，底下压着一小撮手工工具：Text Search、Image Search、Webpage Visit、Zoom-in、Visual Grounding、OCR、Depth Estimation、Code Execution。论文 Table 1 把这八个按 Search / Vision / Code Execution 三类码得整整齐齐，搜索走 Serper API，视觉工具包了 SAM3、PaddleOCR-VL、Depth Anything 3。

问题在哪？作者列了两条，我觉得一条真一条半真。

真的一条：这套库贵且冻结。生产系统里 shipped 的工具清单、开发者攒的 skill bank，都停在"开发者当初能想到的覆盖面"。野外冒出来的新查询类型、新证据格式、新失败模式，只能靠人改工具、人工介入。这条我在工程里是真被咬过，长尾问题永远补不完。

半真的一条：作者把"学记忆"（在固定清单上学 memory）和"学用工具"（训练 Agent 把现有工具用得更溜）归为一类，说它们只打磨"怎么用"，不扩充"有哪些"。这个划分挺利落，但也把对手削得偏薄——毕竟把工具用对，很多时候比多造一个工具管用得多。不过作为立论，够用了。

顺着这个往下，作者抛了个我觉得是全文最值钱的类比：**人类探索世界时，既用现成工具，也会在工具不够使时拿熟零件拼个新的，还会在测试用例上先验证一遍再收进工具箱**。现成的多模态搜索 Agent 只有"用"这一半，缺了"造"这一半，更缺"验"这一半。工具一失灵，它们选择"算了"，而不是把工具箱改大一点。

说到这个，Agent 自己造工具其实一点不新鲜。Voyager 2023 年在 Minecraft 里就把成功经验写成可执行代码存进技能库，靠环境反馈迭代调试，拿到 3.3 倍于基线的物品发现量；CRAFT 给数学、表格 QA 造并检索 Python 工具；CREATOR 把"抽象造工具"和"具体用工具"拆开；TOOLMAKER 把代码仓库变成 LLM 可调的 utility；还有 GENOME、SkillWeaver、Alita 这一串。Survey 里管这叫从 tool user 到 tool maker 的转向。所以 ToolSmith 自己挂的"首个多模态搜索自动造工具框架"，那个"首个"得仔细读——是"首个把这个范式搬进多模态搜索"，不是"首个想到让 Agent 造工具"。这点后面评判时还会拎出来说。

## 🏗️ 方法核心：四个阶段，一条会自己长的流水线

先看全景。Figure 2 把整条流水线画得很清楚，我盯着看了好一会儿，它的顺序其实讲究：便宜的检查一律排前面，贵的 LLM 调用压到后面。

![图2：ToolSmith 四阶段流水线概览](https://arxiv.org/html/2611.31198v1/teaser_tg2.png)

*图2：从训练池上的 Agent 轨迹里挖出能力缺口 → 经 reuse-or-grow 与工具目录比对 → 交给 LLM 把每个新工具写成 Python 源码 → 只有过完两道验证门才准入，被拒时带反馈重试。右侧是推理时按 query 做 top-K 检索，把新工具挂回 Agent。*

符号先交代一句，免得看公式发懵：$\mathcal{A}_\theta$ 是基线 Agent，$\mathcal{D}_{\text{train}}$ 是训练池，$\mathcal{T}_t$ 是第 $t$ 轮的工具目录（初始化为八个基础工具 $\mathcal{T}_{\text{base}}$），$G_\phi$ 是造工具的生成模型，$\psi$ 是句向量编码器。

### Phase 1 轨迹挖掘：从"错了"里挑出"缺工具"

把基线 Agent 在训练池上跑一遍，对每条轨迹套两层触发器。

第一层是便宜信号：LLM judge 判最终答案错，就打个标。第二层才是 LLM 自我批判，逐条读被标错的轨迹，从 $\{ \text{new\_tool\_needed},\ \text{argument\_mistake},\ \text{search\_noise},\ \text{ambiguous} \}$ 里给一个失败标签。只有 `new_tool_needed` 才产出能力缺口，记成一个四元组：失败 query、Agent 已经试过的工具、自我批判给出的失败原因、图像相关的引用。

这个双层设计我挺喜欢。答错不等于缺工具——参数写错、搜索噪声、题目本身歧义，这三类硬塞去造工具只会造出一堆垃圾。先用一个近乎零成本的判错门把量缩下来，再让 LLM 做归类，算力花在刀刃上。

接着是保多样性：把每个缺口用（问题 + 预测 + 标准答案）拼起来过句向量 $\psi$，在余弦距离上做 average-linkage 层次聚类，聚成 $C$ 簇，每簇只放一个代表进下游。训练池是 9174 条 query（FVQA 3312、InfoSeek 3000、EncyclopedicVQA 2862），$C$ 默认取 500。

### Phase 2 复用还是新造：一次 TF-IDF 就够

对每个缺口，算它的文本（query 拼子任务）跟目录里每个工具描述的 TF-IDF 余弦相似度，取最大值：

$$\rho_{\text{pre}}(g,\mathcal{T}_t)=\max_{t\in\mathcal{T}_t}\cos\big(\mathrm{tfidf}(\tilde g),\ \mathrm{tfidf}(d_t)\big),\qquad \tilde g = q_g \oplus s_g$$

$\rho_{\text{pre}} > \tau_{\text{pre}}$ 就认为已有工具能盖住，跳过；否则送去造。作者特意解释了为什么不用花哨的向量：工具描述短、词表就 search/image/OCR/code 那点领域词、只需要挡住明显重复，TF-IDF 完全够。说实话这个"够用就好"的克制，比动不动上大模型的做法更让我有好感。

### Phase 3 造工具：带着镣铐写 Python

生成模型 $G_\phi$ 拿到的条件有四样：能力缺口、当前目录、一份规定工具类接口并**禁止动态执行 / 越权 I/O / 硬编码答案**的 system prompt、几个可照抄的示例工具。吐出来的是候选三件套：Python 源码 + 类型 schema + 一句自然语言描述。

"禁止硬编码"这条约束看着不起眼，其实是要害。附录 G.3 收了个被拦下的反面例子：生成器造了个叫"飓风风速查询"的工具，docstring 吹得挺通用，body 里却把触发它的那条训练 query 里的目标实体 `ernesto`（还拼错成 `eresto`）写死了，换个飓风直接返回空列表然后崩。这种"背答案"的伪工具要是混进目录，比没有还糟。

### Phase 4 验收：两道门 + 一道去重，按成本从低到高排

候选要连过三关才准进目录，顺序是刻意的——先跑便宜的，拒得越早越省钱。

**Gate 1 静态 + 冒烟**：解析源码，扫动态执行和危险 I/O 模式，然后在最小 dummy 输入上真跑一次，卡 10 秒墙钟预算。AST 违规或运行时报错，直接丢。**Gate 2 LLM 代码审查**：一个 critic 在四个 0–5 分的轴上打分——参数化使用、描述抽象度、边界情况处理、任务对齐，均分不低于 $\mu_{\min}$ 且单轴最低不低于 $a_{\min}$ 才放行。Figure 2 里那四条黄框写的就是这个："输入真的驱动逻辑而不是写死"、"描述的是一类 query 而非单独一条"、"空/None/坏输入不崩"、"解的确实是触发它的那道题"。critic 可以换模型，描述太窄、缺错误处理的工具就死在这一关。

任意一门拒了，就把"哪门挂了、为啥"压成一句自然语言回喂给 $G_\phi$ 重试，每候选最多 $A$ 次。作者观察到重试大多第二次就过、要么因为同一个原因一直错，所以 $A$ 卡得很小——这个经验判断挺实在，没在那儿硬堆重试预算。

活下来的候选还要跟目录里每个工具做一次 TF-IDF 相似度比对（用更严的 $\tau_{\text{post}}$），只有最相近匹配也低于阈值才收进 $\mathcal{T}_{t+1}$，重复的直接丢。冗余控制这个动作放了两遍——造之前挡一次，造之后再挡一次，说明作者对"工具库膨胀"是真有戒心。

### 推理时：别把整个目录塞给 Agent

要是把生成的全部工具连同基础原语一起摆到 Agent 面前，每轮的 schema 会爆，工具选择反而变烂。作者的解法是按 query 检索：每个工具描述预先用 $\psi$ 嵌好，来一个测试 query $q$，Agent 只看

$$\mathcal{T}_q=\mathcal{T}_{\text{base}}\ \cup\ \mathrm{top\text{-}K}\big(\cos(\psi(q),\psi(d_t));\ t\in\mathcal{T}_{\text{new}}\big)$$

也就是每样本固定 $|\mathcal{T}_{\text{base}}| + K$ 个工具。八个基础原语常驻（system prompt 里按名字引用），生成工具按相关性轮换出场。这一步看着平淡，其实是整套方案能不能落地的关键——工具越多越多，选择越难，这个矛盾不解决，前面造得再多也白搭。

![图1：固定工具库失败 vs ToolSmith 扩展工具库成功](https://arxiv.org/html/2611.31198v1/teaser_v6.png)

*图1：论文 teaser。同一道题"这辆大巴跟哪个事件有关"（答案：Manila hostage crisis，马尼拉人质事件）。上半部分固定工具库：Agent 拿 Text Search、Webpage Visit 硬搜，从"Hong Thai Travel bus accident"一路偏到泰国车祸，最后答"泰国东部致命车祸"，错。下半部分 ToolSmith 长出 `Event In Image` 工具，先做视觉实体检索认出这是 Hong Thai Travel 的巴士、关联到 2010 年人质事件，再一步网页访问确认，答对。*

## 🧪 实验结果：数字不大，但铺得很密

评测分两条轴：域内（ID）是挖掘轨迹用的三个数据集的留出 test split——FVQA 1800、InfoSeek 2000、EncyclopedicVQA 1960；域外（OOD）是十个训练时完全没见过的多模态搜索 benchmark，只取带图的多模态子集。答案对错用 GPT-4o 做 VLM-as-a-Judge。推理侧跑了 Qwen3-VL-8B-Instruct、8B-Thinking、32B-Instruct 和 GPT-5（gpt-5-2025-08-07），温度 0.3、top-p 0.95、单 query 最多 15 轮工具调用、上下文 120K，三次独立跑取均值。

### 主表：三档设置一起摆

论文每张主表都把三档摆齐——Direct Inference（裸模型）、Agent Workflow w/ Base Tools（八个原语）、Agent Workflow w/ Base + ToolSmith（GPT-5 当生成器，工具准入后叠上去）。这个摆法我觉得挺诚实，因为它把"工具本身值多少"和"造工具额外值多少"拆开了。

| Direct · Qwen3-VL-32B | 32.67 | 33.20 | 32.76 | 32.88 |
| Direct · GPT-5 | 54.67 | 53.67 | 43.33 | 50.46 |
| +Base · Qwen3-VL-8B | 55.00 | 50.67 | 38.67 | 47.94 |
| +Base · Qwen3-VL-32B | 62.67 | 55.33 | 49.00 | 55.47 |

看到这张表我第一反应是愣了一下：八个基础原语一上，8B 从 22.62 直接干到 47.94，涨了 **25 个点**还要多；而 ToolSmith 在上面只再叠了 2.20 个点。作者在正文里也直说了——多模态搜索压根是个"工具驱动"的任务，工具本身才是大头。所以这篇论文真正在解的是**那一两个点的边际**，不是主升力。这个比例感，读的人心里得有数。

还有个反直觉的地方：域内 8B 的增量（+2.20）反而比 32B（+1.67）和 GPT-5（+1.04）都大。别急着夸小模型，这跟"越大越受益"的宣传口径是拧着的，原因藏在域外那张表里。

32B 十个域外 benchmark **一项没落**，8B 涨了八项、剩两项基本持平（RealX-Bench −0.17、VisBrowse-Bench −0.02）。作者把"越大越受益"归到强骨架更能吃下更丰富的工具生态，还给了个补充解释：8B 增量偏小是被"工具箱变大后的长上下文选择代价"拖了后腿，GPT-5 增量偏小是撞上了身份类 query 的隐私拒答地板（附录 B.4，GPT-5 遇到"照片里这人是谁"这类题会拒答，judge 直接算错，所以它的行系统性被压低）。

把 ID 和 OOD 的 Δ 平均一下，32B 是 +2.32、8B 是 +1.77、GPT-5 是 +1.72，峰值落在 32B。这就是"越大越受益"的完整口径。我读到这儿有点想抬杠：换个说法，这套方法恰好在**你最不缺能力的强模型上收益最大**，在最需要补能力的 8B 上反而被选择开销吃掉一块。这算 scalability 还是算"锦上添花"，见仁见智。

顺带一提，8B-Thinking 在裸推理时略强于 Instruct，但在完整 Agent 工作流里单 query 延迟是 5 倍还多，所以后面所有实验统一用 Instruct 当默认部署体。这种"性能和延迟摆一起选默认"的取舍交代，比只报最好看的数要靠谱。

### 消融：三根旋钮，结论都挺干净

因为每组消融都得把 Phase 1–4 从头跑一遍，作者只在 FVQA（代表 ID）和 MMSearch（代表 OOD）上做，还明说这是"说明性发现而非统计结论"——这份坦诚我给加分。

**生成器强度（Table 4，节选 FVQA / MMSearch）**

| 造工具的模型 | 8B 消费 · FVQA | 32B 消费 · FVQA | GPT-5 消费 · FVQA | 8B 消费 · MMSearch |
|---|:--:|:--:|:--:|:--:|
| Base tools only | 55.00 | 62.67 | 55.00 | 51.46 |
| Qwen3-VL-8B 造 | 52.00 | 60.67 | 54.00 | 48.54 |
| Qwen3-VL-32B 造 | 56.00 | 63.17 | 55.20 | 53.22 |
| GPT-5 造 | 58.00 | 64.55 | 56.10 | 55.56 |

*表：固定消费模型、换生成器，准确率随生成器变强单调上升，无例外。数据取自论文 Table 4。*

按列读，生成器越强工具越好，没有例外；而且消费者越弱，生成器带来的差距越大——8B 消费从"8B 造"换到"GPT-5 造"能捡回六七分，GPT-5 消费只捡两分左右。作者的结论干脆：算力该砸在最强的可用生成器上，部署的 Agent 单独按规模选。说到底，这是一次**离线用强模型把工具蒸馏出来、线上让便宜模型消费**的解耦。

**轨迹挖掘源（Table 5）**：固定 GPT-5 造工具、8B-Instruct 消费，换"挖谁失败轨迹"。准入工具数 $|\mathcal{T}_{\text{new}}|$ 随挖掘模型变强单调下降——8B 挖出 264 个、32B 挖 218 个、GPT-5 只挖 173 个，因为强模型本来失败就少、冒出来的缺口更专门。可结果偏偏是 8B 自挖最好（FVQA 58.00 / MMSearch 55.56），强模型挖的反而掉一分左右。这个结论我是真觉得漂亮：**给 8B 部署体补工具，就该从 8B 自己的失败里挖**，生成器看到的失败分布跟推理时撞上的分布对得最齐。这跟前面"生成器要最强"放一起看有点张力，但其实不矛盾——生成器管的是"工具写得多好"，挖掘源管的是"缺口味不对不对路"，两根轴。

**聚类数 $C$（Table 6）**：$C=0$ 时 0 个工具 / FVQA 55.00 / MMSearch 51.46；$C=250$ 得 145 个 / 57.39 / 54.97；$C=500$ 得 264 个 / 58.00 / 55.56；$C=750$ 得 298 个 / 57.50 / 54.97。典型的 Goldilocks 形状，中间略高，作者自己说这是"平坦高原而非尖锐最优点"，取 500 当默认就不调了。没硬凑一个最优点出来，这份克制也记一笔。

### 采用率与成本：工具是真的被用了

这块是我判断"涨点是不是巧合"的关键证据。

| 维度 | 域内 | 域外 |
|---|:--:|:--:|
| 生成工具占全部工具调用（New calls） | 27% | 15% |
| 至少调用过一次生成工具的样本占比（Adoption） | 40.9% | 16.3% |

*表：新工具采用率，取自论文 Table 7。*

域内四成样本真的用上了新工具，域外也有一成六——工具是从域内失败里挖出来的，域外掉下来正常，但没掉到零，说明其中一部分确实泛化出了训练分布。作者拿这个数论证"涨点来自真实工具调用，而不是换了个 prompt 的偶然"，我认为站得住。

成本也没藏着。一次性造工具全流程 \$41.44：生成器 codegen 455 次调用、5.19M 输入 + 2.77M 输出 token、\$34.18；自我批判触发 446 次、\$7.26；分类器跑本地 8B，零 API 费。墙钟 170 分钟、4 个并发 worker。GPT-5 按 \$1.25 / 1M 输入、\$10 / 1M 输出算（推理 token 计输出）。四十来美元换一个能反复检索的工具库，摊到大量推理上几乎可以忽略——这是这套方案最容易被低估的优势。

还有张有意思的表（Table 10）：在 300 条 FVQA 训练 query 上换生成器，GPT-5 触发 73 次、通过 50 次（68%）、去重挡掉 23 个、花 \$1.03；Qwen3-VL-32B 触发 83 次、通过 67 次（81%）、去重 6 个、本地零成本；Qwen3-VL-8B 通过率只有 29%，人工一看，逻辑 bug 混过了验收门、真到运行时才炸。附录 F.2 那句观察挺精到：GPT-5 写出来的工具带模块化 helper、知识源分级、多层 fallback，32B 写得干净但简单，8B 就有点筛不住了。所以默认生成器定 GPT-5，是用 API 成本换结构上更禁用的代码。

### 四个 case：涨的点到底从哪来

论文 Figure 3–6 给了四个对照例子，我逐张看过，主导模式出奇一致——**生成工具把"先看清是谁/是哪，再去查"这个感知优先的顺序强行立了起来**，而基础 Agent 老是跳过这一步直接文本搜索。

![图3：实体优先识别（Reed Hastings 与 5000 万美元捐赠）](https://arxiv.org/html/2611.31198v1/case_studies_v5.png)

*图3：问"He 哪一年捐了 5000 万美元创立 Hastings Initiative？"（答案 2025）。只用基础工具时，Agent 从没认出照片里是谁，两轮 Text Search 把人错认成 Eric Schmidt，答"捐给 AI2050 基金"，错。生成的 `Image Entity Canonical Name` 工具先做人脸/实体匹配认出 Reed Hastings，再一次文本搜索就查到 2025 年向 Bowdoin College 的捐赠。作者管这叫 entity-first。*

![图4：视觉线索模糊时的人物识别](https://arxiv.org/html/2611.31198v1/case_studies_v6.png)

*图4：问"这个人关联的是什么赛事？"（答案 Miss Universe Philippines 2021）。基础 Agent 用 OCR 没读到有效文字，从"戴头冠的女性"这种模糊线索瞎猜了个"Mississippi"，答"Miss Mississippi pageant"，国家赛事全错。生成的 `Celebrated Person From Image` 走反向图搜 + 名人匹配，先锁定 Beatrice Luigi Gomez，再网页确认 2021 年菲律宾环球小姐，答对。*

![图5：美国地图上的精确区域识别](https://arxiv.org/html/2611.31198v1/case_studies_v7.png)

*图5：问"标红这个州的州长是谁？"（答案 Tina Kotek）。基础 Agent 把标红的 Oregon 认成相邻的 Washington，答了 Washington 州长 Bob Ferguson。生成的 `State Context Lookup` 先解读地图高亮锁定 Oregon，再查州长，一步到位。*

![图6：搜索排序纠偏](https://arxiv.org/html/2611.31198v1/case_studies_v8.png)

*图6：问"这张地图代表什么事件？"（答案 1996 年美国总统大选）。基础 Agent 的通用图搜返回一堆跨年份的选举地图，它咬住一个 1968 年的 Reddit 帖确认为"1968 大选"。生成的 `Event Name From Image` 把搜索意图先掰到"抽取事件名"，重排后维基百科（1996）压过 Reddit（1968），答对。*

四个例子连起来，其实指向同一件事：这批生成工具大多不是什么新算法，而是**把"反图搜 → 结构化知识库查询"打包成一次调用，逼 Agent 按正确顺序走**。丢分的样本作者也摊开了：少数工具返回了错误信息，还有 Agent 明明已经从基础工具拿到正确结果，却偏信生成工具的输出。这个"过度信任"是自动生长工具库绕不开的坑，后面单说。

## ⚖️ 我的判断：闭环漂亮，但别把定位读错了

先说打动我的地方。

第一，四阶段的成本排序和双门递进，是真做过工程的人才写得出来的。判错门 → 自我批判 → TF-IDF 复用判定 → 生成 → 静态冒烟 → LLM 审查 → 事后去重，每一道都比后一道便宜，拒得越早越省。这套"便宜检查前置"的直觉，谁在线上被 LLM 账单教育过谁懂。

第二，反硬编码约束 + Gate 2 里"描述抽象度""参数化使用"这两根轴，精准打在"工具把触发它的那道题背下来"这个最恶心的失效模式上。附录 G.3 那个写死 `ernesto` 的飓风工具被拦下来，是全文我最想拍桌子的一处细节。

第三，挖掘源消融的结论有真洞察——补谁的短板，就从谁的失败里挖。这条我大概率会直接搬到自己项目里试。

再说让我皱眉的地方。

**增量到底值不值这一整套流水线？** 基础工具把 8B 从 22.62 抬到 47.94，涨 25 个点；ToolSmith 只在这之上加 2.20。也就是说，这套方案真正解的是"工具已经很好用了之后，还能不能再抠两分"。这不是否定工作，但读的人得把它当一个边际增益的精细化框架，而不是"让 Agent 从无到有获得能力"。作者自己在正文里也没藏着这点。

**首个这个说法得收窄着看** 造工具这条线从 Voyager（2023）、CRAFT、CREATOR、TOOLMAKER 到 GENOME、SkillWeaver、Alita 已经很拥挤。ToolSmith 的真实贡献，是把这套范式搬进多模态搜索这个"轨迹长、状态里混着图片 / 链接引用 / 工具输出"的硬场景，并且把验证、去重、检索这几块补齐到一个能跑通的完整闭环。这是扎实的领域迁移 + 工程整合，不是底层方法突破。看到"first"就该警觉，这次也不例外——不过作者加了 "to the best of our knowledge" 和精确的领域限定，算克制。

**生成能力其实押在 GPT-5 上。** 消融明说生成器强度主导一切，8B 自造工具甚至掉到基线以下（FVQA 52.00 vs Base 55.00）。所以"Agent 自己造工具"这句话得打个折：是"一个强专有模型离线替一群便宜模型造工具"。好处是成本能摊薄（\$41.44 一次性），代价是这套自进化并没有真的把造工具的门槛降下来。换个没 GPT-5 的环境，效果大概率要打折。

**评估链有几处该留个心眼。** GPT-4o 当 judge 判开放式答案，噪声比 exact match 大；三次独立跑取了均值，但没看到方差区间（附录 B.3 只说存在 run-to-run variance）。域外用的是各 benchmark 的多模态子集，样本量从 169 到 500 不等，MM-BrowseComp 只有 243 条，个位数的绝对分数上抖一两分就是几个点。作者做了 retrieval-shortcut 检查（附录 B.2，说没观察到搜索工具把标准答案原文吐出来），这个补得及时；但 judge 本身的偏置没同等力度地处理。还有 GPT-5 那行因为身份类隐私拒答，分数被成片拉低，所以"+ToolSmith 对 GPT-5 只涨 1.04"别当成模型能力天花板。

**工具库膨胀和错误污染是悬着的剑。** 论文 Limitations 自己也认了：冗余控制没彻底解决、描述偏窄、可复现性会随实时搜索 API 和专有模型漂移（他们固定模型快照、归档轨迹来缓解，但承认没法完全复现）；没纳入会自己生成图片的工具；也没用代码专用 LLM 当生成器。而分析部分那句"少数工具返回错误信息""Agent 宁可相信生成工具也不信已经拿到的正确结果"，我觉得比上面所有 limitation 都更值得警惕——一个会自己长的工具库，一旦放进一个会撒谎的工具，它会被反复检索、反复调用，错误是能扩散的。冗余挡得住重复，挡不住"自信地错"。

还有个小遗憾：消融只在 FVQA 和 MMSearch 两个 benchmark 上做，作者诚实标了"说明性发现"，但"越大越受益""自挖最好"这些结论的统计支撑因此是偏薄的。这块我自己也还没完全捋清到底该给多大置信度，可能得等复现代码放出来再看。

综合定位：如果你冲着"Agent 自主进化"的底层突破来，会有点落差；如果你在做多模态搜索 / 深度研究 Agent，正在为长尾题型手工补工具补到头秃，这篇给的是一份可以直接照着搭的、成本可控的工程蓝图。值是值在后者。

## 💡 工程启发：能直接搬走的几条

聊了这么多，落到"我明天能改点什么"上。

**精简基础库 + 按需生长，别再堆大而全的工具清单。** 八个原语打底，剩下的从真实失败里长出来，比维护一个几百个工具的 skill bank 现实得多。库是长出来的，不是设计出来的。

**失败轨迹要做归因再聚类，别拿所有错题直接造工具。** 双层触发（判错 + 自我批判分类）+ 层次聚类去冗余，是把"造什么"这件事从拍脑袋变成需求驱动。直接把所有失败 query 丢给 LLM 造工具，目录三天就烂了。

**验证按成本分层，静态冒烟一定要排在 LLM 审查前面。** 再加一条硬约束：禁止动态执行、越权 I/O、硬编码答案，审查时专门设一根"描述抽象度"的轴。Appendix G 那三个例子（成功 / 运行时崩 / 被拦下的伪通用工具）建议当 checklist 抄走。

**造工具和用工具解耦。** 离线用最强模型把工具写好、验干净，线上让便宜模型按 top-K 检索消费。生成器强度和部署体规模是两根独立的旋钮，别绑在一起调。

**给谁补短板就从谁的失败里挖。** 部署 8B 就挖 8B 的轨迹，别拿 GPT-5 的失败去指导一个 8B 该长什么工具——分布对不齐，挖出来的工具再精致也用不上。

**推理时永远按 query 检索 top-K，别把全目录塞进 schema。** 工具一多，选择质量塌得比想象快；8B 上那个"工具箱变大反而吃不到收益"的现象，就是这块的账单。

**给自动生长的工具库配一层"输出可信度"监控。** 论文没做，但既然已经发现"Agent 会偏信生成工具的错误输出"，工程上就该给生成工具单独记调用日志、抽样校验返回、必要时允许基础工具结果覆盖它。一个会自己长的库，得配一套会自己查的账。

往远一点想，还有个更根本的问题没解决：现在这套是"离线挖一批、验收一批、冻住上线"，本质仍是 batch 式生长。真正让人期待的是在线闭环——推理时遇到新失败就当场造、当场验、当场入库。论文里那个 feedback-driven retry 已经有雏形了，但离在线自进化还差一步。这一步要是走通了，Agent 才算真的把"造工具"这半个能力补齐。
