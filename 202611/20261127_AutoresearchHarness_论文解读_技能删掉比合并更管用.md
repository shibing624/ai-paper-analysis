# 攒了 312 条经验教训，结果删掉最管用：拆解自演化 Agent 的 Harness

## 🎯 核心摘要

跑过自动研究 Agent 的人大概都碰过这档事：同一个任务迭代一百轮，模型没变，成绩却卡在半山腰上不去。上下文窗口被历史记录撑爆，最早那些失败的尝试被悄悄丢掉；技能库里攒了几百条"经验教训"，检索的时候越来越难挑出真正有用的那条。这篇论文没去卷模型，也没发明新算法，它把外面那层 harness 拆成两条轴——上下文怎么留、技能怎么管——在完全相同的 Agent 框架里一次只改一个组件，做了六个设置 × 三个模型 × 两个基准的组件级消融。结论干净得有点反直觉：把每次尝试压成一行摘要、但保留随时展开原文的能力（context folding），六个设置全赢，相对基线最高涨 19.2%；技能那边，把长期没人选的经验直接删掉，平均表现比合并同类项、比提升成常设规则都好。两者拼成 MLEvolver，在 MLE-Bench Lite 拿到 72.7% 奖牌率、KernelBench Level 3 拿到 94% 的 $\mathrm{fast}_1$。它不是底层突破，是一份写得相当扎实、能直接照着改代码的工程手册；缺点是基线选得偏弱，结论跟模型强绑定。

## 🧠 从一个很具体的痛点聊起

你有没有过这种体验：让 Agent 自己跑 Kaggle 比赛，前二十轮涨势喜人，后面八十轮基本在原地打转。偶尔冒出一个好点子，跑了两轮又绕回老路上，甚至把之前踩过的坑又踩一遍。

我之前调这类长程 Agent 的时候，第一反应总是"模型不够强"。换个更大的模型，涨一点；再加两轮反思，涨一点。但账其实算在别的地方——这类系统的产出不止取决于模型，还取决于外面那层 harness 怎么管理它自己积累出来的记忆。论文里管这个叫 autoresearch agent：给一个任务和一个打分器，它自己提想法、写代码、跑实验、读分数、决定下一步。同一件事反复做几十上百次，每次都拿到一个真实反馈。

问题就出在这个"反复"上。记忆分成两层，压力各不相同：

| 记忆层 | 装什么 | 会长出什么毛病 |
|---|---|---|
| 尝试历史 $H_t$ | 每次生成的方案、评测反馈、当时的推理 | 线性增长，很快撑爆上下文窗口，只能截断 |
| 技能库 $L_t$ | 从尝试里蒸馏出来的自然语言经验教训 | 可以无限膨胀，但越来越冗余、越来越吵，检索命中率往下掉 |

坦率的讲，这两层的处理方式，过去大多埋在一整套系统里。AIDE 用树搜索管理候选解，AlphaEvolve 那一路用程序池加 diff，还有一堆工作给 Agent 加反思、加层级工作记忆、加经验手册。每个系统都声称自己涨了点，可搜索策略、提示词结构、工具用法全都不一样，你根本没法判断涨的那部分到底该归给谁。

翻到 arXiv:2611.28244 这篇时，我对题目没太大期待，读完 Table 1 才觉得有点东西。它想干的事说起来挺朴素：把这些机制从各自的系统里抠出来，塞进同一个 Agent 框架，一次只动一个组件，看它单独贡献多少。这个思路本身不新鲜，但真肯花六个设置、三个模型、两个基准去铺开做的，我确实是第一次见到做得这么齐的。

![图1：论文整体思路与最终成绩](https://www.mulanai.com/fs/files/1127_531abac5_autorese.jpg)

*图1：论文的整体叙事。上半部分从左到右：长时程任务（CUDA kernel 优化与 Kaggle ML 任务，每个任务 100 次带评分的尝试）→ 基线暴露的两个毛病（历史超出 32K 窗口后丢掉最老记录、技能只进不出）→ 两条轴各自的最优选择（Folding 把每次尝试压成一行并允许按需展开、Deletion 删掉长期未被选中的技能）→ 合成 MLEvolver。下半部分给出对比结果：Kaggle 侧 MLEvolver 奖牌率 72.7%（16/22），AIDE 59.1%，OpenEvolve 63.6%；CUDA 侧 $\mathrm{fast}_1$ 为 94%（47/50），AIDE 78%，OpenEvolve 70%。图中还标明了对比条件：同一模型、32K 上下文、每任务 100 次尝试。*

## 🏗️ 把 harness 拆成两条轴

### 共享的迭代循环

所有配置跑的是同一套循环。第 $t$ 轮，Agent 先从三个动作里选一个：`propose_new`（提个新方案）、`refine_current`（改当前最优）、`debug_current`（修当前失败）；技能挑选器从该任务专属的技能库里捞出若干条经验；coder 拿到任务描述、常设规则、选中的技能、以及历史尝试的某种表示，产出新方案；评测器跑代码返回分数；技能写入器把这一轮的教训记下来。

![图2：自演化循环与六种配置](https://www.mulanai.com/fs/files/1127_6148baaf_autorese.jpg)

*图2：上半部是每轮重复的循环——Choose action → Pick skills → Code → Evaluate → Write skills，左侧标出它读写的三类记忆（History 存尝试与分数、Skills 存经验教训、Rules 每条 coding prompt 都带）。下半部是六种配置的对照矩阵：行是 History / Skills / Rules 三类记忆，列是基线、Folding、Compaction、Deletion、Merging、Promotion。只有带颜色的格子相对基线有改动，灰色格子完全一致——这正是"一次只改一个组件"的直观体现。*

形式化一点，coder 第 $t$ 轮看到的是：

$$C_t=[T,R_t,K_t,\Phi(H_t)],\qquad |C_t|\le B$$

$T$ 是任务描述，$R_t$ 是常设规则集合，$K_t$ 是挑选器选中的技能子集，$\Phi$ 就是这个配置特有的历史策略，预算 $B=32{,}000$ tokens。整篇论文的消融，其实就是在这个式子里换 $\Phi$、换 $L_t$ 的维护方式，其余一概不动。这个设计我挺喜欢的：变量少，因果链清楚。

### 上下文这条轴

**基线：近期截断**：留能塞进预算的最长后缀，最老的记录先丢，丢了就再也拿不回来：

$$(a_j,\ldots,a_{t-1}),\quad j=\min\{k: |(a_k,\ldots,a_{t-1})|\le B_H\}$$

**Folding**（折叠）：把每次尝试都用一个摘要器压成简短的诊断摘要 $\hat{a}_i=\sigma(a_i)$，所有摘要按序列摆在上下文里，同时允许 Agent 挑一个子集 $U_t$ 把对应尝试展开成完整原文：

$$\Phi_{\mathrm{fold}}(H_t)=(\hat{a}_0,\ldots,\hat{a}_{t-1})\oplus(a_i)_{i\in U_t}$$

关键在于"每一次尝试都仍然可寻址"。摘要给出全局视野，展开给出细节，Agent 自己决定要挖哪一条。

**Compaction**（压缩）：维护一份滚动摘要 $m$ 加一小段近期尾部 $\tau$，窗口满了就把较老的一段 $h$ 并进摘要：

$$m\leftarrow S(m,h),\qquad \Phi_{\mathrm{comp}}(H_t)=m\oplus\tau$$

摘要有固定结构（任务目标、重要细节、当前工作状态）。它跟 folding 的差别只有一句，却是整篇论文最要紧的一句：压缩之后，单次尝试不再能单独被选中、被展开。

### 技能这条轴

技能库按任务独立初始化，每个任务开跑前清空，技能只有被挑选器选中才会进 coder 的 prompt。三种管理方式：

**Deletion**（删除）：记 $u_k(t)$ 为技能 $k$ 连续多少轮没被选中，阈值 $\tau_d=5$，把 $\{k\in L_t: u_k(t) \lt \tau_d\}$ 留下，其余删掉。它动的只有技能目录，不碰历史和规则。

**Merging**（合并）：用 Qwen3-Embedding-0.6B 给技能算 embedding，新写入的技能 $k'$ 找余弦最近邻：

$$k^{*}=\arg\max_{k\in L_t}\cos(e(k'),e(k))$$

相似度 $\ge \theta=0.8$ 就合并，否则作为新技能入库。

**Promotion**（提升）：一个提升 Agent 看技能被选中次数、以及"它出现时是否产生了新的最好成绩"，提名那些至少贡献过一次改进的技能变成常设规则 $R_t$，之后每轮必带，不再需要检索。

你想想看，这三条其实代表了三种完全不同的知识观：删除是把"没人再用"当作过时信号，合并是相信语义相近的教训可以无损归并，提升是相信好经验值得永远挂在嘴边。我第一反应是提升最靠谱——把验证过的教训写进 system prompt，多稳。结果被打脸了，后面细说。

## 🔧 实验怎么搭的

两个基准，反馈性质差得很远。

**MLE-Bench**：选了 10 个 Kaggle 竞赛（6 个低复杂度、4 个中复杂度），每个配置跑 100 轮迭代，每轮训练、写 submission、拿分数和终端输出。因为各比赛指标量纲和方向都不同，作者用了金牌归一化分数：

$$\mathrm{GNS}_i=100\cdot\frac{s_i-s_i^{0}}{s_i^{\mathrm{gold}}-s_i^{0}}$$

$s_i$ 是该轮最好成绩，$s_i^0$ 是啥也不干的分数，$s_i^{\mathrm{gold}}$ 是排行榜金牌阈值。10 个比赛按低/中复杂度取权重 1 和 2 加权平均：

$$\mathrm{GNS}=\frac{\sum_{i=1}^{N}w_i\,\mathrm{GNS}_i}{\sum_{i=1}^{N}w_i}$$

**KernelBench**：50 道题，覆盖 Level 1 单算子 20 道、Level 2 融合算子链 20 道、Level 3 完整模型架构 10 道，每道跑 50 轮。生成的 CUDA kernel 编译后跟 PyTorch Eager 参考实现对比，报告几何平均加速比。评测器加了静态与运行时防作弊检查（禁用代码模式、防止复用参考输出），违规实现直接判无效——这点我很在意，kernel 生成这个领域 reward hacking 太容易了，不设防的数字基本没法看。

三个模型骨干：`gpt-oss-120b`、`gpt-6-luna`、`gpt-6-sol`。所有配置在同一任务上从同一个"刻意做得很弱"的种子解出发，技能库每任务重置。

![图3：上下文机制的使用情况与推进效率](https://www.mulanai.com/fs/files/1127_f178e2da_context_.jpg)

*图3：(a) 左轴是上下文里能看到的过往尝试数，基线平均只有 6.2 条完整记录，Compaction 是 3.7 条（摘要 + 尾部），Folding 达到 42.0 条（紫色斜纹为摘要、实心为按需展开的完整记录）；右轴是上下文 token 数，基线 18.4k，Compaction 和 Folding 都是约 12.1k。(b) 是 new-best rate（该轮成绩超过此前所有轮次的比例）：前 10% 轮次三者接近（35.3% / 36.3% / 35.4%），10% 之后 Folding 12.0%，基线 10.2%，Compaction 9.7%。*

## 🔬 为什么赢的是"可寻址"，不是"省 token"

论文用 new-best rate 把这件事拆开了：某轮成绩超过此前所有轮次，就算一次推进。

前 10% 的轮次，三种上下文机制几乎没差别（Folding 35.4%、Compaction 36.3%、基线 35.3%）。那时候历史还短，谁都不吃亏。等尝试攒起来之后，分叉出现了：Folding 12.0%，基线 10.2%，Compaction 9.7%。论文算了一下，后期 Folding 找到改进的频率比基线高约 18%，比 Compaction 高约 24%。

再看图3(a) 那组数字就通了。基线平均只留 6.2 条完整记录，18.4k tokens；Folding 留 42.0 条记录，只要 12.1k tokens；Compaction 同样 12.1k，却只有 3.7 条记录加一份摘要。

这就是关键。

Compaction 把老历史压成一份有长度上限的摘要，历史越长，摘要越装不下；更重要的是，某次具体失败的代码、输出、推理过程，在合并的那一刻就没了，之后再想按相关性把它捞出来，做不到。Folding 把每次尝试压成一行诊断摘要，等于给整个历史建了一份目录，任何一条都能凭索引展开成原文。**省上下文只是副作用，保住"每一条都还能单独取回来"才是主效应**。

这个区分对做 Agent 的人挺有用了。我见过太多"上下文压缩"方案，目标函数只盯着 token 数，压完发现模型开始重复犯错——因为犯错的那次细节被抹平了。论文的措辞也很克制：reducing context usage alone is insufficient，表示形式还得保住对累积实验历史的有效访问。

## 💡 技能侧：删掉 > 提升成常设规则 > 合并

技能这边得先把两层收益剥开。作者专门做了 No-Skill 消融（关掉技能挑选器和写入器），结果：光是"有个不管理的技能库"就比 No-Skill 高 2.1%；在这个基础上再做管理，Deletion 再贡献 4.1%，Promotion 3.0%，Merging 2.2%。

![图4：技能管理的收益拆解与检索行为](https://www.mulanai.com/fs/files/1127_87a7efef_skill_ma.jpg)

*图4：(a) 相对 No-Skill 的增益，斜纹段是"有技能库"本身的 2.1%，实色段是各管理机制额外带来的增益——Deletion 合计 6.2%、Merging 4.3%、Promotion 5.1%。(b) 每次 prompt 被选中的技能数（柱，左轴）与该配置相对基线的增益（圆点，右轴）：gpt-oss-120b 约 6.4–7.1 条，gpt-6-luna 约 1.2–1.9 条，gpt-6-sol 约 0.5–0.6 条。(c) 三个模型选中技能的攻防取向占比：进攻型（鼓励新实现/新优化）分别是 53.1%、30.2%、25.4%，其余为防守型（保住正确性、避开已知失败）。*

为什么"删"比"合并"和"提升"强？论文给的解释我觉得站得住：

合并看的是语义相似度，$\theta=0.8$ 一刀切下去，两条教训措辞接近但适用条件、实现细节不同，硬揉成一条就把边界条件揉没了。提升更微妙——它把某次有效的经验变成每轮必带的常设规则，可方案本身在演化，当初成立的前提过几轮未必还成立，一条过时的规则还占着 prompt 的黄金位置。删除反而最诚实：它不判断经验"对不对"，只看 Agent 自己还捡不捡它，用检索行为当相关性信号，长期不选就当作已经过时。

![图8：技能库随迭代的增长](https://www.mulanai.com/fs/files/1127_5db24894_skill_li.jpg)

*图8：两行分别是 KernelBench（50 轮）与 MLE-Bench（100 轮），三列对应三个骨干。纵轴是库存技能数，曲线标注了终值。以 MLE-Bench + gpt-oss-120b 为例：Folding 攒到 365 条、Promotion 330 条、基线 312 条，而 Deletion 只留 31 条；KernelBench 同列对应 205 / 94 / 111 / 28 等。删除机制（粉色三角形）几乎压平在底部，其余机制近似线性增长。*

312 对 31，差了十倍。挑技能的时候面对 31 条和面对 312 条，噪声量完全不是一个级别。顺带一提，图8 里 Folding 攒得最多（365 条）——上下文那套机制只管历史，技能库该膨胀还是膨胀，所以后面 MLEvolver 才要把两条轴的最优解拼起来。

还有个我一开始没料到的角度：三个模型用技能库的方式差得离谱。`gpt-oss-120b` 每次 prompt 捞 6.4–7.1 条技能，进攻型占 53.1%；`gpt-6-luna` 只捞 1.2–1.9 条，`gpt-6-sol` 更保守，0.5–0.6 条，进攻型只剩 25.4%。两个闭源骨干更像在拿技能当"防错清单"，开源那个拿它当"点子库"。技能管理给 `gpt-oss-120b` 带来的增益（约 5.1%）也确实比另外两个（1.9%、2.1%）大得多。

这算一个挺重要的提醒：**harness 的收益不是模型无关的常数**。同一个机制，遇上不爱检索的模型，天花板天然就低。

## 🧪 MLEvolver：两条最优轴装一起

把 Folding 和 Deletion 合起来就是 MLEvolver。对比对象是 AIDE（树搜索候选解，每步 draft / refine / debug）和 OpenEvolve（AlphaEvolve 的开源实现，用 islands 组织程序库，采样父代 + 高分程序 + "灵感"程序，靠 search-and-replace diff 编辑）。三个系统都用 `gpt-6-sol`、32K 上下文、每个任务 100 轮，预算对齐得算公道。范围换成 22 个 MLE-Bench Lite 竞赛和 50 道 KernelBench Level 3 题。

![图5：MLEvolver 与 AIDE、OpenEvolve 的正面对比](https://www.mulanai.com/fs/files/1127_a1ee875b_mlevolve.jpg)

*图5：(a) 22 个竞赛的任意奖牌率 72.7 / 59.1 / 63.6，金牌率 45.5 / 31.8 / 31.8。(b) 50 道 Level 3 题的 $\mathrm{fast}_1$ 为 94.0 / 78.0 / 70.0，$\mathrm{fast}_2$ 为 62.0 / 26.0 / 14.0。(c) MLE-Bench Lite 的 GNS 随迭代曲线，终值 98.1 / 96.7 / 95.6。(d) KernelBench Level 3 相对 PyTorch Eager 的几何平均加速比曲线，终值 2.99× / 1.85× / 1.41×。*

| 指标 | MLEvolver | AIDE | OpenEvolve |
|---|---|---|---|
| MLE-Bench Lite 任意奖牌率 | 72.7%（16/22） | 59.1% | 63.6% |
| MLE-Bench Lite 金牌率 | 45.5%（10 金） | 31.8% | 31.8% |
| 终局 GNS（100 轮） | 98.1 | 96.7 | 95.6 |
| KernelBench L3 $\mathrm{fast}_1$ | 94.0%（47/50） | 78.0% | 70.0% |
| KernelBench L3 $\mathrm{fast}_2$ | 62.0%（31/50） | 26.0% | 14.0% |
| 终局几何平均加速比 | 2.99× | 1.85× | 1.41× |

*表2：MLEvolver 主对比，数据取自原文第 6 节与图5。*

最让我在意的不是终值，是爬升速度。MLEvolver 在第 20 轮就到了 97.4 GNS、第 10 轮就到 2.08× 加速比——这两个数都超过了两个 baseline 跑满 100 轮的终值。KernelBench 那边后半程还在拉开：50→100 轮 MLEvolver 从 2.67× 涨到 2.99×（+11.9%），AIDE 只涨 0.8%，OpenEvolve 涨 5.2%。

论文对"为什么这两个基准表现不同"的解释也挺有意思。MLE-Bench Lite 的解空间偏离散，选哪个模型族、哪种特征表示，差别是跳跃式的，所以 AIDE 的树分支、OpenEvolve 的种群采样在前半程能追得比较近（AIDE 的差距从 3.5% 收窄到 1.4%，OpenEvolve 从 15.4% 收窄到 2.6%）。KernelBench 的解空间偏连续，第一个能跑对的 kernel 大概就和 PyTorch Eager 一样快，后面全靠一轮轮叠加小优化，单链条的顺序自我改进更占便宜。这么看，harness 的适配性跟任务的解空间结构有关，不是一套打天下。

![图7：32K 与 128K 上下文窗口下的 MLEvolver](https://www.mulanai.com/fs/files/1127_65b1c21d_context_.jpg)

*图7：(a) MLE-Bench Lite 奖牌率 32K 为 59.1%、128K 为 63.6%，金牌率 27.3% → 31.8%；(b) KernelBench Level 3 的 $\mathrm{fast}_1$ 为 72.0% → 78.0%，$\mathrm{fast}_2$ 为 10.0% → 20.0%。窗口放宽确实还有收益，但论文主设置锁在 32K，为的是跟基线公平比较。*

附录这组 32K / 128K 对比值得多说一句：把窗口放大四倍，$\mathrm{fast}_2$ 从 10% 翻到 20%，说明上下文预算仍然是瓶颈。可也正是因为主实验全部锁死 32K，Folding"用更少 token 装更多历史"的价值才被凸显出来——要是直接给 128K，截断基线大概没那么难看，19.2% 这个数也就不会这么漂亮。这个我放在下面一起说。

## ⚠️ 我的判断：值钱的地方和不那么结实的地方

**这篇论文最值钱的地方，是把"记忆"这件事从系统竞赛里拆成了可单独验证的组件**。顺着 Harness Engineering 这条线往下看，AlphaEvolve 把候选程序池、diff 生成、评估器打包成一套 coding-agent harness；Darwin Gödel Machine 干脆让 Agent 去改自己的 harness 代码；Self-Harness 用失败轨迹聚类来提修改提案。这些工作都在证明"模型不动、外面这层能涨分"，可它们比的是整套系统。这篇反过来，不比系统比零件，而且把六个配置放在同一个循环、同一个种子解、同一个评分器下。这种做法产出的不是 SOTA 数字，是可迁移的因果结论——"保留可单独寻址的历史记录比滚动摘要好"这句话，换个框架大概率还成立。

**但基线确实选得偏弱**。recency truncation 是记忆策略里最省事也最粗糙的一种，超窗口就丢最老的，连检索都没有。拿它当参照，+19.2% 的成色要打折。我更想看到的是跟带检索的摘要、层级工作记忆（HiAgent 那一路）、或者带价值筛选的经验回放比一比。论文自己也在附录里做了 128K 对照，等于侧面承认了预算这个变量很敏感。要是把窗口开到 128K 再跑一遍消融，Folding 相对基线的优势还剩多少？这个问题没答案。

**范围边界得看清**。作者在 Limitations 里写得很坦白：只在**线性、顺序**的改进链上做，并行树搜索、种群演化一概没测；对比对象只覆盖有引导研究循环的结构化框架，Claude Code、Codex 那类交互式 coding agent 因为"迭代单位难以对齐"被排除了；每个任务重置技能库，所以结论只刻画**任务内**的经验积累，跨任务技能迁移、多任务蒸馏完全没碰。这三条恰好是现在很多 Agent 产品真正在用的形态。你要是做多任务共享记忆的，直接照抄"删掉长期未用技能"可能会把跨任务才用得上的经验误杀。

**结论跟模型强耦合这件事，论文自己发现但没深挖**。技能检索量 6.4–7.1 对 0.5–0.6，进攻型占比 53.1% 对 25.4%，这种量级的差异足以让"Deletion 最优"变成只在爱检索的骨干上成立的经验规律。三个骨干里两个是名字不透明的闭源模型（`gpt-6-luna`、`gpt-6-sol`），外部想复现基本没门。这点我不怪作者，但读的时候得留个心眼：这不是一个模型无关的设计原则，更像一份带前提的调参记录。

**指标也有可挑的地方**。MLE-Bench Lite 上终局 GNS 98.1 对 96.7，差 1.4%，已经贴着金牌归一化的天花板了，这个指标区分度在后期其实很弱；真正拉开的是奖牌率（72.7% 对 59.1%）和 KernelBench 的 $\mathrm{fast}_2$（62% 对 26%）。作者把四个指标都摆出来，算是厚道，读者自己得知道该盯哪个。还有个细节我核对时对不上：图1 的示意里写的是"删除 20 次未被选中的技能"，方法节公式给的却是 $\tau_d=5$ 连续未选中。可能是示意图做了简化，也可能是版本间改动没同步，我倾向按方法节的正式设定理解，但这处不一致确实让人有点犯嘀咕。

**对比对象的选择也谈不上完备**。引言里点名的 ML-Master、Kevin、CUDA Agent 这些同期工作，第 6 节一个都没进对比表。AIDE 和 OpenEvolve 都是通用 harness，论文也给了同模型同迭代预算的控制，公平性没什么大毛病；只是在 100 轮固定预算下，树搜索和种群方法偏探索的优势未必能完全展开——作者自己在讨论里也提到 AIDE 的差距在后半程从 3.5% 收窄到 1.4%。预算再放大，排序会不会变？没测。

剥掉包装看本质：这是一份工程整合 + 受控消融的工作，不是新机制、新模型、新理论。它提出的 Folding、Deletion、Merging、Promotion 没有一样是新东西，贡献在于"在同一把尺子下量清楚了谁值多少"。别被 72.7% 和 94% 晃花眼，那两个数是把两条最优轴拼起来的结果展示；论文真正的输出是 Table 1 那六个格子里稳稳的 +8.6% 和 +4.1%。

## 🔗 工程上怎么用

如果你也在做长程迭代 Agent，我觉得有三条可以直接搬。

先别急着做上下文压缩，先问自己一句：压完之后，第 37 轮那次失败的代码还能按相关性取回来吗？取不回来，就得做索引 + 按需展开，而不是一味把历史塞进一份摘要。Folding 的实现成本其实不高，摘要器给每次尝试生成一行"试了什么 / 结果如何 / 为什么失败"，再留一个按 id 展开原文的工具就够了。

技能库要设淘汰机制，而且优先级高于合并和提升。最省事的信号就是 Agent 自己的检索行为：连续若干轮没被选中就移出活跃目录（注意是移出活跃目录、不是物理销毁，留个冷备方便回溯）。合并需要 embedding 和阈值调参，还容易把适用条件揉糊；提升成常设规则风险更大，方案一演化，旧规则就从助力变成枷锁。

还有一条容易被忽略的：先量一下你的骨干到底捡不捡技能。要是每轮只捞 0.5 条，那技能库做得再精致也白搭，这时候该投入的是检索策略或者提示词，而不是淘汰算法。

一个最小可用的骨架大概长这样：

```python
for t in range(T):
    action = agent.choose_action(digests)          # 看摘要目录决定下一步
    unfolded = agent.retrieve_attempts(digests)     # 按相关性展开若干条完整记录
    skills = picker.select(live_library, k=None)    # 挑活跃技能
    solution = coder(task, rules, skills, unfolded) # Φ(H_t) = digests ⊕ unfolded
    score, log = evaluator(solution)
    digests.append(summarize(solution, score, log))
    live_library.update(writer.distill(solution, score, log))
    for s in live_library:                          # deletion：连续 5 轮未被选中
        s.unused = s.unused + 1 if s not in skills else 0
    live_library = [s for s in live_library if s.unused < 5]
```

十几行的事，但顺序别搞反：先写摘要、再蒸馏技能、收尾时按本轮是否被选中更新计数。

说实话这块我自己也还在摸索——尤其"删除阈值取几轮"这种参数，论文给的 5 是在 100 轮 / 50 轮的任务尺度上调出来的，换成 20 轮就收工的短任务，5 轮可能太狠。还有跨任务复用技能库时该怎么改淘汰信号，论文没给答案，我一时也没想明白。

## 📝 收个尾

这篇论文给我的感觉挺踏实：没喊什么新范式，就是把一个大家都隐约觉得重要、但没人认真量过的变量，拿六个设置、三个模型、两个基准老老实实量了一遍。"保留可单独访问的历史"和"把没人用的经验删掉"，两句话都不性感，但都是明天就能改到自己代码里的东西。

论文把地基打好了，房子还没盖。
