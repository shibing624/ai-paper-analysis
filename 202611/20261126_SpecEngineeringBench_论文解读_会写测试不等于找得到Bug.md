# 91% 的测试能过，26% 能抓到 Bug：SpecEngineeringBench 给 Coding Agent 的一记诊断

前段时间帮一个团队看 Coding Agent 的训练日志，reward 曲线一路稳稳往上，测试通过率也漂漂亮亮，可拉几条 rollout 出来人工看，Agent 的调试能力好像没长多少。当时的第一反应是数据污染了，或者 verifier 太松被人钻了空子。翻来覆去查了两天，直到读到这篇 SpecEngineeringBench，我愣了一下——问题可能出在一个更靠前、更不起眼的地方：Agent 辛辛苦苦写出来的测试，压根就没打算去抓 Bug。

它跑得通，它覆盖得到，它甚至长得很像一份合格的单元测试。就是不会失败。而不失败的测试，在一个有缺陷的实现面前，等于什么都没说。

---

## 🎯 核心摘要

把编码 Agent 从「照着线索写测试」推到「自主规格工程」：只给一份功能需求文档（PRD）、一个预发布仓库和一个配好的环境，让 Agent 自己决定测什么、去哪调查、并主动把未知缺陷挖出来。这篇论文做了这样一个基准，100 个实例、78 个开源 Python 仓库、531 个真实缺陷，用测试有效性、缺陷检测、覆盖率、定位精确率-召回率四个维度联合打分。结果挺扎心：七个前沿 Agent 的 Head Pass Rate 到了 **91.47**，Change-focused Coverage 到了 **80.48**，可 Fail-to-Pass Rate 只有 **26.36**；定位召回率从文件级 78.11% 掉到函数级 51.29%。我的判断是，这不是又一篇刷榜的 benchmark 论文，它更像一份给 RLVR 奖励设计和训练数据构造写的体检报告——如果你正在用「测试通过率」当 reward，这篇文章值得你把实验表格一个数字一个数字读完。

## 🤔 问题动机：我们一直在考「照着线索写测试」，没考「自己决定测什么」

聊这篇之前，先把坐标系摆清楚。

SWE-bench 是这一波 Coding Agent 评测的起点，普林斯顿团队 2023 年做、ICLR 2024 发表，拿真实 GitHub Issue 加修复前的仓库快照，让 Agent 产出补丁，再用 Fail-to-Pass 和 Pass-to-Pass 两重测试判分。它把「单文件函数补全」升级成「在几万行的多文件工程里真修一个 Issue」，这步跨得很扎实。后来 SWT-bench 把任务翻了个面：不写补丁了，写测试，要求生成的测试在有缺陷的代码上失败、在打上开发者修复后通过，也就是复现 Issue 里描述的那个 Bug。TDD-Bench Verified、TestGenEval、CLOVER、TestExplora、Active-SWE 这些，各自在函数、文件、多文件、指定组件、指定入口接口的粒度上做文章。

你发现共性了吗？它们都给了线索。有的给 Issue 描述（「这个场景下会崩」），有的给指定的调查目标（「去测这个函数」「看这个目录」），有的给复现栈。线索一给，任务就从「需求到实现的映射」退化成了「局部代码补全 + 复现脚本编写」。说到底，考的是执行，不是判断。

SpecEngineeringBench 的作者把这件事挑明了：真实发布前的测试是探索式的、多缺陷的调查，规格工程师不会拿到一份定位好的 Bug 报告，也不会拿到现成的失败栈。他们得自己读高层产品说明，自己逛代码库，自己写有区分度的用例，自己写能复现的缺陷报告。给线索，恰好绕过了最难的那一段。

![图1：三类 benchmark 设定的概念对比](https://www.mulanai.com/fs/files/1126_35a1fb26_fig_conc.png)

*图1：论文 Figure 1。(a) Issue-guided：给一份「观察到的失败 + 期望行为」的 Issue 报告，Agent 产出复现/验证测试；(b) Target-guided：代码里直接圈定 `src/a.py` 里的 `def target()` 或指定入口函数，Agent 只管检查/测试；(c) SpecEngineeringBench：只给 PRD、预发布仓库、Docker 环境三样东西，仓库里那些问号要 Agent 自己去找。它自己决定测什么、在哪测，走「探索仓库 → 设计测试 → 执行测试 → 分析结果」的循环，再拆成两个独立任务分别评估：Task 1 交可执行测试套件（看测试能不能跑通/抓不抓得到缺陷/覆盖够不够），Task 2 交缺陷位置 + 测试证据（看定位召回与精确率）。底部那行写着「Multiple defects; no issue or location hints」。*

论文里有一张 benchmark 属性对比表，我把它压成更直观的版本：

| 基准 | 输入线索 | 需要自己定测什么 | 需要自己定去哪查 | 单个实例多个缺陷 | 显式打分缺陷定位 |
|---|---|---|---|---|---|
| SWE-bench 系 | Issue 描述 + 仓库 | 否 | 否（Issue 指向） | 通常单缺陷 | 否（判补丁） |
| SWT-bench / TDD-Bench | Issue 描述 | 否（复现指定 Bug） | 否 | 通常单缺陷 | 否 |
| TestGenEval / CLOVER / TestEval | 指定函数/类/文件 | 否 | 否 | 否 | 否 |
| TestExplora / Active-SWE | 指定入口接口 / 限定 review 文件 | 部分 | 否 | 否 | 部分 |
| **SpecEngineeringBench** | **仅 PRD + 预发布仓库** | **是** | **是** | **是（4–15 个）** | **是** |

表：按论文 Table 1 的属性定义整理。Exploration scope、Issue-free、Location-hint-free、Multi-bug、Bug location、Executable evidence 这几列是原表的骨架。

我个人觉得这张对比表比结果表还重要。它把「benchmark 之间的差别」从「数据集不一样」重新定义成「线索给到哪一层」。以前大家比的是 Agent 能不能把给好的活干完，现在比的是没人给活时它会不会自己找活。这是评测范式上的挪动，不只是又多了一个数据集。

## 🏗️ 方法核心：把线索全部拿走，剩下的才是真本事

一句话讲清核心思路：把 Issue 描述和定位提示全删掉，只留 PRD，逼 Agent 从「需求」推出「测试范围」和「判定预言（oracle）」。

论文的写法比这严谨。每个实例形式化成一个四元组 $(r_i, d_i, e_i, \mathcal{B}_i)$：$r_i$ 是未修复的仓库快照，$d_i$ 是产品需求文档，$e_i$ 是隔离的 Docker 运行时，$\mathcal{B}_i$ 是这个实例里共存的参考缺陷集合，且 $|\mathcal{B}_i| \ge 4$。关键在于 Agent 只能看到 $(r_i, d_i, e_i)$ 三样，$\mathcal{B}_i$ 对它完全隐藏。PRD 描述的是「什么该正常工作、边界条件、错误行为」，也就是「what」；「where」和「how」得 Agent 自己填。

然后拆成两个互不干扰的任务，这一步设计我挺喜欢：

**Task 1（测试生成）**，$\mathcal{T}_i^{(1)} = \mathcal{A}(r_i, d_i, e_i; \pi_1)$，交一份独立测试套件。评测器把这份套件分别在缺陷快照 $r_i$ 和真值修复快照 $r_i^{+}$ 上离线跑一遍，打分。

**Task 2（缺陷发现与报告）**，$(\mathcal{T}_i^{(2)}, \mathcal{R}_i) = \mathcal{A}(r_i, d_i, e_i; \pi_2)$，Agent 可以写临时探针测试去主动探索，末了交一份结构化诊断报告 $\mathcal{R}_i$，每条疑似缺陷都得附可复现的执行日志和有源码依据的位置。

把「会不会写测试」和「会不会用测试查案」拆开考，是这篇论文方法论上最值钱的一处。混在一起考，你永远分不清一个 Agent 是测不出来，还是测出来了但读不懂结果。

指标定义也值得抄下来，因为后面的「脱钩」结论完全建立在这几个式子上。设 $\mathcal{T}_i$ 为提交的注册测试，$\mathcal{H}_i$ 是在修复快照上通过的子集，$\mathcal{F}_i$ 是在缺陷快照上失败、在修复快照上通过的子集：

$$\mathrm{HP}=\frac{\sum_{i=1}^{M}|\mathcal{H}_i|}{\sum_{i=1}^{M}|\mathcal{T}_i|},\qquad \mathrm{F2P}=\frac{1}{M}\sum_{i=1}^{M}\frac{|\mathcal{F}_i|}{|\mathcal{T}_i|}$$

HP（Head Pass Rate）是把所有测试数池化后算的通过率，检查的是「你这测试跟修好的实现兼不兼容」。F2P（Fail-to-Pass Rate）按实例平均，要求测试在缺陷版失败、修复版通过，且要反复执行确认，衡量的才是「这测试能不能把缺陷捅出来」。注意两者的分母口径不一样，一个池化一个实例平均，这个细节后面读表时别混。

覆盖率两个指标同理：

$$\mathrm{EC}=\frac{1}{M}\sum_{i=1}^{M}\frac{|\mathcal{C}_i\cap\mathcal{E}_i|}{|\mathcal{E}_i|},\qquad \mathrm{CFG}=\frac{1}{M}\sum_{i=1}^{M}\frac{|\mathcal{C}_i\cap\Delta_i|}{|\Delta_i|}$$

EC（Entry Coverage）看测试有没有跑到目标功能的可执行行，CFG（Change-focused Coverage）看有没有跑到参考修复改动的那批行。$\mathcal{E}_i$、$\Delta_i$、$\mathcal{C}_i$ 都是只在评测器手里的信息，Agent 看不到——它得自己从需求里找到实现在哪。

定位这块，对粒度 $g \in \{\mathrm{file}, \mathrm{function}, \mathrm{hunk}\}$：

$$\mathrm{LR}_i^g=\frac{a_i^g}{|G_i^g|},\qquad \mathrm{LP}_i^g=\frac{b_i^g}{|P_i^g|}$$

$a_i^g$ 是命中的参考位置数，$b_i^g$ 是被评测器认可的报告位置数。文件按归一化路径匹配，函数额外要求名字对上，hunk 要求同一文件且源码行落在 $\tau=3$ 行容差内（用缺陷快照的坐标，插入型改动用源码行锚点）。这个 3 行容差挺关键，它让 hunk 级的精确率比函数级反弹了不少，读表时别被这个反弹骗了，等会儿细说。

看到这张表我第一反应是去核了一遍列对齐——HP 那一列 90 出头整整齐齐，F2P 那一列 20 到 34 之间晃，两列差了 **65 个点**左右。这不是某个模型翻车，是七个模型集体如此，开源闭源一视同仁。

作者把这种断裂叫「test validity and coverage decouple from defect exposure」，测试有效性与缺陷暴露能力脱钩。为了确认不是统计口径搞的鬼，他们摊开了 5 个系统、500 次评测、49,317 条注册测试的细账：67.44% 的测试在修复快照上通过、且没在缺陷快照上失败（跑了，但啥也没抓到），24.17% 满足 F2P，8.39% 在修复快照上直接挂掉。还有 5.60% 的评测里，测试全过但一条 F2P 都没有。

67.44% 这个数我盯了挺久。它不是「写错了」，是「写对了却没用」。Agent 从仓库现有输出、默认 fixture、既有返回模式里反推判定预言，把 PRD 里的边界契约晾在一边，于是测试把眼前这份有缺陷的实现「验证」了一遍。论文里那句说得挺狠：Agent 把实现当成了真理的来源，而不是把规格当成真理的来源。这跟做测试的老兵常念叨的一句话撞上了——别让被测代码自己告诉你对不对。

重点看最右边那一列：即便 CFG 冲到 80–100% 区间，也就是参考修复改动的行基本都跑到了，F2P 也只在 24.24% 到 37.82% 之间。而且中间几列并不单调，GLM-5.3 在 40–60 区间只有 15.47，比它自己 20–40 区间的 21.49 还低。跑到那行代码，和给出能触发缺陷的输入、断言受影响的行为，是两件事。作者也老实标了这是描述性分组，不是因果估计。

说实话这个表打消了我一个偷懒的念头：以前调 Agent 写测试，习惯拿覆盖率当代理指标，觉得覆盖上去了质量自然跟上。这篇论文等于把这条捷径堵死了。

### 召回率在粒度上塌方

文件级 LR 78.11% → 函数级 51.29% → hunk 级 51.88%，从文件到函数掉了 26.81 个点。精确率则是 75.33% → 53.77% → 68.78%，函数级掉 21.56 个点又弹回 hunk 级。

这个「掉下去又弹回来」别读成 hunk 级更强。hunk 匹配带 $\tau=3$ 行容差，天生更容易算命中，是评测口径松了一档。真问题在函数级：Agent 能圈出相关文件，但在文件内部那一堆 caller、helper 里，分不清哪个才是根因函数。

再往下一层更刺眼。RQ2 统计「一个缺陷被完整定位」的比例（要求所有参考文件、函数符号都命中，且 hunk 召回过半）：

| 模型 | 总体定位率 | 单文件缺陷 | 多文件缺陷 |
|---|---|---|---|
| DeepSeek-V4.1-Flash | 37.93 | 46.19 | 3.92 |
| Kimi-K3 | 42.72 | 52.14 | 3.92 |
| GLM-5.3 | 42.34 | 51.90 | 2.94 |
| Claude-Sonnet-5 | 33.14 | 40.63 | 2.00 |
| Claude-Opus-5 | 45.37 | 54.57 | 7.84 |
| GPT-5.6-Sol | 43.30 | 52.38 | 5.88 |
| GPT-6-Astra | **49.04** | **59.05** | **7.84** |

表：论文 Table 3（RQ2）。定位率 = 被定位的参考缺陷数 / 可评参考缺陷数，每个缺陷等权。

最强的 GPT-6-Astra 也就 49.04%，连一半都没到；单文件缺陷还能做到 40.63%–59.05%，一碰到跨文件缺陷就塌到 2.00%–7.84% 这个区间。GPT-6-Astra 文件级召回明明有 85.85%，整体缺陷定位率却不到五成。作者还补了一刀：在 70.71%–88.89% 的实例里，提交结果都是「定位了一部分、漏了一部分」；GPT-6-Astra 在定位到至少一个缺陷之后，83.00% 的实例里剩下的共存缺陷就不管了。找到第一个失败就收工，这是 Agent 的通病。

这个现象我自己在跑多 Bug 场景时也隐约见过，只是没有量化到这么直白。看到 Table 3 才意识到，问题的根子不是单个 Bug 太难，是**探索会过早终止**。

### 偏科：哪类缺陷最抓不到

![图3：按缺陷类型分组的定位召回率](https://www.mulanai.com/fs/files/1126_ec52d543_fig_defe.png)

*图3：论文 Figure 3。左半 panel (a) 是函数级召回、右半 panel (b) 是 hunk 级召回，五列依次是 DeepSeek-V4.1-Flash、Kimi-K3、GLM-5.3、GPT-5.6-Sol、GPT-6-Astra。每一行是一种缺陷类型，括号里是实例数，底部色条 35→90，橙红系=实现不完整、蓝色系=实现错误、紫色系=通用编程错误。可以看到上半部分「Incomplete data processing (55)」「Missing input validation (25)」「Incomplete output (5)」整片偏橙红（低召回），下半部分「Typo / symbol error (3)」「Generic data-operation error (3)」「Loop / control-flow error (7)」明显偏蓝（高召回）。图注说明：这批实例有 442 条缺陷记录，430 条有类型标注，12 条未定标签被排除，另有 14 个替换实例还没做类型标注。*

图很直观：越靠近「没写完的功能」，颜色越冷不下来——Incomplete data processing（55 个实例）五个模型的函数/hunk 召回平均只有 50.88% / 50.23%；Incomplete output（5 个实例）hunk 召回均值 40.56%，是全场最低一档。反过来，拼写/符号错误、通用数据操作错误、循环控制流错误这些「写错了」的类型，召回能冲到 75–90。

我的解读是，写错的东西会报错，会抛异常，会有可见的失败信号；没写完的东西安安静静地少处理一种输入、少校验一个边界，运行时一片祥和，Agent 没有任何钩子去怀疑它。这跟前面 67.44% 的「跑了但没抓到」其实是同一个病的两张片子。

还有个细节挺有意思：论文在「文件级召回已完整」的子集里继续看，Missing input validation 那组 46 条记录里，95.65% 漏掉了参考函数、93.48% 漏掉了参考 hunk；Incorrect configuration 那组 48 条里是 89.58% / 91.67%。文件都找对了，函数还是挑不出来。而 Incorrect regular expression 组只有 44.00% 漏函数，平均函数召回 90.57%。也就是说，输入校验和配置这类缺陷，光找对文件远远不够，得往里钻。

### RQ4：失败到底失败在哪

作者人工标注了一批失败轨迹，把机制拆成两组数字。

测试构造这边：mock 配置错误占 37.5%，断言不匹配占 31.6%，API/参数错误 22.8%，无效输入或 setup 7.4%，运行时异常 3.7%，语法/集合类失败 1.5%。定位这边：过早终止搜索 36.0%，证据利用不足 30.9%，依赖链截断 25.0%；报告策略上还有保守省略 19.9%、把症状当原因 25.0%、粒度报错 4.4%。

两组数字合起来指向同一幅画面：Agent 观察到一条失败或一个异常栈，立刻锚定在第一个可见的错误帧或入口点，然后停了。上游的调用链、跨文件的数据流、执行日志，都不看了。交上来的报告记的是症状位置，不是根因路径。而报告那边又有个反向的小算盘——为了不让「报多了被扣分」拉低精确率，Agent 会主动少报几个候选位置，宁可漏也不肯错。作者管这叫 defensive reporting，拿完整性换精确率。

这段我读得挺有共鸣，因为它把一个纯技术指标（LP）和 Agent 的「策略选择」连起来了：评分规则本身在塑造 Agent 的行为。你越惩罚误报，它越保守，召回越难看。

### RQ5 消融：自己写测试到底值多少

这是全文我最关心的一组对照，也是唯一一个严格意义上的消融/对照实验：同一个 GPT-5.6-Sol + Codex，同样 100 个实例，一边只跑仓库现成测试套件，一边允许从 PRD 自己写测试，用同一套配对报告和参考标注打分。

| 测试套件 | File LR | File LP | Function LR | Function LP | Hunk LR | Hunk LP |
|---|---|---|---|---|---|---|
| 仓库现成测试 | 74.81 | 78.00 | 49.82 | 60.16 | 49.53 | 73.59 |
| Agent 自主写测试 | 79.80 | 75.26 | 52.59 | 58.55 | 52.22 | 70.34 |
| 变化(百分点) | **升 4.99** | 降 2.74 | **升 2.77** | 降 1.60 | **升 2.69** | 降 3.25 |

表：论文 Table 6（RQ5）。值是实例平均百分比；变化按未四舍五入的差值算，所以 Function LP 正文里写的是降 1.61，表里标注 1.60，别当成两个数打架。

自主写测试把文件/函数/hunk 的召回分别抬了 4.99 / 2.77 / 2.69 个百分点——这正是摘要里那组数。但代价也写得很清楚：三个粒度的精确率全降了，而且这个增益**不平均**，函数召回只在 31% 的实例里改善、hunk 召回只在 35% 里改善，三个粒度的配对变化中位数都是零。你想想看，一半以上的实例里，自己写测试没带来任何召回提升。

再拆一层更清醒：报告的函数位置从 868 涨到 1,011（+16.47%），被认可命中的参考函数只从 521 涨到 572（+9.79%）；hunk 报告数 +15.37%，命中数 +9.44%。报得比找得快，精确率自然往下掉。作者把话说得很克制：自主测试拓宽了发现，但「报哪些位置」仍然是精确率的瓶颈。

我觉得这组消融才是整篇论文最实在的贡献。它没有喊「自主测试更好」，而是把「好多少、在哪好、代价是什么」摊开了。4.99 个点不算大，但它证明了一件事：主动调查这个动作本身是有信息增量的，光跑现成套件会漏东西。对做 Agent 训练的人来说，这比一个漂亮的 SOTA 数字有用得多。

## 💡 我的判断：这更像一份给奖励设计写的体检报告

先说定位。这不是底层突破，也不是把几个模块拼一拼的工程整合，它是一篇**评测范式论文**——重新定义了「考什么」，然后用一组设计得挺克制的指标把现状量出来。基准本身（100 实例、PRD、双任务、四维度）是骨架，那组「脱钩」的数字才是肉。

它跟同期那批讨论 RLVR 奖励可信度的工作是一路人。今年陆续有研究在讲同一件事：测试通过率当 reward，会碰到「测试太弱」「verifier 不完整」「reward 涨了但真实正确性没涨」这些坑，于是有人上 Agentic Quality Judge 先区分「能跑」和「可信」，有人做轨迹级行为监控去堵搜索原始 PR、改测试脚本这类捷径。SpecEngineeringBench 从另一个口子切进去，给的证据更具体：91.47% 的 HP 和 26.36% 的 F2P 摆在同一张表里，直接说明**「测试通过」和「测试有区分度」是两个可以完全解耦的能力**。

这对训练数据构造的含义挺直接。如果你的 SFT/RL 数据是从「跑通测试」的轨迹里筛出来的，那筛出来的很可能是一批最会「顺着实现写断言」的样本；如果你拿 HP 或覆盖率当密集奖励，Agent 有充足的空间把 reward 刷高而一点缺陷都不暴露。论文自己也在结论里点了这层：随着需求被自动扩写成规格，验证实现是否符合规格会成为自主开发的瓶颈。我的建议更具体一点——构造这类训练数据时，可以把 F2P 之类的区分度信号、以及「定位到函数/hunk」的粒度信号单独拎出来当奖励项，别让通过率一家独大；RQ4 那组失败机制分布（mock 配置 37.5%、过早终止 36.0%）甚至可以反过来当难例挖掘的标签来源。

该挑的刺也得挑，不然就成了软文。

其一，语言单一，全是 Python。78 个仓库、16 个应用类别看着铺得开，但类型系统、构建链、测试框架的差异完全没覆盖，跨语言能不能复现这套「脱钩」，原文没给证据。作者自己在结论里也只把「扩展到更多语言」列为 future work。

其二，PRD 是人写好的。作者把「需求自动扩写成规格」当成远景，可现实里更难的恰恰是需求本身含糊、自相矛盾、缺边界那种情况。给一份干净 PRD，某种程度上又把「what」这层的难度削掉了一截——比不给线索难，但离真实的规格工程还有距离。这块我也不是特别确定该怎么量化，可能得等他们说的 agent-generated specifications 那一版。

其三，标注有缺口。RQ3 那批只有 86 个实例做了类型标注、442 条缺陷里 430 条有标签、12 条 unresolved 被排除、14 个替换实例还在等标注。缺陷类型那张热力图的结论是建立在残缺标注上的，作者标了，但读的时候心里得有数。

其四，也是最想说的一点：主表里每个百分比列都做了 top-3 着色加粗，一眼看过去「谁第一谁第二」很清楚，可七模型在 F2P 上的绝对水平全在 21–34 之间，这种「矮子里拔将军」的呈现容易让人误读成模型之间有实质差距。真正该被强调的是那条横贯全表的鸿沟，不是列内的排名。另外 HP 用池化、其余指标用实例平均，两个口径放一张表里，跨列直接比大小其实不严谨，作者在图注里写清了，但读者很容易顺手就比了。

还有个我惦记的点：Task 2 允许写临时探针测试，Task 1 的套件是独立评分的，两者是解耦的。这设计干净，但论文并没有直接回答「一份好测试套件能不能直接换来一份好缺陷报告」——它只证明了这两件事都难，且难在不同地方。

## 🔧 收尾：如果你也在做 Agent，这几个动作可以马上试

如果你在训 Coding Agent，别再把「测试通过率」单独当 reward，把区分度信号（F2P 类）和定位粒度信号拆出来，看看 reward 曲线和这两条线是不是还同向。如果你在做评测，别拿覆盖率当测试质量的代理指标，这篇论文的 Table 2 就是反例。如果你在做 Agent 产品，值得给「找到第一个失败之后继续查」加个显式机制——RQ2 里 83.00% 的实例在定位到一个缺陷后就停了，这个数字比任何模型排名都值得修。

还有一个更根本的问题没解决：当我们把需求自动扩写成规格，谁来验证规格本身是对的？SpecEngineeringBench 把「验证实现」这一步的难量化出来了，可「验证规格」还悬着。这篇给了一个挺扎实的经验地基，但地基之上那层楼，还没盖。

如果你也在跟 Coding Agent 的 reward 死磕，这篇 2611.32973 建议存下来，尤其 Table 1 和 Table 6，比结论段落值钱。
