# MIRIX-2.0：长期记忆不该为了压缩，弄丢原始证据

一个助手如果记得你买过 Suica 交通卡，也记得你说过“坐地铁会紧张”，它在你下次询问东京出行时，就不该再推荐你买卡，更不该只甩来一份地铁攻略。真正难的不是把这些话塞进数据库，而是几个月后仍能找回那张卡、那条顾虑，以及它们分别来自哪次对话。

长期记忆系统常在这里掉进一个三角困境：压缩成摘要，细节可能永久消失；保留全部记录，检索范围会随历史膨胀；把经验训练进参数，又离不开训练流程，也难以直接用于闭源模型。MIRIX-2.0 给出的答案很干脆：**原始记录永远是事实源，超图只负责做索引，整理记忆时不准改写证据。**

> **核心摘要**：MIRIX-2.0 用六个类型化记忆 Agent 保存完整记录，再以可溯源的 n 元超图连接事件、实体和时间；查询只在明确预算内取证据，AutoDream 则在线下合并重复实体、蒸馏任务技能。它在 LoCoMo 达 91.4%，在 LongMemEval-S 达 72.6%，比最强基线高 14.3 个点。我的判断是，这不是凭空发明“记忆图”，而是一套边界清楚的工程整合：最值钱的不是超图名词，而是证据不可被索引和压缩破坏的约束。

## 一、记忆系统真正难的是：既能找到，又不能弄丢

假设用户三次提到同一个项目：第一次说预算 420 美元，第二次改了日期，第三次补充同行人。系统若只留下“用户讨论过项目”的摘要，后续问答就很难还原具体数字；若把每段原文都扔给向量检索，相似却无关的记录又会越积越多。

图记忆也不是天然解法。普通知识图谱喜欢把事实拆成二元三元组，例如“航班—出发地—东京”“航班—同行人—Mia”。拆完以后，出发地、承运人、日期和同行人仍属同一次航班这件事，反而可能散掉。HyperMem 已经用主题、片段和事实三层超图来保留高阶关联，说明“超图用于长期记忆”本身并不是 MIRIX-2.0 的新发明。它进一步追问的是：**图里的一个事实，能否带着我回到生成它的原始记录？**

不同路线牺牲的东西，可以这样看：

| 记忆路线 | 得到的便利 | 容易付出的代价 |
|---|---|---|
| 参数化记忆 | 经验进入模型权重或潜在状态 | 需要训练，难覆盖闭源模型 |
| 摘要与压缩记忆 | 存储紧凑，上下文较短 | 被丢弃的细节无法恢复，摘要可能写错 |
| 平坦向量记忆 | 完整记录仍在，实现直接 | 历史越长，候选越多、噪声越大 |
| 二元图记忆 | 实体关系清晰 | n 元事实被拆碎，角色与时间联系易丢失 |
| 层级或超图记忆 | 能组织主题、事件及高阶关系 | 若从摘要逐层向下找，细节仍受上层入口限制 |
| MIRIX-2.0 | 完整证据、关系索引、受控读取并存 | 写入和建图成本更高，系统组件更多 |

说实话，我很喜欢论文把“存储”和“索引”分开的态度。数据库里的记录是账本，超图只是目录。目录可以重建、去重、优化，但不能趁没人注意时把账本改掉。

## 二、MIRIX-2.0 的核心：一张证据底表，一张可溯源超图

![图1：MIRIX-2.0 总体架构](https://www.mulanai.com/fs/files/1117_e44c0e2e_fig1.png)

*图1：系统总览。上方从左到右依次是记忆形成、类型化证据平面、可溯源超图和图驱动的受控检索；下方是位于写入路径之外的 AutoDream。语义记忆只合并身份锚点并重连引用，程序记忆则由 Distiller 和 Curator 从任务会话中整理技能。图中还明确画出 fail-soft：图索引失败不应回滚已经提交的原始记忆。*

### 2.1 六个写入 Agent，不是六份彼此隔绝的摘要

Meta Memory Manager 接收对话或多模态输入，决定本次需要更新哪些记忆类型。六类记忆各有自己的 writer 和 schema：

| 类型 | 主要职责 | 是否进入超图索引 |
|---|---|---|
| Core | 持久保存用户与 Agent 的核心状态 | 否 |
| Episodic | 保存带时间定位的具体事件 | 是 |
| Semantic | 保存较稳定的事实和概念 | 是 |
| Procedural | 保存可执行流程与技能 | 否 |
| Resource | 保存文档和多模态资源 | 否 |
| Knowledge Vault | 保存敏感的原文取值 | 否 |

情节记忆和语义记忆的每条记录可写成：

$$m=(i,k,y,\tau_e,\tau_m,\rho,\mathbf z)$$

这里，$i$ 是不可变的行标识，$k$ 是记忆类型，$y$ 是完整文本，$\tau_e$ 与 $\tau_m$ 分别表示事件发生时间和被提及或写入的时间，$\rho$ 记录来源及 chunk 溯源，$\mathbf z$ 是检索 embedding。

这组字段里有个很实用的细节：发生时间和提及时间分开。用户今天说“上周已经跑了三次步”，与上周三次跑步各自发生，并不是同一种时间信息。混在一起，后面的时间问答很容易翻车。

写入顺序也被硬性规定：**先提交向量数据库中的完整记录，再构建图。** 图写入失败，记录仍保留；图读取报错，则退回直接证据检索。这个设计不花哨，却比多一层复杂摘要更接近生产系统需要的故障边界。

### 2.2 n 元事实帧：关系不是一串散落的二元边

超图 $G_u=(\mathcal A_u,\mathcal F_u,\mathcal E_u)$ 包含三类对象：实体或概念锚点、具象化的事实帧，以及带角色类型的关联边。

一次航班不必被拆成数条互不知情的三元组，而可保留为一个事实帧：谓词是“乘坐航班”，agent、origin、destination、carrier、companion 等角色各自连接相应锚点，价格、日期、数量作为字面属性挂在帧上。事实帧还保存 $C_f$，也就是支持它的原始数据库行标识。

这带来两层收益。读图时，参与者仍处在同一个事件结构里；读完图后，回答器拿到的不只是“图说它是真的”，还能拿到原始记录。你想想看，如果回答只能引用另一个模型生成的摘要，所谓可解释性其实只往前退了一步。

事件身份也做了区分。同一个持久事实被多次提到，可以在一个语义帧上累积引用；情节事件则额外加入 occurrence key：

$$\operatorname{id}_E(f)=H(u,p,\sigma(f),\chi(f))$$

$\chi(f)$ 优先取显式事件时间；没有事件时间时，退回不可变记忆行 ID。于是，同一 dated event 的重复描述能合并，两次措辞相似却没有日期的跑步不会被粗暴压成一次。这个规则挺朴素，但正中时间记忆的要害。

### 2.3 查询不是“搜得越多越好”，而是按题型领预算

查询先由确定性 planner 分类为 single、temporal、intersection、list-union 或 count，再得到关系、约束、答案类型、时间条件与两项行数预算。检索从匹配问题的锚点进入，而不是先扫整段历史。

| 查询算子 | 基础召回行数上限 $B_q^B$ | 关系引用行数上限 $B_q^R$ |
|---|---:|---:|
| Single | 6 | 4 |
| Temporal | 6 | 6 |
| Intersection | 7 | 7 |
| List-union | 7 | 9 |
| Count | 8 | 12 |

锚点侧先召回 15 个候选，再综合向量相似度、精确提及、词面重合、谓词兼容性和多词特异性排序，同时用对数度惩罚压制“什么都连”的泛化枢纽。事实帧侧则按关系、实体、字面约束、答案类型、时间、交集对象、角色和事件状态打分。

证据沿两条通道返回：基础召回通道提供锚点直接关联的记录，关系引用通道提供图事实及其引用行。融合时优先保留引用证据并去重。回答 Agent 最多调用检索器五次；草稿若显式表达不确定、缺少题目要求的值，或与证据账本冲突，还会触发一次补搜和改写。

这里要把论文的“bounded”说准确：**预算约束的是一次问题能检查的证据规模，不等于已经证明端到端延迟与历史长度严格无关。** 图索引、模型调用和工程实现仍会影响真实延迟。

### 2.4 AutoDream：语义记忆做去重，程序记忆做蒸馏

AutoDream 不在写入的关键路径上运行，并刻意用两套方式处理两类记忆。

语义侧只处理新写入的 semantic frontier。对 person、organization、location、object、concept 这些身份相对稳定的类型，系统从名称索引取最近邻，要求余弦相似度至少 0.86，再让 LLM 判断两者是否指同一实体。确认合并后，只统一锚点、别名、引用集和图边，原始记录、事件锚点与事实帧都不改写；否定判断会缓存，避免下轮重复付费。

程序侧则更像经验整理。Distiller 根据任务 transcript 的原文引文判断结果，提炼“值得复用的做法”和“应当避免的错误”；Curator 再创建或编辑技能。技能编辑若声称来自某段经验，必须能通过引文校验。

![图2：用户中心记忆的完整链路](https://arxiv.org/html/2611.12068v1/mirix_user_centric.png)

*图2：Mia 在 5 月 2 日提到已买 Suica，在 5 月 9 日提到安装 TripIt 且对地铁感到紧张。系统保存情节与语义记录，并以 owns、uses、concern 三个图事实连接 Mia、Suica、TripIt 和 Tokyo transit。5 月 30 日询问东京出行时，检索返回 3 个事实和 5 行证据，回答同时利用已有工具并照顾地铁顾虑；每个说法都能回指来源日期。*

![图3：失败任务如何转成可复用技能](https://arxiv.org/html/2611.12068v1/mirix_agent_centric.png)

*图3：早期 WebShop 任务要求购买 30 美元以下的蓝色不锈钢水瓶，Agent 却因未设置颜色而买下默认灰色。AutoDream 提炼出“设置颜色和尺寸前不要购买”和“先核对价格”两类经验，Curator 将约束检查加入购物 routine。后续任务因此依次核对价格、选择蓝色与 32 oz、验证全部约束后再下单。图中 steel bottle 与 stainless steel bottle 的身份合并也只改图，不改源记忆。*

## 三、实验：对话记忆提升扎实，但不是所有任务都赢

### 3.1 实验配置与消融口径

用户记忆的 answerer 和 extractor 使用 gpt-4.1-mini，温度 0、seed 42；topic extractor 使用 gpt-4.1-nano，MIRIX-2.0 的 embedding 为 text-embedding-3-small。LoCoMo 与 LongMemEval-S 由 gpt-4o-mini 做 majority-of-3 评判，文档任务使用字符串或选项精确匹配。

三个配置别混淆：

| 配置 | 图索引与检索 | AutoDream | 对应含义 |
|---|---|---|---|
| M0 | 无 | 无 | 平坦向量记忆，对应 MIRIX-1.0 |
| M1 | 有 | 无 | 只增加超图 |
| M2 | 有 | 有 | 完整用户记忆系统 |

文档 QA 和计时实验用的是 M1，不是完整 M2。这个口径在解读效率数字时尤其关键。

### 3.2 对话消融：超图管连接，AutoDream 管入口

![图4：LoCoMo 与 LongMemEval-S 组件消融](https://www.mulanai.com/fs/files/1117_3e68d483_fig4.png)

*图4：M0、M1、M2 在两个对话基准上的递进结果。LoCoMo 总分为 85.7、88.4、91.4；LongMemEval-S 为 58.8、70.0、72.6。图中还列出 LoCoMo 的 multi-hop、temporal、open-domain 和 single-hop 分项，三种配置呈一致上升。*

| 配置 | Overall | Multi-hop | Temporal | Open | Single-hop |
|---|---:|---:|---:|---:|---:|
| M0 | 85.7 | 83.3 | 85.0 | 70.8 | 88.3 |
| M1 | 88.4 | 89.0 | 86.0 | 71.9 | 91.1 |
| M2 | 91.4 | 91.8 | 89.4 | 74.0 | 94.1 |

M0 到 M1，LoCoMo 总分涨 2.7 个点，multi-hop 涨 5.7 个点；M1 到 M2，总分再涨 3.0 个点，temporal 涨 3.4 个点。LongMemEval-S 上，超图一步就带来 11.2 个点，AutoDream 再带来 2.6 个点。

这个结果与方法分工是吻合的：n 元帧把相关证据连起来，身份合并让同一实体的入口更完整。不过作者也承认，表格只证明整组组件的结果，没有逐题审计检索记录和锚点合并，因此“为什么涨”仍是解释，不是直接因果证据。

### 3.3 五个 QA 基准：四个领先，DetectiveQA 暴露边界

![图5：五个 QA 基准上的系统对比](https://www.mulanai.com/fs/files/1117_c776e86c_fig5.png)

*图5：红色 MIRIX-2.0 在 LoCoMo、LongMemEval-S、SHDocQA 和 MHDocQA 上最高；DetectiveQA 则由 MemoryBank 的 67.6% 领先，MIRIX-2.0 为 64.8%。文档三项使用 M1，两个对话项使用 M2。*

| 方法 | LoCoMo | LongMemEval-S | SHDocQA | MHDocQA | DetectiveQA |
|---|---:|---:|---:|---:|---:|
| mem0 | 82.9 | 56.3 | 48.0 | 22.0 | 53.5 |
| A-Mem | 68.3 | 45.0 | 14.0 | 20.0 | 62.0 |
| MemoryBank | 59.5 | 39.7 | 34.0 | 28.0 | 67.6 |
| Graphiti | 58.4 | 23.0 | 50.0 | 43.0 | 54.9 |
| HyperMem | 91.0 | 58.3 | 52.0 | 49.0 | 66.2 |
| MIRIX-2.0 | **91.4** | **72.6** | **83.0** | **71.0** | 64.8 |

最抓眼的是文档单跳与多跳：83.0% 和 71.0%，分别比 HyperMem 高 31.0 和 22.0 个点。保留原文细节，同时返回事实帧及引用行，确实很适合这类证据密集任务。

但别只看最高分。LoCoMo 上 MIRIX-2.0 只比本次复跑的 HyperMem 高 0.4 个点，而且 HyperMem 原论文报告的是 92.73%。两者运行结果口径不同，不能据此宣布稳定反超。MIRIX-2.0 的 open-domain 与 single-hop 也仍低于本次 HyperMem 的 76.0% 和 95.2%。

DetectiveQA 更值得盯住：MemoryBank 67.6%、HyperMem 66.2%、MIRIX-2.0 64.8%。把证据组织好，并不会自动补齐侦探式推理。论文没有做错误拆解，所以目前无法判断是证据没取回，还是取回后没推理对。

### 3.4 个性化生成：指标领先，不等于用户真的更喜欢

MemoryCD 的跨域评论摘要中，MIRIX-2.0 四项指标都最高：ROUGE-1 为 0.1603，ROUGE-L 为 0.1510，BLEU-4 为 0.0209，BERTScore-F1 为 0.8754。对应的最强基线值分别为 0.1567、0.1430、0.0162 和 0.8749。评论生成任务也在两种设定的四项指标上取得最高报告值。

不过，单域摘要的 BLEU-4 仍由 long-context 的 0.0249 领先，MIRIX-2.0 为 0.0234。更关键的是，ROUGE、BLEU 和 BERTScore 不直接衡量事实一致性、偏好满足度或真实用户满意度；该实验记录也没有标清 M0、M1、M2 配置，不能拿它单独证明 AutoDream 的功劳。

### 3.5 程序记忆：学会流程有用，也可能干扰原本会做的任务

![图6：ALFWorld 与 WebShop 的 held-out 任务成功率](https://www.mulanai.com/fs/files/1117_b2c28a81_fig6.png)

*图6：三组柱状结果分别对应 ALFWorld 的 GPT-6 Luna、ALFWorld 的 GPT-5.6 Luna 和 WebShop 的 GPT-6 Luna。橙色 MIRIX-2.0 均取得最高均值，但误差线不小，尤其第二组；ReasoningBank 在 GPT-6 Luna 上还低于无记忆基线。*

| 基准与模型 | No memory | ReasoningBank | AWM | MIRIX-2.0 |
|---|---:|---:|---:|---:|
| ALFWorld，GPT-6 Luna | 69.4 ± 0.7 | 66.9 ± 2.8 | 73.6 ± 1.9 | **76.4 ± 6.2** |
| ALFWorld，GPT-5.6 Luna | 54.2 | 52.2 | 58.0 | **61.7** |
| WebShop，GPT-6 Luna | 31.9 ± 1.8 | 25.7 ± 3.8 | 36.0 ± 4.3 | **37.4 ± 2.1** |

每种记忆方法在相同训练任务上学习：ALFWorld 39 个、WebShop 40 个；随后冻结记忆，在 134 个 held-out ALFWorld episode 和 140 条 WebShop 指令上测试，重复三次。

MIRIX-2.0 的均值最高，但 GPT-6 Luna 下标准差 6.2 个点，GPT-5.6 Luna 下更达 14.0 个点。三次运行不足以证明它稳定优于 AWM。分任务看也不是普涨：Clean 从 60.2% 到 74.2%，Heat 从 47.8% 到 73.9%，Pick、Look、Pick Two 却低于无记忆。经验不是越多越好，过时或不合场景的 routine 会抢 actor 的注意力。

MetaClaw-Bench Part I 进一步区分了“题目得分”和“文件产物完成率”：

| 模型 | 技能模块 | Accuracy | Completion |
|---|---|---:|---:|
| GPT-5.2 | Baseline | 41.1 | 14.7 |
| GPT-5.2 | MetaClaw Skills | 44.0 | 17.1 |
| GPT-5.2 | MIRIX-2.0 | **49.2** | **27.7** |
| Qwen3.6-35B-A3B | Baseline | 40.3 | 12.1 |
| Qwen3.6-35B-A3B | MetaClaw Skills | 51.8 | 30.8 |
| Qwen3.6-35B-A3B | MIRIX-2.0 | **52.7** | **30.8** |

GPT-5.2 上，完成率从 MetaClaw Skills 的 17.1% 提到 27.7%，涨幅比题目得分更有看头；换到 Qwen3.6-35B-A3B，得分只多 0.9 个点，完成率持平。还要留意，GPT-5.2 基线取自 MetaClaw 论文报告值，并非完全受控的同场复跑。

## 四、效率账：查询更快，写入账单并不会消失

![图8：五个用户记忆基准的写入与回答耗时](https://www.mulanai.com/fs/files/1117_7f23b194_fig8.png)

| 基准 | HyperMem 回答秒数 | M0 回答秒数 | M1 回答秒数 |
|---|---:|---:|---:|
| SHDocQA | 10.55 | 3.76 | 5.45 |
| MHDocQA | 10.65 | 7.46 | 9.01 |
| DetectiveQA | 13.05 | 5.11 | 7.24 |
| LoCoMo | 9.70 | 未报告 | 5.46 |
| LongMemEval-S | 10.73 | 未报告 | 10.10 |

相对 HyperMem，M1 五项都快；相对平坦 M0，三个文档任务反而都慢。图检索不是天然便宜，它只是把更多工作提前放到 ingestion，并在查询时多做结构化证据处理。

写入开销很实在：SHDocQA、MHDocQA、DetectiveQA 的 M1 ingestion 分别为 23,784、55,301、39,491 秒，约为 M0 的 3.8 到 4.0 倍。DetectiveQA 上，M1 回答 token 也达到 1.16M，高于 HyperMem 的 0.35M，同时准确率还更低。延迟、token 和质量必须分开算账。

程序记忆也不是必然省 token。WebShop 上，MIRIX-2.0 每轮训练与测试 token 为 1.815M 和 4.975M，是三种记忆方法里最低的；ALFWorld 上测试 token 却为 3.813M，高于 ReasoningBank 的 3.351M 和 AWM 的 3.674M。步骤变少，单步携带更多流程上下文，总 token 仍可能上升。

## 五、我的判断：最值钱的是约束，不是又画了一张图

我觉得 MIRIX-2.0 最值得工程团队借走的，是三条可以写进系统验收标准的约束。

**原始记录是 system of record。** 图、摘要、技能都能重建，但源行不可因整理而消失。图写入失败不回滚记录，图读取失败有降级路径，这比单纯追求一个漂亮架构更接近可运维系统。

**返回事实时必须带回出处。** n 元帧保留参与者角色，引用行保留具体证据。对需要审计、排错、解释回答来源的产品，这比只返回 top-k 文本块更有用。

**记忆整理要限定权限。** 语义 AutoDream 只能合并身份和重连引用，不能重写事件；程序 AutoDream 虽会修改技能，却要求经验与引文对应。权限越明确，自动化整理越不容易把错误扩散到整库。

问题也同样清楚。组件消融是成组开启，无法单独判断 n 元帧、源行引用、occurrence identity、回答验证器和六 writer 路由各贡献多少；没有报告 merge precision、源细节保留率、技能溯源覆盖率。用户记忆结果来自单次运行并部分依赖 LLM judge，Agent 结果只有三次运行且波动较大。完整 M2 没有计时，现有证据不足以把 M1 的效率数字直接贴到全系统身上。

所以，这不是“长期记忆已经解决”的论文。它更像一份设计得很认真的系统答案：用更多写入成本和更复杂的管线，换更可追溯、更受控的读取。如果你正在做个人助手或跨任务 Agent，我会优先试它的证据分层、预算检索与离线去重；对自动技能蒸馏则会更谨慎，先加任务级回归测试，再让它改生产 routine。

长期记忆真正需要的，也许不是让模型“记得像个人”，而是让系统在每次压缩、合并和复用之后，仍能回答一句很朴素的话：**你这个结论，是从哪条原始经历来的？**
