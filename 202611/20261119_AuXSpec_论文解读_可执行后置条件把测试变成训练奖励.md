# 让 Lean 规格"跑"起来：AuXSpec 用可执行后置条件把测试变成训练奖励

## 核心摘要

模型写代码早就不是新闻了，可"怎么证明这段代码真的对"这件事一直卡在一个很不起眼的地方：规格（specification）得由人写。在 Lean 这种交互式定理证明器里手写前置/后置条件又慢又吃专家，公开数据集 Clever 只有 161 道题、Verina 只有 189 道题，规模根本喂不饱训练。想训练一个"把自然语言题目自动翻成 Lean 规格"的模型，真正的拦路虎不是生成，而是**没有便宜的反馈信号**来判断生成的规格对不对——代码生成能用测试用例一跑就给奖励，规格是个 `Prop` 命题，跑不起来。AuXSpec 的解法挺巧：给每个声明式后置条件配一个能执行的 Bool 孪生兄弟，用一条**后置条件等价定理**把两者在所有合法输入上绑死，之后任意数量的测试用例直接 `#guard` 执行就行，证明只在造数据时做一次。靠这个执行式奖励，作者合成了 3,037 道 LeetCode 题、扩到 19.5K SFT 样本，把 Qwen3.5-9B 的 SpecGen pass@4 从 0.7% 拉到 82.7%、Qwen3.8-27B 从 14.3% 拉到 84.3%，域外的 Verina 上从 7.0%/21.9% 双双干到 90.5%，27B 模型在域内超过所有前沿闭源模型。我的判断是：这不是底层理论突破，而是一次把"证明成本"从训练环路里搬出去的工程重构，思路干净、数据扎实、负结果也敢写，做形式化、做 RL 奖励设计的人都值得细读。

## 🎯 一个被卡了很久的死结：怎么便宜地判断"规格写对了没"

你有没有碰到过这种局面：模型写代码越来越溜，跑一遍测试用例一测一个准，可你心里还是不踏实——测试没覆盖到的输入怎么办？形式化验证给的是更强的保证：给程序配一份规格（前置条件界定合法输入，后置条件刻画正确输出），让 Lean 证明"对所有合法输入，实现都满足规格"。这个保证的强度取决于规格本身有没有把题意写对。

问题就出在这。规格太弱，带 bug 的实现也能通过验证；规格写错，正确的实现反被拒之门外。而写一份高质量的 Lean 规格，得把可能含糊的自然语言翻成无歧义的逻辑命题，还得懂 Mathlib、懂类型类、懂终止性。人工策展的结果就是 Clever 161 题、Verina 189 题这么个量级，谈"规模化"有点勉强。

于是很自然的念头是：训练一个自动形式化（autoformalization）模型，把题目直接翻成规格。可训练需要反馈，代码生成那边反馈来得极便宜——输入输出测试一跑，对就给 1 分。规格这边不行，因为它是一个 `Prop`，不是能执行的函数。以前在 Lean 里干这件事，主流是把每个测试用例变成一个待证定理（论文里叫 symbolic specification testing），或者另写一份实现代码、再证明两份东西的对应关系（Table 1 里 VeriSpecGen、Verina、Clever 都在这条路上）。前者遇到无界量词的规格，证明可能根本找不到，找不到就得挂起或者交给 LLM 裁判；后者等于把"写规格"的活儿又加了一份"写实现 + 写对应证明"。两条路都贵，贵到没法当 RL 的每一步奖励。

说实话，我的第一反应是：这不就是差一层"可执行视图"吗？代码生成能跑测试，是因为代码是 `def`；规格是 `Prop`，天生不能跑。要是能给 `Prop` 挂一个 `Bool` 的镜像，并且证明两者等价，测试用例不就能直接跑了吗？AuXSpec 干的就是这件事，而且它把这件事做成了一个可以批量造数据、批量发奖励的完整框架。

## 🏗️ 核心方法：给每个后置条件配一个能执行的孪生兄弟

一句话讲清核心 idea：一个 AuXSpec 题目文件里，同一个行为被写了两遍，一遍是给人看、给证明用的声明式 `Prop`，一遍是给测试跑的 `Bool`，中间用一条等价定理锁住。

具体到声明（论文 Table 6），每道题固定六个部件：

| 部件 | Lean 声明 | 作用 |
|---|---|---|
| 前置条件 | `isValidInput` | 可执行的 Bool 谓词，编码输入约束 |
| 后置条件 | `<algo>_spec` | 关联输入与输出的 `Prop` |
| 可执行后置条件 | `<algo>_check` | 关联输入与输出的 Bool 函数 |
| 后置条件等价定理 | `<algo>_check_iff_spec` | 证明 `_check` 在合法输入上判定 `_spec` |
| 实现 | `<algo>` | 计算输出的全函数 |
| 正确性定理 | `<algo>_correct` | 证明 `<algo>` 在合法输入上满足 `_spec` |

关键在 `_check` 怎么来。两条路（摘要里写得很清楚）：能走**类型类解析**就直接走，Lean 里只要 `Prop` 有 `Decidable` 实例，`decide` 就能把它变成一个 Bool，`_check` 写成 `decide (<algo>_spec input result)`，两者等价由构造保证，证明长度为 0；走不通（比如规格里有做不出判定的量词），就单独定义一份 `_check`，再补一条等价证明。论文数据里 35.5% 的题（1,079/3,037）走的是 decidable 这条路，剩下的 1,958 题单独定义、等价证明中位数 112 行、P90 达 394 行。

把这条等价定理写出来大概长这样，读一遍就懂它为什么值钱：

```lean
theorem algo_check_iff_spec (input) (result) (h : isValidInput input) :
    algo_check input result ↔ algo_spec input result := by
  -- 证明只做一次，插在造数据阶段

theorem algo_correct (input) (h : isValidInput input) :
    algo_spec input (algo_impl input) := by
  -- 300 道测试题上做完整证明，用来当评测的 Verified 参考
```

有了 `↔`，测试用例就不需要逐个变成待证定理了。你直接 `#guard algo_check 526 true`、`#guard !(algo_check 526 false)`，编译器一跑就知道结果——`#guard` 表达式为假时编译直接失败。论文把测试按被测部件和错误类型分层（Table 7）：L1a/L1b 查前置条件过严/过松，L2a/L2b 查可执行后置条件不完整/不健全，L3 查实现输出对不对，L4 查实现输出会不会被 `_check` 拒掉。这些测试在合成前就冻结，生成的 `#guard` 命令必须和冻结用例逐条对上。

这个设计我觉得最漂亮的地方，是它把"证明"这件事从训练热路径里彻底挪走了。合成阶段花力气证一次（而且 99.0% 的题不用改定义就能证出来），之后不管生成多少个测试用例、跑多少步 RL，都只是执行 Bool 函数。等等，那规格有没有可能"两个都错但错得一致"？作者自己也点了这个漏洞：等价定理只保证两个后置条件彼此同意，不保证它们跟题意一致。300 道 AuXSpec-Test 里人工评审揪出 9 道这种"证明了但一致地理解错了"的题（Appendix I.1）。所以语义正确性最终还是压在测试用例、LLM 裁判和人工评审三件套上，证明解决的是"执行反馈可信"，不是"意图对齐"。这个边界划得很清楚，我挺欣赏。

除了测试，还有四个 LLM 裁判把关（faithfulness 是否覆盖题意、non-tautology 是不是把解法重述了一遍而非刻画正确输出、completeness 在未测输入上是否接受正确输出、termination 实现是否终止）。数据过滤、专家迭代、RL、评测共用同一套接受标准——这点很关键，后面讲 RL 奖励时会看到，奖励就是照着这套标准逐阶段拆出来的。

## 🧠 训练：SFT 打底，再用 6 阶段渐进奖励做 RL

配置先摆一下（Table 8/9/10），做复现的人用得上：

| 项 | SFT | RL |
|---|---|---|
| 基座 | Qwen3.5-9B / Qwen3.8-27B | 各自的 SFT 模型 |
| 硬件 | 4 / 8 张 GH200 | 16 / 64 张 GH200 |
| 学习率 | 1e-5，cosine，warmup 5% | 1e-6，constant |
| Epoch / 步数 | 3 epochs | 1 epoch，434 步（9B）/ 208 步（27B） |
| 每 prompt rollouts | — | 16 |
| Clip / 温度 | — | 0.2 / 0.28，温度 0.7，top-p 1.0 |
| 序列长度 | 16,384 tokens | 16,384 tokens |

RL 算法是 DAPO 的变体，把 advantage 按 batch 的标准差而不是 group 归一化，还加了防重复和防 reward hacking 的一串处理。但真正的主角是奖励设计。

这里有个很现实的麻烦：SFT 模型在 SpecGen 上 pass@1 只有 10.1%（9B）和 18.7%（27B）。要是用"满足全部接受标准才给 1 分、否则 0 分"的二值奖励，绝大多数 rollout 都是 0，reward 方差极低，优化几乎推不动（论文引了 Razin et al., 2025 那个稀疏奖励的分析）。Table 18 的数据很直白：27B 的 SpecGen 里，二值奖励下只有 59.4% 的生成组有非零方差，换成渐进奖励是 91.6%。

于是作者把接受标准按顺序拆成 6 个阶段，rollout 在第一个失败的阶段拿到该阶段的分值：

$$r(y)=\begin{cases}1&\text{if }y\text{ passes all stages}\\ v_k&\text{if }k\text{ is the first stage that }y\text{ fails}\end{cases}$$

| 阶段 | 失败时奖励 | 含义 |
|---|---|---|
| 格式 | 0 | 没代码块、格式错 |
| 编译 | 0.1 | Lean 编不过 |
| 测试用例对齐 | 0.1 | 测试没调输出声明、或数量不够 |
| 测试执行 | 0.2 | `#guard` 跑挂了 |
| 非重言 | 0.1 | 规格把解法重述了一遍 |
| 整体质量 | 0.4 | LLM 裁判没放行 |
| 全部通过 | 1.0 | 接受 |

两个细节我盯着看了一会儿。一是"非重言"只给 0.1，比"测试执行"的 0.2 还低，作者解释是想让"把计算过程复述一遍"的规格排在连测试都没过的下面；附录里的回放实验说明这个值调成 0.3 就会出事——在没有满分组里，重言规格的 advantage 会翻正，模型就学会投机了。这种把奖励数值当成可调超参、还拿训练 rollout 回放验证的做法，比拍脑袋定权重扎实得多。二是两类"过了所有阶段但不给满分"的 rollout：枚举式规格给 0.4、正确但太慢的实现给 0.5，评测其实接受它们，但训练上故意压分，防止模型走捷径。防作弊还包括：测试必须调用输出的声明才算数（排除恒真测试）、硬编码答案或照抄给定用例直接 0 分、repair 原样返回 0 分。

自修复（self-repair）也进了训练：把当前策略失败的 rollout 连同编译器报错或裁判反馈存进 buffer，每个 batch 抽 40% 做单轮修复任务，最多修 3 轮，修复 rollout 的奖励从第一轮的 1 线性衰减到第 3 轮的 0.8。这么做的理由很朴素——避免训练和推理时的分布错配。

顺带一句，Appendix E 里还试了 on-policy distillation（把 27B-SFT 蒸到 9B-SFT），结果是负的：9B-SFT 的 AuXSpec-Test SpecGen pass@4 从 24.3 掉到 5.3，Verina Advanced 从 42.0 掉到 18.5（Table 23）。作者没藏这个，Figure 6-10 还专门剖了重复循环、decidable 形式使用率、近重复样本这些退化现象。一篇论文肯花五张图讲一个失败的尝试，比只报喜的更可信。

## 📊 实验：数字到底有多能打

|---|---|---|---|---|
| Claude-Opus-5 | 57.7 | 81.3 | 93.0 | 98.3 |
| Claude-Sonnet-5 | 13.8 | 39.3 | 54.8 | 73.0 |
| GPT-5.6-Sol | 29.8 | 59.7 | 80.0 | 96.3 |
| GPT-5.6-Luna | 9.5 | 28.7 | 39.9 | 71.3 |
| Kimi-K3 | 43.8 | 83.7 | 67.2 | 94.3 |
| DeepSeek-V4-Pro | 21.2 | 54.3 | 48.6 | 72.3 |
| DeepSeek-V4-Flash | 38.4 | 76.7 | 45.0 | 69.7 |
| Qwen3.5-9B（基座） | 0.2 | 0.7 | 8.2 | 18.0 |
| Qwen3.8-27B（基座） | 4.5 | 14.3 | 8.9 | 22.0 |
| AuXSpec-9B-SFT | 10.1 | 24.3 | 13.1 | 28.3 |

看到 0.2 → 58.6 这一列我愣了一下。基座 Qwen3.5-9B 在 SpecGen 上几乎是一道题都写不对（pass@1 = 0.2%），RL 之后 58.6%，连 Claude-Opus-5 的 57.7% 都压过去了。27B-RL 更狠，SpecGen pass@1 = 65.7%、CodeGen pass@1 = 94.8%、CodeGen pass@4 = 99.7%，四个任务里三个拿到全场第一，剩下 repair 类指标也都保持在最好的 2 个点以内。一个 9B/27B 的开源权重模型在自家格式上把一票前沿闭源模型按下去，这个幅度确实能打。

不过这里我得给自己泼点冷水：AuXSpec-Test 是作者自己合成、自己定义格式、自己设评测器的域内集，"主场优势"是客观存在的。真正能说明泛化的是下一张表。

| AuXSpec-9B-SFT | 34.9 | 65.6 | 36.5 | 71.4 |
| **AuXSpec-9B-RL** | **73.7** | **90.5** | **89.8** | **97.4** |
| **AuXSpec-27B-RL** | **84.5** | **90.5** | **89.7** | **93.7** |

（† 为 VeriSpecGen 原论文报告值，用同一 Verina 评测器打分，且只有不给测试用例的那一档；它的 63.9 是 pass@10，其余是 pass@4。这个口径差异得留意，直接比 90.5 和 63.9 会略微夸大差距，但 47.6 → 84.5 的 pass@1 是同口径的，26.9 个点没水分。）

两个 RL 模型在 SpecGen pass@4 都顶到 90.5%，比基座分别涨 83.5 和 68.6 个点；CodeGen 上两个模型 pass@1 都到 89 个点以上，把最好的基线 56.6%（Claude-Opus-5）甩开一大截。把测试用例放进提示词，两个 RL 模型的 SpecGen pass@4 还能从 90.5% 涨到 96.8%，而同样的用例给前沿模型只带来 5 到 24 个点的提升——说明自家模型更会把具体输入输出当约束用。

让我觉得最有说服力的其实是另一组对照。有人会质疑：你基座是 Qwen3.5-9B / Qwen3.8-27B，比 VeriSpecGen 用的 Qwen3-4B 强，赢在起跑线。作者专门补了公平性实验（Table 24/25）：从 VeriSpecGen-4B 的同一个基座 Qwen3-4B-Instruct-2507 出发，只换成自己的 SFT 数据和 RL 配方，Verina 无测试用例那档的 SpecGen pass@1 从基座 0.0% 一路训到 RL step 120 的 54.2%，反观 VeriSpecGen-30B-A3B 是 47.6%。同一个 4B 基座、方法不同，结果反超 30B 的模型——增益来自方法而不是基座，这条论证补得很到位。

### 消融：哪块砖真在承重

9B 配方逐项拆（Table 26，AuXSpec-Test），完整 RL 与三个变体：

| 配置 | 步/训练 prompt | SpecGen p@1 | SpecGen p@4 | CodeGen p@1 | CodeGen p@4 |
|---|---|---|---|---|---|
| AuXSpec-9B-SFT | 0 / 0 | 10.1 | 24.3 | 13.1 | 28.3 |
| 完整 RL | 210 / 6,186 | 46.7 | 71.7 | 74.9 | 92.0 |
| 去掉测试执行 | 150 / 4,796 | 31.4 | 53.7 | 37.6 | 62.3 |
| 去掉 LLM 裁判 | 150 / 4,556 | 20.0 | 35.7 | 54.8 | 75.3 |
| 去掉自修复 | 150 / 6,334 | 43.1 | 67.3 | 70.2 | 91.7 |

Paper 特意说明按"大致相同的训练 prompt 数"比较（去掉自修复的 step 150 用了 6,334 个 prompt，和完整 RL 的 6,186 接近）。我的读法是：**测试执行**和 **LLM 裁判**是两块真承重的砖，去掉后 SpecGen p@4 分别掉到 53.7 和 35.7，后者到后期还崩了一截（step 100 曾到 62.0，step 150 回落到 35.7，明显是奖励被钻空子了）；**自修复**的影响相对温和，67.3 对 71.7，差 4.4 个点。这个结论我信，因为它和渐进奖励的设计动机自洽——执行与裁判恰好是反馈信号最密集的两层。

### 几个不该被略过的数字

- **RL 提升的是采样效率，不是解题上限**。Table 22 统计 300 道测试题在 256 次采样内能否解出：SFT 和 RL 都能解 256 道（85.3%），RL 单独多解 33 道（11.0%），两者都解不出 10 道（3.3%）。可 pass@1 从 18.7% 涨到 65.7%。也就是说 RL 主要把"能解但很难采到"变成了"高概率一次采中"，而不是教会了模型全新的能力。这个区分挺重要，别把 pass@1 的暴涨全记成能力涌现。
- **修复循环要多轮才有意义**。ICPC-Eval 的 75 题上（Table 18 / Figure 3），pass@16 = 61.3%，带编译器 + 裁判反馈的 refine@16 = 82.7%，只给编译器消息的 refine@16 = 44.0%（还不如不修）。反馈质量比反馈次数要紧。
- **token 效率**。AuXSpec-27B-RL 每解出一道题的输出量低到 1.2 到 2.7 千 tokens（Table 14），论文说只用了最省前沿模型每个 solved 样本输出量的 20.3%。RL 把"想半天还想不对"的废话压掉了。
- **代价：通用能力掉点**。Table 15 是我不太愿意轻描淡写的一张表。27B 基座 AIME 25 = 84.1%，SFT 之后砸到 31.0%（−53.1 个点），RL 拉回 69.3%（仍 −14.8）；GPQA-Diamond 84.5 → 62.9 → 74.2；HumanEval+ 92.5 → 79.0 → 89.3。9B 那边 SFT 把 AIME 从 62.3 砸到 25.6，RL 拉回 52.2。专精化的税交得实实在在，做落地的人得先想清楚要不要交这笔钱。

## 🔬 训练分析里几个有意思的发现

Figure 2 的 RL 曲线有个现象：奖励只在合成题上算，可 Verina 的分数一路跟着涨（9B 的 SpecGen pass@1 从 37.3% 到 87.0%，27B 从 57.3% 到 91.9%）。Verina 是用提示词里看不到的测试用例、拿参考规格打分的，训练时模型根本没见过这些用例。作者的解释是策略学到了"忠于题目描述"这件事本身，而不只是背下了冻结用例。我觉得这个说法方向对，但严格讲还缺一个直接的因果证据，可能我的理解有偏差，这块留个问号。

Table 20/21 里关于"部分进展"的分析很见功力。枚举式规格拿 0.4 分、慢实现拿 0.5 分，这些是评测接受、训练却刻意压分的 rollout。回放发现，当一个 16 条 rollout 的组里满分组数超过 3/16（枚举规格）或 2/16（慢实现）时，这些部分进展的 advantage 就转负——模型于是被推着往真正的声明式规格、快实现上走。数据也印证了：修复轮把 74.1%（27B）和 54.6%（9B）的枚举规格改成了能过全部阶段的声明式规格；慢实现占比从训练早期的 14.5% 一度飙到 67.4%，到 27B 训练结束时回落到 0.4%。这种"奖励形状如何塑造策略"的细粒度复盘，比多报一张榜单有价值。

还有一个反直觉的小地方：Figure 6 显示 OPD 之后 92% 的 SpecGen 样本卡在"声明编译不过"这一步，而 CodeGen 样本从声明错误挪到了 guard 层错误、通过率没变。蒸馏把小模型往重复循环里带偏了，这也解释了 Table 23 那串负增益。

## 💡 我的判断

**这篇论文最值钱的地方，是把形式化反馈太贵这个老问题重新框成了一道接口设计题**。 它没有去卷更强的证明器、更大的证明搜索，而是问：能不能让声明式规格借一层可执行视图，把测试用例的廉价反馈引进来？答案是可以，代价是造数据时一次性付清等价证明的成本。35.5% 的题靠 `Decidable` 白拿、其余付平均 112 行证明，换来训练阶段每一步都零证明开销。这笔账算得很划算。

放到同期工作里看位置会更清楚。VeriSpecGen（arXiv 2604.10392，Ye et al., 2026b）走的是另一条路：把自然语言拆成原子需求，生成带 traceability map 的定向测试，失败时定位到具体子句做外科式修复，用 Claude Opus 4.5 在推理时做到 Verina SpecGen 86.6% pass@1，还顺手蒸馏出 343K 训练样本。那是**推理时的结构化引导 + 轨迹蒸馏**；AuXSpec 是**训练时的可扩展执行奖励**。两者都盯上了"规格反馈贵"，一个把成本摊在推理链路上，一个把成本挪到数据合成阶段。有意思的是 AuXSpec 拿 VeriSpecGen-30B-A3B 当开源 SOTA 来比，还在同基座实验里正面赢了它——但得注意 VeriSpecGen 那个 86.6% 是拿 Claude Opus 4.5 跑推理时框架的结果，跟开源 SFT 模型的 47.6% 不是一个赛道，别被数字串了台。

所以我的定位是：**工程重构级别的扎实工作，不是底层理论突破**。贡献拆开看——可执行规格格式（思路漂亮但概念不新，论文自己也在 Section 6 承认这种 pairing 在形式化方法里由来已久）、3,037 题带证明的数据集 + 300 题专家评审基准（真金白银的社区资产）、两个开源权重模型（可复现）。三项里我觉得数据集和 benchmark 的长期价值可能比方法本身还大。

要挑刺的话，有几个地方我保持警惕：

1. **域内主场**。AuXSpec-Test 的格式、评审器、接受标准全是作者自家的，"27B 超过所有前沿模型"这个说法换个格式还成不成立，没验证。域外 Verina 的结果补了大半，但也是 Lean 4 生态里的近邻。
2. **意图对齐没有闭环**。专家评审在 300 道测试题里找出 9 道"等价定理证了、但两个后置条件一致地理解错了题意"的题；对 100 个被自动接受的 RL 输出做复核，正确 90 道，10 道错**全部**出在 `isValidInput` 漏了输入约束（Table 44）。论文在 Limitations 里也承认：接受标准只用测试查 validity predicate，缺一个把谓词和题目约束对照的裁判。这是目前最明确的短板。
3. **证明仍是事后补**。生成出来的规格和实现被接受时，两个定理的证明都还是 `sorry`；等价定理是事后给 RL 输出补证的（99.2% 成立）。也就是说"接受"和"已证明"在训练环路里始终是两件事。
4. **修复只评了一轮**。训练里支持最多 3 轮自修复，评测只跑单轮，多轮能补回多少与前沿模型的差距，作者自己列为未来工作。

**工程上能带走什么**？ 如果你在做带验证器的 RL（代码、SQL、定理证明、Agent 工具调用都算），这篇最值得抄的是那条思路：别死磕"终局二值奖励 + 稀疏信号"，把接受标准按执行顺序拆成分阶段的稠密奖励，然后**用训练 rollout 回放去校验每个阶段的值会不会诱发投机**（重言 0.1 那个例子是范本）。另一条是：当你的验证信号本身太贵时，先想想能不能给它造一个便宜的近似视图，再用一次性证明把这个近似和真信号锁死——这个模式比具体用 Lean 还是 SMT 通用得多。至于要不要照搬专精化，先看看 Table 15 那 53 个点的通用能力回撤，想清楚你的场景能不能承受。

还有个更根本的问题没解决：形式化规格的"对"，最终还是要人来判断。测试用例、LLM 裁判、等价证明、专家评审叠了四层，300 道题里仍漏了 9 道语义错误。把规格写对这件事的收尾那段路，这篇论文把它圈出来了，但没走完。

## ⚠️ 局限（作者自述 + 我的补充）

论文 Appendix J 列了四条：推理时多轮修复未评测；专家评审覆盖有限（300 道测试题只有 1 位评审、100 个 RL 输出 2 位评审，训练问题全靠测试 + 裁判 + 等价证明，缺抽样估计错误率）；生成输出带 `sorry` 接受、证明只保证两个后置条件彼此一致；validity predicate 的漏约束问题。我补两条前面提过的：域内主场优势、以及专精化带来的通用能力回撤。

说到底，这套东西目前还牢牢长在"LeetCode 风格的、有明确输入输出的小函数"上。真实代码库里那些带状态、带 IO、带并发的规格，能不能也配出可执行的孪生兄弟，我没有答案，说实话这块我也还在琢磨。
