# 考卷也会自己长大：CUA-SEE 把静态评测改成了闭环演化

你有没有碰到过这种尴尬：花两周把 Agent 调了一版，跑完评测发现分数从 89 掉到 53，团队里一半人说"改崩了"，另一半人说"这次的题根本不是上次那批"。两边吵不出结果，因为谁都说不清分数下降到底来自模型退步，还是来自考卷换了。

我最近就卡在这个坑里。做 computer-use agent（直译是"会用电脑的智能体"，下文就叫 Agent）的人应该都懂：OSWorld 这类基准的任务和验证器都是人工一次性写死的，Agent 一迭代，题目原地不动，分数很快饱和，然后你想再往前推一点，连"谁比谁强"都测不出来。更难受的是，一个总分 78.0 什么也告诉不了你——它到底不会拖动、不会处理跨表格状态，还是仅仅在第 40 步撞了步数上限？

这篇 arXiv:2611.30962 的论文给了个挺硬核的回应：既然 Agent 会自己进化，评测环境凭什么不动？

---

## 核心摘要

静态基准有三个死穴：难度天花板固定、功能覆盖有限、聚合分数太粗。作者提出 CUA-SEE，一个让**任务**和**可执行验证器**从 rollout 证据里协同演化的闭环评测环境，并且把三件常被搅在一起的事拆开——基准演化负责拓宽测量范围（队列校准的难度 + 覆盖增长），诊断演化负责提高分辨率（以单个 Agent 为条件探能力边界），验证器演化负责提高精度（把变化的需求翻译成状态检查点 + 对抗审计）。四轮下来，五个 Agent 的宏平均分数从 60.6 降到 47.5，轨迹长度从 27.4 涨到 39.3 步，精确功能操作覆盖扩张 3.65 倍，演化出的检查点验证器与人工轨迹判断一致率 84.0%。我的判断：这不是数据集发布，也不是把已有模块拼一遍，它真正值钱的地方是把"评测"从一个静态量表改成了一条带过程证据的控制系统；代价是整套机制很重，而且有几处实验解释我觉得还站不太稳。

## 🎯 问题动机：静态考卷是怎么失效的

作者的诊断挺干脆，三条，条条戳在工程痛点上。

**难度天花板**。任务集固定，Agent 一旦把这批题做熟，分数就贴到天花板上不再动，之后任何真实进步都测不出来。这不是假想，论文里 R0 那一轮五个 Agent 的 Overall Score 分别是 89.0、78.0、80.0、73.0、68.0，Pass 率齐刷刷贴着 68 到 89，区分度已经很薄了。

**功能覆盖有限**。这条我看到时愣了一下：作者审计了 OSWorld 的核心应用，发现现有任务只覆盖到可用软件功能分类树的不到 20%。也就是说，一个 Agent 在 OSWorld 上拿高分，只能证明它会用这些软件里很小的一撮按钮。剩下的 80% 从来没被考过。

**缺少评测动态性**。静态基准不会追踪移动中的能力边界，也不会主动去找新冒出来的弱点、捷径行为和泛化缺口。分数是个标量，过程里发生了什么，它一概不记。

说到这个，顺手掏一下同期的工作，位置感会清楚很多。OSWorld 和 WindowsAgentArena 提供了可复现的真实桌面环境，但任务集是预 curated 的；CUA-Gym 自动生成可验证的"任务-状态-奖励"三元组，OpenComputer 生成带状态验证器和部分给分的任务，这两家的主要目标是扩容训练数据或可验证环境，不是反复把一个基准对准固定 Agent 的观测行为去调。TRACE 更接近，它用 test-time exploration 生成越来越难的搜索题并做轨迹验证，但范围只锁在任务难度上，验证器还是静态的 exact-match。

还有一条不太一样的路子：EvoCUA 那一类工作把"自进化"用在 Agent 自己身上，靠可验证合成任务 + 大规模 sandbox rollout + 迭代训练去提升策略。CUA-SEE 反过来，进化的是考卷和尺子，Agent 是被观测对象。你看，一个在改学生，一个在改考场，两者其实是互补的。

回到这篇论文，作者的判断是：评测系统得跟被评测的对象一起动。但"让题变难"这件事，说起来一句话，做起来全是坑。

## 🧠 最值钱的一步：把三个目标拆开

说实话，我第一反应是"这不就是自动加难吗"。往下读才意识到，作者真正花力气的地方不是加难算法，而是先把三个长期被混为一谈的目标显式解耦：

| 维度 | 要回答的问题 | 对应机制 | 产出的东西 | 优化什么 |
|---|---|---|---|---|
| Scope（范围） | 测什么 | 基准任务演化 | 模型无关的共享基准 | 难度前沿 + 功能覆盖增长 |
| Resolution（分辨率） | 边界在哪 | 诊断任务演化 | 以 Agent 为条件的探针任务 | 局部可归因的 pass/fail 边界 |
| Precision（精度） | 怎么测准 | 统一验证器演化 | 状态接地的可执行检查点 | 需求覆盖 + 判别可靠性 |

这个拆分为什么关键？你想想看，传统"任务加难"流水线里，加难、诊断、改验证器是同一根绳上的：题目变难了，原来的成功判据可能直接失效；为了补判据，又得顺手改题；改完题，你也不知道分数下降是 Agent 变弱还是尺子变松。三件事搅在一起，任何一轮的结论都没法归因。

拆开之后，每个算子可以有自己的优化目标和自己的准入闸门。基准演化是**队列级、模型无关**的，不许针对某个 Agent 的偶发失误定制题目；诊断演化反过来，是**Agent 条件化**的，专门贴着某一个模型的能力边界撒探针；验证器演化则是两者共享的测量骨架，保证不管任务怎么长，测量义务都还能落到可观测状态上。

| Benchmark | 任务难度 | 功能覆盖 | 边界分辨率 | 验证器质量 | 过程信号 |

| OSWorld | × | × | × | × | × |

## 🏗️ 方法核心：闭环怎么转起来

![图1：CUA-SEE 系统总览](https://arxiv.org/html/2611.30962v1/CUA-SEE.png)

*图 1（论文 Figure 3）：系统总览。中央是 Agent–Environment Rollout，左侧是任务演化的两条支路，右侧是验证器演化的五步流水线，底部是共享测量基础层。*

这张图信息量很大，我按自己读图的顺序拆一遍。

顶部左上的蓝框是**批级证据聚合与轮次规划**（Batch-Level Evidence Aggregation & Round Planning）：把上一轮轨迹、任务需求画像、覆盖登记表三样东西喂进去，依次做证据归一化（区分 pass / fail / 截断 / invalid）、测量状态汇总（看队列整体掌握度与分歧）、扩展方向分配（deconfound、transfer、cover、replicate）。它吐出两类东西：给基准演化的"群体前沿与覆盖目标"，给诊断演化的"Agent 专属诊断派发"。

中间的灰色框是 **Agent–Environment Rollout**，同时产出任务执行轨迹和检查点轨迹（Task Execution + Checkpoint Traces）。这一步是全系统的燃料来源。

左侧绿框两条支路，就是上面说的 Scope 和 Resolution。左下 **Benchmark Task Evolution** 标着 "Population-level measurement growth"，五层依次是：对齐多智能体证据 → 双目标（难度增长 + 覆盖增长）→ 演化方向 → 选择闸门 → 通用基准任务提案，底下还画了 software×capability 与 capability×intensity 两张小热力图。中下 **Diagnostic Task Evolution** 标着 "Agent-conditional boundary refinement"，从 Target Diagnostic Cell（software × feature × capability × intensity）开始，经过候选实现、自适应探针策略、混杂控制，落到"干净的诊断任务提案"，最下面那条 0–5 刻度尺把区域分成 Pass Region、Uncertain Boundary、Fail Region——注意它的注脚，*prefer clean attribution over maximal difficulty*，宁可要能干净归因的弱探针，也不要难度高但说不清的题。

右侧橙框是 **Verifier Evolution**，标着 "How to Measure"，五步写得很清楚：① 原子需求分解（Atomic Requirement Decomposition）；② 状态接地与可观测性（Task Requirements → Canonical State）；③ 检查点谱系变换（Checkpoint Lineage Transformation，四个动作 KEEP / MODIFY / REMOVE / ADD）；④ 可执行验证器构造；⑤ 验证与对抗审计（Validation and Adversarial Audit）。第⑤步里有个我很喜欢的设计：左边 PASS AGENT 独立造出一个"应当判通过"的完成态，右边 VERIFIER AGENT 在看不到 PASS 实现的前提下审计这个状态是否真的满足任务，两边信息隔离、互相挑刺，用来逼出偷懒的检查点、漏掉的需求和写错的期望值。

底部紫色 **Shared Measurement Substrate** 把 8 个 OSWorld 应用扩展到 20 个可验证桌面环境，固定件包括 Software Environments、Feature Taxonomy、CanonicalState Adapters、7D Capability Ontology、Lineage Registries、Agentic Harness。附录里点名了新增的 12 个：Blender、VSCodium、JupyterLab、Krita、Draw.io、SMPlayer、OBS Studio、ONLYOFFICE、OpenScreen、ComfyUI、Zotero、Brave。

一句话概括这个闭环：每一轮，Agent 在当前"任务–验证器"对上跑；经过合法性过滤的轨迹和检查点结果更新测量状态；这份证据再决定下一轮该测什么、以及对应的验证器该怎么写。周而复始。

### 3.1 基准演化：队列说了算，不许为单个模型定制

这部分我读得最细，因为它决定了整套系统会不会沦为"给某个模型挖坑"。

**对齐多智能体证据**。把所有轨迹按规范的源任务身份 join，保留每一个兼容的重复样本。关键在证据完整性和任务结果分开建模：正常的成功/失败是干净证据；撞到步数上限的跑批保留为**删失观测**（censored）；setup、控制器、环境自身出错的直接标 invalid。然后用分数、终止状态、检查点跃迁、回退、路径多样性，把每条源谱系归类成 universally easy / mostly mastered / discriminating / universally hard / unstable / confounded 六种之一。这一步的意思是：某个模型偶然手滑一次，不能变成下一轮全队列的考题。

**双目标轮次规划**。难度增长要求至少一个校准能力维度可测量地上升，且整体任务不能实质回退；覆盖增长要求在"软件–分类–操作"精确格点或"能力–强度"格点上出现**严格的集合新增**。动作家族只按暴露度记录，不当成 Agent 能力。共享的谱系与覆盖登记表用原子认领协调并行 worker，防止同一个已测功能被重复计为新广度。单个任务可以只专攻难度或只专攻覆盖，但整批选出来的任务必须在合计上同时推进两个目标。

**谱系锚定的演化方向**。每个合格源任务构造四类候选：难度升级、覆盖扩张、带可测量升级的迁移、以及三者的连贯组合。每个候选都得保留一个 lineage anchor——让跨轮比较还有意义的那个语义需求；值、目标、规模、上下文、支撑子目标都可以变，纯水平搬运不加分。无关功能嫁接和表面堆砌不算演化。

**候选选择闸门**。要过六关：保留谱系锚、难度不实质回退、交互预算内可行、存在唯一可观测终态、由模型无关证据支撑、以及可验证性。排序看可行性、可验证性、校准难度、覆盖增益、模型中立性、自然度，步数需求超过可用预算 0.85 的直接拒掉。输出在每条演化义务都被可执行验证器实例化之前，都只是"通用基准任务提案"。

这里有个工程上很实在的取舍：把"能不能测"放在"难不难"前面。我之前做类似的事吃过亏，题出得漂亮但状态导不出来，到头来只能靠截图肉眼判，评测直接失去可复现性。

### 3.2 诊断演化：贴着边界撒探针，而不是一味往上加难

![图2：Chrome 隐私任务的基准演化案例](https://arxiv.org/html/2611.30962v1/case_1_benchmark_chrome_privacy.png)

*图 2（论文 Figure 4a）：Chrome 隐私任务的基准演化。R0 是单一开关，到 R3 变成带精确排除项的复合控制；绿条标出从 R2 到 R3 的证据驱动升级，下半部分是 Kimi 在 R1 的 rollout 证据局部截图。*

先借这张案例图把"难度怎么长"讲具体，它比抽象描述清楚太多。R0 源任务只是打开 Chrome 的 Do Not Track 开关，验证器"1 exact switch"。R1 走覆盖扩张：KEEP 住 DNT ON，新增"全局阻止第三方 cookie"策略，再加一条不变式"不许出现站点级 cookie 例外"，验证器变成"2 states + invariant"。R2 走组合：Privacy Sandbox 三个子项（Topics / Audience / Measurement）全部关掉且 0 exceptions，图上标着 "6/6 across Kimi, Seed, and Gemini"，验证器 6 项跨 3 个模型。R3 走精度：要求把 `https://example.com` 且仅此一条加入第三方 cookie 阻止名单，明确排除 Allow、全量 Block、其他站点，验证器"exact entry + 3 neg."。中间那条绿条写得很好：R2 在三个模型上干净通过 6/6，于是 R3 保留全部 5 个已掌握的开关，只在精度上加 1、验证上加 1，把难度推 +0.6，靠的是"精确列表位置的放置"。

这才是"演化"该有的样子——不是把题目写长，是每条新增义务都能被独立观测、独立判分。

![图3：Kimi 的 LibreOffice Calc 诊断演化案例](https://arxiv.org/html/2611.30962v1/case_3_diagnose_kimi_calc.png)

*图 3（论文 Figure 4b）：针对 Kimi 的 Calc 透视表诊断。R0 基线满分掌握，R1–R3 各自只动一个能力维度，把"复合失败"拆成可归因的单一边界。*

再看诊断这一侧，气质完全不同。R0 源锚是"在 Invoices.xlsx 新 Sheet2 里做透视表，统计每个 Invoice No. 出现次数"，Score 1.00，掌握。R1 把 Integration 拉到 4：要求透视表 + 把表头与总计以**数值**粘到 A1（不许公式），结果 4/7 checks、partial，挂在一个"精确总计标签"检查上。R2 换成 Scale 拉到 4：用 COUNTIF 在 C2:C9 为 8 个有序区间（10500–10505、Magnetic、Quad 等）生成计数，4/6 checks、partial，把 8 目标公式规模单独隔离出来。R3 回到 Integration 4：Sheet2 透视 + 关联图表（Sales Rep = all、Sum - Units、Date = all）并要求保留 Sheet1，5/6 checks、partial，定位到原生组合探针。图中间那句注脚是整套诊断逻辑的灵魂：*Non-cumulative diagnostic probes*——不是在 R1 的部分失败上继续堆未解子句，而是每轮从 R2（4/6）和 R3（5/6）里选一个干净的能力格点去定位边界。下半部分 R1 rollout 证据显示：透视布局与源检查通过，A8 标签不匹配（应为 Total Result 却复制了 Invoice No.）。

技术上有三层。**目标诊断格点**：批级 planner 先把 pass / partial / confounded / invalid 分开，只用 setup 与验证器都合法的观测当干净边界证据，再聚合出 capability、software、feature 多张视图，找稳定失败区、证据不足区；每个派发锁定一个由软件、功能、主能力、强度定义的格点，附带控制维度与混杂上限。**KNN 式候选实现**：一次派发生成一个局部邻域——请求的强度、一个更干净的低强度回退、可行的相邻高强度或替代因子探针；任务由一个主需求维度和若干次要维度定义，全来自 7D 能力（scale consistency、precision control、target grounding、state-dependent reasoning、procedure following、feature integration、verification and control），强度按 0–5 打分，描述的是任务需求而非预测的模型表现。**自适应探针策略**：干净的通过把强度往上调，干净的失败往下调，含糊结果触发去混杂、简化或复现；只有验证器演化完成且跑出合法 rollout 之后，才允许更新该 Agent 的能力边界。

七个维度的强度锚点，论文 Table 4 给得很细，我压缩成一张表：

| 能力维度 | 接地任务因子 | 0–1（最低） | 2–3（中等） | 4–5（最高／主导） |
|---|---|---|---|---|
| Scale Consistency | 目标数、去重值、同质性 | 单目标／一次批量动作搞定两个 | 2–3 个手工目标／4–6 个目标或去重值 | 7–12 个跨视图目标／超过 12 个目标且受步数约束 |
| Precision Control | 值的数量类型、容差、单位换算、耦合 | 无精确值／单个默认选项 | 1–2 个简单精确值／多个精确值或严格格式 | 耦合值、公式或单位换算／异构精度耦合 |
| Target Grounding | 候选数、干扰相似度、可见性 | 显式可见目标／无干扰的清晰标签 | 2–4 个不同候选／元数据内容相似的候选 | 计算属性部分隐藏／多阶段跨视图定位 |
| State Reasoning | 读取状态变量数、推导步、分支数 | 与状态无关／读一个直接可见值 | 单条件或单变换／1–2 步推导或 2 分支 | 多变量多分支推导／迭代状态更新 |
| Procedure Following | 子目标数、顺序严格度、不可逆性 | 一次操作／两个独立明显操作 | 3–4 个弱序子目标／4–6 个依赖子目标 | 长严格链、不可逆步骤或精确导出／带守卫的多阶段工作流 |
| Feature Integration | 功能数、UI 距离、跨对象数据搬运 | 单一功能区／一个功能内两个控件 | 两个相邻功能区／三个区或显式数据搬运 | 远距离功能跨对象联动／多制品跨应用集成 |
| Verification & Control | 不变式数、检查修正、副作用 | 无约束／基础完成检查 | 一条显式保留规则／多个不变式或检查修复 | 条件式多对象修正与副作用控制／迭代恢复负担 |

### 3.3 验证器演化：让尺子跟着考卷一起长

这是我认为论文最扎实的一块，也是它跟 TRACE 拉开距离的地方。

**以需求为中心的契约分解**。把演化后的任务契约重建成一组可独立测试的结果需求，从显式 evaluator 要求和指令的原子子句里抽出来；目标值、顺序约束、制品状态、保留条件、禁止的副作用都当成一等义务保留，不许悄悄合并成粗粒度成功判据。

**状态接地与可观测性**。每条需求映射到一个可观测状态字段或制品、一个计划检查点，以及三种覆盖状态之一：covered / partially observable / unverifiable。状态路径必须被应用的状态目录或捕获的快照支持；只靠文件存在、文件名、setup 状态、拿不到的动作前取值来做代理检查，一律禁止。不支持的子句就明确保留为覆盖缺口，不许拿不可靠的替身糊上——这条设计防的是很隐蔽的选择偏差：把难测的应用直接丢掉，会让基准看起来更容易、也更"干净"。

**检查点谱系变换**。对源验证器的每个既有检查点打一个明确动作：Keep（义务没变）、Modify（目标或期望值变了）、Remove（演化后任务里没了）、Add（新要求的效果）。原 OSWorld evaluator 只能提供关于意图事实、容差、合取结构的语义证据，演化后的契约才是权威。单条失败 rollout 不足以判定验证器出错。

**可执行验证器构造**。每个软件配一个任务无关的 adapter，去探原生状态导出接口（论文举例 debug protocols），把快照归一化成共享的 `CanonicalState` schema；变换后的契约编译成 schema 接地的检查点，每个只查一个任务效果，返回具体的"期望 vs 实际"原因。每条需求必须映射到检查点或被声明为可观测性缺口，禁止无条件通过、禁止基于推断的兜底。只要有一个目标效果被可靠验证、且所有遗漏都被声明，部分可观测任务仍然可以进入 rollout。

**验证与对抗审计**。三道静态闸门（语法与 import、结构契约、静态 schema）加两道行为闸门（PRE/PASS 判别、检查点级负样本 fixture）。信息隔离的 pass agent 独立造出一个可执行 PASS 态并审计检查点的必要性与完备性，verifier agent 看不到 pass 的实现却要审这个状态是否真满足任务；两边的对抗式交叉审查用来暴露偷懒检查点、缺失义务和错误期望值。修订只有在保留任务语义、且不降低已验证最佳验证器分数时才被采纳。

论文 Table 5 把"什么不许动、什么可以演化"切得很利落，我转成表格：

| 系统层 | 跨所有轮次固定（不变基础层） | 每轮演化（自演化产物） |
|---|---|---|
| 环境与状态执行 | Ubuntu VM 与适配器：隔离镜像、20 个应用二进制、任务无关的 CanonicalState adapter、50 步 rollout 控制器 | 任务实例：谱系派生的初始状态、输入文件与夹具、每实例演化参数 |
| 分类体系与量规 | 校准本体：四级 software–feature–category–operation 树、7 维 0–5 量规、8 个动作家族、混杂上限 | 动态规划状态：共享前沿覆盖登记表、每任务 7 维需求画像、Agent 条件化诊断派发 |
| 测量与闸门 | 审计协议：静态契约/schema 闸门、隔离的 PASS-agent 与验证器交叉审计、clean/censored/confounded 有效性类别 | 可执行契约：原子需求分解、Keep/Modify/Remove/Add 检查点、经验边界图 |

看到这张表我是真的觉得舒服。自演化系统最怕的就是"什么都在变"，到头来连自己测的是什么都说不清；把基础层钉死、只让产物动，是可复现性的前提。

一个核心公式，用来说明分数怎么聚合（论文附录 B.3）：

$$s_{a,t}^{(r)} \in [0,1], \qquad \bar{S}^{(r)} = \frac{1}{|\mathcal{A}|\,|\mathcal{T}|}\sum_{a \in \mathcal{A}}\sum_{t \in \mathcal{T}} s_{a,t}^{(r)}$$

$s_{a,t}^{(r)}$ 是 Agent $a$ 在第 $r$ 轮、任务谱系 $t$ 上的归一化分数，$\bar{S}^{(r)}$ 是在固定「Agent × 任务」面板上的宏平均。要点不在公式本身，而在**面板固定**：100 个谱系贯穿 R0–R4 不变，每轮都被同样的五个 Agent 跑一遍，于是聚合分数的变化不能赖到"这轮换了题"上。Pass 定义为拿到满分 1.0 的任务占比，score ≥ 0.99 判 pass、≤ 0.01 判 fail，中间保留部分给分；撞到 50 步上限的零分局判为删失而非干净失败。

## 📊 实验结果：数字都得能追到原文

### 实验设置

基准演化从 100 条 OSWorld 任务谱系出发，每条演化四轮，产出 R0 与 R1–R4；每轮保留同样的 100 个谱系 ID、由全部五个 Agent 评测，每轮 500 个"任务–Agent"观测，全轨迹 2,500 个配对观测。Kimi-K2.6、Seed-2.1-Pro、Gemini-3.5-Flash 驱动演化，Qwen-3.7-Plus 与 GPT-5.5 严格留出（held-out）。诊断演化独立跑：Kimi 四轮 100 任务，Seed 和 Gemini 各三轮 100 任务，合计 1,000 个演化任务画像；主诊断矩阵把匹配的 100 任务 R0 基线与 R1–R3 合并，共 1,200 个计划槽位（还要过 rollout 可用性与合法性过滤）。底子有 20 个应用，但纵向 R0–R4 面板锁在八个核心 OSWorld 应用上，避免新软件域污染跨轮指标。每 episode 上限 50 步，R0 用原生 OSWorld 任务与验证器，演化轮用 CanonicalState 验证器。

合成后端用 GPT-5.5、reasoning effort 设 high；两个 CPU 服务器（96 核 Xeon Platinum 8163 / 376 GiB，256 核 EPYC 7T83 / 1008 GiB），本机无 GPU，推理走远程服务；默认 3 个并发 Codex worker、2 秒错峰、单任务 45 分钟超时，有界修复与验证器任务可提到 10 并发。

这两张图放一起看才有意思。Gemini 那张里 Scale Consistency 从强度 3 开始转黄、4 变橙、5 直接进红区（接近 0 分），把"大规模一致性"这条边界画得明明白白；Kimi 那张整体偏绿，但 Verification & Control 在强度 4 有一块橙色低分。作者的画像总结也对得上：Gemini 强在 precision control 和 target grounding，高 scale 的一致性仍吃力；Kimi 在点击、输入、导航上稳，Seed 对拖动、滚动、状态依赖控件更敏感；三者都在 Chrome 和 VS Code 上更稳，GIMP 和 Thunderbird 更容易暴露弱点。

这种"每个模型一张能力地形图"的东西，聚合分数永远给不了。论文还有一个我挺在意的量：每一轮稳定引入 57–73 个新的功能叶节点，说明诊断在变宽，不是反复重采样同一批相似难题。另外论文 Figure 2 记录了 Kimi 每轮挖到的诊断能力边界数量，配合"把原本接近普遍成功的饱和基准推向更有信息的区间"这个结论——路径是从"人人通过"往"能分辨"挪，而不是往"人人挂科"挪。

### 验证器：84.0% 一致率与它的可信度

在 400 条 Kimi 轨迹（跨四轮）上做人工判断与检查点验证器的收敛效度评估：两者在 **84.0% 的运行上达成一致**，Cohen's κ = 0.640，一致率从 81% 升到 89%，连续分数也呈中等一致性。被审计出的分歧主要来自 adapter 状态不完整、验证器覆盖不全、状态字段错配——都是可观测性的残余缺口，不是判分逻辑乱来。

规模统计也给了：962 个任务、平均每任务 4.82 个检查点，原子需求覆盖率 92.5%，几乎所有应用都超过 85%，偏低的是受原生 adapter 限制的应用（点名 Thunderbird）；检查点数跟着需求数沿 $y = x$ 对角线走（$r = 0.55$–$0.65$），即便部分可观测的 Partial 任务也仍旧接地 3–7 个检查点。作者用这组数反驳"验证器会退化成最小检查"的担心，我认为这个反驳是成立的。

### 可靠性、效率，以及"消融"去哪了

4.4 节这几组数，我觉得是全文最该细读的部分，因为它直接回应"分数下降是不是尺子漂了"这个致命质疑：

| 检验维度 | 原文数值 | 它在证明什么 |
|---|---|---|
| 队列外泛化 | 留出的 Qwen −26.9、GPT −24.0 | 没参与驱动演化的模型，分数照样跟着变难，排除"针对训练集定制题目" |
| 校准协同演化 | Keep/Modify 继承、隔离的 PASS 态可解闸门、人类一致率 81% → 89%、验证器无关的 2× 步数增长、2–3.5× token 增长 | 用多组间接证据排除 verifier drift |
| 部分验证器对称性 | 保留可靠的 Partial 验证器、对所有 Agent 施加同一套检查 | 不靠丢掉难测应用来 inflate 分数 |
| 结构化区分度 | R4 的 Pass 仅 13–19%；连续分数把边界信息量抬高 20.8 个百分点到 69.7；暴露出被标量均值掩盖的 20–37 个百分点的分应用排名反转 | 低 Pass 率下，过程级分数仍能保持判别力 |

表格末行我想多说两句。R4 的 Pass 掉到 13–19%，宏平均的区分度确实被压窄了，但连续分数把边界信息量抬到 69.7，还翻出 20–37 个百分点的分应用排名反转——这正是"保留过程级证据"的回报。如果你只看一个总分，R4 会显得五个模型都差不多烂；有了检查点矩阵，谁在哪款软件上翻车一目了然。

效率这块，论文 Figure 10 按 GPT-5.5 API 费率估算成功演化任务的 token 与等效成本：验证器演化的成本跨 Agent 很稳，基准任务演化因为共享上下文更大而更贵，瓶颈在**上下文构造**，不在验证器生成。Table 2 里 Kimi 的 input token 从 R0 的 103.0K 涨到 R4 的 363.9K，Qwen 甚至到 487.6K，这个量级做持续演化，账单不是小数目。

这里得说句实话：我翻了两遍，没找到传统意义上的"去掉某个模块再跑一遍"的消融表。作者用留出队列、验证器漂移排查、人评一致性、部分验证器对称性这些**可靠性检验**替代了组件消融。这套检验设计得挺周密，尤其 held-out 那两个模型是硬证据；但它回答的是"分数变化可信吗"，没回答"三个演化算子各贡献了多少"。比如把诊断演化关掉、只留基准演化 + 验证器演化，覆盖增长会不会打折？把对抗审计去掉，84.0% 的一致率掉多少？这两刀没切，我觉得是实验部分最明显的空缺。也可能作者把篇幅全给了 Appendix，反正主文里我没看到，这块我保留意见。

## 💡 我的判断

**这篇论文值钱在哪。** 不是"自动出题"这个点子——TRACE 已经做过更轻的版本。它的贡献是把评测重新定义成一个有状态、有反馈、有固定基础层的控制系统，而且把 Scope / Resolution / Precision 三个目标从工程上一一落到了独立的算子、独立的准入闸门和独立的证据类型上。特别是"宁要可归因的弱探针，不要说不清的难题"这个取舍，还有"不支持的子句必须显式声明为覆盖缺口"这条规矩，都是踩过坑的人才写得出来的。PASS agent 与 verifier agent 信息隔离互审，也是个又便宜又漂亮的点子。

**定位上，它是方法创新，不是数据集发布。** 跟 TRACE 比，它补上了验证器演化和诊断分辨率；跟 CUA-Gym / OpenComputer 比，它盯的是"反复适配一个固定基准"而不是扩容训练数据；跟 EvoCUA 那一类自进化 Agent 比，它进化的是考场而非考生。把这几家的坐标摆出来，CUA-SEE 的位置很清楚：给越来越会自我改进的 Agent 配一个同样会自我改进的测量系统。

| 工作 | 进化的对象 | 任务难度 | 覆盖增长 | 验证器演化 | 过程级证据 |
|---|---|:---:|:---:|:---:|:---:|
| OSWorld | 无（人工固定） | × | × | × | × |
| TRACE | 搜索任务难度 | ✓ | × | 静态 exact-match | ✓ |
| CUA-Gym / OpenComputer | 可验证环境／训练数据 | 部分 | 部分 | 生成时不演化 | 部分 |
| EvoCUA 类 | Agent 策略自身 | 训练侧 | 训练侧 | 合成时一次性 | 训练侧 |
| CUA-SEE | 任务 + 验证器 + 测量状态 | ✓ | ✓ | ✓ | ✓ |

**我不太买账的几处。** 一是能力覆盖那 35 个格点两轮就 100%，后面的"覆盖增长"几乎全靠操作级分类撑着，指标粒度配不上结论的口气。二是"分数下降 = 任务变难"这条因果链，作者是靠一组间接证据（步数、token、人评一致率、留出模型）围出来的，没有直接把"同一 Agent 在同一批固定任务上的表现"当作不随轮次变化的锚；2,500 个配对观测解决了样本漂移，但解决不了测量工具本身随轮次升级带来的口径问题。三是合成后端用 GPT-5.5，而 GPT-5.5 恰好也在被评测的五个 Agent 里（虽然是留出组），这个闭环有没有轻微的自我参照，论文没展开讨论——可能我想多了，但这类系统就该把这点挑明。四是人评只做了 400 条 Kimi 轨迹，84.0% 这个数能不能推到 Seed、Gemini 和那 12 个新增应用，我心里没底。五是"更长的交互链"是不是就等于"更难"，这两者在 CUA 里相关但不等价，R2 分数反弹那段就是提醒。

**工程上我会怎么用。** 如果你在维护一个 Agent 评测平台，别一上来就搭全套自演化。按投入产出排，我会先做三件：把成功判据从"终态单分数"换成带 `expected vs actual` 原因的检查点集合，这一步立刻就能拿到过程级诊断；给所有任务建一张覆盖登记表，让"新增了什么功能格点"变成可审计的硬指标，而不是靠人写题时的感觉；再留出一两个从不参与出题的 held-out 模型，专门用来抓"是不是在给-driving 模型挖坑"。等这三件稳了，再考虑让任务自己长。至于 20 个应用的 CanonicalState adapter 和双 agent 对抗审计，那是重资产，得有专门的 infra 团队才扛得住——论文自己用两台 CPU 服务器、45 分钟单任务超时、3–10 并发 worker 的规模，也说明这不是周末能撸出来的玩具。

还有个更根上的问题没解决：当考卷和尺子都在演化，跨实验室、跨论文之间还怎么比？CUA-SEE 内部靠固定基础层和谱系锚保证了跨轮可比，但两个各自演化了十轮的评测环境，彼此的分数没有共同标尺。作者把 adaptive evaluation 定位成 self-evolving agents 的对应物，这个方向我认同；可要是评测本身也变成每个团队私有的动态系统，"谁更强"这个问题可能会从"刷一个公共榜"退回"各自报各自的内部曲线"。这块我自己也还在摸索，说不准会不会有更好的解法。

回到开头那个争吵。有了这套东西，至少你能拿出检查点矩阵说清楚：分数掉了，是 GIMP 的精度控制从第 3 档推到了第 4 档，Agent 在第 31 步选错了容差，不是模型退步。就冲这一点，这篇 arXiv:2611.30962 值得花一个下午细读。
