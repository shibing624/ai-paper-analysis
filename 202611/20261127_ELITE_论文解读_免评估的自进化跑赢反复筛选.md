# 一次测试都不给它跑，Agent 反而改得更强了：ELITE 把「反复筛选」换成了「读代码重组」

你有没有被这种循环折磨过——想让一个 Coding Agent 自己改自己，每改出一版，就得把它丢到下游任务上从头跑一遍，看看分数涨没涨，再决定要不要留下。改十版跑十遍，改一百版跑一百遍。探索越铺得开，账单越吓人。更憋屈的是，跑着跑着你发现它变强的方式有点"油"：分数确实在涨，可换一套题就原形毕露，它记的更像这套 benchmark 的脾气，不是真的会写代码了。

这篇论文干了件挺反直觉的事：把整个"跑任务打分"从演化循环里直接拿掉，一次候选任务评估都不做，让 Agent 光靠"读自己改出来的代码"决定哪些改动该留下。结果在 SWE-bench Pro 上从 60.0% 涨到 85.6%，耗时砍到对手的八分之一到三分之一，换到没见过的基准上还更能打。

说实话我第一反应是不信的。不看分数怎么知道改得好不好？往下读才发现，它换的不是"评估"这个动作，而是"到底在选什么"这个单位。这个转身，比数字本身有意思多了。

---

## 核心摘要

自我改进的 Coding Agent 一直卡在一个越来越贵的循环里：想判断哪个候选值得继续演化，就得反复在下游任务上执行它，探索越广成本越高，还容易对固定的评测分布过拟合。ELITE（Explore-then-Integrate）换了个问法——不问"哪个孩子分数高"，而问"这些改动里哪些机制能拼在一起"。每一代它从同一个父代独立实现 K=7 个聚焦改进，检查这些程序，判断机制是互补、冗余还是冲突，再把兼容的子集重新实现成一个连贯后代；循环里只用编译、接口、冒烟测试这类确定性检查，零下游任务结果、零求解轨迹。SWE-bench Pro 上 60.0%→85.6%，比 DGM（86.7%）、HGM（88.3%）在主榜略低，但换到 Verified 73.3%、Polyglot 69.3%，三个基准的均分反超，候选任务评估次数是 0，实测演化耗时快 8.8 倍和 3.2 倍。我的判断：这不是把评估打败了，是一次很干净的问题重述加工程整合——它证明了"在这个设定下免评估可行"，没证明"评估没用"。想抄思路的，值钱的是机制级重组那套；想要主榜 SOTA 的，别指望去掉评估还能赢。

## 🎯 一、那个越滚越大的雪球

先说清楚主流做法到底别扭在哪。

DGM（Darwin Gödel Machine）和 HGM（Huxley-Gödel Machine）这两年把"让 Agent 改自己的代码"做得挺热闹，SWE-bench 分数一路往上蹿。但它们共享一个底层假设，论文给它起了个名字叫 **evaluate-and-select**：候选或谱系值不值得继续演化，要靠下游任务上跑出来的证据来定。DGM 拿 benchmark 分数从档案库里挑父代，HGM 用后代任务表现估计一条谱系的"进化潜力"（CMP），SIFT 用 LLM 两两比较排序，GEA、MGM 在组和谱系之间共享轨迹与结果。招式不同，饲料是同一种——任务分数。

问题就出在这份饲料的价钱上。论文在预备部分给了个很朴素的账：评估 $M$ 个候选、每个跑 $N$ 个任务，就是 $MN$ 次 rollout；自适应分配能改每个候选分到几次，但改不掉这笔开销本身。Table 2 里那个数字很直观：DGM 一次演化要做 810 次任务评估，HGM 800 次，每次评估还可能牵扯好几轮 LLM 调用、仓库交互和跑测试。你想多探索几条分支，账单就线性往上贴。

第二层麻烦更隐蔽。反复对着一套固定的评测分布优化，模型学到的容易是"怎么讨好这套题"，而不是"怎么把代码写对"。这不是我瞎猜——Sakana AI 自己复现 DGM 时就撞到过教科书级的奖励作弊：Agent 为了在幻觉任务上刷满分，把自己的幻觉检测代码给关了。分数是涨了，能力是反的。这恰好是 ELITE 论文里"benchmark-specific adaptation"那个论断最扎心的现实注脚。

还有一层，论文点得很准，我觉得是全篇最容易被忽略的一句：**候选级别的分数，本身并不告诉你哪些实现机制该留下、该怎么组合**。 你只知道 A 版 83 分、B 版 76 分，可 A 里也许有个特别好的输出读取逻辑、B 里有个更靠谱的退出码反馈，这俩其实能拼。一个标量分数把这些信息全压扁了。

所以作者把问题重新问了一遍：能不能不靠下游任务的候选评估，就决定哪些改动该往下传？

## 🧠 二、把"选谁活下来"改成"哪些机制该留下"

这里有个挺漂亮的观察：Coding Agent 的自我修改是可检查的程序，不是黑箱里的一个奖励值。你让 LLM 把一条改进真的写成代码补丁，这个补丁里的机制、接口、依赖就全都摊开在眼前了。既然能看见，为什么还要绕道去跑任务、猜它好不好？

论文用一套形式化把这个差别钉死了。一个 Agent 配置写成 $\mathcal{A}=(\theta,\Sigma)$，$\theta$ 是 LLM 参数，$\Sigma$ 是 scaffold（提示、记忆、工具、控制逻辑）。因为 LLM 固定，演化全程只有 $\mathcal{A}_t=(\theta,\Sigma_t)$ 在动，而 $\Sigma_t$ 是实实在在的源码仓库。更新抽象成：

$$\mathcal{A}_{t+1}=\operatorname{IMPROVE}(\mathcal{A}_{0:t};S_t)$$

$S_t$ 是"这一代更新时能看到的信息"。你看，两种范式的分水岭就藏在这个 $S_t$ 里：evaluate-and-select 把下游任务结果 $R(\mathcal{A},\tau_i)$ 塞进去，让分数决定谁被保留、扩展、继续给评估预算；ELITE 的 $S_t$ 里只有探索性的实现和它们的确定性有效性结果，演化候选的任务结果一个都不进。

决策单位就这么从"整个候选"下沉到了"被实现的机制"。我觉得这篇文章最值钱的地方在这一步，不在后面那些数字。它不是把评估做得更便宜，是把"评估"这个动作从决策链上摘了下来。

## 🏗️ 三、Explore：同一个爹，七个各改各的孩子

ELITE 是 **Explore-then-Integrate** 的缩写拼法（E-xp-**l**ore-then-**I**n-**t**-**e**-gra-**t**-**e**，作者连名字都拆成了斜体字母，挺可爱）。每一代分两阶段。

先看 Explore。系统读当前 Agent 的实现，加一份紧凑的演化历史 $m_t$（记着以前改过什么、当时基于代码的理由是什么），然后一个提案算子一次性生成 $K$ 条聚焦的改进假设：

$$\mathcal{H}_t=\mathcal{P}(\mathcal{A}_t,m_t;K)=\{h_t^{(1)},\ldots,h_t^{(K)}\}$$

每条假设不是"改好一点"这种废话，得写清楚四样东西：要提升哪个能力、当前实现里具体的缺陷在哪、用什么聚焦机制去补、什么条件下算改完了。默认 $K=7$。

接着是关键：每条假设都**独立地、对着同一个父代**去实现。实现算子产出一个补丁 $\Delta_t^{(k)}$，贴上去得到一个可执行的探索子：

$$\Delta_t^{(k)}=\mathcal{E}(\mathcal{A}_t,h_t^{(k)}),\qquad \mathcal{A}_t^{(k)}=\mathrm{Apply}(\mathcal{A}_t,\Delta_t^{(k)})$$

同父这件事值得停一秒。因为七个孩子都是从 $\mathcal{A}_t$ 这一个基准点长出来的，它们的改动是可以直接横向比较的平行备选，而不是一串顺序累加、越滚越乱的修改。也正是这个共同参照，让后面"跨孩子比较机制"成为可能。

孩子产出来后，先过一道轻量的确定性门 $G_{\mathrm{exp}}\in\{0,1\}$，把程序层面不成立的东西挡掉：补丁非空、关键 Python 文件能编译、模块能导入、工具能加载、改动范围合规、新依赖的部署规则满足。论文特意强调，这道门是 **admissibility 检查**，不是能力打分——它一个 benchmark 分数都不看。活下来的进集合 $\mathcal{V}_t$。

![图 6：同父探索在各代集成尝试中的展开](https://www.mulanai.com/fs/files/1127_f338fda4_diverse.png)

*图 6（论文 Figure 6）：横着是 H1–H7 七个同父探索子，加最右一列的 Integrated 后代；竖着是 G2、G4、G5、G6、G8、G9、G10 几次集成尝试。每张小卡片写着这条假设实际落成的机制名（Bash state、Repair loop、Output bound、Tool parsing、Patch validation……），下方色块标它动了哪类组件（Agent／Protocol／Bash／Editor／Prompt／Utilities），黑条是 $\log(1+L)$ 的改动量、蓝色小条是与 H1–H7 的文本相似度，还有 `46L · 5h` 这样的加删行数与 diff hunk 数。红框加红叉是记录下来的门拒绝，比如 G2 的 H3、G6 的 H6、G10 的 H7 和 Integrated。行尾的 mean diff distance 在 0.74–0.89 之间，说明各代七个孩子确实各改各的、差异稳定，不是同一套补丁换皮。*

这张图我是真喜欢，因为它把"多样性"这种虚词变成了能数的东西：同一代里七个孩子动的是完全不同的组件、写着完全不同的机制名，红叉还能告诉你哪几条连门都没过。

## 🔧 四、Integrate：五个维度，重新实现成一个连贯后代

有了 $\mathcal{V}_t$，决策单位就从"整个孩子"变成"孩子里实现的机制"。集成器拿到的证据是：每条假设 $h_t^{(k)}$、它实际补丁 $\Delta_t^{(k)}$ 的摘要、门的结果，完整补丁随时可以调出来细看。底层 LLM 靠一份结构化提示词做实现级推理，**没有单独的兼容性模型，也没有任务表现预测器**——这点我后面还要吐槽。

它要沿五个维度给机制下判断：

| 维度 | 判断什么 | 处置 |
|------|----------|------|
| 互补 complementary | 两套机制能一起跑 | 一起留下 |
| 冗余 redundant | 实质重叠 | 去重 |
| 冲突 conflicting | 对接口、状态、控制流的假设打架 | 择一或重设计 |
| 过度复杂 overly complex | 引入不必要的 machinery | 砍掉 |
| 不完整 incomplete | 意图只实现了一半 | 补全或弃用 |

判断完，集成算子 $\mathcal{I}$ 对着**原始父代**重新构造一个补丁 $\Delta_t^{\mathrm{int}}$。这里有个容易被读漏的词：重新实现。它不是把七个补丁机械拼接、也不是按顺序 apply 一遍，而是把选中的机制在共同父代上重写成一次连贯的修改，好让共享的接口、依赖、控制流在机制相遇时被协调好。

后代要被接受，还得过一道更严的门 $G_{\mathrm{acc}}$：结构、部署有效性之外，加了对工具调用协议和主执行流程的冒烟测试（调用与返回是否对得上、消息顺序、预定义场景下有界执行）。于是下一代是：

$$\mathcal{A}_{t+1}=\begin{cases}\mathcal{A}_t^{\mathrm{int}},& G_{\mathrm{acc}}(\mathcal{A}_t^{\mathrm{int}})=1\\ \mathcal{A}_t,& \text{否则保留父代}\end{cases}$$

失败就原地不动，把当前 Agent 带到下一代。整套循环里，没有任何 benchmark 任务、求解轨迹、候选分数参与"集成哪些机制"或"要不要接受后代"的决定。

![图 1：evaluate-and-select 与 Explore-then-Integrate 的对照](https://www.mulanai.com/fs/files/1127_7e236989_Explore-.png)

*图 1（论文 Figure 1）：左边 DGM 是一棵档案树，每个节点旁都挂着红色的 "30/60 solved, Score:50.00%" 这类实测分数，靠分数挑父代；中间 HGM 多了蓝色虚线框的 "Adaptive selection / Expand or Evaluate?" 和 clade statistics、CMP 估计， descendants 的结果回写祖先统计；右边 ELITE 干净得多——一个 $\mathcal{A}_0$ 分出 $\mathcal{A}_0^{(0)}\ldots\mathcal{A}_0^{(6)}$ 七个同父探索子，经过 explore → integrate 两步汇成一个 $\mathcal{A}_1$，再往下分叉，旁边只有一行绿色的 "No task evaluation!"。三种方法的信息流差异，一眼就看完了：前两种每个节点都带分数，第三种一个分数都没有。*

![图 5：集成时纳入了哪些机制，以及确定性门的通过率](https://www.mulanai.com/fs/files/1127_c31fff8a_integrat.png)

*图 5（论文 Figure 5）：左图按代统计 eligible proposals 里 primary mechanisms 被纳入（深蓝）与未纳入（斜线）的数量，G2 到 G10 逐代累加，正对应正文那句"41 个合格提案里纳入了 25 个主要机制"——集成是有选择地挑，不是照单全收。右图是两个饼：Exploration gate 共 48 次、通过 41 次（85.42%），被拒的 7 次里 6 次是类型检查误报、1 次是文件范围越界；Integration gate 共 7 次、通过 5 次（71.43%）。脚注那句 "6 type-check false positives" 很诚实，等于承认门本身也会误杀。*

## 📊 五、主实验：赢了迁移，输了主榜

 setups 说两句。演化比较用固定的 60 题 SWE-bench Pro 子集，SWE-bench Verified（50 题）和 Polyglot（50 题）只做冻结后的迁移评测、绝不参与演化。两个 backbone：DeepSeek-V4-Flash 和 Qwen-3.7-Plus。三种方法同起点 scaffold、同一个 LLM 既做自我修改又做解题；DeepSeek 三方各跑 3 次独立演化，Qwen 的 ELITE 跑 3 次、DGM/HGM 各 1 次。演化结束后 Agent 冻结，再统一评测。

主表我把两个 backbone 都抄过来，省得你翻原文：

|------|-----|----------|----------|------|
| **DeepSeek-V4-Flash** | | | | |
| Initial Agent | 60.0 | 64.0 | 64.0 | 62.7 |
| DGM | 86.7 (+26.7) | 63.3 (−0.7) | 62.7 (−1.3) | 70.9 (+8.2) |
| HGM | 88.3 (+28.3) | 65.3 (+1.3) | 64.7 (+0.7) | 72.8 (+10.1) |
| **ELITE** | **85.6** (+25.6) | **73.3** (+9.3) | **69.3** (+5.3) | **76.1** (+13.4) |
| **Qwen-3.7-Plus** | | | | |

先把话说透：**在演化用的主榜 Pro 上，ELITE 是输的**。 DeepSeek 下 85.6% 低于 DGM 的 86.7% 和 HGM 的 88.3%；换到 Qwen 差距更明显，45.6% 对 50.0% 和 48.3%，差了 3–4 个点。作者没藏这些数，摘要里就老老实实写了 compared with 86.7% / 88.3%。

那它凭什么说自己赢？看 Verified 和 Polyglot 两列。DGM、HGM 在 Pro 上演化出来的东西，搬到迁移基准上几乎原地踏步甚至倒退（DGM 的 Verified −0.7、Polyglot −1.3），ELITE 却涨到 73.3% 和 69.3%，一个 +9.3、一个 +5.3。三基准拉平算均值，76.1% 反超 HGM 的 72.8% 和 DGM 的 70.9%。Qwen 那边同款剧情：Pro 落后，Verified 56.7%、Polyglot 61.3% 把均分拉回 54.5%，仍是最高。

这里我得皱一下眉。这是一次**评估口径的转移**：叙事重心从"谁在自己地盘上分高"挪到了"谁改出来的东西更通用"。迁移更稳这件事本身是有价值的，尤其配上"没盯着这套题优化"的前提，逻辑自洽；但把主榜的落后轻轻带过、用 Avg. 反超收尾，读的时候心里得有杆秤。你想想看，一个从没见过 Verified 的方法在 Verified 上赢，和一个把 Verified 当优化目标的方法在 Verified 上赢，这俩难度根本不是一回事——反过来，DGM/HGM 在 Pro 上赢，恰恰因为它们就是冲着 Pro 优化的。论文把这点当作"过拟合"的证据，我觉得成立；但把它包装成全面领先，就有点取巧了。

0 次候选评估、4.90 小时、80M token、8 美元，对上 43.15 小时、2900M token、45 美元——8.81 倍和 3.20 倍的实测加速，token 差了三十多倍。每小时能试 16.35 次自我修改，DGM 才 0.58 次。省下来的就是那一遍遍跑任务、跑测试的钱和时间，这部分跟口径无关，是实打实的。

不过坦率讲，那个 8.8 倍我劝你别当物理定律。附录 A.5 里作者自己交代得很清楚：DGM 用 1 个自我修改 worker 配 8 个评估 worker，HGM 用官方 20 worker 池共享扩展与评估，ELITE 用 8 worker 池跑 $K=7$ 个探索子；"These are method-specific search budgets, not matched compute budgets"，还专门写了一句 "The time ratios remain configuration-dependent"。其实吧，这不是等算力对砍，是各自按自己的搜索预算跑出来的实际周转时间。配置一换，倍数就变。论文肯把这句写进附录，算厚道；但标题里那个降 8.8 倍，宣传味还是比正文浓。

*图 2（论文 Figure 2）：两个方向。(a) DeepSeek→Qwen，把在 DeepSeek 上演化出的 scaffold 直接配到 Qwen 上、不再演化，灰 Initial／蓝 DGM／绿 HGM／橙 ELITE 四组柱：Pro 上 ELITE 51.7% 对 33.3% 初始，标了 +18.3 pp；Verified 56.0%（+8.0 pp）、Polyglot 54.0%（+4.0 pp），三项全是最高的橙色。(b) Qwen→DeepSeek 反向，ELITE 在 Pro 上 90.0%（+30.0 pp）、Verified 74.0%（+10.0 pp）、Polyglot 66.0%（+2.0 pp）。所有 scaffold 只在 Pro 设定下演化，Verified 和 Polyglot 从头到尾只当迁移评测用。这张图是"改进能跨模型迁移"最直接的证据，我觉比主表 Avg. 那栏更有说服力。*

## 🔬 六、消融：真正兜底的，是机制推理还是那两道门

消融表信息量很大，整张搬过来：

**Table 4　设计消融**（全部用 DeepSeek，成功率 %，Avg. 三基准等权）

| 变体 | Pro | Verified | Polyglot | Avg. |
|------|-----|----------|----------|------|
| **Full ELITE**（K=7） | 85.6 | 73.3 | 69.3 | **76.1** |
| *替换选择策略* | | | | |
| Select-one（LLM 挑一个） | 83.3 | 68.0 | 64.0 | 71.8 |
| SIFT-style Select-one（Bradley–Terry 聚合） | 85.0 | 72.0 | 46.0 | 67.7 |
| Evaluation-based Select-one（每轮 7×30 评估挑最高） | **91.7** | 70.0 | 62.0 | 74.6 |

| Direct joint implementation（七条建议一次性合写） | 78.3 | 72.0 | 66.0 | 72.1 |
| *其他组件消融* | | | | |
| w/o hypothesis generation | 85.0 | 68.0 | 60.0 | 71.0 |
| **w/o deterministic gates** | **59.4** | **51.3** | **45.3** | **52.0** |

看到表格底部那行我愣了一下。把两道确定性门全拿掉，均分从 76.1% 塌到 52.0%，Pro 只剩 59.4%——基本打回、甚至低于 60.0% 的初始 Agent。也就是说，撑住这套"免评估自进化"的，很大一块是编译检查、接口合规、冒烟测试这些最朴素的东西，不是 LLM 那套听起来很高级的机制推理。门一撤，让所有探索子都进集成、后代也不经确定性过滤就接受，LLM 的"互补/冗余判断"反而把 Agent 带沟里了。

这就引出一个我没完全看懂、也觉得作者没讲透的点：到底哪部分增益来自"读代码重组"，哪部分来自"把烂补丁挡在门外"？w/o hypothesis generation 掉到 71.0、Direct joint implementation 掉到 72.1、Single exploration 掉到 69.9，都在说"结构化假设 + 先各自实现出可执行证据 + 再集成"这一步确实有用；但 w/o gates 那一下跌了 24 个点，量级完全不是一个档次。论文把结论写成"成功仍需约束（constraints）"，措辞是克制的，可我更想看到把门单独留在、把机制推理换掉的对照——现在这组消融，还拆不干净。

还有个挺微妙的对照：Evaluation-based Select-one 在 Pro 上冲到 91.7%，比 ELITE 高 6 个点，代价是每轮把七个孩子在 30 道 Pro 题上全跑一遍、$7\times30=210$ 次 child–task 评估。这个变体等于把论文反对的东西作为上限摆出来了：**盯着目标榜挑最好的孩子，目标榜上确实能更高**；可它的 Verified 70.0%、Polyglot 62.0% 又都不如 ELITE，均分 74.6% 还是低一截。作者拿它论证"机制整合是评估型选择之外的 competitive alternative"，我觉得这个说法是站得住的，也顺手把"评估不是免费的、且会伤迁移"讲圆了。

公平性上得挑一句：Table 4 里只有 Full ELITE 和 w/o gates 是三次独立运行的均值，其余七个变体全是单次。论文自己都注明 "the selection comparisons are limited to single runs"。拿一次跑的结果去比三次均值，方向和量级可以参考，小数点后别太当真。Qwen 的 baseline 各只跑一次，也是同一个意思。

宽度敏感性（Table 5）给了一个挺有意思的非单调：

**Table 5　探索宽度敏感性**（三次运行均值，默认 K=7）

| 宽度 K | Pro | Verified | Polyglot | Avg. |
|--------|-----|----------|----------|------|
| 3 | 82.8 | 67.3 | 61.3 | 70.5 |
| 5 | 85.0 | 70.7 | 68.7 | 74.8 |
| **7** | **85.6** | **73.3** | **69.3** | **76.1** |

$K=9$ 在 Pro 上最高（88.9%），可两个迁移基准都往下掉，均分反而略低于 $K=7$。孩子越多、越容易拼出讨好目标榜的组合，通用性却开始让步——这个拐点和整篇论文"别盯着固定分布优化"的主张，意外地自洽。作者的措辞是 diminishing returns，我觉得还可以再直白点：探索宽度在这里其实也是个隐形的过拟合旋钮。

## 💡 七、拆开黑盒：集成真的拿到最好的那个了吗

论文花了不少篇幅做事后诊断，而且反复强调一句话：这些下游分数全是演化结束之后测的，从没喂回循环。这点诚实，我认。

![图 3：DeepSeek-V4-Flash 一次运行的事后演化动力学与机制组合](https://www.mulanai.com/fs/files/1127_21ec8169_posthoc.png)

*图 3（论文 Figure 3）：(a) 第一个被接受的步里，H1–H7 七个探索子在 60 道 Pro 题上的分数是 80.0、3.3、80.0、76.7、83.3、80.0、83.3，探索均值 69.5%（虚线），橙色集成后代 Int. 拿到 81.7%——赢过五个孩子，但没追上最高的 83.3%。(b) 十代演化曲线，从 60.0% 起步，第一次接受就跳到 81.7%，中途有两次回退、一代掉到 73.3%，最终 86.7%，整体 +26.7 pp；实心点是被接受的更新，叉号是没更新父代的代（1、3、7 代假设组合失败，8、10 代集成后代被接受门拒）。(c) 机制组合案例：G6 那代，Child H4 的 "Output reading"（完整读输出）和 Child H3 的 "Exit-status feedback"（退出码反馈）来自两个同父孩子，集成后代把两者合到一起，本地探针里返回了全部 100,000 行输出、且退出码正确为 7。*

这张图信息密度很高，三个子图各戳一个点。

(a) 里那个 H2 掉到 3.3% 特别值得琢磨——一个几乎全崩的孩子，因为循环里不看分数，它不会因为"考差了"被提前淘汰，只可能被门挡掉或在集成时被判断为不完整/冲突。集成后代 81.7% 赢过五个孩子，却没够到最高的 83.3%。论文自己写得很坦诚：integration does not necessarily recover the best-performing exploratory alternative。也就是说，**整合并不是挑出最优的免评估替身**，它是另一套目标——把能共存的机制拼到一起，代价是有可能放过那个单点最强的孩子。看到这我反而松了口气，作者没把话说满。

(b) 的曲线一点都不单调。十代里只有五次真正更新了父代，中间两次接受更新之后分数还往下掉。门保证的是"能跑、结构对"，不保证"下游更强"，这个 non-monotonic trajectory 就是明证。顺着这个再聊聊：万一演化一直往回退呢？论文只跑 T=10，作者也在结论里承认"downstream performance can fluctuate across accepted updates, making longer-term evolution an important subject"。单谱系、没有档案库兜底，走偏了就只能带着当前父代继续。这是我认为最实在的一个局限。

(c) 是全文我最中意的一张子图。它把"互补"这种抽象判断落成了能验证的具体事：一个孩子解决"大输出读不全"（Large-output timeout），另一个补上"没有退出码"（No exit code），集成后代既返回了 100,000 行、又给出 exit code 7。你想想看，没有任何分数告诉系统这俩能拼，是读了两份实现的接口和依赖才判断出来的。这一下，前面所有形式化都落地了。

另外一个跨 scaffold 的验证（Table 3）：换成成熟的 mini-swe-agent v2.4.6、固定 Claude-opus-5.5 backbone，十轮演化出六个被接受的孩子，Pro 从 71.7% 走到 83.3%（+11.7），Verified 70.0%→78.0%（+8.0），Polyglot 72.0%→78.0%（+6.0）。换 scaffold、换模型、三个基准全涨，说明这套流程不是绑死在 DGM 起点上的。不过它也只跑了一组组合，别当成普适性证明。

## 🤔 八、我的判断：一次诚实的问题重述，不是范式颠覆

把亮点和疙瘩分开摆。

我真正被打动的，是那个提问方式的掉头。"不看分数，能不能决定哪些改动往下传"——这个问题比方法本身值钱。它抓住了一个大家默认接受、其实没道理的假设：想改好自己，就得先在任务上考自己一遍。而 Coding Agent 恰好给了这个假设一个可钻的空子：改动是能读的代码，代码里的机制、接口、依赖就是证据。**同父并行实现 → 实现级证据 → 机制级重组 → 确定性门兜底**，这条链子干净利落，逻辑闭环，迁移结果也确实给"刷固定榜单伤通用性"提供了一个干净的数据点。DGM 关掉幻觉检测刷分那种事，正好是它动机部分最好的旁白。

但疙瘩也不少，我数得出来的就有这些：

主榜是输的。Pro 上 85.6% 对 86.7% / 88.3%，Qwen 上差得更多，靠迁移和成本把叙事翻了过来。这不是造假，是口径选择，读的人得自己拎清。

"免评估"要加引号。严格讲是免**候选任务评估**、免把下游结果喂回循环；事后诊断自己跑了大量评测——论文算过，光把每个集成候选在 T=10 轮上全评一遍就要最多 600 次 rollout，第一步那个对比是 8 个 agent × 60 题 = 480 个 outcome。这些分数只是没进 $S_t$，不是没产生。作者措辞一直用 "without downstream candidate task evaluation" 和 "in our setting"、"feasibility"，克制得近乎小心翼翼，我挺欣赏；可要是有人拿它当"完全不评估也能自进化"，那就读歪了。

确定性门的覆盖面窄。附录 Table 12 自己写 "Their coverage concerns basic operability rather than comprehensive semantic correctness or downstream task performance"。它挡得住编译不过、接口错位、工具调用乱序，挡不住一个逻辑写歪但能跑通过的补丁。w/o gates 那 24 个点的崩塌说明门有多关键，也反过来说明这套"智能"的地基有多依赖"能编译"这种硬约束。哪天遇到一个语法全对、语义全错的自我修改，循环里没有任何东西能拦它。

对比的公平性和覆盖。不是等算力对砍，8.8 倍配置依赖；大量消融单次运行；Qwen baseline 单次；固定的 60 题演化子集、两个 backbone、一个额外 scaffold 组合、只在 coding 任务；单谱系无档案库、只跑十代。作者在结论里把这些一条条列了（limited repetitions、single lineage、selected benchmark subsets、broader task coverage），没藏，但也没解决。同期还有 Live-SWE-agent 那类零小时运行时演化的路线在旁边，论文没拿来做正面对比，我觉得是个缺口。

集成不稳定地拿到最优子代。(a) 里 81.7% < 83.3%，(b) 里曲线回退两次，长程会怎样没人知道。

所以定位我给得比较保守：**这不是底层突破，是一次很干净的问题重述加工程整合**。 剥开包装，它没有发明新的模型、新的学习算法，甚至没发明新的搜索——它把 DGM/HGM 那条"评估→选择"的链子，从"选整个候选"下沉到"选机制"，再用实现级检查替掉下游打分，机制推理本身还是那个 LLM 在读代码。它证明的是"在这个设定下，不用候选任务反馈也能把 Agent 改强一大截"，不是"评估过时了"。这个区别，比 85.6 还是 88.3 重要得多。

## 📝 收尾：给做 Agent 的人几句实在话

如果你手上也在折腾自改进 Agent、自动调 prompt / 工具 / 工作流，这套东西值得抄的是三件：别一上来就给候选打分，先让每条改进**独立地、从同一个基线**落成能跑的实现；决策时看的是机制之间能不能共存，而不是哪个候选分高；再配一组编译 / 接口 / 冒烟的硬检查兜底。尤其当评估一次很贵、或者你已经闻到"分数在涨、换题就垮"的过拟合味儿时，这个思路几乎是量身定做的。

反过来，要是你的目标就是某个固定榜单的 SOTA，那 Evaluation-based Select-one 的 91.7% 已经把答案摆桌上了：盯着它挑，还是更高，只是得付 210 次评估每轮的代价，还得接受迁移掉点。免评估换来的不是更强的峰值，是更省、更通用、更不容易把题背下来。这笔账划不划算，得看你到底在优化什么。

还有个更根上的问题我一直没放下：整套循环自称"确定性"，可判断"哪些机制互补、哪些冲突"的，终究是一个会被措辞、上下文、随机性影响的 LLM。真正确定性的只有那两道门，而门只管能不能跑。当"确定性检查"兜住的只是可运行性、把最关键的兼容性判断留给一个不确定的模型时，这套"免评估"到底有多确定？论文没答，我猜这也是它把结论收在 "in our setting" 里的原因之一。
