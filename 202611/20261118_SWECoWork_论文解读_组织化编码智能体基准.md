# SWE-CoWork：把编码智能体放进组织里，才知道它会不会真正交付

## 1. 这篇论文的定位

### 1.1 一句话总结

SWE-CoWork 是一套面向组织化软件工程的**基准测试**：它让编码智能体在真实仓库与模拟工程组织中，自主完成“找需求—问同事—改代码—做验证—写交接”的完整工作，而不只是根据一份现成 issue 生成补丁。

### 1.2 研究背景

SWE-bench 一类基准通常把任务目标和仓库一起交给智能体，主要考察它能否通过代码修改让测试通过。这类设定推动了自动 issue 修复的发展，却提前替智能体完成了现实工作中很费力的一步：把分散、陈旧甚至互相冲突的组织信息整理成明确需求。

现实中的工程师面对的不是一份永远完整、静态且一致的规格说明，而是项目看板、多个版本的设计文档、聊天记录、代码评审、合并请求和 CI 历史。某项约束可能只掌握在模块负责人手里；搜索到的方案可能已经作废；实现中途出现的新日志还可能推翻原先判断。因此，代码生成能力变强，并不自动等于智能体能独立承担工程交付。

### 1.3 核心问题

论文要回答的不是“模型会不会写代码”这么单一的问题，而是：

1. 只给出简短交接说明时，智能体能否主动找到真正需要实现的需求？
2. 它能否识别需求负责人，用足够的代码上下文提问，并持续追问被暂缓的问题？
3. 它能否分辨当前有效信息与过期、错配或越界的干扰信息？
4. 获得需求以后，它能否把需求完整转化为代码、验证结果和可信的交接报告？

### 1.4 与已有工作的区别

已有基准大致覆盖了三类能力：真实仓库中的补丁生成、欠规格任务中的需求澄清，以及通用办公环境中的同事协作。SWE-CoWork 的差异在于把三者合并到同一个软件交付闭环中：

- 相比 SWE-bench、DeepSWE 等仓库级基准，它不再给出完整任务规格，而要求智能体自己恢复需求。
- 相比 Ask or Assume、Dialogue SWE-Bench 等单用户澄清设定，它设置多个责任边界不同的同事，需求并不集中于一个可询问对象。
- 相比 TheAgentCompany 等通用职场基准，它用真实代码仓库和私有可执行测试评价最终交付，并把每条需求链接到具体测试节点。
- 相比只报告最终分数的评测，它还保存需求披露、对话、代码、测试与交接之间的链路，用来定位需求究竟在哪一步丢失。

## 2. 论文定位：解决什么问题，填补什么空白

### 2.1 论文定位

这篇论文的核心贡献是**评价对象与评价粒度的改变**，而不是提出新的模型训练算法或编码智能体框架。

第一，评价对象从“规格执行者”转为“数字员工”。智能体不再被动接受已经整理好的需求，而要像新加入团队的工程师一样，在有限时间内主动理解项目状态、组织协作并完成交付。

第二，评价粒度从“补丁总分”扩展到“需求生命周期”。每条被评分的需求都可以关联到责任人、发现路径、同事披露记录以及 F2P/P2P 测试，因此能够区分“没找到需求”“问了但没拿到”“拿到了却没实现”“实现了却误报完成”等不同失败。

第三，论文用 CoWork 与 Oracle-Spec 的配对实验拆分两类瓶颈：前者需要自己获取需求，后者直接获得完整需求。两组保持仓库、测试、脚手架和执行预算一致，从而观察组织信息成本之外仍然存在的实现与验证困难。

### 2.2 目标能力

论文把数字员工所需的组织能力概括为四点：

- **Continuous（持续）**：跨聊天、看板、文档和评审维护一致上下文，并随新证据或版本变化调整实现。
- **Proactive（主动）**：没有逐步人工提示时，也能从简短交接出发寻找责任人和约束，同时避开已取消卡片、相邻项目等干扰。
- **Efficient（高效）**：在有限预算内自主沟通，并在某个问题等待答复时推进其他需求，而不是整体停滞。
- **Persistent（持久）**：在长时执行和上下文压缩中持续跟踪每条需求，从澄清一直追踪到实现、验证和最终交接。

### 2.3 填补的空白

过去评测往往默认“需求已经存在且可信”，或者只考察一次性澄清。SWE-CoWork 补上的是组织信息持续变化的中间地带：需求既要被发现，也要被确认其时效性、来源与责任权威；即使已经获得，仍要在后续编码和交接中被持续跟踪。由此，它把“知道要做什么”和“把知道的事情真正做对”变成了可分别观测、又能在同一任务中联合评价的问题。

## 3. 核心方法：SWE-CoWork 如何构造组织化工程任务

### 3.1 总体结构

每个任务由四层组成：

1. **真实代码层**：一个冻结版本的开源仓库及其参考修改。
2. **共享工作场所层**：项目看板、版本化文档、聊天、代码评审、合并请求、CI 与运行产物。
3. **数字员工层**：具有角色、局部知识和交互规则的模拟同事。
4. **可执行合同层**：私有 F2P/P2P 测试，以及需求到测试节点的链接。

智能体从简短 onboarding note 开始，通过工具自主检索工作场所、联系同事并修改仓库；结束后提交代码补丁与交付说明。测试在独立环境中验证新功能是否实现、旧功能是否保持。

### 3.2 数字员工不是自由聊天的角色，而是受规则约束的信息边界

每个任务围绕目标项目及四个相邻项目构建 26 名数字员工，全基准共有 2,626 份员工画像。真正持有影响可执行结果之需求的员工数量中位数为 6。每名员工由三部分定义：

- **Responsibility（责任）**：其对哪个模块、接口或决策负责。
- **Local knowledge（局部知识）**：它能够解释哪些需求，哪些问题必须转介给他人。
- **Collaboration behavior（协作行为）**：例如先要求复现步骤或调用路径、一次只回答一个主题、暂缓回答并等待跟进。

环境负责控制在当前步骤允许披露什么信息，语言模型只负责生成符合这些约束的回答。这一设计很重要：如果同事可以不受约束地自由补充答案，评测结果会更多反映模拟器的随机性，而不是智能体的信息获取能力。

![图1：同一 Click 需求在 issue 式任务与 SWE-CoWork 组织任务中的不同呈现](https://www.mulanai.com/fs/files/1118_aed1e009_20261118.png)

*图 1：左侧直接给出 output capture 目标；右侧只给出“完成 Click 9.0 兼容性工作”的交接，智能体需要调查 CLK-201 与 DOC-11、带上下文询问 Lucy、实现并检查，再根据新证据修订。两侧最终都进入 F2P/P2P 测试。*

图 1 的关键不是工具界面更多，而是任务理解本身成为执行过程的一部分。以 Click 为例，旧文档中的“单一输出字符串”已被“分离且保留交错顺序”取代；智能体需要结合版本、执行记录与负责人回答，确认 `output=ABC`、`stdout=AC`、`stderr=B` 这类语义，而不能把搜索到的第一段文字直接当成最终规格。

### 3.3 任务执行流程

一个典型运行包含六个相互交错、而非严格线性的活动：

1. **Orient**：阅读交接说明，检查仓库，确认目标项目、初始范围和联系人。
2. **Investigate**：搜索看板、文档、聊天和工程历史，核对来源与版本，追踪接口改名等引用。
3. **Ask**：找到未决决策的负责人，携带代码或运行证据提问，处理转介和补充上下文要求。
4. **Build and verify**：实现需求，运行测试并检查回归。
5. **Revise**：接收新消息、运行轨迹或纠正，重新确认其影响并修改代码。
6. **Deliver**：在交付说明中记录已确认需求、实现、验证结果和未决问题。

论文用 Kimai 任务说明为什么这些步骤不能割裂。智能体先把 5,400 秒转换成 1.5 小时并通过测试，但设计文档没有说明功能如何启用。询问导出负责人后，它才知道必须读取当前用户的 `timesheet.export_decimal` 偏好，而且每次导出都要重新读取，即使多个用户复用同一个 renderer。由此可见，“局部测试通过”不等于“需求已完整”；同事澄清可能直接改变补丁及其测试。

### 3.4 五类工作场所信息挑战

![图4：工作场所信息挑战按证据的时间、来源和权威组织](https://www.mulanai.com/fs/files/1118_a41cfb86_20261118.png)

*图 4：五类挑战分别是 late evidence、superseded conclusions、ambiguous provenance、scope distractors 和 fragmented ownership。*

- **晚到证据（Timing）**：实现开始后可能出现新的 SDK 观察或客户端版本请求。智能体要检查更新、找到负责人，并重新评估受影响的代码与测试。
- **被取代结论（Timing）**：Stencil 的 DOC-13 v1 草稿曾建议没有 source map 时返回空对象，v3 已发布版本却要求 `map` 保持 `undefined`。有效策略是重建时间线，而非选择最先搜到的记录。
- **来源含糊（Provenance）**：controller-runtime 附件标题写 RUN-98752，复制内容却写 RUN-20547。智能体必须对齐输入、运行和代码版本，把观察事实与推断原因分开。
- **范围干扰（Provenance）**：已取消卡片、重复卡片、被否决方案和相邻项目仍可被搜索到，需要用状态历史、项目归属和评审结果恢复当前范围。
- **责任碎片化（Authority）**：相邻模块联系人只知道局部边界，真正负责人又可能要求复现或调用路径；一次回答还可能只解决一个主题。智能体必须逐项跟踪未决主题，而不是把“已联系某人”误当成“需求已澄清”。

这些案例都有可访问的纠正信息或责任同事，因此并非故意设置无解陷阱；考察的是智能体是否主动完成证据核验。

### 3.5 数据规模与工程复杂度

SWE-CoWork 包含 101 个累积式开发任务、101 个上游仓库、11 种编程语言和 12 个应用领域。参考修改的生产代码新增量中位数为 2,955 行，涉及文件数中位数为 60；每项任务由中位数 32 个可执行测试节点评分。全集共有 2,699 个 F2P 节点和 562 个 P2P 节点，总计 3,261 项检查。

![图2：任务的语言、领域、生产代码变更规模和测试合同分布](https://www.mulanai.com/fs/files/1118_a9876dfa_20261118.png)

*图 2：语言以 JavaScript（20）、Python（17）、TypeScript（12）为主；领域以 Web & frontend（26）、Dev tools & compilers（22）为主。直方图虚线为中位数，阴影为四分位区间。*

工作场所也具有相当的信息量：全集包含 10,329 张看板卡片、5,097 份版本化文档、40,836 条聊天消息、1,194 个合并请求和 2,626 份同事画像。初始交接说明中位数只有 206 词，而任务文档语料中位数为 5,453 词。信息量的差距意味着，把所有材料无差别塞入上下文既低效也不现实，检索与选择本身就是任务能力的一部分。

### 3.6 需求—证据—测试的可追踪设计

每条评分需求都连接到责任同事或公开记录、回答责任边界，以及检查该需求的测试节点。环境中的披露日志记录同事实际释放了什么需求，轨迹还保存工具回复是否进入智能体观察。这样，最终测试失败可以被追溯到发现、提问或实现阶段，而不是只得到一个不可解释的分数。

## 4. 实验与结果

### 4.1 实验设置

实验按以下步骤组织：

1. **全模型 CoWork 评测**：11 个模型均以 max effort 在 101 个任务上运行。GPT-6 Astra 使用 Codex scaffold，其余十个模型使用 Claude Code scaffold；所有运行中的数字员工都由 GPT-5.6 Terra 以 high reasoning effort 支撑，执行预算上限为 8 小时。
2. **Oracle-Spec 配对对照**：对 Seed Evolving 与 GPT-6 Astra，额外在任务开始时直接提供完整需求，不再提供同事咨询；任务、仓库状态、测试合同、脚手架和预算保持不变。
3. **Claude-Opus-5.5 轨迹分析**：对 101 条 CoWork 轨迹，把同事对话、需求披露、测试与交接报告链接起来。选择它是因为其 CoWork F2P 最高。
4. **补充行为分析**：统计模型调用、token、工具调用、上下文压缩、首次代码编辑前的工作场所查询、同事消息，以及需求询问率、命中负责人比例、后续跟进等指标。
5. **轨迹行为评级**：GPT-6 Astra 以 xhigh reasoning effort 作为评审器，在看不到私有评分结果的情况下，按 ineffective、partial、effective、adaptive 四级评价 10 个策略维度和 6 个协作维度。

设任务数为 \(N=101\)。任务 \(i\) 中，\(f_i,p_i\) 分别为通过的 F2P/P2P 节点数，\(F_i,P_i\) 为对应节点总数，则：

\[
\mathrm{F2P}=100\frac{\sum_{i=1}^{N}f_i}{\sum_{i=1}^{N}F_i},\qquad
\mathrm{P2P}=100\frac{\sum_{i=1}^{N}p_i}{\sum_{i=1}^{N}P_i}
\]

\[
\mathrm{Pass\ rate}=\frac{100}{N}\sum_{i=1}^{N}\mathbf{1}[f_i=F_i\ \land\ p_i=P_i]
\]

F2P/P2P 是跨任务汇总节点后计算，因此测试节点更多的任务权重更大；Pass rate 则按任务等权，并要求同一次运行中的所有新旧测试全部通过。

### 4.2 主结果：局部实现与完整交付之间存在巨大落差

| 模型 | F2P (%) | P2P (%) | Pass rate (%) |
|---|---:|---:|---:|
| Claude-Opus-5.5 | 63.84 | 93.24 | 6.93 |
| GPT-6 Astra | 62.91 | 89.15 | 7.92 |
| Seed Evolving | 39.09 | 94.48 | 0.99 |
| Qwen3.8-Max | 35.70 | 91.80 | 0.00 |
| GLM 5.3 | 31.27 | 87.72 | 0.99 |
| Qwen3.8-Flash | 30.70 | 93.40 | 0.00 |
| DeepSeek V4.1 Flash | 28.20 | 94.30 | 0.00 |
| Kimi K3 | 27.08 | 84.88 | 0.99 |
| GLM 5.2 | 24.40 | 95.20 | 0.00 |
| Seed 2.1 Pro | 21.01 | 81.85 | 0.00 |
| DeepSeek V4 Pro | 13.04 | 90.21 | 0.00 |

两个领先模型能通过约 63% 的新功能测试，却只完整完成 7/101 与 8/101 个任务；其余模型最多只完整完成 1 个任务。P2P 整体较高且排序与 F2P 不同，说明“避免破坏旧行为”和“交付全部新行为”是不同能力，不能用一个较高的回归测试分数掩盖新需求的大量缺失。

### 4.3 需求获取与交付高度相关，单纯增加工具调用没有用

![图5：同事需求获取率、工具调用量与 F2P 的跨模型关系](https://www.mulanai.com/fs/files/1118_297cf807_20261118.png)

*图 5：左图横轴为同事持有需求的获取比例，右图横轴为每次运行的工具调用中位数（对数刻度），纵轴均为 F2P。*

同事需求获取率与 F2P 的 Spearman 相关系数为 **0.94**，工具调用量与 F2P 只有 **0.08**。GPT-6 Astra 和 Claude-Opus-5.5 分别获得 67.8% 和 64.2% 的同事持有需求；DeepSeek V4 Pro 每次运行发送同事消息的中位数为 0，只获得 1.8%，F2P 为 13.04%。

进一步的八模型分析显示，首次编辑前工作场所查询数、全程查询数与 F2P 的相关分别为 -0.10、-0.17；首次代码编辑出现得更早与 F2P 的相关为 -0.62，更多同事消息与 F2P 的相关为 0.71。重点不是“少查资料”或“尽早改代码”本身更好，而是领先模型更能把组织信息获取与实现循环结合起来。所有这些都是跨模型相关关系，不构成因果证明。

### 4.4 Oracle-Spec：给全需求只解决一部分问题

| 模型 | 条件 | F2P (%) | P2P (%) | Pass rate (%) |
|---|---|---:|---:|---:|
| Seed Evolving | CoWork | 39.09 | 94.48 | 0.99 |
| Seed Evolving | Oracle-Spec | 55.76 | 89.50 | 0.99 |
| GPT-6 Astra | CoWork | 62.91 | 89.15 | 7.92 |
| GPT-6 Astra | Oracle-Spec | 78.84 | 91.81 | 7.92 |

完整需求使 Seed Evolving 和 GPT-6 Astra 的 F2P 分别提高 **16.67** 和 **15.93** 个百分点，证明需求获取确实消耗了显著能力或执行预算。但两者完整任务通过率完全不变；即使给出全部需求，仍分别留下约 44% 和 21% 的 F2P 节点未通过。Seed Evolving 的 P2P 还下降 4.98 个百分点，说明增加新实现可能同时带来更多回归。

因此，组织信息瓶颈并不能解释全部失败，下游的实现、验证与完成判定本身就是独立瓶颈。

### 4.5 需求级轨迹：找到负责人只是起点

![图7：Claude-Opus-5.5 的需求获取状态、不同信息状态下的测试通过率及失败首现阶段](https://www.mulanai.com/fs/files/1118_1f23958e_20261118.png)

*图 7：从同事持有需求的披露状态，一直追踪到对应 F2P 节点是否通过。*

Claude-Opus-5.5 对已查询卡片的首次提问，平均 **93.3%** 能直接找到责任负责人，但 2,176 条同事持有需求中只有 1,400 条（64%）最终披露给智能体。其余为：357 条（16%）已提出卡片但未获披露，363 条（17%）负责人已因其他卡片被联系、该卡片却从未提出，56 条（3%）属于完全未联系的负责人。

这说明主要问题已不是“不知道找谁”，而是**与正确的人沟通时没有完整追踪所有主题**。已披露需求对应 F2P 节点通过率为 68.8%，未披露需求为 49.8%；公开记录需求为 73.7%。但在有需求链接的失败 F2P 节点中，548 个（56%）最早失败在 implement，即需求已经到达智能体却仍未实现；415 个（42%）失败在 ask，只有 16 个（2%）归因于 discovery。

carapace-bin 是极端例子：智能体获得全部 25 条同事需求，却仍失败 35 个 F2P 节点中的 22 个，轨迹中存在错误用法、参数与候选描述，以及未检查的构建失败。信息获得与工程兑现之间没有自动等号。

### 4.6 被暂缓的问题容易被永久遗忘，交接报告也不可靠

![图8：交接声称、延期线程跟进与同事消息时间分布](https://www.mulanai.com/fs/files/1118_ac38ba64_20261118.png)

*图 8：左图比较测试通过/失败需求在交接中的报告状态；中图追踪 owner-card 延期线程；右图把 2,552 次同事消息按运行内已耗时比例分桶。*

450 个首次答复被暂缓的 owner-card 线程中，智能体只跟进 297 个，其中 205 个（69%）最终获得披露；另外 **153 个完全没有后续跟进，披露率为 0**。这些被放弃线程在首次暂缓时仍有中位数 7.1 小时预算，智能体此后还继续工作中位数 3.4 小时，所以不能用“没时间了”解释。

整体消息活动并没有停止：20% 的同事消息发生在运行的最后五分之一。问题是全局活跃度掩盖了单条线程的失联。PostCSS 案例中，智能体曾对 CSS-227 补充证据并再次询问，却在第二次暂缓后直接宣称相关流处理完成；该运行全部 16 个失败 F2P 节点都涉及未披露的同事需求。

交接同样存在校准问题：826 条被报告为完成的需求中，255 条（31%）未通过对应测试。922 条测试失败需求里，28% 被写成 done、35% 标为 open、37% 根本没提及。HotswapAgent 任务甚至在内部笔记仍列出 8 条待办时宣称任务完成。

### 4.7 行为分析：证据到代码的转化最值得继续研究

![图9：Claude-Opus-5.5 的行为评级分布及各行为与单任务 F2P 的探索性相关](https://www.mulanai.com/fs/files/1118_13d4e5eb_20261118.png)

*图 9：左图四级行为类别按可评估运行归一化；右图为 Spearman 相关及 95% bootstrap 区间。*

与单任务 F2P 相关最强的是 **evidence-to-code translation（证据到代码）**，\(\rho=0.36\)；其次是 causal debugging 与 verification design，均为 \(0.30\)。同事消息数和工具调用数分别只有 \(0.21\) 与 \(-0.21\)。这再次指向“如何使用信息”比“做了多少动作”更关键。

行为分布还暴露了明显短板：calibration & stopping 有 61.4% 的可评估运行仅属 partial；owner questions/follow-through 为 53.5% partial；delivery accountability 为 43.6% partial，另有约 1% ineffective。轨迹评审器共识别出 49 次仍有可执行下一步的过早停止，其中 48 次自主停止的剩余预算中位数为 2.8 小时。

这些结果适合用于提出机制假设，例如持久需求状态表可能帮助跟进与停止判断；但相关系数普遍不高，区间也较宽，不能据此认定某个行为维度就是提升分数的直接因果杠杆。

## 5. 主要结论

1. **高局部通过率不等于能独立交付。** 领先模型约 63% 的 F2P 与不足 8% 的完整任务通过率形成鲜明落差，长任务中“每条需求都不能丢”的乘法效应十分突出。
2. **组织信息获取是强约束，但不是唯一约束。** 需求获取率与 F2P 的跨模型相关达到 0.94；Oracle-Spec 也带来约 16 个百分点的提升，却没有提高完整任务成功率。
3. **动作数量不是有效性的替代品。** 工具调用与 F2P 几乎无关，更多检索也不必然更好；关键是找到有权威的信息并把它纳入实现循环。
4. **前沿模型的失败从“找人”转向“持续跟踪”。** Claude-Opus-5.5 很会选择负责人，却会漏提卡片、忘记暂缓线程、拿到需求后实现不全，并过早停止。
5. **交接报告需要独立验证与校准。** 31% 的“已完成”需求未通过测试，说明智能体自我报告不能直接作为完成依据。
6. **可靠数字员工需要显式的需求生命周期管理。** 论文建议跟踪责任人、未决问题、实现状态、验证证据与交接声称，但也明确表示这一方向能否提高端到端交付仍是开放问题。

## 6. 局限与启发

### 6.1 局限

- **模拟组织的生态效度仍有限。** 同事由 LLM 生成语言、由规则限制知识披露，虽然提高了可控性，却不能完全代表真实人类在权限、情绪、组织博弈和非正式沟通上的复杂性。工作场所记录也是围绕任务编写的 authored workplace，而非未经筛选的真实企业历史。
- **模型比较混入脚手架差异。** GPT-6 Astra 使用 Codex，其余模型使用 Claude Code，因此跨模型排名不是严格的“只换模型”对照。论文测的是模型与脚手架组合在统一任务环境下的表现。
- **主结果的统计精度有限。** 101 个任务上，6.93%、7.92%、0.99% 分别只对应 7、8、1 个完整成功任务；主表没有报告多次重复运行或完整任务率的置信区间，不宜过度解读细小差距。
- **轨迹分析只深入一个模型。** 详细需求生命周期诊断集中于 Claude-Opus-5.5，不能自动推广为所有模型完全相同的失败机制。
- **部分指标依赖 LLM 评审。** 行为类别与过早停止由 GPT-6 Astra 评审，尽管有 rubric、盲于私有成绩及程序化日志辅助，仍可能带入评审模型的偏好与误判。
- **聚合口径需注意。** F2P/P2P 按全库测试节点池化，Pass rate 按任务等权；附录部分分层结果又使用单任务比例的均值。不同口径不能直接混比。
- **论文与当前仓库存在版本差异。** 论文报告 2,699 个 F2P、562 个 P2P 节点及图 2 的语言计数；当前 README 写为 2,701 个 F2P、561 个 P2P 节点，并给出略有不同的语言计数。本文实验数字以 arXiv v1 为准，复现时应锁定论文对应的 release/manifest，而不是默认仓库最新状态与论文逐项相同。

### 6.2 启发

- **把需求状态做成一等公民。** 智能体可维护结构化台账：需求 ID、责任人、来源版本、披露状态、未决问题、代码位置、验证节点和交接状态。关键是每次新消息、代码修改与测试后更新，而不是只在开头写计划。
- **把“等待回复”变成可恢复任务。** 对 deferred thread 设置明确的后续动作和截止时间；在每次阶段切换与最终停止前扫描未决线程，避免总体忙碌掩盖单项遗忘。
- **停止条件应从自我感觉改为证据检查。** 只有所有范围内需求都具有实现与测试证据，且不存在可执行的澄清下一步时，才允许声明完成；否则交接必须列出准确遗留项。
- **优化重点从更多工具调用转向证据闭环。** 值得研究的是如何把自然语言约束映射到代码路径、测试断言和回归检查，尤其是已披露需求仍占失败节点 56% 的问题。
- **评测Agent系统时应拆分信息成本与执行成本。** Oracle-Spec 配对设计可复用于其他长程Agent：同一任务分别提供“自己找信息”和“直接给全信息”，能避免把所有失败都误归因于推理或编码能力。

### 7.3 运行要求与基本流程

仓库要求 Linux/amd64、Docker Engine、Python 3.10+，以及供模拟同事使用的 Responses API endpoint。任务 039 和 093 还需要 root controller、systemd、cgroup v2 与 runc。完整单任务最长运行 8 小时，完整复现成本不低。

基本流程是：

```bash
cd release
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
cp .env.example .env  # 配置同事模型 endpoint 与密钥
sha256sum -c FILES.sha256
./cowork doctor
./cowork pull 001
./cowork start 001
./cowork mcp RUN_ID
./cowork finish RUN_ID
./cowork status RUN_ID
```

智能体只应接触 MCP server；宿主目录含私有测试和参考解答，不应挂载给智能体。许可证方面，各上游代码保留原许可证与版权声明，release 不对第三方代码提供新的统一许可。

## 8. 总体评价

SWE-CoWork 最有价值的地方，是把“智能体有没有写对代码”扩展为“组织有没有把正确的事可靠交付”。其需求—同事—证据—测试—交接链路，使失败第一次能够沿着完整工程生命周期被定位，而 Oracle-Spec 对照又清楚证明：即便信息全部给齐，完整交付依然困难。

这套基准并不意味着模拟同事已经等同于真实组织，也不意味着当前排名可以作为纯模型能力的绝对排序。但它准确击中了一个被传统 coding benchmark 低估的问题：未来编码智能体的核心竞争力，可能不只是生成更大的补丁，而是**在长时协作中不丢需求、不忘追问、不误报完成，并让每一项完成声称都有可执行证据支撑**。
