# 不让模型写一个字，Agent 反而更准了：System 1 Agents 把工具调用做成选择题

之前帮一个做影像组学的朋友调本地 agent，碰上一个特别难查的 bug：整条流水线跑完，结果离谱得不行，但全程没有一个报错。翻了半天日志才发现，第一步调工具的时候，模型给 `fold` 参数填了一个请求里根本没出现的数字——它自己觉得这个数挺合理，就写上了。JSON 合法，schema 校验通过，工具照跑不误，后面十几步全踩在这个假值上，一路错到底，安静得像什么都没发生。

做过 agent 流水线的人大概都懂这种恐惧。幻觉最吓人的地方不是胡说八道，而是胡说得格式正确、悄无声息。

上周刷到 arXiv 上这篇 2611.21053，标题叫 *System 1 agents: a method for local, reliable and fast agentic AI*，我第一反应是"又来一个给小模型套壳的"。读完发现，这帮人干了一件挺狠的事：干脆不让模型生成任何一个字的工具调用。

---

## 📝 核心摘要

痛点很具体：临床和科研里的敏感数据不能出院，云上那些最能打的大模型用不了；换成本地小模型，它又会往工具调用里塞编造的参数值，一个假值污染整条流水线。作者的解法是把"生成"整个拿掉——一个确定性 compiler 把工具的 JSON schema 和用户请求编译成一道道选择题，选项只来自请求原文、schema 和几条固定规则，决策模型单次前向给每个选项打个概率，代码再照着选中的答案逐字拼出调用。在 1,952 条请求、157 个生物医学工具上，最好的 System 1 agent 选对工具或正确拒答 97.0%，压过 18 个本地 LLM agent 配置的上限 95.2%；10,888 次调用零虚构，对照组是 5.5–19.7%。

说实话，这不是模型层面的突破。六个决策模型全是别人发布的，一个都没微调，标题老老实实用了 "a method" 而不是 "a model"。它更像一次很扎实的系统整合。最值钱的地方也不在**零虚构**这句口号——那是设计上的必然，不是实验跑出来的惊喜——而在 compiler 怎么把候选值凑齐，以及这套评测做得有多较真。

## 🎯 两堵墙，和一个被忽略的事实

要把这件事讲清楚，得先看作者面对的是哪两堵墙。

第一堵是隐私。最能打的语言模型都跑在云上，每一次请求、每一份被提到的数据都要离开机构。放到病人数据上，这跟数据保护规则和院内制度直接冲突。本地模型把这堵墙拆了，数据不出院。

第二堵是可靠性。本地模型个头小，而且**任何**基于语言模型的 agent 都是逐 token 把工具调用写出来的。它可能调一个不存在的工具，可能用一个 schema 里根本没有的参数名，更常见的是给某个参数填一个用户从来没给过的值。论文里这句话我读了两遍：在一个分析流水线里，这种幻觉值不会显眼地失败，它只改变这一步的结果，而后面每一步都建在这个结果上。

推理模式（reasoning on）能压掉一部分错误，代价是每次调用生成的文本成倍上涨，时间和能耗跟着涨。这就成了个死结：要隐私就得本地，要本地就小，要小就爱编，想让它少编就开推理，一开推理就慢又费电。

关键在于作者盯上了一个大家容易滑过去的事实：工具调用其实不是开放式写作。工具是列在目录里的，一次正确调用需要的几乎所有值，要么**就写在请求里**，要么由请求按固定规则推出来（比如单位换算），要么明明白白列在工具的 schema 里。真正剩下的，只是一连串选择——调哪个工具、请求里哪个值该给哪个参数、到底该不该调。

这个判断成立有个前提，而这两年恰好把这个前提铺好了：MCP（Model Context Protocol）把工具统一成了「名字 + 描述 + 参数 JSON schema」的接口。既然工具已经被 schema 化了，那"写一段 JSON"就可以被改写成"答几道选择题"。我看到这儿的时候愣了一下——这个替换其实一直摆在那儿，只是没人把它推到这么彻底。

顺带说个命名上的反讽。作者借了卡尼曼《思考，快与慢》里的 System 1：快、自动、单步直觉判断。可卡尼曼笔下的 System 1 恰恰是偏见的来源，锚定效应、光环效应都归它管。这篇论文里 System 1 反倒成了可靠性的保证，原因无他——它的选项被关进了笼子。

## 🏗️ 方法核心：模型只判断，代码逐字执行

一句话讲清核心 idea：**把生成换成选择**。模型不再写调用，它只在一堆已经摆好的选项里挑；拼装调用的事交给确定性代码，一个字符都不许自由发挥。

整套东西拆成三个各管一摊的组件。

![图1：System 1 agent 架构，以及一条 nnU-Net 请求的完整走查](https://www.mulanai.com/fs/files/1121_0d507658_image1.jpg)

*图1：上半（a）是三个组件与数据流。左侧喂进来的是用户请求、MCP 工具目录（图上标了 42 个影像工具、115 个生物医学工具）和调用规则；中间的 Agent 是确定性控制流，五步依次是工具选择、工具适配、能力检查、参数填充、要值还是调用；右上是决策模型，一次前向、不生成文本，读的是 state / question / options，输出每个选项的校准概率；右下 compiler 把 schema 变成带类型的问题。最下面的输出只有三种：一次带置信度的 MCP 调用、一次拒答、或一条用固定模板写的缺失值追问。下半（b）是真实走查：请求是「Train the nnU-Net model liver_v1 for 100 epochs with the 2d configuration on fold 0」，工具选择在 43 个选项里给出 nnunet/nnunet_train，p=0.985；能力检查「这个工具能做请求里的事吗」yes 0.993；参数表里 configuration 选 2d（p=0.990）、epochs 选 100（p=0.997）、model_name 选 liver_v1（p=0.991）、fold 选 0（p=0.968，但它是文档默认值，不传），另有 9 个参数请求里没写就不传；再拼出 nnunet/nnunet_train 调用，置信度 0.985，全程 14 次模型调用、4.5 秒。*

### 决策模型：一次前向，给每个选项一个概率

接口定得很干净，一个 question 有四样东西：state（请求、工具名和描述、前面的步骤）、question 文本、option 列表、kind（choice 或是/否）。模型一次前向、不采样，返回每个选项的概率：

$$p = f_{\theta}\big(s,\ q,\ \{o_1, o_2, \dots, o_n\}\big), \quad \sum_{i=1}^{n} p_i = 1$$

落到实现上，不同协议的读法不一样，但都是"读一次，不吐字"。decider 家族取选项标签 token 的 log-probability，除以拟合温度再在合法标签上归一化（最多 10 个选项用 A–J，更多就用单 token 标签，最多 255 个）：

$$p_i = \frac{\exp(\ell_i / T)}{\sum_{j} \exp(\ell_j / T)}$$

pplx-decider 家族的非因果全注意力层跑 embeddings 模式，取 marker 位置的隐藏状态，乘一个 255 × hidden 的 read-out 矩阵再归一化。OpenJev、Clef 是原生 SystemOne 模型，llama.cpp 直接实现了它们的 prompt 和 read-out head，走 `/v1/systemone` 端点；OpenJev 单题最多 52 个选项，超了就分组作答、组内赢家再比，某个选项的概率等于它所在组赢家的最终概率乘它在组内的概率。

有个工程细节我很喜欢：每个答案按 SHA-256(model, kind, state, question, options) 存盘。同样的模型、硬件、llama.cpp 版本，同样的输入给出同样的分布，整条评测能靠存下来的答案精确重放，一题一题审计。论文说重放能重建全部 12,756 条记录，这个后面还会提到。

### 确定性 compiler：把 schema 编译成选择题

真正的技术含量我觉着在这一块。compiler 拿到选中工具的 JSON schema 和请求，把每个参数按 type、name、description 归成一类：枚举、布尔、数字、路径、列名、自由文本、列表、二维数组、对象。然后按类出题：

- 枚举题："参数 x 该取哪个值？"选项就是它的取值，可选参数再加一个"请求未指定（保持默认）"；
- 布尔题："请求是把选项 x 打开还是关掉？"选项是 on / off / not mentioned；
- 数字、路径、列名、自由文本走 value question，候选值加一个"not specified"；
- 列表项一次挑一个，候选互相竞争，另加"没有下一项"；
- 对象要么整体给出，要么用一道是/否题加每个键一道 value question 填。

候选值来自四个地方，这块设计得相当细：请求原文（路径、数字或词写的数字、区间、引号字符串、标识符、紧凑编码、最多三个词的短语、写好的列表和字典、标签后面的文本）；从请求派生的形式（单位换算、分数和百分比、类别数、数据集标识、染色体与等位基因记号、由写好的片段拼出的路径）；schema 里描述列出的值和文档化的列表项；还有环境和早前步骤（另一个参数指向的 CSV 表头、前面步骤的结果）。工具名和 server 名不会被当成候选。

出题之后还有一套"落定"规则。独立的题一起发出去，按固定顺序 settle：自由值按概率从高到低落，一个写好的值会去最想要它的那个参数；一个值最多填请求里写了它那么多次，用掉的值还看得见但不能再被选；两个参数抢同一个值时，模型被问"这个值属于哪个参数"，答案概率要到 0.7 才采纳。可选参数只有在请求里的值概率达到 0.7 才设，列表首项也要 0.7。等于文档默认值的不传。必需参数没值就报 missing，概率低于 0.5 报 uncertain。

### 一堆阈值拼出来的控制流

Agent 那侧的判断全靠概率阈值，论文把数都写死了：

| 环节 | 触发条件 | 动作 |
|------|---------|------|
| 工具选择 | 前两名概率差在 0.3 以内 | 追加一题：这两个工具里，哪个的参数对得上请求给出的值 |
| 能力检查 | 肯定回答 $p \lt 0.5$ | 拒绝，不调用 |
| 可选参数 / 争值归属 | 概率 $\ge 0.7$ | 才设置 / 才采纳 |
| 部署时的选择置信度 | 各步概率乘积 $\lt 0.3$ | 拒绝（**评测时没启用**） |
| 必需值缺失 | 编译器报 missing | 不填，用固定模板（参数名 + schema 描述前 120 字符）问用户 |

那个"评测时没启用"我要特意标一下，因为它挺关键：部署里还有一道基于整体置信度的拒答闸，为了公平比较，评测时关掉了，所以实验里的拒绝只来自选中"none of these"或能力检查没过。作者没有把这道有利的闸偷偷算进成绩，这点算厚道。

### 为什么"零虚构"是定理而不是发现

把上面这些串起来，结论几乎是同义反复：决策模型只能在给它的选项里挑，而每个选项都来自请求、schema、固定规则或 agent 的固定 policy。于是一次 System 1 调用里，工具必来自目录，参数名必来自 schema，参数值必来自请求或 schema——**没有任何一步有机会凭空造出一个字符串**。

想明白这层之后，我对论文里 "No System 1 call contained invented content" 这句话的态度就变了。它不是跑了实验才得到的惊喜，是架构定义直接推出的结果。真正需要实验回答的问题其实变成了两个：compiler 能不能把正确的值都摆进选项里（覆盖率），以及决策模型能不能在摆好的选项里挑对（判断力）。后面所有数据，本质都是在回答这两问。

### compiler 是怎么"炼"出来的

这段我觉得是全文最容易被跳过、但最该看的部分。作者开发 compiler 时用了一个叫 **compiler oracle** 的东西：把决策模型临时换成一个「知道标准答案」的组件，只要正确值出现在选项里它就选对。这么一换，就能把失败拆成两类——oracle 都完不成的，说明某个值压根没被任何问题提供，是 compiler 的锅；选项里有正确值但真模型没选，是模型的锅。

只修 compiler 的锅，而且只加**通用规则**（关于请求怎么写值、schema 怎么描述参数），不许给某个具体工具开后门。一条改动能不能留下，得同时满足几条提前写死的验收线：开发集上跨模型的正确调用总数要涨、不能让早前的参考请求掉出容差、要扛得住留一法（去掉任何单条改动都不能让总分更高）、还要能靠留一法证明它没多余。存下来的模型答案让反复评测变得又便宜又精确可复现，测试评测之前代码和配置还先做了哈希。

这套开发纪律，比很多论文里"我们调了调 prompt"要扎实得多。

## 🔧 放到更大的图景里：它跟 constrained decoding 差在哪

聊到这儿，做过推理部署的人大概会想到另一条路：结构化输出。OpenAI 的 strict structured outputs、Anthropic 的 strict tool use、vLLM 里的 XGrammar / Outlines、llama.cpp 的 GBNF grammar，都是把 JSON schema 编译成有限状态机或上下文无关文法，在每个生成步把非法 token 的 logit 掩码掉，让输出**结构上**不可能跑偏。这是过去两年被工业界反复打磨成熟的一条线，OpenAI 当年报告复杂 schema 遵循率从不到 40% 提到 100%（按几家工程博客的转述，属于厂商发布数据，不是这篇论文的结论）。

System 1 走的是同一条思路的极端版，但约束的对象完全不同：

| 方案 | 约束的是什么 | 能不能编造一个「合法但假」的值 | 生成文本 | 判断谁来做 |
|------|-------------|------------------------------|---------|-----------|
| 纯 prompt / JSON mode | 只保证是合法 JSON | 能，字段名类型都可能错 | 是 | 模型逐 token 写 |
| function calling（非 strict） | 大致对齐函数签名 | 能 | 是 | 模型 |
| constrained decoding / strict mode | token 层面符合 schema 的语法与类型 | **能**——一个 schema 合法的超参照样可以是编的 | 是，只是被掩码 | 模型 |
| MCP + schema 校验 | 服务端事后校验 | 调用已经发出去了，值可能已污染下游 | 是 | 模型 |
| System 1（这篇） | 具体取值的来源，限定在请求 / schema / 固定规则 | 结构上不能 | 否，一次前向打分 | 模型只挑，代码执行 |

Adroit 那篇工程复盘里有一句话跟这里对得上：constrained decoding 保证的是句法合规，**保证不了取值正确**；一个 schema-perfect 但 content-empty 的 JSON，解析得漂漂亮亮，业务上却是空的。System 1 补的正是这一层——它把"值从哪来"也一并锁死了。

但别急着把功劳全给架构。MCP 把这层可行性铺好是前提（工具目录 + 完整 schema），BFCL、ToolBeHonest 这类基准早就把「工具幻觉」当成一类独立问题在测了（它们是论文引用文献里的前置工作，不是这篇提出的）。这篇的贡献是把"约束值"这条路一次性走到底，并且配了一套能证明它真有用的评测。

## 🧪 实验：数据说话，但得会看

### 设置先摆清楚

评测集 2,126 条请求：2,003 条作者自己写的 custom prompts，123 条从已发表研究的 notebook 里原样搬来（73 条来自 ReclAIm、50 条来自 mAIstro）。其中 1,645 条是 complete 请求，一共写明 6,056 个参数值；307 条 out-of-scope（没有任何工具能满足），174 条 underspecified（缺一个必需参数，单独评估）。主基准是前两类合起来的 1,952 条。

工具侧是 157 个工具、18 个 MCP server：影像目录 42 个工具 / 11 个 server（2D、3D 分类，nnU-Net，Merlin CT 基础模型，PyCaret，PyRadiomics，TotalSegmentator 等），生物医学目录 115 个 / 7 个（proteomics 53 个、AlphaGenome 22 个、MSMCP、ClinicalTrials.gov、ChEMBL、Scanpy、TISSUE）。

对照双方：6 个 System 1 agent，用的是 4B 到 35B 的六个已发布决策模型，全部没微调；对面是 9 个开源权重 LLM，每个跑 reasoning on / off 两档，合 18 个配置。硬件统一是一台工作站、单张 NVIDIA RTX PRO 5000 Blackwell（48 GB）、32 CPU 线程、62 GB 内存、Ubuntu 24.04，全走本地 llama.cpp（build b11929），随机种子 20261102。LLM 那边的设置值得单独记一笔：请求是**唯一**一条 user message，没有专门的 system prompt，每个工具作为原生 function 挂上去，一次 completion，只评第一次调用，工具本身不执行，没给出调用就算拒答。

看这张表的时候，有几个数得停下来琢磨。

有个数我盯着看了半天：argument filling 的上限其实在 LLM 那边。Qwen3.5-27B（reasoning off）填对了 97.2% 的值，比最强 System 1 的 97.0% 还高那么一点。整篇论文的叙事是"System 1 更准"，但这个更准主要体现在**选工具**上（76 对领先 vs 5 对落后），到了填值这个环节，差距明显收窄：46 对领先、19 对落后、43 对打平，而且论文自己承认有 5 个 LLM 跟最强 System 1 没有统计上的差别。其实填值比的是"从请求里认出哪个数该给哪个参数"，这活儿语言模型本来就擅长；System 1 真正的杀招是把 157 个工具里那一个挑出来，以及该拒答时真的拒答。

还有个地方得替作者把话说准：摘要里那句 "significantly ahead of all 18 local LLM-agent settings" 别读成碾压。它说的是**最好的那个** System 1 agent（pplx-decider-27b）赢下全部 18 个配置，这个说法站得住。但 108 对配对比较的全貌是 73 对 System 1 领先、11 对 LLM 领先、24 对没差别——而且那 11 场 LLM 的胜利，全部落在两个最弱的 System 1 agent（decider-4b、decider-35b-a3b）身上。6 个 System 1 里最差的 fully correct 是 81.4%，比 LLM 那边的中位数高不了多少。所以更准确的说法是：挑对了决策模型，这套架构能稳稳压住本地 LLM；挑错了，优势就没了。

reasoning 开不开几乎没用，这点我倒没料到。开了推理让 5 个模型的 fully correct 变好，却让另外 4 个变差，没有一个模式稳定占优。这点挺反直觉，也顺手拆了"加推理 token 就能换准确率"的默认预期。

![图3：System 1 与 LLM agent 的 108 对逐对比较](https://www.mulanai.com/fs/files/1121_edd50d95_image3.jpg)

同一个基座，换上决策头、走选择题路线，大多能涨 2 到 9.6 个点；但 decider-35b-a3b 反而**输给**了让它直接当 agent 跑的基座。我看到这行的时候有点意外，也挺服气作者没把它藏起来——它恰好说明，**把生成换成选择不是无条件的免费午餐**，决策模型本身的质量是这套架构的命门，换个不合适的头，连自家基座都打不过。

还有个 lexical baseline 值得拎出来：完全不用模型、只按字面匹配，tool calling 49.3%、argument filling 20.5%、fully correct 10.9%。这个数低得很有用——它证明光有一个会把 schema 变成选项的 compiler 远远不够，判断力确实是决策模型贡献的，不是 compiler 顺手白送的。

按工具组拆开看也挺有味道（Extended Data Table 5）：System 1 在 nnU-Net 这类「一次调用带一大堆技术参数」的影像工具上领先最狠（tool calling 94.7 / 78.6 / 82.5，三类 agent 对比）；而 ClinicalTrials.gov、ChEMBL 这种标识符密集的生物医学数据库，LLM 填值反而更好（临床实验 82.9 / 95.4 / 88.2）。想想也合理——前者拼的是把一堆写好的值精确对位，正是选择题的强项；后者要处理的是 identifier 那种带领域味道的字符串，语言模型的先验更管用。

## 🔬 可靠性：这才是这篇论文真正的主场

![图4：可靠性评估](https://arxiv.org/html/2611.21053v1/media/image4.png)

*图4：面板 a 是"含至少一个编造参数值的调用占比"，六个 System 1 agent 全是 0，橙色（reasoning on）和绿色（reasoning off）的 LLM 条从约 5% 一路排到约 20%，误差线是按 200 个标记值人工复核的精确度校正后的上下界。面板 b 是 174 条欠指定请求的结果分布，绿色表示"工具选对、缺失必需值留给用户"（正确行为），紫色是没给调用，灰色是工具对但其他错，橙色是选错工具，黄色是把缺失值填上了；System 1 那几条几乎全绿，LLM 那几条大面积是紫、灰、黄。面板 c 是 307 条 out-of-scope 请求按三类拆的拒绝率：far（n=92，完全无关）大家都在 95% 以上，near（n=153，相关任务但没工具）散在 70–100%，modality（n=62，有工具能干这活但不支持指定输入）掉到 20–100% 一片散沙，是最难的一类。*

数字摆出来：10,888 次 System 1 调用，每个工具名、参数名都在目录和 schema 里；33,945 个参数值，没有一个 ungrounded。LLM 那边从没调过不存在的工具，但 9 个里有 3 个用了 schema 里没有的参数名（每个配置 19–53 次），5.5–19.7% 的调用至少带一个编造值，而且编的多半是用户根本没提过的设置——超参、文件路径、选项。开了 reasoning 也压不掉。

这里有个方法学上的诚实我得点出来：判定 grounded 的规则是「只要这个值在请求里**任何位置**以文本或数字出现过就算有据」，作者自己写了，这会**低估**幻觉。也就是说 5.5–19.7% 是一个保守下界，真实情况只会更糟。这个口径对 System 1 有利（它的值本来就都从请求里来），但作者没有把它包装成"我们测得更准"，而是明说了检测偏松，这点我买账。

欠指定请求那组对比更刺眼。174 条故意少给一个必需参数的请求，System 1 在 86.2–93.7% 的情况下做对了：选对工具、填好写明的值、把缺的那个报出来用模板问用户。LLM 的正确率最高只有 5.7%，最多在 62.1% 的请求里直接把缺失值编出来填上；连最准的那个 LLM 配置，也有 27.6% 是编的。这个差距不是一点点，是把「不知道就说不知道」这件事做成了架构保证和靠 prompt 祈祷之间的差距。System 1 偶尔也会在 2–6 个 case 里拿请求里**别处**写的值去填缺失参数——那是选错了，不是凭空编，论文特意做了区分。

out-of-scope 那边有个我认为最值得警惕的发现：拒绝率最高的两个 LLM 配置（41.4–97.4% 这个区间的上端）虽然很爱拒答，却把 24.3% 和 36.5% 的**本该正常调用**的 complete 请求也晾在那儿没给调用。会拒答不等于会判断，一刀切地"少做事"也能刷高拒绝率。System 1 拒绝 87.0–94.5%，同时只把 1.0–3.3% 的 complete 请求漏掉，两头都稳。三类 out-of-scope 里 modality 最难，System 1 / LLM on / LLM off 的正确率只有 57.3 / 51.1 / 44.4——"这个工具能干这活，但不支持你给的这种输入"，这种边界谁都容易翻车。

作者也没把话说满：System 1 仍会在 grounded 的选项里选错，10,888 次里有 22 次把一个请求里写好的值放到了 schema 要求另一种形式的位置（比如该是 identifier pattern 的地方塞了普通文本），还说"提供选项前先按参数的 schema、pattern、type 校验一遍就能消掉这类错"。这个说法我信，但没看到对应的消融验证，只能算作者的一个判断。

![图5：效率评估](https://arxiv.org/html/2611.21053v1/media/image5.png)

*图5：面板 a 是 fully correct 率对「每条 fully correct 请求的 GPU 能耗」（对数横轴），每个点都标了 agent 名字；蓝圆 System 1、橙三角 reasoning on、绿方 reasoning off。右上角是 pplx-decider-27b 和 OpenJev，右下角那条长尾是 Qwen3.8-27B、Muse Glimmer 30B 这些 reasoning-on 的 LLM（横轴一直拉到 10 Wh 以上）。面板 b 是全部 agent 的平均单请求耗时排名（对数横轴），System 1 大多落在 1–10 秒，reasoning-on 的 LLM 普遍在 5–26 秒。*

| 维度 | System 1 | LLM（reasoning on） | LLM（reasoning off） |
|------|----------|---------------------|----------------------|
| GPU 能耗 / fully correct（Wh） | 0.072–0.407 | 0.198–2.481 | 0.080–0.853 |
| 单请求耗时（s） | 1.2–10.1 | 2.6–26.1 | 1.1–9.2 |

高精度段那个对比最有说服力：OpenJev 版 System 1 做到 92.9% fully correct，2.6 秒、0.228 Wh；最好的 LLM 配置（Qwen3.5-27B, off）是 91.3%、4.5 秒、0.413 Wh。又准又快又省，还少烧近一半电。

但得给"更快更省"加个限定词。看 Extended Data Table 6 的最便宜那一档：Qwen3.5-35B-A3B 关掉推理是 1.07 秒、0.080 Wh，比最快的 System 1（decider-4b，1.17 秒、0.072 Wh）基本打平，比 OpenJev 的 2.56 秒、0.228 Wh 快得多也省得多；作者自己在 Discussion 里也承认了 "Qwen3.5-35B-A3B with reasoning used less energy than OpenJev-based System 1 agent"，在 Comparison by category 里也写了最便宜的无推理 LLM 跟最便宜的 System 1 在能耗和时间上打平。另外最强的 System 1（pplx-decider-27b）反而是全场最慢最费的之一：10.14 秒、0.407 Wh、35,057 MiB 显存。

所以准确的讲法是：跟**开推理**的 LLM 比，System 1 在能耗和时间上是碾压（最夸张的 Qwen3.8-27B reasoning on 到 26.09 秒、2.481 Wh，差出一个数量级）；跟**最便宜的关推理小模型**比，优势基本消失。原因也不神秘——System 1 一次请求要问约 12 道题，每道题都是一次独立的模型前向，题数一多，27B 的模型就慢下来了。它省的是"逐 token 生成"那部分，不是"前向次数"。

## 🤔 我的判断：这篇论文到底怎么样

**定位：工程整合，不是底层突破。** 六个决策模型全是现成的（Perplexity 的 pplx-decider、Cloudflare 的 Clef、Mapika 的 decider、OpenJev），没训新的、没微调。新东西是确定性 compiler、agent 的控制流、那套 oracle 驱动的开发方法，以及一整套评测。标题用 "a method" 很诚实。我给它的标签是"系统派的胜利"：不花哨，但真能拿来用，尤其在医疗、金融、政务这类数据不能出院、又要求每一步可审计的场景。

**最大的水分在基准本身，这点得直说。** 2,003 条 custom prompts 是作者自己设计的，而且标注规则写得很明白：只标请求里**明确写出**的值，"需要外部知识的值"和"只在 schema 示例里出现的值"一律排除。这跟 System 1 的能力边界几乎是同义反复——它的定义就是「只能用请求和 schema 里写好的值」，而基准恰好把所有需要模型自己想出值的题都拿掉了。你想想看，这场擂台是按 System 1 的形状搭的。作者显然意识到了这个风险，补了 123 条从 ReclAIm、mAIstro 原样搬来的已发表请求，结果 System 1 也不差（tool calling 100.0 / 98.9，LLM 那边 96.4 / 93.3 / 97.1 / 98.8），这个补救我认。但 123 条对 2,003 条，而且全落在影像目录，说服力还是有限。真要让我完全信服，得看它在**别人建的、允许开放式取值**的基准上跑一遍。

**LLM baseline 的设置也让我有点皱眉。** 请求是唯一一条 message、没有专门 system prompt、没有 few-shot、没有 ReAct 式的多轮自我修正、只评第一次调用、工具不执行。作者说 LLM agent "ran as distributed"（按发布方给的方式跑），可"不给 system prompt"是一个明确的选择，不是环境限制。给几个工具调用示例、加一轮"检查一下参数是不是都在请求里"的自检，LLM 的编造率大概率会往下掉一截——未必掉到 0，但 5.5–19.7% 这个对照数字未必稳。公平地说，System 1 那边同样没微调，两边都是"原样上场"；只是这两边"原样"的自由度不一样，System 1 的 compiler 是精心开发过的，LLM 那侧却没给任何 prompt 层面的调优空间。

**泛化天花板得摆到台面上。** 整套设计押在一个前提上：正确调用需要的值，都能从请求或 schema 里枚举出来。一旦任务变成"帮我挑个合适的学习率""用默认推荐配置跑一遍""按上次的设置继续"，值不在请求里，System 1 就只能问人，或者走那条写死的 policy（论文里 output folder 就是这么处理的）。它把"智能"压缩成了**路由 + 对齐**，把需要生成的那部分全推回给用户。在临床场景这是优点——不越权、可审计、不擅自替医生做决定；但当作通用 agent 的蓝图，天花板一眼能看见。再加上 157 个工具全是有干净 JSON schema 的 MCP 服务，现实里大量工具压根没这待遇，compiler 的候选生成规则能不能扛住五花八门的脏 schema，论文没给答案。

还有一个我没完全看懂的地方：compiler 那套候选规则是作者按通用现象手工归纳的（单位换算、词写数字、染色体记号、CSV 表头……），它对新工具、新 schema 的覆盖率能做到多少，正文没有单独量化。oracle 能测出开发集上"哪些值没被任何问题提供"，但那是在这套规则已经调过之后测的。这块如果我的理解有偏差，欢迎指正。

以及那个被我反复念叨的点：**零虚构是架构的定义，不是实验的成绩**。论文把 10,888 次调用零编造成当作核心结论之一，逻辑上没毛病（它确实验证了实现没漏），但读者别把它误读成"作者找到了抑制幻觉的新算法"。真正的算法贡献是 compiler 的候选覆盖率和决策模型的判断力，这两样才是数据里那 97.0% 的来源。

## 💡 工程上能带走什么

如果你手上正好有个跑在本地、要碰敏感数据的 agent，我觉得可以直接动手试的，按性价比排：

1. **先做 grounding 校验**，成本最低、收益最快。调用发出去之前，逐值检查它能不能在请求原文或 schema 里找到出处，找不到就拦下来问人。这一步就能砍掉大部分"格式合法但值凭空来"的静默污染，不改模型、不改架构。
2. **再上 schema 级的约束**（strict function calling / constrained decoding），把字段名和类型锁住。但记住前面那张表：它管语法，不管取值对不对。
3. **再考虑把生成整个换成选择题**。这一步最重，要写 compiler、要挑决策模型、要设计阈值，收益是零虚构 + 可重放审计，代价是放弃所有"模型替你想一个值"的能力。

阈值那套（0.3 / 0.5 / 0.7）别照抄，它是作者在自家开发集上调出来的，换个领域大概率要重标。真正值得抄的是**开发方法**：用 oracle 把"compiler 没把值摆出来"和"模型没选对"分开，只修前者、只加通用规则、每条改动都设好验收线再上。这套纪律比任何一组超参都值钱。

至于什么时候别用它——任务里需要模型自己拿主意、值不写在请求里、工具 schema 残缺、或者你在做一个开放域的探索型 agent，这套架构会把你锁死。它是给"不许擅自发挥"的场景准备的，不是给"需要发挥"的场景准备的。

回到开头那个阴间的 bug。这篇论文给的其实不是更聪明的模型，而是一条很朴素的规矩：模型可以判断，但不许编；凡是它没从你这儿听到的值，一个字都不许写进调用。规矩立住了，那类悄无声息污染整条流水线的错误，就没有出生的缝隙了。

想通这层之后，我倒觉得标题里那个 "System 1" 取得挺妙——它借的是"快而直觉"，交付的却是"被关在笼子里的直觉"。
