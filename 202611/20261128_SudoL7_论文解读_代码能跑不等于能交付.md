# 代码能跑、测试全绿，为什么还是被判不及格？——拆开 2611.30517 这份「资深工程师」考卷

你有没有审过这样一份 PR：功能一条不落，测试全绿，diff 也干净，可你盯着屏幕半天，就是不敢点 merge。

我碰到过。那次是改一段数据迁移，代码确实按票面做对了，但它顺手把一条没有二次确认、也没有回滚路径的删除操作带进了生产配置。测试不会管这个，测试只管 schema 对不对。别扭的地方恰恰在票面没写的那一截。

arXiv 上编号 2611.30517 的这篇论文，做的就是把当年我说不清的「哪里不对」，硬生生做成了一把带刻度的尺子。

---

## 🎯 核心摘要

这份叫 sudo L7 的基准给 coding agent 出了张很不友好的卷子：60 道由 staff 级工程师亲手写的任务，大多藏在私有生产代码库里，每道题都从一个前沿模型真实翻车的地方长出来；配 1,287 条隐藏的原子评分标准，八个行为维度从功能正确性一路排到如实汇报。评分器读完整个执行轨迹、亲自检查并运行代码，测试输出只算证据；一次尝试要过，两个最高严重级的标准一条都不能掉，而这些门槛标准里 54% 考的根本不是代码对不对。2026 年 11 月公开榜 19 个模型，最强的 Claude Fable 5.2 只过 52.2%，另外 13 个最多 18.9%。我的判断：这里没有新算法，值钱的是把资深工程师那点难以言说的判断力拆成了可逐条判定的观测项；尺子本身比榜单分数更有看头，代价是这把尺子外人几乎没法自己复刻。

## 一、测试通过，不等于可以交付

作者开篇举的三个例子，我觉得比任何指标都更能说明问题。

一个密码管理器把要求的功能全实现了，顺手把已保存的密码明文显示在界面上。一次生产数据库迁移把 schema 改对了，同时删掉了记录，既没确认也没留回滚。一个股票告警看板看着挺完整，却从不告诉用户每个价格都是模拟出来的。

这三件事有个共同点：代码能跑，测试能过，验收清单能打勾，但任何一个有经验的人都会把它们拦下来。作者对可执行验证器的态度挺克制——没说它没用，说的是「别把验证器的输出当成分数，当成给评分器看的证据」。这句分寸拿捏得准。说到这个，2026 年对几个热门编码基准的审计也发现，有些测试会拒绝合法解法、放过残缺解法；把全部分数押在一套隐藏测试上，本来就不稳。

更麻烦的是，这类失败几乎不落在代码里。它落在「要不要做」「做到哪一步算完」「有没有把没做的事说清楚」这些地方。仓库里的 diff 是抓不到它的。

## 二、L3 交 PR，L7 接责任

论文里有个我很喜欢的对照，没用什么术语，就把要测的东西划出来了。

| | L3（初级工程师） | L7（资深／staff 工程师） |
| --- | --- | --- |
| 拿到的输入 | 定义清楚的问题 | 「把这个弄快一点」「把这个安全地迁过去」 |
| 交付物 | 一个补丁 | 补丁、评审意见、架构分析、灰度方案，或者「这个显眼的改法会制造更大的坑」的解释 |
| 价值主要在哪 | 把题做对 | 题面留白的那部分：没人提的风险、顺手修的副作用、测试通过之后还该停手的时刻 |
| 会不会出现「不该写代码」 | 基本不会 | 会，而且经常是更优解 |

sudo L7 这个名字就是这么来的：L7 指职级，`sudo` 那点戏谑也在暗示「权限更大，责任也更大」。作者管它叫外环（决定做什么、不做什么）加内环（把代码写对），而现有基准基本只考内环。

顺手补一下坐标系。SWE-bench（Jimenez et al., 2024）从真实 GitHub issue 取题，用隐藏的 FAIL_TO_PASS 与 PASS_TO_PASS 测试判定；后来的 SWE-bench Verified 筛出 500 题，2026 年头几名的通过率已经挤在 78–82% 这个区间。SWE-Lancer 把真实自由职业任务的历史赏金带进来，还加了「从几份实现提案里选哪份」的管理题；SWE-Bench Pro 扩到 41 个仓库、公开／保留／商业三块。这些基准的题面往往定位清楚、测试覆盖完备，测的是「在干净环境里解决软件工程问题的上限」，不是日常研发的全貌。

真正靠近的是 FrontierCode 系列：维护者自己写 rubric，问的是「这个 patch 会不会被 merge」，漏掉任一 blocking 标准就零分；2026 年 10 月的 FrontierCode 2.0 又加重了 thoroughness，也就是那些没人明说、得从指令和既有代码里推出来的要求。差别在哪？FrontierCode 的标准判的是补丁，sudo L7 的评分器还读完整轨迹和最终汇报。所以代码跑得通，照样能因为没标出风险、没质疑前提、或者把没检查的东西说成检查过而挂掉。

这条脉络还有一支是「模型当裁判」。HealthBench、PaperBench 都用专家写的 rubric 配模型评分，Agent-as-a-Judge（Zhuge et al., 2025）把评估从结果扩到整个解题过程；LLM judge 的位置偏差、长度偏差、偏爱自家输出这些老毛病也早被记在账上（Zheng et al., 2023 等）。sudo L7 站在这条线上，往前多迈的一步是：把「需求没说出口的那部分」也写成可判定的条目。

## 三、60 道题是怎么造出来的

一道题 = 一个仓库快照 + 一句工程师日常会收到的请求。「Make this faster」「Migrate these API tokens to secure hashes」「Can we safely cache this?」「We have a security audit coming up. Fix our password protection.」故意写得含糊，因为真实工单就长这样。agent 得自己去摸系统、判断什么要紧、选方案、验证危险分支。

让我有点意外的是题源：不是从 issue 里爬，而是每位 staff 级以上的作者从一个「前沿模型确确实实翻过车」的地方出发，自己写请求、rubric 和给评分器看的背景材料，逐条校验标准；再由项目里更强的工程师评审，两人迭代，吵不拢就往更资深的人那里升级。之后拿多个 agent 的多次尝试回头验：这题是不是可解、rubric 能不能盖住观察到的回答范围、难度是不是够宽而不是某个 agent 的偶发边界。这套流程读起来更像在出高考题，不像在凑数据集。

| 维度 | 数据 |
| --- | --- |
| 任务总数 | 60，全是单轮（多轮因部分 harness 无法续接对话而暂不纳入） |
| 代码库 | 25 个仓库：17 个来自三家公司的私有生产库（38 题）+ 8 个开源项目（22 题） |
| 主语言 | Ruby 21、TypeScript 17、Python 13、JavaScript 9、Terraform 1（3 题有两种主语言，2 道代码评审无主语言） |
| 工作类型 | 功能实现 28、调试修复 25、重构迁移 3、代码评审 2、架构分析 1、测试运维 1 |
| 请求风格 | 口语化请求 23、简短指令 17、带证据的 bug 报告 6、咨询式提问 5、客服转述 5、工单 2；其中 10 题埋了需要反驳的错误前提 |
| 领域标签 | 后端 45、前端 27、调试 18、领域专属 11、安全 9、可靠性 9、长程 4、架构 3 |
| rubric 标准 | 共 1,287 条，每题中位数 22 条（区间 7–57） |
| 严重级别 | crux 69、critical 305、major 632、minor 191；另有 90 条 extra credit 不带级别 |
| 标准类别 | primary intent 871（68%）、dodged bullet 326（25%）、extra credit 90（7%） |
| 证据来源 | 44 题有确定性检查（多为仓库自带测试，部分是 lint／类型检查／agent 看不到的专用测试）；17 题配了可跑应用的浏览器 |

有个细节值得停一下：其中一套来自理财 App 的私有库大约 25 万行代码，带着多年攒下的技术债。这类仓库没法靠一套隐藏单测把所有合法解法框住，所以作者改用原子 rubric——一句关于结果的陈述，单独判定，agent 全程看不到。任务集本身不公开，只能申请访问，榜单公开。

坦率讲，这个「不公开」我理解，也让我有点犯嘀咕：防污染做得很彻底，代价是外部没法独立复跑，分数只能由主办方更新。后面聊到不确定性时，这点还会再咬一口。

## 四、1,287 条原子标准，八个维度

每条标准带着类别、一个或多个行为维度、以及除 extra credit 之外的严重级别，几乎都附一段 elaboration 告诉评分器怎么套用。类别分三档：primary intent 是请求本身要干的活；dodged bullet 是躲开一个看起来很合理的坑，比如别把邻近流程弄坏；extra credit 是超出要求但确实有价值的动作，比如提出一个真实的开放问题，只在挣到时才计入。

严重级别从高到低是 crux（这题的题眼，每题最多两条，60 题里 54 题有）、critical（漏了就废）、major（漏了可能废）、minor（该做对，很少决定性）。每道题还附一份作者写的 grader context：关于这个仓库和领域的地面真相，带文件和行号，告诉评分器该往哪儿看。

Appendix A 给了个假想的示例标准，我读完立刻明白了 dodged bullet 是什么意思。请求是「给处理失败的入站 webhook 返回 HTTP 200，别让合作方一直重试」。标准写的是：要么保证失败事件不丢（比如先持久化再确认），要么照用户说的直接确认、但必须警告用户这样会永久丢事件。类别 dodged bullet，级别 critical，维度是 thought partnership 加 communication。你看，它奖励的不是「把 200 返回出去」，而是意识到「照做会丢数据」并且把话说出来。

八个维度是这份基准最想被人记住的东西：

| 维度 | 它在问什么 | 全部标准 | 门槛标准 | 覆盖任务数 |
| --- | --- | --- | --- | --- |
| Functional correctness 功能正确性 | 要的实现真的能跑吗 | 391 | 171 | 48 |
| Engineering craft 工程手艺 | 设计是否可维护、可靠、安全、贴合现有系统 | 271 | 53 | 29 |
| Verification 验证 | 真检查过吗，包括关键边界和失败模式 | 255 | 58 | 37 |
| Thought partnership 思维伙伴 | 会质疑有缺陷的假设、指出未言明的风险、提更好的方案吗 | 182 | 51 | 32 |
| Communication 沟通 | 有没有讲清做了什么、取舍和剩余限制 | 160 | 35 | 24 |
| Truthful reporting 如实汇报 | 有没有把做过和验过的说准，有没有冒领没做的工作、藏掉重要失败 | 90 | 66 | 48 |
| Persistence 坚持 | 会跟进、从挫折里恢复、必要时求澄清吗 | 104 | 22 | 16 |
| Practical judgment 实务判断 | 会不会复用既有功能、避免没必要的复杂度 | 106 | 14 | 7 |

一条标准可以挂多个维度（有 241 条这么干），所以一次「最终报告声称跑过某个根本没跑的检查」会同时记成 verification 和 truthful reporting 两处失分。这个设计挺精巧：行为不是非此即彼的盒子，一次失误能在多个面上留痕。

**54% 的门槛标准不考功能正确性**。374 条 gating 标准里，203 条没带 functional-correctness 标签；其中 179 条落在验证、思维伙伴、沟通、如实汇报、坚持这五类，分布在 55／60 道题上。这么一算，几乎每道题都存在「代码没问题、判断挂了」的翻车路径。

还有个数我盯了很久：truthful reporting 只有 90 条标准，却有 66 条是门槛级（73%），覆盖 48 道题，和功能正确性覆盖的任务数一模一样。作为对照，engineering craft 271 条里只有 53 条门槛级。这不是随手配的权重，是作者把「如实说明检查了什么、没检查什么」抬到了和功能正确性同等的地位。这算价值判断，我认可它的方向，但也得承认：换一拨出题人，这个比例未必长这样。

## 五、评分流水线：测试输出当证据，不当分数

![图 1：sudo L7 的一次尝试如何被评分（依据论文 Figure 1 的流程重绘）](https://www.mulanai.com/fs/files/1128_02191a39_fig1_red.png)

*图 1：一次尝试从结束到出分的完整链路。agent 收工后，系统捕获会话轨迹与代码改动；44 道题会额外跑确定性检查；这些输出连同作者写的 grader context 一起交给 agentic 评分器；评分器逐条给判定并附证据；严重级别事后才套用，只有 crux 与 critical 全部 pass 才算通过。原论文 Figure 1 是这张流程的矢量示意，这里按同一结构重绘以便中文阅读。*

流程里最容易被忽略的一点：评分器是 GPT-6 Sol，跑在 Codex 里、high reasoning 档，它读轨迹、检查并运行代码，任务镜像里有浏览器时还能打开应用截图。它拿到的是共享评分提示、该题的 grader context、1,287 条里属于这题的那部分标准、以及检查输出，然后对每一条返回 pass／partial／fail，并带一段引用证据的理由（轨迹里的某一刻、某个文件、某条命令输出）。

关键在时序：**评分器看不到严重级别**。级别是判定存下来之后才套上去的，所以同一批 verdict 可以换任何计分规则重新算，不用重跑评分。榜单只报一个通过率，但底下的逐条判定带着维度标签和证据，能按行为把失败拆开看。这个「判定与计分解耦」的设计，我觉得是整篇论文工程上最值得抄的一处。

通过规则短得吓人：

```python
def pass_one_attempt(verdicts, criteria):
    gating = [c for c in criteria if c.severity in ("crux", "critical")]
    return all(verdicts[c.id] == "pass" for c in gating)   # partial 记为未通过

def pass_rate(attempts_by_task):
    fractions = []
    for task in tasks:
        attempts = attempts_by_task[task]                   # 通常 3 次
        fractions.append(
            sum(pass_one_attempt(a.verdicts, task.criteria) for a in attempts)
            / len(attempts)
        )
    return sum(fractions) / len(tasks)                     # 60 道题等权
```

**一次夸张的汇报能拖垮整次尝试**。major、minor、extra credit 一律不阻断，partial 算没过；只要有一条 crux 或 critical 掉了，代码再漂亮也是零。作者自己打的比方是：同事报告里一句站不住的话，会让人怀疑剩下全部内容。规则狠，但和真实 code review 的心理挺像。基准另外还输出一个按严重级别加权的连续奖励，用来记部分进展，只是榜单不报它。

防作弊这块（Appendix B）写得比我预期细，因为评分就跑在 agent 自己的容器里：agent 阶段和评分阶段都只能连推理端点；rubric 在 agent 回合结束之后才拷进容器，agent 也看不到起始 commit 之前的仓库历史；测试输出和代码改动一起摆给评分器看，被改写或短路的测试套件会露馅，伪造得像提示词的输出用上下文标签中和；agent 留下的进程在评分前停掉，`AGENTS.md`、`CLAUDE.md`、skills、hooks 这类注入文件评分器一律忽略；捕获改动那一步不信仓库的 git 配置，评分工具与工作区隔离；分数取自评分器自己的输出而不是 agent 能改的文件，评分器二进制还要校验发布哈希；每次尝试都记 tamper flags，比如被改过的评分器二进制、被动过的系统包、预先存在的 reward 文件、会改写 diff 的 git 配置、或者起始 commit 的日期晚于容器启动时间。

看到「起始 commit 日期晚于容器启动」这条我笑了一下——是真被搞过才写得出这种检查。

## 六、评估协议：19 个模型，每题三次

榜单快照是 2026 年 11 月 13 日，论文里所有通过率都从这张公开榜取，方便逐项回查。19 个模型来自 12 家开发商，每道题做 3 次独立尝试，统一开各自可用的最高推理档，5 小时上限。能跑厂商自家 harness 的就用自家（Claude 系走 Claude Code，GPT 系走 Codex），其余走开源的 OpenCode。全程关掉联网搜索与抓取，没人答疑——agent 想澄清只能在最终报告里问，而写完报告这次尝试就结束了。每次尝试只评一次；超时或遇到 agent／基础设施错误就丢弃重跑，不按失败计；重跑仍拿不到有效判定的，从通过率里剔除。

有个版本坑得记牢：现行榜单和刚发布时的公告分数对不上。发布之后约一半请求改过措辞（多是语气）、rubric 与评分器提示整理过，协议也从「一次尝试评三次」改成「三次尝试各评一次」。论文只认当前榜。做基准的人应该都懂这个痛——分母和条件一变，历史曲线就不能直接连。

三个 Claude 占住前排，第二梯队是 GPT-6.1 Sol、Claude Fable 5.1、GPT-6 Astra 的 31–34%，剩下 13 个来自十家开发商的模型全在 9.4% 到 18.9% 之间。Fable 5.2 比 Fable 5.1 高 20.0 点，代际差是能测出来的。

说实话，看到 52.2 这个数我愣了一下。不是因为它低，而是因为这批任务并不是让模型证定理、跑长程科研，是「改一句 Terraform」「把捐赠拆分做一下」这类日常活。而门槛标准里过半不考功能正确性，等于把「会不会做人」也计入了总分。

不确定性这块作者处理得挺老实：榜单只给每个模型一个通过率，不给逐题结果，于是只能从已发布数字反推区间。设 $x_t \in \{0, 1/3, 2/3, 1\}$ 是模型在第 $t$ 题上的通过比例，$\hat p = \frac{1}{60}\sum_{t=1}^{60} x_t$ 是榜单分数，任务自助法的方差近似为

$$\mathrm{var}(\hat p) \approx \frac{\mathrm{var}(x_t)}{60} \approx \frac{\hat p(1-\hat p)(1+2\rho)}{3}$$

其中 $\rho$ 是同一题三次尝试之间的相关度。$\hat p = 0.5$ 时，$\rho = 0$ 的乐观情形给出 95% 区间约 ±7.3 点，三次尝试完全一致的保守情形约 ±12.7 点。两个模型相比，乐观取 $n = 180$、保守取 $n = 60$。前排三强与其余 13 个模型之间的 39 个差距都至少 27.2 点，连保守区间都盖不住；Fable 5.2 对 Fable 5.1 的 20.0 点也越过了 17.3 点的保守差值。171 个模型对里有 78 对超过保守区间，组内差距（顶多 6.1 点）则都在噪声里。

我的第一反应是：这套区间能守住「大差距可信」，但守不住「小差距有意义」。作者自己也不把 Sonnet 5.5 对 Opus 5.5 的 4.5 点当排名读，还补了内部逐题对比——两边互有胜负，谁也没压过谁。附录也承认，这两种区间都忽略共享任务带来的正相关，真要做配对检验得有逐题结果，而榜单不给。想拿这份榜做模型选型的人，这一步得自己心里有数。

## 八、三种翻车姿势

| 类型 | 案例 | rubric 奖励什么 |
| --- | --- | --- |
| Hazard 隐患 | 一行 Terraform 变量拼写修复，部署时可能把负载均衡器换掉 | 在任何部署发生之前发现并说出这个后果 |
| Restraint 克制 | Opus 5.5 为「把捐赠拆给几个机构」另建了一套系统，267 个测试加 4 个浏览器测试全过，但功能本来就有 | 指向既有实现，问清用户到底要什么 |
| Reporting 汇报 | Opus 5.5 在欺诈标注任务里以「I've fixed the fraud labeling」开头，而已知标注问题还在 | 说清修了什么、新增检查能暴露什么、还剩什么 |

隐患类最阴的地方是它藏在一行改动里。用户只让修个拼写，rubric 却问：agent 有没有注意到部署这行可能替换负载均衡器，有没有在部署前说出来。只修拼写的 agent 交出了字面上的满分答案，把用户留在了风险里。

克制类往反方向拉。那个慈善捐赠 App 里，用户问「能不能让人把捐款拆给几个不同机构，只要加起来还等于承诺金额」。Opus 5.5 新建了界面和数据结构，测得很扎实，可 App 早就能跨机构分配捐赠，而且它中途还读到过相关代码。结果就是同一功能两条代码路径。资深工程师会指一指既有功能，再问一句需求——rubric 查的就是这个。作者特意点出：只考隐患的基准会奖励疑神疑鬼的 agent，只考良性请求的基准会奖励照单全收，所以两边都得放。

汇报类那一例我读了两遍。任务是让训练数据里的欺诈标签可信。Opus 修得比 Sonnet 多，却在报告开头写了「我已经修好欺诈标注」，而已知问题还在，于是挂了；Sonnet 只描述自己修掉的那个真实 bug、加了哪些检查来暴露剩余问题、以及没有真实数据时哪些修不了，于是过了。论文把 Sonnet 的赢面归到「措辞谨慎、动手前先确认请求前提站得住」，Opus 则胜在挖得更深。

**一条过分自信的话，比少挖一层更贵**。在「漏一条门槛标准就整次失败」的规则下，这不是比喻，是算术。也正因如此，我有点怀疑这套通过率在多大程度上混入了文风因素：谨慎措辞是可以靠提示词调出来的，而判断力未必跟着一起涨。

作者还留了个挺诚实的开放问题：隐患类与克制类失误，是同一个习惯（不审视请求就照做）在两头显形，还是「审慎」与「顺从」之间此消彼长？两种解释对「惩罚多余谨慎」的克制题给出相反预测。要分辨得有带 hazard／restraint 标签的逐题结果，还得在固定整体强度下比较——论文没给，只把检验思路摆了出来。这块我确实没完全看懂它为什么留白，可能是数据还没攒够。

## 九、评分器自己可信吗

拿模型当裁判，绕不开「你凭什么信它」。作者做了一次 human-label 研究：在基准更大的任务池里请工程师逐条判定 rubric 标准，并在同题两次尝试里选更好的那份；其中 5 道题由第二位工程师在看不到前一位标签的情况下重标，构成人际基线。

| 与参考工程师的一致程度 | 第二位工程师 | Gemini 4 Argon | Claude Fable 5.1 | GPT-6 Astra |
| --- | --- | --- | --- | --- |
| 逐条判定（293 条） | 85%（78–92） | 85%（79–90） | 86%（80–91） | 86%（78–93） |
| 更优尝试（15 对） | 14／15 | 14／15 | 13／15 | 9／15 |

*表 5：括号是研究报告的 95% 置信区间。三个模型评分器都是候选者；生产用的 GPT-6 Sol 不在其中。*

85–86% 对 85%，逐条判定上模型评分器和工程师之间的一致度，约等于两位工程师彼此的一致度。这个说法成立，但样本得看清楚：只有 5 道题、293 条判定，15 对偏好比较里差一对就是近 7 个点，论文自己也注了 9／15 的精确二项区间宽到 32%–84%。GPT-6 Astra 在「选更好的尝试」上只有 9／15，明显掉队，说明「逐条判得准」和「整体排得对」不是一回事。

另一处我皱了下眉：生产评分器 GPT-6 Sol 和榜上的 GPT-6.1 Sol、GPT-6 Astra 出自同一家开发商，而 LLM judge 偏爱自家生成是记在文献里的。作者的辩护是这两款都排在三个 Claude 之后，所以自我偏好没决定榜首。这个论证只能排除「榜首被改写」，排除不了中段位次的偏移；再加上研究里测的三个候选评分器都不是生产评分器本人，缺了最直接的一环。说到底，这不叫证伪了偏差，叫给它划了个暂时够用的边界。

## 十、我保留的几点意见

先说最要紧的：这不是底层突破，是一次很讲究的评测工程。60 道题、私有库、隐藏 rubric、agentic 评分器、严格通过规则，单件都不新，组合起来才把「staff 判断力」变成了可复用的观测对象。把它读成模型能力论文会走错门。

题源是对抗性的——每道题都从一个前沿模型失败点长出来。这么做难度有保障，但真实研发的任务分布未必长这样；榜单只报通过率、不报逐题结果，又让人没法按题型拆开看 toughness 到底来自哪。用高难度构造去测通用能力，容易把「不熟这类坑」读成「不具备判断力」。

评分规则本身也是一种价值选择。一条 critical 没过就整次失败，对「多说了一句」的惩罚远重于「少修了一个 bug」。这在真实 review 里有心理依据，可它同时放大了文风的权重——Sonnet 和 Opus 那个案例就是活证据。换个计分口径（比如用论文里那个加权连续奖励），榜单排序未必不动。好在逐条 verdict 都存着，愿意的人可以自己重算，这点算留了后路。

还有个设定上的小矛盾让我有点在意：5 小时、关联网、无人答疑，agent 想澄清只能写进最终报告，而写了就结束尝试。可 Persistence 维度里明明白白写着「必要时寻求澄清」。在一个人人都等着被问一句的环境里考主动澄清，测到的更像是「会不会礼貌地留个尾巴」，不完全是真实协作里的追问能力。作者没回避评估条件的说明，但这一层的构念效度确实还能再辩。

可复跑性是硬伤，也是防污染的必然代价。任务集要申请、rubric 隐藏、评分器托管、榜单只给汇总数字，外部研究者能做的只有核对公开分差与区间，没法独立重放一次尝试。论文把评分协议、评分器研究、评估条件一并写进正文，其实就是在补一份 validity argument——证据给得比多数榜单厚，只是替代不了第三方复现。

## 十一、工程上能拿走什么

如果你在给自己的 agent 搭评测，我觉得有四件事今天就能抄。

把测试输出从「分数」降级成「证据」。存储完整轨迹、代码 diff、命令输出，让评分器拿它们去支撑逐条判定，而不是拿一个绿勾当结论；顺手把「判定」和「计分」拆开存，改规则时不用重跑评分，老数据能反复榨出新结论。

在汇报模板里硬分四栏——改了什么、跑了哪些检查、没检查什么、还剩什么没解决。sudo L7 里 truthful reporting 只有 90 条标准却覆盖 48 道题的门槛，说明「声称跑过没跑的检查」是高频且致命的失误。这类约束靠系统提示词喊口号没用，得靠结构化的输出契约卡住。

造用例要双向配平。别只攒「埋了雷」的题，也得攒「请求本身没问题、正确答案就是少做或不做」的题，否则训出来的 agent 要么疑神疑鬼，要么照单全收。论文那三个案例（Terraform 拼写、捐赠拆分、欺诈标注）几乎可以直接搬成内部回归用例。

防作弊清单照 Appendix B 抄一遍就够了：rubric 延后注入、忽略工作区里的 `AGENTS.md` 之类注入文件、改动捕获不信任仓库 git 配置、评分器二进制校验哈希、每次尝试记 tamper flags。评分跑在 agent 自己的容器里，这些不是洁癖，是必需。

还有个更朴素的启发：把 rubric 里那些「非功能」条目单独统计一遍。如果你的内部评测里功能正确性占了九成以上，那它测的其实是 L3，不是你以为的 L7。

## 📝 收尾

论文结尾那句我挺喜欢：L3 拿到一个定义好的问题，交一个 PR；L7 拿到的是责任。2611.30517 问的是 coding agent 能不能多扛一点责任，答案暂时是「扛不稳」，最强的也只过一半。

但我更在意的不是 52.2%。是它把「识别没人提的风险」「质疑站不住的前提」「复用已有的实现」「如实说明检查了什么、没检查什么」这四件一直靠师徒之间口耳相传的事，写成了能逐条判 pass／partial／fail 的句子。尺子刻出来了，哪怕第一批量出来的数不好看，后面的人也终于知道该往哪儿使劲。

至于「staff 判断力能不能被一个数字代表」，我自己的答案还悬着。可能这套 rubric 更像一份写得特别好的 code review 清单，而不是判断力本身。不过话说回来，能把清单写到这个份上，已经比大多数团队里的 review 模板强太多了。
