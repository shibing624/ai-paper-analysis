# 33.7B token 教会模型“用 Lean 干活”：daVinci-Prover 把 Agent 轨迹前移到了 mid-training

让模型写一段数学证明，它可能讲得头头是道；把同一段证明丢进 Lean，页面却很快被 `unknown constant`、`type mismatch` 和 `no goals` 染红。更折磨人的是，模型看着报错，常常只会把整份答案重写一遍，再撞上另一堵墙。

daVinci-Prover 盯上的正是这条裂缝：**训练时看的是整理完毕的定理与证明，部署时却要做检索、编辑、验证、读报错和返修**。这就像只让学员看标准工程代码，期末却要求他独立调试一个真实仓库。我的第一反应是，这个痛点不新鲜；有意思的是，作者没有继续往推理脚本上叠模块，而是把交互经验大规模塞进了 mid-training。

## 核心摘要

daVinci-Prover 用 **33.7B token** 构造 Agent 原生的中训练语料，把证明分解、子目标搜索、自我验证、错误修复，以及真实工具调用和 Lean 反馈放进同一套数据配方；随后再用约 **36K 条**经严格验证的智能体轨迹做 SFT。在 Qwen3-8B 的匹配对照中，MiniF2F、FATE-M、ProofNet 平均提高 **13.7 个点**。我觉得它最值钱的不是又刷新一张榜单，而是用消融证明：会推理和会在环境里把推理落地，是两种需要分别训练、又能互补的能力。不过，部分横向比较混用了 pass@8 与外部结果的 pass@32，训练和评测又共用 harness，这些边界不能略过。

## 不是再写一个证明器，而是提前训练“工作方式”

形式化定理证明的诱人之处，在于答案不靠评委感觉。Lean 会把定义、命题和证明变成可检查的计算对象，通过严格验证才算成功。但模型得到这种严格性，也付出了交互上的代价： Mathlib 里该用哪个声明、当前目标是什么、某个 tactic 为什么失败，都不是一次性生成容易解决的事。

已有路线大致分成三类：

| 路线 | 模型怎样工作 | 长处 | 卡住的地方 |
|---|---|---|---|
| 整证明生成与修复 | 一次生成完整 Lean 证明，可结合编译反馈重写 | 推理流程简单，调用便宜 | 长证明里局部错误容易拖垮整体 |
| 单智能体证明 | 在环境中检索、编辑、验证并迭代 | 能根据状态调整策略 | 长程交互能力要求高，工具开销更大 |
| 编排式系统 | 把分解、草图、验证、返修分给多个组件 | 能组织复杂流程和并行搜索 | 系统复杂，底层证明器仍是能力上限 |

Goedel-Prover-V2 已把编译器反馈用于自我修正，OProver 也把检索、失败尝试和多轮修复纳入训练。因此，daVinci-Prover 的卖点不能笼统写成“让模型利用反馈”。它真正往前推的一步是：**不只把这些行为留在后训练或推理脚本里，而是在 mid-training 就同时教授数学技能先验与环境原生交互**。

![图1：daVinci-Prover 的中训练数据设计与跨模型结果](https://arxiv.org/html/2611.16433v1/figures/midtrain_data_and_benchmarks_davinci_palette_no_outer_frames.png)

*图1把全文压缩在了一张图里。左侧四类技能先验是分解与组装、子目标搜索、错误定位与修复、自我验证，中间是“推理—工具调用—反馈”的循环；右侧显示同一配方在 Qwen3-8B 和 Qwen3.5-9B 上都带来增益。Qwen3-8B 相对 Base + SFT 在三项基准分别增加 11.9、17.3、12.0 个点，平均正好约 13.7 个点。*

这条思路跟软件工程 Agent 的中训练趋势很像：与其指望模型在 SFT 的几千条样本里突然学会整套工作流，不如更早让它见过大量真实操作。论文也明确把 DaVinci-Dev、Kimi-Dev 作为相邻背景。说回到定理证明，Lean 的严格反馈让这种做法格外有吸引力，因为候选步骤是否被接受，不需要再训练一个爱打偏分的奖励模型来判断。

## 33.7B token 里到底装了什么

这套语料不是把 Lean 文件堆到 33.7B 就结束。作者把数据分成技能先验和 Agent 轨迹两块，再做父轨迹级 replay。原始数据源包括 NuminaMath-LEAN、AoPS、Lean Workbook、Goedel-LM/SFT_dataset_v2 和 OProofs，token 数按 Qwen3.5 tokenizer 统计。

| 数据类别 | 样本数（百万） | token 数（十亿） | 占比 |
|---|---:|---:|---:|
| Self-verification | 0.083 | 5.70 | 16.9% |
| Theorem Decomposition | 4.662 | 8.43 | 25.0% |
| Proof Revision | 1.027 | 3.84 | 11.4% |
| Proof Search | 1.962 | 3.45 | 10.2% |
| Environment-Aware Agent Trajectories | 0.397 | 7.17 | 21.3% |
| Pre-Replay 合计 | 8.131 | 28.60 | 84.8% |
| Replay 数据 | 1.454 | 5.11 | 15.2% |
| **最终合计** | **9.585** | **33.70** | **100.0 个百分点** |

*表：论文 Table 1。环境感知 Agent 轨迹在 pre-replay 部分是 7.17B token；后文消融中的完整 Agent 数据子集为 8.4B token，两个数字对应不同统计阶段。*

### 四类技能先验，分别补四种短板

**分解与组装**解决“知道证明方向，却组织不出可维护结构”的问题。教师模型拿到 Lean 定理和已验证参考证明后，生成自然语言计划、带依赖关系的辅助引理，以及重新组装好的完整证明。辅助引理必须写清变量和假设，并保持原定理陈述不变。这里训练的不是把长证明随意切成几段，而是找出能独立成立、还能重新组合的数学中间结果。

**子目标搜索**把“下一个 tactic 怎么选”变成有执行结果的对照实验。系统重放已验证证明，抽取中间状态和可执行快照；提案模型生成多个候选 tactic，再与参考 tactic 一起匿名、打乱，从同一快照独立执行。成功闭环、被接受但仍开放的中间状态、Lean 报错都保留，超时和基础设施故障则剔除。模型由此看到不同选择的后果，而不是只背那条恰好正确的路线。

**错误诊断与修复**要求模型回答四个问题：错在哪、表现是什么、为什么错、怎样改。教师根据失败尝试、诊断反馈和参考修正生成 `location`、`symptom`、`cause`、`fix`，随后给出返修计划和新证明。相比“这是错误版本，这是正确版本，请自己领悟”，这种监督把调试过程摊开了。

**自我验证**来自 Nemotron-Math-Proofs-v2，并采用 DeepSeekMath-V2 风格的提示构造。数据覆盖证明生成与自评、证明验证、元验证三层：既检查证明有没有缺口，也检查自评或独立评审指出的问题是否成立。这层挺关键，会说“我觉得不对”还不够，批评本身也得经得起检查。

![图2：四类中训练数据的构造示例](https://arxiv.org/html/2611.16433v1/midtrain_data_example_cards_editable.png)

*图2给出了四种样本的实际形态：分解样本从定理到计划和组装证明；搜索样本并列展示同一 Lean 状态下 `omega` 成功、减法引理留下开放目标、`assumption` 报错；修复样本把自然数默认类型导致的问题定位到引理，并显式改为实数；自我验证样本则同时包含证明、评价和对评价的复核。它不是抽象流程图，而是在展示训练文档究竟长什么样。*

Replay 的设计也有细节。作者把一个 32K 语义切分前的完整逻辑轨迹称为 parent example，按数据源质量分分配 replay 预算，先覆盖不同题目，再重复同一题的其他轨迹。选中 parent 后，它的全部语义块一起重放，避免模型只看到一段没有上下文的“证明残片”。

污染控制同样做到 parent 级。作者在 2,137 道评测题中确认 29 道重叠，占 1.36%；保守统计对应至多 11.55M token，占全语料 0.03427%。命中后连同语义块和 replay 副本一起删除，SFT 数据也做重叠剔除。MiniF2F 的重叠率是 16/244，即 6.56%，这提醒我们：总量占比很小，不代表单个基准上的污染可以不看。

## Harness 很克制，但成功判定不宽松

Agent 原生数据需要真实环境，作者因此搭了一个轻量 daVinci-Prover harness。输入定理会逐字复制到 `scratch/solution.lean`，智能体在隔离工作区里反复执行“编辑—检查—返修”。`scratch/` 放候选证明和辅助文件，`sketch/` 放可选的引理分解草稿，`target/` 中的 Lean/Mathlib 项目只读。

![图3：daVinci-Prover 的智能体工作区与 Lean 验证闭环](https://arxiv.org/html/2611.16433v1/figures/davinci_prover_harness_swe_agent_style.png)

*图3展示了定理进入智能体后，工具调用如何连接证明工作区和 Lean 环境。每次写入 Lean 文件都会触发检查，错误或局部目标作为环境反馈返回；只有严格目标检查通过，才输出 verified proof。图中也把文件编辑、Mathlib 查询和 Lean probe 分成三组，与正文的七工具设计一致。*

七件工具分别是 `file_read`、`file_write`、`file_edit`、`file_search`、`content_search`、`lean_retrieve`、`lean_verify`。没有 Bash，也没有 Python，作者说这样是给后续 RL 扩展保留更干净的动作空间。每次编辑 Lean 文件自动验证；含占位符的草稿可以看局部目标和诊断，但最终候选必须去掉占位符并接受严格检查。

成功不是“编译器没吐红字”那么简单。系统还检查声明和 elaborated type 是否与原定理匹配，防止模型悄悄证明了一个更弱或不同的命题。评测时也拒绝引入公理或局部实例的证明，包括利用 `native_decide` 绕过正常验证的做法。这个设计我很喜欢： Agent 越自由，终点检查越应该无聊、死板、可机械执行。

SFT 数据由 DeepSeek-V4-Flash-0731 在同一 harness 中采集。题目主要来自约 99K 个未验证问题的 Goedel-LM/RL_dataset_V2，并用 Goedel-LM/SFT_dataset_V2 补充领域。单次最多 30 轮、200 次工具调用，只保留成功证明，再去掉重复严重、无谓调用过多、少于 5 轮以及超过 144K token 上下文的轨迹，留下约 36K 条。

![图4：SFT 轨迹覆盖的 11 个数学领域](https://arxiv.org/html/2611.16433v1/figures/sft_v12_domain_distribution.png)

*图4显示，代数与不等式占 38.81%，Mixed/Other 占 14.56%，数论占 14.05%，分析与微积分占 13.50%；几何为 5.81%，抽象代数为 3.87%，拓扑、组合、概率统计都在长尾。覆盖面确实广，但“领域多样”不等于“领域均衡”，前四大类已经占了八成以上。*

## 训练上的硬细节：不是把长文档粗暴拼到 32K

中训练采用全参数训练，保留自回归 next-token 目标，也保留一层 multi-token prediction 目标，权重为 0.1。MoE 模型还沿用预训练路由配置，加入全局 batch 的负载均衡损失。可以把目标简洁写成：

$$\mathcal{L}=\mathcal{L}_{\mathrm{NTP}}+0.1\mathcal{L}_{\mathrm{MTP}}+\lambda\mathcal{L}_{\mathrm{balance}}$$

其中稠密模型的 $\lambda=0$，MoE 模型使用 $\lambda=10^{-3}$。优化器是 AdamW，weight decay 为 0.1；学习率先在前 3% step 线性 warmup，再 cosine decay 到零。

更有工程味的是 32K 离线 packing 的样本隔离。不同样本拼进同一序列后，作者用逐样本累积边界形成 block-diagonal causal attention，同时重置位置索引和 Gated DeltaNet 状态，并 mask 跨样本边界的 next-token target。没有这些约束，模型可能在样本 B 的开头偷看样本 A 的结尾，训练文档看起来整齐，注意力却早已串台。

## 实验：增益稳定，但别把所有高分放进同一把尺子

主实验使用 Qwen3.5-9B-Base 和 Qwen3.5-35B-A3B-Base，另在 Qwen3-8B-Base 上做语料对照。五个主基准覆盖 244 道 MiniF2F 高中奥赛题、360 道 MathOlympiadBench 近期竞赛题、186 道 ProofNet 本科定理、325 道 ProverBench 混合难度题，以及 672 道 PutnamBench 竞赛题；另测抽象代数与交换代数的 FATE-M、FATE-H。

Agent 评测温度是 1.0，上下文为 200K，最多 30 次交互；环境固定为 Lean v4.26 和 Mathlib commit `2df2f0150c275ad53cb3c90f7c98ec15a56a1a67`。Table 2 中作者自测模型用 pass@8，外部带 dagger 的数字则是原论文报告的 pass@32，没有在新协议下重跑。论文对 pass@8 的定义是：

$$\operatorname{Pass@8}(i)=\mathbf{1}\left[\sum_{j=1}^{8}\operatorname{success}_{ij}\gt 0\right]$$

也就是八次尝试至少成功一次。它和 pass@32 都衡量采样预算下的成功覆盖，但预算不同，不能仅凭数值大小判定谁更强。

### 匹配 Base + SFT 对照：中训练带来一致增益

| 模型 | MathOlympiad | MiniF2F | ProofNet | ProverBench | Putnam |
|---|---:|---:|---:|---:|---:|
| Qwen3.5-9B-Base + SFT | 32.3 | 92.6 | 51.1 | 66.2 | 22.3 |
| Qwen3.5-9B-Midtrain + SFT | 35.3 | 93.9 | 52.7 | 66.5 | 24.9 |
| Qwen3.5-35B-Base + SFT | 35.8 | 93.0 | 52.7 | 66.5 | 24.3 |
| Qwen3.5-35B-Midtrain + SFT | 36.1 | 94.3 | 53.8 | 67.1 | 26.5 |

*表：论文 Table 2 中作者自测的 pass@8 结果。*

9B 模型在 MathOlympiad 和 Putnam 上分别涨 3.0、2.6 个点，ProofNet 涨 1.6 个点；35B 模型在 Putnam 上涨 2.2 个点，其余多项只有 0.3 到 1.3 个点。一致性是有的，但 35B 在 MathOlympiad 上仅多 0.3 个点，ProverBench 也只有 0.6 个点，不能把“所有任务都大幅提升”当成结论。MiniF2F 已经站在 93 分附近，头部空间也确实有限。

如果看外部系统，OProver-8B 的五项 pass@32 为 21.7、91.8、31.9、56.0、9.0，OProver-32B 为 22.8、93.3、33.2、58.2、11.3；DeepSeek-V4-Flash-0731 接入 daVinci harness 后的五项 pass@8 则达到 52.2、95.9、56.5、68.9、39.7。教师模型很强，但这里同时改变了模型、推理框架和采样口径，不能把差距全记到 harness 或训练配方名下。

检索工具本身的收益倒有一组同协议对照。Table 3 报告三次运行的平均 pass@1：DeepSeek-V4-Flash 加入 Mathlib retrieval 后，MiniF2F 从 90.2 到 91.3，FATE-M 从 94.7 到 99.3，FATE-H 从 19.0 到 29.0，Putnam 从 18.9 到 22.8；Qwen3.6-35B-A3B 也从 68.0、48.7、4.0、3.0 提高到 73.0、57.3、5.0、3.4。难题收益更大，不过 FATE-H 的绝对分数仍低，离“可靠解决”还很远。

### SFT 曲线：中训练让模型更早进入状态

![图5b：五个 SFT epoch 上 MiniF2F avg@5 的变化](https://arxiv.org/html/2611.16433v1/figures/minif2f_qwen9b_35b_avg5.png)

*图5b中，实线是 mid-train，虚线是 base；红绿两色对应 35B，蓝紫两色对应 9B，纵轴是五次运行的平均成功率 avg@5。第 1 个 epoch 就拉开明显差距，随后 base 逐步追赶，但 mid-train 曲线整体仍更高。误差棒也没有被藏起来，这是读小样本基准曲线时必须要看的信息。*

论文给出的精确变化是：一个 epoch 后，9B 和 35B 的 avg@5 分别提高 5.33、5.08 个点，而且 mid-train 此时的 pass@5 已能匹配 base 在第 5 个 epoch 的水平。这里最打动我的不是终点多赢一点，而是起点更接近 SFT 分布。它支持了“中训练缩小分布差”的解释，比只晒最终 checkpoint 更有说服力。

### 组件消融：8.4B Agent token 不是万能，但确实很能打

| 数据组件 | token 数 | MiniF2F | FATE-M | ProofNet |
|---|---:|---:|---:|---:|
| Qwen3.5-9B Base | — | 87.4 | 88.4 | 42.9 |
| 技能先验 $\mathcal{D}_{skill}$ | 25.3B | 87.8 | 89.8 | 43.6 |
| Agent 轨迹 $\mathcal{D}_{agent}$ | 8.4B | 88.8 | 92.2 | 43.5 |
| 两者结合 | 33.7B | 90.1 | 93.3 | 44.5 |

*表：论文 Table 4。每项都在 Qwen3.5-9B 上做组件对照。*

Agent 数据只有技能先验约三分之一的 token，却在 MiniF2F 和 FATE-M 上取得更大的单项增益；两者结合又是全部配置里最好的。这支持作者的核心判断：技能先验教模型“怎样想”，环境轨迹教模型“怎样把想法变成工具操作”。

但 ProofNet 上，Agent 单项是 43.5，技能先验是 43.6，前者并没有更强。两组单项实验的 token 预算也不相等，所以不能进一步推出“Agent 数据每个 token 的效率就是高三倍”。严谨的读法是：交互轨迹在当前 harness 和评测分布上回报很高，技能数据仍有补充价值，尤其是组合后的 44.5。

### 与已有语料对照：33B 胜过 65B，原因不只是规模

| 初始化与训练 | MiniF2F | FATE-M | ProofNet |
|---|---:|---:|---:|
| Qwen3-8B-Base + SFT | 73.4 | 68.0 | 28.4 |
| OProver-8B-Base + SFT | 80.3 | 73.1 | 30.3 |
| Qwen3-Base + daVinci mid-training + SFT | 85.3 | 85.3 | 40.4 |

*表：论文 Table 5。三种初始化都接同样的五 epoch Agent SFT，并用 YaRN 把上下文从 32K 扩到 256K。*

相对 Qwen3-8B 的 SFT-only 基线，三项依次增加 11.9、17.3、12.0 个点，平均 **13.7 个点**；相对使用 65B token 中训练的 OProver-8B-Base，daVinci 配方用约 33B token 还多出 5.0、12.2、10.1 个点。至少说明后续 Agent SFT 不是全部原因，数据组成值得单独优化。

话说回来，这也不是严格的“同质量数据只改一半 token”实验。两种 Base 的语料来源和训练过程不同，结论应落在“这套配方更匹配当前下游任务”，而不是抽象的 2 倍数据效率。

### 数据扩展与记忆压缩：收益还在，瓶颈开始移动

![图8：中训练 token 规模与平均 pass@1 的近似对数线性关系](https://arxiv.org/html/2611.16433v1/figures/minif2f_fate_m_qwen9b_data_scaling_loglinear_fit.png)

*图8使用 7.5B、15B、22.5B、30B、33.7B token 的 Qwen3.5-9B checkpoint，横轴为对数刻度。MiniF2F 和 FATE-M 的拟合 $R^2$ 分别为 0.9461、0.9417；Base 分数是 82.38 和 77.56，到 15B token 时为 86.34 和 88.67，恰好对应论文正文写出的 3.96、11.11 个点增益。后半程仍上升，但斜率变小。*

这张图支持“继续加数据还有用”，却不支持无限外推。五个点都围绕同一条曲线时很漂亮，跨数据分布、跨 harness 是否还成立，论文没有回答。并且图8是数据扩展实验的特定快照，不宜把上面的终值与另一张表的最终模型分数直接拼接。

真正让我愣了一下的，是 memory compaction 那张表：

| 模型 | 是否压缩记忆 | MiniF2F | FATE-M | FATE-H |
|---|---|---:|---:|---:|
| Qwen3.5-midtrain-9B | 否 | 90.1 | 93.3 | 16.7 |
| Qwen3.5-midtrain-9B | 是 | 97.1 | 96.7 | 28.0 |
| Qwen3.5-midtrain-35B | 否 | 90.1 | 93.7 | 16.3 |
| Qwen3.5-midtrain-35B | 是 | 97.1 | 97.3 | 42.0 |

*表：论文 Table 6，pass@1，三次运行取平均。它与 Table 2 的 pass@8 口径不同。*

上下文到 200K token 后，系统用确定性抽取的工具证据替换旧交互，同时保留原定理、当前 Lean 证明和最近交互，最多压缩 8 次。35B 在 FATE-H 上从 16.3 到 42.0，这个跨度比很多中训练增益都大。它提示我们：长程证明里，模型可能已经“有能力”，只是被几十轮前的冗余工具输出挤掉了工作记忆。

但先别急着把 42.0 当成纯模型能力跃迁。记忆压缩改变了智能体可见的信息和可继续交互的空间，它是推理系统的一部分。这里也缺一个更细的行为分析：压缩后究竟多解决了哪类题、是否增加了额外轮次、证据选择会不会丢掉关键失败原因。说实话，这块我觉得论文还可以再深挖。

## 我的判断：最值钱的是数据观，最该警惕的是评测边界

这篇工作不是从零发明 Agentic proving，也不是第一个使用 Lean 反馈的人。它的贡献更像一次扎实的训练配方重构：把数学技能、环境交互和严格验证组织成可复用的数据生产流程，再用匹配基线、组件消融、SFT 曲线和行为统计把故事补齐。尤其是“分解步骤随难度增加”的现象很有意思——在 DeepSeek 八次都没解出的高难度 Putnam 题上，首个候选证明的局部 `have/suffices` 步数，9B 从 5.13 增到 9.57，35B 从 5.73 增到 9.63；换算成每千个词法 token 的密度也上升，说明不只是代码变长。

我有四点保留。

**同 harness 训练与评测既是优势，也是边界**。 分布对齐当然会带来收益，但收益里有多少能迁移到另一套工具 schema、另一种上下文组织方式，论文没有测。它证明的是 Agent-native，不等于 Agent-agnostic。

**跨系统榜单不能混读**。 Table 2 的作者结果是 pass@8，外部基线是 pass@32，而且外部结果没有重新运行。作者已在表中用 dagger 标明，读者也应该保留这层提醒。尤其 MiniF2F 接近饱和后，继续比较几个小数点，未必比 Putnam、FATE-H 的行为分析更有信息量。

**通用能力没有纳入证据链**。 作者在 Limitation 中承认，中训练没有 replay 通用数据，也认为保留和提升通用能力是必要的。当前实验只回答“是否更会做 Lean Agent”，没有回答数学以外的代码、知识或通用推理是否受影响。

**数据生产并不便宜**。 附录 F 给出的教师部署是 48 张 NVIDIA H200 跑约 20 天，共 23,040 GPU-hours；按论文引用的 2026 年 11 月 9 日公共云价格折算约 12.2 万到 14.6 万美元。这只是数据合成的租赁等价估算，不是实际支出，也不含 Lean CPU 服务、存储和模型训练成本。Lean 验证另用约 8 个 worker，总计 160 CPU 核、640GB 内存，运行约 20 天。小团队可以借鉴数据思想，但很难原样复刻规模。

复现上也要多一句冷静的话：论文承诺在匿名评审结束后开放数据、模型、harness、代码和训练基础设施。承诺很完整，当前能否从头复现，仍要看最终发布物，而不是只看仓库链接是否存在。

## 如果你在做 Agent，这套思路怎么搬

| 你的场景 | 值得借鉴的做法 | 不建议直接照搬的地方 |
|---|---|---|
| 代码智能体 | 把检索、编辑、测试、报错和返修轨迹前移到中训练 | 只收成功最终补丁，丢掉中间状态 |
| 数学与形式化推理 | 保留验证器接受的开放状态，不只保留完整闭环 | 把“没报错”当作唯一成功条件 |
| 长程任务 | 用确定性证据压缩旧上下文，保留当前工件 | 无差别摘要全部历史，丢掉关键失败细节 |
| 数据配比优化 | 对技能数据和交互数据分别消融，再看组合 | 只按 token 总量判断数据价值 |
| 小预算复现 | 先复用现有教师轨迹，做同协议小样本对照 | 一开始就复制 48 卡、20 天的数据生产 |

坦率的讲，我会把 daVinci-Prover 归为一篇“训练阶段设计”的论文，而不是“又一个证明器排行榜冠军”。它给出的核心提醒很朴素：**部署时需要的能力，最好在训练数据里就有对应物**。 如果模型上线后要读工具输出、管理长上下文、从局部失败中恢复，却只喂它完美答案，那我们其实是在把最难的部分留到上线以后碰运气。

下一步真正值得看的，不是 MiniF2F 能否再挤高零点几分，而是这套 Agent 原生中训练能否跨工具、跨任务迁移，以及加入 RL 和通用 replay 后，能不能同时保住交互能力与普通能力。这个问题还没有被回答，也正是这篇论文留下的空间。
