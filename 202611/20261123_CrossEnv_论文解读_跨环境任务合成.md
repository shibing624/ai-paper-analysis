# 只用 2954 条数据，让 Agent 学会跨服务办事：CrossEnv 把「数据对不齐」炼成了可验证的训练任务

你有没有碰到过这种事：给一个 Agent 单独派活，订机票、订酒店、订餐厅，样样利索；可一旦任务变成「按航班落地时间和酒店位置，找一家 1 公里内的素食餐厅，晚餐至少安排在落地 90 分钟后」，它立刻开始顾此失彼。要么把 `arrival_time` 当字符串去比大小，要么压根没意识到餐厅搜索的半径参数得拿酒店地址来填。

说实话，我之前倒腾合成训练数据的时候也被这个卡过。单个服务的数据库好造、工具好写、验证规则也好写——查一下订单在不在、时间对不对，完事。可当你想把两个独立造出来的环境拼成一个任务，麻烦就来了：同一家「12 Rue Atlas」酒店，在订房环境里登记的是这个地址，到了导航环境里可能写成「12 Rue de l'Atlas」，甚至压根没这条记录。数据各造各的，单独看都合法，拼起来就对不上。任务不可执行，验证规则也就成了摆设。

CrossEnv 让我觉得有点意思的地方，就是它没绕开这个脏活，反而把它做成了整条流水线的核心。

---

## 🎯 核心摘要

真实的长程任务往往跨服务：一个动作要吃另一个服务吐出来的信息。现有程序化环境合成基本只造单环境任务，卡点不在生成工具，而在跨环境数据对不上——各建各的库，同一实体在不同服务里地址、编号、状态互相矛盾，任务没法执行，更谈不上可验证。CrossEnv 用一张实体工具图按共享实体类型把环境连起来，采连通子图当任务骨架，再对齐任务级数据、生成可执行验证规则；配套 CrossEnv-Curriculum 从单环境 SFT 一路阶梯式 RL 走到跨域加用户交互。只用 2,954 条训练记录（约 EnvScaler 的四分之一），CrossEnv-8B 在 DeepPlanning 从 1.7 提到 10.8、Claw-Eval 从 14.4 提到 23.6。我的判断是：这不是底层算法突破，是一次相当扎实的系统整合——把「造任务」这件事从单环境推到了跨环境，数据效率那笔账得打折看，但方向值得跟进。

## 🧠 问题动机：单环境任务为什么不够用

先把这篇论文要打的靶子立清楚。

以 LLM 为内核的 Agent 靠调工具、看环境反馈来推进任务，训练它需要两样东西：足够多样的可执行环境，以及能给出可靠对错信号的验证任务。真实服务受访问限制、交互成本高，直接在上面练不现实，于是程序化合成环境成了主流替代——用代码造工具、造有状态的数据库、造能自动判分的任务。

问题在于，这套流程造出来的基本都是「单环境任务」。你想想看，一个订票环境里的任务，起点、动作、终点、判分规则全在这个环境的边界内，闭合得很好。可真实世界里稍微像样一点的事务都是跨服务的：订完机票和酒店，才轮到挑餐厅；而挑餐厅这件事，得同时用到航班落地时间、酒店地址、还有用户自己那句「吃素、离酒店 1 公里内、落地后至少 90 分钟」的偏好。

![图1：独立任务与跨环境任务的对比](https://arxiv.org/html/2611.22777v1/figure1_v23_spacing.png)

*图1：论文 Figure 1。上半部分是三种各自独立验证的任务（航班、酒店、餐厅各查各的）；下半部分把它们串成一个旅行规划任务——酒店地址被复用为餐厅搜索的坐标，航班到达时间被复用为晚餐时间的下界，再用一条联合验证规则同时检查距离、时间、素食选项三个条件。*

图 1 把差别画得很直白：独立任务里，每个环境自己给自己打勾（`verified`），判分是局部的；跨环境任务里，信息要从一个服务流到另一个服务，判分变成一条横跨三个环境的联合规则。作者给这类任务下的定义是「至少涉及两个环境的工具调用，且完成条件要求用某个环境的信息去指导另一个环境的动作，或者对多个环境的合并结果加约束」。

难点就藏在「合并」二字里。数据一致性。

这句话值得停一下。同一个酒店，在订房库和导航库里是两个独立造出来的记录，地址对不上、ID 对不上、甚至有没有这家店都对不上；单独跑各自的任务都没毛病，一旦要求「用订房库的地址去导航库查附近餐厅」，任务当场崩掉。所以跨环境任务合成不是「把两个单环境任务拼起来」这么简单，它得在任务级别重新对齐数据：哪些记录一开始就得存在，哪些得靠前面的动作生成，哪些冲突必须消除，哪些约束要跨库成立。

作者把现有方案按能力拆成了一张表，我把它浓缩成下面这张对比：

| 方法类别 | 代表工作 | 可执行 | 可验证 | 复杂度可控 | 跨环境任务 | 数据对齐 | 新环境接入联合任务 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 真实服务 | ToolLLM、Toucan、AgentTrek | 支持 | 有限 | 有限 | 部分支持 | 未明确 | 部分支持 |
| LLM 模拟环境 | Simia、DreamGym、EnvACE | 有限 | 有限 | 有限 | 部分支持 | 未明确 | 未明确 |
| 程序化环境 | EnvScaler、AWM、ScaleEnv、Agent-World、Skill2Env | 支持 | 支持 | 部分支持 | 有限 | 未明确 | 未明确 |
| **CrossEnv** | 该框架 | 支持 | 支持 | 支持 | 支持 | 支持 | 支持 |

*表1：据论文 Table 1 整理。Exec. 真实服务或代码执行；Verif. 程序化结果检查；Ctrl. 复杂度可调；Cross 多环境任务；Consist. 跨环境数据对齐；Ext. 把新环境接入联合任务。*

坦率地讲，这张表里最值钱的不是「多环境」那一列，而是「数据对齐」和「新环境接入」这两列。跨应用基准（τ²-bench、AppWorld 一类）本来就带跨环境依赖，只是任务与评测器多半靠人工或半自动设计，规模上不去；ARE 那类工作也在处理跨应用数据一致性，但走的是依赖感知生成。CrossEnv 想补的空位很明确：把跨环境任务的合成做成可规模化的自动流水线，同时保留程序化验证。

## 🏗️ 方法核心：把「连接」和「对齐」做成流水线

先看全貌。

![图2：CrossEnv 五阶段任务合成框架](https://arxiv.org/html/2611.22777v1/figure2_v19_logo.png)

*图2：论文 Figure 2，整个框架的五个阶段。① 单环境调研（MCP / Skill seeds → 领域与能力分类 → 文档、初始数据库）；② 局部依赖图（每个环境抽出实体类型与工具关系）；③ 跨环境图组合（按共享实体类型合并，采样连通子图得到任务骨架）；④ 工具合成与测试（复用已测工具，coding agent 补缺，失败即修复重测）；⑤ 任务实例化与验证（对齐数据 → 参考执行 → 生成检查规则 → 重放加独立尝试双重校验）。*

一句话讲清核心 idea：**先把环境之间能连接的地方显式建出来，再在任务级别对齐数据，让验证规则从参考执行里自动长出来**。顺着这个思路，五个阶段就不再是罗列，而是层层收紧的因果链。

**阶段一，单环境调研**。从 MCP 服务和公开 skill 文档收种子，过滤后留下 801 个 MCP 种子、682 个 skill 种子。一个 research agent 去检索文档和数据，一个 data construction agent 建初始数据库，缺信息就回头再检索。种子被归到 10 个业务域、84 个能力类别里（借了 Agent-World 的分类法）。这张分类表不是摆设，后面 L2 到 L4 的「域内 / 跨域」难度旋钮就靠它。

**阶段二，局部依赖图**。每个环境单独抽实体类型和属性，建一张局部实体工具图 $G_i=(V_i,R_i)$：节点是实体类型，有向边是工具支持的关系。图 2 里给了两个例子，`reserve_room` 撑起 Person→Hotel 的预订关系，`search_hotels` 撑起 City→Hotel 的检索关系。到这一步，环境仍然是各自独立的。

**阶段三，跨环境图组合**。这是我认为整篇最漂亮的一步。不同环境可能对同一实体类型提供不同操作，那就按共享类型把局部图合并成 $G^{\times}$，同时保留每条关系原本属于哪个环境、由哪个工具支持：

$$V^{\times}=\bigcup_i V_i,\qquad R^{\times}=\bigcup_i\{(i,r)\mid r\in R_i\}$$

合并之后，Person、City 这类共享节点把航班图、酒店图、餐厅图缝成一张图。接着从这张合成图里采连通子图，要求跨越至少两个环境，并且按三个维度筛：实体关系上这些操作能不能围绕共同对象、操作互补上增删改查能不能凑成连贯工作流、业务相关性上这些能力放在一起像不像一个真实任务。通过筛选的连通子图就是任务骨架 $S$，附带参与环境集合和所需工具。

难度旋钮也在这个阶段拧：环境个数控制协调规模，业务域范围控制语义跨度，再加一个「要不要用户交互」的开关。看到这里我才意识到，Curriculum 那五级台阶不是训练时临时拍脑袋分的，而是合成阶段就把结构参数埋进了任务里。

**阶段四，工具合成与测试**。骨架里缺的工具交给 coding agent 按描述、调研材料和初始库去实现，已测过的直接复用。测试查三件事：读操作的返回值对不对且数据不动、写操作的变更有没有真的发生（用后续查询确认）、非法输入和冲突操作能不能正确报错。失败就打回修复重测，全部通过才算环境可运行。

**阶段五，任务实例化与验证**。这里是脏活的主战场。给定骨架和目标，选具体实体与记录，补缺失数据，消除环境之间的冲突，而且初始数据与参考动作要**联合规划**：读、改、删所需的记录要么一开始就在，要么由更早的动作生成；任务要求 Agent 自己创建的记录，绝不提前塞进去。这一步产出对齐后的联合初始状态 $\mathbf{s}_{0,\tau}$。

然后从 $\mathbf{s}_{0,\tau}$ 跑一遍计划动作，后面的动作可以引用前面动作的输出，跑挂了就按反馈修订数据与动作计划再跑。跑通了，得到参考动作序列 $A^{*}$，再据此生成任务指令 $I$。

任务最终被形式化成一个五元组：

$$\tau=(\mathcal{E}_{S},\,I,\,\mathbf{s}_{0,\tau},\,A^{*},\,C_{\tau})$$

$\mathcal{E}_{S}$ 是参与环境，$I$ 是指令，$\mathbf{s}_{0,\tau}$ 是联合初始状态，$A^{*}$ 是参考执行，$C_{\tau}$ 是一组可执行验证规则。完成条件写成一条乘积：

$$\operatorname{Pass}_{\tau}(A)=\prod_{c\in C_{\tau}} c\!\left(O_{A},\,\mathbf{s}_{T(A)}\right)$$

只有当所有规则在工具输出与终态上都为 1，任务才算过。规则从任务目标和参考执行结果里推导，检查三样东西：需要的记录有没有被创建/更新/删除、返回结果满不满足条件、相关信息跨环境是否一致；还会专门造负例（漏掉某个操作、填错值）去验证规则确实会把不完整的结局判失败。

还有一道双重校验，我觉得这个设计挺克制：重置环境重放 $A^{*}$，要求结果可复现且 $\operatorname{Pass}_{\tau}(A^{*})=1$；再从同一初始状态跑 5 次独立 Agent 尝试，至少 2 次通过才保留这个任务。前者保证参考解不是偶然，后者保证任务从指令和接口出发是可解的、不至于难到没边。

说到这个，补一句工程上的直觉：把「联合验证」放在工具输出和终态上，而不是靠 LLM 判分，是这类合成方法能给出稳定 RL 奖励的前提。规则是代码，跑一百次结果一样，奖励才不会漂。

## 🔧 CrossEnv-Curriculum：五级台阶怎么搭

任务造出来了，怎么喂给模型也有讲究。作者按环境数、业务域范围、是否需要用户交互，把任务分成五级：

| 层级 | 训练阶段 | 训练集 | 验证集 | 平均轮数 | 结构 |
| --- | --- | --- | --- | --- | --- |
| L1 | SFT | 800 | 40 | 4.73 | 单环境，打基础工具使用 |
| L2 | RL | 579 | 40 | 4.84 | 同一业务域内，两个环境协调 |
| L3 | RL | 620 | 50 | 8.70 | 同域内，三个及以上环境 |
| L4 | RL | 600 | 50 | 12.66 | 跨多个业务域，仍三个及以上环境 |
| L5 | RL + 用户交互 | 355 | 40 | 13.76 | 保留 L4 结构，引入用户交互 |

*表2：据论文 Table 2 整理，Turns 统计工具调用数，L5 额外含一次必需的澄清提问。合计 800 条 SFT + 2,154 条 RL = 2,954 条训练记录。*

训练路径是：L1 用参考轨迹做全参数 SFT，教工具选择、参数填写、怎么用工具输出；L2 到 L5 逐级做轨迹级 outcome GRPO，每一级都从上一级的 checkpoint 初始化。L5 的用户交互细节值得一提：Agent 一开始只拿到公开指令，用户私有的事实被藏起来，得主动调 `ask_user` 去问，回复以 tool-role 消息接回上下文，每个任务最多问三次，用户回复由 Qwen3.8-Flash 生成。

训练配置（论文 Table 7）也摆一下，方便想复现的人对参数：L1 SFT 峰值学习率 $5\times10^{-7}$、约 10% warmup 加余弦衰减、全局 batch 8 条 assistant 回复；L2–L5 RL 恒定学习率 $5\times10^{-7}$、全局 batch 16 个任务槽、每任务采 8 条轨迹、PPO 1 个 epoch、损失里 KL 系数 0.001、训练温度 1.0 验证温度 0，每个 RL batch 共 128 条采样轨迹。

GRPO 的优势就是组内归一化，八条轨迹的终末奖励减均值除标准差：

$$\hat{A}_i=\frac{R_i-\mu_R}{\sigma_R+10^{-6}}$$

这个优势被赋给该轨迹里所有 assistant 生成的 token。真正让我多看两眼的是终末奖励的设计：

$$R = 0.85(P_T-P_0) - 0.20(V_T-V_0) - 0.01\,n_{\text{invalid}} + 0.10\,I_F + 0.05\,I_F I_D\, e$$

$P$ 是通过的任务检查加权占比，$V$ 是被违反的约束加权占比，下标 0 和 T 是初态与终态；$n_{\text{invalid}}$ 记非法动作数；$I_F$ 要求所有执行检查通过且给出有效答案，$I_D$ 标记工具发现协议是否满足；$e$ 是效率项，把交互轮数压在预算内，$L2$ 用 $(T_{\max},T_{\text{ref}})=(32,18)$，$L3$–$L5$ 用 $(40,30)$。

等等，这个 loss 真的只靠通过率就能收敛吗？其实它给了部分分：只要比初态多通过几条检查就有正奖励，不是非黑即白的二值成功信号。对长程任务来说这个取舍很实际——14 步的参考动作，若只按「全对」给分，绝大多数 rollout 都是 0，梯度稀得可怜。但代价也埋在这儿：训练时优化的是检查通过率的增量，评测时看的是严格成功率，两者并不对齐，后面聊批判时还会回到这点。

## 🧪 实验结果：把数字摆出来

评测用四个外部基准，覆盖互补的能力面：τ²-bench 测交互式工具使用与用户协调、DeepPlanning-Shopping 测带约束的长程规划、VitaBench 测多服务协同、Claw-Eval 测通用助理的服务编排与专业对话。骨架统一用 Qwen3 的 1.7B / 4B / 8B，对照原始 base 模型，再拉上一串环境训练 baseline（Toucan、EnvACE、EnvScaler、Arctic-AWM、Agent-World）和若干闭源前沿模型当参照。

主表里我摘出 8B 这一档最关键的几行：

| 模型 | 训练记录 | τ²-bench Avg | DeepPlanning Avg | VitaBench Avg | Claw-Eval Avg |
| --- | --- | --- | --- | --- | --- |
| Qwen3-8B（base） | — | 11.5 | 1.7 | 7.0 | 14.4 |
| EnvScaler-8B | 11,572 | 12.8 | 8.3 | 9.0 | 21.5 |
| Agent-World-8B | 3,000 | 9.3 | 9.2 | 14.0 | 20.5 |
| Arctic-AWM-8B | 3,315 | 11.5 | 1.7 | 5.0 | 14.4 |
| **CrossEnv-8B** | **2,954** | **12.3** | **10.8** | **14.0** | **23.6** |
| Qwen3.8-Max（闭源参照） | — | 19.5 | 70.0 | 47.0 | 77.9 |
| Kimi-K3（开源参照） | — | 13.9 | 31.7 | 46.0 | 80.5 |

*表3：据论文 Table 3 整理，Avg 按子集大小加权。τ²-bench 下含零售/航空/电信/银行四个子集，VitaBench 下含配送/到店/OTA/信贷，Claw-Eval 下含通用/多轮。*

作者自己点了三条发现。一是三个尺寸上都对 base 有增益或打平，8B 上 DeepPlanning 从 1.7 到 10.8、VitaBench 从 7.0 到 14.0、Claw-Eval 从 14.4 到 23.6。二是数据效率高：2,954 条记录约为 EnvScaler 的四分之一，在四个基准里有三个超过 EnvScaler-8B，DeepPlanning 和 Claw-Eval 拿到 1.7B–8B 档里的最高分，VitaBench 与 Agent-World-8B 打平。三是增益不均衡：规划与服务协同三个尺寸都涨，通用助理任务只有大模型涨得明显，交互式工具使用的提升「比较有限」——论文用的是 modest 这个词，我看了下表，8B 在 τ²-bench 上是从 11.5 到 12.3，涨了 0.8 个点，确实谈不上好看。

回到能力是怎么长出来的这块，Figure 3 把 Qwen3-8B 从 Base 到 L5 逐阶段拆成五个面板：

![图3：Qwen3-8B 从 Base 到 L5 的五项能力演化](https://www.mulanai.com/fs/files/1123_4383f5d4_curricul.png)

*图3：论文 Figure 3 重绘。(a) 工具执行 Base 65.0 → L5 95.6，L1 一次 SFT 就冲到 89.1；(b) 环境覆盖 Base 约 37 → L3 100 → L5 92.5；(c) 后期步骤执行 L2 81.0、L3 87.0、L5 86.7；(d) 状态准确率 Base 37.3 → L4 88.1 → L5 89.6；(e) 用户交互是复合分数，L1 掉到 0、L3 回到 20.0、L5 22.5。浅色阴影标出各阶段对应的训练区间。*

这张图里有个反直觉的地方我盯着看了一会儿：L3 时模型执行了更多必需工具，最终状态检查通过率反而更低。作者的解释是「会调更多工具」和「把整件事做对」之间有一段爬坡期，能力不是同步到位的。(e) 那个面板得小心——它是复合交互分数，不是成功率，L1 掉到 0 是因为 SFT 阶段压根没练过问用户，别当成能力退化。

课程学习到底值不值，Figure 4 给了直接对比：同一个 L1 SFT 起点、同一批 L2–L4 任务池，只改「按级推进」还是「混着喂」。

![图4：课程训练与混合训练的对比](https://www.mulanai.com/fs/files/1123_8a65da18_checkpoi.png)

*图4：论文 Figure 4，8B 结果。(a) 在相近累计 GPU 小时下按任务级看严格成功率，Curriculum 在 L1 约 63% 对 Mixed 约 50%、L2 约 52% 对 42%、L3 约 15% 对 11%、L4 约 18% 对 4%，每一级都更高；(b) 累计 rollouts 随 GPU 小时增长，1200 GPU 小时处 Curriculum 约 68k 对 Mixed 约 52k。*

作者的解释挺朴素：先练短的两环境任务，早期每条样本的交互成本更低，同样算力能攒出更多 rollout。这个说法我信一半，另一半得留给作者自己在 Limitations 里承认的那句——两组在 batch 配置、并行度、参考模型设置上并不完全一致，所以增益不能全记在「课程顺序」头上。

跨环境数据本身有没有用，Table 5 这组消融比主表更有说服力。同一 SFT 冷启动，只换 RL 数据：

| --- | --- | --- | --- | --- |
| τ²-bench | 11.5 | 8.5 | 8.8 | 11.5 |
| DeepPlanning | 1.7 | 3.3 | 6.7 | 7.5 |
| Claw-Eval | 14.4 | 16.9 | 15.4 | 20.0 |
| 输出复用 | 6.7 | 8.3 | 1.7 | 11.7 |
| 后期步骤成功 | 23.3 | 18.3 | 28.3 | 33.3 |

*表4：据论文 Table 5 整理，Qwen3-8B，百分数。三组执行能力指标是作者遍历四个评测基准的轨迹后归纳出来的。*

看到 Table 5 我才意识到差距在哪：单环境 RL 把「输出复用」从 6.7 拉到 1.7，反而练退了；「联合成功」直接归零。CrossEnv 把这两项分别拉到 11.7 和 8.3。说到底，单环境任务里根本没有「把上一个服务的返回值填进下一个服务的参数」这种结构，模型自然学不会；跨环境任务逼着它练这个，才有后面的协同增益。这条因果链比主表那几个百分点更值钱。

| 4B | 见过 | +30.0 | +43.7 | +48.5 | +32.2 |
| 4B | 没见过 | +24.0 | +33.7 | +26.9 | +22.5 |
| 8B | 见过 | +28.0 | +44.3 | +30.4 | +26.4 |

*表5：据论文 Table 4 整理，均为相对 Base 的百分点增益，任务成功要求满足全部要求。*

三个尺寸在没见过的组合上都还有正增益，1.7B 的「状态」那格是 +0.0，等于没动。这个结果支持「学到的是可迁移的协调能力，不是记住了具体环境搭配」，但增益幅度相比见过的组合普遍缩水一截，也别夸大成完全泛化。

二是更长的工作流。训练里参考动作最长 14 次工具调用，测试直接上 16–18 和 24–28 两档：

## 📊 把账算清楚：两组对比

把前面散落的数字收拢一下，先看方法定位：

| 维度 | 单环境程序化合成（EnvScaler / AWM 等） | 跨应用基准（τ²-bench / AppWorld 系） | CrossEnv |
| --- | --- | --- | --- |
| 任务来源 | 自动生成，单环境内 | 人工或半自动设计 | 自动生成，跨环境组合 |
| 数据一致性 | 单库内自洽即可 | 人工保证 | 任务级对齐 + 冲突消解 |
| 验证方式 | 程序化结果检查 | 定制评测器 | 从参考执行生成可执行规则 |
| 复杂度控制 | 部分支持 | 固定 | 环境数 / 业务域 / 用户交互三旋钮 |
| 规模 | 高 | 低 | 候选产出随环境数加速 |
| 新环境接入 | 未明确 | 需重设计 | 接进共享实体类型即可 |

再看 8B 这一档「数据效率」这笔账：

| 方法 | 训练记录 | DeepPlanning | VitaBench | Claw-Eval | 备注 |
| --- | --- | --- | --- | --- | --- |
| Qwen3-8B | 0 | 1.7 | 7.0 | 14.4 | 未经训练的原始模型 |
| EnvScaler-8B | 11,572 | 8.3 | 9.0 | 21.5 | 记录数最多 |
| Agent-World-8B | 3,000 | 9.2 | 14.0 | 20.5 | 作者自行复现 |
| CrossEnv-8B | 2,954 | 10.8 | 14.0 | 23.6 | 记录数最少 |

单看这张表，「四分之一数据、三个基准反超」确实亮眼。但把它当结论之前，得先读作者自己写的 Limitations。

## 🤔 我的判断：哪些地方我皱了眉

这篇论文我读得挺顺，方法链条完整、图也画得清楚，可越到实验部分越想慢下来核一核。

**数据效率这笔账得打折**。2,954 是**训练记录**数，不是训练算力。RL 阶段每个任务采 8 条轨迹、每个 batch 128 条采样轨迹、L2 到 L5 逐级跑，累计交互次数和 GPU 小时远超「2,954」给人的直觉；而 EnvScaler 那 11,572 是它报告的数据集规模，两者的构造成本、单条轨迹长度也不在一个量纲上。作者在 Limitations 里自己写了一句「训练记录数的对比并不建立训练算力上的等价优势」——这话很诚实，但也等于把主表最响的那个卖点削了一刀。我的第一反应是：把「fewer training examples」当成效率结论可以，当成算力效率结论就过头了。

**τ²-bench 上基本没涨**。8B 从 11.5 到 12.3，0.8 个点；1.7B 在 Claw-Eval 上从 7.7 到 7.7，纹丝不动。论文用「improves or matches」带过，可「matches」在这里就是没涨。四个基准里交互式工具使用这一项恰恰最贴近「需要跟用户来回确认」的真实场景，而 L5 专门加了用户交互，结果这块收益最薄。这个错位我觉得论文没解释透，可能是 τ²-bench 的评测口径与合成任务的用户交互协议对不上，也可能是 355 条 L5 数据太少。

**跟前沿模型的差距别被省略**。Claw-Eval 上 CrossEnv-8B 是 23.6，Qwen3.8-Max 是 77.9、Kimi-K3 是 80.5，差三倍多；DeepPlanning 上 10.8 对 70.0。作者把这些放进表里当参照点，正文没怎么展开。这当然是模型尺寸的鸿沟，不算论文缺陷，但读者若只盯着「1.7B–8B 档里最高」这句话，很容易误判成整体够用。

**baseline 的可比性有暗坑**。EnvScaler-4B、Agent-World-4B/8B 是作者自己复现的，Agent-World 的实现当时没公开；复现质量、RL 步数（表里写的是 step50 的冻结 checkpoint）都会影响对比。这不是说结果不可信，而是「反超」这类措辞在数据效率本来就难对齐的情况下要留余量。

**泛化的口径偏松**。组合实验测的是「熟悉环境的新搭配」，不是全新服务；长工作流测到 24–28 次工具调用，但纵轴是检查通过占比而非端到端完成；相似度实验里散点负增益不少、置信区间跨零。三项都指向「有迁移迹象」，离「可靠泛化到真实跨服务场景」还有距离，作者自己在 Limitations 里也划了这条线。程序化环境把真实服务的接口漂移、噪声响应、复杂业务约束都简化了，这个 gap 是整条路线的共性，不是 CrossEnv 独有的，但它确实限制了结论能外推多远。

**训练信号与评测口径不一致**。前面提过，奖励是按检查通过率的增量给部分分，评测看的是严格成功率。Figure 3 里 L3「执行更多工具但通过更少检查」那个现象，我猜就跟这种部分分信号有关系——模型被鼓励多做事，但「多做事」和「做对整件事」在奖励里不是一回事。这块我自己也还在琢磨，论文没给更细的归因，可能我的理解有偏差。

剥开包装看本质：CrossEnv 没有提出新的 RL 算法、没有新模型结构，GRPO、课程学习、图引导合成、程序化验证都是现成零件。它真正的贡献是把「跨环境数据一致性」这个被绕开的工程问题，拆成图组合、任务级数据对齐、参考执行生成验证规则三步，并和五级课程拼成一条能规模化的流水线。系统整合，不是底层突破——但这不代表它不值钱。能把脏活标准化、还能给出 2,954 条可用训练数据，比很多「新方法涨 0.5 个点」的工作对工程更有用。

## 💡 工程启发与收尾

如果你也在给 Agent 造训练环境，这篇里有几个点可以直接搬：

用共享实体类型做环境之间的「接口契约」，比硬编码服务组合扩展性高得多——新环境只抽实体和关系、接进合成图，就能和老环境自动产生组合，边际成本递减那条曲线就是这么来的。数据对齐要跟参考动作**联合规划**，别先造库再写动作，否则「该由 Agent 创建的记录被提前塞进初始状态」这种泄漏会悄悄把任务变简单。验证规则从成功的参考执行里反推、再用负例反向测一遍，是让 RL 奖励不漂移的便宜办法；再加一道「5 次独立尝试至少 2 次成功」的门槛，能滤掉一大批看着合理其实不可解的任务。

课程这块，先单环境 SFT 打底、再按「环境数 → 业务域跨度 → 用户交互」逐级加难度，比一上来混着喂更省早期算力，Figure 4 的 rollout 曲线给了直接证据。不过别照抄它的隔离结论，作者自己都说了 batch 和并行度没对齐。

还有一个更本质的问题没解决：合成环境里的「一致性」是任务级、静态对齐出来的，真实服务的数据是动态变的、接口会改、响应带噪声。当 Agent 从「对齐好的快照」走向「随时在变的线上服务」，今天这套联合验证规则还灵不灵，论文没答，Limitations 也老实承认了。我倒觉得这才是跨环境 Agent 训练下一阶段真正要啃的骨头——把数据一致性从「合成时保证」挪到「运行时校验」，可能会是比再堆环境数量更值得走的方向。

回到 arXiv:2611.22777 这篇论文本身：值得花一小时读方法部分，实验部分带着上面的折扣看。它把一块没人愿意碰的工程泥地，整成了可复用的地基。
